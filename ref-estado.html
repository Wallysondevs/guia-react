Estado

Estado é a memória de um componente: o valor que sobrevive entre um desenho e outro e que, quando muda, manda o React desenhar de novo. Esta página é a consulta rápida do assunto — o par valor e setter, por que nunca se altera o valor na mão, como atualizar objeto e array sem mutar, o que é estado derivado, como o lote junta várias mudanças e onde o estado deve morar. A Ana começou com um contador de pães e chegou a um painel com carrinho, pedido e filtro; o que ela consulta antes de criar mais um useState está aqui.

Como usar esta página
  • Cada seção responde a uma dúvida que aparece no meio do código; as tabelas são o resumo.
  • As caixas rodam React 19 de verdade: edite, clique em Rodar e leia o painel.
  • Quando a dúvida for "onde guardo isso?", comece pela tabela da seção 1.

1. O que é estado

Estado é o dado que o componente guarda entre renders. Uma variável comum não serve: ela nasce de novo a cada chamada da função e volta ao valor inicial. O useState pede ao React que guarde o valor em um lugar que sobrevive — e devolve o valor atual junto com a função que o substitui.

function Contador() {
  const [paes, setPaes] = useState(0);

  return (
    <div>
      <p>pães: {paes}</p>
      <button onClick={() => setPaes(paes + 1)}>Somar um</button>
    </div>
  );
}

O estado é do componente, por instância. Dois <Contador /> na mesma tela têm contadores separados: cada um guarda o seu. E o estado morre quando o componente sai da tela — por isso recarregar a página zera tudo, e por isso existe localStorage quando o valor precisa durar mais.

Nem todo dado precisa de estado. Texto, número e booleano que a tela mostra e a pessoa altera, sim. Valor calculado a partir de outros, não. Valor que só controla bastidor — id de timer, elemento do DOM —, não. A tabela abaixo é o filtro inicial.

Uma pergunta resolve a maior parte: "se eu recarregar o componente, esse valor pode voltar ao início?" Se pode e ele aparece na tela, é estado. Se pode e ele não aparece, é ref ou variável. Se não pode, o lugar é o servidor ou o localStorage.

2. O par valor e setter

useState devolve um array de dois itens: o valor de agora e a função que pede a troca. Por convenção, o segundo se chama set mais o nome do primeiro — paes e setPaes. O valor é somente leitura: atribuir paes = 3 não muda a tela e ainda quebra o código, porque paes é uma constante.

Chamar o setter não muda a variável do render atual. Ele agenda um novo render com o valor novo; o render que está rodando continua vendo o valor antigo até terminar. Isso explica por que um console.log logo depois do setter mostra o valor velho — e por que a tela, no fim, mostra o novo.

estado
O valor que o React guarda entre renders: const [valor, setValor] = useState(inicial).
setter
A função que agenda a troca. Recebe o valor novo ou uma função que calcula a partir do atual.
render
A chamada da função do componente para produzir o JSX. Acontece de novo quando o estado muda.
retrato
O valor do estado durante um render. Ele não muda no meio do render, mesmo depois do setter.
updater
A forma de função no setter: setValor((v) => v + 1), que recebe o valor atual.

O valor inicial só é usado na montagem — mas a expressão entre parênteses é avaliada em todo render, e o resultado é descartado depois do primeiro. Se ela for caro de produzir — ler o localStorage, por exemplo —, passe uma função: useState(() => lerDoStorage()). Aí a leitura acontece uma vez só, na montagem, e não em cada desenho.

O valor pode ser de qualquer tipo: texto, número, booleano, objeto, array, null. O que ele não pode é ser confundido com uma variável comum. Uma variável declarada no corpo da função é recriada a cada render; mudá-la não avisa ninguém e a tela não acompanha. O teste é prático: se o valor precisa sobreviver ao próximo desenho, é estado; se ele é recalculado sempre, é variável local.

3. Atualizar: valor novo ou função

O setter aceita duas formas. Com um valor, ele substitui o estado por aquele valor. Com uma função, ele recebe o valor atual e devolve o próximo. A diferença aparece quando você chama o setter mais de uma vez no mesmo evento, ou quando a atualização depende do que já estava lá.

FormaExemploQuando usarAula
valor diretosetPaes(3)quando o novo valor não depende do antigoO useState

várias chamadassetPaes((p) => p + 1) duas vezesquando o mesmo evento muda o valor duas vezesAtualizações em Lote

O erro clássico é somar dois com setPaes(paes + 1) duas vezes. As duas chamadas leem o mesmo paes do render, calculam o mesmo resultado e o estado termina com um a mais, não dois. Com a forma de função, cada chamada recebe o resultado da anterior e a conta fecha.

O botão "Somar dois" soma 1, porque as duas chamadas leem o mesmo total. Troque por setTotal((t) => t + 1) nas duas e clique: o painel tem de mostrar total: 2.

function App() {
  const [total, setTotal] = useState(0);

  function somar() {
    setTotal(total + 1);
    setTotal(total + 1);
  }

  return (
    <div>
      <p>total: {total}</p>
      <button id="somar" onClick={somar}>Somar dois</button>
    </div>
  );
}

No painel do código inicial, um clique leva o total a 1. Na solução, leva a 2. Repare que o React fez um render só nos dois casos: as duas chamadas entram na mesma fila e são aplicadas em ordem. Com valor direto, a segunda sobrescreve a primeira; com função, a segunda parte do resultado da primeira.

4. Objeto e array: substituir, não mutar

O React decide se redesenha comparando o estado novo com o antigo por identidade. Um objeto ou array mutado é o mesmo objeto — então o React conclui que nada mudou e não desenha. A regra é sempre substituir por um valor novo, montado a partir do antigo.

// objeto: copia e sobrescreve
setPedido({ ...pedido, pago: true });

// array: copia e acrescenta
setItens([...itens, "rosca"]);

// array: filtra (já devolve novo)
setItens(itens.filter((i) => i !== "rosca"));

// array: atualiza um item
setItens(itens.map((i) => (i.id === id ? { ...i, pronto: true } : i)));

Objeto dentro de objeto pede cópia em cada nível que muda — { ...pedido, cliente: { ...pedido.cliente, nome } } —, porque o spread é raso. Array de objetos pede map para trocar um item e filter para remover. O que nunca entra é push, splice, sort no array original ou atribuição em estado.campo.

function App() {
  const [itens, setItens] = useState(["pão francês"]);

  function adicionar() {
    itens.push("rosca");
    setItens(itens);
  }

  return (
    <div>
      <p>itens: {itens.join(", ")}</p>
      <button id="add" onClick={adicionar}>Adicionar rosca</button>
    </div>
  );
}

No inicial, o clique não muda o painel: o array foi alterado por dentro, mas é o mesmo objeto e o React não vê motivo para desenhar. Pior, o estado guardado agora está diferente da tela — o próximo render, por qualquer outro motivo, mostra a rosca. Na solução, o array novo aparece na hora.

5. Estado derivado: não guarde o que dá para calcular

Se o valor sai de outro estado ou das props, ele não precisa de useState: calcule no render. Total de um pedido, lista filtrada, quantidade de itens selecionados, mensagem de erro — todos são contas feitas na hora do desenho, e o resultado fica sempre em dia, sem sincronização manual.

function Carrinho() {
  const [preco, setPreco] = useState(2.5);
  const [quantidade, setQuantidade] = useState(1);

  const total = preco * quantidade;              // derivado
  const vazio = quantidade === 0;                // derivado

  return (
    <div>
      <p>total: R$ {total.toFixed(2)}</p>
      {vazio && <p>Escolha pelo menos um pão</p>}
    </div>
  );
}

Guardar o derivado em estado cria duas fontes de verdade. Um dia o preço muda e o total não; no outro, o total muda e o preço não. O sintoma é sempre o mesmo: um número certo e outro errado na mesma tela. Se a conta é cara, o problema é de desempenho, não de estado — e a resposta é useMemo, não um segundo useState.

O caso mais traiçoeiro é copiar props para o estado. const [nome, setNome] = useState(props.nome) guarda o valor da primeira renderização e ignora as mudanças do pai. Se o valor vem de fora e precisa acompanhar, use a prop direto; se precisa de uma cópia independente e editável, o nome deve dizer isso — rascunho, nomeEditado — e a sincronização precisa ser consciente.

Listas filtradas e ordenadas são o exemplo mais comum de derivado. Guardar filtrados no estado obriga a atualizar a lista em dois lugares — quando o termo muda e quando o dado muda —, e é questão de tempo até um dos dois esquecer. Calculando no render, o filtro acompanha os dois de graça:

function Busca() {
  const [termo, setTermo] = useState("");
  const [paes, setPaes] = useState(PAES);

  const encontrados = paes.filter((p) =>
    p.nome.toLowerCase().includes(termo.toLowerCase())
  );

  return (
    <div>
      <input value={termo} onChange={(e) => setTermo(e.target.value)} />
      <p>{encontrados.length} encontrados</p>
    </div>
  );
}

Validação segue a mesma regra. As regras — nome preenchido, telefone com dígitos, e-mail com arroba — são contas feitas no render a partir do que a pessoa digitou. O único estado extra é "já tentou enviar?", que decide se a mensagem aparece. Guardar cada erro em um useState separado é o caminho mais curto para a mensagem de erro ficar na tela de um campo que já foi corrigido.

6. Lote, ordem e o momento do render

O React junta as atualizações feitas no mesmo evento e faz um render só. É o batching: dois setters em um clique produzem um desenho, não dois. As atualizações são aplicadas na ordem em que foram enfileiradas, e o render seguinte vê o resultado de todas.

Um console.log ajuda a ver o momento. O log do corpo do componente roda uma vez por render; o log dentro do handler roda antes, com o valor do render atual.

total no render: 0
total no render: 2

O primeiro render mostra 0. O clique enfileira duas somas, o React aplica as duas e faz um render com 2. Não existe um render intermediário com 1 — e é por isso que a tela não pisca. Se você precisa do valor novo imediatamente para outra conta, calcule antes: const proximo = total + 2.

No React 19 o lote é automático em todo lugar: clique, setTimeout, resposta de fetch e promessa. Antes, só eventos do React eram agrupados; hoje, três setters dentro de um then também produzem um render só. Isso é bom para desempenho e indiferente para a lógica — desde que cada atualização use a forma de função quando depende da anterior.

Uma consequência prática: não leia o estado logo depois do setter esperando o valor novo. Ele só existe no próximo render. E não chame setter durante o render — o React agenda um novo render, que chama o render de novo, que chama o setter, e o processo não termina.

function somar() {
  setTotal(total + 1);
  console.log(total);        // ainda o valor deste render
  console.log(total + 1);    // o valor que vai aparecer no próximo
}

Se você precisa do novo valor para outra conta no mesmo handler, calcule-o numa variável e use a variável. Se precisa do valor dentro da próxima atualização, use a forma de função. O que não funciona é ler o estado de novo logo depois do setter: a variável do render não muda.

7. Onde o estado mora

Todo estado tem um dono: o componente que chama o useState. Quem precisa do valor recebe por prop; quem precisa mudar recebe a função. Se dois irmãos precisam do mesmo dado, o dono sobe para o ancestral comum — é o "elevar o estado".

O estado local é o padrão e deve continuar sendo. Ele é simples de ler, de mover e de apagar. O estado elevado entra quando dois componentes precisam concordar sobre o mesmo valor. O contexto entra quando o valor precisa chegar a muitos lugares distantes sem passar por todo mundo — tema, idioma, usuário logado. Nenhum dos dois é "mais moderno": são ferramentas para distâncias diferentes.

function Pedido() {
  const [itens, setItens] = useState([]);   // dono é Pedido

  return (
    <div>
      <Lista itens={itens} aoAdicionar={setItens} />
      <Resumo itens={itens} />
    </div>
  );
}

Repare que setItens desce como prop. É legítimo e comum: o filho não sabe como o array é montado, só pede a troca. Se a regra de troca ficar complicada — adicionar, remover, limpar, aplicar desconto —, o par vira um useReducer, e o filho passa a receber dispatch, que é estável.

O exemplo clássico de elevar é o campo de busca com a lista ao lado. Se o campo e a lista são irmãos, nenhum dos dois pode guardar o termo sozinho: quem guarda é o pai, que passa o termo para um e a função de troca para o outro. O pai fica um pouco maior e os dois ficam simples — melhor do que duplicar o estado e sincronizar na mão.

function Busca() {
  const [termo, setTermo] = useState("");   // dono: o pai

  return (
    <div>
      <Campo termo={termo} aoMudar={setTermo} />
      <Resultados termo={termo} />
    </div>
  );
}

Há ainda uma decisão que não é de estado: o que pode ser recalculado. Antes de criar mais um useState, pergunte se o valor não é só uma conta com o que você já tem. A maior parte dos "estados demais" nasce de uma conta que ninguém quis fazer no render.

O laço infinito tem uma mensagem própria, que aparece no console do navegador e no painel:

Maximum update depth exceeded.

A leitura: um componente está pedindo atualização dentro do próprio render, ou um efeito está mudando um estado que ele mesmo observa. A primeira coisa a fazer é procurar setAlgo fora de handler e de efeito. A segunda é conferir o array de dependências do efeito — um objeto recriado a cada render faz o efeito rodar sempre.

Já a mutação não gera erro nenhum, e é por isso que ela é pior. Se a tela mostra um valor e o console mostra outro, desconfie de estado mutado antes de desconfiar do React. O teste é simples: o objeto novo é diferente do antigo? Se a resposta for não, o React não tem como saber que algo mudou.

Resumo

useState guarda um valor entre renders e devolve o par valor e setter. O valor é somente leitura e constante durante o render; o setter agenda um novo render. Para atualizações que dependem do valor atual — somar, remover, trocar um campo de objeto —, use a forma de função: setValor((v) => ...).

Objeto e array se substituem, nunca se mutam: spread para copiar, map e filter para transformar. O valor que sai de outro estado ou de props é derivado e se calcula no render, não em um segundo useState. O React junta as atualizações do mesmo evento em um render e aplica na ordem.

O estado mora no componente que precisa dele; irmãos pedem para o ancestral comum, e o contexto entra para distâncias grandes. Antes de criar mais um estado, pergunte: esse valor pode ser calculado? Ele aparece na tela? Ele precisa sobreviver ao render? As três respostas dizem se o lugar é estado, ref ou variável.

Para lembrar

  • const [valor, setValor] = useState(inicial); o setter agenda um render.
  • O valor é constante no render: o log depois do setter mostra o antigo.
  • Use setValor((v) => v + 1) quando a conta depende do atual.
  • Objeto e array: copie e sobrescreva; nunca push nem atribuição direta.
  • Estado novo igual ao antigo não redesenha — é o que a mutação provoca.
  • Total, filtro e validação são derivados: calcule no render.
  • Prop copiada para estado para de acompanhar o pai.
  • Vários setters no mesmo evento: um render, aplicado em ordem.
  • O dono do estado é quem chama o useState; os outros recebem prop.
  • Antes de mais um useState, pergunte se o valor não é conta.
