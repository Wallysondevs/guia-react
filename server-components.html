Server Components

A Ana descobriu que a página do catálogo manda dois mil pães para o navegador do cliente só para desenhar uma lista que ele nem pode alterar. O trabalho todo — buscar, ordenar, montar o HTML — acontece no aparelho de quem visita, e o servidor fica parado olhando. Nesta aula ela conhece o outro tipo de componente do React 19: aquele que roda no servidor, manda a tela pronta e nunca chega como JavaScript. As três caixas rodam aqui, no navegador, e simulam a fronteira para você ver o que passa e o que não passa por ela.

Você vai aprender
  • O que é um Server Component e por que ele não pesa no navegador.
  • Por que no servidor não existe “carregando”: os dados chegam prontos.
  • A fronteira do "use client" e o que ela separa.
  • O que atravessa por prop e o que nunca atravessa.
  • Por que estado e evento ficam sempre do lado do cliente.
  • Como um componente de servidor entra em um de cliente pelo children.
  • Quando vale usar — e por que isso pede um framework, não só o Vite.

1. A cena: dois mil pães viajando até o cliente

O catálogo da Ana tem dois mil itens. A página busca a lista, ordena por preço e desenha. Tudo isso acontece no navegador de quem visita: o JavaScript desce pela rede, roda, pede os dados, espera a resposta, mostra “carregando…” e só então pinta as linhas. No celular do balcão, entre o pedido e a primeira linha, passam-se quase dois segundos.

O desconforto da Ana não é com o React, é com o lugar. A lista é igual para todo mundo, não tem interação nenhuma e não muda enquanto a pessoa olha. Fazê-la no aparelho do cliente é repetir o mesmo trabalho em cada visita, gastar a bateria de cada visitante e ainda mandar os dois mil itens pela rede — sendo que a única coisa que a pessoa precisa receber é o HTML pronto.

É isso que o React 19 chama de Server Component: um componente que roda no servidor. Ele busca no banco, monta a lista, calcula o total e devolve o resultado já em JSX. O React transforma esse resultado em HTML e manda para o navegador. O código desse componente não vai junto: o cliente recebe a tela, não a receita.

A consequência mais visível é o tamanho do que desce. Um componente de cliente precisa do React, dos seus hooks e do seu código para funcionar; um de servidor não deixa nada disso no navegador. Em um site grande, isso é a diferença entre mandar 800 KB de JavaScript e mandar 80 — com a página aparecendo antes de qualquer script rodar.

2. Dois tipos de componente, uma fronteira

Até aqui, todo componente que você escreveu era de cliente: rodava no navegador, podia ter estado, podia responder a clique. O Server Component é o outro lado. Ele não tem estado, não tem efeito, não escuta evento e não conhece window, porque quando ele roda não existe navegador — existe um servidor, com acesso ao banco e ao disco.

Server Component
Componente que roda no servidor e não é enviado ao navegador como JavaScript. Pode ser async e buscar dados direto.
Client Component
Componente que roda no navegador, com estado, efeitos e eventos. É marcado com "use client".
fronteira
O ponto onde um componente de servidor desenha um de cliente. Tudo o que cruza passa por props.
serializável
O que consegue virar dados e ser reconstruído do outro lado: texto, número, lista, objeto simples, elemento React.
hidratação
O trabalho de o React assumir um HTML já pronto no navegador e ligar os eventos. Só acontece nos componentes de cliente.

A tabela abaixo é o resumo que vale colar no monitor. Repare que a maior parte das linhas é sobre o que não existe do lado do servidor — e é aí que mora quase todo erro de quem chega achando que é só “mover o componente para cima”.

Vale dizer o óbvio: você não escolhe “usar Server Components” como escolhe um hook. Quem tem componente de servidor é a aplicação, não a linha de código — e para isso a aplicação precisa de um servidor que saiba renderizar React. É o caso dos frameworks com App Router (Next.js, Waku, React Router com servidor). Um projeto criado com Vite puro, como o do Nível 3, é uma aplicação de cliente: os componentes todos rodam no navegador, e é assim que deve ser.

3. No servidor, os dados chegam prontos

Esta é a diferença que mais muda o código do dia a dia. No cliente, buscar dados é sempre uma coreografia: um estado para o resultado, um para o “carregando”, um efeito que dispara a busca e um desenho condicional que troca o aviso pela lista. No servidor, o componente espera os dados com await e devolve a lista — o “carregando” não existe, porque ninguém está esperando um desenho que já vai chegar pronto.

A caixa a seguir mostra os dois lados. O código inicial é a versão de cliente, com efeito e aviso de carregando; a solução é o mesmo componente recebendo os pães por prop, como faria um componente de servidor que buscou os dados antes de desenhar. Repare que a solução não tem estado nem efeito nenhum.

A lista passa por “carregando…” porque busca no efeito. Apague o estado e o efeito e receba os pães por prop: o componente deve desenhar as três linhas direto, sem passar pelo aviso.

const paes = [
  { id: 1, nome: "Pão francês", preco: 12 },
  { id: 2, nome: "Pão de queijo", preco: 8 },
  { id: 3, nome: "Croissant", preco: 14 }
];

function ListaDePaes() {
  const [carregando, setCarregando] = useState(true);
  const [itens, setItens] = useState([]);

  useEffect(() => {
    setTimeout(() => {
      setItens(paes);
      setCarregando(false);
    }, 400);
  }, []);

  if (carregando) return <p>carregando: sim</p>;

  return (
    <ul>
      {itens.map((p) => <li key={p.id}>{p.nome}</li>)}
    </ul>
  );
}

function App() {
  return (
    <div>
      <h1>Catálogo</h1>
      <ListaDePaes />
    </div>
  );
}

Na solução, o componente é uma função de quatro linhas que devolve uma lista. Não há useState, não há useEffect, não há if (carregando). Isso é o desenho de um componente de servidor: ele recebe os dados já resolvidos e devolve a tela. No projeto de verdade, esses dados viriam de um await na primeira linha, e o componente seria async.

export default async function Catalogo() {
  const paes = await buscarPaesNoBanco();   // roda no servidor, antes de desenhar

  return (
    <main>
      <h1>Catálogo</h1>
      <ListaDePaes paes={paes} />
    </main>
  );
}

Repare no que a função acima não tem: estado, efeito, try/catch de carregamento, nada disso. O await roda no servidor, e o que desce para o navegador é o resultado. Se a consulta falhar, quem trata é o servidor — o cliente recebe uma página de erro, não um “carregando” eterno.

4. A fronteira do use client

Um componente de servidor não consegue fazer tudo, e é aí que entra a marcação "use client". Ela fica na primeira linha de um arquivo e diz ao framework: “daqui para baixo, tudo é componente de cliente”. Tudo o que esse arquivo importar também vira cliente, mesmo que não tenha a marcação — a fronteira é o arquivo, não a função.

A regra de ouro é descer a marcação o mais fundo possível. Se a página inteira é "use client", você perdeu o benefício: o servidor volta a ser um repassador de dados e o navegador recebe todo o código. O desenho bom é a página de servidor com pequenos bolsões de cliente: o botão que compra, o campo que filtra, o menu que abre.

"use client";

import { useState } from "react";

export default function BotaoPedir({ nome }) {
  const [pedidos, setPedidos] = useState(0);

  return (
    <button onClick={() => setPedidos(pedidos + 1)}>
      pedir {nome} ({pedidos})
    </button>
  );
}

E o arquivo do servidor usa esse botão como se fosse uma tag comum, passando só o que ele precisa saber. O componente de servidor não sabe que existe estado do outro lado; ele entrega um nome, e o cliente cuida do resto. É a mesma ideia de props que você já conhece, com uma diferença importante: o que atravessa não pode ser qualquer coisa.

5. O que atravessa a fronteira

Aqui está o erro que mais aparece em quem está começando. Props que passam de um componente de servidor para um de cliente precisam ser serializáveis: precisam virar dados, viajar e ser reconstruídas do outro lado. Texto vai, número vai, lista vai, objeto simples vai. Função não vai — porque não existe um jeito de mandar “um pedaço de código” para o navegador sem mandar o código.

No console, o teste é rápido: transforme o objeto em texto e veja o que sobra. A função some sem aviso, e o objeto volta sem ela.

JSON.stringify({ nome: "Pão", preco: 12, formatar: (n) => n })
'{"nome":"Pão","preco":12}'

A caixa a seguir simula a viagem com JSON.stringify e JSON.parse, que é o transporte mais rígido que existe. A simulação é proposital: o transporte real do React aceita mais coisas, mas o que ele nunca aceita é função. Se o dado sobrevive ao JSON, sobrevive à fronteira; se desaparece ali, também desapareceria no projeto de verdade.

O cartão recebe uma função formatarPreco, e função não atravessa a fronteira: o preço fica “indisponível”. Tire a função e passe o preço já formatado em precoTexto, mantendo a chamada de atravessa.

function atravessa(props) {
  // simula a fronteira: só o que é serializável chega do outro lado
  return JSON.parse(JSON.stringify(props));
}

function Cartao({ dados }) {
  return (
    <div className="cartao">
      <h2>{dados.nome}</h2>
      <p>{dados.formatarPreco ? dados.formatarPreco(dados.preco) : "preço indisponível"}</p>
    </div>
  );
}

function App() {
  const dados = {
    nome: "Pão francês",
    preco: 12,
    formatarPreco: (valor) => "R$ " + valor + ",00"
  };

  return <Cartao dados={atravessa(dados)} />;
}

Na versão inicial, o painel mostra “preço indisponível”. A função existia no objeto, mas não sobreviveu à viagem: do outro lado, dados.formatarPreco é undefined. O conserto não é mandar a função “de outro jeito” — é mandar o dado pronto, que é o que a formatação produzia de qualquer forma.

No projeto de verdade, esse caso nem chega a desenhar: o React para com um erro dizendo que funções não podem ser passadas de um componente de servidor para um de cliente. A exceção é a função marcada com "use server" — as Server Actions, que têm uma aula própria nesta sequência e são a forma oficial de mandar “algo que faz” para o outro lado.

6. Estado e evento ficam do lado do cliente

A terceira consequência é a que mais muda a arquitetura. Componente de servidor não tem estado nem evento: ele é desenhado uma vez, no servidor, e o resultado é enviado como HTML. Um clique não muda nada nele, porque não há nada rodando do outro lado para reagir. Quem guarda o “quantos pedidos” e responde ao clique é o componente de cliente.

Por isso o padrão que aparece em todo app com Server Components é este: o componente de servidor busca os dados e desenha a estrutura; o componente de cliente, pequeno, fica com o estado e recebe uma função por prop para avisar o que aconteceu. Quem “manda” no dado continua sendo o cliente, mas só no pedacinho que precisa.

O cartão guarda o próprio contador, e o painel nunca sabe de nada — estado dentro de componente de servidor não existe. Tire o estado do cartão, receba aoPedir por prop e guarde a lista de pedidos no App.

function Cartao({ nome, preco }) {
  const [pedidos, setPedidos] = useState(0);

  return (
    <div className="cartao">
      <h2>{nome}</h2>
      <p>{"R$ " + preco + ",00"}</p>
      <button onClick={() => setPedidos(pedidos + 1)}>pedir</button>
      <p>{"neste cartão: " + pedidos}</p>
    </div>
  );
}

function App() {
  return (
    <div>
      <p>pedidos no painel: 0</p>
      <Cartao nome="Pão francês" preco={12} />
    </div>
  );
}

No código inicial, clicar aumenta “neste cartão”, e “pedidos no painel” fica em zero para sempre: o estado mora dentro do cartão e ninguém de fora o enxerga. Na solução, o cartão ficou sem estado — só desenha e chama —, e o número aparece no painel. Esse formato é o que atravessa a fronteira sem problema: dados descem por prop, eventos sobem por função.

Repare que a solução passa uma função (o aoPedir) do App para o Cartao. Isso é permitido porque os dois são componentes de cliente, no mesmo lado da fronteira. A regra da seção 5 vale para o que cruza de servidor para cliente — e é por isso que o cartão “de servidor” precisa ficar sem estado: ele não tem como receber comportamento, só dados.

7. O que o servidor não pode fazer

Vale uma lista do que não existe do lado do servidor, porque cada item é uma tentativa que quebra a página com uma mensagem diferente. Hooks: nada de useState, useEffect, useContext — o servidor não tem estado de componente nem ciclo de vida. Eventos: onClick, onChange são ignorados, porque não há navegador para clicar. APIs do navegador: window, document, localStorage não existem ali. Efeitos: timer, assinatura, qualquer coisa que dependa de tempo de vida da tela.

O que existe do lado do servidor: acesso ao banco, a arquivos, a variáveis de ambiente com segredo, a cabeçalhos da requisição, a cookies. É uma troca justa — o servidor ganha poderes que o cliente nunca teria e perde tudo o que é interativo. Quem tenta fazer um formulário inteiro no servidor descobre isso no primeiro onChange.

Quando o componente de servidor toca em algo do navegador, o erro aparece no terminal do servidor, não no console do cliente — e a mensagem é direta sobre o que faltou:

ReferenceError: window is not defined
    at Tema (app/tema.jsx:3:15)

Há um caso que costuma confundir: gerar um número aleatório ou a data de hoje no componente de servidor. Funciona, mas o valor fica congelado no HTML enviado — e se o mesmo HTML for reaproveitado em cache, dois visitantes veem o mesmo “agora”. O cliente, ao hidratar, pode calcular outra coisa, e a tela pisca ou diverge. Quando o valor depende do momento ou do aparelho, o lugar dele é o cliente.

8. Composição: o servidor dentro do cliente

Falta a peça que faz o desenho fechar: um componente de cliente não consegue importar um de servidor, mas consegue receber um pelo children. Você já sabe que children é o conteúdo entre as tags; aqui ele é o que permite montar um painel interativo que envolve conteúdo estático vindo do servidor.

import Abas from "./abas";                  // cliente: tem estado
import ListaDePaes from "./lista-de-paes";  // servidor: só desenha

export default async function Catalogo() {
  const paes = await buscarPaesNoBanco();

  return (
    <Abas>
      <ListaDePaes paes={paes} />
    </Abas>
  );
}

O componente Abas é de cliente: ele guarda qual aba está aberta e desenha o botão. Não sabe o que está dentro; só decide quando mostrar. A lista continua sendo de servidor — o código dela nunca desce para o navegador, mesmo estando dentro de um componente de cliente. Essa é a composição que resolve o caso “preciso de interação em volta de conteúdo que não deveria pesar”.

É o mesmo raciocínio do children que você aprendeu no Nível 1, com uma consequência nova: o React não precisa mover o conteúdo entre lados, porque o conteúdo já foi resolvido no servidor. O cliente recebe um elemento pronto, com um espaço para ele. Por isso a regra “passe como children, não importe” é tão repetida na documentação de Server Components.

9. Cenários do dia a dia

Cenário 1: a página inteira marcada como cliente

A Ana pôs "use client" no topo do arquivo da página para poder usar um botão. O botão funcionou e o ganho desapareceu: o arquivo da página importa a lista, e a marcação transformou lista, cabeçalho e rodapé em cliente. A correção foi mover a marcação para o arquivo do botão — três linhas de cliente em uma página que continua sendo de servidor.

Cenário 2: a função que sumiu no caminho

Ela passou formatarPreco por prop para o cartão e recebeu “indisponível” na tela. Função não atravessa a fronteira sem "use server". O conserto foi formatar no servidor e mandar o texto pronto — o que também deixou o cartão mais simples. Quando o dado é o que importa, mande o dado; comportamento só quando ele precisa acontecer no cliente.

Cenário 3: o localStorage que não existe no servidor

Ela copiou o componente de tema, que lia localStorage, para a página de servidor, e o build quebrou com “localStorage is not defined”. Não é limitação do React: no servidor não há armazenamento do navegador. O tema virou um componente de cliente, e a página de servidor passou a receber só o nome do tema escolhido.

Complete as duas linhas. Na primeira, a marcação que transforma um arquivo em componente de cliente; na segunda, o tipo de valor que nunca atravessa a fronteira por prop:

"use "; // o que não atravessa:

Dica: a primeira resposta é a palavra que vem depois de use, em inglês, minúscula. A segunda é o tipo de valor que representa comportamento — o que o servidor não consegue enviar para o navegador sem mandar código junto.

11. Resumo

Server Component é o componente que roda no servidor e não é enviado ao navegador. Ele pode ser async, busca no banco, lê arquivo e nunca usa hook nem evento. O cliente recebe o HTML pronto — e o ganho aparece no tamanho do JavaScript e na hora em que a página fica visível. No servidor não existe “carregando”: os dados chegam resolvidos antes do desenho.

A fronteira é o arquivo marcado com "use client", que transforma em cliente tudo o que ele importa. Desça essa marcação até o menor componente possível. O que cruza de servidor para cliente precisa ser serializável: texto, número, lista, objeto simples e elemento React passam; função e instância de classe não, a não ser que a função seja uma Server Action.

Estado e evento ficam do lado do cliente, sempre. O padrão é o de sempre: dados descem por prop, eventos sobem por função — só que agora cada lado tem o seu papel. E a composição resolvida com children permite pôr um componente de servidor dentro de um de cliente sem trazer código junto.

Por fim, o aviso prático: aplicação com Server Components é aplicação com servidor renderizando React. O projeto de Vite do Nível 3 é de cliente, e isso não é uma falha — é um tipo diferente de projeto. Saber a diferença evita passar a tarde procurando um "use client" que aquele projeto não tem.

Para lembrar

  • Server Component roda no servidor e não manda código para o navegador.
  • Pode ser async; não tem useState, useEffect nem onClick.
  • No servidor os dados chegam prontos: sem estado de “carregando”.
  • "use client" na primeira linha do arquivo marca a fronteira para tudo o que ele importa.
  • Props entre servidor e cliente precisam ser serializáveis; função não passa.
  • "use server" é a exceção que permite mandar comportamento (Server Actions).
  • Estado e eventos moram no cliente; dados descem, eventos sobem.
  • Cliente não importa servidor, mas recebe servidor por children.
