Erros Comuns

Numa semana, a Ana caçou três bugs que pareciam impossíveis: a lista que não atualizava, o preço que ficava velho e a marcação que pulava de linha. Nenhum deles deu mensagem de erro. Todos eram o mesmo tipo de problema — uma ideia errada sobre o que o React compara para decidir redesenhar. Nesta aula ela aprende a reconhecer os três pelo sintoma e a corrigir sem tentativa e erro.

Você vai aprender
  • Por que a maioria dos erros de React não aparece no console.
  • O que é mutação de estado e por que o React não percebe.
  • Por que um estado que copia a prop nunca acompanha a prop.
  • O que a key realmente faz e por que o índice é uma escolha ruim.
  • Como o React compara o valor antigo com o novo.
  • Outros cinco erros silenciosos que aparecem em todo projeto.
  • Um roteiro de investigação para achar o culpado em minutos.

1. A cena: três bugs sem mensagem

O primeiro: a Ana clicava em “Adicionar pão” e nada acontecia na tela. O console mostrava o array com dois itens; a lista continuava com um. O segundo: o preço ficava sempre no valor antigo, mesmo quando o pai mandava outro. O terceiro: ela marcava a primeira linha da lista, removia aquela linha e a segunda aparecia marcada, sem ninguém ter marcado.

Os três têm uma coisa em comum: o código roda sem erro. Não há exceção, não há aviso, não há tela vermelha. O React fez exatamente o que foi mandado, e o resultado ficou errado porque a instrução estava errada. É o tipo de bug que faz a pessoa concluir “React é imprevisível” — quando o problema é uma regra que ninguém contou.

A regra é uma só, e vale para os três casos: o React compara referências, não conteúdos. Ele guarda o valor antigo de cada estado, compara com o novo usando igualdade de referência e decide se redesenha. Array, objeto e função são comparados pelo endereço na memória — não pelo que estão por dentro. Quem mexe no mesmo objeto e devolve o mesmo endereço não mudou nada, aos olhos do React.

2. As palavras que explicam os bugs

Cinco termos dão nome ao que você vai ver nesta aula. Eles aparecem em toda documentação e em toda conversa de trabalho, então vale fixar agora.

mutação
Alterar o objeto ou array que já está no estado: lista.push(x), objeto.nome = "Ana". A referência continua a mesma.
estado derivado
Um estado que poderia ser calculado a partir de outro. Guardar uma cópia costuma criar duas versões que se desencontram.
key
O identificador que o React usa para saber qual item da lista é qual entre um desenho e outro.
closure velha
Uma função que guardou o valor de um estado de um desenho anterior. Ela lê o passado, não o presente.
efeito sem retorno
Um useEffect que cria algo (timer, listener, pedido) e não devolve a função que desfaz.
identidade
O que faz o React tratar dois valores como “o mesmo”. Para objetos, é o endereço.

Há uma diferença importante entre “errado” e “mutado”. Um valor errado é um valor calculado mal: o React redesenha, você vê o resultado e corrige a conta. Um valor mutado é um valor que não mudou de identidade, então o React nem tenta redesenhar. O primeiro bug se vê; o segundo se procura. É por isso que esta aula insiste tanto em referência antes de mostrar código.

Repare que nenhuma dessas palavras fala de biblioteca ou de ferramenta. São conceitos de JavaScript: referência, cópia, identidade. O React só usa essas regras para decidir o que redesenhar. Quem entende de referência entende metade dos bugs de React.

Vale também saber por que o console fica quieto. Em produção, o React remove quase todos os avisos de desenvolvimento para a página ficar menor e mais rápida. Um erro que apareceria no seu notebook pode não aparecer no site publicado — e vice-versa. Por isso o roteiro de investigação da seção 8 não depende de mensagem: depende de comparar o que você esperava com o que a tela mostra.

3. A caixa: a lista que não muda

O clássico número um. A função adiciona um item com push — que altera o array original — e depois entrega esse mesmo array ao setPaes. Para o React, o valor novo é o valor antigo: mesma referência, nenhum redesenho.

O clique adiciona o pão ao array, mas a tela não muda. Troque o push por um array novo — paes.concat("Pão de queijo") — e clique em Adicionar pão.

function App() {
  const [paes, setPaes] = useState(["Pão francês"]);

  function adicionar() {
    paes.push("Pão de queijo");
    setPaes(paes);
  }

  return (
    <div>
      <button onClick={adicionar}>Adicionar pão</button>
      <ul>{paes.map(function (pao) { return <li key={pao}>{pao}</li>; })}</ul>
    </div>
  );
}
<div>
  <button>Adicionar pão</button>
  <ul>
    <li>Pão francês</li>
  </ul>
</div>

Depois do conserto, o clique muda a tela porque concat devolve um array novo. O antigo continua intacto, e o React vê duas referências diferentes. O mesmo vale para objeto: em vez de pedido.status = "pago", escreva setPedido({ ...pedido, status: "pago" }). O espalhamento cria um objeto novo com os campos antigos e o campo trocado.

Uma consequência que confunde: a mutação “funciona” em outros lugares. Se outro estado mudar no mesmo clique, o React redesenha e a lista aparece com o item novo — porque o desenho aconteceu por outro motivo. Isso cria o pior tipo de bug: o que funciona às vezes. A regra é nunca alterar o que está no estado, nem “só para testar”.

4. A caixa: o preço que ficou velho

O segundo clássico é mais sutil porque o código parece cuidadoso: o componente guarda o valor recebido num estado, “para poder mudar depois”. O problema é que o useState(valor) usa o valor apenas na primeira renderização. Nas seguintes, ele devolve o que está guardado e ignora a prop nova.

O botão muda o valor no pai, mas o preço continua 10. Pare de copiar a prop para o estado: use valor direto no componente e clique em Mudar o preço.

function Preco({ valor }) {
  const [preco, setPreco] = useState(valor);
  return <p>{"R$ " + preco + ",00"}</p>;
}

function App() {
  const [valor, setValor] = useState(10);
  return (
    <div>
      <button onClick={function () { setValor(valor === 10 ? 12 : 10); }}>Mudar o preço</button>
      <Preco valor={valor} />
    </div>
  );
}
<div>
  <button>Mudar o preço</button>
  <p>R$ 10,00</p>
</div>

function Preco({ valor }) {
  const preco = valor;
  return <p>{"R$ " + preco + ",00"}</p>;
}

function App() {
  const [valor, setValor] = useState(10);
  return (
    <div>
      <button onClick={function () { setValor(valor === 10 ? 12 : 10); }}>Mudar o preço</button>
      <Preco valor={valor} />
    </div>
  );
}

A correção é apagar o estado. Se o valor vem de fora e o componente não precisa mudá-lo, ele é prop e pronto — derivar não é guardar. Guardar cópia de prop cria duas fontes de verdade: a prop, que muda, e o estado, que fica. Quem lê o código vê duas variáveis parecidas e não sabe qual manda.

Existe um caso em que copiar faz sentido: quando o valor inicial é só um ponto de partida e a pessoa pode editá-lo sem avisar o pai — um formulário de rascunho, por exemplo. Mesmo aí, o nome ajuda: useState(valorInicial) deixa claro que aquilo é semente, não espelho. E se a prop precisar recomeçar o estado, o caminho é uma key no componente, não um efeito que copia.

5. A caixa: a marcação que pulou de linha

O terceiro é o erro que ninguém acredita até ver. Cada linha tem o próprio estado de “marcado”, e a lista usa key={i}, o índice. Quando a primeira linha sai, a segunda passa a ocupar a posição zero — e o React entrega a ela o estado que era da primeira.

Marque o primeiro pão, remova o primeiro e veja a marcação ficar na linha errada. Troque key={i} por key={pao} e repita a operação.

function Linha({ pao }) {
  const [marcado, setMarcado] = useState(false);
  return (
    <li className={marcado ? "marcado" : ""}>
      {pao} <button className="marcar" onClick={function () { setMarcado(true); }}>Marcar</button>
    </li>
  );
}

function App() {
  const [paes, setPaes] = useState(["francês", "queijo"]);
  return (
    <div>
      <button className="remover" onClick={function () { setPaes(paes.slice(1)); }}>Remover o primeiro</button>
      <ul>
        {paes.map(function (pao, i) { return <Linha key={i} pao={pao} />; })}
      </ul>
    </div>
  );
}
<div>

  <ul>

      francês
      <button class="marcar">Marcar</button>
    </li>

      queijo

</div>

A key não é um detalhe de lista: é a identidade do item. Com o índice, a identidade é a posição — e posição muda quando alguém remove ou reordena. Com o nome do pão, a identidade acompanha o item, e o estado vai junto. Em dados de verdade, use o id que veio do servidor; o nome serve quando ele é único e estável.

Uma regra que evita o problema: a key precisa ser estável, única entre irmãos e independente da ordem. Índice só é aceitável quando a lista nunca muda de ordem nem perde itens — uma lista fixa de meses, por exemplo. Em qualquer lista que cresce, encolhe ou é ordenada, use o identificador do dado.

6. O catálogo dos silenciosos

Os três da aula são os mais comuns, mas não são os únicos. Estes cinco aparecem em todo projeto e quase nunca dão mensagem clara.

O que você escreveuO sintomaO conserto
estado atualizado dentro do renderredesenho infinito, às vezes “Maximum update depth”calcular no corpo ou atualizar em evento/efeito
useEffect sem lista de dependênciaso efeito roda em todo desenho[] ou as dependências reais
efeito que busca dados sem cancelarresposta velha sobrescreve a novalimpar no retorno do efeito
objeto novo inline numa prop de memoo filho redesenha semprecriar fora do JSX ou memorizar
componente definido dentro de outro componenteo filho desmonta e perde o estado a cada desenhomover a definição para fora

A última linha merece um exemplo, porque o efeito é dramático. Se você escreve function Dentro() { … } dentro do corpo de App, cada desenho cria uma função nova. Para o React, é um tipo de componente diferente — então ele desmonta o anterior e monta outro. Todo o estado interno do filho se perde, e os efeitos rodam de novo. A cura é sempre mover a definição para fora da função do pai.

Vale um comentário sobre o memo, que aparece na quarta linha. Memorizar um componente só ajuda quando as props continuam iguais entre um desenho e outro. Passar um objeto criado direto no JSX cria uma referência nova a cada desenho, e o filho redesenha sempre — o memo vira decoração. A aula de O memo mostra como medir antes de memorizar.

Já as duas primeiras linhas pertencem à mesma família: efeito que faz demais. Um useEffect sem dependências roda depois de cada desenho, e se ele atualiza um estado, provoca outro desenho, que provoca outro efeito. O React interrompe depois de algumas dezenas de voltas com a mensagem “Maximum update depth exceeded”, que é o único aviso desta lista que você vai ver de fato.

7. O que grita e o que sussurra

Vale separar os erros em dois grupos, porque a estratégia de investigação é diferente. Os que gritam interrompem o desenho e deixam a tela vazia; os que sussurram produzem uma tela quase certa.

GrupoExemplosComo achar
gritamcomponente com nome errado, undefined no lugar de componente, erro de sintaxea mensagem aponta o arquivo e a linha
sussurrammutação, estado copiado, key por índice, closure velhacomparar o esperado com o desenhado, com log no ponto certo

8. O roteiro de investigação

Para os que sussurram, o log precisa estar no lugar certo. Logar no componente que usa o dado, não no que repassa, é o que separa “não chegou” de “chegou e eu desenhei errado”. E imprimir a referência, não só o conteúdo, revela mutação na hora:

function App() {
  const [paes, setPaes] = useState(["Pão francês"]);

  function adicionar() {
    console.log("antes: " + paes.length + " item(ns)");
    paes.push("Pão de queijo");
    console.log("depois: " + paes.length + " item(ns)");
    setPaes(paes);
  }
  console.log("desenhando com " + paes.length + " item(ns)");
  return <button onClick={adicionar}>Adicionar pão</button>;
}

Com um clique, o console mostra o desencontro sem nenhuma ambiguidade:

antes: 1 item(ns)
depois: 2 item(ns)
desenhando com 1 item(ns)

O array tem dois itens, e o React desenhou com um. Isso só acontece quando o valor entregue ao set é o mesmo objeto de antes. Se o log dissesse “desenhando com 2”, o problema estaria no JSX — e a investigação mudaria de lado.

O outro extremo é o desenho disparado em laço. Quando um efeito atualiza estado sem parar, o React interrompe e mostra no console a única mensagem desta aula que aparece em produção:

Maximum update depth exceeded. This can happen when a component repeatedly calls setState inside useEffect.

“Profundidade máxima de atualização excedida” — traduzindo: um desenho pediu outro, que pediu outro. As causas comuns são três: efeito sem lista de dependências que atualiza estado, efeito que atualiza um estado que está na própria lista de dependências e set chamado no corpo do render. Em todos, a saída é a mesma pergunta: quem deveria ser o dono deste valor? Se for o pai, o estado vai para lá; se for cálculo, vira constante no corpo.

9. Cenários do dia a dia

Cenário 1: a encomenda que aparecia duas vezes

Ao adicionar um pão, a lista mostrava o item duplicado. O culpado era um push dentro de um laço que rodava duas vezes no modo de desenvolvimento. A mutação não era só invisível: ela acumulava. Depois do conserto com concat, cada clique produzia exatamente um item novo.

Cenário 2: o cliente que trocava e o cupom que não

O componente de cupom copiava o nome do cliente para um estado. Quando a pessoa entrava com outra conta, o cupom continuava no nome antigo. O useEffect que “sincronizava” os dois rodava depois de cada desenho e criava um laço. A solução foi apagar o estado e ler a prop direto.

Cenário 3: a lista de encomendas que embaralhava os checks

As encomendas eram desenhadas com key={i}. Ao filtrar por “entregues”, os checkboxes marcados pulavam para outras linhas. Trocar a chave pelo número do pedido resolveu — e mostrou que o problema existia desde o começo, só não tinha aparecido porque ninguém removia item da lista.

Exercício: a chave estável

A lista de pães precisa de uma key que acompanhe o item. Complete a expressão.

paes.map(function (pao) { return <li key={}>{pao.nome}</li>; })

Dica: é o identificador que vem do servidor, não a posição na lista. Com ele, remover ou ordenar não embaralha o estado de cada linha.

11. Resumo

Quase todo bug silencioso de React nasce da mesma confusão: o React compara referências. Mudar o array com push mantém a referência e não redesenha; criar outro com concat ou espalhamento muda e redesenha. Copiar prop para estado guarda o valor do primeiro desenho e ignora os seguintes; ler a prop direto acompanha sempre.

A key é a identidade do item, não um número de ordem. Índice muda quando a lista muda, e o estado de cada linha vai junto para o lugar errado. Use o id do dado. E deixe o useEffect para o que é de fora do React: timer, listener, pedido — sempre com o retorno que desfaz.

Para investigar, compare o esperado com o desenhado e logue no ponto certo, imprimindo o tamanho ou o conteúdo antes e depois da atualização. Quando o log mostra o dado novo e a tela mostra o velho, o problema é referência. Quando mostra os dois iguais, o problema é o JSX. Na próxima aula o assunto é a ferramenta que revela esses bugs no modo de desenvolvimento: O Strict Mode.

Para lembrar

  • O React compara referências; array e objeto contam pelo endereço.
  • push e atribuição direta são mutação: não redesenham.
  • concat, espalhamento e map criam valor novo.
  • useState(prop) usa a prop só na primeira vez.
  • Se o valor vem de fora e não muda aqui, é prop — não estado.
  • key é identidade: use id, não índice.
  • Definir componente dentro de componente recria o tipo e perde o estado.
  • Efeito sem retorno deixa timer, listener e pedido vivos.
  • Log no componente que usa o dado mostra se o problema é acima ou abaixo.
  • “Maximum update depth exceeded” é o aviso de estado atualizado em laço.
