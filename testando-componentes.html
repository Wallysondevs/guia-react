Testando Componentes

Toda entrega do site da padaria passa pelo mesmo ritual: a Ana abre a página, clica em tudo, digita nos campos, troca de aba e diz “acho que está bom”. Na semana passada ela esqueceu de abrir a lista vazia, e foi justamente a lista vazia que o cliente viu primeiro. Testar componentes é transformar esse ritual em código que roda sozinho, em segundos, e que não esquece o caso que você esqueceu.

Você vai aprender
  • O que é um teste, uma asserção e um teste que confere comportamento.
  • Como testar uma função pura sem nenhuma biblioteca, com um runner de vinte linhas.
  • Como montar um componente de verdade, clicar nele e conferir o que apareceu.
  • O que o React faz no navegador quando você renderiza fora da tela e por que o teste precisa de flushSync.
  • Quais testes escrever primeiro e quais casos costumam ficar de fora.
  • Como achar um elemento por papel e nome em vez de por classe CSS.
  • O que torna um teste frágil — e por que teste frágil é pior do que teste nenhum.

1. A cena: a lista vazia que ninguém testou

O site da Ana tem uma página de encomendas com uma lista de pães reservados. Quando havia pães, tudo funcionava. Quando não havia, aparecia um espaço branco do tamanho de uma caixa e nada mais — nem uma frase, nem um aviso. Quem abria a página pela primeira vez concluía que o site estava quebrado e ia embora. O erro estava lá desde o começo; ninguém tinha visto porque ninguém abre a lista vazia de propósito.

A Ana já sabia conferir o que fazia. O problema não era falta de cuidado, era falta de repetição: cada conferência era feita uma vez, à mão, no dia da entrega, e nunca mais. Uma conferência que não se repete não protege nada. Na aula anterior você viu o Strict Mode denunciando efeito sem limpeza; agora o assunto é o outro tipo de rede de segurança, a que continua funcionando quando você muda o código seis meses depois.

Testar componente é isso: escrever, em código, o que o usuário deve ver e fazer, e deixar a máquina conferir. O teste não substitui o olho humano, mas ele nunca esquece e nunca está com pressa. E o melhor: ele conta a história do componente para quem chegar depois — inclusive para você mesmo, daqui a um ano.

2. As peças de um teste

Três palavras resolvem quase tudo. O teste é um bloco com nome que prepara uma situação, executa uma ação e confere um resultado. A asserção é a linha que diz o que deveria ser verdade — é ela que falha quando algo muda. E o runner é o programa que encontra os testes, roda todos, conta quantos passaram e mostra o motivo de cada falha.

teste
Um bloco com nome, do tipo “soma um a cada clique”. Prepara, age e confere. Roda isolado dos outros.
asserção
A comparação que precisa ser verdadeira: “o texto da tela é Pedidos: 1”. Se for falsa, o teste falha.
runner
Quem organiza e executa os testes. No ecossistema React, o mais comum hoje é o Vitest; o npm test do projeto chama ele.
teste de componente
Monta o componente num navegador simulado, interage como o usuário e confere o que aparece na tela.
teste frágil
Teste que quebra quando você muda algo que o usuário não vê: uma classe CSS, um nome de estado, a estrutura das divs.
comportamento
O que a tela mostra e o que acontece quando a pessoa age. É o que um bom teste confere — não os detalhes internos de como o componente chegou lá.

O resto é vocabulário de ferramenta. Você vai ver describe para agrupar, it ou test para declarar um caso, expect para a asserção e beforeEach para preparar algo antes de cada teste. São nomes diferentes para as mesmas três ideias. A que importa nesta aula é a asserção: um teste sem asserção de verdade passa sempre e não protege nada.

Comece pelo mais simples. Uma função que formata preço não tem estado, não tem tela e não tem efeito: dado um número, devolve um texto. Se ela errar, o erro aparece em três lugares da padaria ao mesmo tempo. Testar essa função é escrever a entrada, escrever a saída esperada e comparar.

3. A caixa: testando uma função pura

A caixa abaixo traz um runner mínimo, do tipo que cabe numa tela: uma variável que conta os testes, uma função teste que roda o caso dentro de um try e uma função conferir que lança erro quando a condição é falsa. O componente testado é o formatador de preço da padaria. Rode e veja o resultado.

O formatador devolve R$ 12 e o teste espera R$ 12,00. Conserte a função para que o teste passe e o painel mostre “1 de 1”.

let passou = 0;
let total = 0;

function teste(nome, fn) {
  total = total + 1;
  try {
    fn();
    passou = passou + 1;
  } catch (erro) {
    // o teste falhou: no console apareceria o motivo
  }
}

function conferir(condicao, mensagem) {
  if (!condicao) throw new Error(mensagem);
}

function formatarPreco(valor) {
  return "R$ " + valor;
}

teste("12 vira R$ 12,00", function () {
  conferir(formatarPreco(12) === "R$ 12,00", "esperava R$ 12,00");
});

function App() {
  return <p>{passou} de {total} testes passaram</p>;
}

O painel mostra “0 de 1” no código inicial e “1 de 1” depois da correção. Repare no desenho: o resultado do teste não aparece na tela por mágica — o App lê as variáveis passou e total depois que os testes já rodaram. Num projeto de verdade, quem lê esses números é o runner, que imprime uma lista no terminal e devolve um código de saída: zero quando tudo passa, um quando algo falha. É esse código que a esteira de integração contínua consulta antes de publicar.

Duas escolhas do runner valem comentário. A primeira é o try: um teste que lança erro não derruba os outros, e o runner continua até o fim para te mostrar o quadro completo. A segunda é a mensagem: conferir recebe um texto que diz o que era esperado. Sem isso, a falha vira “false is not true” e você perde dez minutos descobrindo qual comparação quebrou.

Uma função pura não precisa de navegador, de React nem de nada: é o teste mais barato que existe e o primeiro que você deve escrever. Formatação de preço, cálculo de frete, filtro de busca, validação de telefone, conversão de data — tudo isso vive fora do componente, em arquivos comuns, e pode ser testado em milissegundos.

4. A caixa: testando um componente de verdade

Agora o teste precisa de tela. A caixa monta o componente num div que nunca entra na página, procura o botão, dispara um clique e confere o texto. É o mesmo caminho que as bibliotecas fazem por baixo — só que escrito à mão, para você ver as peças.

O botão soma no estado errado: o teste do clique falha e o painel mostra “1 de 2”. Conserte o onClick para que os dois testes passem.

let passou = 0;
let total = 0;

function teste(nome, fn) {
  total = total + 1;
  try {
    fn();
    passou = passou + 1;
  } catch (erro) {
    // falhou
  }
}

function conferir(condicao, mensagem) {
  if (!condicao) throw new Error(mensagem);
}

function montar(elemento) {
  const caixa = document.createElement("div");
  ReactDOM.flushSync(function () {
    ReactDOM.createRoot(caixa).render(elemento);
  });
  return caixa;
}

function Botao() {
  const [n, setN] = useState(0);
  const [enviados, setEnviados] = useState(0);
  return (
    <button onClick={function () { setEnviados(enviados + 1); }}>Pedidos: {n}</button>
  );
}

teste("mostra zero no começo", function () {
  const tela = montar(<Botao />);
  conferir(tela.textContent === "Pedidos: 0", "esperava Pedidos: 0");
});

teste("soma um a cada clique", function () {
  const tela = montar(<Botao />);
  const botao = tela.querySelector("button");
  ReactDOM.flushSync(function () {
    botao.dispatchEvent(new MouseEvent("click", { bubbles: true }));
  });
  conferir(tela.textContent === "Pedidos: 1", "esperava Pedidos: 1");
});

function App() {
  return <p>{passou} de {total} testes passaram</p>;
}

O primeiro teste passa nos dois casos, porque o estado inicial já estava certo. O segundo falha, e falha pelo motivo certo: o botão atualiza enviados, um estado que ninguém mostra na tela, enquanto o texto lê n. A tela continua em “Pedidos: 0” depois do clique. O teste encontrou o bug em duas linhas — e sem abrir o navegador à mão.

Sobre o montar: ele cria um div solto, chama ReactDOM.createRoot e renderiza. Esse div nunca é anexado ao documento, então nada aparece na página de verdade e o teste não interfere no que o leitor está vendo. Já o ReactDOM.flushSync é a peça que garante que o React terminou de desenhar antes da próxima linha. Sem ele, o React pode agendar o desenho para depois e a asserção roda com a tela vazia — o teste falha e você culpa o componente errado.

Em projetos com Testing Library, esse trabalho está empacotado. O teste real fica assim:

import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { expect, test } from "vitest";
import Botao from "./Botao.jsx";

test("mostra zero no começo", () => {
  render(<Botao />);
  expect(screen.getByRole("button", { name: "Pedidos: 0" })).toBeInTheDocument();
});

test("soma um a cada clique", async () => {
  render(<Botao />);
  await userEvent.click(screen.getByRole("button", { name: "Pedidos: 0" }));
  expect(screen.getByRole("button", { name: "Pedidos: 1" })).toBeInTheDocument();
});

Compare com a caixa. render é o montar; screen é o div que você procuraria; getByRole é o querySelector que procura por papel e nome acessível; userEvent.click é o clique com flushSync embutido; e expect é o conferir. As bibliotecas também embrulham cada interação em act, uma função do React que avisa “vou mexer no estado agora, termine de desenhar antes de eu conferir”. Você não precisa escrever isso à mão, mas precisa saber que existe: é o motivo pelo qual o teste espera o clique com await.

O data-modo da caixa é automático: o motor desta página roda o código sem Testing Library, então montar faz o papel dela. O importante não é decorar a caixa; é reconhecer as quatro etapas em qualquer ferramenta — preparar, renderizar, agir, conferir.

5. A caixa: o teste que encontra o caso esquecido

O caso da lista vazia é o mais fácil de deixar de fora, porque ele não aparece enquanto você desenvolve com dados de exemplo. A caixa escreve três testes para a lista: um para o vazio, um para a quantidade e um para o nome. Rode.

A lista vazia não avisa nada, e o primeiro teste falha: “2 de 3”. Faça o componente mostrar Nenhum pão por aqui quando não houver pães.

teste("avisa quando não há pão", function () {

Os dois últimos testes passam no código inicial: a lista com dois pães desenha dois itens e mostra o nome. Só o primeiro falha, e ele é o que o cliente encontrou. O valor do teste não está em provar que o componente funciona — está em provar que ele funciona no caso que você não ia lembrar de abrir.

Repare também no tipo de asserção. Nenhum teste olha para o estado interno da Lista, para o nome da função ou para a classe CSS: eles olham para o texto e para a quantidade de itens. Isso importa porque o teste precisa continuar valendo quando você mudar a implementação. Se amanhã a lista passar a usar useMemo ou um componente Item, os testes continuam iguais; se amanhã ela parar de avisar o vazio, os testes quebram na hora.

Escrever o teste antes do código — a tal de TDD — é opcional, mas escrever o teste junto com o caso que você acabou de consertar não é. Todo bug que chega na mão da Ana merece um teste que falharia se ele voltasse. É um investimento de dez minutos que impede a reincidência.

6. Que tipo de teste escrever

Existem camadas, e elas custam preços diferentes. O teste de função pura roda em milissegundos e não sabe nada de tela. O teste de componente monta o React, espera o desenho e interage. O teste de ponta a ponta abre um navegador de verdade, navega entre páginas e conversa com o servidor. Quanto mais alto o nível, mais confiança ele dá e mais lento e frágil ele fica.

TipoO que cobreVelocidadeQuantos escrever
função puraformatação, cálculo, validação, filtromilissegundostodos os casos de borda
componenteo que aparece na tela e o que o clique fazdezenas de milissegundosos fluxos de cada tela

ponta a pontao site inteiro num navegador de verdadesegundospoucos: login, encomenda, pagamento

A proporção saudável é uma pirâmide: muitos testes de função pura, uma boa camada de componentes, poucos de integração e um punhado de ponta a ponta. Se todo teste for de ponta a ponta, a suíte demora vinte minutos e ninguém roda antes de publicar. Se nenhum for, você descobre o bug da lista vazia na casa do cliente.

Quando o projeto tem testes, o terminal passa a ser uma fonte de informação diária. A saída do npm test, com cinco testes espalhados em dois arquivos, é esta:

 ✓ src/Preco.test.jsx (3 testes) 12ms
 ✓ src/Lista.test.jsx (2 testes) 18ms

 Testes  5 passaram (5)

O ✓ é o teste que passou, o número entre parênteses é a contagem do arquivo e a última linha é o resumo. Quando algo falha, o runner destaca o arquivo e o nome do caso, e mostra a comparação. Vale aprender a ler essa saída com calma: o nome do teste bem escrito já diz o que quebrou, e a comparação diz o que era esperado contra o que veio.

7. Conferir pelo que a pessoa vê

A decisão mais importante de um teste de componente é como achar o elemento. A tentação é usar classe CSS, porque é o que você tem à mão. O problema é que classe muda quando o visual muda, e aí o teste quebra sem que nada de errado tenha acontecido com o comportamento. A alternativa é procurar pelo que o usuário percebe: o papel do elemento e o nome dele.

Como procurarServe paraAcha mesmo quando
getByRole("button", { name: "Encomendar" })botões, links, campos, títulosmuda a classe, muda a cor, muda o texto ao redor
getByLabelText("Cliente")campo de formulário com rótulomuda o id, muda a ordem
getByText("Nenhum pão por aqui")mensagens e textos soltosmuda a estrutura em volta
getByPlaceholderText("Buscar pão")campo sem rótulo visível— (prefira rótulo)
container.querySelector(".card")nada que o usuário vejaquase nunca: quebra fácil

Procurar por papel também melhora o site. Se o teste não encontra um botão pelo papel, é porque o elemento não é um botão — provavelmente é uma div com onClick, que o teclado não alcança e o leitor de tela não anuncia. O teste vira uma conferência de acessibilidade de graça, como você viu em Acessibilidade. Um componente difícil de testar por papel costuma ser um componente difícil de usar.

Duas convenções ajudam a manter a suíte legível. A primeira: um comportamento por teste, com nome que descreve a expectativa — “avisa quando não há pão” diz mais do que “teste da lista 2”. A segunda: prefira asserções que apontam para o resultado visível. Comparar o textContent inteiro é bom quando o texto é curto e estável; procurar um trecho é melhor quando há números ou datas no meio.

E cuidado com o excesso de detalhe. Conferir que o componente chamou uma função três vezes, que o estado interno virou true ou que a div tem a classe ativo é testar a implementação, não o comportamento. No dia em que você trocar a implementação por uma melhor, os testes quebram e você perde a confiança neles. Teste o que o usuário vê; o resto é conversa interna do componente.

8. Quando o teste falha

Uma falha bem reportada é metade do valor de uma suíte. O runner diz onde, qual caso e qual era a expectativa. Um exemplo real, do botão que somava no estado errado:

 FAIL  src/Botao.test.jsx > soma um a cada clique
 AssertionError: esperava Pedidos: 1

 - Pedidos: 0
 + Pedidos: 1

 Testes  1 falhou | 1 passou (2)

O sinal de menos é o que veio, o de mais é o que era esperado. Com essa informação você vai direto ao onClick. O que não se deve fazer é o contrário: mudar a asserção para Pedidos: 0 só para o teste passar. Teste que é ajustado para aceitar o bug deixa de ser teste e vira decoração.

A outra armadilha é o teste que passa sempre. Um caso com asserção fraca, do tipo “o container não é nulo”, passa com o componente completamente quebrado. Um teste só vale se ele pudesse falhar: escreva a asserção pensando no que estaria errado se o bug existisse, e desconfie de qualquer teste que nunca falhou na vida.

Vale também saber o que não testar. Não escreva teste para biblioteca de terceiros, para o React, para o roteador. Não teste detalhe de CSS — se a cor está certa, isso é conversa de revisão visual. Não tente cobrir 100% das linhas: persiga os casos que doem, os que já quebraram e os que ninguém lembra de abrir, como a lista vazia, o campo em branco e o erro de rede.

Por último, uma ligação com a aula anterior. O Strict Mode chama seu componente duas vezes em desenvolvimento; se um teste falha só quando você o roda duas vezes, provavelmente há escrita no desenho ou efeito sem limpeza. Teste e modo estrito se completam: um procura o caso esquecido, o outro procura a escrita escondida.

9. Cenários do dia a dia

Cenário 1: o teste que quebrava a cada mudança de cor

A primeira suíte da Ana procurava tudo por classe: .card-botao, .lista-ativa. Bastou o designer renomear as classes para trinta testes falharem de uma vez, sem nenhum bug. A reescrita levou uma tarde e trocou tudo por papel e texto: botão por getByRole, campo por getByLabelText, mensagem por getByText. Depois disso, mudar a aparência parou de assustar.

Cenário 2: o formulário que passava nos testes e falhava no site

O teste do formulário de encomenda conferia que o estado mudava ao digitar, e passava. No site, a encomenda não saía: o botão estava desabilitado por uma condição que o teste nunca exercitou. O conserto foi trocar a asserção de estado por uma asserção de comportamento — digitar, clicar, esperar o texto de confirmação — e o teste passou a olhar a mesma coisa que o cliente.

Cenário 3: o bug que voltou três vezes

Um problema de arredondamento no preço voltava a cada mudança na tela de carrinho. Na terceira vez, a Ana escreveu um teste de função pura com os quatro casos que já tinham quebrado: 0,10 + 0,20, desconto de 10% e frete grátis. Nunca mais voltou. O teste levou quinze minutos e economizou três atendimentos e duas tardes de investigação.

11. Resumo

Um teste é um bloco com nome que prepara, age e confere. A asserção é a parte que importa: se ela não puder falhar, o teste não protege nada. Comece pelas funções puras, que rodam em milissegundos, e suba para o componente quando o assunto for tela. Renderizar fora do documento, procurar o elemento, simular a interação e comparar o texto é o desenho que está por baixo de qualquer biblioteca.

Confira pelo que a pessoa vê: papel, rótulo, texto. Classe CSS, estado interno e número de desenhos são detalhes de implementação — e teste preso a detalhe quebra sem bug, o que ensina o time a ignorar falha. Cubra os casos que doem: lista vazia, campo em branco, erro de rede, o bug que já voltou uma vez.

Com isso você fechou o Nível 3. Você viu o React de verdade: build, rotas, desempenho, Suspense, Actions, acessibilidade, os erros que se repetem, o Strict Mode e agora os testes. O passo seguinte é juntar tudo em um projeto inteiro, começando por Lista de Tarefas.

Para lembrar

  • Teste = preparar, agir, conferir. Sem asserção forte, não é teste.
  • Função pura primeiro: é o teste mais barato e o que mais pega bug de conta.
  • Monte o componente num div solto e espere o desenho antes de conferir.
  • Em projeto real, render, screen, userEvent e act fazem o trabalho da caixa.
  • Procure por papel e nome acessível: o teste fica estável e ainda confere acessibilidade.
  • Não confira classe, estado interno nem contagem de desenhos.
  • Nunca ajuste a asserção para aceitar o bug.
  • Todo bug que chega ao cliente merece um teste que falharia se ele voltasse.
  • Poucos testes de ponta a ponta, nos fluxos que não podem falhar.
