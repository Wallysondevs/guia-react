Formulário Acessível

A Ana quebrou o pulso numa queda de bicicleta e passou duas semanas sem usar o mouse. Foi assim que ela descobriu que o formulário da padaria só funcionava para quem enxerga a tela e clica com precisão: o texto "Nome" estava num parágrafo solto, o campo só tinha um placeholder cinza, o erro aparecia em vermelho sem avisar ninguém e o botão de enviar era uma imagem. Nesta aula ela refaz o formulário para que ele funcione com teclado, com leitor de tela e com o zoom ligado — sem perder nada do que já tinha.

Você vai aprender
  • O que um leitor de tela lê em cada campo: nome, papel, valor e estado.
  • Como ligar um label ao campo com htmlFor e id.
  • Por que placeholder não é rótulo.
  • Como a dica chega ao campo com aria-describedby.
  • Como marcar e anunciar um erro com aria-invalid e role="alert".
  • Como agrupar opções com fieldset e legend.
  • Como levar o foco ao campo certo quando o envio falha.

1. A cena: a semana sem mouse

No primeiro dia de gesso, a Ana tentou fazer uma encomenda no próprio site para testar. Apertou Tab e o foco sumiu: pulou para um lugar qualquer, sem contorno visível, porque o CSS tinha outline: none para "ficar mais bonito". Chegou no campo de nome e digitou — sem problema. Chegou no botão e apertou Enter: a página recarregou e os campos esvaziaram. Ela tentou de novo, errou o telefone de propósito para ver a mensagem de erro, e a mensagem apareceu em vermelho, longe do campo, sem que nada fosse anunciado.

Nada disso era um bug do React. Era um formulário escrito só para o caminho mais comum: pessoa com mouse, tela grande, visão boa. Quem usa teclado, leitor de tela, zoom de 200% ou tem dificuldade para distinguir vermelho de verde fica de fora — e, no caso da padaria, deixa de comprar.

Acessibilidade tem fama de assunto avançado. Na prática, para formulários, são cinco hábitos: rótulo ligado ao campo, dica ligada ao campo, erro anunciado e ligado ao campo, grupos com nome e foco no lugar certo. Nenhum deles exige biblioteca. Todos cabem no JSX que você já escreve.

2. O que o leitor de tela lê

Um leitor de tela não vê pixels: ele percorre a árvore de acessibilidade que o navegador monta a partir do HTML. Para cada campo, essa árvore tem quatro informações. O papel diz que aquilo é uma caixa de edição, um botão, uma lista. O nome é o texto que identifica o campo — vem do rótulo. O valor é o que está digitado. E o estado diz se está obrigatório, desabilitado, inválido, marcado.

Quando falta o nome, o leitor anuncia só "caixa de edição, em branco". A pessoa ouve três campos seguidos assim e não faz ideia de qual é o nome, qual é o telefone e qual é o endereço. É por isso que o rótulo não é enfeite: ele é o dado que dá nome ao campo.

leitor de tela
Programa que lê a tela em voz alta e navega por ela pelo teclado. NVDA e JAWS no Windows, VoiceOver no Mac e no iPhone, TalkBack no Android.
nome acessível
O texto que o leitor usa para identificar um elemento. Num campo, vem do label, de aria-label ou de aria-labelledby.
papel
O tipo do elemento na árvore: caixa de edição, botão, grupo de opções. Vem da tag HTML; uma div com clique não tem papel nenhum.
descrição
O texto extra que o leitor fala depois do nome: a dica de formato, a mensagem de erro. Vem de aria-describedby.
estado
O que muda sem trocar o texto: obrigatório, inválido, marcado, desabilitado.

No leitor de tela, o campo do nome com rótulo, dica e obrigatoriedade soa assim:

Nome, caixa de edição, obrigatória
Como está no documento, com sobrenome

A primeira linha é o nome mais o papel mais o estado. A segunda é a descrição. Se o rótulo estivesse solto num parágrafo, a primeira linha seria só "caixa de edição". Se a dica estivesse solta embaixo, ela nunca seria lida junto com o campo — a pessoa teria que sair do formulário e voltar para descobrir o que era esperado.

3. label de verdade: htmlFor e id

O jeito mais confiável de dar nome a um campo é o par label com htmlFor e input com id. O React escreve htmlFor porque for é palavra reservada do JavaScript; no HTML gerado, sai for.

function Encomenda() {
  const [nome, setNome] = useState("");

  return (
    <form onSubmit={(e) => e.preventDefault()}>
      <label htmlFor="nome">Nome</label>
      <input
        id="nome"
        value={nome}
        onChange={(e) => setNome(e.target.value)}
      />
      <button type="submit">Encomendar</button>
    </form>
  );
}

Esse par faz três coisas de uma vez. Dá o nome ao campo na árvore de acessibilidade. Faz o texto do rótulo ser clicável: clicar em "Nome" leva o cursor para o campo. E deixa o leitor de tela anunciar o rótulo quando o campo recebe o foco, o que ajuda quem navega por formulários grandes.

Se você escrever for em vez de htmlFor, o React avisa no console do navegador:

Warning: Invalid DOM property `for`. Did you mean `htmlFor`?

O aviso aparece só em desenvolvimento — na build de produção o atributo é ignorado em silêncio, e o campo fica sem nome. É o tipo de erro que passa no teste de quem enxerga e falha no leitor de tela.

Existe uma segunda forma, que dispensa o par: embrulhar o campo dentro do próprio label.

<label>
  Buscar pão
  <input value={busca} onChange={(e) => setBusca(e.target.value)} />
</label>

Funciona igual para o leitor e para o clique. O par htmlFor/id é melhor quando o layout separa o rótulo do campo (uma coluna de rótulos, outra de campos), porque aí o label não pode envolver o input. Nesta aula a Ana usa o par, que é o mais comum em formulários de loja.

Agora a primeira missão. O campo tem só um placeholder e um parágrafo solto escrito "Nome" — o leitor de tela não tem como saber que os dois têm relação.

Troque o parágrafo por um <label htmlFor="nome">Nome</label>. Clique no texto do rótulo: o foco tem de ir para o campo (o painel mostra o contorno do foco).

O clique no rótulo não é um recurso do React: é o navegador ligando o for ao id. Por isso a missão confere o foco no campo — não basta existir um label solto, ele precisa apontar para o campo certo. Um id repetido na página quebra essa ligação: o navegador liga o rótulo ao primeiro elemento com aquele id e ignora o resto.

Repare também que o placeholder continua no código, agora como o que ele é: uma dica de formato, não o nome do campo. Placeholder com o mesmo texto do rótulo é redundância; placeholder com "99999-9999" é ajuda de verdade.

4. Dicas ligadas ao campo

Toda instrução que a pessoa precisa para preencher o campo deve ser lida junto com o campo. A forma de fazer isso é dar um id ao texto da dica e apontar para ele em aria-describedby. O leitor lê o nome, depois a descrição, e a pessoa já sabe o que digitar sem sair do lugar.

<label htmlFor="nome">Nome</label>
<input id="nome" aria-describedby="dica-nome" />
<p id="dica-nome">Como está no documento, com sobrenome.</p>

Se o campo tem mais de uma informação — a dica e o erro —, o aria-describedby aceita vários id separados por espaço: aria-describedby="dica-nome erro-nome". O leitor lê na ordem em que estão ali. É por isso que a dica vem primeiro: ela continua valendo quando o erro aparece.

O que não funciona é confiar na posição visual. Um parágrafo logo abaixo do campo, sem ligação nenhuma, é lido quando o leitor chega nele na navegação — não quando chega no campo. Para quem usa zoom alto, o parágrafo pode estar fora da tela; para quem usa leitor, ele pode vir depois de mais três campos. A ligação explícita resolve os dois casos.

Uma dica que evita erro antes de acontecer: escreva o formato esperado, não o que a pessoa não pode fazer. "Telefone com DDD, só números" ajuda; "não digite parênteses" faz a pessoa descobrir o problema depois. E use autocomplete quando fizer sentido — autocomplete="name", autocomplete="tel" —, porque ele permite que o navegador preencha o campo com um toque em vez de digitar no celular.

5. Quando o campo está errado

Erro em formulário acessível tem três partes: o texto que explica, o estado do campo e o anúncio na hora em que o erro aparece. Só a primeira costuma existir; as três são necessárias.

O texto é o que você já faz na aula de validação: uma frase perto do campo, dizendo o que fazer. O estado é o atributo aria-invalid, que marca o campo como inválido para o leitor de tela e para o CSS ([aria-invalid="true"] pinta a borda). O anúncio é o role="alert" no parágrafo do erro: quando ele aparece, o leitor interrompe o que estava lendo e fala a mensagem.

<input
  id="nome"
  value={nome}
  aria-invalid={erro !== ""}
  aria-describedby="dica-nome erro-nome"
  onChange={(e) => setNome(e.target.value)}
/>
{erro && <p id="erro-nome" role="alert">{erro}</p>}

Três detalhes que fazem diferença. Primeiro: role="alert" é para a mensagem que aparece, não para o container que muda a cada tecla — senão o leitor repete a frase a cada letra e vira tortura. Segundo: a mensagem diz o que fazer ("Informe o nome de quem vai buscar"), não o que a pessoa fez de errado ("campo inválido"). Terceiro: cor não é informação. Quem não distingue vermelho não vê a borda vermelha; o texto e o aria-invalid é que contam a história.

Para quem prefere manter as mensagens de erro sempre no DOM, existe aria-live="polite" num container vazio: o leitor anuncia o que aparecer ali, sem interromper. role="alert" é o mesmo mecanismo com prioridade alta. Para erro de formulário, alert é o mais usado; para contadores e avisos que mudam sozinhos, polite é melhor.

Agora a missão: o erro existe, mas nenhum leitor de tela vai encontrá-lo.

Ligue a dica ao campo com aria-describedby="dica-nome", marque o campo com aria-invalid quando houver erro e dê role="alert" ao parágrafo do erro. Clique em Encomendar com o campo vazio.

Clique em Encomendar e depois digite um nome: o erro some, aria-invalid volta a false e o parágrafo com role="alert" sai do DOM. O estado acompanha o valor, como na validação que você já conhece — a diferença é que agora ele também é anunciado. Se você esquecer o id="erro-nome", o aria-describedby aponta para o nada e o leitor não fala a mensagem; é um erro silencioso.

6. Grupos com nome: fieldset e legend

Algumas perguntas não pertencem a um campo só. "Como você quer receber?" vale para o conjunto de opções — retirar, entrega, correio. Dar o mesmo rótulo a cada opção é errado; deixar sem rótulo é pior. O HTML resolve com fieldset e legend: o legend nomeia o grupo, e o leitor de tela anuncia esse nome antes de cada opção.

<fieldset>
  <legend>Como você quer receber?</legend>
  <label>
    <input type="radio" name="recebimento" value="retirada"
      checked={forma === "retirada"}
      onChange={(e) => setForma(e.target.value)} />
    Retirar no balcão
  </label>
  <label>
    <input type="radio" name="recebimento" value="entrega"
      checked={forma === "entrega"}
      onChange={(e) => setForma(e.target.value)} />
    Entrega em casa
  </label>
</fieldset>

O name igual em todas as opções é o que faz o navegador tratar as bolinhas como um grupo só: escolher uma desmarca a outra, e as setas do teclado pulam de uma para outra. O fieldset é o que diz ao leitor de tela que existe um grupo e qual é a pergunta dele. Os dois juntos é que fazem o serviço; só o name agrupa o comportamento, mas não dá nome ao conjunto.

Aula de radio mostra o grupo controlado com calma, e a de checkbox mostra as caixas de marcar. O que vale levar daqui é o hábito: se duas ou mais opções respondem à mesma pergunta, elas vão dentro de um fieldset com legend. Se o layout não permite, role="group" com aria-labelledby funciona, mas é mais fácil de errar.

7. Para onde o foco vai

Quando o envio falha, quem enxerga vê a mensagem vermelha e rola até ela. Quem usa teclado e leitor de tela continua no botão, sem saber que existe um erro em cima. A correção é mover o foco para o lugar onde está o problema — o primeiro campo inválido.

function Encomenda() {
  const [nome, setNome] = useState("");
  const [erro, setErro] = useState("");
  const campoNome = useRef(null);

  function enviar(e) {
    e.preventDefault();
    if (nome.trim() === "") {
      setErro("Informe o nome de quem vai buscar");
      campoNome.current.focus();
    } else {
      setErro("");
    }
  }

  return (
    <form onSubmit={enviar}>
      <label htmlFor="nome">Nome</label>
      <input
        id="nome"
        ref={campoNome}
        value={nome}
        onChange={(e) => setNome(e.target.value)}
      />
      {erro && <p role="alert">{erro}</p>}
      <button type="submit">Encomendar</button>
    </form>
  );
}

useRef(null) cria uma caixa que guarda uma referência ao elemento; ref={campoNome} entrega o input de verdade para essa caixa; .focus() é o método do elemento que leva o cursor para lá. A aula de useRef destrincha o assunto — aqui basta saber que é assim que se fala com um elemento do DOM.

Duas regras. Primeiro: mova o foco só quando o erro aparece, nunca a cada tecla; um campo que rouba o cursor enquanto a pessoa digita é pior que um erro silencioso. Segundo: se o formulário tem muitos campos, considere focar um resumo de erros no topo, com tabIndex={-1} para poder receber foco sem entrar na ordem do Tab. O resumo lista os problemas e cada item leva ao campo.

Enquanto você mexe no foco, não apague o contorno. outline: none no CSS deixa o foco invisível para quem usa teclado — é a reclamação número um de quem navega com Tab. Se o contorno padrão não combina com o layout, troque por outro (outline: 2px solid, box-shadow), mas não remova sem colocar nada no lugar.

Agora a missão. O erro é anunciado, mas o foco continua no botão.

Na prévia ao vivo, repare no que muda: o cursor pisca no campo do nome e o contorno aparece nele, não no botão. É a diferença entre "aconteceu um erro em algum lugar" e "o nome está vazio, preencha aqui".

8. Teclado, ordem e os detalhes que somam

Formulário acessível é formado por muitos detalhes pequenos. Estes são os que mais aparecem no dia a dia de quem constrói tela.

A ordem do Tab segue a ordem do HTML, não a posição na tela. Isso importa quando o CSS usa order ou posicionamento absoluto: o visual diz uma coisa e o teclado faz outra. Se a sua tela usa flex-direction: column-reverse para o rodapé, teste com Tab — o caminho pode estar de trás para frente.

Sobre required: ele é bom e tem efeito colateral. O navegador passa a validar o campo sozinho e mostra um balão nativo, no idioma do navegador, antes do seu onSubmit rodar. Se você quer a sua própria mensagem, use required para o leitor de tela e noValidate no form para desligar o balão — assim o campo continua sendo anunciado como obrigatório e a mensagem que aparece é a sua.

Por último, três ajustes de CSS que não são enfeite: contraste de pelo menos 4,5:1 entre texto e fundo; área de toque de pelo menos 44 por 44 pixels nos botões; e tamanho de fonte que aguente o zoom de 200% sem quebrar o layout. Nada disso é React — é a mesma página que você já tem, vista por outra pessoa.

9. Cenários do dia a dia

Cenário 1: o campo que o leitor chama de "caixa de edição"

A Ana tinha três campos com placeholder e nenhum rótulo. No leitor de tela, os três eram "caixa de edição, em branco" — sem nome, sem ordem reconhecível. O conserto foi trocar cada parágrafo solto por um label com htmlFor apontando para o id do campo. Três linhas de HTML mudaram a experiência inteira.

Cenário 2: o erro que ninguém ouviu

O erro aparecia em vermelho, com texto, e desaparecia quando a pessoa corrigia. Só que nada disso era anunciado: quem não estava olhando a tela não sabia que o envio tinha falhado. A correção foi role="alert" no parágrafo, aria-invalid no campo e o foco indo para o campo com problema. Três atributos, um problema resolvido.

Cenário 3: o Tab que pulava o botão

O botão de enviar era uma imagem com onClick. Mouse funcionava; teclado, não — a imagem não recebe foco nem responde a Enter. O conserto é trocar por <button> com o ícone dentro, que já vem com papel, foco e teclado de graça. Estilo é CSS; comportamento é HTML.

Dica: é o atributo que aponta para o id de um ou mais textos de apoio, separados por espaço. Não é o mesmo atributo que dá o nome ao campo.

11. Resumo

Acessibilidade em formulário começa pelo nome. Cada campo precisa de um label ligado por htmlFor e id — ou envolvendo o campo —, porque é isso que o leitor de tela anuncia junto com o foco. Placeholder é dica de formato, não nome. Dicas longas vão em aria-describedby, apontando para o id do texto.

Erro tem três partes: a mensagem clara, o aria-invalid no campo e o role="alert" no parágrafo, para o anúncio acontecer na hora. Grupos de opções vão em fieldset com legend, e o name igual agrupa o comportamento do teclado. Quando o envio falha, o foco vai para o campo com problema — com useRef e .focus() —, e nunca a cada tecla.

O resto é disciplina de HTML: button no lugar de div clicável, contorno de foco visível, ordem do Tab igual à ordem do documento, contraste e área de toque. Nada disso é React específico — é a mesma página, agora legível para todo mundo. E vale testar com Tab, com zoom de 200% e, se puder, com um leitor de tela: cinco minutos de teste com teclado encontram mais problema que uma tarde de leitura de documentação.

Para lembrar

  • O leitor lê nome, papel, valor e estado de cada campo.
  • label htmlFor="nome" + input id="nome" é o par que dá nome ao campo.
  • Clicar no rótulo foca o campo — é o navegador ligando for a id.
  • Placeholder não é rótulo: some ao digitar.
  • aria-describedby liga a dica (e o erro) ao campo.
  • aria-invalid marca o estado; role="alert" anuncia a mensagem.
  • Erro só em vermelho não é informação para todo mundo.
  • fieldset + legend nomeiam um grupo de opções.
  • useRef + .focus() leva o cursor ao campo com problema.
  • Nunca apague o contorno do foco; teste a página inteira com Tab.
