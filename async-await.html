async e await

Na aula anterior a Ana viu o fetch e a espera com .then. Funciona, mas o código fica em escada: um degrau para a resposta, outro para o corpo, outro para o que depende do anterior. O JavaScript tem uma sintaxe que desmancha a escada em linha reta, e é ela que todo projeto React usa hoje: async e await. Não é uma biblioteca nova nem um recurso do React — é JavaScript puro, e a diferença é de leitura. Nesta aula ela vê as duas palavras, o que cada uma faz por baixo e os três erros que aparecem em quase todo código que começa.

Você vai aprender
  • Por que a função async sempre devolve uma Promise.
  • O que o await faz na prática, linha por linha.
  • Onde o await pode ficar — e onde não pode.
  • O erro de esquecer o await e como reconhecer o sintoma.
  • A diferença entre esperar em série e esperar em paralelo.
  • Promise.all e Promise.allSettled: quando cada um serve.

1. A cena: a fila que anda em linha reta

Imagine o balcão da padaria com uma fila. A atendente chama o primeiro, entrega o pão, chama o segundo. Cada pedido termina antes de o próximo começar, e o mundo faz sentido na ordem em que as coisas aparecem. O .then é o contrário disso: ele entrega um papel com "quando ficar pronto, faça isto", e você segue trabalhando em outra coisa. Poderoso, mas difícil de ler quando há três pedidos encadeados.

async e await devolvem a sensação da fila. A função marcada com async ganha permissão para usar await, e o await faz o código parar naquela linha até o valor chegar. O resto do programa continua rodando — só aquela função espera. É a diferença entre "a atendente espera o pão assar" e "a padaria inteira fecha até o pão assar".

O resultado é o mesmo .then de antes, escrito de cima para baixo. E é exatamente por isso que essa sintaxe virou padrão: ela parece código comum, com try, catch e return nos lugares de sempre.

2. async: a função que promete

Marcar uma função com async muda uma coisa só, e é bom saber qual: o valor devolvido por ela nunca sai direto. Sai embrulhado em uma Promise. Se a função faz return 3, quem chamou recebe uma Promise que se cumpre com 3.

async function total() {
  return 3;
}

const a = total();        // Promise {<fulfilled>: 3}
const b = await total();  // 3

Isso não é capricho: a palavra async é o contrato de que a função pode esperar coisas do mundo real — rede, arquivo, temporizador — e por isso ninguém pode depender de o resultado estar pronto imediatamente. O embrulho garante que existe um jeito de esperar. No console, a diferença é visível:

> async function total() { return 3; }
undefined
> total()
Promise {<fulfilled>: 3}
> await total()
3

A primeira linha devolve undefined porque declarar função não produz valor. A segunda mostra o embrulho, com o valor já dentro — mas dentro do embrulho. Só o await entrega o 3. E note que uma função async que não devolve nada devolve uma Promise cumprida com undefined: o embrulho existe do mesmo jeito.

async
Marca a função. Ela passa a devolver Promise e ganha o direito de usar await dentro.
await
Espera a Promise da direita se cumprir e devolve o valor dela. Só existe dentro de função async.
Promise
O embrulho do valor que ainda vai chegar. Tem três estados: pendente, cumprida e rejeitada.
Promise.all
Recebe uma lista de Promises e devolve uma só, com a lista de resultados na mesma ordem.
Promise.allSettled
Igual ao anterior, mas espera todas terminarem, mesmo quando alguma é rejeitada.
rejeição
O "não deu" de uma Promise. Sem tratamento, vira erro não capturado no console.

3. await: esperando o valor

await faz duas coisas ao mesmo tempo. Primeiro, espera: se a Promise da direita ainda não se cumpriu, a função para ali e devolve o controle para quem a chamou. Segundo, desembrulha: quando a Promise se cumpre, o await devolve o valor de dentro, e não a Promise.

É por isso que const dados = await resposta.json() dá o objeto, enquanto const dados = resposta.json() dá a Promise. A diferença de duas palavras muda o tipo do valor, e tipo errado é a causa da maior parte dos bugs desta aula.

Vale entender o que acontece enquanto a função espera, porque é a pergunta que todo mundo faz. O JavaScript tem uma única linha de execução: quando o await para a função, ele devolve o controle para quem chamou e continua atendendo o resto da página — cliques, digitação, animações. A função fica parada num canto, esperando a promessa avisar. Quando o valor chega, ela retoma exatamente da linha seguinte, com o valor na mão. Nada de tela congelada.

Um detalhe que alivia: por baixo dos panos, await é .then. Nada de mágica e nada de bloqueio real da página. Se a função tem três await em sequência, os três pedidos saem em sequência — e isso pode ser lento de propósito ou por acidente, assunto da seção 6.

4. O erro número um: esquecer o await

A função contarPaes abaixo é async: devolve uma Promise que se cumpre com o número de pães. Quem chama sem await recebe o embrulho, e o embrulho não soma. Veja o que acontece na tela:

O painel mostra 10[object Promise] no lugar do total. Falta esperar a função contarPaes(): coloque await antes dela.

function buscarPaes() {
  return new Promise((ok) => {
    setTimeout(() => ok(["pão francês", "croissant", "brioche"]), 10);
  });
}

async function contarPaes() {
  const lista = await buscarPaes();
  return lista.length;
}

function App() {
  const [total, setTotal] = useState(0);

  useEffect(() => {
    async function carregar() {
      const n = contarPaes();
      setTotal(10 + n);
    }
    carregar();
  }, []);

  return (
    <div>
      <h1>Padaria da Ana</h1>
      <p>Total: {total} reais</p>
    </div>
  );
}

O texto 10[object Promise] é o resultado de somar número com Promise: o JavaScript desiste da conta e junta tudo como texto. Se fosse uma conta de multiplicação, apareceria NaN. Se o valor fosse direto para o JSX, apareceria nada — ou um erro dizendo que objeto não é filho válido do React. Três sintomas, uma causa.

O hábito que evita o problema: sempre que chamar uma função async, pergunte "eu quero a Promise ou o valor?". Se quiser o valor, await. E se você não tem certeza de que a função é async, olhe a declaração — a palavra está lá, antes do nome.

5. Onde o await pode ficar

await é filho de async. Fora de uma função marcada, ele nem compila: o JavaScript recusa a sintaxe antes de rodar qualquer coisa. Isso explica três situações que confundem.

A primeira é no componente: o corpo de App não é uma função async, então const dados = await buscar() direto no componente não compila. O lugar certo é dentro do efeito, em uma função interna, como na caixa anterior.

A segunda é no efeito: useEffect(async () => { ... }) parece a solução, mas o React espera uma função que devolve nada — e uma função async devolve Promise. O efeito passa a devolver uma Promise no lugar da função de limpeza, e a limpeza se perde. A forma que funciona é declarar uma função async dentro do efeito e chamá-la em seguida.

A terceira é em retorno de chamada de evento: onClick={() => await salvar()} também não compila. O contorno é o mesmo: marcar a função como async, e aí o onClick={async () => { await salvar(); }} funciona. Um async a mais resolve, e o React trata o retorno como "não me interessa".

6. Em série ou em paralelo

Três await em sequência somam os tempos: se cada pedido leva um segundo, a tela espera três. Às vezes é necessário — quando o segundo pedido depende do primeiro —, mas na maioria dos casos não é. Pedir o cardápio, as promoções e o horário são pedidos independentes, e esperar um depois do outro é desperdício.

O erro comum com await e map é achar que o map espera. Ele não espera: ele chama as funções e guarda o que cada uma devolve. Se a função é async, o que fica no array são Promises — três embrulhos no lugar de três pães.

A lista tem três itens, mas todos vazios: o map devolveu Promises. Troque por await Promise.all(ids.map((id) => buscarPao(id))) para ter os três pães.

const NOMES = { pao: "Pão francês", croissant: "Croissant", brioche: "Brioche" };

function buscarPao(id) {
  return new Promise((ok) => {
    setTimeout(() => ok({ id: id, nome: NOMES[id] }), 10);
  });
}

function App() {
  const [paes, setPaes] = useState([]);

  useEffect(() => {
    async function carregar() {
      const ids = ["pao", "croissant", "brioche"];
      const lista = ids.map(async (id) => await buscarPao(id));
      setPaes(lista);
    }
    carregar();
  }, []);

  return (
    <div>
      <h1>Vitrine</h1>
      <ul>
        {paes.map((p) => (
          <li key={p.id}>{p.nome}</li>
        ))}
      </ul>
    </div>
  );
}

O Promise.all recebe a lista de Promises e devolve uma Promise só, que se cumpre com a lista de resultados na mesma ordem — a ordem do array, não a ordem de chegada. É esse detalhe que faz o map voltar a ser útil: você mapeia os ids, o all espera todos e o resultado sai alinhado com o que você pediu.

E os pedidos saem juntos: três pedidos de 20 milissegundos levam 20 milissegundos no total, não 60. Sempre que os pedidos não dependem um do outro, Promise.all é a resposta. Quando dependem, await em série, um depois do outro, e não há vergonha nisso.

Para guardar os lados bons e os ruins, existe o Promise.allSettled, e é ele que resolve o caso mais chato de todos: a vitrine com três pães em que um deles está esgotado. Com Promise.all, os três pedidos são jogados fora; com allSettled, os dois que deram certo chegam e o que falhou vem marcado. Você mostra os dois e um aviso discreto sobre o terceiro. A seção seguinte mostra isso em código.

7. Quando um dos pedidos falha

Promise.all tem um comportamento duro: se uma das Promises for rejeitada, o all inteiro é rejeitado, com o erro daquela. As outras podem até se cumprir, mas o resultado já foi descartado. Em uma vitrine de três pães, um brioche esgotado derruba a lista toda.

Um dos pedidos falha, e o Promise.all derruba os três. Use Promise.allSettled e conte quantos resultados têm status igual a "fulfilled".

const NOMES = { pao: "Pão francês", croissant: "Croissant", brioche: "Brioche" };

function buscar(id) {
  return new Promise((ok, falha) => {
    setTimeout(() => {
      if (id === "brioche") falha(new Error("brioche esgotado"));
      else ok(NOMES[id]);
    }, 10);
  });
}

function App() {
  const [resumo, setResumo] = useState("Buscando...");

  useEffect(() => {
    async function carregar() {
      try {
        const lista = await Promise.all([buscar("pao"), buscar("brioche"), buscar("croissant")]);
        setResumo("Carregou " + lista.length + " de 3");
      } catch (e) {
        setResumo("Falhou tudo");
      }
    }
    carregar();
  }, []);

  return (
    <div>
      <h1>Vitrine</h1>
      <p>{resumo}</p>
    </div>
  );
}

const NOMES = { pao: "Pão francês", croissant: "Croissant", brioche: "Brioche" };

function App() {
  const [resumo, setResumo] = useState("Buscando...");

  useEffect(() => {
    async function carregar() {
      const resultados = await Promise.allSettled([buscar("pao"), buscar("brioche"), buscar("croissant")]);
      const bons = resultados.filter((r) => r.status === "fulfilled").length;
      setResumo("Carregou " + bons + " de 3");
    }
    carregar();
  }, []);

  return (
    <div>
      <h1>Vitrine</h1>
      <p>{resumo}</p>
    </div>
  );
}

O allSettled espera todas terminarem — cumpridas ou rejeitadas — e devolve uma lista de objetos com status e, conforme o caso, value ou reason. Você decide o que fazer com cada um. É o coletor certo quando o pedido é "traga o que der".

Sem tratamento, o erro de uma Promise aparece assim no console, e é o sintoma de Promise.all com um item quebrado:

Uncaught (in promise) Error: brioche esgotado

O try e o catch em volta do await pegam esse erro — e essa é uma das grandes vantagens da sintaxe: o erro cai no catch de sempre, com a mesma cara de qualquer outro erro. A aula de tratamento de erro explora isso a fundo.

8. Os atalhos que economizam linhas

Três práticas que você vê em código experiente e que vale entender. A primeira: return await dentro de try é útil (o catch pega o erro); fora dele, é redundante — o return de uma função async já embrulha o valor. A segunda: em laço com dependência, for (const id of ids) { const p = await buscar(id); } roda em série, e é o que você quer quando cada pedido depende do anterior.

A terceira é sobre tempo total. Vale fazer a conta antes de escolher: cinco pedidos de 300 milissegundos em série levam um segundo e meio; em paralelo, 300 milissegundos. O usuário sente a diferença, e a mudança é de uma linha — trocar o laço por Promise.all(ids.map(...)).

O Promise.race merece um exemplo, porque resolve um problema real sem biblioteca: se o servidor da padaria às vezes demora demais, você pode apostar corrida entre o pedido e um relógio. O primeiro que terminar define o resultado — se o relógio ganhar, o código segue com um erro de "demorou demais" em vez de esperar para sempre. É a versão em JavaScript do bom e velho tempo limite, e a aula de cancelamento mostra a versão moderna, que também interrompe o pedido na rede.

9. Cenários do dia a dia

Cenário 1: o preço que virou texto estranho

A Ana somou o frete ao total e a tela mostrou 15[object Promise]. A função do frete era async e ela esqueceu o await na chamada. O sintoma é sempre esse: número virando texto esquisito, conta virando NaN, valor sumindo do JSX. O conserto é o await — e a checagem é olhar a declaração da função chamada.

Cenário 2: a lista com três itens vazios

Ela mapeou os ids com ids.map(async (id) => buscar(id)) e a lista apareceu com os lugares certos e sem conteúdo. O map não espera: guardou três Promises. A correção foi await Promise.all(ids.map((id) => buscar(id))), que espera as três e entrega os valores na ordem dos ids. O async dentro do map não é proibido — só não faz o que se espera dele.

Cenário 3: o efeito que devolveu Promise

Ela escreveu useEffect(async () => { ... }, []) e recebeu um aviso no console do navegador. O React espera que a função do efeito devolva nada ou uma função de limpeza; uma função async devolve Promise, e a limpeza se perde. A correção é declarar uma função interna async e chamá-la — o efeito continua devolvendo o que o React espera, e a limpeza volta a funcionar.

Exercício: os dois pedidos juntos

Complete o código para pedir os dois produtos ao mesmo tempo, numa espera só:

const lista = await ([buscar("pao"), buscar("croissant")]);

Dica: é o coletor que recebe uma lista de Promises e devolve uma Promise com a lista de resultados, na mesma ordem. Tem ponto no meio: Promise.all, com o all em minúsculas.

11. Resumo

async marca a função e embrulha o retorno em Promise; await espera essa Promise e devolve o valor de dentro. Os dois juntos transformam a escada de .then em linha reta, com try e catch nos lugares de sempre. Nada de bloqueio: só a função marcada espera, o resto da página continua vivo.

O erro mais comum é esquecer o await, e os sintomas são reconhecíveis: número somando com Promise vira texto estranho, conta vira NaN, e o JSX às vezes não desenha nada. O segundo erro é achar que map com async espera: ele devolve Promises, e o conserto é Promise.all.

E o terceiro é escolher mal o coletor. Promise.all quando todos precisam dar certo; Promise.allSettled quando basta trazer o que der. Pedidos independentes em paralelo, pedidos dependentes em série. A conta do tempo total vale antes de escrever, não depois.

Na próxima aula, um botão que ninguém aperta duas vezes: cancelar um pedido em andamento com o AbortController, e o que fazer com o erro que aparece quando o pedido é interrompido.

Para lembrar

  • async sempre devolve Promise, mesmo com return 3.
  • await só existe dentro de função async.
  • Sem await, você recebe o embrulho, não o valor.
  • map com async devolve Promises: use Promise.all.
  • Promise.all rejeita se um falhar; allSettled espera todos.
  • Pedidos independentes rodam juntos; dependentes, em série.
  • try/catch em volta do await pega o erro.
  • No efeito, função async interna — nunca useEffect(async …).
