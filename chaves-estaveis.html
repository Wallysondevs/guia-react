Chaves Estáveis

A fila de encomendas da Ana muda de ordem todo dia: quem chega primeiro, quem pediu urgente, quem desistiu. E tem um bug estranho — o "pronto" marcado em um pedido aparece em outro. Nesta aula ela descobre que a key não é um detalhe para calar o console: é a identidade do item, e quando ela muda sem o item mudar, o estado do React fica na linha errada.

Você vai aprender
  • O que o React faz quando a lista muda de um desenho para o outro.
  • Por que a key precisa ser a mesma entre desenhos — o que "estável" quer dizer.
  • O que acontece quando a chave é sorteada: remontagem e estado perdido.
  • Por que o índice costuma falhar quando a lista muda de ordem, tamanho ou filtro.
  • O teste de três perguntas para escolher uma chave.
  • Quando você quer uma chave nova de propósito, para recomeçar um componente.
  • Por que no build de produção o aviso some e só o comportamento denuncia.

1. A cena: o pedido que troca de lugar

O painel da Ana tem uma fila de encomendas com três botões: cada linha mostra o nome do pão e marca se está pronto. O botão "Inverter a fila" põe quem chegou por último na frente — e é aí que aparece o problema. Ela marca o pão francês como pronto, inverte a fila, e o "pronto" está no croissant.

Na aula de A key, você viu o básico: toda lista feita com map precisa de uma key em cada item, e a key vai no elemento mais externo que o map devolve. Agora o assunto é o outro lado da palavra: a chave precisa ser estável. Mesma chave, mesmo item, entre dois desenhos da tela. Se a chave muda sem o item mudar, o React acha que é outra coisa naquele lugar — e trata como outra coisa.

A confusão inicial é achar que a key serve para o React "saber a ordem". Não é isso. A ordem está no array; o React percorre na ordem que veio. A key serve para o React reconhecer o mesmo item quando o array é reordenado, filtrado ou acrescentado. É identidade, não posição.

Pense em uma ficha de padaria: cada pedido tem um número de comanda. Se a comanda 12 sai da terceira posição da fila e vai para a primeira, o pedido continua sendo o 12. Se você identificasse os pedidos pela posição — "o terceiro da fila" —, ao mudar a ordem o "terceiro" seria outro pedido. É exatamente esse o papel da key.

2. O que o React faz com a lista: identidade

Quando o React redesenha uma lista, ele precisa decidir, item por item, entre três coisas: reaproveitar o elemento que já está na tela, mover o elemento de lugar ou destruir e criar do zero. A key é o critério dessa decisão. Com a mesma key, ele reaproveita o componente — e o estado que mora dentro dele — e só atualiza as props. Com a key diferente, ele descarta o antigo e monta um novo, com estado zerado.

Esse "estado que mora dentro" é a parte que pega. Um <li> com um botão é só aparência; mas o componente que envolve a linha pode ter o seu useState — o "pronto", o texto digitado, o aberto e fechado. Esse estado pertence à instância do componente, e a instância é identificada pela key. Chave trocada, estado novo.

key
Um atributo especial que o React usa para identificar um item entre irmãos. Não vai para o HTML e não chega ao componente como prop.
identidade
O que faz o React reconhecer "é o mesmo item de antes". Vem da key, não do conteúdo nem da posição.
remontar
Destruir o componente e criar outro no lugar. Acontece quando a key muda. Todo estado interno volta ao inicial e os efeitos rodam de novo.
estável
Que não muda entre dois desenhos enquanto o item for o mesmo. p.id é estável; Math.random() não é; o índice só é enquanto a lista não muda.
irmãos
Os elementos que estão no mesmo nível, dentro do mesmo array ou do mesmo pai. A unicidade da key vale entre eles.

Com isso, a regra fica fácil de lembrar: a key é o nome próprio do item, não o número da cadeira. Duas pessoas não podem ter o mesmo nome na mesma lista, e o nome não muda quando a pessoa troca de cadeira.

3. A chave que vem do dado

A melhor key é a que já existe no dado: o id que veio do banco, o código da comanda, o slug da página. Ela é única por construção, não muda quando a lista é reordenada e sobrevive a um recarregamento — o que importa quando o estado do item é salvo em algum lugar.

function Fila({ pedidos }) {
  return (
    <ul>
      {pedidos.map((p) => (
        <li key={p.id}>{p.nome}</li>
      ))}
    </ul>
  );
}

Quando o dado não tem id, a primeira providência é criar um. Uma lista de pães cadastrados no sistema deve ter identificador, nem que seja um número sequencial guardado junto. Criar o id na hora de desenhar — key={indice} ou key={nome} — é remendo, e remendo tem prazo de validade.

O nome pode servir de key em uma lista que nunca muda de ordem e nunca tem nomes repetidos, como os itens fixos de um menu. É frágil: no dia em que dois itens tiverem o mesmo nome, a lista quebra; no dia em que o nome for editável, cada letra digitada vira uma identidade nova. Se há edição, não use o texto como chave.

E há um caso em que a chave não vem de um id: listas de tamanho fixo, geradas por um laço, como as doze casinhas de um calendário. Ali não existe "o item 3" com identidade própria — a posição é a identidade. Nesse caso, índice é uma escolha legítima, porque a lista nunca reordena. O problema não é o índice em si; é o índice em lista que muda.

4. Chave instável: o que remonta e o que se perde

Agora o primeiro dos dois erros clássicos. Sortear a chave parece resolver o aviso do console e é o pior conserto possível: a cada desenho, todas as chaves são diferentes, então o React desmonta e monta a lista inteira de novo. O estado de cada linha volta ao inicial — e o usuário vê o que marcou desaparecer.

Marque o pão francês como pago e vire o dia: o pagamento some, porque Math.random() troca a chave a cada desenho. Troque a chave por algo que venha do dado e não mude.

function Item({ nome }) {
  const [pago, setPago] = useState(false);
  return (
    <li>
      <button onClick={() => setPago(!pago)}>{nome}</button>
      {pago ? " — pago" : " — em aberto"}
    </li>
  );
}

function App() {

}

Para enxergar a remontagem acontecendo, há um truque simples: um useEffect com array de dependências vazio roda uma vez por montagem. Se você registra uma linha a cada montagem, a linha aparece de novo sempre que o componente é recriado:

function Item({ nome }) {
  useEffect(() => {
    console.log("montei: " + nome);
  }, []);
  return <li>{nome}</li>;
}

Com duas encomendas e uma chave estável, o console mostra duas linhas na primeira montagem:

console: montei: Pão francês
console: montei: Broa de milho

Com a chave sorteada, as mesmas duas linhas voltam a aparecer a cada redesenho da lista — no console do navegador, aberto com F12. O painel da caixa mostra apenas o desenho inicial, então ali as linhas não se repetem: é um dos lugares em que o DevTools do navegador conta mais que a prévia.

5. Índice como chave: a posição não é identidade

O segundo erro é mais sutil, porque às vezes funciona. Usar o índice do map como chave parece natural: é único dentro da lista, é fácil. O problema é que o índice descreve a posição, e a posição muda quando a lista é ordenada, filtrada ou quando um item é removido. Aí o React faz o que prometemos a ele: mantém o estado naquela posição, mesmo que o item que está ali agora seja outro.

Marque o primeiro pedido como pronto e inverta a fila: o "pronto" fica na posição, não no pedido. Troque a chave do índice pelo id do pedido.

function Pedido({ nome }) {
  const [pronto, setPronto] = useState(false);
  return (
    <li>
      <button onClick={() => setPronto(!pronto)}>
        {nome + ": " + (pronto ? "pronto" : "na fila")}
      </button>
    </li>
  );
}

function App() {
  const [pedidos, setPedidos] = useState([
    { id: 1, nome: "Pão francês" },
    { id: 2, nome: "Broa de milho" },
    { id: 3, nome: "Croissant" }
  ]);

  return (
    <div>
      <button className="inverter" onClick={() => setPedidos([...pedidos].reverse())}>

      </button>
      <ul>
        {pedidos.map((p, i) => (
          <Pedido key={i} nome={p.nome} />

  );
}

Com key={i}, depois de inverter, o "pronto" aparece no croissant — a posição que era do pão francês. Com key={p.id}, o estado viaja junto com o pedido e o pão francês continua pronto, agora no fim da fila. A estrutura do painel é a mesma nos dois casos; o que muda é o texto de cada botão.

Vale ver a ordem dos dados separada da ordem do estado. Um log da fila mostra o array na ordem nova, enquanto o estado continua preso à posição antiga:

antes:  Pão francês, Broa de milho, Croissant
depois: Croissant, Broa de milho, Pão francês

Se a lista é filtrada, o mesmo estrago acontece: ao remover o primeiro item, todos os índices escorregam uma posição e o estado passa a pertencer ao vizinho. É por isso que a aula de Filtrar insiste em manter o array original intacto e derivar a lista visível: com o id como chave, filtrar não embaralha identidade nenhuma.

6. O teste de três perguntas

Antes de escolher a chave de uma lista, faça três perguntas ao candidato. Ele é único entre os irmãos? Ele continua o mesmo entre dois desenhos? Ele vem do dado, e não da posição ou do acaso? Três "sim" e pode usar; qualquer "não" e você está comprando um bug futuro.

CandidatoÚnico?Estável?Veredito
p.id do bancosim, por construçãosim, não muda ao reordenara melhor escolha
índice do mapsim, no momentonão, se a lista muda de ordem ou tamanhosó em lista fixa
nome ou texto editávelaté o dia da repetiçãonão, muda quando o texto mudaevite em item editável
Math.random()simnuncaquebra tudo a cada desenho

Repare que a coluna "único" é a mais fácil de cumprir e a "estável" é a que decide. Sortear garante unicidade e destrói estabilidade. O índice garante unicidade e perde estabilidade assim que a lista se mexe. O id cumpre as duas porque foi feito para identificar a coisa, não o lugar.

Há um caso intermediário que vale reconhecer: a lista de tamanho fixo, em que o índice é a identidade real. Doze meses, sete dias da semana, três abas na mesma ordem. Ali, key={i} não causa problema porque nada reordena nem sai da lista. A diferença entre o uso certo e o errado não está no índice: está na promessa de que a lista não muda.

7. Quando você quer uma chave nova

Tudo o que foi dito até aqui trata chave trocada como acidente. Existe um caso em que trocar a chave é exatamente o que se quer: quando o componente precisa recomeçar do zero. Mudar a key de um componente é o jeito mais direto de dizer ao React "esqueça o que estava aí e monte outro".

Corte uma fatia e troque de pão: a ficha continua mostrando a contagem do pão anterior, porque o estado é o mesmo componente. Use a chave para recomeçar a ficha quando o pão mudar.

function Ficha({ pao }) {
  const [fatias, setFatias] = useState(0);
  return (
    <div>
      <p>{pao.nome + ": " + fatias + " de 8 fatias"}</p>
      <button className="cortar" onClick={() => setFatias(fatias + 1)}>Cortar uma fatia</button>
    </div>
  );
}

function App() {
  const [indice, setIndice] = useState(0);
  const paes = [
    { id: 1, nome: "Pão francês" },
    { id: 2, nome: "Broa de milho" }
  ];
  const pao = paes[indice];

  return (
    <div>
      <Ficha pao={pao} />
      <button className="trocar" onClick={() => setIndice(1)}>Trocar para a broa</button>
    </div>
  );
}

Sem a chave, a ficha é o mesmo componente e guarda as fatias do pão anterior: "Broa de milho: 1 de 8 fatias". Com key={pao.id}, trocar de pão monta uma ficha nova, com zero fatias — que é o comportamento correto, porque a broa ainda não foi cortada. A key aqui não é identidade de lista: é um pedido explícito de recomeço.

Esse recurso substitui um monte de código de sincronização. Sem ele, você teria de observar a mudança do pão com um efeito e zerar o estado à mão — mais linhas, mais chance de errar. Com a key, a intenção fica escrita no JSX.

Eu quero…FerramentaCuidado

Nas três linhas, a pergunta é sempre a mesma: o estado atual ainda faz sentido para o dado novo? Se faz, mantenha a chave; se não faz, troque. Chave estável e chave nova são ferramentas diferentes, e o erro é usar uma achando que está usando a outra.

8. Os erros silenciosos do build de produção

No modo de desenvolvimento, o React reclama: "Each child in a list should have a unique key prop". Esse aviso é útil e é o primeiro lugar onde o problema aparece em um projeto de verdade. Só que ele não existe no build de produção — e é produção que roda quando você publica o site.

As caixas deste guia rodam o build de produção do React 19. Isso significa que nenhum aviso de key aparece no painel: nem chave faltando, nem chave repetida, nem chave sorteada. O que aparece é o comportamento — a tela com o texto certo, o estado na linha errada, ou um item que pisca. Aprender a ler o sintoma, e não o aviso, é o que salva o dia.

Três sintomas que denunciam chave ruim, todos visíveis sem console. Primeiro: o estado de uma linha aparece em outra depois de reordenar ou filtrar. Segundo: o texto digitado em um campo some, e o campo perde o foco a cada letra — sinal de remontagem a cada desenho. Terceiro: a animação de entrada recomeça sozinha sempre que outro pedaço da página muda.

Há também um erro de lugar, que a aula de A key detalha: a key precisa estar no elemento que o map devolve, não em um filho interno. Se o item é um <Fragment> com dois irmãos, a key vai no <Fragment key={...}>, e não em um dos irmãos. E lembre que a key não chega ao componente como prop: se o componente precisa do id por dentro, passe também id={p.id}.

9. Cenários do dia a dia

Cenário 1: o campo perde o foco a cada letra

A Ana digitava a observação de um pedido e o cursor pulava fora do campo a cada tecla. A key era o próprio texto da observação, então cada letra criava uma identidade nova, o campo era remontado e o foco morria. Trocar a chave para pedido.id resolveu. Regra prática: chave nunca é um valor que o usuário edita.

Cenário 2: a lista filtrada embaralha os checks

Ela filtrava "só os pães doces" e os quadradinhos marcados mudavam de lugar. A chave era o índice do array filtrado: ao esconder itens, cada posição passava a apontar para outro pão. Com o id como chave, o check segue o pão — e a aula de Filtrar mostra como filtrar sem destruir o array original.

Cenário 3: dois itens com a mesma chave

Ela usou o nome do pão como chave e cadastrou dois "Pão de queijo" — um doce e um salgado. O React ficou sem saber qual é qual: um dos dois sumiu da tela e o outro apareceu com o estado misturado. Chave repetida entre irmãos é sempre erro, mesmo quando parece que "funciona". A saída é o id; quando não existe, crie um na origem dos dados.

11. Resumo

A key é a identidade do item entre irmãos. Com a mesma chave, o React reaproveita o componente e o estado dele; com chave diferente, remonta do zero. Por isso "estável" não é adjetivo decorativo: é a propriedade que faz o estado ficar no item certo quando a lista muda de ordem, de tamanho ou de filtro.

A melhor chave vem do dado — o id. O índice serve só quando a posição é a identidade de verdade, como em uma lista fixa que nunca reordena. Sortear a chave é sempre errado: garante unicidade e destrói estabilidade. E chave repetida entre irmãos é erro mesmo quando a tela parece funcionar.

Do outro lado, trocar a chave de propósito é uma técnica legítima: quando o componente precisa recomeçar com um dado novo, key={dado.id} descarta o estado antigo sem uma linha de efeito. A pergunta que decide é se o estado atual ainda faz sentido para o dado novo.

Por fim, a lição de ambiente: no build de produção o aviso de key não aparece. Quem escreve para produção aprende a reconhecer o sintoma — estado na linha errada, campo perdendo o foco, animação reiniciando — porque o console não vai ajudar. É o mesmo raciocínio do encanador que ouve o barulho em vez de esperar o vazamento.

Para lembrar

  • Key é identidade entre irmãos; a ordem continua vindo do array.
  • Mesma key: reaproveita o componente e o estado. Key nova: remonta e zera.
  • Chave boa: única, estável e vinda do dado — key={p.id}.
  • Índice só em lista que nunca reordena, cresce ou é filtrada.
  • Math.random() e Date.now() remontam tudo a cada desenho.
  • Nunca use como chave um valor que o usuário edita: o campo perde o foco.
  • A key vai no elemento que o map devolve, ou no Fragment que os envolve.
  • Key não chega ao componente como prop: passe o id também, se precisar.
  • Trocar a chave de propósito é o jeito mais curto de recomeçar um componente.
  • No build de produção não há aviso de key: o sintoma é o único sinal.
