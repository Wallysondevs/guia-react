Painel de Pedidos

Na cozinha da padaria, a Ana precisa de uma tela que mostre os pedidos do site na ordem em que chegam: os novos, os que estão sendo preparados e os que já saíram. Ela quer filtrar por status, ver quantos pedidos há em cada etapa e avançar cada um com um clique — sem recarregar a página e sem perder o que já foi feito. Neste projeto ela monta o painel do zero: os dados que chegam de uma "API" simulada, os estados de carregando e erro, a lista com filtro, as contagens e o botão que empurra o pedido para a próxima etapa.

Você vai aprender
  • Como modelar um pedido com id, cliente, itens, total e status.
  • Como simular a rede com Promise e setTimeout.
  • Como mostrar carregando e erro sem confundir com vazio.
  • Como filtrar por status sem estragar a lista.
  • Como avançar o status com map e um objeto novo.
  • Como derivar contagens e faturamento do estado.
  • Como ordenar sem mutar o array.
  • O que quebra quando o carregando não desliga.

1. A cena e o escopo do painel

O painel é a tela de quem trabalha na cozinha, não a de quem compra. Ele mostra os pedidos que chegaram, com o cliente, o que foi pedido, o total e o horário. Cada pedido tem um status: novo, preparando ou entregue. A Ana quer ver a fila inteira, filtrar por etapa e avançar um pedido com um clique.

Duas decisões de projeto aparecem antes do código. A primeira: o status é um texto curto e fixo, não um número. "novo" é legível, fácil de comparar e não precisa de legenda. A segunda: a lista de pedidos vem de fora, não nasce no componente. Num app de verdade, ela chega de um servidor; aqui, de uma promessa que resolve depois de um instante.

O que fica de fora: login, edição de itens, cancelamento, impressão. O painel é para acompanhar, e o escopo é esse. Cada recurso a mais é uma chance de não terminar — e o valor deste projeto está em ver a tela reagir a dados que chegam e a cliques que mudam o status.

A ordem de montagem também é uma decisão: primeiro os dados e a carga, depois a lista, depois o filtro, depois o botão de avançar. Quem começa pelo botão descobre tarde que o pedido não tem status, e volta duas etapas. Construir na ordem dos dados economiza retrabalho.

2. Os dados: o pedido e o status

Um pedido é um objeto com seis campos. O id identifica; o cliente dá o nome; os itens dizem o que preparar; o total é o valor a cobrar; o status é a etapa. O horário serve para ordenar a fila, e é o campo que a cozinha mais olha depois do status.

pedido
Um objeto com os dados de uma linha do painel: { id, cliente, itens, total, status, horario }.
status
Um dos três textos: "novo", "preparando", "entregue". É o que o filtro compara e o botão avança.
itens
Um resumo legível do pedido: "2 pães e 1 café". Num app completo, seria uma lista de produtos com quantidade.
total
O valor do pedido, em número. Formatação só na tela, como no carrinho.
horario
O texto "07:10" que ordena a fila. Aqui é dado de mentira; num app real, viria do servidor em formato de data.

Com a forma definida, os pedidos iniciais ficam assim:

const pedidosDaApi = [
  { id: 101, cliente: "Marta", itens: "2 pães e 1 café", total: 4.5, status: "novo", horario: "07:10" },
  { id: 102, cliente: "João", itens: "1 bolo de cenoura", total: 12, status: "novo", horario: "07:25" },
  { id: 103, cliente: "Clara", itens: "6 pães de queijo", total: 9, status: "preparando", horario: "07:40" },
  { id: 104, cliente: "Rita", itens: "3 pães franceses", total: 3, status: "entregue", horario: "08:05" },
];

O status é o campo que mais aparece no código, então vale definir as transições antes de escrever a tela. A tabela é a regra do negócio, e o botão de avançar é só a implementação dela:

StatusO que significa na cozinhaO que o botão faz
novochegou e ninguém começouvira preparando
preparandoestá no forno ou sendo montadovira entregue
entreguesaiu para o clientenão muda mais

A última linha é defesa contra dado ruim. Um status desconhecido não deve quebrar a tela nem virar undefined: o mapa de transições devolve o próprio status quando não encontra o próximo. É uma linha de código que evita um erro estranho no meio do expediente.

3. A carga simulada

Não há rede no quadro onde as caixas rodam, então a API é simulada com uma promessa que resolve depois de um tempo. A estrutura é exatamente a de um fetch: uma função que devolve promessa, um estado para a lista, um para o carregando e um para o erro.

Na caixa abaixo, a carga funciona mas o carregando nunca desliga: a tela fica em "Carregando pedidos…" para sempre, mesmo com os dados já no estado. Esse é o bug mais comum de quem começa com promessa. Conserte desligando o carregando no finally:

A lista chega, mas a tela continua em "Carregando pedidos…". Desligue carregando quando a promessa terminar — no .then, no .catch ou, melhor, no .finally.

const pedidosDaApi = [
  { id: 101, cliente: "Marta", status: "novo" },
  { id: 102, cliente: "João", status: "novo" },
  { id: 103, cliente: "Clara", status: "preparando" },
];

function buscarPedidos() {
  return new Promise((ok) => setTimeout(() => ok(pedidosDaApi), 50));
}

function App() {
  const [pedidos, setPedidos] = useState([]);
  const [carregando, setCarregando] = useState(false);

  function carregar() {
    setCarregando(true);
    buscarPedidos().then((lista) => {
      setPedidos(lista);
    });
  }

  if (carregando) return <p>Carregando pedidos…</p>;

  return (
    <div>
      <button onClick={carregar}>Carregar pedidos</button>
      <p>{pedidos.length} pedidos</p>
      <ul>
        {pedidos.map((pedido) => (
          <li key={pedido.id}>{pedido.cliente}</li>
        ))}
      </ul>
    </div>
  );
}

Clique em Carregar pedidos: a tela mostra o carregando por um instante e depois a lista com três nomes. O finally roda nos dois caminhos, sucesso e falha, e é por isso que ele é o lugar certo para desligar o carregando. Se você desligar só no then, um erro deixa a tela presa para sempre.

O console mostra a ordem em que os estados mudam durante a carga:

Num app de verdade, a função muda pouco:

function buscarPedidos() {
  return fetch("https://loja.test/api/pedidos").then((resposta) => {
    if (!resposta.ok) throw new Error("falha na rede");
    return resposta.json();
  });
}

function carregar() {
  setCarregando(true);
  setErro(null);
  buscarPedidos()
    .then((lista) => setPedidos(lista))
    .catch(() => setErro("Não foi possível carregar os pedidos"))
    .finally(() => setCarregando(false));
}

O catch é o que separa erro de vazio — a aula de carregando e erro mostra a mesma tela com fetch de verdade. Com ele, a tela pode mostrar "Não foi possível carregar" e um botão "Tentar de novo" que chama carregar outra vez. Sem ele, a promessa rejeitada some no console e a tela fica em "Carregando" para sempre — o mesmo sintoma do bug que você acabou de consertar, com outra causa.

Ordem das condições na tela: carregando primeiro, erro depois, vazio depois, lista por último. Cada uma responde a uma pergunta diferente, e misturá-las produz mensagens erradas — "Nenhum pedido" enquanto os dados ainda vêm, por exemplo.

4. A lista e o filtro por status

Com os pedidos no estado, a lista é um map com uma key por id. O filtro é um estado separado que guarda o status escolhido — incluindo "todos" — e uma conta que decide quem aparece. A regra de ouro é a mesma da galeria: filtrar não altera o array original.

Na caixa abaixo, os botões mudam o filtro e a lista ignora: os quatro pedidos aparecem sempre. Faça a conta de visiveis e use essa lista no map:

Os botões mudam filtro, mas a lista mostra sempre todos. Calcule visiveis a partir do filtro (deixe passar quando for "todos") e desenhe os cartões com essa lista.

5. Avançar o status

Avançar é trocar um pedido por outro com o status seguinte. O mapa de transições diz qual é o próximo, e o map devolve a lista com o pedido trocado. O erro clássico é o mesmo de sempre: mudar o campo no objeto e entregar o mesmo array ao set.

Na caixa abaixo, clicar em Avançar não muda a contagem de "preparando". Conserte trocando a mutação por um map com objeto novo:

O avancar muda o objeto no lugar e a tela não atualiza. Use map para devolver { ...pedido, status: novoStatus } no pedido clicado e a lista nova em setPedidos.

const pedidosDaApi = [
  { id: 101, cliente: "Marta", status: "novo" },
  { id: 102, cliente: "João", status: "novo" },
  { id: 103, cliente: "Clara", status: "preparando" },
];

const proximo = { novo: "preparando", preparando: "entregue" };

function App() {
  const [pedidos, setPedidos] = useState(pedidosDaApi);

  function avancar(id) {
    const pedido = pedidos.find((p) => p.id === id);
    pedido.status = proximo[pedido.status] || pedido.status;
    setPedidos(pedidos);
  }

  const preparando = pedidos.filter((p) => p.status === "preparando").length;

  return (
    <div>
      <p className="resumo">
        novos: {pedidos.filter((p) => p.status === "novo").length} · preparando: {preparando}
      </p>
      <ul>
        {pedidos.map((pedido) => (
          <li key={pedido.id} className="pedido" data-status={pedido.status}>
            <strong>{pedido.cliente}</strong>
            <button className="avancar" onClick={() => avancar(pedido.id)}>
              Avançar
            </button>
          </li>
        ))}
      </ul>
    </div>
  );
}

Clique em Avançar na Marta: o status dela vira preparando, a contagem do topo vai para "preparando: 2" e o data-status do cartão muda. O resumo é derivado do array — não há um segundo estado para manter em sincronia.

avancar
Recebe o id do pedido. Devolve a lista com aquele pedido no status seguinte.
proximo
O mapa de transições: { novo: "preparando", preparando: "entregue" }. Quem não está no mapa fica como está.
data-status
Atributo do li com o status atual. Aparece no HTML gerado e serve de seletor para CSS e para teste.
resumo
A linha com as contagens por status. É uma conta feita no render, não estado.
status final
"entregue" não tem próximo: o botão continua na tela, mas não muda mais nada.

Uma decisão de interface que vale a pena: quando o status é final, o botão pode ficar desabilitado ou sumir. Um botão que não faz nada é pior que um botão ausente — a pessoa clica, nada acontece, e ela acha que o sistema travou. Se o pedido está entregue, mostre "Entregue" no lugar do botão.

6. As contagens e os números do topo

O painel tem quatro números que a Ana olha de longe: quantos pedidos novos, quantos preparando, quantos entregues e quanto já entrou de dinheiro. Nenhum deles é estado. Todos saem do mesmo array, com filter e reduce.

const novos = pedidos.filter((p) => p.status === "novo").length;
const preparando = pedidos.filter((p) => p.status === "preparando").length;
const entregues = pedidos.filter((p) => p.status === "entregue").length;
const faturamento = pedidos
  .filter((p) => p.status === "entregue")
  .reduce((soma, p) => soma + p.total, 0);

O faturamento conta só o que foi entregue. Se contasse tudo, o número incluiria pedidos que ainda podem ser cancelados — e a Ana tomaria decisão com dado errado. Regra de negócio também é uma decisão de código.

NúmeroDe onde saiQuando muda
novosfilter(status === "novo").lengthao carregar e ao avançar
preparandofilter(status === "preparando").lengthao avançar
entreguesfilter(status === "entregue").lengthao avançar
faturamentoreduce sobre os entreguesao avançar

Quatro filter sobre quatro itens é barato. Com mil pedidos, valeria uma passada só, contando tudo num objeto. Não otimize antes de doer: a legibilidade de quatro linhas separadas vale mais que a economia de três passadas enquanto a lista é pequena.

O console confirma as contas com a lista atual:

novos: 2
preparando: 1
entregues: 1
faturamento: 3

Se você quiser mostrar os números no topo com rótulo, a formatação é a mesma do carrinho: reais(faturamento). E cuidado com o plural: "1 novos" é feio. Uma função pequena resolve — {novos} novo{novos === 1 ? "" : "s"} —, e a Ana agradece.

7. Ordenar e o que quebra no painel

A fila da cozinha tem uma ordem natural: o pedido mais antigo primeiro. O sort resolve, mas com dois cuidados. O primeiro é que ele muda o array no lugar; numa lista do estado, isso é mutação disfarçada. O segundo é que, sem comparador, ele ordena como texto.

const emOrdem = [...pedidos].sort((a, b) =>
  a.horario.localeCompare(b.horario)
);

O spread cria uma lista nova antes de ordenar; o localeCompare compara os horários como texto, o que funciona para "07:10" e "08:05". Se a lista já vem ordenada do servidor, você não precisa de nada disso — e essa é a solução mais comum em produção.

A quarta linha é sutil. Ao avançar um pedido já entregue, proximo["entregue"] é undefined, e sem a reserva o status do pedido seria apagado. Com || pedido.status, ele continua entregue. A reserva custa quatro palavras e evita um bug de dado.

Uma última armadilha: key com índice. Ao filtrar, os pedidos visíveis mudam de posição, e o React reaproveitaria cartões errados — o status de um aparecendo no outro. O id é estável e resolve. O mesmo vale para a key do resumo por status, se você renderizar uma lista de contadores.

8. Cenários do dia a dia

Cenário 1: o painel abre vazio e a Ana acha que perdeu os pedidos

A tela mostrava "Nenhum pedido ainda" no primeiro segundo, antes de a promessa resolver. O estado inicial da lista é vazio — isso não quer dizer que não há pedidos, quer dizer que a resposta ainda não chegou. Com a condição de carregando na frente, a mensagem de vazio só aparece depois da resposta. Ordem de condição muda o significado da tela.

Cenário 2: dois cliques rápidos no Avançar pulam uma etapa

A Ana clicou duas vezes no mesmo pedido e ele foi de "novo" para "entregue" sem passar por "preparando". Cada clique lê o estado do render atual; dois cliques antes do próximo desenho podem aplicar a mesma transição duas vezes. A cura é calcular o próximo status dentro do set, com função atualizadora: setPedidos((atual) => ...). O assunto tem aula própria, mas o sintoma vale reconhecer.

Cenário 3: o faturamento conta pedido que ainda está no forno

Ela somou todos os totais e o número do dia ficou maior que o caixa. Pedido preparando ainda pode ser cancelado e não é dinheiro no bolso. O filtro por "entregue" antes do reduce resolve. Número de painel é decisão de negócio tanto quanto código: some o que já aconteceu, não o que pode acontecer.

Complete a linha que devolve o status seguinte, com reserva para quem já está no fim. Escreva só o método do objeto que guarda as transições (o trecho entre colchetes):

const novoStatus = proximo[] || pedido.status;

Dica: é a chave do mapa, ou seja, o status atual do pedido. Sem a reserva || pedido.status, um pedido já entregue ficaria com status undefined.

10. Resumo

O painel começa pelos dados: cada pedido tem id, cliente, itens, total, status e horário. A lista chega por uma promessa simulada com setTimeout, e a tela tem três estados de carga — carregando, erro e pronto — mais o vazio, com mensagem própria. O finally desliga o carregando nos dois caminhos.

O filtro é estado; a lista visível é conta. Avançar o status é map com um objeto novo, e o mapa de transições com || pedido.status protege contra status desconhecido. As contagens e o faturamento saem de filter e reduce no render, e a ordenação pede uma cópia antes do sort.

Com isso, os quatro projetos do nível estão de pé: lista de tarefas, galeria, carrinho e painel. Todos usam o mesmo esqueleto — estado, handler, conta, lista e vazio — com um ingrediente diferente em cada um. O próximo passo é juntar os pedaços num app com rotas e dados vindos de uma API de verdade, no nível 3. Se quiser revisar a parte de rede, a aula de fetch mostra a mesma promessa com resposta real, e a de ordenar detalha o comparador.

Para lembrar

  • Pedido: { id, cliente, itens, total, status, horario }; status é texto curto.
  • Promise + setTimeout simulam a rede; fetch é o mesmo desenho.
  • Carregando desliga no finally; erro tem catch e botão de tentar de novo.
  • Ordem da tela: carregando, erro, vazio, lista.
  • Filtro é estado; lista visível é filter no render.
  • Avançar é map com { ...pedido, status: proximo[status] }.
  • Contagens e faturamento são contas, não useState.
  • sort muta: copie com [...pedidos] antes.
  • data-status no cartão ajuda o CSS e o teste.
  • Status final merece botão desabilitado ou ausente.
