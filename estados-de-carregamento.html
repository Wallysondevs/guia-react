Estados de Carregamento

A Ana reparou numa coisa no site da padaria: quando a busca demora, a tela fica igual à tela de "nada encontrado". A cliente digita "brioche", espera, e o silêncio da página diz a ela que não existe brioche. Algumas aulas atrás o carregando apareceu pela primeira vez, colado no erro. Hoje o assunto é a forma dele: quantos estados a tela tem de verdade, o que fazer na segunda busca (quando já existe resultado na tela), como um botão avisa que está trabalhando e por que três retângulos cinzas comunicam mais do que a palavra "Carregando".

Você vai aprender
  • Os quatro estados de uma tela que busca dados.
  • Por que uma variável de status vale mais do que três booleanos.
  • Como atualizar sem apagar o que já está na tela.
  • O botão que se desabilita e troca o rótulo enquanto salva.
  • Esqueleto, spinner ou texto: quando cada um serve.
  • Como garantir que o carregando sempre termine.

1. A cena: o silêncio que parece resposta

Existe uma diferença enorme entre "não achei nada" e "ainda estou procurando", e a tela em branco comunica a primeira quando deveria comunicar a segunda. A Ana levou um tempo para perceber que o problema não era a busca estar lenta: era a página não dizer que estava ocupada. Quem não sabe que o site está trabalhando clica de novo, ou pior, vai embora achando que a padaria não tem o produto.

Resolver isso é menos sobre spinner e mais sobre contar a verdade em cada momento. Uma tela que busca dados tem quatro situações possíveis, e cada uma pede um desenho diferente: ainda não pedi nada, estou pedindo, chegaram os dados, deu erro. Quatro, não dois. Quando o código guarda só "carregando" e "dados", os outros dois viram improviso — e é aí que nascem as telas confusas.

Esta aula é sobre a forma do carregamento, não sobre a busca em si. O fetch, o await e o try/catch já foram vistos; aqui eles entram prontos, como pano de fundo.

2. Quatro estados, uma variável

A tentação de quem começa é criar um booleano para cada coisa: carregando, temErro, temDados. Funciona até o dia em que dois deles ficam verdadeiros ao mesmo tempo — a tela mostra "Carregando" e a mensagem de erro juntas, ou a lista e o aviso de vazio. Três booleanos têm oito combinações; só quatro fazem sentido.

O jeito que não mente é uma única variável de texto, com os quatro valores possíveis. Ela só pode estar num estado por vez, e é isso que se quer:

const [estado, setEstado] = useState("ocioso"); // "ocioso" | "carregando" | "pronto" | "erro"

Com um estado só, o desenho fica direto: um if para cada caso, e nunca dois pedaços de tela contraditórios. As transições também ficam explícitas — pedir é setEstado("carregando"), chegar é setEstado("pronto"), falhar é setEstado("erro"). Quando você lê o código, sabe exatamente quais são os caminhos.

Quem tem o hábito de derivar em vez de guardar ganha um atalho: dá para calcular o estado a partir dos dados que já existem, sem criar mais nenhum. Se você guarda a lista e o erro, o carregando pode ser deduzido — "lista vazia e sem erro" é a primeira busca em andamento. O risco é justamente quando a dedução mente: uma busca que legitimamente voltou vazia fica idêntica a uma busca que ainda não terminou. Por isso o estado explícito costuma compensar.

ocioso
Nada foi pedido ainda. A tela mostra o convite: "digite o nome do pão".
carregando
O pedido está no ar. A tela mostra que está trabalhando — esqueleto, texto ou botão em espera.
pronto
Os dados chegaram. A tela mostra a lista, mesmo que ela esteja vazia.
erro
A busca falhou. A tela mostra o que aconteceu e o caminho de volta.
atualizando
Variante do carregando em que já existe conteúdo na tela: mantém o conteúdo e avisa por cima.
aria-busy
Atributo que avisa leitores de tela que a região está carregando.

3. A segunda busca: atualizar sem apagar

A primeira carga pode mostrar esqueleto. A segunda não: se a lista já está na tela e a pessoa clica em "Atualizar", apagar tudo e mostrar "Carregando" é um piscar que assusta. O conteúdo antigo é melhor que o vazio, e o aviso de atualização pode conviver com ele.

Na caixa abaixo, a função de carregar limpa a lista antes de pedir. O resultado você já sabe: a vitrine some por um instante. A missão é parar de limpar e deixar o aviso aparecer junto da lista.

Ao clicar em Atualizar, a lista desaparece e volta. Tire o setPaes([]) e mostre o aviso de atualização sem esconder a lista: use {carregando && ...} e mantenha o <ul> sempre renderizado.

function buscarPaes(espera) {
  return new Promise((ok) => {
    setTimeout(() => ok(["Pão francês", "Croissant", "Brioche"]), espera);
  });
}

function App() {
  const [paes, setPaes] = useState([]);
  const [carregando, setCarregando] = useState(true);

  function carregar(espera) {
    setPaes([]);
    setCarregando(true);
    buscarPaes(espera).then((lista) => {
      setPaes(lista);
      setCarregando(false);
    });
  }

  useEffect(() => {
    carregar(10);
  }, []);

  return (
    <div>
      <h1>Vitrine</h1>
      {carregando ? (
        <p className="aviso">Carregando...</p>
      ) : (
        <ul>
          {paes.map((p) => (
            <li key={p}>{p}</li>
          ))}
        </ul>
      )}
      <button onClick={() => carregar(400)}>Atualizar</button>
    </div>
  );
}

Depois do clique, a lista continua com os três pães e o aviso "Atualizando..." aparece em cima. Quando a resposta chega, a lista troca e o aviso sai. Nada pisca. O pedido aqui demora de propósito, para que você veja o estado intermediário; no dia a dia, é essa diferença que separa um site que parece sólido de um que parece nervoso.

O nome desse padrão, se você encontrar em texto em inglês, é stale-while-revalidate: mostrar o dado velho enquanto o novo chega. Bibliotecas de dados fazem isso por padrão, e o motivo é o de sempre — o usuário prefere informação de um segundo atrás a uma tela vazia.

4. O botão que avisa que está trabalhando

Carregamento não é só lista. Toda ação que demora — salvar, enviar, apagar — precisa do mesmo cuidado, e o alvo é o próprio botão. Ele deve ficar desabilitado, para não receber dois cliques, e trocar o rótulo, para dizer o que está acontecendo.

Ao clicar em Salvar, o botão continua igual e aceita mais cliques. Use disabled={salvando} e troque o texto para "Salvando..." enquanto o pedido está no ar.

function salvarPedido() {
  return new Promise((ok) => {
    setTimeout(() => ok({ id: 7 }), 400);
  });
}

function App() {
  const [salvando, setSalvando] = useState(false);
  const [recado, setRecado] = useState("");

  function salvar() {
    setSalvando(true);
    salvarPedido().then((r) => {
      setRecado("Pedido " + r.id + " salvo");
      setSalvando(false);
    });
  }

  return (
    <div>
      <h1>Encomenda</h1>
      <button onClick={salvar}>Salvar</button>
      {recado && <p>{recado}</p>}
    </div>
  );
}

O painel mostra o botão com o atributo disabled e o texto novo. São duas informações diferentes: o disabled protege o servidor de receber o mesmo pedido duas vezes; o rótulo explica, para quem está olhando, por que o clique não respondeu. Um sem o outro gera dúvida — botão mudo que não reage parece defeito.

Uma armadilha clássica: desabilitar o botão e esquecer de reabilitar quando o pedido falha. O setSalvando(false) tem de estar em todos os caminhos — no sucesso e no erro. É o mesmo raciocínio do finally que a aula de carregando mostrou: o estado de carregamento é uma promessa que você faz ao usuário, e precisa ser cumprida mesmo quando dá errado.

5. Esqueleto, spinner ou texto

Existem três desenhos para o mesmo aviso, e a escolha depende do que está chegando. Texto é o mais simples e o mais honesto: "Carregando os pães...". Spinner é um círculo girando, que diz "estou ocupado" sem dizer o quê. Esqueleto são retângulos cinzas com o formato do conteúdo, que dizem "vem uma lista de três itens aqui".

A primeira carga mostra só o texto "Carregando...". Troque por três esqueletos: três <div className="esqueleto"></div> no lugar do parágrafo.

function buscarCardapio() {
  return new Promise((ok) => {
    setTimeout(() => ok(["Pão francês", "Croissant"]), 400);
  });
}

function App() {
  const [itens, setItens] = useState([]);

  useEffect(() => {
    buscarCardapio().then((lista) => setItens(lista));
  }, []);

  return (
    <div>
      <h1>Cardápio</h1>
      {itens.length === 0 && <p>Carregando...</p>}
      <ul>
        {itens.map((i) => (
          <li key={i}>{i}</li>
        ))}
      </ul>
    </div>
  );
}

O esqueleto precisa ter a forma do que vem: três blocos para três pães, um bloco largo para um parágrafo, um círculo para um avatar. Esqueleto genérico é pior que texto, porque promete um formato que não chega. E ele é branco e cinza no CSS, de propósito: quem desenha o esqueleto é a folha de estilo, não o JSX.

A última linha é séria: mostrar carregando por 30 milissegundos produz um piscar pior que a espera. Se a resposta é rápida, o melhor é não anunciar nada. Quando a resposta é imprevisível, vale a pena atrasar o aviso — mostrar o esqueleto só depois de uns 200 milissegundos —, e há até um hook do React para adiar atualizações que não são urgentes, o useTransition, para casos em que a tela precisa continuar respondendo enquanto os dados chegam.

6. O carregando que sempre termina

A regra de ouro: para cada setCarregando(true) existe um caminho de volta. Se o pedido pode falhar, o catch também desliga; se pode ser cancelado, o cancelamento desliga; se a tela pode ser desmontada, tanto faz — o estado morre junto. O que não pode é o caminho do erro esquecer o desligamento.

async function carregar() {
  setCarregando(true);
  try {
    const lista = await buscarPaes();
    setPaes(lista);
  } catch (e) {
    setErro(e.message);
  } finally {
    setCarregando(false);
  }
}

O finally é o que garante o desligamento nos dois desfechos. Sem ele, cada catch teria de lembrar de desligar, e um esquecimento deixa a tela girando para sempre. É um dos poucos lugares em que o finally é obrigatório na prática.

Para enxergar o que acontece de verdade, um console.log no topo do componente mostra a ordem dos estados. É o jeito mais rápido de descobrir um piscar:

> render: carregando=true
> render: carregando=false, itens=3
> render: carregando=true
> render: carregando=false, itens=3

Cada par dessas linhas é uma busca: acende e apaga. Se aparecer carregando=false, itens=0 entre eles, é sinal de que a lista foi limpa no meio do caminho — exatamente o piscar da seção 3. E se o segundo false nunca chegar, você encontrou o carregando eterno.

7. Carregando por pedaço

Em uma tela grande, um único "carregando" para tudo é ruim: a página inteira espera o pedaço mais lento. O melhor é cada região cuidar do seu estado, com o seu próprio booleano ou status. O cabeçalho aparece na hora, as promoções aparecem quando chegam, o horário idem.

Isso também evita o efeito colateral mais chato de um carregando global: desmontar o formulário. Se a pessoa está digitando o endereço e um pedido de outra parte da tela termina, você não pode redesenhar o campo — ela perde o que digitou. Estados separados resolvem; um estado só para a página inteira, não.

Um exemplo concreto do que evitar: a tela de encomenda tem o formulário de endereço e, do lado, a lista de sugestões que carrega enquanto a pessoa digita. Se o carregando das sugestões controlar a tela inteira, cada letra digitada pode redesenhar o formulário — e o cursor pula, o texto some, a pessoa desiste. Com estados separados, as sugestões acendem e apagam sozinhas e o formulário fica quieto.

E vale marcar a região com aria-busy. É um atributo que leitores de tela entendem e que não muda nada visualmente: ele avisa que aquela parte está em movimento. É o tipo de detalhe que ninguém nota quando existe e todo mundo nota quando falta.

8. Três decisões que dão o tom

Primeira: onde o carregando aparece. No topo da lista, no meio dela, no botão, ou numa tarja fixa? O lugar deve ser onde o olho já está — quem clicou em Atualizar olha para a lista; quem clicou em Salvar olha para o botão. Aviso longe do ponto de ação passa despercebido.

Segunda: por quanto tempo. Um carregando breve é melhor nem aparecer; um carregando longo precisa de mais do que três pontinhos, precisa de contexto — "buscando os pães de hoje". Se a espera passa de alguns segundos, diga o que está acontecendo e dê uma saída: cancelar, tentar de novo, falar no WhatsApp.

Terceira: o que fica na tela. Se há conteúdo antigo, mantenha (seção 3). Se não há, mostre a forma do que vem (esqueleto) ou um texto curto. O que nunca serve é o vazio sem explicação, que o usuário interpreta como resposta negativa.

9. Cenários do dia a dia

Cenário 1: a lista que piscava a cada filtro

A Ana tinha um filtro por categoria e, a cada clique, a lista era zerada e o esqueleto reaparecia. Em conexão rápida, era um piscar de olhos; no celular, meio segundo de nada. A correção foi manter a lista anterior enquanto a nova chega e mostrar um aviso pequeno. O mesmo padrão da seção 3, aplicado a um filtro em vez do botão de atualizar.

Cenário 2: dois pedidos, um pedido de desculpas

O botão de salvar não desabilitava, e a cliente tocou duas vezes. O servidor recebeu dois pedidos e a padaria assou dois bolos. O conserto foi disabled={salvando} mais o rótulo "Salvando...". Se o pedido falhar, o botão precisa voltar a funcionar com uma mensagem honesta: "não deu para salvar, tente de novo".

Cenário 3: o esqueleto com forma errada

Ela colocou um esqueleto de três linhas e o conteúdo real era uma tabela de cinco colunas. Quando os dados chegavam, o layout saltava e o texto se reorganizava. O esqueleto precisa ter a mesma forma do conteúdo; se o formato é imprevisível, um texto curto é mais honesto do que uma promessa que não se cumpre.

11. Resumo

Uma tela que busca dados tem quatro estados — ocioso, carregando, pronto e erro —, e uma única variável de status evita as contradições de três booleanos. Cada estado pede um desenho: convite, aviso, conteúdo ou mensagem com saída. O importante é nunca deixar o usuário no escuro nem no vazio.

Na segunda busca, mantenha o conteúdo antigo e avise por cima; apagar para mostrar "Carregando" produz o piscar que passa impressão de instabilidade. Em ações pontuais, o alvo é o botão: desabilitar para não receber dois cliques e trocar o rótulo para explicar a espera — sempre com um caminho de volta, inclusive no erro.

Esqueleto quando a forma do conteúdo é previsível, spinner em ação pontual, texto quando a espera é curta ou o formato é incerto, e nada quando a resposta é rápida. Cada região cuida do seu carregando, e a aria-busy avisa quem não vê a tela. Na próxima aula, o outro lado: o que a tela mostra quando a busca dá errado, e como escolher a mensagem certa para cada tipo de falha.

Para lembrar

  • Quatro estados: ocioso, carregando, pronto, erro.
  • Um status de texto vale mais que três booleanos.
  • Atualizar não apaga: mantenha a lista e avise.
  • Botão que salva fica desabilitado e muda o rótulo.
  • finally garante que o carregando desliga.
  • Esqueleto com a forma do conteúdo que vem.
  • Espera curta não precisa de aviso.
  • Cada região tem o seu próprio carregando.
