Como Ele Funciona

Na aula passada a Ana entendeu por que usar React. Agora ela quer saber como: o que acontece entre o clique em Rodar e aquele HTML aparecendo no painel? Se você já ficou incomodado com a sensação de que React é mágica, esta aula é o truque revelado. Não tem mágica nenhuma: tem uma tradução, um objeto, uma raiz e uma comparação. Quatro passos, todos visíveis se você souber onde olhar.

Você vai aprender
  • O que o JSX vira depois de traduzido, e quem faz essa tradução.
  • Que o JSX não cria a tela: ele cria um objeto que descreve a tela.
  • O papel do react-dom: pegar esse objeto e montar no navegador.
  • O que é a raiz (createRoot) e a linha de render que liga tudo.
  • Quem chama o seu componente — e por que não é você.
  • Como o React atualiza só o que mudou, em vez de redesenhar a página.

1. A cena: entre o clique e o HTML

O botão Rodar já foi clicado umas trinta vezes na frente da Ana, e ela nunca pensou no que acontece nesse meio. O texto que ela escreveu vira HTML na tela; parece direto, mas não é. Entre o código e o painel existem quatro estações, e cada uma faz um trabalho diferente.

Entender essas estações resolve três tipos de dúvida que voltam sempre: por que existe um passo de "compilar", por que o React reclama de alguma coisa que parece certa, e por que a tela não pisca inteira quando um número muda. É o tipo de conhecimento que não muda o seu dia hoje e economiza um dia inteiro no futuro.

Vamos por partes, na ordem em que as coisas acontecem.

2. JSX é JavaScript com roupa de HTML

O bloco abaixo parece HTML. Não é. Repare que ele está dentro de uma função e que o return devolve aquilo como se fosse um valor — HTML não funciona assim, e é por isso que essa escrita tem nome próprio: JSX.

function App() {
  return (
    <div className="cartao">
      <h1>Padaria da Ana</h1>
      <p>Aberto das 6h às 18h</p>
    </div>
  );
}

O navegador não sabe ler isso. Ele sabe ler JavaScript. Então existe uma ferramenta que traduz o JSX para JavaScript antes de qualquer coisa rodar. Aqui no guia essa ferramenta é o Babel; num projeto de verdade, é um plugin do Vite fazendo o mesmo serviço. Traduzir, nesse caso, é bem literal: cada tag vira uma chamada de função.

function App() {
  return React.createElement("div", {
    className: "cartao"
  }, React.createElement("h1", null, "Padaria da Ana"), React.createElement("p", null, "Aberto das 6h às 18h"));
}

Essa é a tradução de verdade, sem enfeite. Os comentários que o Babel costuma colocar (/*#__PURE__*/) foram removidos para não atrapalhar a leitura. Repare no formato de createElement: primeiro o tipo ("div"), depois os atributos ({ className: "cartao" }) e depois os filhos, um a um. Aquele null ali é onde ficariam atributos quando não há nenhum.

É por isso que o JSX não é HTML: ele é uma escrita mais curta para essas chamadas. O navegador nunca vê o seu <div className="cartao">; ele vê o resultado da tradução. Guardar isso explica metade dos erros de sintaxe do guia: o compilador reclama do JSX porque é ele quem precisa dar conta da tradução, e algumas coisas que o HTML aceita não têm tradução válida.

3. O JSX vira um objeto simples

Agora o passo que mais surpreende: React.createElement não cria um elemento na página. Ele devolve um objeto — uma descrição do que você quer. Esse objeto tem três campos, e só isso: o tipo, os atributos e os filhos.

Dá para ver com os próprios olhos. No código abaixo, o JSX é guardado em uma variável e impresso no console antes de ser devolvido:

Guarde o JSX em titulo e mande o elemento inteiro para o console com console.log(titulo). Depois imprima também o texto de dentro: console.log(titulo.props.children).

function App() {
  const titulo = <h1>Pão quentinho</h1>;
  return titulo;
}
<h1>Pão quentinho</h1>

function App() {
  const titulo = <h1>Pão quentinho</h1>;
  console.log(titulo);
  console.log(titulo.props.children);
  return titulo;
}

O painel mostra o HTML e, embaixo, o que foi para o console. A primeira linha do console é o objeto inteiro, e é ela que interessa:

console: {"type":"h1","key":null,"ref":null,"props":{"children":"Pão quentinho"}}
console: Pão quentinho

Leia com calma, porque é o coração da aula. Não há DOM ali, não há página, não há HTML: há um objeto com type valendo "h1" e um props com children valendo "Pão quentinho". Se você quisesse, poderia escrever esse objeto à mão — o React aceitaria do mesmo jeito. O JSX é só um jeito confortável de montá-lo.

Isso tem uma consequência importante: criar um elemento React é barato. É só um objeto na memória do JavaScript. Você pode criar milhares deles sem tocar na tela. Quem toca na tela é a próxima estação.

elemento
O objeto que descreve uma peça da tela: { type, props }. Não é o nó do DOM; é a receita dele.
componente
A função que devolve elementos. Quando o type de um elemento é uma função, o React a chama para saber o que vem no lugar.
raiz (root)
O ponto da página onde o React manda montar. É um elemento do HTML escolhido por você.
react-dom
A parte do React que conversa com o navegador: transforma elementos em nós de verdade e atualiza o DOM.
reconciliação
A comparação entre a descrição anterior e a nova, para descobrir o mínimo a mudar no DOM.

4. Quem desenha o objeto é o react-dom

Se o elemento é só um objeto, alguém precisa pegar esse objeto e construir elementos de verdade na página. Esse alguém é o react-dom, a parte do React feita para o navegador. O react cuida de componentes, elementos e estado; o react-dom cuida da página.

A divisão não é detalhe de organização: é o que permite o mesmo React desenhar em lugares diferentes. No celular, o react-native faz o papel do react-dom criando componentes nativos em vez de tags. No servidor, outra peça gera uma string de HTML. O núcleo é o mesmo — muda quem desenha.

Para o react-dom trabalhar, ele precisa de duas informações: o que desenhar (o elemento) e onde desenhar (a raiz). O "onde" é um elemento do HTML, geralmente uma div vazia com um id. É ali que o React vai morar: ele não toma conta da página inteira, toma conta daquele pedaço.

Aqui no guia, a caixa já tem esse pedaço pronto: uma <div id="raiz"></div> esperando. Por isso, no modo normal, você só escreve o componente e o motor faz a ligação. No modo manual, você mesmo escreve a ligação — e é o que vamos fazer agora.

5. A raiz e a linha que monta

Este é o trecho que existe em todo projeto React do mundo, geralmente em um arquivo chamado main.jsx. Duas linhas: uma cria a raiz, a outra manda desenhar. No código abaixo, a segunda está faltando — e sem ela, nada aparece.

A raiz já foi criada, mas ninguém mandou desenhar. Acrescente a linha root.render(<App />); no fim do arquivo.

function App() {
  return <h1>Padaria da Ana</h1>;
}

const raiz = document.getElementById("raiz");
const root = ReactDOM.createRoot(raiz);
(o React não desenhou nada: o componente devolveu null?)

function App() {
  return <h1>Padaria da Ana</h1>;
}

const raiz = document.getElementById("raiz");
const root = ReactDOM.createRoot(raiz);
root.render(<App />);

Antes de rodar, o painel diz que nada foi desenhado. É a verdade: existia uma raiz, mas ninguém pediu nada para ela. Depois de acrescentar a linha, o <h1> aparece. Repare também no detalhe de document.getElementById("raiz"): o id tem de ser o mesmo da div do HTML. Se errar o nome, o React reclama de um jeito pouco amigável — e a causa quase sempre é essa.

Num projeto de verdade, essas linhas aparecem assim, com o import no topo:

import { createRoot } from "react-dom/client";
import App from "./App.jsx";

createRoot(document.getElementById("root")).render(<App />);

Duas diferenças em relação à caixa, e as duas são só de arrumação. A primeira: o createRoot vem de um import, porque num projeto cada peça é um arquivo. A segunda: o id costuma ser root, porque é o que o Vite escreve no index.html; aqui a caixa usa raiz. Fora isso, é a mesma ideia: pegue o elemento e mande desenhar na raiz.

6. Quem chama o componente é o React

Uma coisa que confunde muito: você escreve function App() e nunca escreve App() em lugar nenhum. Quem chama é o React, na hora de desenhar. É por isso que o componente pode calcular coisas no começo da função: ele está sendo executado, e não apenas declarado.

Dá para provar com console.log. No código abaixo, uma linha solta roda assim que o arquivo é executado; a linha de dentro do App só roda quando o React vai desenhar. A ordem no painel mostra quem manda em quem.

Acrescente console.log("App rodou") dentro do App, antes do return, e rode. Observe a ordem das duas linhas do console.

console.log("antes do React montar");

function App() {
  return <p>Pão quentinho</p>;
}
<p>Pão quentinho</p>
console: antes do React montar

console.log("antes do React montar");

function App() {
  console.log("App rodou");
  return <p>Pão quentinho</p>;
}

O painel mostra o HTML e, embaixo, as duas linhas na ordem em que aconteceram:

console: antes do React montar
console: App rodou

Primeiro o arquivo inteiro roda — é aí que a função App é só definida, sem executar. Só depois o React chama App(), recebe o elemento e monta. Se você escrevesse App() você mesmo, teria um elemento solto na mão e nada na tela; a tela só aparece porque alguém com acesso ao DOM recebeu aquele elemento.

Esse detalhe explica por que o componente roda de novo cada vez que algo muda: quem decide quando chamar é o React, não você. E é também o motivo de o componente precisar ser previsível: mesma entrada, mesma descrição de tela.

Há um comportamento que assusta quem está começando e que vale conhecer desde já. Em modo de desenvolvimento, um projeto React costuma ligar o StrictMode, um recurso que chama cada componente duas vezes de propósito. Não é bug: é um teste. Se o seu componente faz algo com efeito colateral — grava em algum lugar, busca dados, altera uma variável de fora —, a segunda chamada denuncia o problema na hora. Componente bem-comportado é aquele que, chamado duas vezes com os mesmos dados, devolve exatamente a mesma descrição. Aqui nas caixas isso não acontece: cada Rodar é uma execução só.

7. Quando algo muda: comparar e trocar o mínimo

Volte ao objeto do passo 3. Se os dados mudam, o React chama o componente de novo e recebe uma descrição nova — outro objeto, com outro texto. Agora ele tem duas descrições: a antiga e a nova. O trabalho passa a ser aplicar só a diferença na página.

Esse é o ponto que faz o React parecer mágico. Sem ele, a saída óbvia seria jogar fora todo o conteúdo da raiz e desenhar de novo — o que funciona, mas destrói o que a pessoa estava fazendo: o cursor do campo de texto, a posição da rolagem, a animação em andamento. Comparando, o React muda só o texto que mudou e o resto fica intacto.

Elemento React (o objeto)Nó do DOM (o elemento de verdade)

é tratado como imutável: para mudar, cria-se outroé mutável: dá para alterar com JavaScript

não sabe onde está na telasabe a posição, o tamanho e o que está em volta

Essa comparação é o que se chama de reconciliação. Você não precisa saber o algoritmo — e não precisa otimizar nada no começo. O que vale guardar é a consequência prática: no React você descreve a tela inteira de novo, sem medo de estar refazendo trabalho, porque quem faz o mínimo é ele. Quem tenta "ajudar" mexendo no DOM à mão costuma brigar com esse mecanismo.

8. O caminho completo, em quatro estações

Juntando tudo, o percurso de um componente é sempre o mesmo. A tabela abaixo serve como mapa para quando algo não aparecer na tela: descubra em qual estação o processo parou.

EstaçãoO que existeQuem fazSintoma de erro
1. JSX escritotexto no arquivo, ainda não é JavaScriptvocêerro de sintaxe do compilador
2. Traduçãochamadas de React.createElementBabel (ou Vite)"não compilou" com a linha do problema
3. Elementoum objeto { type, props }reactelemento com tipo errado: aparece texto estranho ou nada
4. Montagemnós de verdade dentro da raizreact-domraiz errada: nada aparece, ou erro do React

Note que os sintomas são bem diferentes, e é isso que torna o mapa útil. Um erro de sintaxe impede até a tradução: o componente nem chega a rodar. Um elemento com tipo errado roda normalmente e desenha outra coisa. Uma raiz errada é silenciosa: o componente roda, o objeto é criado, mas não há onde montar. São três mundos distintos, e o painel das caixas mostra qual deles você está vivendo.

Para investigar, o console é a ferramenta das estações 3 e 4. Imprimir o elemento mostra o objeto da estação 3; imprimir document.getElementById("raiz").innerHTML mostra o que o react-dom construiu na estação 4. Comparando os dois, você vê se o problema é o que você pediu ou o que foi montado. É primitivo e é o que funciona quando a tela teima.

Tem ainda um quarto caso, mais sutil: nada dá erro, o HTML aparece certo e a tela não muda como você esperava. Aí não é falha de React — é a sua descrição que não reflete os dados. Nesse momento vale imprimir os dados no console, que é a estação 3 vista por dentro.

9. Cenários do dia a dia

Cenário 1: "por que preciso de uma raiz?"

A Ana perguntou por que o React não cuida da página inteira. Porque a página pode ter outras coisas: um cabeçalho servido por outro sistema, um script de análise, um formulário antigo. A raiz é o contrato: "daqui para dentro é meu". Isso também permite ter duas raízes na mesma página — um widget de pedidos no meio de um site comum, por exemplo. O React não invade o que não é dele.

Cenário 2: "o HTML que eu escrevo some?"

Some, e é proposital. O conteúdo da raiz é substituído pelo que o React desenhar. Se você escrever um parágrafo dentro da div da raiz no HTML, ele não vai sobreviver à montagem. Para o conteúdo estático, use uma raiz ao lado; para o conteúdo que o React controla, descreva tudo dentro do componente. Misturar os dois é a receita de "cadê o texto que eu tinha escrito?".

Cenário 3: "a tela pisca quando muda?"

Não deveria, e quando pisca é sinal de que algo está sendo recriado. A comparação da estação 4 mantém os nós que não mudaram. O caso clássico de piscada é uma lista sem identificação: o React não sabe qual item é qual e recria todos. Isso se resolve com a key, que tem aula própria — mas já vale saber que o sintoma vem daí, e não do React ser lento.

10. Fixando o que ficou

1. O que o JSX devolve, depois de traduzido?

2. Quem constrói os elementos de verdade na página?

3. Quem chama a função do seu componente?

Exercício: a linha que monta

Complete a chamada que manda o React desenhar o componente dentro da raiz já criada:

const root = ReactDOM.createRoot(document.getElementById("raiz"));
root.(<App />);

Dica: é o método que recebe o elemento e o coloca na raiz. Sem ele, a raiz existe e fica vazia.

11. Resumo

O caminho é sempre o mesmo. Você escreve JSX; uma ferramenta traduz cada tag em React.createElement; essa chamada devolve um objeto simples, com type e props; e o react-dom pega esse objeto e constrói os nós de verdade dentro da raiz.

A raiz é uma div do HTML escolhida por você, e a linha de render é o contrato: "desenhe isto aqui". Sem render, a raiz existe e nada acontece. Com uma raiz errada, o componente roda e nada aparece. É por isso que o primeiro lugar para olhar, quando a tela fica vazia, é a ligação — e não o componente.

Quem chama o seu componente é o React, nunca você. Ele chama na montagem e chama de novo quando os dados mudam. Cada chamada produz uma descrição nova, e o React compara com a anterior para aplicar só a diferença no DOM — a reconciliação. Isso é o que mantém o campo de texto com o cursor no lugar e evita o pisca-pisca.

Guarde o mapa das quatro estações: sintaxe, tradução, elemento, montagem. Quando algo não aparecer, descubra em qual delas o processo parou, e você economiza a caçada. A próxima aula entra na estação 1, com as regras que o JSX precisa seguir para ser traduzido sem erro.

Para lembrar

  • JSX não é HTML: é uma escrita curta para React.createElement.
  • O Babel (ou o Vite) traduz; o navegador só vê JavaScript.
  • O resultado do JSX é um objeto { type, props }, não um nó da página.
  • Criar elementos React é barato; mexer no DOM é caro.
  • createRoot escolhe onde montar; render manda desenhar.
  • O id da raiz no HTML tem de ser o mesmo que você busca no código.
  • Quem chama o componente é o React; você só o define.
  • Na atualização, o React compara e troca só o que mudou.
