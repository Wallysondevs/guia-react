Buscar

A Ana tem uma lista de pães no site e um cliente por dia perguntando “tem pão de queijo?”. Ela responde de cabeça, mas a lista cresceu: agora são broa, sonho, brioche, croissant e mais uma dúzia de nomes. Procurar com o dedo na tela funciona até a terceira linha. Nesta aula ela aprende a busca de verdade: um campo onde a pessoa digita, um filtro que decide quem fica, e a lista original intacta o tempo inteiro.

Você vai aprender
  • Por que a busca é um filtro da lista, e não uma lista nova guardada no estado.
  • Como ligar o campo ao estado e filtrar a cada letra digitada.
  • O que o includes responde e por que ele diferencia maiúsculas.
  • Como buscar sem tropeçar em acento: normalize e toLowerCase.
  • Como procurar em dois campos, como nome e código.
  • O que mostrar quando nenhum item casa com a busca.
  • Como limpar a busca e voltar à lista completa.

1. A cena: procurar com o dedo na tela

O site da padaria mostra os pães em Cards, um abaixo do outro. Quando alguém pergunta por um pão específico, a Ana rola a página e lê os nomes. Com sete pães, isso leva dois segundos. Com trinta, leva uma eternidade — e ela sempre erra na terceira dobra, porque os nomes são parecidos: pão francês, pão de queijo, pão doce, pão integral.

A busca resolve esse problema de um jeito que parece mágica e é bem direto: enquanto a pessoa digita, o site mostra só os itens que combinam com o que foi digitado. Nada é enviado para lugar nenhum, nada é recarregado. A cada letra, o React redesenha a lista com menos itens.

O que confunde no começo é achar que a busca “cria” uma lista nova. Ela não cria: ela filtra a lista que já existe. A lista de pães continua com trinta itens; o que muda é quantos deles você manda desenhar. Guardar isso na cabeça evita a maior parte dos bugs desta aula — inclusive o clássico “limpei a busca e os pães não voltaram”.

Então o desenho é: um estado pequeno com o texto digitado, a lista completa guardada como está, e uma conta feita na hora de desenhar que decide quem aparece. Três peças, nenhuma mágica.

2. A busca é um filtro, não uma lista nova

Filtrar é escolher. O método de array que faz isso é o filter: ele recebe uma função, roda essa função para cada item e devolve um array novo só com os itens em que a função devolveu true. O array original não é tocado.

const paes = ["Pão de queijo", "Broa de fubá", "Sonho"];

const comQueijo = paes.filter((pao) => pao.includes("queijo"));

console.log(comQueijo);

O resultado é ["Pão de queijo"]. O array paes continua com os três itens, na mesma ordem. Essa é a diferença essencial entre filter e sort: o sort mexe na lista, o filter devolve outra. Guarde a comparação, porque ela explica por que a busca é segura de rodar quantas vezes for preciso.

Dentro do componente, o filtro acontece entre o estado e o map. A ordem das operações é sempre a mesma: primeiro você decide quem fica (filter), depois transforma cada um em elemento (map). Se inverter, você desenha tudo e esconde depois — funciona, mas é mais trabalho e mais difícil de ler.

E o filter precisa de uma resposta de sim ou não. É aí que entra o teste da próxima seção: o que exatamente significa “combina com o que foi digitado”.

3. O campo controlado, em duas linhas

Para saber o que a pessoa digitou, o campo precisa ser controlado pelo React: o valor vem do estado, e cada tecla avisa o estado para mudar. São duas linhas, e elas aparecem em qualquer busca do guia:

const [busca, setBusca] = useState("");

<input
  type="search"
  value={busca}
  placeholder="Buscar pão"
  onChange={(e) => setBusca(e.target.value)}
/>

value={busca} manda o estado para o campo. onChange recebe o evento e guarda e.target.value — o texto que está no campo agora — no estado. Sem o onChange, o campo fica travado e a pessoa não consegue digitar; sem o value, o estado e a tela podem discordar. A aula Entrada Controlada destrincha esse mecanismo; aqui basta reconhecer o par.

O estado inicial é uma string vazia, e isso importa: busca vazia significa “mostre tudo”. Um filter com critério vazio aceita todos os itens, porque toda string contém a string vazia. Essa coincidência feliz é o que faz a lista aparecer inteira antes de a pessoa digitar qualquer coisa.

Note também o type="search". Ele não muda a lógica, mas dá ao navegador a dica de que aquele campo é de busca: no celular, o teclado pode ganhar a tecla “buscar”; no desktop, alguns navegadores mostram um “x” para limpar. É detalhe de interface, não de dados — e é de graça.

4. includes: o teste que decide quem fica

Toda string tem um método includes que responde uma pergunta simples: “este pedaço de texto aparece aqui dentro?”. A resposta é true ou false, exatamente o que o filter precisa.

> "Pão de queijo".includes("queijo")
true
> "Pão de queijo".includes("QUEIJO")
false
> "Pão de queijo".includes("")
true

A segunda linha é a que surpreende: includes diferencia maiúsculas de minúsculas. Quem digita “QUEIJO” com o Caps Lock ligado não encontra nada. E a terceira explica por que a lista inteira aparece antes de digitar: toda string contém a string vazia.

MétodoPergunta que respondeExemplo com “Pão de queijo”
includeso pedaço aparece em qualquer posição?includes("queijo") devolve true
startsWitho texto começa com o pedaço?startsWith("Pão") devolve true
endsWitho texto termina com o pedaço?endsWith("queijo") devolve true
toLowerCasecomo fica tudo em minúsculas?"PÃO".toLowerCase() devolve "pão"
trimcomo tirar os espaços das pontas?" pão ".trim() devolve "pão"

O conserto é padronizar os dois lados antes de comparar. Baixar tudo para minúsculas com toLowerCase() resolve a maior parte dos casos:

const encontrados = paes.filter((pao) =>
  pao.toLowerCase().includes(busca.toLowerCase())
);

Repare que o toLowerCase aparece duas vezes: no item e no texto buscado. Se você baixar só um dos lados, continua errado — é uma comparação, e os dois lados precisam falar a mesma língua. O mesmo vale para espaços: busca.trim() corta o espaço que sobra no começo e no fim, e evita que alguém digitando “ pão” não encontre nada.

O campo já guarda o que a pessoa digita, mas a lista mostra todos os pães sempre. Filtre a lista com includes, comparando os dois lados em minúsculas, para que digitar “queijo” deixe só um item.

const paes = ["Pão de queijo", "Broa de fubá", "Sonho"];

function App() {
  const [busca, setBusca] = useState("");
  return (
    <div>
      <input

      />
      <ul>
        {paes.map((pao) => (
          <li className="item" key={pao}>{pao}</li>
        ))}

Clique em Verificar depois de digitar “queijo” na prévia. A conferência conta os itens da lista: com o filtro certo, sobra um. Se sobrarem três, o filtro não está sendo usado no map; se sobrar nenhum, provavelmente um dos lados não foi padronizado.

busca
O texto que a pessoa digitou, guardado no estado. Começa como "", que significa “mostre tudo”.
filter
Método que devolve um array novo só com os itens aprovados pela função. Não altera o original.
includes
Responde se um pedaço de texto aparece dentro de outro. Diferencia maiúsculas de minúsculas.
normalize
Converte o texto para uma forma em que letra acentuada e letra simples podem ser comparadas. Usado com "NFD" e uma expressão que remove os acentos.
entrada controlada
Campo cujo valor vem do estado (value) e que avisa cada tecla (onChange).
derivado
A lista filtrada: calculada a partir da lista e da busca, na hora de desenhar, sem estado próprio.

5. Acento é o teste de verdade

Baixar para minúsculas resolve metade. A outra metade é acento. Em português, ninguém digita acento em campo de busca — e “broa de fuba” precisa encontrar “Broa de fubá”. O includes não sabe disso: para ele, “á” e “a” são letras diferentes.

> "Broa de fubá".normalize("NFD").replace(/[\u0300-\u036f]/g, "")
Broa de fuba
> "Broa de fubá".includes("fuba")
false

O normalize("NFD") separa a letra do acento: “á” vira “a” mais um sinal gráfico invisível. O replace com aquela expressão apaga só os sinais gráficos, e o texto volta sem acento. É feio de ler e funciona sempre. Vale embrulhar num nome melhor, uma vez, e usar em todo o site:

function semAcento(texto) {
  return texto.normalize("NFD").replace(/[\u0300-\u036f]/g, "");
}

Com isso, o filtro fica uma linha comprida, mas honesta:

const encontrados = paes.filter((pao) =>
  semAcento(pao).toLowerCase().includes(semAcento(busca).toLowerCase())
);

Há um detalhe de desempenho aqui que vale mencionar e não vale otimizar ainda: a cada tecla, o filter roda para todos os itens e normaliza o texto de cada um. Com trinta pães, isso é invisível. Com trinta mil, você vai querer useMemo ou normalizar os textos uma vez, quando os dados chegam. A regra é sempre a mesma: primeiro funciona, depois mede, depois otimiza.

Quem digita “FUBA”, sem acento, não encontra “Broa de fubá”. Crie a função semAcento e aplique nos dois lados da comparação, mantendo também o toLowerCase.

const paes = ["Pão de queijo", "Broa de fubá", "Sonho"];

E cuidado com a expressão copiada: ela precisa das barras no começo e no fim e do g no final, senão o replace troca só o primeiro acento que encontra.

6. Buscar em mais de um campo

Quando o item deixa de ser texto e passa a ser objeto, a busca muda um pouco. Cada pão tem nome, codigo e talvez categoria. A pessoa pode digitar “sonho” (nome) ou “17” (código) — e é razoável esperar que as duas coisas funcionem.

A receita é juntar as condições com ||: o item fica se casa por um campo ou pelo outro. E atenção a um detalhe de tipo: codigo é número, e número não tem includes. Converta antes com String(pao.codigo), ou compare com == depois de converter a busca. Sem isso, a busca por código simplesmente não acha.

const encontrados = paes.filter((pao) => {
  const texto = busca.trim().toLowerCase();
  return (
    pao.nome.toLowerCase().includes(texto) ||
    String(pao.codigo).includes(texto)
  );
});

Com três ou mais campos, o código começa a ficar repetitivo. Vale a pena montar uma lista de valores e usar some, que responde “algum destes combina?”. É a mesma ideia do filter, um nível abaixo, e a aula Listas com map já mostrou que métodos de array se combinam.

const encontrados = paes.filter((pao) =>
  [pao.nome, String(pao.codigo), pao.categoria]
    .some((valor) => valor.toLowerCase().includes(texto))
);

As duas versões funcionam. A primeira é mais fácil de ler quando são dois campos; a segunda escala sem virar uma escada de ||. Escolha pela clareza, não pela esperteza.

A busca só olha o nome. Faça ela achar também pelo código, para que digitar “17” mostre o sonho — e confira que o botão Limpar devolve os quatro pães.

O botão Limpar faz uma coisa só: devolve a busca para a string vazia. Como o filtro é derivado, a lista inteira volta sozinha — não há nada para “restaurar”. Esse é o teste prático de que você escolheu o desenho certo: limpar é uma linha, e não uma cópia de segurança da lista.

7. Quando nada é encontrado

Busca vazia mostra tudo; busca sem resultado mostra nada. E uma área em branco é a pior resposta possível: a pessoa não sabe se o site quebrou, se ainda está carregando ou se aquele pão não existe. A solução é dizer o que aconteceu, com as palavras de quem está usando:

{encontrados.length === 0 ? (
  <p>Nenhum pão encontrado para "{busca}".</p>
) : (
  <ul>
    {encontrados.map((pao) => (
      <li className="item" key={pao.codigo}>{pao.nome}</li>
    ))}
  </ul>
)}

Repare que a mensagem cita o que foi buscado. Isso ajuda a pessoa a perceber o próprio erro de digitação — “pao de quejo” — e a corrigir sem achar que o site está quebrado. Uma boa mensagem de vazio tem três coisas: o que não foi encontrado, o termo usado e um caminho de saída (limpar a busca, ver tudo).

Essa diferença entre “lista vazia porque não há dados” e “lista vazia porque o filtro não achou nada” é o assunto da aula de Estados Vazios, mais adiante neste nível. Por enquanto, guarde a distinção: são dois vazios diferentes, e a mensagem de cada um deve ser diferente.

Um cuidado de acessibilidade que vale desde já: coloque a mensagem num elemento com role="status". Leitores de tela anunciam mudanças nesse elemento, então quem não vê a lista descobre que a busca não achou nada. É um atributo, não um curso.

8. Limpar, focar e não filtrar o estado

Três decisões pequenas que fazem a busca parecer profissional. A primeira: o botão de limpar deve devolver o foco ao campo, para a pessoa continuar digitando. Isso se faz com uma referência ao input e uma chamada de focus() depois de limpar — o useRef resolve, e tem aula própria mais adiante.

A segunda: não guarde a lista filtrada no estado. Guardar resultados e busca ao mesmo tempo cria duas verdades que precisam ser sincronizadas em cada tecla, em cada item novo, em cada limpeza. Guarde só busca; a lista é conta. Se um dia a conta ficar cara, useMemo resolve sem mudar o desenho.

Onde fica a lista filtradaComo fica o códigoO que acontece
no estadosetResultados(paes.filter(...))a lista original se perde; o próximo filtro roda sobre o resultado
calculada no renderconst encontrados = paes.filter(...)sempre parte da lista completa: é o jeito recomendado
no servidoruma requisição por buscaprecisa de atraso, estado de carregamento e tratamento de erro

A terceira: com dados locais, não precisa de espera. Com dados de uma API, cada tecla viraria uma requisição, e você vai querer atrasar a chamada — debounce — ou usar useDeferredValue para a tela não engasgar. São assuntos de outro nível; o importante agora é saber que a busca local é síncrona e instantânea.

9. Cenários do dia a dia

Cenário 1: a busca acha, mas apaga o resto

A Ana salvou o resultado do filtro no mesmo estado da lista. Depois de buscar uma vez, a lista original “sumiu”: o próximo filtro roda sobre o resultado anterior, e a busca vira uma armadilha que só encolhe. Filtro é cálculo, não armazenamento. Mantenha a lista completa e derive o que aparece.

Cenário 2: ninguém acha nada com acento

Quem digita “fuba” não encontra “fubá”, e quem digita “Fuba” também não. São dois problemas diferentes no mesmo filtro: acento e maiúscula. A correção é padronizar os dois lados com semAcento e toLowerCase, sempre na mesma ordem. Se funcionar para um caso e não para o outro, falta padronizar um dos lados.

Cenário 3: buscar por código não retorna nada

O campo codigo é número, e .includes não existe em número. O console do navegador acusa “pao.codigo.includes is not a function”, e a busca inteira para. Converta para texto com String(pao.codigo) antes de comparar — e lembre que “17” como texto encontra “170” também, o que às vezes é desejado e às vezes não.

Exercício: a busca sem acento

Complete a função que deixa o texto pronto para comparar: separa as letras dos acentos e apaga os sinais gráficos.

function semAcento(texto) { return texto.normalize("NFD").replace(, ""); }

Dica: é uma expressão regular com as barras, o intervalo dos sinais gráficos e a letra g no fim, para trocar todos e não só o primeiro.

11. Resumo

Buscar é filtrar. O estado guarda o texto digitado — uma string que começa vazia —, o filter decide quem fica e o map transforma quem ficou em elementos. A lista original nunca é alterada; por isso limpar a busca é só voltar a string para "".

A comparação é a parte que exige atenção. includes diferencia maiúsculas; para resolver, baixe os dois lados com toLowerCase. Acentos exigem normalize("NFD") e a remoção dos sinais gráficos. Com mais de um campo, junte as condições com || ou percorra uma lista de valores com some — e converta números com String() antes de comparar.

Quando o resultado é zero, diga isso com todas as letras e ofereça uma saída. Área em branco não é resposta. E não guarde o resultado no estado: guarde a pergunta (a busca) e calcule a resposta (a lista filtrada), do mesmo jeito que a Ana guarda o critério de ordenação e calcula a ordem na aula anterior.

Para lembrar

  • A busca é um estado de texto + um filtro derivado.
  • filter devolve array novo; o original fica intacto.
  • includes diferencia maiúsculas: padronize os dois lados.
  • normalize("NFD") + replace resolve acento.
  • trim() corta os espaços das pontas da busca.
  • Número não tem includes: use String(codigo).
  • Dois campos: ||; muitos campos: some sobre uma lista.
  • Zero resultados merece mensagem, com o termo buscado e uma saída.
  • Limpar a busca é setBusca("") — nada de restaurar cópia.
  • Busca local é síncrona; API pede atraso ou useDeferredValue.
