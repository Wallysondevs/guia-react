O useId

A Ana montou um componente de campo de e-mail e usou o mesmo componente nos dois formulários do site: o cadastro do cliente e o cadastro do fornecedor. Cada campo tem o seu rótulo clicável, e clicar no rótulo do segundo formulário leva o cursor para o campo do primeiro. O culpado é uma linha só: os dois campos saíram com id="email", porque o componente é o mesmo. Nesta aula a Ana aprende o useId, o hook que dá a cada cópia do componente um identificador só dela — e aprende também para que esse identificador serve, e para o que ele não serve.

Você vai aprender
  • Para que serve o id de um campo e o que ele liga no HTML.
  • Por que um componente reutilizado gera ids repetidos e o que isso quebra.
  • Como o useId resolve, com uma linha e sem contador global.
  • Que o id devolvido é estável entre desenhos e único por cópia do componente.
  • Como ligar uma dica ou uma mensagem de erro ao campo com aria-describedby.
  • Por que o id precisa nascer antes de o campo aparecer na tela.
  • Por que Math.random() e contador global dão problema, e o que o useId não é.

1. A cena: dois formulários, o mesmo id

O site da Ana tem dois formulários parecidos: um para o cliente entrar na lista de novidades e outro para o fornecedor mandar o preço do dia. Ela escreveu um componente CampoDeEmail e usou nos dois lugares — decisão certa, é para isso que componente serve. O componente devolve um <label htmlFor="email"> e um <input id="email">.

Uma cópia funciona. Duas cópias produzem duas tags com o mesmo id no mesmo documento, e o HTML não permite isso: o id tem de ser único na página. O navegador não reclama, não escreve nada no console, não pinta a borda de vermelho. Ele simplesmente obedece à primeira: quando você clica no rótulo do segundo formulário, o foco vai para o campo do primeiro. Para quem usa leitor de tela, é pior — o rótulo anunciado pode ser o do outro campo.

Esse é o tipo de defeito que sobrevive a meses de uso, porque nada quebra de forma visível. A pessoa só percebe se clicar no rótulo e reparar que o cursor foi para o lugar errado. É exatamente o motivo de o React ter um hook dedicado a isso: gerar um identificador único para cada cópia de um componente, sem sorteio e sem contador.

2. Para que serve um id, afinal

O id é o nome de um elemento dentro do documento. Duas coisas dependem dele: o <label for="...">, que aponta para o campo que ele descreve, e os atributos aria-*, que dizem ao leitor de tela onde estão a dica e a mensagem de erro. Sem id, o rótulo é só um texto ao lado — não é clicável e não é anunciado junto com o campo.

id
O nome único de um elemento na página: <input id="email-1">. Tem de ser diferente de todos os outros ids do documento.
htmlFor
No JSX, o for do rótulo. Recebe o id do campo: <label htmlFor="email-1">. No HTML gerado, sai como for.
label
O rótulo do campo. Clicar nele leva o foco para o campo cujo id combina — e é o que o leitor de tela anuncia.
aria-describedby
Aponta para o id do texto que descreve o campo: a dica, o formato esperado, a regra de senha.
aria-labelledby
Aponta para o id do texto que nomeia o campo quando não existe label, como um título acima de um grupo de campos.
useId
O hook que devolve um id único para aquela cópia do componente e estável entre desenhos: const id = useId().

Guarde a diferença entre os dois atributos aria, porque ela confunde: aria-labelledby dá o nome do campo (o que ele é), e aria-describedby dá a descrição (o que ele espera). Um campo pode ter os dois. Na prática, o aria-labelledby só aparece quando não há um <label> possível; o aria-describedby aparece sempre que existe uma dica.

Quando o campo é único na página, escrever o id à mão é perfeitamente bom: id="busca", htmlFor="busca". O problema começa quando o campo mora dentro de um componente que pode ser usado duas, três, dez vezes. Aí o id não pode ser uma constante do arquivo: ele precisa ser diferente em cada cópia.

3. A caixa: o mesmo componente, dois ids

O caso do começo da aula, reduzido ao osso. O CampoDeEmail é usado duas vezes e as duas cópias saem com id="email". O painel mostra os dois blocos iguais — e é aí que está o defeito: dois elementos com o mesmo nome.

Dentro de CampoDeEmail, chame const id = useId() e use id={"email-" + id} no campo e htmlFor={"email-" + id} no rótulo. As duas cópias precisam sair com ids diferentes.

  return (
    <p>
      <label htmlFor="email">E-mail</label>
      <input id="email" type="email" />
    </p>
  );
}

  return (
    <form>
      <h1>Dois cadastros</h1>
      <CampoDeEmail />
      <CampoDeEmail />
    </form>
  );
}

Rode e compare o painel antes e depois. Antes, os dois blocos mostram id="email". Depois, cada um tem um id próprio, terminado em algo diferente, e o for do rótulo acompanha. O prefixo email- não é exigência do React: é para você abrir o inspetor do navegador e saber de que campo aquele id veio. O React só garante a parte única.

Repare também no que o useId não faz. Ele não altera o texto do rótulo, não muda o comportamento do campo e não resolve o problema de dois formulários idênticos na tela. Ele só devolve uma string. Quem liga rótulo e campo é o par htmlFor + id, e é você quem escreve os dois.

4. O que o useId devolve

A chamada é const id = useId(), sem argumento. O que volta é uma string que serve como id: única naquela página, estável entre os desenhos do mesmo componente, e diferente para cada cópia. Duas coisas importantes vêm daí.

Primeira: é estável. Digitar no campo, marcar um checkbox, trocar um estado — nada disso muda o id. O React guarda o valor na posição do hook, como faz com o useState. Se o id mudasse a cada desenho, o rótulo perderia o campo no meio da digitação, e o leitor de tela perderia a referência. No console do seu projeto, com um console.log(id) no corpo do componente, você vê a mesma linha em cada desenho:

id do campo: _r_0_
id do campo: _r_0_
id do campo: _r_0_

Segunda: é único por cópia. Duas chamadas de <CampoDeEmail /> são dois componentes diferentes, e cada um ganha o seu id. É por isso que o useId resolve o problema da caixa anterior sem que você precise passar um id por prop. E se você chamar useId duas vezes no mesmo componente, ganha dois ids diferentes — útil quando um componente tem dois campos.

O formato do texto não é contrato. Nesta versão do React, na caixa, ele sai como _r_0_; em outras versões você pode ver :r0: ou «r0». Não escreva código que dependa disso, não use o id em teste automatizado e não tente adivinhar o próximo. Trate o valor como uma senha: você repassa, não inspeciona.

Um detalhe prático que vale desde já: o id devolvido pode conter caracteres que não funcionam bem em seletor de CSS. Se você precisar estilizar o campo, use uma classe; o id é para o HTML e para os atributos aria-*, não para #email-_r_0_ no CSS.

5. Rótulo, dica e mensagem de erro

Campo de senha é o exemplo onde tudo aparece junto: o rótulo diz o que é, a dica diz o que se espera e a mensagem de erro diz o que deu errado. Os três precisam estar ligados ao campo — e o campo é um só. A convenção mais comum é chamar useId uma vez e montar os ids derivados com prefixo.

O campo e o rótulo já usam o id. Falta ligar a dica: chame const id = useId() (já está lá), dê ao <small> o id={"ajuda-" + id} e ponha aria-describedby={"ajuda-" + id} no <input>.

function CampoDeSenha() {
  const id = useId();
  return (
    <p>
      <label htmlFor={"senha-" + id}>Senha</label>
      <input id={"senha-" + id} type="password" />
      <small>Mínimo de 8 caracteres.</small>
    </p>
  );
}

function App() {
  return <CampoDeSenha />;
}

No painel, o aria-describedby do campo e o id do small terminam com o mesmo sufixo. É essa combinação que faz o leitor de tela anunciar “Senha, campo de texto, mínimo de 8 caracteres” em vez de só “Senha”. Sem a ligação, a dica continua visível na tela e invisível para quem não vê a tela.

Se o componente tiver dois campos independentes, você tem duas opções honestas: chamar useId duas vezes, uma por campo, ou chamar uma vez e derivar dois prefixos. A primeira é mais fácil de ler; a segunda deixa claro que os ids andam juntos. Nenhuma das duas é errada — o que não vale é escrever id="senha" em um componente que pode aparecer duas vezes.

Vale o mesmo para a mensagem de erro. Quando a validação falha, o campo ganha aria-describedby apontando para o parágrafo do erro, e o erro ganha um id. Assim o leitor de tela anuncia o problema junto com o campo, em vez de deixar a pessoa procurando texto vermelho pela página.

6. O id precisa existir antes de o campo aparecer

Agora o caso que separa quem entendeu de quem decorou: o campo que só aparece depois de um clique. A Ana põe um checkbox “Quero nota fiscal” e, quando ele é marcado, o campo de CNPJ aparece. O id desse campo tem de ser gerado com useId — e o useId tem de ficar no topo do componente, junto dos outros hooks, não dentro do trecho que só desenha às vezes.

O motivo é o de sempre: hooks são identificados pela ordem das chamadas. Se o useId só rodasse quando o campo aparece, a lista de hooks mudaria de tamanho entre um desenho e outro, e o React perderia a conta. Gerar o id sempre, mesmo sem usar, custa nada.

Marque “Quero nota fiscal”: o campo CNPJ aparece sem rótulo ligado. Ponha const id = useId() no topo do App e ligue o rótulo ao campo com htmlFor={"cnpj-" + id} e id={"cnpj-" + id}.

function App() {
  const [nota, setNota] = useState(false);

  return (
    <div>
      <label>
        <input
          type="checkbox"
          checked={nota}
          onChange={(e) => setNota(e.target.checked)}
        />
        Quero nota fiscal
      </label>

      {nota && (
        <p>
          <label>CNPJ</label>
          <input />
        </p>
      )}
    </div>
  );
}
<div>
  <label>
    <input type="checkbox">
    Quero nota fiscal
  </label>
</div>

function App() {
  const [nota, setNota] = useState(false);
  const id = useId();

  return (
    <div>
      <label>
        <input
          type="checkbox"
          checked={nota}
          onChange={(e) => setNota(e.target.checked)}
        />
        Quero nota fiscal
      </label>

      {nota && (
        <p>
          <label htmlFor={"cnpj-" + id}>CNPJ</label>
          <input id={"cnpj-" + id} />
        </p>
      )}
    </div>
  );
}

O painel prova as duas coisas de uma vez: o campo aparece depois do clique e já sai com id e rótulo ligados. Se você mover o useId para dentro do if, a caixa quebra — o painel não muda mais ao marcar e desmarcar o checkbox, porque o React abortou o desenho. É a regra dos hooks cobrando o seu preço, e ela tem aula própria em As Regras dos Hooks.

Uma variante do mesmo caso: o campo de CNPJ só aparece quando nota é verdadeiro, mas o hook está no topo desde o primeiro desenho. O id é gerado, guardado e usado no desenho em que o campo entra. Nada se perde, nada é gerado duas vezes.

7. Por que não Math.random() nem contador global

Antes do useId, a gambiarra clássica era id={"campo-" + Math.random()}. Ela funciona em uma tela simples e quebra em três situações: o id muda a cada desenho (e o rótulo perde o campo), dois desenhos podem sortear o mesmo número (raro, mas acontece) e, num projeto que renderiza no servidor, o número sorteado no servidor é diferente do sorteado no navegador. Aí você vê o aviso mais chato do React:

Warning: Prop `id` did not match. Server: "campo-0.7314" Client: "campo-0.2981"

Um contador global do tipo let proximo = 0; const id = "campo-" + (proximo++) parece mais organizado, e é pior: em desenvolvimento o React desenha duas vezes para ajudar a achar problemas, e o contador anda o dobro; no servidor, cada requisição começa do zero e os ids se repetem entre páginas. O useId existe justamente porque essas duas tentativas falham.

“Renderização no servidor” é o nome do arranjo em que o HTML da página é montado no servidor e depois o React assume no navegador, conferindo se o que chegou combina com o que ele desenharia. Esse encontro é a hidratação. Ids que não combinam quebram a conferência. Este guia não usa servidor — a caixa roda no seu navegador —, mas frameworks como o Next.js usam, e é por isso que a documentação do React insiste no useId em vez de “um contador serve”.

8. O que o useId não é

Três confusões aparecem sempre que o assunto é useId. Vale desfazer cada uma, porque as três levam a código que parece certo e não é.

A primeira: não é para key. O key de uma lista diz ao React qual item é qual, e precisa vir do dado — o id do produto, o número do pedido. Usar useId ali daria um id novo para cada item da lista a cada mudança de ordem, e o React recriaria todos os elementos. Se o seu item não tem id, veja Listas com map.

A segunda: não é para seletor de CSS. O texto devolvido pode ter caracteres que atrapalham querySelector e #id. Para estilo, use classe; para teste, use aria-label ou texto visível; para o HTML, use o id.

A terceira: não gera id para elemento que você não desenha. Se o alvo é uma âncora href="#contato" para pular até uma seção, o id é fixo e escrito à mão — ele faz parte do endereço e alguém vai digitar isso na barra do navegador. Id gerado por hook é para uso interno da página.

Há ainda um detalhe de escopo que economiza dúvida: o id gerado vale para a página inteira, não para o componente. Dois componentes diferentes nunca recebem o mesmo useId, e é por isso que ele serve como id de documento. Se você montar duas cópias da mesma aplicação na mesma página, elas precisam de prefixos diferentes — e isso é configuração de raiz, não do hook.

9. Cenários do dia a dia

Cenário 1: o rótulo que focava o campo errado

A Ana clicou em “E-mail” no formulário do fornecedor e o cursor foi para o campo do cliente. Os dois componentes tinham id="email". Ela chamou useId dentro do componente e montou {"email-" + id} no rótulo e no campo. O clique passou a ir para o lugar certo sem que nenhum dos dois formulários soubesse que o outro existia.

Cenário 2: o leitor de tela lia a dica do vizinho

Dois campos de senha na mesma tela, os dois com aria-describedby="ajuda". O leitor de tela anunciava sempre a mesma dica, mesmo quando a regra de cada campo era diferente. Com um useId por componente e o prefixo ajuda-, cada campo passou a apontar para o seu próprio texto. O conserto foi de duas linhas, e a diferença só aparece para quem usa leitor de tela — o que é exatamente o motivo de fazer certo desde o começo.

Cenário 3: o campo que aparecia depois do clique

No formulário de encomenda, o campo de observação só aparece quando a Ana marca “é para festa”. O id estava sendo gerado dentro do trecho condicional, e o componente quebrava ao marcar e desmarcar. Mover o useId para o topo, junto do useState, resolveu — e é a mesma regra que vale para todos os hooks.

11. Resumo

O useId é o hook dos identificadores: devolve uma string única para cada cópia do componente, estável entre desenhos e igual no servidor e no navegador. Ele resolve o caso do componente reutilizado, em que um id fixo no arquivo produz duas tags com o mesmo nome e o rótulo passa a apontar para o campo errado. O uso típico é uma linha no topo, um prefixo legível e o par htmlFor + id ligado nas duas pontas.

O mesmo id ainda serve para amarrar a dica e a mensagem de erro: aria-describedby no campo, id no texto. Chamar useId uma vez e derivar dois prefixos é o padrão mais comum, mas duas chamadas também valem. E o hook fica sempre no topo, porque o campo pode aparecer só depois de um clique — o id precisa existir antes.

O que não fazer: sortear com Math.random() (muda a cada desenho e quebra a hidratação), contar com variável global (anda duas vezes em desenvolvimento e recomeça no servidor) ou usar o id gerado como key de lista e como seletor de CSS. O id do hook é para o HTML e para o leitor de tela; para o resto, existe o instrumento certo.

Por último, uma questão de bom senso: se o campo é único na página e você tem certeza disso, um id escrito à mão é mais simples e mais fácil de achar no código. O useId entra quando o campo vira componente — porque aí a segunda cópia é só uma questão de tempo.

Para lembrar

  • const id = useId(): sem argumento, no topo do componente.
  • O id é único por cópia e estável entre desenhos — não muda ao digitar.
  • O formato do texto é interno (_r_0_ nesta versão): não dependa dele.
  • Ligue rótulo e campo com htmlFor={"nome-" + id} e id={"nome-" + id}.
  • Dica e erro vão em aria-describedby, apontando para o id do texto.
  • aria-labelledby nomeia; aria-describedby descreve.
  • O hook vem antes do if: o id pode ser gerado mesmo quando o campo está escondido.
  • Math.random(), Date.now() e contador global quebram a hidratação.
  • Id de key vem do dado; id de âncora é fixo e escrito à mão.
  • Campo único na página pode ter id escrito à mão, sem hook.
