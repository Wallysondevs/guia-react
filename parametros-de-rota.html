Parâmetros de Rota

A Ana tem a lista de pedidos e quer mandar o link de um pedido específico para o entregador. Hoje a rota é só #/pedidos: todo mundo cai na lista e precisa procurar o número. O endereço precisa carregar mais informação — #/pedidos/3 — e o componente precisa saber ler esse 3. Nesta aula o hash vira uma pequena tabela de rotas, com parâmetros, validação e um detalhe de key que evita o clássico "o pedido anterior ficou na tela".

Você vai aprender
  • O que é um parâmetro de rota e quando ele substitui a query string.
  • Como quebrar #/pedidos/3 em segmentos e ler a parte que muda.
  • Como casar o primeiro segmento com a tela e passar o segundo como prop.
  • Por que o parâmetro chega como texto e o que validar antes de usar.
  • O que acontece com o estado do componente quando só o parâmetro muda.
  • Como a key força um componente novo — e por que isso é o certo aqui.

1. A cena: o link de um pedido só

Na aula de link e navegação, o site da Ana passou a ter links de verdade. O menu leva à vitrine, à lista de pães e ao contato — rotas fixas, cada uma com um nome. A lista de pedidos, porém, é diferente: cada pedido tem o seu próprio endereço, e o nome da tela é sempre o mesmo.

A cliente liga perguntando do pedido 3. A Ana quer mandar https://loja.test/#/pedidos/3, o entregador abrir e ver aquele pedido, com o nome, o valor e a hora. Com uma rota fixa, só existe #/pedidos, e o endereço não diz qual pedido é.

A ideia do parâmetro de rota é simples: o caminho tem partes fixas e partes variáveis. #/pedidos/3 tem a parte fixa pedidos e a parte variável 3. Quem escreve a rota marca onde a variável entra; quem lê a URL descobre o valor e entrega ao componente.

2. Parâmetro, rota fixa e query string

Existem três jeitos de carregar informação no endereço, e eles não competem: cada um responde a uma pergunta diferente. O parâmetro diz qual recurso; a query diz como mostrá-lo; a rota fixa diz apenas onde você está.

FormaExemploRespondeQuando usar
Rota fixa#/pedidosonde estoutelas que não mudam de conteúdo
Parâmetro#/pedidos/3qual itemuma página por item: pedido, pão, cliente
Query string#/pedidos?ordem=precocomo listarfiltro, ordem, página, aba

A confusão comum é usar query para identificar: #/pedido?id=3. Funciona, e é pior de compartilhar, de indexar e de ler. O identificador do recurso pertence ao caminho; o resto é ajuste de exibição. Se você precisa das duas coisas, elas convivem: #/pedidos/3?aba=itens é o pedido 3, na aba de itens.

Na rota por hash, o "caminho" é o que vem depois de #/. A mecânica é a mesma de um roteador de verdade: separar por barras, casar o primeiro segmento com uma tela e entregar os demais como parâmetros.

rota
O caminho que aparece depois do #: em #/pedidos/3, a rota é pedidos/3.
segmento
Cada pedaço entre barras. pedidos/3 tem dois segmentos: "pedidos" e "3".
parâmetro
O segmento que muda de página para página e carrega a identidade do item. Na tabela de rotas aparece como :id.
rota dinâmica
Um padrão com um coringa no lugar do valor fixo, como pedidos/:id. Casa com pedidos/3, pedidos/9, pedidos/abc.
query string
O que vem depois do ?: ?aba=itens. Não é parâmetro de rota e precisa ser separada antes do split("/").
key
Prop especial que diz ao React se aquele componente é o mesmo da renderização anterior. Valor diferente, componente novo — e estado interno zerado.

3. Quebrando o hash em segmentos

O primeiro passo é transformar a string da rota numa lista. O split("/") faz isso: cada barra vira uma divisória, e cada pedaço vira um item do array.

function analisar(rota) {
  const partes = rota.split("/").filter(Boolean);   // remove vazios
  return {
    tela: partes[0] || "inicio",
    id: partes[1] || null
  };
}

O filter(Boolean) tira pedaços vazios — útil quando alguém abre #/pedidos/ com barra no fim ou #//pedidos com barra dupla. Sem ele, ("pedidos/").split("/") devolve ["pedidos", ""] e o parâmetro vem vazio em vez de ausente.

A rota é pedidos/3 e a tela trata a string inteira como nome de tela, então nenhum caso casa. Quebre a rota em segmentos e use o segundo como número do pedido.

const janela = new EventTarget();
janela.hash = "#/pedidos/3";

function irPara(hash) {
  janela.hash = hash;
  janela.dispatchEvent(new Event("hashchange"));
}

function useRota() {
  const [rota, setRota] = useState(janela.hash);

  useEffect(() => {
    const aoMudar = () => setRota(janela.hash);
    janela.addEventListener("hashchange", aoMudar);
    return () => janela.removeEventListener("hashchange", aoMudar);
  }, []);

  return rota.replace(/^#\/?/, "") || "inicio";
}

function App() {
  const rota = useRota();

  return (
    <div>
      <p>Rota: {rota}</p>
      {rota === "pedidos" ? <p>Lista de pedidos</p> : <p>Pedido {rota}</p>}
    </div>
  );
}

Repare que a condição mudou de rota === "pedidos" para id: se existe um segundo segmento, é um pedido; se não existe, é a lista. A desestruturação const [tela, id] = rota.split("/") só funciona porque a ordem é garantida — primeiro a tela, depois o parâmetro.

rota crua: "pedidos/3"
segmentos: ["pedidos", "3"]

Essas duas linhas saem de um console.log(rota, rota.split("/")) antes do return. Quando a tela mostra o valor errado, esse log diz na hora se o problema é a leitura (o array está certo) ou o desenho (o array está errado).

4. Uma tabela de rotas

Com duas telas e um parâmetro, o if resolve. Quando o site cresce, uma tabela de rotas deixa tudo num lugar só: cada linha tem o padrão (com o parâmetro marcado por :id) e a tela correspondente.

const rotas = [
  { padrao: "inicio", tela: "inicio" },
  { padrao: "pedidos", tela: "lista" },
  { padrao: "pedidos/:id", tela: "pedido" }
];

function casar(rota) {
  const partes = rota.split("/").filter(Boolean);
  for (const r of rotas) {
    const alvo = r.padrao.split("/");
    if (alvo.length !== partes.length) continue;
    const casa = alvo.every((p, i) => p.startsWith(":") || p === partes[i]);
    if (casa) return { tela: r.tela, params: { id: partes[1] } };
  }
  return { tela: "nao-encontrada", params: {} };
}

O casador compara segmento por segmento e trata o que começa com : como coringa. A ordem importa: a rota pedidos/:id precisa vir depois de pedidos? Não — pedidos tem um segmento e pedidos/:id tem dois, então o tamanho já separa as duas. Mas, se você tivesse pedidos/:id e pedidos/novo, a ordem decidiria qual ganha — a mais específica primeiro.

É esse desenho que as bibliotecas de rota entregam pronto, com um hook useParams devolvendo o objeto. Aqui o objeto vem da sua própria função — a ideia é a mesma, e agora você sabe o que acontece por baixo.

Repare que o params do exemplo é montado à mão com id: partes[1], o que funciona enquanto houver um único parâmetro. Para generalizar, percorra o padrão e guarde o valor de cada posição que começa com :: a posição do coringa é a posição do valor. Com esse laço, a mesma função serve para pedidos/:id, pedidos/:id/itens/:item e qualquer padrão futuro, sem uma linha nova por rota.

5. Passando o parâmetro para o componente

Encontrada a tela e o parâmetro, o trabalho é o de sempre: passar por prop. O componente da tela do pedido não sabe de URL nem de hash; ele recebe um id e desenha o que aquele id significa.

function Pedido({ id }) {
  return (
    <section>
      <h1>Pedido {id}</h1>
      <p>Retirada às 18h</p>
    </section>
  );
}

Essa separação é o que torna a tela testável e reutilizável: para ver o pedido 3, basta renderizar <Pedido id="3" />. Quem lida com endereço é o App; quem desenha o pedido é o Pedido.

O parâmetro chega sempre como texto, porque veio de uma string. Se você precisa somar, comparar com número ou usar como índice de array, converta com Number(id) — e trate o caso em que a conversão falha, porque o endereço é digitável por qualquer pessoa.

O endereço #/pedidos/9 aponta para um pedido que não existe, e a tela fica com "Pedido:" vazio. Trate o caso: quando o id não estiver na lista, mostre "Pedido não encontrado".

6. O estado que sobrevive à troca de parâmetro

Aqui está a pegadinha da aula. Quando o parâmetro muda — de #/pedidos/1 para #/pedidos/2 —, o React vê o mesmo componente no mesmo lugar da árvore. Ele não desmonta e monta de novo: ele atualiza as props. E estado interno, como a quantidade escolhida, continua de onde estava.

Na prática, o cliente escolhe 2 pães no pedido 1, clica no pedido 2 e encontra a quantidade 2 já preenchida. Não é bug do React: é a definição de "mesmo componente". A solução é dizer ao React que, para efeitos de identidade, aquele componente é outro: a key.

Aumente a quantidade e clique no link do pedido 2: a quantidade continua 2, porque o componente foi reaproveitado. Use a key para o React montar um componente novo a cada pedido.

const janela = new EventTarget();
janela.hash = "#/pedidos/1";

function irPara(hash) {
  janela.hash = hash;
  janela.dispatchEvent(new Event("hashchange"));
}

function useRota() {
  const [rota, setRota] = useState(janela.hash);

  useEffect(() => {

    janela.addEventListener("hashchange", aoMudar);
    return () => janela.removeEventListener("hashchange", aoMudar);
  }, []);

  return rota.replace(/^#\/?/, "") || "inicio";
}

function Pedido({ id }) {
  const [qtd, setQtd] = useState(1);

  return (

      <p>Quantidade: {qtd}</p>
      <button onClick={() => setQtd(qtd + 1)}>Mais um</button>

}

          Pedido 2
        </a>
      </nav>

    </div>
  );
}

A key é a mesma ferramenta das listas, com outro uso: quando o valor muda, o React descarta o componente antigo e monta um novo, com o estado inicial. Aqui ela diz "o pedido 2 é outra tela, não a mesma tela com outro número".

sem key → Quantidade: 2 (o componente foi reaproveitado)
com key → Quantidade: 1 (componente novo, estado inicial)

Cuidado para não exagerar: colocar key em tudo remonta componentes sem necessidade e derruba o foco do teclado a cada mudança. Use quando a identidade do conteúdo muda — o id do pedido, o id do pão, o usuário logado. Se o estado interno deve sobreviver à troca, não use.

7. Dois segmentos, três telas

Com o parâmetro no lugar, o mesmo prefixo desenha telas diferentes conforme o que vem depois. Vale enxergar a tabela completa do site da Ana:

EndereçoSegmentosTela
#/[]vitrine
#/pedidos["pedidos"]lista de pedidos
#/pedidos/3["pedidos", "3"]pedido 3
#/pedidos/3?aba=itens["pedidos", "3"] + querypedido 3, aba de itens

Note que a query não entra no split("/") — ela vem depois do ? e precisa ser separada antes, com split("?"). Se você esquecer, o parâmetro vira "3?aba=itens" e nada casa. Ordem certa: primeiro tire a query, depois separe os segmentos.

Vale pensar também no formato do id. Números são o caso fácil; nomes de pão como pao-de-queijo exigem cuidado com acentos e espaços, porque o endereço só aceita uma faixa de caracteres e o resto precisa ser codificado com encodeURIComponent na hora de montar o link. Se o id é gerado pelo sistema, prefira algo simples e estável — o contador do pedido ou um código curto — em vez de derivar do nome do cliente, que muda e cria endereços quebrados.

Com três linhas na tabela, o if ainda é legível. Com dez, a tabela de rotas da seção 4 passa a valer. O limite é o mesmo de sempre: quando você começa a repetir a mesma estrutura de comparação, é hora de transformar em dado.

8. Parâmetro na mão e parâmetro de biblioteca

Bibliotecas de rota fazem exatamente o que você fez aqui: leem o endereço, casam com uma tabela, extraem os parâmetros e entregam num hook. A diferença é o acabamento — casamento com curingas, rotas aninhadas, transições, carregamento sob demanda — e a quantidade de casos que já resolveram por você.

Saber o mecanismo muda o jeito de depurar. Quando o useParams devolve vazio, você sabe que o problema está no padrão da rota (o :id não está lá), não no componente. Quando o valor vem certo e a tela não muda, você sabe que é a key ou o próprio desenho. E quando o endereço tem query, você sabe que ela não está nos segmentos.

Para um site de três telas, o roteador caseiro desta sequência é honesto e suficiente. Para uma aplicação com dez rotas, permissões e carregamento por tela, a biblioteca paga o próprio peso — e você vai lê-la sabendo o que procurar.

9. Cenários do dia a dia

Cenário 1: o link do pedido 3 abria a lista

A Ana mandou #/pedidos/3 e o entregador viu a lista. O código comparava a rota inteira com "pedidos": "pedidos/3" não é igual, e a tela caía no caso padrão. Separar em segmentos e testar o segundo resolveu — e o mesmo erro explica a tela em branco em qualquer rota de dois níveis.

Cenário 2: a quantidade do pedido anterior

O cliente escolhia 2 pães no pedido 1, abria o pedido 2 pelo link e a quantidade continuava 2. O componente era o mesmo, só a prop tinha mudado; o estado interno sobreviveu. A key={id} resolveu na hora, porque força o React a montar um componente novo para cada pedido.

Cenário 3: o pedido 9 que ninguém pediu

Um cliente digitou #/pedidos/9 por curiosidade e viu "Pedido:" sem nada depois. O id veio da URL e o código confiou nele. Procurar na lista e mostrar "Pedido não encontrado" — ou redirecionar para a lista — é parte do trabalho da rota, não um detalhe de acabamento.

11. Resumo

Parâmetro de rota é a parte variável do caminho: em #/pedidos/3, o 3 identifica o pedido. Ele vem antes da query na ordem de leitura — primeiro separe a query, depois quebre o resto em segmentos com split("/") (e filter(Boolean) para ignorar barras sobrando). O primeiro segmento escolhe a tela; os seguintes viram props.

O valor chega como texto e veio de fora: converta quando for número e valide antes de usar, mostrando uma mensagem quando o recurso não existe. Para o componente, o parâmetro é só uma prop — quem lida com endereço é o pai, e é isso que deixa a tela fácil de testar.

Quando só o parâmetro muda, o React reaproveita o componente e o estado interno sobrevive; a key com o id força um componente novo e é o que se quer numa tela por item. Com isso, as rotas do site da Ana ficam completas — falta combinar com o que fazer quando o endereço não corresponde a nada, que é o assunto da rota 404.

Para lembrar

  • Parâmetro diz qual item; query diz como mostrar.
  • split("/") quebra a rota; filter(Boolean) tira segmento vazio.
  • Primeiro segmento escolhe a tela; o segundo vira prop.
  • Ordem de leitura: tire a query (?), depois separe os segmentos.
  • O parâmetro chega como texto: converta com Number quando precisar de número.
  • Id que não existe pede mensagem, não tela vazia.
  • Mudar só o parâmetro não remonta o componente: o estado interno fica.
  • key={id} força componente novo — e estado inicial.
  • Não use key onde o estado deve sobreviver à troca.
  • Bibliotecas de rota fazem o mesmo; o mecanismo é este.
