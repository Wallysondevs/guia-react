Formulários com Actions

O formulário de encomenda da Ana já funciona com onSubmit: ela lê os campos um por um, monta o objeto do pedido, chama preventDefault e reza para não esquecer nenhum passo. No React 19 existe um caminho mais curto: o atributo action do próprio form recebe uma função, e o React entrega os campos já reunidos. Nesta aula ela reescreve o formulário da padaria desse jeito e descobre o que o React faz — e o que continua sendo trabalho dela.

Você vai aprender
  • Como o action substitui o onSubmit e o preventDefault.
  • O que é FormData e por que o name de cada campo importa tanto.
  • Como ler texto, número e caixa de seleção do formulário.
  • Como validar dentro da ação e devolver a mensagem para a tela.
  • O reset automático do formulário depois do envio.
  • Como guardar um histórico de pedidos sem perder os anteriores.
  • O que o painel mostra no atributo action e por que aquilo é normal.

1. A cena: o pedido que apagava a tela

Na aula de Envio de Formulário, a Ana aprendeu o caminho clássico: o form tem onSubmit, a função chama event.preventDefault() para o navegador não recarregar a página, lê cada campo com event.target e monta o objeto do pedido. Funciona, e é o que a maioria dos projetos ainda faz.

O incômodo é a cerimônia. São quatro passos para cada formulário, e três deles são sempre iguais. Pior: quando um campo novo aparece, alguém precisa lembrar de ler mais um valor no lugar certo — e esquecer um campo não dá erro, só um pedido incompleto chegando na padaria.

O React 19 olhou para isso e fez uma pergunta simples: se o navegador já sabe reunir os campos de um formulário, por que o React não usa isso? A resposta é o atributo action recebendo uma função. O React cuida do preventDefault, reúne os campos num FormData e entrega tudo pronto para a sua função — que passa a se chamar action.

2. O que muda: action, FormData e name

Três peças novas entram no formulário e uma antiga sai. Sai o onSubmit com preventDefault. Entram o action como função, o objeto FormData que ela recebe e a regra de que cada campo precisa de name para existir dentro desse objeto.

action
O atributo do form que recebe uma função: <form action={enviar}>. O React chama essa função no envio, sem recarregar a página.
FormData
O objeto que a ação recebe, com todos os campos do formulário. Lê-se com dados.get("nome").
name
O nome do campo dentro do FormData. Sem name, o campo não é enviado — nem para o React, nem para o servidor.
ação assíncrona
Uma ação que devolve promessa, como um fetch. O React segura o envio até ela terminar e marca o período como pendente.
reset automático
Depois de uma ação bem-sucedida, o React limpa os campos não controlados do formulário.
pending
O aviso de que a ação está em andamento. Vem do useActionState ou de um useTransition em volta do envio.

O ganho maior é o FormData. Em vez de uma linha de leitura por campo, a ação recebe o formulário inteiro e pergunta o que quiser. Um campo novo no JSX entra no pedido sem nenhuma mudança na função — desde que tenha name. E é aí que mora o primeiro tropeço de todo mundo.

Há uma pergunta justa aqui: se o action aceita uma função, ele continua sendo um atributo do HTML? Continua. E é isso que permite os dois mundos conviverem. Um formulário pode ter action="/encomenda" — um endereço de verdade, que funciona mesmo sem JavaScript — ou uma função, que só existe quando o React assume. O React 19 foi desenhado para o segundo caso, mas o primeiro continua valendo quando você quer que o envio funcione mesmo numa conexão ruim ou com o JavaScript bloqueado.

3. A caixa: o nome do campo é a chave

Na caixa abaixo, a ação já está ligada ao formulário e lê dados.get("pao"). O campo, porém, está sem name: o FormData não tem essa chave, e o pedido chega como null. Digite um pão e clique em Encomendar para ver.

Dê ao campo o nome que a ação procura: name="pao". Depois digite “Pão integral”, clique em Encomendar e veja o pedido aparecer.

function App() {
  const [pedido, setPedido] = useState("(nada)");

  return (
    <form action={function (dados) { setPedido(String(dados.get("pao"))); }}>
      <input />
      <button>Encomendar</button>
      <p>Pedido: {pedido}</p>
    </form>
  );
}

Repare em dois detalhes do painel. O primeiro: sem o conserto, o parágrafo mostraria “Pedido: null” — não um erro, só um valor vazio que virou texto. É o mesmo silêncio das props ausentes que você já viu: falta um nome, o dado não chega, e a tela mostra o que der.

O segundo detalhe é aquele action enorme, cheio de JavaScript, que aparece no HTML gerado. Ele não é o seu código: é uma trava do React. Se o formulário for enviado antes de o JavaScript assumir — numa página que ainda está carregando, por exemplo —, o navegador executa aquela linha e mostra o erro em vez de navegar para outro lugar. Ignore o texto; o que importa é que o form está lá e a ação roda.

4. O que a ação recebe

Vale abrir o FormData para ver o que ele é. A ação pode listar as chaves que chegaram, e o console mostra a forma do objeto sem precisar de nenhuma biblioteca:

function Encomenda() {
  return (
    <form action={function (dados) {
      dados.forEach(function (valor, chave) {
        console.log("campo: " + chave + " = " + valor);
      });
    }}>
      <input name="pao" />
      <input name="quem" />
      <button>Encomendar</button>
    </form>
  );
}

Com “Baguete” no primeiro campo e “Ana” no segundo, o console mostra duas linhas:

campo: pao = Baguete
campo: quem = Ana

Duas coisas ficam claras. Primeiro, a ordem é a ordem dos campos no formulário. Segundo, só aparece o que tem name e só aparece o que tem valor — campo vazio simplesmente não entra. Isso explica por que a validação precisa acontecer dentro da ação: o FormData não reclama de nada, ele só entrega o que existe.

Existe uma diferença importante entre os tipos de campo, e ela confunde na primeira vez. Texto, e-mail, número e área de texto chegam como texto — número também, ainda que você tenha digitado type="number". Caixa de seleção marcada chega com o valor "on" quando não tem value, e desmarcada não chega. Vários campos com o mesmo name chegam todos, e para ler todos é preciso dados.getAll("pao"), não get.

Um caso especial que vale reconhecer: arquivos. Um input type="file" também entra no FormData, e o valor lido com get é um File, não texto. É por isso que a caixa usa String(dados.get("pao")) antes de guardar: sem a conversão, o valor bruto é null ou o que veio, e o JSX reclama ao desenhar um objeto. Converter na entrada evita o erro mais adiante.

5. A caixa: validar dentro da ação

Validação em formulário com ação tem um lugar natural: a própria ação. Ela recebe os dados, decide se está tudo certo e devolve o que a tela deve mostrar. Para guardar esse retorno existe o useActionState, que devolve três coisas: o estado atual, a ação pronta para o form e um aviso de pendência.

Clique em Encomendar com o campo vazio: hoje entra um pedido com “null”. Faça a ação devolver "Informe o pão" quando o campo estiver vazio, e o pedido normal quando não estiver.

function App() {
  const [estado, enviar] = React.useActionState(function (anterior, dados) {
    const pao = dados.get("pao");
    return "Pedido: " + pao;
  }, "(nada)");

  return (
    <form action={enviar}>
      <input name="pao" />
      <button>Encomendar</button>
      <p>{estado}</p>
    </form>
  );
}

function App() {
  const [estado, enviar] = React.useActionState(function (anterior, dados) {
    const pao = dados.get("pao");
    if (!pao) return "Informe o pão";
    return "Pedido: " + pao;
  }, "(nada)");

  return (
    <form action={enviar}>
      <input name="pao" />
      <button>Encomendar</button>
      <p>{estado}</p>
    </form>
  );
}

A ação recebe dois argumentos: o estado anterior e o FormData. O valor que ela devolve vira o novo estado. Isso é diferente de useState, em que você chama o setter: aqui a ação devolve o próximo estado, e o React guarda. O primeiro argumento existe porque a próxima ação pode querer saber o que aconteceu antes — um histórico, um contador, um “acrescentar ao que já existe”.

O useActionState é assunto da aula O useActionState, onde ele aparece inteiro. Aqui ele entra só para você ver a validação no lugar certo, sem precisar de um estado separado nem de um useState paralelo. O terceiro item, que a caixa ignora, é a pendência — o “está enviando” que veremos na seção de armadilhas.

Sobre a pendência, uma recomendação prática. Enquanto a ação roda, o React considera aquele envio em andamento e o useActionState devolve pendente: true. Use isso em três lugares: no disabled do botão, no texto dele (“Enviando…” em vez de “Encomendar”) e num aviso para leitor de tela, com role="status". O primeiro evita o pedido duplicado; os outros dois evitam a dúvida de quem está olhando para a tela sem saber se o clique funcionou.

6. A caixa: o histórico que não perde pedido

Agora o caso que a Ana viveu na padaria. O formulário guarda os pedidos numa lista, e cada envio deveria somar um item. No código abaixo, o envio troca a lista inteira por um array de um item só: o cliente encomenda três vezes e vê só o último pedido.

Cada envio deve somar à lista, não substituir. Use a forma de atualização com o valor anterior dentro do setPedidos, e encomende dois pães diferentes.

function App() {
  const [pedidos, setPedidos] = useState([]);

  return (
    <form action={function (dados) { setPedidos([String(dados.get("pao"))]); }}>
      <input name="pao" />
      <button>Encomendar</button>
      <ul>
        {pedidos.map(function (pao, i) { return <li key={i}>{pao}</li>; })}
      </ul>
    </form>
  );
}
<form action="javascript:throw new Error('A React form was unexpectedly submitted. If you called form.submit() manually, consider using form.requestSubmit() instead. If you\'re trying to use event.stopPropagation() in a submit event handler, consider also calling event.preventDefault().')">
  <input name="pao">
  <button>Encomendar</button>
  <ul></ul>
</form>

function App() {
  const [pedidos, setPedidos] = useState([]);

  return (
    <form action={function (dados) {
      const pao = String(dados.get("pao"));
      setPedidos(function (anteriores) { return anteriores.concat(pao); });
    }}>
      <input name="pao" />
      <button>Encomendar</button>
      <ul>
        {pedidos.map(function (pao, i) { return <li key={i}>{pao}</li>; })}
      </ul>
    </form>
  );
}

Depois do primeiro envio, repare em uma coisa que não está no código: o campo voltou a ficar vazio sozinho. É o reset automático do React 19 para formulários não controlados — envio concluído, campos limpos. Ele é ótimo para uma encomenda e péssimo para um formulário de cadastro em que a pessoa perdeu o que digitou por causa de um erro; nesse caso, devolver o que ela escreveu faz parte da mensagem de erro.

Se o formulário precisa manter o que a pessoa digitou depois de um erro, o reset automático vira um problema. Duas saídas comuns: tornar os campos controlados, guardando cada valor em estado e devolvendo-o na mensagem de erro, ou usar o estado que a ação devolve para preencher os campos com defaultValue na próxima renderização. As duas funcionam; a primeira dá mais trabalho e mais controle, a segunda é mais barata e combina com o jeito do React 19.

A forma de atualização, setPedidos(function (anteriores) { … }), também merece atenção. Ela não é exclusividade de actions: vale em qualquer lugar. Serve porque a ação pode rodar depois de um tempo, quando o valor de pedidos no closure já está velho. Recebendo o anterior por parâmetro, você sempre soma sobre o valor mais recente — e nunca perde um pedido.

7. Action ou onSubmit?

O caminho antigo não morreu. Ele é necessário quando você precisa de algo que só o evento submit dá, ou quando está num projeto com uma biblioteca que toma conta do formulário. A diferença é de quem faz o trabalho de colher os campos.

PassoCom onSubmitCom action
impedir o recarregamentoevent.preventDefault() na mãoo React faz
reunir os camposFormData(event.target) na mãoo React entrega pronto
avisar que está enviandoum useState ligado e desligadoo item pending do useActionState
limpar depois do envioreset manual ou estado controladoreset automático dos campos não controlados
quando usarevento com lógica própria, biblioteca externaformulário comum que envia dados

Há uma diferença de comportamento que não aparece no JSX: o React executa a ação dentro de uma transição. Na prática, isso quer dizer que a interface continua respondendo enquanto o envio acontece — a pessoa pode clicar em outro lugar, digitar em outro campo, e a tela não trava esperando o servidor. É o mesmo mecanismo do useTransition da aula O useTransition, aplicado ao formulário: o envio é trabalho não urgente, e o React sabe disso.

Repare que o FormData aparece nos dois caminhos. Ele não é uma invenção do React: é uma API do navegador, que existe desde muito antes. O React 19 só passou a construir e entregar esse objeto para você, no lugar de obrigar cada projeto a repetir as mesmas quatro linhas.

8. As armadilhas

Quatro tropeços concentram quase todos os problemas de formulário com ação. Três deles não dão erro nenhum: só produzem pedidos errados, o que é pior.

SintomaCausaConserto
o pedido chega com nullo campo está sem namedar ao campo o mesmo nome que a ação lê
o primeiro pedido funciona e o terceiro nãoa ação substitui em vez de somaratualizar com o valor anterior
a caixa marcada chega como "on"falta value no campovalue="urgente"
o botão pode ser clicado cinco vezesa pendência foi ignoradadisabled={pendente} no botão

A terceira linha é a que mais surpreende. Uma caixa de seleção sem value manda o texto "on", e uma caixa desmarcada não manda nada — nem false, nem "off". No servidor, “não veio” é o jeito de dizer “desmarcada”. Se você precisa de um valor com significado, escreva o valor:

campo: pao = Baguete
campo: urgente = on
campo: observacao = sem cebola

Vale também saber o que o preventDefault deixou de existir. Com action, não existe mais evento chegando na sua função: o que chega é o FormData. Se você precisa do evento — para ler um campo que não tem name, ou para focar um elemento depois do envio —, guarde uma referência com useRef e use ref.current em vez de event.target.

9. Cenários do dia a dia

Cenário 1: o campo de observação que ninguém recebia

A Ana acrescentou “observação” ao formulário e esqueceu o name. Os pedidos chegavam sem o texto, e o cliente reclamava no balcão. Como a ação lia só os campos que existiam, nada quebrou: o pedido saiu sem o recado. O conserto foi uma palavra no JSX — e a lição de conferir o FormData no console antes de dizer que o formulário está pronto.

Cenário 2: o formulário que limpava o nome da cliente

No cadastro de cliente, a ação recusou o telefone e devolveu a mensagem de erro. O React já havia limpado os campos, então a cliente teve de digitar tudo de novo — e desistiu. A saída foi devolver os valores na mensagem e preencher os campos com eles, ou manter o formulário controlado enquanto a validação não passa.

Cenário 3: a encomenda enviada duas vezes

O serviço da padaria demorava dois segundos. Sem desabilitar o botão durante a pendência, o cliente clicava três vezes e gerava três pedidos iguais. O disabled={pendente} resolveu na hora — e o aviso “Enviando…” no botão resolveu a dúvida de quem estava olhando para a tela.

11. Resumo

Com action, o formulário entrega os campos reunidos num FormData e o React cuida do preventDefault, do reset e do período de pendência. Cada campo precisa de name, e o nome é a chave que a ação usa para ler. Texto chega como texto, caixa marcada sem value chega como "on", e campo vazio não chega.

A validação mora dentro da ação. Com useActionState, o que a ação devolve vira o estado que a tela mostra — mensagem de erro ou confirmação —, e o terceiro item avisa quando o envio está em andamento. Para listas, atualize com o valor anterior, senão cada envio apaga o que veio antes.

O resto é cuidado: desabilitar o botão enquanto envia, devolver os valores quando a validação falha e lembrar que o reset automático é ótimo para encomenda e ruim para cadastro. As actions têm aula própria em As Actions, e o estado delas em O useActionState — o que você viu aqui é o suficiente para reescrever os formulários do site da padaria.

Para lembrar

  • <form action={fn}> substitui onSubmit + preventDefault.
  • A ação recebe um FormData; lê-se com dados.get("nome").
  • Sem name o campo não é enviado — e não dá erro.
  • Número chega como texto; caixa marcada sem value chega como "on".
  • Vários campos com o mesmo nome: getAll, não get.
  • useActionState devolve estado, ação e pendência.
  • A ação devolve o próximo estado; não chama setter.
  • Lista se atualiza com o valor anterior, nunca substituindo.
  • O React limpa os campos não controlados depois do envio.
  • Desabilite o botão enquanto pendente para não duplicar pedido.
