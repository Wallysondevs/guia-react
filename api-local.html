API local

A Ana precisa cadastrar os pães da vitrine pelo próprio site: nome, preço, se está quente. O servidor da padaria só fica pronto no mês que vem — e ela tem feira no sábado. A saída não é esperar nem inventar dados em cada componente: é escrever, dentro do projeto, uma camada que faz o papel do servidor. Ela responde com atraso, guarda o que foi cadastrado, sabe recusar nome repetido, e tem as mesmas funções que a API de verdade vai ter. É a API local.

Você vai aprender
  • O que é uma API local e por que ela não é “dado falso”.
  • Como a tela pede dados sem saber de onde eles vêm.
  • Uma base de dados em memória, com listar e criar.
  • Como simular o erro que o servidor devolveria — 409, nome repetido.
  • Por que o atraso artificial de 10 ms faz parte do exercício.
  • O que muda quando a API de verdade chega: só um arquivo.
  • O que a API local não resolve, e é bom saber desde já.

1. A cena: o servidor que ainda não existe

Sem servidor, o caminho natural é cada componente carregar os próprios dados. A vitrine tem uma lista de pães escrita no arquivo; o painel tem outra; o carrinho tem uma terceira. A Ana cadastra um pão novo e precisa editar três lugares — e, claro, esquece um.

function Vitrine() {
  const paes = ["pão francês", "brioche"];
  return <ul>{paes.map((p) => <li key={p}>{p}</li>)}</ul>;
}

function Painel() {
  const paes = ["pão francês", "brioche", "sonho"];
  return <p>{paes.length} pães cadastrados</p>;
}

Aqui já há um problema antes de qualquer servidor: não existe uma fonte da verdade. Cada componente tem a sua, e elas discordam — a vitrine mostra dois pães, o painel conta três. A API local resolve isso do jeito que o servidor resolveria: um lugar só guarda os dados, e todo mundo pergunta para esse lugar.

2. O que é uma API local

“API” é o conjunto de funções que um programa oferece para outros programas conversarem com ele. Quando o servidor existir, a vitrine vai chamar fetch("https://loja.test/api/paes") e receber um JSON. Enquanto ele não existe, a vitrine chama listarPaes() — uma função do próprio projeto que devolve os mesmos dados, no mesmo formato.

A palavra “local” quer dizer “roda junto com o site, no navegador”, e não “falsa”. A diferença está no endereço: em vez de atravessar a internet, a resposta nasce dentro do arquivo api.js. O que importa é o contrato: quais funções existem, o que elas recebem, o que devolvem e que erros podem dar. Se o contrato for igual ao do servidor futuro, trocar um pelo outro é trabalho de meia hora.

API
Conjunto de funções com que um sistema conversa com outro. Aqui, as funções que falam com os dados dos pães.
contrato
O que cada função promete: nome, o que recebe, o que devolve e que erro pode lançar. É o que permite trocar a implementação sem mexer em quem chama.
base
A lista de dados em memória — o array que faz o papel de tabela do banco. Vive enquanto a página estiver aberta.
simular
Reproduzir de propósito as condições do servidor: atraso, erro, validação. Sem isso, o código só é testado no cenário fácil.
409
O número que um servidor devolve quando o dado conflita com outro que já existe — nome repetido, por exemplo.

3. A tela pede, a API responde

O primeiro passo é tirar os dados de dentro do componente. A tela deixa de saber onde os pães estão guardados e passa a perguntar; quem sabe é a função. Isso dá um pouco mais de código agora e muito menos depois.

A vitrine tem a lista escrita à mão e mostra um pão só. Use a função listarPaes() dentro do efeito para a tela refletir a base da API local — três pães, incluindo o pão de queijo.

const base = ["pão francês", "brioche", "pão de queijo"];

function listarPaes() {
  return new Promise((ok) => setTimeout(() => ok([...base]), 0));
}

function App() {
  const [paes, setPaes] = useState([]);

  useEffect(() => {
    setPaes(["pão francês"]);
  }, []);

  return <ul className="paes">{paes.map((p) => <li key={p}>{p}</li>)}</ul>;
}

function App() {

}

Repare no [...base] dentro de listarPaes. Ele devolve uma cópia, e não o array original. Isso é imitação de servidor, não preciosismo: quando a resposta vem pela rede, ela é sempre uma cópia — mexer nela não mexe no servidor. Se a API local devolvesse o array interno, o componente poderia alterar a base sem pedir, e o dia da troca pelo fetch seria um festival de bugs.

4. A base em memória

Guardar é a segunda função do contrato. criarPao(nome) recebe o nome, acrescenta na base e devolve o pão criado, já com identificador — é o que um servidor faria. A base é um array no topo do arquivo, fora de qualquer componente, para que todas as telas vejam o mesmo conteúdo.

A função criarPao responde como se tivesse gravado, mas não grava nada. Acrescente o pão na base antes de resolver a Promise: depois de cadastrar croissant, a lista tem de mostrar dois pães.

const base = ["pão francês"];

function listarPaes() {
  return new Promise((ok) => setTimeout(() => ok([...base]), 0));
}

function criarPao(nome) {
  return new Promise((ok) => setTimeout(() => ok({ nome: nome }), 0));
}

function App() {
  const [nome, setNome] = useState("");
  const [paes, setPaes] = useState(base);

  function cadastrar() {
    criarPao(nome).then(() => listarPaes().then((lista) => setPaes(lista)));
  }

  return (
    <div>
      <input id="nome" value={nome} onChange={(e) => setNome(e.target.value)} />
      <button id="cadastrar" onClick={cadastrar}>cadastrar</button>
      <ul className="paes">{paes.map((p) => <li key={p}>{p}</li>)}</ul>
    </div>
  );
}

A sequência do cadastrar é a sequência de qualquer servidor: mandar, esperar a confirmação, pedir a lista de novo. Poderia ser mais econômico — usar o pão devolvido e acrescentar na tela —, e seria ótimo para a sensação de velocidade; é exatamente o assunto da aula de atualização otimista. Para a API local, o importante é o listarPaes() no fim: a tela fica sincronizada com a fonte da verdade, e não com o que ela acha que aconteceu.

5. Erro de propósito: a validação que o servidor faria

Um servidor de verdade não aceita dois pães com o mesmo nome. Ele responde 409 e a tela mostra a mensagem. Se a API local aceita tudo, o código de tela nunca exercita o caminho do erro — e no dia da troca aparece uma tela quebrada em produção.

Simular validação é fácil: antes de gravar, olhe a base; se o nome já está lá, rejeite a Promise com um erro que traga a mensagem combinada. Quem chama trata com catch, como trataria o erro do fetch.

A API local aceita pão repetido. Faça criarPao recusar nome que já está na base, rejeitando com a mensagem 409: já existe um pão com esse nome. Cadastre brioche e confira: a lista continua com dois pães e a mensagem aparece.

const base = ["pão francês", "brioche"];

function listarPaes() {
  return new Promise((ok) => setTimeout(() => ok([...base]), 0));
}

function criarPao(nome) {
  return new Promise((ok) => setTimeout(() => {
    base.push(nome);
    ok({ nome: nome });
  }, 0));
}

function App() {
  const [nome, setNome] = useState("");
  const [paes, setPaes] = useState(base);
  const [aviso, setAviso] = useState("");

  function cadastrar() {
    criarPao(nome)
      .then(() => listarPaes().then((lista) => { setPaes(lista); setAviso(""); }))
      .catch((e) => setAviso(e.message));
  }

  return (
    <div>
      <input id="nome" value={nome} onChange={(e) => setNome(e.target.value)} />
      <button id="cadastrar" onClick={cadastrar}>cadastrar</button>
      <p>{aviso}</p>
      <ul className="paes">{paes.map((p) => <li key={p}>{p}</li>)}</ul>
    </div>
  );
}

Note que o componente mudou zero linha para a validação existir. Ele já tinha o catch, já mostrava a mensagem; quem ganhou regra foi a API. Essa é a vantagem de ter o contrato num lugar só: o comportamento novo entra na camada de dados e a tela continua a mesma.

6. O atraso artificial

Todas as funções da API local devolvem Promise resolvida depois de um tempinho. Poderia ser instantâneo, e o código funcionaria — mas o aprendizado seria incompleto. Com setTimeout de 0 a 10 milissegundos, você é obrigado a escrever o then ou o await, exatamente como escreveria com servidor de verdade.

const ATRASO = 10;

function listarPaes() {
  return new Promise((ok) => {
    setTimeout(() => ok([...base]), ATRASO);
  });
}

O valor do ATRASO fica numa constante com nome, e não espalhado. Na vida real de quem desenvolve, esse número costuma ser maior no começo do projeto: quinhentos milissegundos para você sentir a tela de carregando, trezentos para ver o botão desabilitado, dois segundos para descobrir que falta um indicador de progresso. Simular lentidão é um favor que você faz a si mesmo — e a lista de estados de carregamento da aula de carregando e erro só faz sentido se existir algo lento para esperar.

Um cuidado com atraso grande: ele atrapalha os testes automáticos, que têm limite de tempo. Por isso os exemplos deste guia usam zero ou dez milissegundos, e o número maior é sugerido no comentário, para você experimentar com a mão.

Vale também uma função de leitura por identificador, buscarPao(nome), que devolve o pão ou null. Ela parece redundante com listarPaes e não é: o servidor de verdade vai ter um endpoint barato para isso, e o componente que precisa de um pão só não deve baixar a lista inteira. Cada função da camada é uma promessa de que aquele dado existe e é buscável — e promessa que a tela já usa hoje não vira surpresa amanhã.

7. A API local e a API de verdade

A graça da camada é a troca. Quando o servidor ficar pronto, o arquivo api.js muda por dentro e as funções continuam com o mesmo nome e o mesmo formato de retorno. A tabela mostra o antes e o depois:

FunçãoHoje, localAmanhã, com servidor
listarPaes()devolve [...base] depois de 10 msfetch("/api/paes").then((r) => r.json())
criarPao(nome)base.push e resolve com o pãofetch com POST e JSON.stringify
apagarPao(nome)base.splice e resolvefetch com DELETE
erro de nome repetidoerro(new Error("409: …"))o servidor responde 409 e a tela lê a mensagem do corpo
atrasosetTimeout de 10 mso tempo da rede, que ninguém controla

O ponto delicado da troca é o erro. Na versão local, o erro chega como exceção (Promise rejeitada). Na versão real, o fetch não rejeita quando o servidor responde 409: ele resolve com uma resposta cujo status é 409, e o corpo traz a mensagem. Quem escreveu a camada com cuidado esconde essa diferença: a função criarPao do servidor real confere o status e lança o erro, para que a tela continue só com o catch. É por isso que a camada de dados vale a pena mesmo quando o servidor já existe.

8. O que a API local não resolve

A lista do que ela não faz é tão útil quanto a do que faz. Ela é memória de navegador: some ao recarregar a página, não é vista pela Ana no celular, não sobrevive a duas abas abertas ao mesmo tempo. Também não valida de verdade — qualquer pessoa com o console aberto pode chamar base.push. E não protege dado nenhum: não há login, não há permissão, não há registro de quem fez o quê.

Para o que ela serve, nada disso atrapalha: desenvolver a tela antes do servidor, testar estados de erro, combinar o contrato com quem vai escrever o back-end, e ensinar o caminho dos dados sem depender de rede. Para o que não serve, é bom saber antes: não use API local para guardar o que precisa durar — para isso existe localStorage, e mesmo ele é só do navegador.

Esse log, escrito dentro de listarPaes, é o retrato da base no momento da chamada. É a primeira coisa a conferir quando a tela mostra algo estranho: se a base já está errada, o problema é de dados; se está certa, o problema é de desenho.

console: erro 409: já existe um pão com esse nome

E esse, escrito antes de rejeitar, mostra a validação fazendo o trabalho dela. Duas linhas de log na camada de dados valem mais do que dez no componente, porque elas contam o que o “servidor” viu.

Há um terceiro item nessa lista, mais sutil: a API local não tem concorrência. Dois cliques rápidos cadastram o mesmo pão duas vezes sem ninguém reclamar, porque não há outro cliente disputando a mesma linha do banco. No servidor, esse caso é tratado com transação e índice único. Enquanto você está na versão local, a defesa é a de sempre: desabilitar o botão enquanto a chamada está em andamento.

Nada disso diminui a utilidade dela. Desenvolver contra uma API local é o que permite começar a tela na segunda-feira e ter o servidor na sexta sem reescrever componente. O que não se pode é confundir “funciona no meu navegador” com “pronto para produção”: a distância entre os dois é exatamente a lista acima.

9. Cenários do dia a dia

Cenário 1: a feira de sábado

O servidor só ficaria pronto no mês seguinte e a feira era no sábado. Com a API local, a Ana cadastrou os doze pães, ajustou preços e testou a tela de erro digitando um nome repetido. No dia da feira o site funcionou; na segunda, o Nando trocou o arquivo api.js pelas chamadas de verdade e nenhum componente precisou ser tocado.

Cenário 2: o contrato combinado antes do código

Antes de o servidor existir, a Ana e o Nando escreveram juntos as quatro funções da camada: listarPaes, criarPao, apagarPao e buscarPao. Decidir os nomes e os formatos no papel evitou a discussão clássica de depois: a tela esperando nome e o servidor mandando titulo.

Cenário 3: o erro que só existia em produção

Numa versão anterior, a API local aceitava qualquer coisa. No dia em que o servidor entrou no ar, o cadastro de pão repetido passou a devolver 409 e a tela ficou em branco — ninguém tinha escrito o caminho do erro. Depois disso, a regra ficou: se o servidor pode recusar, a API local recusa também, com a mesma mensagem.

Exercício: o contrato da camada

Toda função da API local devolve algo que pode ser esperado com await, igual à resposta do servidor. Complete o tipo de retorno que a camada usa:

function listarPaes() { return new ((ok) => { setTimeout(() => ok([...base]), 10); }); }

Dica: é o objeto que representa “um valor que ainda não chegou” — o mesmo que o fetch devolve e o mesmo que o await espera.

11. Resumo

API local é a camada que faz o papel do servidor dentro do projeto: funções com nome, base de dados em memória, respostas assíncronas com atraso pequeno, erros simulados com as mesmas mensagens que o servidor daria. A tela deixa de conhecer os dados e passa a pedir — e todo mundo que pede vê o mesmo conteúdo.

O valor está no contrato: quando o servidor chegar, só o arquivo da camada muda. Para isso, devolva cópias, use setTimeout para manter o código assíncrono, rejeite o que o servidor rejeitaria e lembre que fetch não rejeita sozinho em 409. E não peça à API local o que ela não pode dar: dados que duram, dados compartilhados entre pessoas e validação de verdade.

Para lembrar

  • API local = funções do projeto que imitam o servidor.
  • O que importa é o contrato: nomes, entradas, saídas e erros.
  • Base em memória fora do componente: uma fonte da verdade.
  • Devolva cópia ([...base]), como a rede faria.
  • setTimeout pequeno mantém o código assíncrono de verdade.
  • Simule o erro (409) — a tela precisa do caminho do erro.
  • Na troca pelo fetch, confira resposta.ok dentro da camada.
  • Memória some ao recarregar; para durar, é localStorage ou servidor.
