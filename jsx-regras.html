As Regras do JSX

O primeiro componente da Ana funcionou, e ela foi comemorar cedo demais: na segunda tentativa veio um erro que falava de "conteúdo não terminado", e ela passou vinte minutos olhando um parágrafo de duas linhas. O problema não era o parágrafo, era uma tag que não fechava. JSX parece HTML e não é: ele é traduzido para JavaScript, e a tradução exige regras. Nesta aula a Ana aprende as cinco regras que resolvem quase todo erro de sintaxe — e a ler as mensagens, que são feias mas dizem mais do que parecem.

Você vai aprender
  • Por que toda tag precisa fechar, inclusive as vazias como <br>.
  • Por que o componente devolve um pai só e o que o fragmento faz de diferente.
  • Quando usar aspas e quando usar chaves dentro de um atributo.
  • Como se escreve comentário dentro do JSX.
  • Que dentro das chaves cabe valor, não comando.
  • A ler as mensagens reais do compilador e achar a linha do problema.

1. A cena: o erro que não fala do problema

A Ana queria duas linhas no aviso da padaria. Escreveu o parágrafo com uma quebra no meio, do jeito que se faz em HTML há trinta anos:

function App() {
  return (
    <p>Aberto das 6h às 18h<br>aos sábados até 13h</p>
  );
}

E recebeu isto:

Erro: não compilou: /App.jsx: Unterminated JSX contents. (3:54)

"Conteúdo JSX não terminado", na linha 3, coluna 54. A linha 3 é o parágrafo inteiro, e a coluna 54 é o fim dele — depois do </p>. Nada disso aponta para o <br>, que é o culpado. A mensagem parece errada e não é: o compilador chegou ao fim do parágrafo ainda esperando o fechamento de alguma tag aberta, e o que ele sabia dizer era "não terminou".

É assim que o JSX se comporta quando algo está fora do lugar: o erro aparece onde a leitura parou, não onde o problema começou. Saber disso muda a forma de procurar. Em vez de procurar na coluna indicada, procure a última tag que você abriu.

2. Regra 1: toda tag fecha

Em HTML, <br>, <img> e <input> vivem sem fechamento, e o navegador releva. Em JSX não existe relevar: cada tag aberta tem de ser fechada, e as que não têm conteúdo se fecham nelas mesmas, com uma barra antes do sinal de maior.

tag de abertura
O começo de um elemento: <p>. Em JSX ela sempre tem um par.
fechamento
O fim do elemento: </p>. Precisa combinar com a abertura, com a mesma palavra.
auto-fechada
A tag que já termina fechada: <br />, <img />. A barra antes do > é obrigatória.
fragmento
Um pai invisível, escrito <>...</>. Agrupa irmãos sem criar nó no HTML.
expressão
O que vai dentro das chaves: algo que produz um valor, como uma variável, uma conta ou um ternário.
atributo
Uma informação na tag: src, alt, className. O valor vem entre aspas ou entre chaves.

Por que tanta rigidez? Porque o HTML é lido por um analisador que foi feito para relevar: ele conhece as tags vazias e sabe fechar sozinho o que faltou. O JSX é lido por um tradutor que precisa produzir JavaScript válido, e JavaScript não tem esse perdão. Cada tag precisa virar uma chamada com começo e fim claros; sem o fechamento, não há como montar a chamada — e o tradutor desiste.

O aviso precisa de duas linhas, e a tag de quebra está sem fechamento. Escreva do jeito que o JSX aceita — a mesma tag, fechada nela mesma.

function App() {
  return (
    <p>Aberto das 6h às 18h<br>aos sábados até 13h</p>
  );
}
Erro: não compilou: /App.jsx: Unterminated JSX contents. (3:54)

  1 | function App() {
  2 |   return (
> 3 |     <p>Aberto das 6h às 18h<br>aos sábados até 13h</p>
    |                                                       ^
  4 |   );
  5 | }

function App() {
  return (
    <p>Aberto das 6h às 18h<br />aos sábados até 13h</p>
  );
}

Depois de rodar, o painel mostra o parágrafo com o <br> dentro — e note que no painel ele aparece como <br>, sem a barra. É que o painel descreve o DOM, e no DOM a tag de quebra é assim mesmo. A barra é uma exigência da escrita JSX, não do resultado.

A mesma regra vale para qualquer tag vazia: <img />, <input />, <hr />. E vale para tags com conteúdo também: um <div> aberto precisa de um </div> no lugar certo, e um <h1> fechado com </h2> não é "quase certo" — é erro. O JSX não adivinha onde você queria fechar.

3. Regra 2: um pai só, e o fragmento como pai invisível

A segunda regra já apareceu na aula do primeiro componente: o return devolve um elemento. Dois irmãos soltos não cabem em uma única chamada de função, e o compilador avisa com a mensagem que você vai reconhecer de longe: Adjacent JSX elements must be wrapped in an enclosing tag.

A solução mais óbvia é embrulhar tudo em uma <div>, e ela funciona — mas cria um elemento a mais no HTML. Às vezes isso não importa; às vezes importa muito, como dentro de um <table>, onde uma div no meio quebra a tabela. Para esses casos existe o fragmento: um pai que não vira nó nenhum.

O componente devolve dois elementos soltos e não compila. Embrulhe os dois em um fragmento — <> para abrir e </> para fechar — e confira no painel que nenhuma div apareceu.

function App() {
  return (
    <h1>Promoções</h1>
    <p>Pão quentinho saindo do forno</p>
  );
}
Erro: não compilou: /App.jsx: Adjacent JSX elements must be wrapped in an enclosing tag. Did you want a JSX fragment <>...</>? (4:4)

  2 |   return (
  3 |     <h1>Promoções</h1>
> 4 |     <p>Pão quentinho saindo do forno</p>
    |     ^
  5 |   );
  6 | }

function App() {
  return (
    <>
      <h1>Promoções</h1>
      <p>Pão quentinho saindo do forno</p>
    </>
  );
}

O painel mostra os dois elementos lado a lado, sem casca:

<h1>Promoções</h1>
<p>Pão quentinho saindo do forno</p>

É exatamente o que se quer. O fragmento é um pai para o compilador e um nada para o navegador. Se você tivesse usado uma div, o painel mostraria a div em volta, e qualquer CSS que contasse filhos ou qualquer leiaute que dependesse da estrutura precisaria de um ajuste a mais.

Existe também a forma escrita por extenso, <Fragment>...</Fragment>, que faz o mesmo. Ela serve quando o fragmento precisa receber a key — assunto de listas — e é a única diferença prática entre as duas. No dia a dia, <>...</> é o que se digita.

4. Regra 3: aspas para texto, chaves para JavaScript

Dentro de um atributo, existe uma separação rígida. Se o valor é texto fixo, vão aspas. Se o valor vem de uma variável ou conta, vão chaves. As duas formas não se misturam: aspas com chaves dentro viram texto literal, e é aí que muita gente se perde.

const arquivo = "pao.jpg";

<img src="arquivo" />      // src vira o texto "arquivo"
<img src={arquivo} />      // src vira o valor da variável

A primeira linha é o erro clássico: a imagem não carrega porque o navegador procura um arquivo chamado literalmente arquivo. Dá para ver a diferença no painel, que mostra o atributo final:

A variável arquivo guarda o nome do arquivo da foto, mas o src está com o texto "arquivo". Use chaves para passar o valor da variável.

function App() {
  const arquivo = "pao.jpg";
  return (
    <figure>
      <img src="arquivo" alt="Pão quentinho" />
      <figcaption>Pão francês</figcaption>
    </figure>
  );
}
<figure>
  <img alt="Pão quentinho" src="arquivo">
  <figcaption>Pão francês</figcaption>
</figure>

function App() {
  const arquivo = "pao.jpg";
  return (
    <figure>
      <img src={arquivo} alt="Pão quentinho" />
      <figcaption>Pão francês</figcaption>
    </figure>
  );
}

Há um caso intermediário que confunde: src={"pao.jpg"} com chaves e o texto entre aspas dentro. Também funciona, porque dentro das chaves você está em JavaScript, e uma string é JavaScript válido. Na prática, aspas diretas são mais curtas quando o valor é fixo — e chaves são obrigatórias quando vem de variável.

Uma nota sobre atributo sem nada: src=pao.jpg, sem aspas e sem chaves, não compila. A mensagem é JSX value should be either an expression or a quoted JSX text — "o valor do JSX tem de ser uma expressão ou um texto entre aspas". É literal: ou um dos dois, nunca um terceiro.

5. Regra 4: os nomes não são os do HTML

Quem vem do HTML escreve class, for e onclick. No JSX esses nomes não são os nomes: como o JSX vira JavaScript, os atributos se chamam className, htmlFor e onClick. A regra por trás é simples — são propriedades de um objeto JavaScript, então usam a convenção do JavaScript, que é a letra maiúscula no meio da palavra.

A lista é curta e a próxima aula é só sobre ela, com as conversões e os detalhes. Por enquanto, guarde a regra geral: se o nome do atributo tem duas palavras no HTML original, no JSX ele costuma virar uma palavra só com maiúscula no meio. E class vira className porque class é palavra reservada do JavaScript — o mesmo motivo para for virar htmlFor.

Uma consequência que surpreende: o JSX diferencia maiúscula de minúscula também nas tags. <div> é a tag do HTML; <Div> é uma função chamada Div, que ninguém definiu. O resultado não é um erro na tela: é nada. O React tenta chamar uma função que não existe, o desenho falha e o painel mostra que nada foi desenhado.

6. Regra 5: comentário é chaves com barra e asterisco

Comentário de HTML, <!-- assim -->, não existe no JSX: dentro do return só pode haver elementos e expressões, e o compilador responde com Unexpected token. Comentário de JavaScript de barra dupla também não funciona direto, porque ele só vai até o fim da linha — e o fim da linha, ali, ainda está dentro do JSX.

A forma correta é um comentário de JavaScript dentro de um par de chaves: {/* assim */}. As chaves avisam que ali começa uma expressão; a barra e o asterisco avisam que não há nada dentro, só um recado para quem lê.

function App() {
  return (
    <div>
      {/* o aviso de promoção saiu do ar em março */}
      <p>Pão quentinho saindo do forno</p>
    </div>
  );
}

O comentário não aparece na tela e não aparece no painel: ele é apagado na tradução. É uma das poucas coisas do JSX que não têm representação nenhuma no HTML gerado.

Existe um jeito alternativo, com barra dupla, mas ele depende de o fechamento ficar na linha seguinte — o que só funciona porque a quebra de linha termina o comentário antes da chave. É frágil e não vale a pena: use {/* */} sempre. Você vai reconhecer essa forma em todo código React do mundo, inclusive nos que comentam uma linha inteira para testar alguma coisa.

Para comentar um bloco inteiro de elementos, a mesma forma serve: abra as chaves antes do primeiro elemento e feche depois do último. O compilador trata tudo o que está lá dentro como um recado, e o bloco desaparece do HTML gerado — o que é ótimo para testar uma hipótese ("será que o problema é este pedaço?") sem apagar nada. Só lembre de que comentar não é o mesmo que esconder: se o elemento aparece na tela, ele não está comentado.

7. Dentro das chaves cabe valor, não comando

As chaves abrem uma porta para o JavaScript, e essa porta tem uma limitação que confunde: ali dentro cabe uma expressão — algo que produz um valor — e não um comando. Parece preciosismo e não é: {if (x) ...} e {for (...) ...} não compilam, enquanto {x ? "sim" : "não"} e {x && "sim"} compilam.

A diferença é a de sempre em JavaScript: um comando manda fazer algo e não vale como valor; uma expressão vale. if não vale nada; o ternário vale. O JSX espera um valor para colocar no lugar, então só aceita expressões.

Na prática você não vai sentir falta de if. Para escolher entre duas coisas, o ternário resolve; para mostrar ou não, o && resolve; para decidir antes do return, você usa if fora do JSX, na parte em JavaScript do componente. Cada uma dessas formas tem sua aula mais adiante — aqui basta saber qual porta dá erro e qual não dá.

8. As mensagens reais, traduzidas

Estas são as mensagens que o compilador realmente devolve, copiadas do motor do guia. Elas são em inglês e falam de coisas que você não escreveu, mas cada uma aponta para um problema bem específico:

Repare que a primeira mensagem cobre vários casos: tag vazia sem barra, div sem fechar, fechamento trocado. O compilador não tenta adivinhar qual dos três você fez — ele só sabe que chegou ao fim esperando algo. Por isso a leitura certa é "procure a última tag aberta", e não "conserte a coluna indicada".

Além da mensagem, o painel mostra um pedaço do seu arquivo com um sinal embaixo da linha problemática. Esse desenho se chama moldura de código, e é o que mais ajuda quando a mensagem é genérica: o sinal aponta a coluna exata em que a leitura parou. Nas caixas do guia ele aparece sempre abaixo do Erro: não compilou, com a linha numerada à esquerda. Vale olhar a moldura antes de reler o código inteiro: em três de cada quatro casos, o problema está na linha anterior à marcada.

Há ainda as mensagens que aparecem no console do navegador, e não no painel. Elas nascem na hora de desenhar, não na tradução: um atributo com nome estranho, uma lista sem identificação, um texto que deveria ser número. Nesse caso o código compila, o componente roda e o React reclama de um detalhe específico. Aqui nas caixas o painel mostra o HTML gerado mesmo assim, e é nele que você percebe o que saiu errado.

9. Cenários do dia a dia

Cenário 1: o erro aponta para a linha errada

A Ana tinha três tags na linha 8 e o erro falava da linha 12. O compilador só percebe o problema quando chega ao fim do bloco, então a linha citada é quase sempre depois do culpado. O método que funciona: apague metade do JSX e rode. Se compilar, o problema estava na metade apagada. Repita até sobrar uma linha. É força bruta e é mais rápido do que reler trinta linhas.

Cenário 2: fragmento ou div?

Use fragmento por padrão e div quando precisar de um lugar para pôr classe ou estilo. A div existe no DOM e serve de caixa; o fragmento não existe e serve só de pai para o compilador. O caso em que isso deixa de ser preferência: dentro de <table>, <ul> e de qualquer pai que só aceite filhos específicos, uma div no meio é um erro de estrutura — ali o fragmento é obrigatório.

Cenário 3: colou HTML de outro lugar e nada funciona

HTML copiado de um site traz class, style="..." e comentários <!-- -->. Os três quebram ou falham silenciosamente no JSX. A conversão é mecânica: class vira className, style vira um objeto entre chaves, e comentário vira {/* */}. Depois disso, boa parte do HTML colado roda sem mais nenhum ajuste — o resto é a próxima aula.

11. Resumo

JSX parece HTML, mas é traduzido para JavaScript, e por isso tem regras mais rígidas. Toda tag fecha; as vazias se fecham nelas mesmas com uma barra. O return devolve um pai só, e quando você não quer criar nó nenhum, o fragmento <>...</> serve de pai invisível. Em atributo, aspas são para texto fixo e chaves são para valores de JavaScript.

Os nomes dos atributos seguem a convenção do JavaScript — className, htmlFor, onClick —, e a maiúscula também separa tag de componente: <div> é HTML, <Div> é uma função que você precisa ter definido. Comentário só existe como {/* */}, e dentro das chaves cabe expressão, não comando.

E a habilidade que vale mais do que decorar as regras: ler a mensagem. Unterminated JSX contents quer dizer "tem tag aberta"; Adjacent JSX elements quer dizer "dois irmãos sem pai"; JSX value should be either an expression or a quoted JSX text quer dizer "faltaram as aspas ou as chaves". A linha indicada é onde a leitura parou, não onde o problema está.

Com essas cinco regras você escreve JSX sem tropeçar no básico. A próxima aula é sobre o que vai dentro das chaves — os valores, as contas e as escolhas que fazem a tela mudar de conteúdo sem mudar de estrutura.

Para lembrar

  • Toda tag fecha; as vazias terminam com />.
  • Um pai só por return; o fragmento não cria nó.
  • Aspas para texto, chaves para variável ou conta.
  • Atributo é camelCase: className, htmlFor, onClick.
  • Maiúscula no começo do nome = componente seu.
  • Comentário é {/* */}, nunca <!-- -->.
  • Nas chaves cabe expressão; if e for ficam fora do JSX.
  • A linha do erro é onde a leitura parou: procure a tag aberta antes dela.
