Depurando no Navegador

O total da Ana apareceu como NaN na tela publicada, e o botão de pedir parou de responder sem mostrar erro nenhum. Ela passou a tarde comentando linhas no escuro, tentando lembrar o que tinha mexido. Na aula de hoje ela troca o chute por método: abre as ferramentas do navegador, lê a mensagem de erro até o fim, põe um ponto de parada e descobre em cinco minutos o que a tarde inteira não revelou.

Você vai aprender
  • Para que serve cada aba do DevTools — e qual delas responde à sua pergunta.
  • A ler uma mensagem de erro: mensagem, componente, arquivo e linha.
  • Como usar console.log sem virar arqueologia.
  • O que é um breakpoint e como andar linha por linha olhando o valor das variáveis.
  • Como o React DevTools mostra props, estado e hooks de um componente.
  • Um método para achar o culpado: reduzir, isolar, comparar.

1. A cena: dois bugs, nenhuma pista

O primeiro bug é barulhento: o total do pedido virou NaN. O segundo é silencioso: o botão "Pedir" não faz nada. Nos dois casos a Ana fez o que todo mundo faz — olhou o código, não viu nada estranho, mudou uma linha qualquer, salvou, o bug continuou, e ela voltou a mexer. Depois de duas horas, o código estava pior e o bug estava lá.

Depurar é investigar, não adivinhar. A diferença entre os dois estilos não está na inteligência: está no método. Em vez de perguntar "o que eu errei?", o depurador pergunta "onde exatamente o valor deixa de ser o esperado?". Cada pergunta dessas tem uma ferramenta no navegador que responde em segundos.

E há uma boa notícia: o React facilita o trabalho. Ele guarda o estado de cada componente de forma visível, avisa no console quando algo suspeito acontece e escreve mensagens que citam o componente e a linha. Metade da depuração é parar de ignorar esses avisos.

O F12 abre as ferramentas (ou o menu do navegador, em "Mais ferramentas"). No Chrome, Firefox e Edge as abas têm os mesmos nomes, com pequenas diferenças. O que você aprende aqui vale nos três.

2. As abas e a pergunta que cada uma responde

O DevTools tem cinco abas que resolvem quase tudo, e cada uma responde a um tipo de pergunta. Escolher a aba certa é metade do trabalho: quem procura um problema de rede no Elements perde a tarde, e quem procura um problema de estilo no Network também.

AbaRespondeQuando é a primeira a abrir
Consoleo que o código disse, avisos e erroshá uma mensagem vermelha na tela
Elementsqual HTML o React gerou e qual estilo venceuo layout ou o texto saiu errado
Sourceso código que rodou, com ponto de parada e passo a passoo valor está errado e você não sabe onde
Networkpedidos, respostas, status e tempoa tela depende de dados que não chegam
Applicationo que está guardado no navegadora configuração ou o login se perde ao recarregar

Além dessas, uma aba extra aparece quando a página usa React: React DevTools. Ela mostra a árvore de componentes em vez da árvore de elementos, e é lá que se vê o estado de cada componente. A instalação é uma extensão do navegador; sem ela, as outras cinco abas continuam funcionando.

console
A saída de texto do navegador. Recebe o que o seu código escreve e o que o próprio navegador e o React relatam.
breakpoint
Um ponto de parada marcado numa linha do código. Quando a execução chega ali, o navegador congela e mostra o valor de todas as variáveis.
stack trace
A lista de chamadas que levou até o erro: de baixo para cima, quem chamou quem, com arquivo e linha.
source map
O arquivo que liga o código minificado ao código-fonte. É o que faz o navegador mostrar App.jsx em vez de uma linha de letras embaralhadas.
React DevTools
A extensão que mostra a árvore de componentes React, com props, estado e hooks de cada um.

3. O console: log com rótulo e objeto separado

O console.log continua sendo a ferramenta mais rápida quando o problema é simples. O que estraga o log é a forma: sem rótulo, ele vira uma pilha de valores sem dono; com +, qualquer objeto vira [object Object] e não diz nada.

A regra é curta: passe uma etiqueta e o valor como argumentos separados, com vírgula. O console mostra a etiqueta e, ao lado, o objeto de verdade — no painel das caixas, em JSON.

Os dois logs não dizem nada: um virou [object Object] e o outro não tem etiqueta. Escreva os dois com rótulo e o objeto separado por vírgula. A missão confere cliente: {"nome":"Ana"} e itens: 3 no painel.

function App() {
  const cliente = { nome: "Ana" };
  const itens = 3;

  console.log("cliente: " + cliente);
  console.log(itens);

  return <p>Pedido de {cliente.nome}</p>;
}
<p>Pedido de Ana</p>
console: cliente: [object Object]
console: 3

function App() {
  const cliente = { nome: "Ana" };
  const itens = 3;

  console.log("cliente:", cliente);
  console.log("itens:", itens);

  return <p>Pedido de {cliente.nome}</p>;
}

No DevTools de verdade o objeto aparece como uma árvore que você abre e fecha, e o valor é lido no momento do clique — o que confunde: um objeto logado e depois alterado mostra o estado novo. Se precisar congelar o retrato, logue uma cópia ({ ...cliente }) ou uma string com JSON.stringify.

Três primos do log valem a viagem, embora o painel das caixas não os mostre: console.table(lista) desenha arrays de objetos em tabela, console.count("pedido") conta quantas vezes aquela linha rodou e console.time("desenho") com console.timeEnd("desenho") mede o tempo entre dois pontos. No painel da caixa você vê só o console.log — e só o do desenho inicial, quando a página monta.

4. Lendo uma mensagem de erro até o fim

A mensagem de erro tem quatro pedaços, e o pessoal costuma ler só o primeiro. O primeiro é o tipo e o texto (TypeError: Cannot read properties of null); o segundo é o que era nulo (reading 'cliente'); o terceiro é o onde, no stack trace; o quarto é o componente que o React cita, quando o erro acontece durante um desenho.

No caso clássico, a leitura é literal: "não consigo ler a propriedade cliente de null". Não é o React, não é o JSX: é um valor que ainda não chegou e já está sendo usado.

O código lê uma configuração que ainda não tem o bloco de entregas, e a caixa mostra o erro. Leia a mensagem e trate o caso: a página deve aparecer com "0 entregas hoje".

const config = { loja: "Padaria da Ana" };
const entregas = config.entregas.ativos;

function App() {
  return (
    <div>
      <h1>{config.loja}</h1>
      <p>{entregas} entregas hoje</p>
    </div>
  );
}
Erro: Cannot read properties of undefined (reading 'ativos')

const config = { loja: "Padaria da Ana" };
const entregas = config.entregas ? config.entregas.ativos : 0;

function App() {
  return (
    <div>
      <h1>{config.loja}</h1>
      <p>{entregas} entregas hoje</p>
    </div>
  );
}

Repare na leitura: o erro não diz "deu ruim no App". Ele diz que não conseguiu ler a propriedade ativos, porque o valor do lado esquerdo (config.entregas) era undefined. A pergunta seguinte se responde sozinha: de onde deveria vir esse entregas? No painel da caixa o erro aparece completo; no navegador, ele vem com a linha exata e a pilha de chamadas:

Uncaught TypeError: Cannot read properties of null (reading 'cliente')
    at Pedido (App.jsx:7:22)
    at renderWithHooks (react-dom_client.js:12171:18)

Leia de baixo para cima: a primeira linha de baixo é o React desenhando, e a de cima é o seu componente, na linha 7. Clicar em App.jsx:7 abre o Sources já naquela linha — esse é o atalho que economiza a tarde.

Quando o erro acontece dentro do desenho de um componente, o React 19 desmonta a árvore e deixa a área vazia: a tela fica em branco e o recado completo vai para o console. No painel das caixas, esse caso aparece como "(o React não desenhou nada)" — o que já é uma pista: o componente quebrou antes de produzir HTML.

Nem todo erro é erro. O React também escreve avisos: chave faltando numa lista, className no lugar de class, campo controlado sem onChange. O aviso não impede a página de rodar, e é exatamente por isso que ele fica lá por meses. Um console limpo é parte de "pronto".

5. O breakpoint: parar o código e olhar dentro

Quando o console.log não basta — porque o valor está certo em um lugar e errado em outro, ou porque você não sabe nem onde procurar —, o caminho é parar o código. Na aba Sources, abra o arquivo, clique no número da linha e um marcador azul aparece. Quando a execução chegar ali, o navegador congela.

Com o código parado, três painéis importam. Scope mostra as variáveis do trecho, com o valor de agora. Watch deixa você escrever expressões para acompanhar. E os botões de passo controlam a execução: "passo a passo" entra na função chamada, "por cima" executa a linha inteira, "continuar" segue até o próximo breakpoint.

Para não parar em toda repetição de uma lista, use o breakpoint condicional: clique com o botão direito no número da linha e escreva a condição, como id === 3. O navegador só para quando aquela expressão for verdadeira.

Existe também a forma manual, dentro do código: a linha debugger; faz o navegador parar ali como se fosse um breakpoint. É útil quando o trecho roda uma vez só, no início, e você não quer caçar o arquivo na lista. Só não deixe um debugger esquecido: em produção ele para a página de quem tiver o DevTools aberto.

6. Elements: o HTML que o React gerou

A aba Elements mostra o DOM de verdade, não o JSX. Isso é ouro em duas situações. A primeira: conferir se o elemento que você escreveu existe e com quais atributos — o className virou class? o htmlFor virou for? a lista tem os itens que você esperava?

A segunda: descobrir por que um estilo não pega. O painel de estilos mostra as regras aplicadas, na ordem, com as riscadas indicando o que perdeu. Muitas vezes a classe está certa no JSX e a regra está sendo vencida por outra mais específica, ou por um estilo inline. Isso não é problema do React; é do CSS.

Dois truques que economizam tempo: o botão de selecionar elemento (o quadradinho com uma seta) aponta para qualquer parte da página e leva ao nó correspondente; e o seletor de estado :hov força o :hover, :focus ou :active, para você inspecionar um estilo que só aparece com o mouse em cima.

Um cuidado: o React redesenha o DOM quando o estado muda. Se você editar um texto no Elements, a edição vale até o próximo desenho — ela não volta para o estado. Ver a página mudar não quer dizer que o dado mudou.

7. Network: quem pediu, o que voltou e em quanto tempo

Quando a tela depende de dados, a pergunta "o dado chegou?" tem uma resposta objetiva na aba Network. Recarregue com ela aberta: cada pedido aparece com método, caminho, status, tamanho e tempo. Clique num pedido e você vê os cabeçalhos, o corpo da resposta e, quando é JSON, uma aba com a árvore.

O que olhar primeiro: o status. 200 é sucesso; 404 é caminho errado; 500 é o servidor quebrando; CORS aparece como erro de rede, não como status. Depois, o tipo: JSON chegando como text/html costuma ser página de erro servida no lugar do dado. Por fim, o corpo: muitas vezes a resposta é {"erro":"não autorizado"} e o componente tenta ler uma lista que não existe.

GET https://loja.test/api/pedidos 500 (Internal Server Error)  1.2 s
GET https://loja.test/api/pedidos 200  312 ms  {"pedidos": []}

A segunda linha é uma armadilha comum: status 200, corpo vazio. O código não pode assumir que há itens; a tela precisa saber mostrar "nenhum pedido". A aula de estados vazios entra nesse caso.

Marque "Disable cache" enquanto investiga. Sem isso, o navegador pode responder do cache e você jura que o servidor está devolvendo o valor antigo — quando o valor antigo está guardado no seu computador.

8. React DevTools: o estado à vista

A aba do React mostra a árvore de componentes, não de elementos. Cada nó é um componente seu, com as props que recebeu e os hooks que declarou. Selecionar um componente na tela (pelo botão de inspeção) seleciona o nó correspondente na árvore — e é assim que se descobre "de onde veio esta prop".

No painel da direita, os useState aparecem na ordem em que foram declarados, com o valor atual e o nome da variável quando o build mantém os nomes. Você também vê os efeitos, com as dependências da última execução. É a resposta para "o estado mudou?" sem nenhum console.log.

Um sintoma clássico que essa aba resolve em dez segundos: a tela mostra o valor antigo, mas o estado está novo. Aí o problema não é o estado, é o lugar que lê — outra variável, um valor calculado antes da atualização, uma prop que não foi passada adiante. Ver os dois lados separados evita consertar o lado errado.

A aba tem ainda um Profiler: você grava uma interação e vê quais componentes desenharam, em que ordem e por quanto tempo. É a ferramenta da aula de medindo performance; para o bug do dia a dia, a árvore de componentes já resolve.

O caso abaixo é o mais chato de todos, porque não há erro: o crachá aparece sem nome. O log das props, que já está no código, mostra o que o componente recebeu de verdade — e a resposta está na chave.

O crachá mostra "Olá, " e nenhum erro no console. Repare no log das props: o componente lê nome, mas recebe outra chave. Conserte para aparecer "Olá, Ana".

function Cracha(props) {
  console.log("props recebidas:", props);
  return <p>Olá, {props.nome}</p>;
}

function App() {
  return (
    <div>
      <Cracha name="Ana" />
      <p>Pedido de hoje</p>
    </div>
  );
}
<div>
  <p>Olá,</p>
  <p>Pedido de hoje</p>
</div>
console: props recebidas: {"name":"Ana"}

function Cracha(props) {
  console.log("props recebidas:", props);
  return <p>Olá, {props.nome}</p>;
}

function App() {
  return (
    <div>
      <Cracha nome="Ana" />
      <p>Pedido de hoje</p>
    </div>
  );
}

Com o log na mão, a comparação fica trivial: o componente pede nome, o pai manda name. Sem o log, o mesmo raciocínio levaria muito mais tempo, porque a tela não acusa nada — e o silêncio é o pior sintoma para depurar.

9. O método na prática

Ferramenta sem método vira clique aleatório. O método tem três passos e cabe num guardanapo.

1) Reduzir. Apague metade do componente e rode. Se o bug continua, o culpado está na metade que ficou; se sumiu, está na que saiu. Repita até sobrar uma linha. É mais rápido do que ler quarenta linhas, porque cada rodada elimina metade das hipóteses.

2) Isolar. Se o problema aparece só com certos dados, use só esses dados: um item na lista, um pedido com aquele preço, o nome com acento. Se aparece só numa tela, leve o componente para uma tela vazia. Bug que some ao isolar é bug de contexto — e o contexto também é uma pista.

3) Comparar. Tenha sempre uma versão que funciona: a versão publicada anterior, outro componente parecido, o exemplo do guia. Compare linha por linha o que difere. "Funciona no meu e não no celular" costuma ser largura da tela; "funciona em dev e quebra em produção" costuma ser build ou variável de ambiente.

Cenário 1: o clique que não chega no botão

O botão "Pedir" não respondia e o console estava limpo. O handler existia, a função estava certa. No Elements, a Ana viu um aviso flutuante do carrinho por cima do botão, com position: fixed e a altura de uma faixa inteira. O clique caía no aviso. A pista não estava no JavaScript: estava na geometria da página.

Cenário 2: o estado novo e a tela velha

No React DevTools, o estado pedidos já tinha três itens. A tela mostrava dois. O JSX usava uma variável lista calculada no começo do componente, antes da atualização. O estado estava certo; a leitura, velha. Ver os dois lados na mesma tela evita a hora gasta consertando o setter.

Cenário 3: funciona no notebook e não no celular

No desktop, tudo no lugar. No celular, a tabela de preços empurrava a página para o lado e escondia o botão. Com o modo de dispositivo do DevTools em 375 px, o problema apareceu na hora: largura fixa em pixels num container sem rolagem. O bug não era de React, e o DevTools mostrou isso antes do código.

Um último recurso, quando nada dá certo: escrever a dúvida em uma frase. "O total está NaN depois de remover um item" já diz onde olhar, e muitas vezes o culpado aparece na própria frase. Depurar é formular a pergunta certa e usar a ferramenta que a responde.

11. Resumo

Depurar no navegador é escolher a ferramenta pela pergunta. Console para mensagens e valores; Elements para o HTML e o estilo que venceram; Sources para parar o código e ver as variáveis de verdade; Network para o que veio da rede; Application para o que ficou guardado. Com React, a extensão acrescenta a árvore de componentes com props, estado e hooks.

Duas habilidades fazem a diferença mais que qualquer truque. A primeira é ler a mensagem inteira: tipo do erro, o que era nulo, o arquivo e a linha. A segunda é logar direito — etiqueta e valor separados por vírgula —, porque [object Object] não é informação. E lembre que aviso não é enfeite: um console limpo é parte do trabalho pronto.

Quando nada disso resolve, o método: reduzir pela metade até sobrar uma linha, isolar o contexto em que o bug aparece e comparar com a versão que funciona. É mais lento que o chute na primeira tentativa e infinitamente mais rápido na segunda. Na aula seguinte, a Ana começa a construir as rotas do site — e o que ela aprendeu aqui vai ser usado a cada passo.

Para lembrar

  • F12 abre o DevTools; escolha a aba pela pergunta, não pelo hábito.
  • Console limpo é requisito: aviso ignorado vira bug depois.
  • console.log("cliente:", cliente) — etiqueta e vírgula, nunca +.
  • Objeto logado é lido no clique: para congelar, copie ou use JSON.stringify.
  • "Cannot read properties of null" é valor que ainda não chegou.
  • App.jsx:7:22 é arquivo, linha e coluna — clique e vá direto.
  • Breakpoint no Sources congela e mostra as variáveis; o condicional filtra a repetição.
  • debugger; faz o mesmo dentro do código; não deixe esquecido.
  • O estado pode estar certo e a leitura errada: veja os dois lados no React DevTools.
  • Método: reduzir, isolar, comparar — e escrever a dúvida em uma frase.
