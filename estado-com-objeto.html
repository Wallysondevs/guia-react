Estado com Objeto

A ficha do cliente da Ana tem quatro campos: nome, telefone, rua e número. Ela guardou cada um no seu useState — e agora, para carregar os dados de um cliente que já comprou antes, precisa chamar quatro setters e lembrar de todos. Esqueceu um, e a rua do cliente antigo apareceu no pedido novo. Nesta aula ela junta os quatro num objeto, aprende a trocar um campo sem perder os outros e descobre por que mexer no objeto direto não redesenha a tela.

Você vai aprender
  • Quando vale guardar um objeto num estado em vez de vários valores soltos.
  • Como ler cliente.nome dentro do JSX.
  • Por que o setter troca o objeto inteiro e o que acontece com os campos esquecidos.
  • O spread: { ...cliente, nome: valor }, e por que a ordem importa.
  • Por que alterar o objeto direto não atualiza a tela.
  • Como atualizar um campo dentro de um objeto aninhado.
  • Um único handler para vários campos, com name e chave calculada.

1. A cena: a ficha do cliente em quatro caixinhas

Depois de aprender a ter vários estados, a Ana montou a ficha do cliente com quatro declarações: nome, telefone, rua e numero. Cada campo do formulário conversa com o seu estado, e digitar funciona. O problema apareceu numa funcionalidade boba: preencher o formulário com os dados de um cliente que já comprou.

Para isso ela escreveu quatro chamadas: setNome(clienteAntigo.nome), setTelefone(...), setRua(...), setNumero(...). Um mês depois, acrescentou o bairro ao formulário e esqueceu de incluir o setBairro na função de preenchimento. Resultado: pedido novo com o bairro do pedido anterior. Esse tipo de bug não dá erro, não aparece no console e é difícil de reproduzir — depende da ordem em que as pessoas clicaram.

O problema não é o número de setters; é que os quatro campos são um dado só. Eles nunca mudam separadamente: quando a Ana troca de cliente, troca o nome, o telefone, a rua e o número juntos. Guardar em quatro caixinhas separa o que a vida mantém unido — e aí cabe a você lembrar de mexer nas quatro.

Um objeto no estado resolve isso: uma caixinha, quatro campos dentro, uma atualização. Quem lê o código vê cliente.rua e sabe de quem é aquela rua. Quem preenche o formulário entrega um objeto inteiro, e não quatro pedaços que podem se desencontrar.

2. O objeto como valor de um estado

Nada muda na forma do useState: o valor inicial é um objeto, e o par continua sendo valor e setter. O que muda é a leitura, que ganha um ponto para chegar ao campo.

function App() {
  const [cliente, setCliente] = useState({
    nome: "Ana",
    telefone: "9999-0000",
    rua: "das Flores",
    numero: "10"
  });

  return (
    <div>
      <h2>{cliente.nome}</h2>
      <p>Telefone: {cliente.telefone}</p>
      <p>{cliente.rua}, {cliente.numero}</p>
    </div>
  );
}

O estado agora guarda um valor — um objeto com quatro propriedades. Essa distinção parece filosófica e tem consequência prática: para o React, cliente é uma coisa só. Quando você chama o setter, ele não está trocando a propriedade nome; está trocando o valor inteiro do estado. O que existir dentro do objeto novo é o que vai aparecer na tela.

Por isso o setter não "mistura" o objeto novo com o antigo. Essa é a pegadinha central da aula, e é onde quase todo mundo tropeça na primeira vez.

3. O setter troca o objeto inteiro

Veja o que acontece quando a Ana atualiza só o campo que mudou:

setCliente({ nome: e.target.value });

Parece razoável: "o nome mudou, mando o nome novo". Mas o estado deixa de ser { nome, telefone, rua, numero } e passa a ser { nome }. As outras três propriedades somem — não viram vazio, viram undefined. Na tela, o telefone desaparece e o campo correspondente começa a se comportar de forma estranha, porque o React recebe value={undefined} e passa a tratar o campo como não controlado.

Cada onChange está mandando um objeto com um campo só, e o outro se perde. Conserte os dois para que o telefone sobreviva à mudança do nome, e vice-versa. A missão digita Ana no nome e 9999-0000 no telefone, e confere os dois campos.

function App() {
  const [cliente, setCliente] = useState({ nome: "", telefone: "" });

  return (
    <div>
      <label htmlFor="nome">Cliente</label>
      <input
        id="nome"
        value={cliente.nome}
        onChange={(e) => setCliente({ nome: e.target.value })}
      />

      <label htmlFor="tel">Telefone</label>
      <input
        id="tel"
        value={cliente.telefone}
        onChange={(e) => setCliente({ telefone: e.target.value })}
      />

      <p>{cliente.nome || "sem nome"} — {cliente.telefone || "sem telefone"}</p>
    </div>
  );
}

O conserto é aquele ... antes do nome. Ele copia para o objeto novo todas as propriedades do objeto antigo; depois, a propriedade escrita na sequência substitui a que veio na cópia. É a receita para "trocar um campo sem perder os outros".

Repare numa malandragem do bug: o campo que perdeu o valor continua mostrando o que você digitou, e o parágrafo logo abaixo já não sabe do nome. Isso acontece porque value={undefined} faz o React tratar o campo como não controlado — ele volta a guardar o próprio texto, e a ilusão fica completa. O React avisa no console ("changing a controlled input to be uncontrolled"), mas o sintoma visível é uma tela que parece certa. Por isso a missão acima confere o parágrafo, e não o campo: é ali que o estado aparece sem disfarce.

4. O spread: copiar e sobrescrever

Os três pontinhos se chamam spread, espalhar. Dentro de um objeto, eles significam "traga para cá todas as propriedades deste outro objeto". O JavaScript monta um objeto novo, com as mesmas propriedades do antigo, e a partir daí você pode acrescentar ou substituir campos à vontade.

const cliente = { nome: "Ana", telefone: "9999-0000" };

const novo = { ...cliente, nome: "Maria" };
console.log("com spread:", JSON.stringify(novo));
console.log("sem spread:", JSON.stringify({ nome: "Maria" }));
com spread: {"nome":"Maria","telefone":"9999-0000"}
sem spread: {"nome":"Maria"}

Duas coisas importantes nesse exemplo. A primeira: o objeto cliente original continua intacto — o spread cria outro objeto, não altera o que existia. A segunda: a ordem importa. As propriedades são aplicadas da esquerda para a direita, então o que vier depois ganha. Se você escrever { nome: "Maria", ...cliente }, o spread traz o nome antigo de volta e o resultado é "Ana". Nome novo sempre depois do spread.

O spread é raso: ele copia as propriedades de primeiro nível. Se um dos campos do objeto for outro objeto, a cópia guarda a mesma referência para o objeto interno — e isso é o assunto da seção 6, porque é a causa de um bug clássico com estados aninhados.

spread
Os três pontinhos antes de um objeto (...cliente) dentro de outro objeto. Significam "traga as propriedades daquele objeto para cá". Criam um objeto novo, não alteram o original.
cópia rasa
Uma cópia que leva as propriedades do primeiro nível. Um objeto dentro do objeto não é copiado: as duas versões apontam para o mesmo interno.
referência
O endereço do objeto na memória. Duas variáveis podem apontar para o mesmo objeto; é isso que o React compara quando você chama o setter.
mutação
Alterar o objeto que já existe, como em cliente.nome = "Maria". O conteúdo muda, a referência não — e o React, que compara referências, não redesenha.
chave calculada
Uma propriedade escrita com colchetes: [campo]: valor. O nome da propriedade vem do valor da variável, não do texto digitado no código.

5. A mutação que não redesenha a tela

Existe um jeito de atualizar o objeto que parece funcionar e não funciona. É quando você altera o campo direto e depois manda o mesmo objeto de volta:

function trocarParaMaria() {
  cliente.nome = "Maria";
  setCliente(cliente);
}

A linha cliente.nome = "Maria" altera o objeto que está no estado — isso se chama mutação. O valor na tela até que existe, mas o React não redesenha: quando você entrega ao setter o mesmo objeto que ele já tinha, o React compara as referências, vê que é o mesmo e conclui que nada mudou. Economia de trabalho — e uma tela que fica parada.

O botão altera o nome dentro do objeto e devolve o mesmo objeto ao setter, então a tela não muda. Faça a troca com um objeto novo. A missão clica no botão e confere que a tela mostra "Cliente: Maria".

function App() {
  const [cliente, setCliente] = useState({ nome: "Ana", telefone: "9999-0000" });

  return (
    <div>
      <button
        onClick={() => {
          cliente.nome = "Maria";
          setCliente(cliente);
        }}
      >
        Trocar para Maria
      </button>
      <p>Cliente: {cliente.nome}</p>
    </div>
  );
}
<div>
  <button>Trocar para Maria</button>
  <p>Cliente: Ana</p>

function App() {
  const [cliente, setCliente] = useState({ nome: "Ana", telefone: "9999-0000" });

  return (
    <div>
      <button onClick={() => setCliente({ ...cliente, nome: "Maria" })}>
        Trocar para Maria
      </button>
      <p>Cliente: {cliente.nome}</p>
    </div>
  );
}

A aula de props com objetos já tinha avisado que o objeto passado adiante é o mesmo objeto, e não uma cópia. Com estado, esse detalhe deixa de ser curiosidade e vira bug: mudar o conteúdo não muda a referência, e é a referência que o React compara.

A confusão é justificável: dentro do handler, cliente.nome já vale "Maria" — a mutação aconteceu de verdade. O que não aconteceu foi o render. O React não observa o conteúdo dos objetos; ele compara a referência que você entregou com a que tinha. Mesma referência, nenhum trabalho. O painel da caixa, que mostra o que foi desenhado na tela, continua com "Ana":

no console: nome depois do clique: Maria
na tela:    Cliente: Ana

Daí a regra que vale para objetos, arrays e qualquer valor composto: nunca altere o valor que já está no estado. Construa um valor novo — com spread, com map, com filter — e entregue esse. O estado é uma foto; para mudar a foto, você tira outra, não pinta em cima da antiga.

6. Objeto dentro de objeto

Quando um campo do objeto é outro objeto — o endereço dentro do pedido, por exemplo —, o spread de fora não basta. Copiar o pedido copia a referência do endereço: os dois pedidos passam a apontar para o mesmo endereço, e mexer num mexe no outro. A receita é um spread para cada nível que você vai alterar.

O campo da rua está dentro de pedido.entrega, e o onChange monta um endereço novo só com a rua — o número se perde. Copie também o endereço antigo. A missão digita Rua Nova e confere "Entrega: Rua Nova, 10".

function App() {
  const [pedido, setPedido] = useState({
    cliente: "Ana",
    entrega: { rua: "das Flores", numero: "10" }
  });

  return (
    <div>
      <input
        value={pedido.entrega.rua}
        onChange={(e) =>
          setPedido({ ...pedido, entrega: { rua: e.target.value } })
        }
      />
      <p>Entrega: {pedido.entrega.rua + ", " + pedido.entrega.numero}</p>
    </div>
  );
}
<div>

Leia de dentro para fora: { ...pedido.entrega, rua: ... } cria um endereço novo, com a rua trocada e o número preservado; { ...pedido, entrega: ... } cria um pedido novo, com o endereço novo dentro. Cada nível ganha o seu spread. Se o objeto tivesse três níveis, seriam três.

Isso pode parecer exagero para um formulário de dois campos. O custo compensa quando o objeto é compartilhado: dois componentes que recebem o mesmo objeto, ou uma lista de pedidos em que cada item aponta para um endereço. Com cópia por nível, cada atualização produz um valor independente; com mutação, um altera o outro e o bug aparece num lugar que você nem estava editando.

7. Um handler para vários campos

Com objeto no estado, os campos ficam tão parecidos que dá vontade de escrever uma função só. Dá: use o atributo name do input para dizer qual propriedade mudar, e a chave calculada do JavaScript para escrever nela.

function App() {
  const [cliente, setCliente] = useState({ nome: "", telefone: "" });

  function mudar(e) {
    const campo = e.target.name;
    setCliente({ ...cliente, [campo]: e.target.value });
  }

  return (
    <div>
      <input name="nome" value={cliente.nome} onChange={mudar} />
      <input name="telefone" value={cliente.telefone} onChange={mudar} />
      <p>{cliente.nome} — {cliente.telefone}</p>
    </div>
  );
}

[campo] entre colchetes significa "use o valor desta variável como nome da propriedade". Se campo vale "telefone", o objeto ganha telefone. Não é magia do React: é JavaScript puro, o mesmo recurso que permite obj[chave] fora do JSX.

Vale a honestidade: esse atalho só compensa a partir de três ou quatro campos. Com dois, escrever cada onChange é mais claro e menos sujeito a erro de digitação no name. E há um cuidado: se o name não bater com a propriedade do estado, o objeto ganha um campo a mais e a tela não mostra nada — erro silencioso, daqueles que tomam meia hora.

8. Lendo o objeto na tela

Objeto não se desenha. Se você escrever {cliente} dentro do JSX, o React reclama com a mensagem Objects are not valid as a React child — "objetos não são filhos válidos do React". Faz sentido: o React sabe desenhar texto, números e elementos; um objeto com quatro campos não é nada disso. Você escolhe o que mostrar, campo por campo.

function App() {
  const [cliente, setCliente] = useState({ nome: "Ana", telefone: "" });

  return (
    <div>
      <h2>{cliente.nome}</h2>
      <p>{cliente.telefone || "telefone não informado"}</p>
      <p>{cliente.nome.length} letras no nome</p>
    </div>
  );
}

Como cada campo é um valor comum, tudo o que você já sabe continua valendo: dá para testar se está vazio, contar letras, colocar em maiúsculas, mostrar uma mensagem alternativa. O objeto é só a embalagem.

Ao depurar, lembre que o painel da caixa mostra o que o console.log escreveu. O motor converte objetos em JSON, então console.log(cliente) aparece como console: {"nome":"Ana","telefone":""} — legível, com os campos na ordem em que foram criados. Se você juntar o objeto numa string com +, o resultado é [object Object] e não ajuda em nada: passe o objeto como argumento separado ou use JSON.stringify(cliente).

9. Cenários do dia a dia

Cenário 1: a rua que foi parar no lugar errado

Ao atualizar o endereço, a Ana escreveu setPedido({ ...pedido, rua: e.target.value }). O pedido ganhou uma propriedade rua no primeiro nível, enquanto a tela lia pedido.entrega.rua — que continuou com o valor antigo. O spread copiou o nível de fora, mas o campo alterado estava um nível abaixo. Quando o caminho da leitura e o caminho da escrita não batem, a tela não muda e nada avisa.

Cenário 2: a cópia que conserta por acidente

Para "avisar o React", ela mutava o objeto e depois chamava setCliente({ ...cliente }) — uma cópia sem nenhuma alteração. Funcionava porque a cópia é uma referência nova, então o render acontecia. O hábito é ruim: se o objeto tiver um campo aninhado, a cópia rasa compartilha o interno, e qualquer alteração nele contamina o estado anterior. Copie sempre trocando o campo, num passo só.

Cenário 3: o console que só mostra [object Object]

Ela escreveu console.log("cliente: " + cliente) e viu cliente: [object Object]. A concatenação transforma qualquer objeto nessa string inútil antes de chegar ao console. As saídas que funcionam são console.log("cliente:", cliente), com o objeto como argumento separado, ou console.log(JSON.stringify(cliente)). No painel das caixas, o objeto aparece em JSON nos dois casos.

10. Fixando o que ficou

1. Como se atualiza só o nome dentro de um estado de objeto?

2. Por que cliente.nome = "Maria"; setCliente(cliente) não muda a tela?

3. O que { ...cliente, nome: "Maria" } produz?

Exercício: copiar o nível certo

Complete as duas atualizações: a do nome do cliente e a da rua dentro do endereço do pedido. O que falta em cada chave é a cópia do nível de cima.

setCliente({ , nome: e.target.value }); setPedido({ ...pedido, entrega: { , rua: e.target.value } });

Dica: os três pontinhos antes do nome do objeto copiam as propriedades dele. O nível de dentro precisa dos seus próprios pontinhos, apontando para o objeto de dentro.

11. Resumo

Um objeto no estado faz sentido quando os campos são um dado só — a ficha do cliente, o endereço de entrega, a configuração de um pedido. A declaração continua sendo useState({ ... }), a leitura ganha um ponto (cliente.nome) e a atualização passa a ser sempre "objeto novo com os campos antigos mais o campo alterado": setCliente({ ...cliente, nome: valor }).

Duas regras sustentam o resto. A primeira: o setter troca o valor inteiro, não mistura; se você mandar um objeto com um campo só, os outros viram undefined. A segunda: o React compara referências, então mutar o objeto e devolvê-lo não redesenha nada — e mutar o objeto do estado é sempre erro, mesmo quando a tela parece funcionar. Objetos aninhados pedem um spread por nível, de dentro para fora.

Para ler, escolha o campo: objeto não é filho válido do React, e {cliente} vira erro. Para depurar, console.log("cliente:", cliente) mostra o objeto em JSON no painel. E o mesmo raciocínio vale para listas: em vez de alterar a lista existente, construa uma nova — que é exatamente o assunto da próxima aula.

Para lembrar

  • Objeto no estado quando os campos sempre mudam juntos.
  • Ler é cliente.nome; desenhar é campo por campo, nunca o objeto inteiro.
  • Atualizar é setCliente({ ...cliente, nome: valor }): copiar e sobrescrever.
  • A ordem importa: o campo alterado vem depois do spread.
  • O setter troca o valor inteiro; campos esquecidos viram undefined.
  • Nunca mute o objeto do estado: cliente.nome = ... não redesenha.
  • Mesma referência, nenhum render: o React compara com Object.is.
  • Objeto aninhado pede um spread por nível.
  • Vários campos iguais podem dividir um handler com name e [campo].
  • console.log("cliente:", cliente) mostra JSON; com + vira [object Object].
