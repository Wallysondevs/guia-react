Build de Produção

O npm run build da vitrine da Ana terminou com uma pasta dist de quatro arquivos — e ela esperava trinta e quatro. O index.html ficou com 0,46 kB, o JavaScript virou um nome estranho com letras e números, e o site funcionou. Nesta aula ela abre a pasta, entende de onde veio cada arquivo, por que o pacote é menor que a soma das partes e o que muda no React quando o código vai para produção.

Você vai aprender
  • O que o vite build faz, etapa por etapa.
  • O que sai em dist/ e por que os nomes ganham letras e números.
  • Tree-shaking e minificação: por que o pacote final é menor que a soma dos arquivos.
  • Como o import() dinâmico divide o site em chunks.
  • O que muda no React entre desenvolvimento e produção.
  • Como conferir o resultado com preview e com sourcemaps.

1. A cena: trinta e quatro arquivos viram quatro

Durante o desenvolvimento, o navegador da Ana pede dezenas de arquivos: main.jsx, App.jsx, cada componente, cada CSS. O Vite transforma cada um na hora e entrega. É rápido porque não há empacotamento — e é ótimo para trabalhar, mas seria péssimo para o visitante do site, que pagaria dezenas de idas ao servidor por uma página.

Na publicação, a conta é outra. O visitante quer a página em um ou dois segundos, no celular, com internet média. O npm run build faz essa tradução: pega o grafo inteiro, descarta o que não é usado, junta o que faz sentido junto, encolhe o texto e escreve o resultado em dist. É o mesmo site, embalado para viagem.

Entender esse processo resolve três tipos de dúvida que aparecem sempre: por que o site que funcionava no dev quebrou no build, por que o nome do arquivo mudou e como fazer o pacote parar de crescer. As três respostas estão nas etapas que você vai ver a seguir.

2. O que o vite build faz

O comando chama o Rollup, o empacotador que o Vite usa em produção. Ele começa pelo index.html, segue cada import até o fim e monta um mapa de tudo o que a página realmente usa. Depois aplica quatro transformações, nesta ordem de ideia: remove o que não é alcançável, junta os módulos em poucos arquivos, minifica o texto e renomeia com um hash do conteúdo.

$ npm run build

vite v7.1.0 building for production...
✓ 34 modules transformed.
dist/index.html                 0.46 kB │ gzip:  0.30 kB
dist/assets/index-a1b2c3d4.css  8.21 kB │ gzip:  2.14 kB
dist/assets/index-9f8e7d6c.js  142.31 kB │ gzip: 45.62 kB
✓ built in 1.18s

A saída conta a história. "34 modules transformed" é o número de arquivos que entraram no grafo. Depois vêm os arquivos gerados, com o tamanho bruto e o tamanho comprimido com gzip — a coluna que importa para quem visita, porque é assim que o servidor costuma enviar. E, no fim, o tempo total. Um projeto pequeno fica em torno de 1 segundo; um grande, em dezenas.

Repare que só existem três arquivos em dist: o HTML, um CSS e um JavaScript. O HTML é o mesmo index.html do projeto, com a diferença de que a tag script agora aponta para o arquivo com hash. O CSS de todos os componentes foi junto num só. E o JavaScript é o grafo empacotado.

O tree-shaking é o mais subestimado. Ele funciona porque os módulos ES são estáticos: o empacotador sabe, antes de executar, quais importações existem. Se você importa uma função de uma biblioteca de 200, e o resto não é usado em lugar nenhum, o resto sai do pacote. Isso vale para o seu código também: componente que ninguém importa não entra no build.

3. O hash no nome e o cache

O nome index-9f8e7d6c.js não é enfeite. O pedaço depois do hífen é calculado a partir do conteúdo do arquivo: mudou uma vírgula, muda o nome. A razão é o cache do navegador. Um arquivo com nome fixo pode ficar guardado por meses; quando você publica uma versão nova com o mesmo nome, o visitante continua vendo a antiga. Com o hash, o navegador vê um nome novo, baixa o novo e mantém o antigo em cache para quem ainda não atualizou.

O mesmo raciocínio vale para as imagens em src/assets, que ganham hash, e não vale para public, que mantém o nome. É por isso que a imagem que muda com frequência deve ficar em src/assets: ela ganha um nome novo quando muda, e o cache não atrapalha.

A função hash devolve sempre o mesmo texto, então os dois casos parecem iguais. Faça ela calcular um número a partir do conteúdo: o mesmo texto precisa gerar o mesmo nome, e textos diferentes precisam gerar nomes diferentes.

function hash(texto) {
  return "abc123";
}

function hash(texto) {
  let h = 0;

  for (let i = 0; i < texto.length; i++) {
    h = (h * 31 + texto.charCodeAt(i)) % 100000;
  }

  return h.toString(36);
}

O algoritmo é uma versão de brinquedo de um hash de verdade: percorre os caracteres, combina cada um com o acumulado e corta o número. O importante é a propriedade, não o algoritmo: mesma entrada, mesma saída; entrada diferente, saída diferente. É isso que o build usa para decidir o nome do arquivo.

Um detalhe de leitura: o painel mostra os dois nomes lado a lado justamente para você comparar. Na segunda linha, o texto tem um sufixo e o nome muda — é o que faria o navegador baixar de novo a versão nova.

4. Tree-shaking e minificação na conta

A diferença entre "soma dos arquivos" e "tamanho do pacote" assusta. Um projeto com 34 arquivos totalizando 750 kB pode gerar um pacote de 88 kB comprimido. Não é mágica: é a soma de três efeitos que se multiplicam — o que ninguém importa sai, o que sobra é minificado, e o servidor envia comprimido.

A conta de produção está devolvendo o mesmo que a de desenvolvimento. Faça totalProd considerar só os módulos usados e aplicar a redução para 40% do tamanho bruto — com os dados atuais, o resultado precisa ser 88 kB.

const modulos = [
  { nome: "react", kb: 140, usado: true },
  { nome: "date-fns", kb: 60, usado: true },
  { nome: "lodash", kb: 530, usado: false },
  { nome: "estilos", kb: 20, usado: true }
];

function totalDev() {
  return modulos.reduce((soma, m) => soma + m.kb, 0) + " kB";
}

function totalProd() {
  return totalDev();
}

function App() {
  return (
    <div>
      <p>desenvolvimento: {totalDev()}</p>
      <p>produção: {totalProd()}</p>
    </div>
  );
}

function totalProd() {
  const usados = modulos.filter((m) => m.usado);
  const bruto = usados.reduce((soma, m) => soma + m.kb, 0);

  return Math.round(bruto * 0.4) + " kB";
}

      <p>produção: {totalProd()}</p>
    </div>
  );
}

A conta tem duas etapas: filtrar o que é usado e aplicar a redução. O lodash de 530 kB sozinho explica a maior parte da diferença — é o exemplo clássico de biblioteca enorme importada inteira para usar uma função. O 0.4 representa a minificação somada à compressão; na vida real, cada arquivo encolhe um pouco diferente, e é aí que entra a análise do build.

Vale reparar que totalDev continua somando tudo. É o retrato do desenvolvimento: o servidor não se importa com tamanho, serve arquivo por arquivo. A comparação lado a lado é justamente o que dá a noção de quanto o build economizou.

5. Chunks: carregando o que é preciso, quando é preciso

Empacotar tudo num arquivo só tem um limite: a primeira tela passa a esperar por código que talvez nunca seja usado. A solução é dividir em chunks — pedaços separados, baixados sob demanda. A ferramenta para isso é o import() dinâmico, que o Vite transforma num chunk próprio.

import { useState } from "react";

export function Encomendas() {
  const [relatorio, setRelatorio] = useState(null);

  async function abrirRelatorio() {
    const modulo = await import("../lib/relatorio.js");
    setRelatorio(modulo.montarRelatorio());
  }

  return (
    <div>
      <button onClick={abrirRelatorio}>Ver relatório</button>
      {relatorio && <pre>{relatorio}</pre>}
    </div>
  );
}

O relatorio.js sai do pacote principal e vira um arquivo à parte. Quem abre a página não baixa esse código; quem clica no botão baixa, com uma pequena espera. Em troca, a primeira tela fica menor — que é o que decide se o visitante espera ou vai embora.

A tela inicial está somando todos os módulos, inclusive os que só são carregados depois. Faça a conta do primeiro carregamento somar apenas os módulos com dinamico: false — ela precisa mostrar 200 kB, e o carregamento posterior, 130 kB.

const modulos = [
  { nome: "react", kb: 140, dinamico: false },
  { nome: "date-fns", kb: 60, dinamico: false },
  { nome: "relatorio", kb: 90, dinamico: true },
  { nome: "exportar", kb: 40, dinamico: true }
];

function tamanho(lista) {
  return lista.reduce((soma, m) => soma + m.kb, 0) + " kB";
}

function App() {
  const inicial = tamanho(modulos);
  const depois = tamanho(modulos.filter((m) => m.dinamico));

  return (
    <div>
      <p>primeiro carregamento: {inicial}</p>
      <p>ao abrir o relatório: {depois}</p>
    </div>
  );
}

O mesmo filtro de antes, agora com a condição invertida. A diferença é conceitual: aqui não se trata de tirar o que não é usado, e sim de adiar o que não é necessário agora. Os 90 kB do relatório continuam existindo — só não entram na primeira conta. Quando o botão é clicado, o navegador baixa o chunk e o código roda.

A regra prática: divida o que é raro ou pesado (relatórios, editor de texto, gráficos, telas secundárias) e mantenha no principal o que toda página precisa (React, layout, tema). Dividir demais cria dezenas de requisições pequenas e piora o tempo total; dividir de menos faz o visitante baixar o site inteiro para ver a capa.

6. O que muda no React em produção

Existe uma diferença que confunde muita gente: o comportamento do React não é idêntico nos dois modos. Em desenvolvimento, ele roda com avisos, verificações extras e o StrictMode chamando efeitos duas vezes de propósito. Em produção, tudo isso sai para o pacote ficar menor e o código rodar mais rápido.

DesenvolvimentoProdução
avisos no consolesim: key, props inválidas, efeitosnão: foram removidos
StrictModeefeitos rodam duas vezes de propósitoroda uma vez
mensagens de errotexto completo e dicacódigo minificado com link
tamanhomaior, com código de diagnósticomenor

Isso explica os dois sustos mais comuns. O primeiro: um aviso que aparecia no dev desaparece no build — ele não foi corrigido, só não é impresso. O segundo: um erro que no dev dizia "Target container is not a DOM element" vira Minified React error #299. O número não é um mistério: o endereço que vem junto (react.dev/errors/299) leva à explicação completa.

O StrictMode merece uma nota: ele só existe em desenvolvimento e serve para revelar efeitos que não sabem lidar com montar, desmontar e montar de novo. Se um efeito faz uma chamada de rede sem limpar, o dev mostra duas e a produção uma — e o bug aparece só em produção, num caso de navegação. É por isso que a recomendação é manter o StrictMode ligado e escrever efeitos que suportem rodar duas vezes.

7. Conferindo o build

O build gera arquivos, não uma página pronta para abrir com dois cliques. Para ver o resultado, existe o npm run preview, que sobe um servidor local em cima de dist:

$ npm run preview

  VITE v7.1.0  ready in 205 ms

  ➜  Local:   http://localhost:4173/
  ➜  press h + enter to show help

A porta padrão é 4173, diferente da 5173 do desenvolvimento, justamente para os dois poderem rodar juntos. Abra, navegue, confira imagens e rotas. Se algo não aparecer, o problema está no build — e é melhor descobrir ali do que depois de publicar.

Quando o erro só acontece em produção, o sourcemap ajuda. Ele é um arquivo que liga o código minificado ao original, permitindo que o navegador mostre a linha real no depurador. Por padrão, o Vite não gera sourcemap no build; para gerar, acrescente build.sourcemap: true na configuração. O arquivo resultante é grande e não deve ser servido ao público em produção — o lugar dele é o serviço de monitoramento de erros.

E para saber o que está pesando, existem duas abordagens. A primeira é olhar a saída do build: os arquivos aparecem em ordem de tamanho, e o maior costuma ser o culpado. A segunda é usar um analisador visual, como o rollup-plugin-visualizer, que gera um mapa do pacote mostrando quanto cada biblioteca ocupa. Em projeto pequeno, a saída do terminal basta.

8. Por que o build quebra e o dev não

Três diferenças entre os dois ambientes explicam quase todos os "funcionava no dev". A primeira é que o build resolve todos os imports de uma vez: um caminho com maiúscula errada, que o Windows aceitava, falha no Linux do build. A segunda é que o build exige que todo import exista — no dev, um arquivo ausente pode passar despercebido até ser aberto.

A terceira é a variável de ambiente. No dev, o Vite injeta o que estiver no .env; no build, ele injeta os valores do modo de produção, e uma variável ausente vira undefined — sem erro no terminal, e um site quebrado no navegador. É o assunto da próxima aula, mas já vale a regra: quando o build gera um site estranho, confira as variáveis antes de suspeitar do React.

9. Cenários do dia a dia

Cenário 1: o CSS e as imagens dão 404

Ela publicou o site numa subpasta e a página abriu sem estilo. O HTML pedia /assets/index-a1b2.css, com barra na frente, e a subpasta ficava em /padaria/. O conserto foi base: "/padaria/" no vite.config.js e um novo build. Sempre que o site não fica na raiz do domínio, o base precisa acompanhar.

Cenário 2: o pacote cresceu 500 kB de um dia para o outro

A Ana importou uma biblioteca de gráficos para um único painel e o pacote principal saltou. A saída do build mostrava o arquivo grande, mas não o culpado. O caminho foi mover o painel para um import() dinâmico: o gráfico virou um chunk separado e a primeira tela voltou ao tamanho anterior.

Cenário 3: o erro que só aparece publicado

O console do site publicado mostrava Minified React error #418, e no dev nada aparecia. A mensagem é de hidratação, um problema que só existe quando o HTML vem do servidor. Para investigar, ela publicou uma versão com sourcemap e reproduziu o caminho; o número, traduzido no site de erros do React, apontou a linha.

11. Resumo

O build pega o grafo que começa no index.html, descarta o que não é usado, junta os módulos, minifica, comprime e escreve em dist com nomes que incluem um hash do conteúdo. O resultado é menor que a soma das partes por três motivos somados: tree-shaking, minificação e compressão.

O hash existe para o cache: mudou o conteúdo, mudou o nome, e o navegador baixa de novo. O import() dinâmico cria chunks para adiar o que não é necessário na primeira tela. Em produção, o React perde os avisos, roda o StrictMode uma vez e mostra erros minificados com um link para a explicação.

E o build é o momento da verdade: import com maiúscula errada, arquivo ausente, variável de ambiente faltando — tudo o que o dev perdoava aparece ali. Conferir com npm run preview antes de publicar é o hábito que evita descobrir no ar. Falta justamente combinar a configuração que muda entre os ambientes, e é o que a próxima aula faz com as variáveis de ambiente.

Para lembrar

  • npm run build gera dist/: HTML, CSS e JavaScript empacotados.
  • Tree-shaking remove o que ninguém importa; minificação encurta o que fica.
  • O hash no nome vem do conteúdo e serve para o cache do navegador.
  • import() dinâmico cria um chunk separado, carregado sob demanda.
  • Em produção, avisos do React não aparecem e erros viram código com link.
  • StrictMode roda efeitos duas vezes só no desenvolvimento.
  • npm run preview serve o dist na porta 4173.
  • build.sourcemap gera o mapa para depurar produção — não sirva ao público.
  • base precisa acompanhar a subpasta onde o site vai morar.
  • Build quebra no que o dev perdoava: caminho, maiúscula e variável de ambiente.
