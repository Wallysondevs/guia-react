O memo

A Ana ligou o "destacar atualizações" do React DevTools para entender por que o site parecia pesado, e levou um susto: cada vez que ela trocava o aviso do dia, o cardápio inteiro piscava. O aviso é um parágrafo; o cardápio são quarenta pães. Nesta aula ela conhece o memo, a ferramenta que segura o desenho de um componente quando nada do que ele recebe mudou — e aprende as duas armadilhas que fazem o memo não servir para nada.

Você vai aprender
  • O que acontece com os filhos quando o componente de cima desenha de novo.
  • O que o memo compara de verdade entre um desenho e outro.
  • Por que uma prop recriada a cada desenho anula a proteção.
  • Quando o segundo argumento do memo resolve — e por que ele é exceção.
  • A diferença entre memo e cache: o que ele guarda (quase nada).
  • Como o children entra na comparação e por que ele costuma atrapalhar.
  • O que o React Compiler muda nessa história.

1. A cena: o cardápio piscando por causa de um aviso

O site da Ana tem duas partes na página inicial: o aviso do dia, que muda de tempo em tempo, e o cardápio, uma lista longa com preço, foto e descrição de cada pão. Quando ela troca o aviso, o cardápio também é redesenhado — mesmo que nenhum preço tenha mudado. No DevTools, as bordas verdes de "atualizou" acendem nos quarenta pães.

Isso acontece porque, em React, quem desenha o pai desenha os filhos. O estado do aviso mora no componente da página; quando ele muda, a página é chamada de novo, e os filhos dela também. O React não sabe que o cardápio é alheio ao aviso: ele só sabe que o pai pediu para desenhar.

Na maioria das vezes isso é bom. O React compara o resultado e mexe só no que mudou no DOM, e o custo é pequeno. Mas quando o filho tem uma lista grande, cálculos, ou quando o pai desenha muito por segundo (um campo de digitação, um relógio, um arrastar de mouse), o trabalho extra começa a aparecer: a digitação engasga, o ventilador liga, a animação perde quadros.

Com um contador de desenhos dentro do cardápio, a cascata fica visível no console: uma linha por desenho, e uma nova a cada troca de aviso.

A pergunta desta aula é: como dizer a um componente "se as suas props forem as mesmas, não precisa desenhar de novo". A resposta é o memo, que embrulha o componente e faz essa comparação antes de chamá-lo.

2. O que o React faz quando o pai desenha

Vale entender o caminho antes da ferramenta. Quando o estado de um componente muda, o React chama aquele componente e monta a árvore de elementos de novo. Para cada filho encontrado, ele chama o filho também — afinal, a prop do filho pode ter mudado. Isso vale até alguém barrar a descida.

desenho
Uma execução da função do componente. Nesta aula, contar desenhos é como a Ana mede o problema.
cascata
Quando o pai desenha, os filhos desenham junto. Ninguém pergunta ao filho se ele quer.
props
O que o filho recebe. São elas que o memo olha, uma a uma.
memo
A função que embrulha um componente e devolve outro: antes de desenhar, ele compara as props.
comparação rasa
Comparar cada prop com Object.is, sem entrar no conteúdo dos objetos.

A comparação rasa é a chave de quase todos os mal-entendidos da aula. O memo não olha dentro do objeto para ver se o conteúdo é igual: ele olha se é o mesmo objeto. Um array novo com os mesmos elementos é outro array; uma função nova com o mesmo corpo é outra função. Do ponto de vista da comparação, mudaram.

E o que o memo faz quando as props são as mesmas? Ele reaproveita o resultado do desenho anterior. Não existe uma "atualização parcial" aqui: o componente inteiro é pulado. Por isso o memo só faz sentido quando o componente não depende de nada além das props — se ele lê um contexto, por exemplo, ele continua sendo atualizado pelo contexto.

3. memo: as props iguais, o desenho pule

Na caixa, o cardápio conta os próprios desenhos em uma variável de módulo. Isso é de propósito: um contador em estado faria o próprio componente desenhar, e a medida ficaria contaminada. A lista de pães vem de uma constante de módulo, então a prop é sempre a mesma referência. Clique em Trocar aviso e veja o número subir.

O cardápio desenha de novo a cada troca de aviso, mesmo recebendo a mesma lista. Embrulhe Cardapio com memo(...) e faça o número continuar em 1 depois do clique.

const PAES = ["pão francês", "pão de queijo", "sonho"];

let desenhos = 0;

function Cardapio({ paes }) {
  desenhos = desenhos + 1;
  return (
    <p>desenhos do cardápio: {desenhos} com {paes.length} pães</p>
  );
}

function App() {
  const [aviso, setAviso] = useState("Padaria aberta");

  return (
    <div>
      <button id="trocar" onClick={() => setAviso("Forno quente até as 10h")}>
        Trocar aviso
      </button>
      <p>{aviso}</p>
      <Cardapio paes={PAES} />
    </div>
  );
}

O painel inicial mostra desenhos do cardápio: 1 porque o componente desenhou uma vez na montagem. Depois do clique, o número vai para 2 no código antigo e fica em 1 na solução. Nada mudou na tela além do aviso, e o cardápio não teve trabalho.

Repare na forma: memo recebe a função do componente e devolve um componente novo. Por isso a variável precisa ser atribuída (const Cardapio = memo(...)) e a função interna precisa ter nome — o nome aparece no DevTools e nas mensagens de erro. Chamar memo(Cardapio) sem guardar o resultado é um erro comum: o componente original continua sendo usado e nada muda.

E a comparação é com as props atuais contra as do desenho anterior. Se o pai passar paes={PAES} nas duas vezes, é o mesmo array, e a comparação passa. Se o pai passar paes={[...PAES]}, é outro array e o memo libera o desenho — que é exatamente o assunto da próxima seção.

4. A prop recriada anula o memo

Aqui a Ana caiu na armadilha que derruba a maioria das tentativas de otimização. Ela embrulhou o cardápio com memo e continuou vendo o número subir. A causa estava na chamada: <Cardapio config={{ titulo: "Pães de hoje" }} />. O objeto é criado no corpo do App, então cada desenho do pai produz um objeto novo — com o mesmo conteúdo, mas outra identidade.

A comparação rasa vê dois objetos diferentes e conclui "mudou". Do ponto de vista do React, está certa: ele não tem como saber que o conteúdo é igual sem entrar objeto adentro, e entrar custaria caro. Quem escreveu a chamada precisa entregar a mesma referência.

O cardápio já está com memo, mas o App cria um objeto novo a cada desenho. Tire a criação do corpo do componente — deixe a configuração em uma constante de módulo — e faça o número continuar em 1 depois do clique.

let desenhos = 0;

const Cardapio = memo(function Cardapio({ config }) {
  desenhos = desenhos + 1;
  return <p>desenhos do cardápio: {desenhos} ({config.titulo})</p>;
});

function App() {
  const [aviso, setAviso] = useState("Padaria aberta");

  return (

      <button id="trocar" onClick={() => setAviso("Forno quente até as 10h")}>
        Trocar aviso
      </button>
      <p>{aviso}</p>
      <Cardapio config={{ titulo: "Pães de hoje" }} />
    </div>
  );
}

Depois do clique, o código antigo mostra desenhos do cardápio: 2; a solução continua em 1. A correção mais simples nem passa por otimização: em vez de um objeto, mande as props soltas — <Cardapio titulo="Pães de hoje" /> — e a comparação trabalha com textos, que são iguais por valor.

Vale a mesma lógica para funções. aoEscolher={() => setEscolhido(p)} cria uma função nova a cada desenho do pai, e o memo do filho deixa de valer. A ferramenta para estabilizar a função é o useCallback, assunto da aula de useCallback na prática, e para estabilizar objetos e arrays é o useMemo, da aula de useMemo na prática. Aqui basta saber que, sem props estáveis, o memo não tem o que proteger.

5. O comparador próprio

Existe uma saída quando a prop é um objeto que você não consegue estabilizar — porque vem de uma busca, de uma lista, de um cálculo. O memo aceita um segundo argumento: uma função que recebe as props antigas e as novas e devolve true quando podem ser consideradas iguais. É o comparador próprio.

A ficha recebe um objeto novo a cada desenho. Passe um comparador como segundo argumento do memo, que devolve verdadeiro quando pao.nome e pao.preco são iguais, e faça o número continuar em 1 depois do clique.

const PAES = [
  { nome: "pão de queijo", preco: 4 },
  { nome: "sonho", preco: 6 },
];

let desenhos = 0;

const Ficha = memo(function Ficha({ pao }) {
  desenhos = desenhos + 1;
  return <p>ficha desenhada: {desenhos} ({pao.nome})</p>;
});

function App() {
  const [aviso, setAviso] = useState("Padaria aberta");
  const escolhido = PAES[0];

  return (
    <div>
      <button id="trocar" onClick={() => setAviso("Forno quente até as 10h")}>
        Trocar aviso
      </button>
      <p>{aviso}</p>
      <Ficha pao={{ nome: escolhido.nome, preco: escolhido.preco }} />
    </div>
  );
}
<div>
  <button id="trocar">Trocar aviso</button>
  <p>Padaria aberta</p>
  <p>ficha desenhada: 1 ( pão de queijo )</p>
</div>

const PAES = [
  { nome: "pão de queijo", preco: 4 },
  { nome: "sonho", preco: 6 },
];

let desenhos = 0;

const Ficha = memo(
  function Ficha({ pao }) {
    desenhos = desenhos + 1;
    return <p>ficha desenhada: {desenhos} ({pao.nome})</p>;
  },
  (antes, agora) => antes.pao.nome === agora.pao.nome
);

  const [aviso, setAviso] = useState("Padaria aberta");
  const escolhido = PAES[0];

      </button>
      <p>{aviso}</p>
      <Ficha pao={{ nome: escolhido.nome, preco: escolhido.preco }} />
    </div>
  );
}

O painel inicial mostra uma ficha; depois do clique, o código antigo mostra duas e a solução continua em uma. O comparador rodou, viu que o nome era o mesmo e disse "pode pular".

Use com parcimônia, e por três razões. A primeira é que o comparador é seu código rodando em todo desenho — se ele ficar caro, você trocou um problema por outro. A segunda é que ele é fácil de errar: se você comparar só o nome, a ficha deixa de atualizar quando o preço muda, e o bug aparece semanas depois. A terceira é que ele esconde a causa: em vez de ensinar o componente de cima a mandar props estáveis, ele contorna. A documentação do React chama isso de saída de emergência, e a expressão é justa.

6. memo não é cache

O nome engana. Um cache guarda um resultado para não calcular de novo; o memo guarda o resultado do último desenho do componente e compara as props para decidir se pode reaproveitá-lo. Não existe uma tabela de resultados por combinação de props: se a prop mudar e voltar, o componente desenha de novo.

Também não existe garantia. O React pode descartar o resultado guardado quando quiser — por exemplo, ao liberar memória. A documentação diz que memo é uma otimização de desempenho, não uma promessa de comportamento. Nenhuma regra do seu site pode depender de "esse componente não desenhou".

E ele custa alguma coisa: comparar props a cada desenho do pai. Para um componente que recebe duas props primitivas, a comparação é barata e o ganho pode ser real. Para um componente que desenha dois parágrafos, comparar três props e pular o desenho pode sair mais caro do que desenhar. Como sempre, medir primeiro: a aba Profiler do React DevTools mostra quanto cada componente levou e quantas vezes desenhou. E vale separar os dois problemas: se o custo está na conta, e não no desenho, a ferramenta é o useMemo.

A última linha é a que mais surpreende, e ela merece a próxima seção: quando você escreve <Moldura><p>oi</p></Moldura>, o <p>oi</p> é um objeto criado no desenho do pai. Para o memo da moldura, é uma prop nova toda vez.

7. O children e a moldura

Um componente que recebe children está recebendo elementos, não texto. Cada desenho do pai cria aqueles elementos outra vez, mesmo que o JSX seja idêntico. Então memo em cima de um layout com children costuma não servir para nada — o que não quer dizer que o layout esteja errado; quer dizer que a proteção do memo não é a ferramenta para ele.

Há três saídas, e vale conhecer as três para escolher com calma. A primeira é estabilizar o elemento do filho com useMemo no pai, o que mantém a mesma referência enquanto as dependências não mudam — o assunto da aula seguinte. A segunda é separar o que muda do que não muda: em vez de um layout com children, um layout com props estáveis e o conteúdo desenhado por dentro, recebendo a página por um componente que já estava memoizado. A terceira é aceitar: se o layout desenha pouco, o memo nele é ruído.

Uma observação que evita confusão: memo em um componente que tem estado próprio não impede o estado de funcionar. Um botão memoizado que guarda "quantas vezes fui clicado" continua atualizando quando o clique acontece; o que ele pula é o desenho causado pelo pai. As duas coisas são independentes.

8. O React Compiler e o fim do memo manual

O React 19 trouxe uma promessa que muda a conversa: o React Compiler, um plugin que analisa os componentes e insere a memoização automática onde ela faz sentido. Com ele ligado, você escreve o código do jeito natural e o compilador cuida de pular o que não mudou — incluindo o caso do memo, do useMemo e do useCallback.

Vale ser preciso: o compilador não vem ligado por padrão no React 19. Ele é uma ferramenta separada, que se configura no projeto — o projeto criado pelo Vite não o traz. Mas a direção é clara, e a documentação já recomenda tratar memo, useMemo e useCallback como recursos de exceção, para quando a medição mostrar que precisa.

Então por que aprender memo hoje? Porque você vai encontrar código com ele em todo lugar, porque entender a comparação de props explica uma família de bugs (o componente que "não atualiza" e o que "atualiza demais"), e porque saber quando não usar é metade do trabalho. O instinto saudável é: primeiro escreva claro, meça, e só depois embrulhe.

9. Cenários do dia a dia

Cenário 1: o componente memoizado não atualiza

A Ana embrulhou o resumo do pedido com memo e ele parou de acompanhar o total. O comparador próprio estava olhando só a quantidade de itens, e o total mudava com o preço. É o risco do comparador: você assume a responsabilidade de listar o que importa. Na dúvida, não escreva comparador; se escrever, compare todas as props que o componente usa.

Cenário 2: a lista com cinquenta itens que trava a digitação

O campo de busca do topo atualiza a cada tecla e a lista de cinquenta cards redesenha junto. Embrulhar cada card com memo resolve metade: os cards cujas props não mudaram são pulados. A outra metade é o array filtrado, que precisa de identidade estável — é onde entra o useMemo. E se a digitação continuar pesada, o assunto passa a ser useDeferredValue ou uma lista virtualizada.

Cenário 3: memo em tudo e o site igual

Embrulhar todos os componentes "por garantia" não melhora nada e atrapalha a leitura: cada memo esconde uma decisão que ninguém mediu. Pior, o comparador de cada um custa tempo em todo desenho. Se o Profiler não mostra um problema, a otimização certa é nenhuma.

const Ficha = memo(FichaBase, (antes, agora) => antes.pao.preco === agora.pao.);

11. Resumo

Quando o pai desenha, os filhos desenham junto. O memo embrulha um componente e, antes de chamá-lo, compara as props atuais com as do desenho anterior, uma por uma, por referência. Se todas forem iguais, o desenho é pulado. Se alguma mudou — inclusive um objeto ou uma função recriada no corpo do pai — o componente desenha normalmente.

O segundo argumento permite escrever a comparação à mão. É útil quando a prop é um objeto que não dá para estabilizar, e é perigoso quando você esquece de comparar o que importa: o componente para de atualizar e o bug demora a aparecer. Antes de chegar nele, prefira props primitivas, constantes de módulo, useMemo para valores e useCallback para funções.

E lembre que memo é otimização, não regra de negócio: pode ser descartado quando o React quiser, custa uma comparação a cada desenho e, com o React Compiler no horizonte, tende a virar exceção. Escreva claro, meça no Profiler, e só então embrulhe.

Para lembrar

  • Pai que desenha faz os filhos desenharem.
  • memo compara props por referência (Object.is), uma a uma.
  • Props iguais: o desenho do componente é pulado inteiro.
  • Objeto, array ou função recriados no pai: a comparação falha e o memo não ajuda.
  • Prefira props primitivas e constantes de módulo à saída do comparador.
  • Comparador próprio é saída de emergência: compare tudo o que o componente usa.
  • memo não guarda cache de resultados e pode ser descartado pelo React.
  • Estado interno continua funcionando em componente memoizado.
  • children é elemento novo a cada desenho: memo em cima dele raramente serve.
  • O React Compiler memoiza sozinho — e não vem ligado por padrão no React 19.
