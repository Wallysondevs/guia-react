Lista de Tarefas

A Ana mantém o caderno de tarefas da padaria aberto no balcão: abrir o forno, lembrar da encomenda da dona Marta, comprar farinha. O caderno funciona, mas some quando ela sai para entregar pão e volta com a página molhada. Neste projeto ela constrói a lista de tarefas no navegador, do zero ao acabamento: decide o formato dos dados, desenha a lista, aprende a adicionar sem estragar o estado, conclui e desfaz, conta o que falta e vê a mensagem certa quando não há nada. Cada caixa roda um pedaço do app de verdade.

Você vai aprender
  • Como decidir a forma dos dados antes de escrever a tela.
  • Por que cada tarefa é um objeto com id, texto e feita.
  • Como desenhar a lista com map e key.
  • Como adicionar com [...tarefas, nova] em vez de push.
  • De onde vem um id que não muda quando a lista muda.
  • Como concluir e desfazer trocando um item por outro com map.
  • Quais números da tela são estado e quais são conta feita no render.
  • O que quebra em cada etapa — e por quê.

1. A cena e o escopo do app

A padaria tem tarefas demais para a memória da Ana. Ela quer uma tela com o nome da padaria, um campo para escrever a tarefa, um botão para acrescentar, a lista do que existe e um jeito de marcar o que já foi feito. Também quer ver, de relance, quantas faltam. Nada de login, nada de servidor: a lista vive enquanto a página está aberta.

Essa última frase é uma decisão de projeto, e decisões de projeto vêm antes do código. Se a lista vive na memória, recarregar a página apaga tudo — e isso é aceitável para a primeira versão. Guardar no localStorage é uma evolução, não um requisito. Escrever o escopo agora evita a armadilha de começar pelo banco de dados e nunca chegar à tela.

O app tem quatro operações: listar, adicionar, concluir e desfazer. Tudo o mais — filtro por status, ordem alfabética, prazo — é acabamento. Neste projeto, o acabamento é o filtro e os contadores, no fim. Cada operação vai virar uma função pequena que recebe o que precisa e devolve uma lista nova para o estado.

Antes de abrir o editor, vale desenhar a tela em três pedaços: o cabeçalho com o título e o contador, o formulário com o campo e o botão, e a lista. Cada pedaço vai virar um componente quando o arquivo crescer — mas não comece por aí. Primeiro faça funcionar num componente só; depois separe. A ordem de montagem deste projeto é essa, e é a mesma que funciona em qualquer app pequeno.

2. Os dados primeiro: a forma da tarefa

A pergunta inicial não é "como desenho a lista?", é "o que é uma tarefa?". Se você guardar só o texto, não tem como saber se ela foi feita nem como diferenciar duas tarefas iguais. Se guardar o texto e um número solto, o número não diz nada. A forma que resolve o app inteiro é um objeto com três campos: um identificador, o texto e um booleano.

tarefa
Um objeto com os dados de uma linha da lista: { id: 1, texto: "Comprar farinha", feita: false }.
id
Um valor único e estável que identifica a tarefa mesmo depois que o texto muda. É a key do map e o que o botão de concluir recebe.
texto
O que aparece na tela. Pode mudar sem que a identidade da tarefa mude.
feita
O booleano que diz se a tarefa foi concluída. É o que a caixa de marcar mostra e altera.
lista de tarefas
O array no estado: useState(tarefasIniciais). Quem manda na tela é ele, não o caderno.

Com a forma definida, os dados iniciais ficam legíveis:

const tarefasIniciais = [
  { id: 1, texto: "Abrir o forno às 5h", feita: true },
  { id: 2, texto: "Encomenda da dona Marta", feita: false },
  { id: 3, texto: "Comprar farinha", feita: false },
];

Três decisões aparecem nesse array, e todas têm consequência. A primeira é guardar objetos em vez de strings: o objeto carrega o estado da tarefa junto com o texto. A segunda é ter id desde o começo: sem ele, concluir uma tarefa específica vira uma comparação por texto, que quebra quando duas tarefas são iguais. A terceira é usar feita: false em vez de deixar o campo vazio: um booleano sempre tem valor, e a caixa de marcar espera true ou false, nunca undefined.

DecisãoSe você escolher o caminho fácilO que acontece depois
guardar só o texto["Comprar farinha"]não dá para marcar como feita nem diferenciar duas iguais
guardar objeto sem id{ texto, feita }a key vira o texto, e editar o texto embaralha a lista
usar o índice como idid: indiceremover uma tarefa muda o id de todas as seguintes
objeto com id, texto e feita{ id, texto, feita }lista, conclusão e remoção funcionam sem gambiarra

O array inicial fica fora do componente porque é constante: ele não muda, o que muda é a cópia que o useState guarda. Isso também deixa claro o que é dado de partida e o que é estado vivo. Quando o app crescer, esse array vira a resposta de uma API — e o resto do componente não precisa saber a diferença.

3. A lista na tela

Com os dados prontos, a primeira tela é só a lista. A Ana começou escrevendo os li à mão, copiando o texto de cada tarefa. Funciona até a terceira, e aí ela esquece uma. O map resolve — a aula de listas com map mostra o passo a passo. Cada objeto vira um li, e a lista na tela passa a ser uma consequência do array.

A caixa abaixo tem o array com três tarefas e uma lista escrita à mão com duas. Complete a lista com map, dando a cada li uma key igual ao id:

No painel aparecem os três li, na ordem do array. Repare que a contagem já estava certa antes do conserto — o {tarefas.length} tarefas lê do array, não da lista desenhada à mão. É uma pista útil: quando o número e a lista discordam, um dos dois não está lendo o estado. Neste caso, o número estava certo e a lista era cópia.

A key não aparece no HTML gerado. Ela é uma identidade para o React: quando a lista muda, ele compara as chaves para saber qual item saiu, entrou ou mudou de posição. Com o id estável, uma tarefa concluída continua sendo a mesma tarefa. Sem key, o console avisa em desenvolvimento e a ordem pode se confundir em listas que mudam — e essa lista muda a cada clique.

Para conferir o que o estado guarda, um console.log antes do return mostra a lista inteira:

tarefas.length: 3
tarefas[2].texto: "Comprar farinha"
tarefas[0].feita: true

Essas linhas são a fonte da verdade. Se a tela mostrar algo diferente, o problema está entre o estado e o JSX — map errado, key repetida, condição invertida —, não no array.

4. Adicionar sem estragar o estado

Agora a operação que mais ensina sobre React: adicionar. A tentação é usar push, que é o método que "acrescenta no fim". Só que push muda o array original e devolve o novo tamanho. Se você fizer tarefas.push(nova) e depois setTarefas(tarefas), entrega ao React o mesmo array de antes — ele compara e conclui que nada mudou, então não redesenha. A tela fica velha com o estado novo.

A caixa abaixo tem esse bug de propósito. Escreva uma tarefa, clique em Adicionar e veja que nada acontece. Depois construa uma lista nova com spread e faça o campo esvaziar:

O botão usa push e a lista não muda. Acrescente a tarefa construindo uma lista nova ([...tarefas, novaTarefa]), ignore o texto vazio e limpe o campo depois de adicionar.

const tarefasIniciais = [

  { id: 3, texto: "Comprar farinha", feita: false },
];

function App() {
  const [tarefas, setTarefas] = useState(tarefasIniciais);

Três coisas acontecem na função consertada. O trim() transforma " " em "", e o if impede a tarefa vazia. O spread copia os itens antigos para um array novo e coloca o item novo no fim. E setNova("") limpa o campo, porque o valor dele vem do estado.

Depois do clique, o console mostra a lista com quatro itens e o campo vazio:

tarefas.length: 4
nova: ""
typeof tarefas[3].id: number

O Date.now() resolve o id porque devolve os milissegundos atuais: dois cliques em momentos diferentes geram números diferentes. É suficiente para um app local. Num app com servidor, o id vem do servidor — e a aula de envio de dados mostra por quê.

Um detalhe que engana: no código com push, o array do estado cresceu de verdade. O que não aconteceu foi o desenho da tela. Se você abrir o console, vê quatro itens; a página mostra três. É o sintoma clássico de mutação: o React não tem como perceber que o conteúdo mudou, porque a referência é a mesma.

5. O id que não muda quando a lista muda

O id é a peça mais subestimada do projeto — a aula da key entra nos detalhes depois. Ele aparece em dois lugares: como key do map e como argumento das funções que concluem ou removem. Se ele muda quando a lista muda, os dois lugares quebram juntos. A tabela compara as fontes mais comuns:

Fonte do idComo ficaProblema
índice do mapkey={indice}ao remover a primeira, todas as seguintes trocam de id
texto da tarefakey={tarefa.texto}duas tarefas iguais colidem; editar o texto troca a identidade
Date.now()id: Date.now()dois cliques no mesmo milissegundo repetem o id
contador que só cresceid: proximoId++precisa de uma variável fora do componente; cresce para sempre

Para um app local, Date.now() é a escolha mais simples e funciona. O caso do clique duplo no mesmo milissegundo é raro em uso humano, mas aparece em teste automatizado — e é justamente o tipo de detalhe que separa um protótipo de um app. Se você quer blindar, combine com um contador: id: Date.now() + contador, ou guarde um número em useRef.

O índice é o mais perigoso porque parece elegante. Ele funciona enquanto a lista só cresce. No dia em que a Ana remove uma tarefa do meio, as seguintes ganham um índice novo, o React acha que os itens mudaram e recria os elementos — perdendo foco, seleção de texto e animação. O texto tem o mesmo problema disfarçado: duas "Comprar farinha" na lista geram duas chaves iguais, e o React avisa no console.

Uma consequência prática: o id nunca deve ser recalculado no render. Ele nasce quando a tarefa é criada e morre quando ela é removida. Se você escrever id: indice dentro do map, está criando um id novo a cada desenho — e a identidade que o React usa deixa de existir.

6. Concluir e desfazer

Concluir uma tarefa é trocar um item da lista por outro, com feita invertido. O map faz isso bem: ele percorre a lista e devolve uma lista nova, trocando só o item cujo id bate. O erro clássico é o atalho: achar o objeto e mudar a propriedade direto, como a Ana fez na primeira versão.

Na caixa abaixo, o alternar muta o objeto e entrega o mesmo array ao setTarefas. Clique na caixa da segunda tarefa e nada muda no contador. Conserte com map e um objeto novo:

O alternar muda o objeto no lugar e a tela não atualiza. Troque por um map que devolve { ...tarefa, feita: !tarefa.feita } para a tarefa certa e a lista original para as outras.

const tarefasIniciais = [
  { id: 1, texto: "Abrir o forno às 5h", feita: true },
  { id: 2, texto: "Encomenda da dona Marta", feita: false },
  { id: 3, texto: "Comprar farinha", feita: false },
];

function App() {
  const [tarefas, setTarefas] = useState(tarefasIniciais);

  function alternar(id) {
    const tarefa = tarefas.find((t) => t.id === id);
    tarefa.feita = !tarefa.feita;
    setTarefas(tarefas);
  }

  const feitas = tarefas.filter((t) => t.feita).length;

  return (
    <div>
      <p>{feitas} de {tarefas.length} concluídas</p>
      <ul>
        {tarefas.map((tarefa) => (
          <li key={tarefa.id} className={tarefa.feita ? "feita" : ""}>
            <input
              type="checkbox"
              checked={tarefa.feita}
              onChange={() => alternar(tarefa.id)}
            />
            {tarefa.texto}
          </li>
        ))}
      </ul>
    </div>
  );
}

Depois do conserto, clicar na segunda tarefa leva o contador de "1 de 3" para "2 de 3" e a classe feita aparece no segundo li. A conta feitas é refeita no render, a partir do array novo. Nada de estado extra.

O console confirma o que a tela mostra, com o array já trocado:

feitas: 2
tarefas[1].feita: true
tarefas[1].texto: "Encomenda da dona Marta"

Há duas armadilhas nesse padrão. A primeira é esquecer o ... e devolver { feita: !tarefa.feita }, perdendo o texto e o id; o item vira um objeto incompleto e a tela mostra vazio. A segunda é inverter a condição: tarefa.id === id ? ... : ... com os lados trocados faz o React trocar todas as outras e deixar a clicada intacta.

Para remover, a lógica é a mesma, com filter em vez de map:

function remover(id) {
  setTarefas(tarefas.filter((tarefa) => tarefa.id !== id));
}

filter devolve uma lista nova só com quem passa no teste: "fique se o id for diferente do que eu quero remover". É o inverso do map, que devolve um item para cada item. Guarde as duas receitas: map troca, filter tira, e [...lista, novo] põe.

7. Contadores, filtro e o vazio

Com listar, adicionar e concluir funcionando, o app já serve. O acabamento são os números e o filtro. Aqui vale uma distinção que economiza metade dos bugs do projeto: nem tudo que aparece na tela é estado. O texto do campo é estado; a lista é estado; a aba escolhida no filtro é estado. O total de tarefas, o número de concluídas e a lista visível são contas feitas no render.

estado
O que muda com o tempo e precisa ser lembrado entre um desenho e outro: a lista, o texto novo, o filtro escolhido.
derivado
O que é calculado a partir do estado no próprio render: feitas, faltando, visiveis.
handler
A função que recebe o evento ou um id e chama o set... com uma lista nova: adicionar, alternar, remover.
item
O componente ou o li que recebe uma tarefa e desenha uma linha. Recebe dados por props e avisa por função.
vazio
O estado legítimo de uma lista sem itens ou de um filtro sem resultado. Merece mensagem própria, não uma tela em branco.

O filtro é o único estado novo que o acabamento pede. Três valores possíveis — todas, abertas, concluídas — e uma conta que decide quem aparece:

const [filtro, setFiltro] = useState("todas");

const visiveis = tarefas.filter((tarefa) => {
  if (filtro === "abertas") return !tarefa.feita;
  if (filtro === "concluidas") return tarefa.feita;
  return true;
});

Repare que visiveis nasce do estado e não vira useState. Se você guardasse a lista filtrada, teria de atualizá-la em toda mudança de tarefa e de filtro — e uma hora esqueceria. A regra é simples: se dá para calcular a partir do que já existe, calcule no render.

O que aparece na telaEstado ou conta?Por quê

O vazio aparece em dois momentos diferentes, e as mensagens não são a mesma. Na primeira vez, a lista está vazia porque nada foi criado: "Nenhuma tarefa ainda. Comece pela primeira." Depois de um filtro, a lista pode estar vazia com tarefas existindo: "Nenhuma tarefa concluída por aqui." A condição é parecida — visiveis.length === 0 —, mas o texto muda conforme tarefas.length e o filtro. Uma tela em branco nunca é resposta.

8. Cenários do dia a dia

Cenário 1: a lista some quando ela recarrega a página

A Ana cadastrou sete tarefas, apertou F5 e voltou ao zero. O estado vive na memória do componente: recarregar a página recria tudo. Para guardar entre visitas, o caminho é o localStorage — gravar com useEffect e ler na função do useState. Isso é evolução, não requisito: a lista funciona sem persistência, e quem tenta guardar antes de a lista funcionar passa o dia depurando JSON.

Cenário 2: duas tarefas com a mesma key

Ela usou key={tarefa.texto} e cadastrou "Comprar farinha" duas vezes. O React avisou no console que havia chaves repetidas e, ao concluir uma, as duas mudaram de aparência. Chave é identidade: precisa ser única entre os irmãos. O id resolve porque é gerado uma vez por tarefa, mesmo quando o texto se repete.

Cenário 3: o contador diz 3 e a lista mostra 2

O número vinha de tarefas.length e a lista de um filter antigo guardado num estado separado. Um dos dois ficou para trás. Quando número e lista discordam, quase sempre há um estado derivado guardado à mão. A cura é apagar o estado extra e calcular os dois a partir da mesma fonte.

10. Resumo

O projeto começou pelos dados: cada tarefa é um objeto com id, texto e feita, e a lista mora no useState. A tela é um map com key estável. Adicionar é [...tarefas, nova], com trim e limpeza do campo; concluir é map trocando o item certo por um objeto novo; remover é filter.

Os números e a lista filtrada não são estado: são contas feitas no render. Guardar só o que muda por decisão do usuário — lista, texto e filtro — evita a maior parte dos bugs de sincronização. E o vazio tem mensagem própria, porque uma tela em branco não explica nada.

O que fica de fora é a persistência: o estado some ao recarregar. O próximo passo natural é gravar a lista no localStorage e ler na criação do estado, com cuidado para o JSON quebrado. Antes disso, porém, vale separar o item num componente próprio: um ItemTarefa que recebe a tarefa e a função de alternar, e um Contador que recebe os números. O app continua o mesmo, dividido em peças menores — e é assim que ele sobrevive ao próximo recurso.

Se quiser comparar com outro app que usa a mesma base, o carrinho de compras leva essas operações para uma lista de objetos com quantidade, e o estado com array tem as receitas de cada operação isoladas. O importante é que você já sabe o desenho: estado, handler, conta, lista e vazio.

Para lembrar

  • Cada tarefa é { id, texto, feita }; o array fica no useState.
  • map desenha; key estável identifica; filter remove.
  • Adicionar: setTarefas([...tarefas, nova]). push não redesenha.
  • Concluir: map com { ...tarefa, feita: !tarefa.feita }.
  • id nasce na criação e não muda; índice e texto não servem.
  • trim() + if (texto === "") return evitam tarefa vazia.
  • Total, feitas e visíveis são contas no render, não estados.
  • O filtro escolhido é estado; a lista filtrada é derivada.
  • A className condicional pinta o item concluído.
  • Lista vazia merece mensagem — e a mensagem muda se há filtro.
