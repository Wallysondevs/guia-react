A key

A Ana já monta a lista de pães com map: um array entra, uma lista de elementos sai. Só que, no dia em que ela tira um pão do meio da lista, a observação que estava escrita no pão errado muda de lugar — e o console do projeto começa a reclamar de uma tal de key. Nesta aula ela entende o que essa palavra significa, por que o React insiste nela e como escolher o valor certo para cada item.

Você vai aprender
  • O que o React faz com uma lista quando ela muda de um desenho para o outro.
  • O que é a key e em qual elemento ela se escreve.
  • O que a key não é: não vai para o HTML, não chega como prop, não é o id.
  • Como escolher uma key única e estável, vinda dos dados.
  • Por que o índice da lista costuma ser uma escolha ruim.
  • Como usar key com Fragment e com componentes.

1. A cena: a lista que se embaralha

A página de pães da Ana tem uma linha para cada pão do dia, e cada linha tem um campinho de observação, daqueles que ela digita à mão: "sem sal", "assar mais", "guardar dois". Num sábado, ela escreve "sem sal" na linha da broa e vai atender o balcão. Quando volta, o pão francês acabou e ela tira esse pão do começo da lista.

A lista se atualiza: agora são broa, croissant e bolo de fubá. Só que a observação "sem sal" pulou para a linha do croissant. Ninguém mexeu no croissant. A Ana não apagou texto nenhum. O texto estava no segundo campinho da lista e continuou no segundo campinho — quem mudou de lugar foi o pão. E, no console do projeto, apareceu um aviso que ela nunca tinha lido com atenção:

Each child in a list should have a unique "key" prop.

Check the render method of `ListaDePaes`.

Esse aviso é a versão de desenvolvimento do React falando. Ele não impede a página de rodar, e é justamente por isso que tanta gente ignora: o sintoma aparece longe do aviso, como um texto que pula de linha ou uma caixa marcada no produto errado. Aqui na caixa do guia esse aviso não aparece, porque a caixa usa a versão de produção do React — a versão que vai para o site e que é calada. No seu projeto, com o servidor de desenvolvimento ligado, ele aparece. Vale aprender a ler os dois.

Repare no que o aviso pede: uma key única para cada filho de uma lista. Não é uma sugestão de estilo, não é um enfeite para o código ficar bonito. É a informação que falta para o React saber qual linha é qual quando a lista muda. Sem ela, ele chuta pela posição — e o chute erra.

2. Por que o React precisa de uma key

Quando o componente roda de novo, o React não joga a página fora e desenha tudo do zero. Ele compara o que estava na tela com o que o componente acabou de devolver e mexe só no que mudou. Essa comparação se chama reconciliação, e para um elemento sozinho ela é fácil: era um p com "0", virou um p com "1", troca o texto e pronto.

Numa lista, a comparação tem um problema a mais: o React precisa decidir qual elemento antigo corresponde a qual elemento novo. Sem nenhuma informação extra, ele usa a posição: o primeiro vira o primeiro, o segundo vira o segundo, e assim por diante. Se a lista só cresce no fim, isso funciona bem. Se um item do meio desaparece, todos os seguintes sobem uma posição — e o React, sem saber disso, reaproveita o nó da posição 1 para o item que agora está na posição 1, mudando só o texto.

É como a etiqueta de bagagem da padaria. Se a Ana guarda as sacolas por ordem de chegada e não anota o nome de ninguém, a terceira sacola da prateleira passa a ser "a terceira pessoa da fila" — e, quando alguém desiste, a sacola é entregue para o cliente errado. Com uma senha presa na sacola, ela acha a dona em qualquer posição. A key é essa senha.

lista
Um array de elementos que o JSX recebe dentro de chaves: {paes.map(...)}. Cada item precisa ser identificável.
reconciliação
A comparação que o React faz entre o desenho anterior e o novo, para reaproveitar nós em vez de recriar a página inteira.
key
Um valor especial que marca a identidade de um item: key={p.id}. O React usa e descarta; ela não chega ao HTML.
identidade
A resposta para "este item é o mesmo de antes?". Com key, é o valor dela; sem key, é a posição.

Há uma consequência prática que explica todos os bugs de key: um nó do navegador carrega estado que não está no seu JSX. O texto digitado num campo, o cursor piscando, a caixa marcada, a posição da rolagem, uma animação no meio do caminho. Se o React reaproveita o nó errado, esse estado fica no lugar errado — e parece mágica, porque o seu código não tem nada de errado.

3. A key na prática

A regra é curta: todo elemento que nasce dentro de um map precisa de uma key, e a key vai no elemento mais externo que a função do map devolve. Um <li> que embrulha nome e preço recebe a key uma vez, na abertura. Os filhos não recebem nada.

function ListaDePaes() {
  const paes = [
    { id: 1, nome: "Pão francês", preco: "R$ 0,90" },
    { id: 2, nome: "Broa de milho", preco: "R$ 3,50" },
    { id: 3, nome: "Croissant", preco: "R$ 6,00" }
  ];

  return (
    <ul>
      {paes.map((p) => (
        <li key={p.id}>
          {p.nome} — {p.preco}
        </li>
      ))}
    </ul>
  );
}

O valor de uma key é sempre uma string ou um número. Pode ser o id que veio do banco, o código do produto, o CPF do cliente, o slug da receita — qualquer coisa que seja única dentro daquela lista e que não mude de um desenho para o outro. O nome da variável não importa: p.id, item.codigo, encomenda.numero; o que importa é o valor.

A lista abaixo não tem key nenhuma. Dê a cada <li> a key={p.id} e escreva também data-id={p.id} — é só para o painel mostrar qual item é qual, já que a key não aparece no HTML.

4. O que a key não é

Quatro confusões aparecem no primeiro dia, e todas têm o mesmo efeito: o aviso continua no console mesmo com o código "parecendo certo".

A key não é um atributo HTML. Você não vai encontrá-la no inspetor nem no painel, e não adianta tentar estilizá-la com CSS. A key não é uma prop: o componente que recebe <Pedido key={p.id} /> não consegue ler props.key — o React consome a key antes de chamar a função. Se você precisa do id lá dentro, passe também id={p.id}. A key não é o id do HTML: são coisas diferentes, com propósitos diferentes, e uma não substitui a outra. E a key não é para você: é para o React. O nome "chave" engana um pouco, porque parece coisa de segurança; é mais uma etiqueta de identidade.

5. De onde vem uma boa key

Uma key boa cumpre três condições. Primeira: é única entre os irmãos — dois itens com a mesma key fazem o React tratar um como o outro. Segunda: é estável — o mesmo item tem a mesma key no desenho de hoje e no de amanhã. Terceira: vem do dado, não da posição nem do acaso. Um id de banco é o exemplo perfeito: nasce único, não muda quando a lista é filtrada ou ordenada, e já está no objeto que você está mapeando.

O índice que o map oferece (paes.map((p, i) => ...)) é a tentação número um, porque está ali de graça. Ele não é proibido, e há casos em que funciona: uma lista fixa, que nunca ganha nem perde item, nunca é reordenada e nunca é filtrada. No momento em que a lista muda, o índice deixa de ser identidade e passa a ser posição — exatamente o que o React já faria sozinho. É por isso que se diz que "usar índice como key é o mesmo que não usar key".

Se o dado não tem id — uma lista de strings, por exemplo —, o caminho honesto é criar um id quando o item nasce (no cadastro, no formulário) ou aceitar que aquela lista é estável e usar o índice com consciência. O que não vale é fingir: colocar o índice e esquecer o assunto é a origem da maioria dos bugs de lista que aparecem depois, quando alguém adiciona um filtro.

6. O que dá errado com a key errada

Vamos seguir o sábado da Ana com o código que ela tinha. Repare que o índice é a key e que cada linha tem um campo sem controle do React, com o texto que ela digita:

function ListaDePaes({ paes }) {
  return (
    <ul>
      {paes.map((p, i) => (
        <li key={i}>
          {p.nome}
          <input placeholder="observação" />
        </li>
      ))}
    </ul>
  );
}

Com a lista completa, cada linha ocupa uma posição e tudo parece certo. Quando o pão francês sai, a lista fica com dois itens: broa na posição 0 e croissant na posição 1. O React compara: "a posição 0 era um li com key 0, continua sendo um li com key 0 — então é o mesmo elemento, só troco o texto". O nó do navegador é reaproveitado, e com ele o texto que estava digitado ali dentro. Resultado: a observação da broa aparece no croissant.

O mesmo mecanismo explica os outros sintomas. Uma caixa de seleção marcada na linha 2 continua marcada na linha 2, agora de outro produto. O cursor que estava no terceiro campo passa a piscar no campo errado. A animação de entrada reinicia no item que não mudou. A rolagem de uma lista longa "pula" quando um item é removido do topo. Em todos os casos, o culpado é o mesmo: o React tratou posições como se fossem identidades.

Com key={p.id}, o React vê que a key 1 desapareceu e que as keys 2 e 3 continuam. Ele remove o nó do pão 1 e move os outros dois, com o estado que estava dentro deles. O texto digitado na broa continua na broa. É uma diferença de uma palavra no código e de comportamento em toda a tela.

Um detalhe importante: com a versão de produção do React — a que roda na caixa deste guia —, o aviso não aparece e nada quebra. O bug fica só no comportamento, calado. É por isso que a key é uma daquelas coisas que se aprende antes de precisar: o erro não grita.

7. Key em Fragment e em componentes

Nem toda lista devolve um elemento só por item. Às vezes cada item são dois irmãos, como o nome e o horário de uma encomenda. Aí entra o Fragment, a casca invisível que agrupa irmãos sem criar nó no HTML. E aqui aparece uma pegadinha: a forma curta <>...</> não aceita atributos, então não dá para escrever key nela. Nesse caso, use a forma completa, <Fragment key={...}>.

Cada encomenda virou uma div dentro do dl, o que estraga a estrutura. Troque a div por <Fragment key={p.id}> e deixe só o dt e o dd como filhos do dl.

function App() {
  const pedidos = [
    { id: 1, nome: "Pão francês", hora: "7h" },
    { id: 2, nome: "Broa", hora: "9h" },
    { id: 3, nome: "Bolo de fubá", hora: "14h30" }
  ];

  return (
    <dl className="pedidos">
      {pedidos.map((p) => (
        <div key={p.id} className="pedido">
          <dt>{p.nome}</dt>
          <dd>{p.hora}</dd>
        </div>
      ))}
    </dl>
  );
}

O painel depois da troca mostra três dt e três dd como filhos diretos do dl, sem div nenhuma no meio. E a key continua fazendo o trabalho dela: o Fragment é o elemento que o map devolve, então é nele que a key mora.

Com componentes a regra é a mesma, só muda o lugar: a key vai no componente, dentro da lista, e não dentro do componente. <Pedido key={p.id} nome={p.nome} /> está certo; <Pedido nome={p.nome} /> dentro de um map está errado, mesmo que o componente internamente tenha uma div bem identificada. Quem está na lista é o componente, então é ele que precisa da etiqueta.

8. Praticando com a lista de encomendas

A Ana agora anota as encomendas num array de objetos, cada uma com um número, o nome de quem pediu e a hora da retirada. O número da encomenda é único e nunca muda — é a key natural. Falta montar a lista.

Monte a lista: um <li> por encomenda, com key={e.id}, data-id={e.id} e o texto "cliente — hora". O painel precisa mostrar as três encomendas.

Duas coisas para conferir no resultado. Primeiro, a ordem: o React desenha na ordem do array, e a key não muda isso — key não é ordenação. Segundo, o texto: cada linha tem os dois campos, e o separador está fora das chaves, como texto comum do JSX. Se você escrever {e.cliente} {e.hora} sem o traço, o painel mostra "Dona Cida 14h30" — o JSX não inventa separador nenhum.

Quando a lista estiver certa, troque a ordem do array no editor e rode de novo: as linhas mudam de posição e o React move os nós, sem recriar. É a mesma tela, com a identidade preservada — e é exatamente isso que vai fazer diferença quando cada linha tiver um campo de texto, uma caixa de seleção ou um botão com estado próprio.

9. Cenários do dia a dia

Cenário 1: a lista que só cresce

A lista de avisos do site da Ana só ganha item no fim e nunca perde nenhum. Nesse caso, o índice funciona: a posição de cada aviso nunca muda, então a key é estável por acidente. O problema aparece no dia em que ela resolve apagar um aviso antigo — e aí a lista inteira muda de posição de uma vez. Se o dado tem id, use o id desde o começo; não vale a pena apostar que a lista nunca vai mudar.

Cenário 2: a key com nome repetido

Ela usou key={p.nome} porque era mais curto. Deu certo até o dia em que a padaria passou a vender dois tipos de pão francês, um tradicional e um integral, com o mesmo nome no cadastro. Duas keys iguais na mesma lista fazem o React tratar um item como o outro, e o aviso de key repetida aparece no console. O nome é um dado do produto, não um identificador; o id é.

Cenário 3: a key no lugar errado

Ela colocou key={p.id} no <span> que fica dentro do <li>, e o aviso continuou. O motivo é simples: o elemento que o map devolve é o li, e é ele que está na lista aos olhos do React. A key no filho não vale nada. Na dúvida, olhe a primeira tag depois do => — é ali que a key mora.

Os três cenários têm o mesmo conserto: descobrir qual elemento o map devolve, escolher um valor único e estável vindo do dado, e escrever a key nele. Nenhum deles precisa de biblioteca, de configuração ou de hook: é uma linha.

11. Resumo

Uma lista em React é um array de elementos, e o React precisa saber qual elemento de hoje é o mesmo de ontem. Sem key, ele compara por posição; com key, compara por identidade. A key se escreve no elemento mais externo que o map devolve, tem de ser única entre os irmãos e estável entre um desenho e outro — e o valor natural é o id do dado. Ela não vira atributo no HTML, não chega como prop e não serve para CSS.

O índice do map é a escolha que parece grátis e cobra caro: assim que a lista é filtrada, ordenada ou perde um item do meio, posição deixa de ser identidade e o estado que mora no nó — texto digitado, cursor, caixa marcada, animação — fica no item errado. Como a versão de produção do React não avisa, o sintoma chega como "a tela está maluca", sem mensagem nenhuma. A key é o que transforma esse mistério em uma linha de código.

Vale notar o que a key não resolve: ela não ordena a lista, não filtra, não deixa o desenho mais rápido por si só e não substitui o id. Ela só responde "quem é quem". A ordenação e o filtro são trabalho do seu código, no array, antes do map — e é por isso que a próxima aula, a de renderização condicional, combina tão bem com esta: primeiro você decide o que entra na lista, depois dá identidade a cada item que ficou.

Para lembrar

  • Toda lista feita com map precisa de key em cada item.
  • A key vai no elemento mais externo que o map devolve.
  • Key boa: única entre os irmãos, estável e vinda do dado (p.id).
  • Índice como key só em lista que nunca muda de ordem, tamanho ou filtro.
  • Math.random() e Date.now() como key recriam tudo a cada desenho.
  • A key não aparece no HTML e não chega ao componente como prop.
  • Precisa do id dentro do componente? Passe também id={p.id}.
  • Vários irmãos por item: <Fragment key={...}>, nunca <>.
  • Key em componente: <Pedido key={p.id} /> na lista.
  • Sem key, o React reaproveita o nó pela posição e o estado dele fica no item errado.
