Props Padrão

O botão da Ana tem três aparências: o principal, o secundário e o discreto. Na chamada, ela escreve tipo="secundario" quando precisa, e na maioria das vezes quer o principal. Só que “na maioria das vezes” virou problema: cada página nova ela esquece de escrever o tipo, e o botão sai com a classe botao undefined, sem cor nenhuma. Nesta aula ela aprende a dar um valor de fábrica às props: se ninguém mandar nada, o componente usa o padrão — e o botão volta a ter cor em todas as páginas.

Você vai aprender
  • Como escrever um valor padrão na desestruturação: { tipo = "principal" }.
  • Quando o padrão vale e quando ele é ignorado.
  • A diferença entre undefined, null, texto vazio e zero.
  • Como dar padrão para children e para props de liga e desliga.
  • Por que || estraga o zero e o ?? não.
  • O que fazer quando o padrão esconde um erro de verdade.
  • A forma antiga, defaultProps, que aparece em código de tutorial velho.

1. A cena: o botão sem cor

O componente do botão recebe o tipo por prop e monta a classe assim:

function Botao({ texto, tipo }) {
  return <button className={"botao " + tipo}>{texto}</button>;
}

function App() {
  return <Botao texto="Encomendar" />;
}

Quando a chamada não escreve tipo, a variável dentro do componente vale undefined, a classe sai como botao undefined e o CSS não encontra estilo nenhum. O botão aparece sem cor, sem borda, sem nada — e no painel dá para ver o estrago: o className com a palavra undefined no meio.

Existem três saídas, e vale conhecer as três para escolher. A primeira é obrigar toda chamada a passar o tipo — funciona, mas é frágil: depende de disciplina de quem escreve. A segunda é tratar dentro do componente, com uma decisão: “se não veio tipo, use principal”. A terceira é o assunto desta aula: dar o valor na própria assinatura, junto com a desestruturação, e não pensar mais nisso.

O nome técnico é valor padrão ou default. Você já usou isso em JavaScript sem saber, quando escreveu uma função que reagia bem a argumentos faltando. No React, o lugar natural é a desestruturação do parâmetro, onde o padrão fica visível para quem lê o componente.

2. O padrão é o que entra quando nada chega

A escrita é curta: dois-pontos… não, sinal de igual dentro das chaves. Cada nome da desestruturação pode receber um valor depois do =, e esse valor é usado quando a chave correspondente não veio — ou veio como undefined. Não é uma condição que você escreve: é o JavaScript fazendo o trabalho.

valor padrão
O que a variável recebe quando a chave não existe: { tipo = "principal" }.
undefined
O valor de “não existe”. É o que a desestruturação encontra quando a prop não foi passada — e é a única situação em que o padrão entra.
null
“Vazio de propósito”. Não é undefined, então o padrão não entra: a variável fica null.
falsy
Valores que o JavaScript trata como falso: 0, "", null, undefined, false. Confundir falsy com “não veio” é a origem do bug do zero.
opcional
Prop que pode faltar sem quebrar o componente, porque tem padrão. O contrário de obrigatória.

Dá para fazer a mesma coisa sem o recurso da desestruturação, com uma condição no corpo. Fica assim:

function Botao({ texto, tipo }) {
  const tipoFinal = tipo === undefined ? "principal" : tipo;
  return <button className={"botao " + tipoFinal}>{texto}</button>;
}

Funciona e é mais verboso. Além da linha extra, aparece uma variável nova que você precisa lembrar de usar em todos os lugares — e, no dia em que esquecer em um deles, o bug volta. O padrão na assinatura resolve o mesmo problema sem criar nome nenhum: a variável tipo já existe com o valor certo desde a primeira linha da função.

Guarde a distinção do null, porque ela pega gente experiente. Se a página escreve tipo={null} querendo dizer “sem tipo”, o padrão não entra: a variável fica null, a classe vira botao null e o problema continua. O padrão só cobre o caso de a prop não ter sido mencionada.

3. O padrão na assinatura

Vamos consertar o botão. O componente ganha um valor para o tipo, e a página que não escreve nada passa a receber o principal:

A etiqueta sai sem cor quando a página não passa fundo: a classe vira etiqueta undefined. Dê o valor padrão amber à prop fundo na assinatura.

function Etiqueta({ texto, fundo }) {
  return <span className={"etiqueta " + fundo}>{texto}</span>;
}

function App() {
  return <Etiqueta texto="Novo" />;
}
<span class="etiqueta undefined">Novo</span>

function Etiqueta({ texto, fundo = "amber" }) {
  return <span className={"etiqueta " + fundo}>{texto}</span>;
}

function App() {
  return <Etiqueta texto="Novo" />;
}

Uma linha, e o componente passou a funcionar sem que a página soubesse de nada. Quem chama continua podendo escolher outra cor — fundo="red" vence o padrão —, e quem não escolhe ganha o âmbar. A missão confere o atributo class, e não o texto: é assim que se prova que a cor veio do padrão e não de um acaso.

Repare no lugar do padrão: junto do nome, na assinatura, e não no corpo da função. Essa escolha tem duas consequências boas. Primeira, o padrão fica visível para quem lê o componente — não é preciso procurar uma condição três linhas abaixo. Segunda, ele vale para todos os usos da variável, inclusive os que aparecem antes do return, como um console.log.

4. Quando o padrão vale

A regra é uma só, e a tabela mostra os casos que aparecem no dia a dia. O padrão entra quando o valor é undefined; qualquer outro valor, inclusive os “vazios”, passa direto. Entender isso evita duas horas de depuração.

A última linha explica um comportamento que parece mágica: passar undefined de propósito é igual a não passar nada. Faz sentido quando você lembra de onde vem o valor: um objeto que veio de outro lugar pode ter a chave com valor undefined, e o JavaScript trata isso como ausente.

Na prática, o caso do null aparece quando o dado vem de outro lugar: uma função que devolve null para “não encontrei”, um campo de formulário vazio que virou null no meio do caminho. Se o componente monta classe de CSS com esse valor, o resultado é uma classe chamada null — e aí o problema não é o padrão, é a origem do dado. Tratar isso é assunto de condição, na aula de renderização condicional.

Já as linhas do null e do texto vazio mostram por que “vazio” não é uma ideia só. Para o JavaScript, são valores como qualquer outro, e a desestruturação não tem opinião sobre eles. Se você quer que texto vazio conte como ausente, precisa dizer isso com uma condição — e a seção 6 mostra a ferramenta certa para cada caso.

5. Padrão para children e para liga e desliga

children também aceita padrão, e o resultado é uma tela de “nada por aqui” quando a página não manda conteúdo. É um recurso honesto: em vez de um espaço em branco sem explicação, o leitor vê uma frase que diz o que aconteceu.

O aviso está sendo usado sem conteúdo e fica vazio. Dê o padrão Nada por aqui ao children, para o espaço não ficar em branco.

function Aviso({ children }) {
  return <div className="aviso">{children}</div>;
}

function App() {
  return <Aviso />;
}
<div class="aviso"></div>

function Aviso({ children = "Nada por aqui" }) {
  return <div className="aviso">{children}</div>;
}

function App() {
  return <Aviso />;
}

A mesma escrita serve para prop de liga e desliga. Um botão que muda de aparência quando está destacado pode ter { destaque = false } e você só escreve destaque quando quer ligar. Sem o padrão, destaque valeria undefined — que em condição funciona como falso, mas aparece em texto e em atributo com a palavra feia, como você já viu na classe do botão.

Padrão em children tem um efeito colateral bom: documenta o que o componente faz quando está vazio. Quem lê a assinatura entende que o aviso pode vir sem recado, e que nesse caso mostra uma frase padrão. É uma decisão de desenho escrita no código, e não uma surpresa descoberta em produção.

6. O zero e o texto vazio

Existe uma forma mais antiga de dar padrão, e ela é a origem de um bug clássico: o || (ou). A ideia é “se o valor for falso, use o padrão”, e o problema é que zero e texto vazio são falsos. Uma quantidade zero vira três; um desconto de 0% vira o desconto padrão.

A sacola recebe quantidade={0} e mostra 3, porque o || trata o zero como ausente. Troque por ??, que só substitui null e undefined.

function Sacola({ quantidade }) {
  const qtd = quantidade || 3;
  return <p>{qtd} pães</p>;
}

function App() {
  return <Sacola quantidade={0} />;
}
<p>3 pães</p>

function Sacola({ quantidade }) {
  const qtd = quantidade ?? 3;
  return <p>{qtd} pães</p>;
}

function App() {
  return <Sacola quantidade={0} />;
}

O ?? é o “ou” dos nulos: substitui apenas null e undefined, que são os valores de “não tem”. Zero, texto vazio e falso passam intactos. A tabela compara os três jeitos, e ela vale como consulta: escolha a linha pelo que você quer que aconteça com o zero.

Como você escreveuValor 0Texto vazionullNão passou

Dá para ler a tabela em três frases. O padrão na assinatura só age quando a prop não vem. O || age em tudo que é falso, e por isso é perigoso com número. O ?? age no que é nulo, e é o que você quer quando zero e vazio são valores legítimos. Para a maioria dos casos desta aula, o padrão na assinatura resolve; o ?? entra quando o valor pode ser calculado antes de mostrar.

Uma dica de leitura de código alheio: quando você vir props.cor || "azul", desconfie. Em texto quase sempre funciona, porque texto vazio raramente é intenção. Em número, é bug esperando a primeira quantidade zero.

7. Vários padrões e a ordem dos parâmetros

Um componente pode ter quantos padrões precisar, e eles convivem na mesma lista. A ordem não importa para o JavaScript, mas importa para quem lê: o costume é deixar as obrigatórias primeiro e as com padrão depois.

function Botao({ texto, tipo = "principal", largura = "normal" }) {
  return (
    <button className={"botao " + tipo + " botao-" + largura}>
      {texto}
    </button>
  );
}

Aqui texto é obrigatória — sem ela o botão fica vazio, e um padrão como “Botão” só esconderia o esquecimento. Já tipo e largura têm escolhas sensatas de fábrica, e a página só fala delas quando quer outra coisa. Essa é a pergunta que decide se uma prop merece padrão: existe um valor que serve na maioria das chamadas?

Quando o mesmo padrão aparece em vários componentes — a cor da marca, por exemplo —, vale guardá-lo numa constante e usar a constante na assinatura: { cor = COR_MARCA }. Assim, mudar a cor de todos os padrões é mudar uma linha, e quem lê o componente vê que aquilo não é um valor qualquer, é uma escolha do projeto. Vale para texto, número e qualquer valor que você queira repetir sem repetir a letra.

Se a resposta for não, não invente padrão. Um componente de cartão de pão não tem “nome padrão”: o nome é o motivo de ele existir. Dar nome = "Pão" faria o cartão mostrar um pão inventado quando a página esquecesse o dado, e um dado errado é pior do que um espaço vazio — porque ninguém percebe. Padrão é para escolha de estilo, nunca para tapar falta de dado.

8. Tropeços de quem dá padrão

Os erros desta aula são mais sutis que os das anteriores, porque o código funciona — só funciona errado. Um padrão no lugar de um dado obrigatório esconde o problema; um || troca zero por três; um null passa por cima do padrão. A tabela reúne os casos.

A quinta linha merece um parágrafo, porque ela aparece em tutorial de 2020. Antes da desestruturação virar moda, dava-se padrão pendurando um objeto no componente: Botao.defaultProps = { tipo: "principal" }. Isso ainda funciona no React 19, mas é um estilo que a documentação atual não usa: o padrão fica fora da função, longe de quem lê, e some quando você converte o componente para outra forma. Se você encontrar num projeto antigo, entenda e siga; em código novo, use a assinatura.

Um cuidado com padrão de objeto. Escrever { pao = { nome: "Pão do dia" } } funciona, mas o objeto é criado de novo a cada vez que o componente roda — o que é bom, porque ninguém compartilha um objeto que não devia. O que não funciona é tentar mudar esse objeto esperando que a mudança fique: a próxima execução cria outro, novinho. Para dado que muda, existe estado; para dado que só preenche espaço, o padrão basta.

console: cor: undefined

Essa linha é o retrato do “antes”: a página não passou a prop, o componente imprimiu o valor e saiu undefined — a palavra que aparece na classe e no texto quando ninguém tratou o caso. Depois do padrão, a mesma linha passa a imprimir o valor escolhido:

console: cor: amber

Duas linhas, uma diferença de uma palavra, e a tela inteira muda. É um bom hábito colocar esse console.log quando estiver decidindo o padrão de um componente: você vê o valor que chega antes de escolher o que fazer com ele.

9. Cenários do dia a dia

Cenário 1: o botão de todas as páginas

O botão principal da padaria aparecia em cinco páginas, e em três delas a Ana esqueceu o tipo. O resultado era um botão sem cor, que ela atribuía ao CSS. Depois do tipo = "principal" na assinatura, as cinco páginas passaram a mostrar o botão certo sem nenhuma edição nelas — só no componente.

Cenário 2: a sacola que cobrava três pães

Uma cliente escolheu zero pães de um item e o resumo mostrou três, porque a conta usava ||. O zero era um valor de verdade e foi tratado como ausência. Trocado por ??, o resumo passou a respeitar o zero. É o tipo de bug que só aparece com dado real.

Cenário 3: o padrão que escondeu o erro

Ela deu nome = "Pão do dia" ao cartão para “nunca ficar vazio”. Semanas depois, uma página com um erro de digitação na prop passou a mostrar “Pão do dia” em vez do brioche, e ninguém desconfiou. O conserto foi tirar o padrão do dado e deixar o cartão em branco quando falta informação — vazio incomoda, e incomodar é bom quando o dado é obrigatório.

Quando o componente recebe uma lista em vez de um valor — os pães da vitrine, por exemplo —, o padrão vira uma lista vazia: { paes = [] }. É o mesmo raciocínio, aplicado a um dado que será percorrido com map em Listas com map.

Os três cenários ensinam a mesma distinção: padrão é para escolha de estilo — o tipo do botão, a largura, a cor de uma etiqueta. Dado obrigatório não tem padrão; tem validação. Quando você mistura as duas coisas, o componente parece mais robusto e fica mais difícil de consertar, porque o erro deixa de aparecer na tela.

O componente Botao recebe texto e largura. Dê à largura o padrão "normal" e depois responda: qual é o operador que separa o nome do valor padrão?

function Botao({ texto, largura "normal" }) { return <button className={"botao botao-" + largura}>{texto}</button>; }

Dica: dentro da desestruturação, o padrão entra com o mesmo sinal que você usa para guardar um valor numa variável. Não é dois-pontos — dois-pontos serve para renomear.

11. Resumo

Prop padrão é o valor que entra quando a prop não chega. Escreve-se na desestruturação, junto do nome: { tipo = "principal" }. O padrão vale só para undefined — null, texto vazio, zero e falso passam direto e continuam sendo o valor.

Use padrão para escolhas de estilo, não para tapar dado obrigatório. Para valores calculados, prefira ?? ao ||: o primeiro só troca nulo e indefinido, o segundo troca também zero e texto vazio. E deixe o padrão na assinatura, onde ele é visível — a forma antiga com defaultProps funciona, mas esconde a informação fora da função.

Para lembrar

  • { cor = "amber" } é a escrita do padrão na desestruturação.
  • O padrão entra quando a prop não veio ou veio undefined.
  • null, "", 0 e false ignoram o padrão.
  • children também aceita: { children = "Nada por aqui" }.
  • Liga e desliga: { destaque = false }.
  • || troca zero e vazio; ?? só troca nulo e indefinido.
  • Não dê padrão a dado obrigatório: o erro precisa aparecer.
  • defaultProps é estilo antigo; na assinatura o padrão fica visível.
