O useMemo

A lista de pães da Ana cresceu: são 240 itens, cada um com nome, preço e tipo. O campo de busca filtra essa lista a cada tecla, e no notebook velho do balcão a digitação começou a engasgar — a letra aparece com atraso, o cursor pula. O culpado não é o filtro: é o fato de ele rodar de novo em todo desenho da tela, inclusive quando a Ana só troca o aviso do dia. Nesta aula ela conhece o useMemo, a ferramenta que guarda o resultado de um cálculo entre um desenho e outro — e aprende também quando ele é perda de tempo.

Você vai aprender
  • Por que um cálculo no corpo do componente roda em todo render.
  • Como o useMemo guarda o resultado entre renders.
  • O que o array de dependências faz e quando o cache é jogado fora.
  • Como a identidade de um array muda o comportamento de um filho com memo.
  • Como reconhecer um cálculo caro — e um barato disfarçado.
  • Quando não usar useMemo.
  • As regras: função pura, dependências completas e nada de efeito colateral.

1. A cena: a busca que engasga

O componente da Ana é simples: um campo de busca, um aviso do dia e a lista filtrada. A cada tecla, o React chama a função do componente, ela filtra os 240 pães e devolve o JSX. Enquanto a lista era de seis pães, ninguém notou. Com 240, cada tecla custa uma varredura completa — e a Ana ainda tem um segundo estado, o aviso do dia, que também provoca renders.

O sintoma que a fez procurar ajuda foi outro: quando ela clicava em "trocar o aviso", a lista piscava. Nada na lista tinha mudado. O que aconteceu é que o componente inteiro rodou de novo e o filtro foi refeito do zero, à toa, porque o React não tem como saber que aquele cálculo depende só da busca.

A ideia do useMemo é essa: dizer ao React "este resultado só muda quando estas coisas mudarem; se elas estão iguais, reaproveite o resultado anterior". Não é mágica nem cache automático; é você apontando a dependência e o React guardando o valor entre um render e outro.

2. O cálculo que roda em todo render

Todo código que está no corpo do componente roda a cada render. Isso não é detalhe: é o modelo. O React chama a função para saber o que desenhar, e a função precisa ser capaz de produzir o desenho do zero, sempre. Um filtro, uma soma, uma ordenação — tudo isso acontece de novo, mesmo que os dados sejam os mesmos.

function ListaDePaes() {
  const [busca, setBusca] = useState("");
  const [aviso, setAviso] = useState("Padaria aberta");

  const lista = PAES.filter((pao) =>
    pao.nome.toLowerCase().includes(busca.toLowerCase())
  );

  return (
    <div>
      <input value={busca} onChange={(e) => setBusca(e.target.value)} />
      <button onClick={() => setAviso("Forno quente")}>Trocar aviso</button>
      <p>{aviso}</p>
      <p>{lista.length} pães encontrados</p>
    </div>
  );
}

Quando a pessoa digita, faz sentido filtrar: a busca mudou, o resultado muda. Quando ela troca o aviso, o filtro roda igual — e o resultado é exatamente o mesmo da última vez. Esse é o desperdício que o useMemo corta.

Antes de seguir, uma pergunta obrigatória: esse cálculo é caro? Filtrar 240 itens com includes leva microssegundos num notebook moderno; num celular antigo, talvez um milissegundo. Ninguém sente. O engasgo que a Ana viu vinha mais do tamanho da lista desenhada do que do filtro. Mas o raciocínio vale para qualquer conta — e a aula precisa de um exemplo visível, então vamos contar quantas vezes o cálculo rodou.

cálculo
A conta que transforma dados em outro dado: filtrar, somar, ordenar, formatar. Não desenha nada por si só.
useMemo
O hook que guarda o resultado de um cálculo entre renders e devolve o mesmo valor enquanto as dependências não mudam.
dependências
O array que diz quando o cache vale. É comparado item por item com o da renderização anterior.
identidade
Ser o mesmo objeto, não um igual. Dois arrays com os mesmos itens são diferentes; o mesmo array, guardado, é igual a si mesmo.
cache
O valor guardado da última execução. O React pode descartá-lo; ele é otimização, não garantia.

O useMemo recebe uma função e um array, e devolve o valor que a função produziu:

const lista = useMemo(
  () => PAES.filter((pao) => pao.nome.includes(busca)),
  [busca]
);

Na primeira renderização, o React chama a função e guarda o resultado. Nas seguintes, ele compara o array: se busca continua igual, devolve o resultado guardado sem chamar a função. Se busca mudou, chama de novo e guarda o novo resultado. É um cache com prazo de validade definido por você.

3. O cache visto por dentro

Para enxergar o cache, a caixa abaixo conta quantas vezes o filtro rodou numa variável fora do componente. O contador é um truque de aula: em código de verdade ninguém conta isso em produção, mas ele torna visível um comportamento que normalmente é invisível.

O filtro roda a cada render, inclusive quando só o aviso muda. Envolva a chamada de filtrar(busca) num useMemo com dependência [busca]: depois de trocar o aviso, o painel tem de mostrar cálculos: 1.

const PAES = ["pão francês", "pão de queijo", "sonho", "croissant", "baguete", "rosca"];

  calculos = calculos + 1;

No código inicial, clique em Trocar aviso: o aviso muda e o contador vai para 2, porque o componente rodou de novo e o filtro junto. Na solução, o aviso muda, o componente roda, mas o contador continua em 1 — a busca não mudou, então o React devolveu o array guardado. Agora digite no campo: o contador sobe, porque aí a dependência mudou de verdade.

Esse é o comportamento inteiro do useMemo. O que muda de um caso para outro é só o que entra no array de dependências — e é aí que mora o perigo.

4. O array de dependências

O array não é uma lista de "coisas que eu quero observar"; é a lista completa de tudo que o cálculo lê de dentro do componente. Se o cálculo usa busca e tipo, os dois precisam estar ali. Se falta um, o React pode devolver um resultado calculado com o valor antigo — e a tela mostra dados errados, sem erro nenhum no console.

ArrayQuando o cálculo rodaUse quando
[]uma vez, na montagemo cálculo não lê nada que mude
[busca]na montagem e quando busca mudaum valor só manda no resultado
[busca, tipo]quando qualquer um dos dois mudao resultado depende de mais de um valor
objeto ou array criado no renderem todo rendernunca: o valor é novo a cada desenho
função criada no renderem todo rendernunca; para funções existe o useCallback

A comparação é de identidade, não de conteúdo: o React usa Object.is em cada item. Números, textos e booleanos são comparados pelo valor, e por isso são as dependências tranquilas. Objetos, arrays e funções criados no corpo do componente são novos a cada render — e uma dependência "nova" a cada render anula o cache por completo. A aula de dependências mostra esse mecanismo em detalhe; aqui ele volta porque é a causa número um de useMemo que não funciona.

Veja o erro na prática: a lista abaixo guarda o resultado com [], então ela é calculada uma vez e nunca mais. Digitar no campo não muda nada na tela — o famoso valor velho, ou stale value.

O useMemo tem o array vazio, então a lista nunca acompanha a busca. Coloque busca nas dependências e digite queijo: a lista tem de ficar com um pão só.

const PAES = ["pão francês", "pão de queijo", "sonho", "croissant", "baguete", "rosca"];

function App() {

Com [], digitar "queijo" não muda a lista: o painel continua mostrando os seis pães e a contagem 6, porque o resultado guardado nunca é recalculado. Com [busca], a lista vira um item e o texto acompanha. O console do navegador não avisa nada nesse caso — o valor só está errado. Quem avisa é o ESLint do projeto:

React Hook useMemo has a missing dependency: 'busca'.
Either include it or remove the dependency array.
  react-hooks/exhaustive-deps

A tradução é literal: "o seu useMemo usa busca e o array não lista busca". A regra do ESLint é a mesma que você viu para o useEffect, e a resposta quase sempre é incluir a dependência. Se incluir criar um laço, o problema é outro — provavelmente um objeto recriado a cada render, que a próxima seção resolve.

5. Identidade: o array que precisa ser o mesmo

Existe um segundo motivo para usar useMemo, e ele não tem nada a ver com velocidade. É a identidade. Um array criado no corpo do componente é um array novo a cada render, mesmo que os itens sejam idênticos. Para o React, "novo" quer dizer "mudou" — e um componente filho embrulhado em memo redesenha à toa por causa disso.

O memo compara as props com Object.is. Se o pai passa sempre um array novo, a comparação falha em todo render e o filho desenha de novo. Com useMemo, o pai passa o mesmo array enquanto o filtro não muda, e o memo finalmente tem o que comparar.

const Lista = memo(function Lista({ itens }) {
  return <p>{itens.length} pães na lista</p>;
});

function App() {
  const [filtro, setFiltro] = useState("todos");
  const [aviso, setAviso] = useState("Padaria aberta");

  const itens = useMemo(
    () => PAES.filter((pao) => filtro === "todos" || pao.tipo === filtro),
    [filtro]
  );

  return (
    <div>
      <p>{aviso}</p>
      <Lista itens={itens} />
    </div>
  );
}

Aqui o useMemo não economiza uma conta pesada: ele garante que itens seja o mesmo array entre renders em que o filtro não mudou. É um uso legítimo e comum. A caixa abaixo mostra isso acontecendo com um contador de desenhos no filho.

O filho está embrulhado em memo, mas o pai entrega um array novo a cada render. Envolva o filtro num useMemo com dependência [filtro]: depois de trocar o aviso, o filho tem de continuar em desenho 1.

Sem o useMemo, o clique em Trocar aviso redesenha o pai, cria um array novo e o memo do filho compara: array novo, props diferentes, filho desenha de novo — o contador vai para 2. Com o useMemo, o array é o mesmo, o memo percebe que as props não mudaram e o filho fica em 1. O mesmo raciocínio vale para efeitos: um array novo no array de dependências de um useEffect faz o efeito rodar em todo render.

Repare que o memo no filho é metade da solução. Se o filho não estivesse embrulhado, ele desenharia de qualquer jeito, e o useMemo só teria economizado a conta do filtro. As duas peças trabalham juntas: o pai segura a identidade, o filho evita o trabalho.

6. O que o useMemo não faz

Três confusões aparecem sempre. A primeira: useMemo não impede o componente de rodar. Ele é chamado dentro do componente, depois que o componente já foi chamado. O que ele evita é a conta, não o render.

A segunda: useMemo não é garantia. A documentação do React diz que o cache pode ser descartado — por exemplo, quando a memória aperta ou quando o React precisa jogar fora o estado de uma tela que saiu de vista. Se o seu código depende de o valor ser sempre o mesmo objeto para funcionar (e não só para ficar rápido), o lugar certo é um estado, uma ref ou um dado fora do componente. Otimização não é regra de negócio.

A terceira: useMemo não conserta laço infinito. Se um efeito roda sem parar por causa de um objeto recriado, colocar o objeto num useMemo resolve o sintoma, mas a pergunta anterior continua valendo — aquele efeito precisava existir? A aula de quando não usar efeito é sobre isso.

Vale saber também que o React 19 vem com o compilador, que faz esse tipo de memoização automática em muitos casos. Isso não torna o useMemo inútil: ele continua sendo a forma explícita de dizer "este valor pode ser reaproveitado", e continua aparecendo em código escrito à mão. O que muda é a expectativa: você não precisa memoizar tudo por medo. Precisa entender quando faz diferença.

7. Quando não vale a pena

A recomendação oficial é medir antes de otimizar, e ela existe porque o useMemo tem custo: um array novo, uma comparação, uma entrada a mais na memória do React e uma camada de leitura a mais para quem mantém o código. Em cálculos baratos, esse custo é maior que a economia.

Se você não sabe se o cálculo é caro, meça. Abra o DevTools na aba Performance, grave enquanto digita e olhe o tempo de cada render. Um jeito mais simples: coloque um console.time em volta da conta e leia o resultado no console.

No console, o tempo de cada execução aparece com o rótulo que você deu:

A primeira linha é uma lista pequena; a segunda, uma lista grande com formatação no meio. Números como 0,4 ms não justificam useMemo nenhum — quem sente 0,4 ms é o cronômetro, não a pessoa. Acima de alguns milissegundos por tecla, a conversa muda.

8. As regras do useMemo

A função tem que ser pura. Ela recebe dados e devolve um valor; não muda estado, não chama setAlgo, não escreve no banco, não faz console.log de efeito. O React pode chamar essa função mais de uma vez (em desenvolvimento, por exemplo) e o resultado tem que ser sempre o mesmo. Efeito colateral dentro de useMemo é bomba-relógio.

Liste tudo o que a função lê. Não só as props e o estado: qualquer valor de fora que participe da conta. O ESLint ajuda, mas ele não adivinha tudo — valores lidos de um módulo externo, por exemplo, não entram na conta dele.

Não chame hooks dentro do useMemo. Hooks seguem a ordem das chamadas no componente; dentro de uma função que pode ou não rodar, essa ordem quebra. O React reclama na hora, e a regra é a mesma de qualquer callback.

Não guarde estado dentro do useMemo. Ele não tem setter e não avisa ninguém: é cache de cálculo, não memória mutável. Para memória mutável, a aula de useRef; para valor que a tela mostra, useState.

Não memoize o que você vai usar uma vez. Criar um objeto dentro do useMemo para passá-lo a uma função que o consome na mesma linha é trabalho puro. O cache só vale quando o valor atravessa renders.

9. Cenários do dia a dia

Cenário 1: o useMemo que não memorizava nada

A Ana colocou o array de dependências com um objeto criado ali mesmo: [{ termo: busca }]. Como o objeto é novo a cada render, o React concluía que a dependência mudou e recalculava sempre — o useMemo existia e não servia para nada. O conserto é listar os valores simples: [busca].

Cenário 2: a lista que ficou velha

Ela colocou [] nas dependências para "rodar uma vez só" e a busca parou de filtrar. Sem erro, sem aviso: só resultado errado. Array de dependências incompleto é o bug mais silencioso do useMemo e do useEffect, e a defesa é a mesma nos dois: listar tudo o que a função lê.

Cenário 3: o filho que redesenha sem motivo

O filho tinha memo e mesmo assim redesenhava a cada tecla. O pai passava um array criado no render, então as props eram sempre diferentes por identidade. Com useMemo no pai, o array passou a ser o mesmo enquanto o filtro não mudava, e o memo começou a funcionar. Note: um problema de identidade, não de velocidade.

Exercício: o cache certo para a busca

O filtro abaixo precisa ser recalculado sempre que busca mudar. Complete o array de dependências:

const lista = useMemo(() => filtrar(busca), []);

Dica: é exatamente o valor que a função de dentro do useMemo lê. Sem ele, o resultado fica velho e a lista para de acompanhar a digitação.

11. Resumo

Todo cálculo escrito no corpo do componente roda em todo render, porque o React chama a função de novo para saber o que desenhar. O useMemo guarda o resultado desse cálculo e devolve o mesmo valor enquanto as dependências não mudam. A função é pura, o array lista tudo o que ela lê, e a comparação é de identidade: números e textos são comparados pelo valor; objetos, arrays e funções criados no render são sempre novos.

Há dois motivos legítimos para usar: economizar uma conta caro e manter a identidade de um array ou objeto. O segundo é mais comum do que parece — é ele que faz o memo de um filho valer alguma coisa e que evita um efeito rodando em todo render. E há um motivo ilegítimo: "colocar useMemo em tudo por segurança". Em cálculo barato, o custo do hook é maior que a economia, e o código fica mais difícil de ler.

Antes de memoizar, meça. Depois de memoizar, confira as dependências. E se o valor precisa aparecer na tela e mudar com o clique, ele não é assunto do useMemo: é estado. O próximo hook da fila, o useCallback, é a mesma ideia aplicada a funções.

Para lembrar

  • O corpo do componente roda em todo render; o cálculo junto.
  • useMemo(() => conta, [deps]) guarda o resultado até as dependências mudarem.
  • Array vazio: calcula uma vez e pode ficar velho.
  • Dependência faltando: valor errado, sem erro no console.
  • A comparação é por identidade; objeto criado no render é sempre novo.
  • O segundo uso é manter a identidade para memo e para efeitos.
  • useMemo não impede render: ele evita a conta.
  • O React pode jogar o cache fora; não dependa dele para funcionar.
  • A função tem que ser pura: nada de efeito colateral ali dentro.
  • Cálculo barato não se memoiza; meça antes de otimizar.
