Publicando

O site da Ana funciona no notebook dela: npm run dev, a página abre em localhost:5173 e tudo roda. O problema é que cliente não entra no notebook dela. Para mandar o link no grupo da padaria, o site precisa morar num computador que responda na internet. Nesta aula a Ana leva o dist/ até um host de verdade, acerta o endereço, resolve os 404 de quem recarrega a página e confere tudo com calma antes de avisar a primeira cliente.

Você vai aprender
  • O que exatamente sobe para o servidor — e o que nunca sobe.
  • As três opções de lugar para publicar e a diferença entre elas.
  • Por que o base quebra todas as imagens quando o site fica numa subpasta.
  • A regra de rewrite que evita o 404 ao recarregar uma rota.
  • O que é conteúdo misto e por que o navegador bloqueia.
  • Por que nada no bundle é segredo.
  • Cache, versões e como voltar atrás em um minuto.
  • O roteiro de conferência depois de cada publicação.

1. A cena: o site que só existe no notebook

Há um mês a Ana roda o projeto com npm run dev. O comando sobe um servidor de desenvolvimento que entrega a página, observa os arquivos e recarrega o navegador a cada alteração. É ótimo para trabalhar e péssimo para mostrar: aquele servidor só escuta o próprio computador, some quando ela fecha o terminal e não tem endereço público.

Publicar é mudar de pergunta. Em vez de "como faço o site rodar na minha máquina?", passa a ser "como faço um computador na internet entregar estes arquivos para qualquer pessoa?". A resposta é mais simples do que parece: o site é um punhado de arquivos estáticos, e alguém precisa servi-los por HTTP.

Na aula de build de produção a Ana gerou o dist/: um index.html pequeno, um JavaScript grande já minificado e otimizado, o CSS e as imagens. Nada daquilo precisa de Node para rodar — é HTML, CSS e JavaScript comuns. O que falta é um lugar para morar.

2. O que sobe: o conteúdo de dist

Sobe o conteúdo de dist/, não o projeto. O src/ com os arquivos .jsx, o package.json e o node_modules ficam no notebook. O navegador não sabe o que é JSX: quem transforma o JSX em JavaScript é o build, e o resultado é o que o host serve.

Como o site é só arquivos, o servidor pode ser bem bobo. Ele recebe um caminho (/assets/index-9f2c.js), procura o arquivo e devolve com o tipo certo. Não há banco de dados nem código de servidor envolvido — e é justamente por isso que publicar React é fácil e barato.

As três opções servem para a padaria. A diferença está em quem cuida das três configurações que vêm a seguir — endereço, rewrite e HTTPS —, e é sobre elas que a aula trata. O lugar é o de menos; o que quebra o site é a configuração.

dist
A pasta que o build gera: o site pronto para ser servido, com index.html e assets/.
host estático
Serviço que só entrega arquivos por HTTP, sem executar código no servidor. Não sabe o que é React — o que é uma vantagem.
domínio
O nome que as pessoas digitam (loja.test), apontado para o endereço do host por um registro DNS.
base
O prefixo do endereço em que o site vai morar. / para a raiz, /padaria/ para uma subpasta. Entra na configuração do build.
rewrite
A regra do host que devolve o index.html para caminhos que não são arquivos. Sem ela, recarregar uma rota dá 404.
HTTPS
O HTTP com criptografia. Hoje é padrão: sem ele o navegador avisa "não seguro" e várias APIs se recusam a responder.

3. O endereço do site e o base

O primeiro detalhe que pega todo mundo é onde o site fica. Na raiz do domínio (https://loja.test/) não há prefixo nenhum. Numa subpasta (https://loja.test/padaria/), todo arquivo precisa ser pedido com o prefixo: /padaria/assets/index-9f2c.js.

Quem escreve esses caminhos é o build. No Vite, a configuração se chama base e vale "/" por padrão. Se você publica numa subpasta e esquece de mudar, o index.html pede /assets/..., o host não tem esse arquivo na raiz e o navegador recebe 404 em tudo. O sintoma é uma tela branca com o console cheio.

O site vai morar em https://loja.test/padaria/, mas o base ainda é a raiz. Ajuste o prefixo para que o link do cardápio aponte para /padaria/assets/cardapio.pdf.

Uma barra no fim faz diferença: "/padaria" e "/padaria/" produzem caminhos diferentes quando grudados num nome de arquivo. A convenção é sempre terminar com barra. No projeto de verdade, isso não fica numa constante do componente: fica no vite.config.js, e o Vite reescreve os caminhos do index.html e das importações de CSS e imagem por você.

GET https://loja.test/assets/index-9f2c.js 404 (Not Found)
Failed to load module script: Expected a JavaScript module script but the server responded with a MIME type of "text/html".

A segunda linha confunde porque fala de tipo, não de arquivo ausente: quando o host não acha o JavaScript, ele devolve o index.html (a página de erro amigável), e o navegador recebe HTML onde esperava script. Sempre que você vir essa mensagem, desconfie do caminho — quase sempre é o base.

4. As rotas que o servidor não conhece

O segundo tropeço aparece na primeira vez que alguém recarrega uma página interna. O site construído tem um index.html; as "páginas" são desenhadas pelo React depois que o JavaScript roda. Para o host, /pedido/3 é um caminho que não existe no disco.

Resultado: a cliente clica em "Pedidos", navega sem problema, e no dia seguinte abre o link salvo e recebe 404. O servidor não sabe que aquele caminho é uma página do aplicativo. A solução é uma regra chamada rewrite (ou fallback): se o caminho não corresponde a um arquivo de verdade, entregue o index.html e deixe o React decidir o que desenhar.

O host devolve 404 para /pedido/3 ao recarregar, mas não pode devolver index.html para o JavaScript. Escreva a regra: arquivo existente é servido; o resto cai no index.html.

function servidor(caminho) {
  if (caminho === "/" || caminho === "/index.html") return "index.html";
  return "404.html";
}

function App() {
  const caminhos = ["/", "/pedido/3", "/assets/app.js"];

  return (
    <div>
      <h1>O que o host devolve</h1>
      <ul>
        {caminhos.map((c) => (
          <li key={c}>{c + " → " + servidor(c)}</li>
        ))}
      </ul>
    </div>
  );
}
<div>
  <h1>O que o host devolve</h1>
  <ul>

    <li>/pedido/3 → 404.html</li>

function servidor(caminho) {
  if (caminho.startsWith("/assets/")) return caminho.slice(1);
  return "index.html";
}

function App() {
  const caminhos = ["/", "/pedido/3", "/assets/app.js"];

  return (
    <div>
      <h1>O que o host devolve</h1>
      <ul>
        {caminhos.map((c) => (
          <li key={c}>{c + " → " + servidor(c)}</li>
        ))}
      </ul>
    </div>
  );
}

A ordem das condições é a regra inteira: primeiro os arquivos (e as pastas de arquivos, como /assets/), depois o fallback. Quem inverte isso entrega HTML no lugar de JavaScript e cai justamente na mensagem de tipo da seção anterior.

No nginx a regra se chama try_files $uri $uri/ /index.html;. No Netlify, uma linha no arquivo de configuração: /* /index.html 200. No GitHub Pages não existe rewrite — e é por isso que ele combina com rotas por hash, em que o caminho depois do # nunca chega ao servidor. As duas soluções resolvem o mesmo problema; escolha conforme o host.

5. HTTPS e o conteúdo misto

Hoje o navegador trata HTTP sem criptografia como site suspeito: mostra "não seguro" na barra e, em alguns recursos, nem deixa funcionar. Câmera, microfone, área de transferência e service workers exigem um contexto seguro. Publicar sem HTTPS, em 2026, é publicar com um aviso vermelho no rosto do cliente.

O problema clássico é a mistura: a página vem por HTTPS e um recurso vem por HTTP. O navegador bloqueia o recurso — e a página funciona pela metade. Acontece com uma imagem do cardápio hospedada em outro servidor, com a chamada de uma API antiga e com o script de um serviço de mapa.

A página é servida por HTTPS, mas o cardápio é pedido por HTTP e o navegador bloqueia. Troque o endereço do cardápio para HTTPS. A missão clica em Carregar e confere que os itens aparecem.

function carregarCardapio(url) {
  if (!url.startsWith("https://")) {
    return Promise.reject(new Error("bloqueado: conteúdo misto"));
  }
  return Promise.resolve(["Pão francês", "Broa de milho"]);
}

function App() {
  const [itens, setItens] = useState([]);
  const [erro, setErro] = useState("");

  function carregar() {
    setErro("");
    carregarCardapio("http://192.0.2.10/cardapio.json")
      .then(setItens)
      .catch((e) => setErro(e.message));
  }

  return (
    <div>
      <button onClick={carregar}>Carregar cardápio</button>
      {erro && <p>Erro: {erro}</p>}
      <ul>
        {itens.map((i) => (
          <li key={i}>{i}</li>
        ))}
      </ul>
    </div>
  );
}

A troca é de uma letra, e o erro que o navegador dá no console é bem explícito:

Mixed Content: The page at 'https://loja.test/padaria/' was loaded over HTTPS, but requested an insecure
resource 'http://192.0.2.10/cardapio.json'. This request has been blocked.

Se o outro servidor ainda não tem HTTPS, a saída não é voltar atrás: é usar o certificado gratuito (Let's Encrypt ou o do próprio host) ou passar por um intermediário que já fale HTTPS. Em último caso, hospede a imagem ou o JSON no mesmo domínio do site.

6. O que é público: segredos e configuração

Aqui vai o aviso mais importante da aula. Tudo que entra no bundle é público: o JavaScript vai para o navegador do cliente, e qualquer pessoa abre o DevTools e lê. Variáveis de ambiente do front não escondem nada — elas são substituídas por texto no momento do build.

Então: chave de API paga, senha de banco, token de administração — nada disso pode estar no src/. O padrão é o inverso: o front chama uma API sua, e é a API que fala com o banco e guarda os segredos. Se o site precisa de uma função pequena no servidor, os hosts modernos oferecem funções serverless, e uma VPS já tem Node disponível.

A configuração legítima é outra coisa: o endereço da API, o nome da padaria, um flag de homologação. Esses valores podem ser públicos, e o build os injeta com import.meta.env — a aula de variáveis de ambiente mostra o arquivo e o prefixo que o Vite exige. A armadilha é acreditar que mudar o .env no servidor muda o site publicado: não muda. O valor foi assado no build; para trocar, build e publicação de novo.

7. Publicar de novo: cache, versões e rollback

Publicar não é um evento único. A Ana muda um preço, roda o build, envia os arquivos — e a cliente jura que o preço antigo continua na tela. É cache: o navegador guardou o JavaScript e não vai pedir de novo só porque você trocou o arquivo no servidor.

O build resolve isso dando nomes novos a cada versão: index-9f2c.js vira index-a41b.js quando o conteúdo muda. O navegador nunca tem o arquivo novo guardado com o nome novo, então baixa. O index.html, por outro lado, precisa ser sempre revalidado — se ele ficar guardado por uma semana, o cliente continua pedindo o JavaScript antigo, porque é o nome antigo que está escrito nele.

ArquivoO nome muda a cada build?Como deve ser servido

Duas práticas deixam o dia da Ana tranquilo. A primeira: subir os arquivos novos numa pasta separada e só então trocar o que o host aponta (ou usar o "deploy" do host estático, que já é atômico). Assim ninguém vê o site pela metade. A segunda: guardar a versão anterior. Se o preço sair errado, a volta é promover a publicação antiga — um clique no host estático, um cp na VPS — em vez de caçar o commit certo com a loja no ar.

8. A conferência depois de publicar

Abrir a home e dizer "funcionou" é a metade da conferência. O roteiro completo cabe em cinco minutos e evita o telefonema constrangedor:

1) Abra numa aba anônima. Sem cache e sem sessão, você vê o que o cliente novo vê. 2) Confira o console. Erro vermelho na home publicada costuma ser caminho de arquivo ou chave faltando. 3) Recarregue numa rota interna. É o teste do rewrite; se der 404, a regra não está lá. 4) Digite um endereço errado. O 404 deve ser o seu, com o caminho de volta — a aula de rota 404 cuida disso. 5) Veja no celular. A tela pequena e a rede lenta revelam o que o notebook esconde.

Para olhar de verdade, use a aba Network: os arquivos devem vir com 200, o JavaScript com text/javascript, o CSS com text/css. Um 200 com o tipo errado é o disfarce do 404. E repare no tamanho: se o JavaScript passar de alguns megabytes, o build de produção não foi usado — provavelmente você publicou a pasta errada.

9. Cenários do dia a dia

Cenário 1: a home abre e a rota dá 404

A Ana publicou, abriu a home e navegou até um pedido: tudo certo. Mandou o link do pedido para a cliente e ela recebeu 404. O caminho existia dentro do app, mas não no disco do servidor. Faltava a regra de fallback — no nginx, try_files; no host estático, a linha de rewrite. Sem ela, só a home funciona em link direto.

Cenário 2: a logo aparece no notebook e some no site

No dev, src="/logo.png" funcionava. Publicado na subpasta /padaria/, o navegador foi buscar /logo.png na raiz do domínio e achou outra coisa — ou nada. O caminho absoluto ignorou o base. A correção é deixar o build escrever o caminho, com a imagem dentro de src/assets e import, ou prefixar a constante de base.

Cenário 3: a chave apareceu no código-fonte

Para "resolver rápido", ela colou a chave do serviço de mapas numa constante. Uma semana depois veio a fatura: alguém copiou a chave do bundle e usou à vontade. No front, chave é texto público. A saída é restringir a chave por domínio no provedor, ou passar a chamada por uma função do servidor que guarda o segredo.

11. Resumo

Publicar é copiar o conteúdo de dist/ para um computador que responda na internet. O projeto com src, package.json e node_modules fica no seu computador: o navegador não roda JSX, e o build já fez esse trabalho. Qualquer host estático serve, porque o site é só arquivos.

Três configurações decidem se o site vai funcionar: o base, que precisa bater com o endereço real (raiz ou subpasta); o rewrite, que devolve o index.html para os caminhos que não são arquivos, sem engolir o JavaScript; e o HTTPS, sem o qual o navegador avisa e o conteúdo misto é bloqueado. Nada no bundle é segredo, e configuração de ambiente é assada no build, não lida do servidor. Cache se resolve com nome com hash para os assets e index.html sem cache longo.

No fim, a conferência: aba anônima, console limpo, uma rota interna recarregada, um 404 seu, uma olhada no celular. Cinco minutos que economizam o telefonema. Na próxima aula, a Ana aprende a fazer essa mesma investigação quando o problema aparece — as ferramentas do navegador, uma por uma.

Para lembrar

  • Sobe o conteúdo de dist/; o código-fonte não vai para o host.
  • Site estático não precisa de Node no servidor.
  • base = o endereço onde o site mora; subpasta errada derruba todos os arquivos.
  • O 404 ao recarregar uma rota se resolve com rewrite para index.html.
  • O rewrite não pode capturar /assets/: HTML no lugar de JS quebra o app.
  • HTTPS é o padrão; conteúdo misto é bloqueado pelo navegador.
  • Nada no bundle é segredo — chave no front é chave pública.
  • import.meta.env é assado no build; mudar no servidor não muda o site.
  • Assets com hash podem ter cache longo; index.html, não.
  • Guarde a versão anterior: rollback é um clique, não uma caça ao commit.
