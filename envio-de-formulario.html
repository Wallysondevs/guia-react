Envio de Formulário

A Ana passou a semana arrumando o formulário de encomenda: o nome tinha regra, o telefone tinha regra, a mensagem de erro aparecia no lugar certo. Na segunda-feira uma cliente ligou dizendo que mandou o pedido três vezes e não recebeu confirmação nenhuma. A Ana abriu o site, digitou o nome e clicou em Encomendar: a página piscou, os campos esvaziaram e a mensagem sumiu. O formulário estava validando direito — o que faltava era o envio: impedir o navegador de recarregar a página, montar o pedido e conversar com o servidor. É o que ela faz nesta aula.

Você vai aprender
  • Por que um botão dentro de um form recarrega a página.
  • O par que resolve isso: onSubmit e e.preventDefault().
  • Como ler os campos na hora do envio, com estado ou com FormData.
  • Como montar o objeto do pedido e o que o servidor espera receber.
  • Como é um envio assíncrono — e por que a caixa simula a rede.
  • Como mostrar "Enviando..." e impedir o pedido duplicado.
  • O que fazer quando o envio falha, sem perder o que a pessoa digitou.

1. A cena: o pedido que a página apagou

O formulário da Ana tinha tudo: campos controlados, validação, mensagem de sucesso. Só que a mensagem aparecia por um instante e desaparecia. Não era bug do React: era o navegador fazendo o que faz com qualquer formulário desde 1995 — enviar os dados para o servidor e trocar a página inteira pelo resultado. Como o formulário não dizia para onde enviar, ele enviou para a própria página. A página recarregou, o componente nasceu de novo (com os campos vazios) e a mensagem que estava no estado foi junto.

O detalhe cruel é que a cliente viu "Encomenda registrada" antes do piscar. Para ela, o pedido tinha sido feito. Para o site, nada tinha acontecido. A Ana passou a tarde procurando o erro na validação, onde não estava: o problema era o comportamento padrão do formulário, que ninguém tinha desligado.

Enviar um formulário, no React, tem três partes e sempre as mesmas três: cancelar a navegação do navegador, ler os valores e conversar com o servidor. A primeira parte é uma linha de código e é onde quase todo mundo tropeça. A segunda já é conhecida, porque os campos são controlados. A terceira tem espera, resposta e erro — e é o que separa um formulário de brinquedo de um de verdade.

2. O que o navegador faz com um form

Uma tag form é o único lugar do HTML onde o navegador tem opinião formada. Ele observa os campos, espera o clique num botão de envio e, quando isso acontece, faz uma requisição com os dados. Sem atributo action, o destino é a própria página; sem method, o método é GET, que coloca os valores na barra de endereços. O resultado é a piscada que a Ana viu:

GET http://localhost:5173/?nome=Maria&telefone=999998888
200 OK — a página inteira de novo

Repare no que aconteceu: o nome e o telefone foram parar na URL. Isso não é um recurso do React, é o formulário do HTML funcionando como sempre funcionou. Em 1995 era assim que se mandava um pedido para o servidor, e o servidor devolvia uma página nova já com a resposta. O navegador não sabe que existe um componente com estado do outro lado; ele só conhece a URL para onde ir.

Por isso o estado se perde. Recarregar a página não é "atualizar os dados": é destruir a árvore de componentes e montar outra do zero. Todo useState volta ao valor inicial, toda mensagem some, todo trabalho feito no navegador é descartado. Se o pedido não foi para lugar nenhum antes disso, ele deixou de existir.

Existe uma coisa boa nesse comportamento, e ela explica por que continuamos usando form: apertar Enter dentro de um campo de texto envia o formulário. É de graça, funciona no celular e é o que qualquer pessoa espera. Quem troca o form por uma div com botões perde isso e precisa reimplementar teclado, foco e leitor de tela. A solução não é fugir do formulário: é assumir o comando do envio.

3. onSubmit: a função que roda no envio

O React escuta o evento submit do formulário, e o jeito de escutar é a prop onSubmit. Quando o navegador decide enviar — clique no botão ou Enter num campo —, ele chama a sua função antes de navegar. E aí está a chave: se a função chamar e.preventDefault(), a navegação é cancelada e a página fica onde está.

function Encomenda() {
  const [nome, setNome] = useState("");

  function enviar(e) {
    e.preventDefault();          // cancela a navegação do navegador
    console.log("pedido de " + nome);
  }

  return (
    <form onSubmit={enviar}>
      <label htmlFor="nome">Nome</label>
      <input
        id="nome"
        value={nome}
        onChange={(e) => setNome(e.target.value)}
      />
      <button type="submit">Encomendar</button>
    </form>
  );
}

O e que chega no onSubmit não é o mesmo e do onChange. No onChange, ele é um evento de mudança de campo, com e.target.value. No onSubmit, ele é o evento de envio do formulário, com e.target apontando para o form inteiro. O método preventDefault existe nos dois, e é o mesmo em qualquer evento: "não faça o que você faria sem mim".

envio (submit)
O momento em que o navegador pega os campos do formulário e monta uma requisição. No React, quem escuta esse momento é onSubmit.
preventDefault
Método do evento que cancela a ação padrão do navegador. No envio, cancela a navegação; no clique, cancela o clique.
pedido
O objeto com os dados que vão para o servidor: { nome, telefone, itens }.
Promise
Um valor que ainda não chegou. O fetch devolve uma; o then diz o que fazer quando ela resolver.
estado do envio
A variável que diz em que ponto a conversa está: ocioso, enviando, deu certo, deu erro.

A ordem importa. preventDefault precisa ser a primeira linha, porque o navegador navega assim que a sua função termina. Se você colocar um return antes, ou deixar a chamada dentro de um if que não rodou, a navegação acontece. Também não adianta chamar preventDefault dentro do onClick do botão: ali você cancela o clique, não o envio — e o formulário continua sendo enviado por outro caminho.

Uma armadilha de leitura: dentro de um form, o valor padrão de type num button é "submit". Ou seja, um botão "Limpar" sem type envia o formulário em vez de limpar. Sempre que o botão não for de envio, escreva type="button".

Agora a primeira missão. O formulário abaixo tem os dois campos e o botão, mas nenhum onSubmit: clicar em Encomendar recarrega a prévia e o pedido se perde.

Escreva um onSubmit que chama e.preventDefault() e mostra Pedido de Maria registrado com o nome que estiver no campo. Digite "Maria", clique em Encomendar e confira que a prévia não recarrega.

Compare os dois comportamentos. No código inicial, a prévia pisca e volta ao começo: é a navegação acontecendo. Na solução, o formulário continua na tela, o campo continua com "Maria" e a mensagem aparece embaixo. A diferença entre os dois mundos é uma chamada de uma linha, mas o efeito é grande: a partir daí quem decide o que acontece é o seu componente, não o navegador.

4. Ler os campos na hora do envio

Com campos controlados, você já tem os valores: eles estão no estado, atualizados a cada tecla. O onSubmit só precisa usá-los. Mas existe um segundo caminho, útil quando o formulário é grande ou quando os campos não são controlados: pedir os valores ao próprio formulário com FormData.

function Newsletter() {
  function enviar(e) {
    e.preventDefault();
    const dados = new FormData(e.target);   // e.target é o <form>
    const email = dados.get("email");       // o name do campo
    console.log("assinar: " + email);
  }

  return (
    <form onSubmit={enviar}>
      <label htmlFor="email">E-mail</label>
      <input id="email" name="email" type="email" />
      <button type="submit">Assinar</button>
    </form>
  );
}

FormData lê os campos pelo atributo name, não pelo id. Se o campo não tem name, dados.get("email") devolve null e o envio vai com o campo em branco — um dos bugs mais silenciosos que existem. A vantagem é que um formulário de vinte campos vira uma linha; a desvantagem é que os valores só existem no momento do envio, então não dá para usar a mesma fonte para validar enquanto a pessoa digita.

Nesta aula a Ana fica com o estado, por um motivo prático: o mesmo valor serve para validar, para o resumo do pedido e para o envio. Um dono só para o dado, como você viu na aula de entrada controlada. O FormData entra quando o formulário é grande demais para valer a pena controlar cada campo, ou quando você recebe um formulário que já existia em HTML.

Um cuidado ao ler pelo estado: o clique acontece no instante em que o estado tem o valor da última tecla processada. Se a pessoa digitar e clicar muito rápido, o React já processou a digitação antes do clique — a ordem dos eventos é a ordem das coisas. Você não precisa se preocupar com isso; precisa se preocupar com o valor estar limpo antes de mandar (o trim() da aula de validação).

5. O objeto do pedido

O servidor não recebe "nome" e "telefone" soltos. Ele recebe um pedido, com uma forma combinada. Antes de enviar, monte esse objeto no seu código: é mais fácil de ler no console, de testar e de mandar como JSON.

function enviar(e) {
  e.preventDefault();

  const pedido = {
    nome: nome.trim(),
    telefone: telefone.trim(),
    itens: ["pão de queijo"],
    retirada: "6h"
  };

  console.log("pedido: " + JSON.stringify(pedido));
}

O JSON.stringify transforma o objeto em texto, que é o formato que atravessa a rede. No console do navegador, você vê o resultado:

pedido: {"nome":"Maria","telefone":"999998888","itens":["pão de queijo"],"retirada":"6h"}

Repare que o objeto tem só o que o servidor precisa. Não mande o estado inteiro, nem valores que ele pode calcular (como o total, que ele vai conferir com os preços dele), nem dados que não são da pessoa. Cada campo a mais é uma decisão de segurança que alguém vai ter que revisar depois.

E repare também no que o objeto não tem: a mensagem de sucesso. A frase "Pedido registrado" não vai para o servidor; ela é a resposta que a tela mostra depois. Misturar as duas coisas é comum e cria problema: o servidor passa a receber texto de interface, que muda a cada semana.

Com o objeto pronto, o envio de verdade é uma chamada de rede. E aqui a caixa deste guia tem uma limitação que vale explicar, em vez de esconder.

6. O envio assíncrono: a resposta não vem na hora

A conversa com o servidor não é instantânea. Você manda o pedido, o servidor pensa, responde — e entre uma coisa e outra passa um tempo que ninguém controla. No JavaScript, esse "depois" tem nome: Promise, uma promessa de que um valor vai chegar. O fetch devolve uma Promise, e await espera por ela sem travar a página.

Só que a prévia desta página roda num quadro isolado, sem servidor: um fetch ali não encontra ninguém do outro lado e falha. Por isso os exemplos da caixa simulam a rede com new Promise((ok) => setTimeout(ok, 400)) — a mesma espera, o mesmo "depois", sem fio nenhum. Quando você passar para o projeto de verdade, troca essa linha pelo fetch e o resto do componente continua igual.

O envio é instantâneo, o que não acontece na vida real. Faça enviar mostrar Enviando... e só trocar por Pedido de Maria registrado depois de uma Promise com setTimeout de 400 ms.

function App() {
  const [nome, setNome] = useState("");
  const [aviso, setAviso] = useState("");

  function enviar(e) {
    e.preventDefault();
    setAviso("Pedido de " + nome + " registrado");
  }

  return (
    <form onSubmit={enviar}>
      <label htmlFor="nome">Nome</label>
      <input
        id="nome"
        value={nome}
        onChange={(e) => setNome(e.target.value)}
      />
      <button id="enviar" type="submit">Encomendar</button>
      {aviso && <p>{aviso}</p>}

function App() {

  const [aviso, setAviso] = useState("");

  function enviar(e) {
    e.preventDefault();
    setAviso("Enviando...");
    new Promise((ok) => setTimeout(ok, 400)).then(() => {
      setAviso("Pedido de " + nome + " registrado");
    });
  }

  return (
    <form onSubmit={enviar}>
      <label htmlFor="nome">Nome</label>
      <input
        id="nome"
        value={nome}
        onChange={(e) => setNome(e.target.value)}
      />
      <button id="enviar" type="submit">Encomendar</button>
      {aviso && <p>{aviso}</p>}
    </form>
  );
}

Clique em Verificar com o nome preenchido: o painel pega a tela no instante em que ela mostra "Enviando...". Na prévia ao vivo dá para ver o resto: a frase muda sozinha 400 ms depois, sem clique nenhum. É o desenho de qualquer envio: uma função que começa, uma espera e um then que termina o serviço.

Se você já viu async e await por aí, a versão equivalente é esta:

async function enviar(e) {
  e.preventDefault();
  setAviso("Enviando...");

  await new Promise((ok) => setTimeout(ok, 400));

  setAviso("Pedido de " + nome + " registrado");
}

O await pausa a função naquela linha e devolve o controle para o navegador — a página continua respondendo, o botão continua clicável, e é justamente por isso que a próxima seção existe. Com a função pausada, nada impede a pessoa de clicar de novo.

7. Enquanto o servidor não responde

Todo envio passa por quatro situações, e a tela precisa dizer em qual delas está. Se ela não disser, a pessoa clica de novo. E clicar de novo, num envio de verdade, é um segundo pedido na cozinha.

deu erro"Não deu para enviar" e o botão de tentarativo de novoo formulário preenchido

O jeito mais curto de garantir um envio por vez é uma guarda no começo da função:

const [enviando, setEnviando] = useState(false);

async function enviar(e) {
  e.preventDefault();
  if (enviando) return;          // já tem um envio em andamento
  setEnviando(true);
  try {
    await mandarPedido({ nome, telefone });
    setAviso("Pedido registrado");
  } finally {
    setEnviando(false);          // em qualquer caso, libera o botão
  }
}

O finally é o detalhe que muita gente esquece. Sem ele, um erro deixa enviando como true para sempre: o botão fica desabilitado, a tela fica em "Enviando..." e a única saída é recarregar a página. O finally roda tanto no sucesso quanto no erro, e é o lugar certo para devolver o controle à pessoa.

mandarPedido, ali no meio, é só o nome que a Ana deu à função que faz o fetch — podia ser enviarParaOServidor. O React não conhece esse nome; quem conhece é o código dela. Separar assim deixa o envio legível e permite trocar o transporte depois, sem mexer no componente.

O disabled no botão é o reforço visual da mesma ideia. Note que ele não substitui a guarda: um clique muito rápido, antes de o React redesenhar, ainda pode chamar a função duas vezes. A guarda está na função, que é onde a decisão acontece.

8. Quando o envio dá errado

Rede cai, servidor reinicia, o banco fica fora do ar por dez segundos. Isso não é exceção: é rotina. Um envio sem tratamento de erro deixa a tela em "Enviando..." eternamente e a pessoa sem saber o que fazer.

Se a função usa await ou then, o erro chega por dois caminhos. O primeiro é a própria chamada falhar (sem rede, servidor fora). O segundo é a chamada dar certo e a resposta ser um erro do servidor — fetch não considera 500 um erro, ele entrega a resposta e você é quem confere o status. Os dois caminhos precisam de mensagem:

try {
  const resposta = await fetch("/api/pedidos", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(pedido)
  });

  if (!resposta.ok) throw new Error("o servidor respondeu " + resposta.status);

  const dados = await resposta.json();
  setAviso("Pedido " + dados.numero + " registrado");
} catch (erro) {
  setAviso("Não deu para enviar. Tente de novo.");
  console.log("falhou: " + erro.message);
}

No console do navegador, esse console.log aparece assim:

falhou: o servidor respondeu 500

Duas regras para a mensagem de erro. A primeira: diga o que aconteceu e o que fazer, não o nome técnico. "Não deu para enviar. Tente de novo." resolve; "TypeError: Failed to fetch" não resolve nada para a cliente da padaria — essa frase é para o console, não para a tela. A segunda: não apague o que a pessoa digitou. Perder o formulário preenchido é o pior desfecho possível de um erro de rede; mantenha os campos e ofereça o botão de tentar de novo.

Agora a missão. O envio abaixo tem a espera e o sucesso, mas nenhum tratamento de erro: se a promessa falhar, a tela fica em "Enviando..." e ninguém fica sabendo.

A promessa falha de propósito. Acrescente um .catch que troca o aviso por Não deu para enviar. Tente de novo. quando a falha chegar, e clique em Encomendar.

function App() {
  const [nome, setNome] = useState("");
  const [aviso, setAviso] = useState("");

  function enviar(e) {
    e.preventDefault();
    setAviso("Enviando...");
    new Promise((ok, falhou) => {
      setTimeout(() => falhou(new Error("sem conexão")), 30);
    }).then(() => {
      setAviso("Pedido de " + nome + " registrado");
    });
  }

  return (
    <form onSubmit={enviar}>
      <label htmlFor="nome">Nome</label>
      <input
        id="nome"
        value={nome}
        onChange={(e) => setNome(e.target.value)}
      />
      <button id="enviar" type="submit">Encomendar</button>
      {aviso && <p>{aviso}</p>}
    </form>
  );
}

Sem o catch, o console do navegador mostra um aviso de promessa rejeitada que ninguém tratou e a tela fica parada em "Enviando...". Com ele, a mensagem aparece e os campos continuam lá. Note que o catch vem depois do then, na mesma corrente: é uma sequência — tenta, deu certo faz isso, deu errado faz aquilo.

9. Cenários do dia a dia

Cenário 1: a página piscou e o pedido sumiu

A Ana esqueceu o preventDefault. A função do onSubmit rodou, mas o navegador navegou logo depois: a prévia recarregou, o componente voltou do zero e o estado foi embora. O sintoma é sempre o mesmo — campos vazios, mensagem que não fica. A conferência é rápida: a primeira linha do onSubmit chama e.preventDefault()?

Cenário 2: dois pedidos iguais na cozinha

A cliente clicou três vezes porque o botão não dava sinal de vida. O servidor recebeu três pedidos iguais e a cozinha assou três bolos. O conserto tem duas partes: mostrar "Enviando..." na hora e guardar a função com um if (enviando) return. O aviso na tela é o que impede o clique repetido; a guarda é o que impede o envio repetido.

Cenário 3: o sucesso que nunca chegou

O servidor respondeu 500, mas o código só olhava o then, nunca o status da resposta. A tela mostrou "Pedido registrado" para um pedido que não existia no banco. fetch não reclama de 500: ele entrega a resposta. Quem decide se deu certo é o resposta.ok, e quem avisa a pessoa é você.

11. Resumo

Um botão dentro de um form dispara o envio nativo do navegador: ele monta uma requisição, navega e recarrega a página, levando junto o estado dos componentes. No React, o envio é seu: a prop onSubmit recebe uma função, e a primeira linha dela é e.preventDefault(). Só depois disso os valores são lidos — do estado, quando os campos são controlados, ou do FormData, quando não são.

O pedido vai como um objeto com a forma que o servidor combinou, e o envio é assíncrono: uma Promise que resolve depois. Enquanto ela não resolve, a tela mostra "Enviando..." e o botão fica bloqueado, para não virar dois pedidos. Quando resolve, a mensagem de sucesso aparece e o formulário é limpo ou mantido, conforme a decisão da loja. Quando falha, uma mensagem clara aparece, os dados continuam na tela e a pessoa pode tentar de novo — o finally garante que o botão volte.

A prévia deste guia não tem rede, então as caixas simulam a resposta com setTimeout. É a mesma estrutura do fetch de verdade: a diferença está só no miolo da função. E a validação do navegador continua valendo o que sempre valeu — conveniência para quem preenche. O servidor confere tudo de novo.

Para lembrar

  • Botão de envio dentro de form navega: a página recarrega e o estado se perde.
  • onSubmit recebe a função do envio; e.preventDefault() vem primeiro.
  • Dentro de um form, button sem type já é type="submit".
  • Campos controlados: os valores já estão no estado na hora do envio.
  • FormData lê pelo atributo name; sem name, vem null.
  • Monte um objeto com o que o servidor precisa e mande como JSON.
  • O envio é assíncrono: mostre "Enviando..." e bloqueie o botão.
  • if (enviando) return é a guarda que evita o pedido duplicado.
  • fetch não reclama de 500: confira resposta.ok.
  • No erro, mantenha os campos e libere o botão no finally.
