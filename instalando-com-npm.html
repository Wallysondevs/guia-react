Instalando com npm

O projeto da Ana já existe na pasta do notebook, criado pelo Vite, e agora ela quer formatar as datas das encomendas — "sábado, 15 de março, 14h30" — sem escrever a lista de meses à mão. Alguém sugere npm install date-fns, ela roda, funciona. E ficam as perguntas: o que o npm acabou de fazer? De onde veio o ^ na versão? Por que a pasta ficou com centenas de pastas? Nesta aula ela entende o gerenciador de pacotes por dentro — instalar, versionar, separar o que é de desenvolvimento e sair dos erros clássicos.

Você vai aprender
  • O caminho de um pacote do catálogo público até o node_modules.
  • Como instalar, remover e atualizar pacotes com o npm.
  • A ler versões: 4.1.0, ^4.1.0, ~4.1.0 e o que cada símbolo aceita.
  • A diferença entre dependencies e devDependencies — e por que ela economiza espaço.
  • Para que serve o package-lock.json e quando usar npm ci.
  • npx, o cache e os três erros que mais aparecem (404, ERESOLVE, permissão).

1. A cena: a data que não formata

A página de encomendas da padaria mostra a data do jeito que o banco entrega: 2025-03-15T14:30:00.000Z. É preciso, mas ninguém entende. A Ana quer "sábado, 15 de março, 14h30". Ela tenta resolver sozinha: cria um array com os meses, outro com os dias da semana, divide a string por hífens e monta o texto. Funciona no primeiro teste e quebra no segundo — o horário vem em UTC, a padaria está em São Paulo, e três horas de diferença transformam o almoço em café da manhã.

Uma amiga que programa em React diz: "instala o date-fns". A Ana abre o terminal na pasta do projeto e roda o comando. Em dois segundos aparece added 1 package, e o format da biblioteca resolve a data, o fuso e o idioma. Maravilhoso — e completamente misterioso. Ela quer entender o que aconteceu, porque a próxima coisa que precisa é de uma biblioteca de testes, e ela não quer descobrir na prática se vai quebrar o projeto.

Este é o assunto da aula: o npm não é uma caixa-preta que baixa coisa. Ele tem um catálogo, um manifesto, um arquivo de trava e uma pasta de depósitos. Quem entende esses quatro lugares instala, atualiza e conserta sem medo — e sabe exatamente o que vai junto para produção e o que é só ferramenta de trabalho.

2. O caminho de um pacote até o seu projeto

Quando você digita npm install date-fns, o npm faz cinco coisas em sequência. Primeiro consulta o registro, o catálogo público onde os pacotes do mundo inteiro moram (registry.npmjs.org). Lá ele descobre qual é a versão mais nova que combina com o nome pedido e baixa o tarball, um arquivo compactado com o código daquele pacote. Depois extrai o conteúdo para dentro de node_modules/date-fns. Em quarto lugar anota a dependência no package.json, para que qualquer pessoa saiba que o projeto precisa dela. E, por último, atualiza o package-lock.json com a versão exata que foi baixada.

Repare que são dois arquivos com papéis diferentes. O package.json é o manifesto do seu projeto: nome, tipo de módulo, dependências e scripts. Ele guarda a intenção — "este projeto usa date-fns na linha 4". O package-lock.json guarda o resultado — "a versão instalada foi a 4.1.0, e o arquivo dela tem este hash". Um é a receita; o outro é a foto do bolo.

registro
O catálogo público de pacotes: registry.npmjs.org. É de lá que o npm baixa.
pacote
Uma pasta publicada com código, um package.json e uma versão. date-fns, react, vite.
dependência
Um pacote que o seu projeto usa. Fica listada no package.json.
faixa de versão
O intervalo aceito, escrito com símbolos: ^4.1.0, ~4.1.0, 4.1.0.
lockfile
O package-lock.json: a árvore exata que foi instalada, com versões e hashes.
node_modules
A pasta onde o código baixado fica. Gerada pelo npm, nunca editada à mão.

Uma consequência prática que evita muita confusão: node_modules não vai para o Git. Ela é derivada do package.json mais o package-lock.json — e qualquer pessoa recria com um comando. Já os dois arquivos JSON vão para o Git, porque são o que conta a história do projeto. O .gitignore do modelo do Vite já traz node_modules na lista, e é por isso que você nunca o vê num repositório.

3. Instalando um pacote

O comando de instalação tem duas formas e um lugar certo para rodar. O lugar é a pasta do projeto: aquela que tem o package.json. Se você rodar em outra pasta, o npm cria um package.json novo ali ou reclama que não achou — os dois casos dão dor de cabeça. A forma curta é npm i, e a longa é npm install; as duas fazem a mesma coisa.

$ npm install date-fns

added 1 package, and audited 156 packages in 1s

found 0 vulnerabilities

Três linhas, três informações. "added 1 package" diz quantos pacotes entraram — o date-fns não tem dependências próprias, então foi só ele. "audited 156 packages" conta todos os pacotes da árvore que o npm conferiu em busca de falhas conhecidas, incluindo os que já estavam lá. "found 0 vulnerabilities" é o resultado dessa conferência: nada grave encontrado. Se aparecesse um número ali, o npm imprimiria uma tabela com o pacote, a falha e a versão que corrige.

Sem nome de pacote, npm install lê o package.json e instala tudo o que está listado. É o comando que você roda ao clonar um projeto ou ao trocar de computador — e é o mesmo que o Vite mandou rodar depois de criar o modelo. Com nome, ele acrescenta uma dependência nova e já a instala. Com @versão, escolhe uma versão específica: npm install date-fns@3.6.0.

Uma nota sobre o que aparece no package.json: o npm escreve ^4.1.0, não 4.1.0. Ele assume que você quer receber correções e melhorias compatíveis, e o ^ é a forma de dizer isso. Para travar exatamente uma versão, use npm install --save-exact date-fns — que grava 4.1.0 sem símbolo nenhum. Vale saber por que você pode querer as duas coisas, e é o que vem a seguir.

4. As versões e os símbolos

Todo pacote do npm segue o semver, a convenção de três números: maior.menor.correção. Em 4.1.0, o 4 é a versão maior, o 1 é a menor e o 0 é a correção. A promessa da convenção é simples: correção não quebra nada, versão menor acrescenta sem quebrar, versão maior pode quebrar. É essa promessa que permite escrever faixas em vez de versões exatas.

SímboloAceitaExemplo com 4.1.0
^4.1.0de 4.1.0 até antes de 5.0.04.1.0, 4.2.0, 4.9.9 — não 5.0.0
~4.1.0de 4.1.0 até antes de 4.2.04.1.0, 4.1.7 — não 4.2.0
4.1.0só essa versão4.1.0
>=4.1.0 <5o intervalo escrito à mãoo mesmo que o ^
*qualquer versãoa mais nova que existir

O ^ é o padrão do npm porque ele equilibra as duas vontades: receber correções de segurança sem precisar reinstalar, e não ser surpreendido por uma mudança que quebra a API. O ~ é mais conservador e aparece quando até uma versão menor pode mudar comportamento. E a versão exata aparece quando você precisa reproduzir um bug ou congelar o projeto.

A caixa abaixo simula a conta que o npm faz ao escolher entre as versões disponíveis. A função aceita decide se uma versão entra na faixa ^19.0.0 — hoje ela aceita tudo, e a missão é corrigir a regra do ^: mesma versão maior, e nunca abaixo da mínima.

A função aceita está devolvendo true para tudo, então as quatro versões aparecem como aceitas. Implemente a regra do ^: mesma versão maior e nunca abaixo de 19.0.0. O resultado precisa ser 19.0.0 e 19.2.0 aceitas, 18.3.1 e 20.0.0 fora.

const versoes = ["18.3.1", "19.0.0", "19.2.0", "20.0.0"];

  const alvo = faixa.slice(1).split(".").map(Number);
  const v = versao.split(".").map(Number);

  return true;
}

function App() {
  return (
    <div>
      <h2>react ^19.0.0</h2>
      <ul>
        {versoes.map((v) => (
          <li key={v} className={aceita(v, "^19.0.0") ? "ok" : "fora"}>
            {v} — {aceita(v, "^19.0.0") ? "aceita" : "fora da faixa"}
          </li>
        ))}
      </ul>
    </div>
  );
}

function aceita(versao, faixa) {
  const alvo = faixa.slice(1).split(".").map(Number);
  const v = versao.split(".").map(Number);

  if (v[0] !== alvo[0]) {
    return false;
  }

  if (v[1] !== alvo[1]) {
    return v[1] > alvo[1];
  }

  return v[2] >= alvo[2];
}

function App() {
  return (
    <div>
      <h2>react ^19.0.0</h2>
      <ul>
        {versoes.map((v) => (
          <li key={v} className={aceita(v, "^19.0.0") ? "ok" : "fora"}>
            {v} — {aceita(v, "^19.0.0") ? "aceita" : "fora da faixa"}
          </li>
        ))}
      </ul>
    </div>
  );
}

O painel depois da correção mostra a faixa funcionando: 18 fica de fora porque a versão maior é outra; 20 fica de fora porque subir a maior é justamente o que o ^ não faz. 19.0.0 entra porque é o piso; 19.2.0 entra porque está acima do piso e abaixo do teto. Essa é a conta que transforma um intervalo escrito no package.json numa versão concreta dentro do node_modules.

Para ver o que está instalado hoje, sem adivinhar, existe um comando: npm ls date-fns mostra a versão resolvida e onde ela está na árvore. Com npm ls sozinho, o npm imprime a árvore inteira — útil quando duas bibliotecas pedem versões diferentes de uma terceira.

5. Dependências e devDependencies

Nem todo pacote tem o mesmo destino. O react e o date-fns precisam existir quando a página roda no navegador: são dependências. Já o vite, o eslint e o vitest só trabalham na sua máquina, durante o desenvolvimento, o build e os testes: são dependências de desenvolvimento. O npm separa as duas em listas diferentes, e a diferença importa na hora de publicar e de economizar tempo.

{
  "name": "padaria",

    "vite": "^7.1.0",

}

O comando para instalar como desenvolvimento é o mesmo com uma bandeira: npm install -D vitest. O -D é o apelido de --save-dev, e o npm grava o pacote em devDependencies. Se você esquecer o -D, o vitest entra em dependencies e passa a ser instalado também em produção — onde ele não serve para nada e só ocupa espaço.

Por que isso importa de verdade: quando o site vai para um servidor, dá para instalar só o que é de produção com npm install --omit=dev (ou usar NODE_ENV=production). A imagem fica menor, a instalação mais rápida e a superfície de ataque também. Em muitos serviços de hospedagem essa é a instalação padrão. Se uma biblioteca de desenvolvimento entrou na lista errada, o build passa a falhar no servidor com "Cannot find module" — e o motivo é esse.

A segunda lista deveria mostrar só o que sobra com npm install --omit=dev, mas ela está repetindo os quatro pacotes. Filtre os que têm dev: false — a lista de produção precisa ficar com dois itens.

6. O package-lock.json e o npm ci

O package-lock.json parece um arquivo gigante e inútil: milhares de linhas com nomes, versões e hashes. Ele resolve um problema específico: garantir que toda instalação do mesmo projeto produza a mesma árvore. Sem ele, o ^4.1.0 de hoje baixaria uma versão e o de amanhã outra — e o bug que aparece na sua máquina não aparece na do cliente.

O arquivo guarda a versão exata de cada pacote, inclusive os indiretos (as dependências das dependências), e um hash de integridade para conferir que o download é o mesmo. Ele é gerado sozinho no primeiro npm install e atualizado a cada instalação. A regra é simples: ele vai para o Git junto com o package.json, e você não o edita à mão.

ComandoO que fazQuando usar
npm installinstala o que falta e pode atualizar dentro das faixasno dia a dia, ao acrescentar algo
npm ciapaga node_modules e instala exatamente o lockno servidor de build, CI e ao clonar
npm updatesobe versões dentro das faixas declaradasde vez em quando, com os testes abertos
npm outdatedlista o que está atrás da versão mais novaantes de decidir atualizar

O npm ci é o comando preferido de qualquer automação por três motivos: ele não altera o lock, ele falha se o package.json e o lock estiverem fora de sincronia (o que é um aviso bom) e ele é mais rápido, porque remove a pasta e instala de uma vez, em vez de conferir item por item. Se você já viu um arquivo de CI começando com npm ci, agora sabe por quê.

7. Atualizando e removendo

Atualizar não é rodar npm install de novo e esperar o melhor. O caminho é perguntar primeiro o que está atrasado:

$ npm outdated

Package   Current  Wanted  Latest  Location
react     18.3.1   18.3.1  19.2.0  node_modules/react
vite       7.1.0    7.1.3   7.1.3  node_modules/vite
eslint     9.12.0   9.15.1  9.15.1 node_modules/eslint
date-fns   3.6.0    3.6.0   4.1.0  node_modules/date-fns

Três colunas merecem atenção. Current é o que está instalado agora. Wanted é a maior versão que a faixa do package.json permite — o que um npm update instalaria. Latest é a mais nova publicada, mesmo que esteja fora da faixa. Quando Current e Wanted são iguais e Latest é maior, significa que a faixa está segurando a atualização: só um npm install pacote@latest (ou editar a faixa) sobe a versão maior.

O npm update respeita as faixas e sobe dentro delas; ele nunca pula para uma versão maior sozinho. Isso é proteção, não preguiça: versão maior pode quebrar a API, e quem decide correr esse risco é você, lendo o changelog e rodando os testes. Para remover um pacote, npm uninstall vitest tira do node_modules, do package.json e do lock de uma vez.

A tabela classifica toda atualização como patch, mas cada tipo pede uma decisão diferente. Compare a versão instalada com a última e marque major quando a primeira casa mudar, minor quando mudar a segunda e patch quando só a terceira mudar.

É muito mais útil do que "tem atualização?" — a pergunta certa é "que tipo de atualização?".

8. npx e o cache

Existe um comando que parece instalar e não instala: npx. Ele executa o programa de um pacote sem acrescentá-lo ao projeto. Se o pacote não estiver no node_modules, o npx baixa para um cache temporário, roda e segue a vida. É assim que se usam ferramentas de uma vez só:

$ npx vite --version

vite/7.1.0 linux-x64 node-v22.14.0

O caso mais comum no começo é npx create-vite@latest padaria, que roda o assistente de criação sem instalar o create-vite globalmente. Também aparece quando um tutorial manda npx prettier --write . e você não quer o prettier no package.json. A regra: ferramenta que o projeto usa sempre vira dependência de desenvolvimento; ferramenta de uma vez só pode ser npx.

Sobre o cache: o npm guarda os tarballs baixados numa pasta do usuário e reaproveita nas próximas instalações. É por isso que o segundo npm install do mesmo projeto é mais rápido. Quando algo parece corrompido, npm cache verify confere a integridade; o npm cache clean --force existe, mas raramente é a solução — na maioria das vezes, apagar node_modules e o lock e instalar de novo resolve sem mexer no cache global.

9. Cenários do dia a dia

Cenário 1: o nome errado

A Ana digitou npm install date-fsn e recebeu 404 Not Found. O npm procurou um pacote que não existe no registro. A mensagem mostra a URL consultada, e é ali que se vê o erro de digitação. Antes de culpar a rede, confira o nome no site do npm e a ortografia; se o pacote for privado, confira também se você está autenticado.

Cenário 2: o conflito de versões

Ela tentou instalar uma biblioteca de calendário que declarava suporte só ao React 18, e o npm respondeu ERESOLVE unable to resolve dependency tree. É o npm avisando que dois pacotes discordam sobre a versão de um terceiro. O caminho é procurar a versão da biblioteca que suporte o React 19 ou conversar com quem mantém; --force e --legacy-peer-deps existem, mas escondem o problema em vez de resolvê-lo.

Cenário 3: permissão negada

Um tutorial mandou rodar sudo npm install -g algo, e a partir dali a pasta do projeto passou a pertencer ao root. O sintoma é EACCES em toda instalação seguinte. O conserto é nunca usar sudo com npm: reinstale o Node pelo site oficial ou por um gerenciador de versões, e, se a pasta já estiver com dono errado, corrija o dono. Instalação global também costuma ser desnecessária — quase tudo cabe em dependência de desenvolvimento.

Exercício: a bandeira do desenvolvimento

Complete o comando que instala o vitest na lista de dependências de desenvolvimento:

npm install vitest

Dica: é a bandeira curta que o npm traduz para --save-dev. Sem ela, o pacote entra em dependencies e passa a ser instalado também em produção, onde não serve para nada.

11. Resumo

O npm é o gerenciador de pacotes que vem com o Node. Ele consulta o registro, baixa o pacote, extrai em node_modules, anota a intenção no package.json e o resultado exato no package-lock.json. Instalar é npm install nome; instalar como ferramenta de trabalho é npm install -D nome; remover é npm uninstall nome. Os dois JSON vão para o Git, a pasta node_modules não.

Versões seguem o semver: maior, menor, correção. O ^ aceita tudo abaixo da próxima maior; o ~ aceita tudo abaixo da próxima menor; sem símbolo, é exatamente aquela versão. O npm outdated mostra installed, wanted e latest, e é a partir dele que você decide o que atualizar. O npm update respeita as faixas; pular de maior é uma decisão consciente.

E o package-lock.json é o que faz o projeto instalar igual em qualquer máquina — por isso o npm ci é o comando das automações. Com essas peças, a Ana instala a biblioteca de testes sem medo, sabe onde ela entrou e o que vai junto para produção. A próxima aula olha para o outro lado: o projeto que o Vite criou, arquivo por arquivo, e o que cada escolha do assistente significa.

Para lembrar

  • npm install nome instala e anota em dependencies.
  • npm install -D nome instala como ferramenta, em devDependencies.
  • ^4.1.0 aceita de 4.1.0 até antes de 5.0.0; ~4.1.0 até antes de 4.2.0.
  • npm outdated mostra current, wanted e latest.
  • npm update sobe dentro das faixas; versão maior é decisão sua.
  • package-lock.json trava a árvore exata e vai para o Git.
  • node_modules é depósito: não edite, não versione, pode apagar e recriar.
  • npm ci instala exatamente o lock — o comando do CI.
  • npx roda uma ferramenta sem acrescentá-la ao projeto.
  • 404 é nome errado; ERESOLVE é conflito de versões; EACCES é permissão — e nunca se usa sudo.
