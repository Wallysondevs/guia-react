Enviar Dados (POST)

Até agora o site da Ana só perguntava: qual o preço, tem pão, que horas abre. Enviar é outro tipo de conversa — a encomenda precisa chegar completa do outro lado, com o nome do pão, a quantidade e o endereço, e o servidor precisa conseguir ler tudo isso. No fetch, enviar quer dizer POST com corpo, e o corpo tem de ser texto no formato certo, com um cabeçalho avisando que formato é esse. Nesta aula a Ana monta a encomenda, vê o servidor recusar duas vezes por motivos diferentes e aprende a ler a resposta de erro que explica o que faltou.

Você vai aprender
  • O que muda entre um GET e um POST.
  • Por que o corpo precisa de JSON.stringify.
  • O papel do cabeçalho Content-Type.
  • Os status de um envio: 201, 400, 415, 500.
  • Como ler o motivo da recusa no corpo da resposta.
  • Como evitar mandar o mesmo pedido duas vezes.

1. A cena: a encomenda no papel

No balcão, a encomenda é uma folha com campos preenchidos. Se faltar o nome, o atendente não adivinha; se o campo quantidade vier rabiscado, ele pergunta de novo. O servidor funciona igual: recebe um corpo com campos, confere se estão todos lá e no formato combinado, e responde dizendo se guardou ou se faltou alguma coisa.

A diferença é que, no HTTP, o corpo é sempre uma sequência de bytes. O navegador não sabe que aquele texto é um objeto JavaScript com nome e preço — ele só sabe mandar texto. Quem transforma objeto em texto é o JSON.stringify; quem avisa o servidor de que aquele texto é JSON é o cabeçalho Content-Type. Sem os dois, a encomenda chega ilegível.

E é por isso que os dois erros mais comuns de quem começa a enviar dados são exatamente esses: mandar o objeto cru e esquecer o cabeçalho. A boa notícia é que os dois têm sintoma claro — e as caixas desta aula mostram cada um.

2. GET pergunta, POST entrega

O método é o verbo da requisição. GET pede alguma coisa e não leva corpo: todos os dados vão na URL. POST entrega alguma coisa e leva corpo: os dados vão no corpo, e a URL só diz para onde enviar. PUT e PATCH também levam corpo; a diferença entre eles é de intenção, e a API da padaria usa POST para criar pedido.

MétodoPara que serveLeva corpo?
GETpedir dados, sem alterar nadanão
POSTcriar algo novo (pedido, cadastro)sim
PUTsubstituir um registro inteirosim
PATCHalterar só alguns campossim
DELETEapagar um registropor convenção, não

A escolha do método não é estilo: é contrato. Ferramentas de cache, proxies e navegadores tratam GET como seguro para repetir e POST como não — e é por isso que um GET repetido não cria pedidos duplicados e um POST repetido cria.

método
O verbo no objeto de opções: method: "POST". Sem ele, o fetch usa GET.
corpo
O conteúdo enviado: body. Precisa ser texto (ou binário), nunca objeto.
Content-Type
O cabeçalho que diz o formato do corpo. Para JSON, application/json.
JSON.stringify
A função que transforma objeto em texto JSON.
status 201
"Criado": o servidor guardou e normalmente devolve o recurso com o id novo.
idempotência
A propriedade de repetir a mesma chamada sem criar duplicata. POST não é idempotente por natureza.

Um detalhe que confunde no começo: o POST que "dá certo" costuma devolver status 201, não 200. É o servidor dizendo "criei uma coisa nova". O 200 é resposta de leitura, quando nada foi criado. Se o seu código trata sucesso como "status === 200", ele vai considerar erro um envio bem-sucedido — o teste certo é resposta.ok, como sempre.

3. O corpo viaja como texto

A primeira tentativa da Ana mandou o objeto direto no corpo. O servidor respondeu 400 e a tela mostrou "Deu erro 400". O motivo: o fetch não converte objeto em JSON por você — ele transforma em texto do jeito pobre, com "[object Object]", e o servidor não consegue ler nada ali.

O body recebeu o objeto dados e o servidor recusou com 400. Converta para texto: body: JSON.stringify(dados).

const dados = { pao: "brioche", quantidade: 2 };

function enviarPedido(opcoes) {
  return new Promise((ok) => {
    setTimeout(() => {
      const cabecalhos = opcoes.headers || {};
      if (cabecalhos["Content-Type"] !== "application/json") {
        return ok({
          ok: false,
          status: 415,
          json: () => Promise.resolve({ erro: "Content-Type precisa ser application/json" })
        });
      }
      if (typeof opcoes.body !== "string") {
        return ok({
          ok: false,
          status: 400,
          json: () => Promise.resolve({ erro: "O corpo não é JSON" })
        });
      }
      const recebido = JSON.parse(opcoes.body);
      if (!recebido.pao) {
        return ok({
          ok: false,
          status: 400,
          json: () => Promise.resolve({ erro: "O nome do pão é obrigatório" })
        });
      }
      ok({ ok: true, status: 201, json: () => Promise.resolve({ id: 7, pao: recebido.pao }) });
    }, 10);
  });
}

function App() {
  const [recado, setRecado] = useState("");

  function salvar() {
    enviarPedido({
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: dados
    }).then((r) => {
      if (r.ok) setRecado("Pão salvo");
      else setRecado("Deu erro " + r.status);
    });
  }

  return (
    <div>
      <h1>Encomenda</h1>
      <button onClick={salvar}>Salvar</button>
      {recado && <p>{recado}</p>}
    </div>
  );
}

Com o texto no lugar do objeto, o servidor recebe algo assim no corpo: {"pao":"brioche","quantidade":2}. É a mesma informação, em um formato que qualquer linguagem consegue ler. Repare que o JSON.stringify não "manda o objeto": ele produz uma string, e é a string que viaja.

O caminho de volta é o json(), que a aula de fetch mostrou: texto do corpo vira objeto de novo. Enviar e ler são operações espelhadas, e as duas são conversão de formato, não mágica.

4. O cabeçalho que diz o que é

Texto no corpo pode ser JSON, formulário, XML ou uma poesia. O servidor não adivinha: ele confia no cabeçalho Content-Type. Sem esse cabeçalho, uma API cuidadosa responde 415 — "tipo de mídia não suportado" —, mesmo que o corpo esteja perfeito.

O corpo já vai como JSON, mas falta avisar o formato: o servidor respondeu 415. Acrescente headers: { "Content-Type": "application/json" } nas opções.

As duas exigências andam juntas e o nome é o mesmo: o Content-Type é application/json e o corpo é JSON de verdade. Mandar um sem o outro é como escrever a carta e esquecer o envelope com o endereço.

Existem outros formatos, e cada um tem o seu cabeçalho. Formulário tradicional vai como multipart/form-data (é o que o FormData produz, e o navegador monta o cabeçalho sozinho). Arquivo binário vai como application/octet-stream. Texto puro, como text/plain. Se você usa FormData, nunca defina o Content-Type na mão: o navegador precisa incluir o separador entre os campos, e só ele sabe fazer isso.

5. O que o servidor responde

Um envio aceito devolve 201 e, nas APIs bem feitas, o recurso criado no corpo — com o id novo. Esse id é ouro: é com ele que você monta o próximo pedido ("acompanhar a encomenda 7") e é ele que o suporte vai pedir quando algo der errado.

POST https://loja.test/api/pedidos   201 (Created)   12 ms

Um envio recusado devolve 4xx, e o corpo costuma explicar o motivo. É a parte que muita gente ignora: o código mostra "deu erro" e joga fora a única informação útil que o servidor mandou. No console, a recusa aparece assim:

Failed to load resource: the server responded with a status of 400 (Bad Request)

O console diz que houve 400, mas não diz por quê. O porquê está no corpo — {"erro":"O nome do pão é obrigatório"} — e para lê-lo é preciso chamar json() mesmo quando a resposta é de erro. A caixa abaixo faz exatamente isso.

O servidor recusou por falta do nome do pão e explicou no corpo, mas a tela só diz "Deu erro 400". Leia o corpo da resposta de erro e mostre o campo erro.

function enviarPedido(opcoes) {
  return new Promise((ok) => {
    setTimeout(() => {
      const cabecalhos = opcoes.headers || {};
      if (cabecalhos["Content-Type"] !== "application/json") {
        return ok({
          ok: false,
          status: 415,
          json: () => Promise.resolve({ erro: "Content-Type precisa ser application/json" })
        });
      }
      if (typeof opcoes.body !== "string") {
        return ok({
          ok: false,
          status: 400,
          json: () => Promise.resolve({ erro: "O corpo não é JSON" })
        });
      }
      const recebido = JSON.parse(opcoes.body);
      if (!recebido.pao) {
        return ok({
          ok: false,
          status: 400,
          json: () => Promise.resolve({ erro: "O nome do pão é obrigatório" })
        });
      }
      ok({ ok: true, status: 201, json: () => Promise.resolve({ id: 7, pao: recebido.pao }) });
    }, 10);
  });
}

6. O formulário e a página que recarrega

Em React, o envio costuma sair de um formulário. Se você deixar o comportamento padrão, o navegador envia o formulário do jeito antigo e recarrega a página — o que apaga o estado, perde a lista e faz o componente começar do zero. A prevenção é uma linha:

function enviar(evento) {
  evento.preventDefault();
  salvar();
}

return (
  <form onSubmit={enviar}>
    <input value={pao} onChange={(e) => setPao(e.target.value)} />
    <button type="submit">Encomendar</button>
  </form>
);

O evento.preventDefault() diz ao navegador "eu cuido disso". Sem ele, a página recarrega e você perde o estado do componente: campos voltam vazios, a mensagem de sucesso some, e a impressão é de que o envio não funcionou. Também vale saber que o botão dentro do formulário precisa de type="submit" — e que um botão sem tipo dentro de um formulário já se comporta como submit, o que às vezes envia sem querer.

Depois do sucesso, três coisas costumam acontecer: limpar o formulário, mostrar o número da encomenda e atualizar a lista. Limpar é setPao(""); mostrar, uma mensagem com o id; atualizar, um novo GET — ou, melhor ainda, acrescentar o que voltou do servidor à lista que já está na tela.

7. Não mandar duas vezes

POST cria coisas, e criar duas vezes é criar duas coisas. O cuidado começa na tela: desabilitar o botão enquanto o pedido está no ar resolve o clique duplo. Mas ele não resolve a retentativa automática, o navegador reenviando depois de uma queda, ou o usuário tocando duas vezes em duas abas. Contra isso existe uma proteção do lado do servidor, e é bom saber que ela existe:

chave de idempotência
Um identificador único que o seu código manda no cabeçalho. Se o mesmo identificador chegar duas vezes, o servidor devolve o primeiro resultado em vez de criar outro.
duplo envio
Dois pedidos iguais por clique duplo ou retentativa. O sintoma é a encomenda duplicada na listagem.
retentativa segura
Tentar de novo só quando a operação pode ser repetida sem efeito colateral extra.

No navegador, a parte que está ao seu alcance é simples: estado de envio que desabilita o botão, e nenhuma retentativa automática em POST sem antes conversar com quem fez a API. Se a sua API não tem chave de idempotência, tentar de novo depois de um tempo limite pode duplicar o pedido — e aí o erro menor vira o maior.

8. Cancelar um envio

A aula de cancelamento mostrou o signal; em POST ele funciona igual, mas o efeito prático é diferente. Cancelar do lado do navegador fecha a conexão, e o servidor pode já ter gravado o pedido. Ou seja: cancelar não desfaz a escrita. Se o usuário desiste no meio do envio, a tela deve dizer algo honesto — "cancelamos o envio; se o pedido aparecer na lista, não é duplicata" — em vez de fingir que nada aconteceu.

Por isso, em escrita, o cancelamento costuma ser usado em outro lugar: quando a tela é desmontada e o pedido não faz mais sentido, ou quando o mesmo formulário é enviado duas vezes e o primeiro pedido já não interessa. Na dúvida, prefira deixar terminar e perguntar depois.

9. Cenários do dia a dia

Cenário 1: a encomenda vazia

A Ana mandou o objeto cru no corpo e o servidor respondeu 400. No painel de rede, o corpo enviado aparecia como [object Object] — o navegador convertendo o objeto do jeito genérico. O conserto foi JSON.stringify; o hábito que evita é o mesmo: antes de enviar, imprima o corpo no console e veja se ele é texto JSON de verdade.

Cenário 2: o pedido que chegou duas vezes

A cliente tocou duas vezes no botão, o envio demorou e dois pedidos foram criados. A tela não desabilitava o botão durante o envio. A correção foi disabled={enviando} com o rótulo "Enviando...", e a padaria passou a conferir duplicatas pelo nome e telefone enquanto a API não tivesse chave de idempotência.

Cenário 3: o erro que não dizia nada

O servidor recusou porque o endereço não tinha número, e a tela mostrou "Deu erro 400". Ninguém sabia o que corrigir. A mudança foi ler o corpo da resposta de erro e exibir o campo erro. Vale lembrar: a mensagem do servidor é escrita por quem conhece a regra — use a dela antes de inventar a sua.

Exercício: a encomenda em texto

Complete o corpo do envio, convertendo o objeto para JSON:

fetch("/api/pedidos", { method: "POST", headers: { "Content-Type": "application/json" }, body: (pedido) });

Dica: é a função que transforma objeto em texto JSON, com o nome em maiúsculas no começo. Sem ela, o servidor recebe [object Object].

11. Resumo

Enviar dados é POST com três peças: method, headers com Content-Type: application/json e body como texto, produzido por JSON.stringify. Objeto no corpo vira [object Object] e o servidor recusa; cabeçalho faltando vira 415.

Sucesso costuma ser 201, com o recurso criado no corpo — guarde o id. Recusa é 4xx com o motivo no corpo: leia com json() e mostre o texto do servidor, porque ele explica o que faltou melhor do que qualquer mensagem genérica. Erro 500 é do servidor, e aí a mensagem é sua.

No formulário, evento.preventDefault() evita a recarga; no botão, disabled evita o envio duplo. E cancelar não desfaz uma escrita: em POST, prefira deixar terminar a interromper no meio. Na próxima aula, o formato que está no meio de tudo isso: o JSON, com suas regras, seus erros de vírgula e o ida e volta entre texto e objeto.

Para lembrar

  • POST leva corpo; GET leva tudo na URL.
  • body é texto: use JSON.stringify.
  • Content-Type: application/json avisa o formato.
  • 201 é sucesso de criação; confira com resposta.ok.
  • O motivo da recusa está no corpo, com json().
  • evento.preventDefault() evita a página recarregar.
  • disabled no botão evita o envio duplo.
  • Cancelar não desfaz o que o servidor já gravou.
