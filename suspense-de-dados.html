Suspense de Dados

A Ana já sabe mostrar “carregando” com três estados: um para o pedido em andamento, um para o erro e um para o resultado. Funciona, mas o mesmo bloco de if aparece em toda tela do site dela. Nesta aula ela conhece o Suspense: uma fronteira que diz “enquanto este pedaço não estiver pronto, mostre isto”, e um jeito de ler o dado que combina com ela. O painel das caixas vai mostrar o fallback sem susto — é ele que aparece antes de o valor chegar.

Você vai aprender
  • O que o Suspense faz e o que ele não faz.
  • O que é uma fronteira e o que é o fallback.
  • Como um componente “suspende”: lançando a promessa em vez de devolver JSX.
  • Por que o resultado só aparece quando a leitura devolve valor.
  • Como colocar cada peça na sua própria fronteira.
  • O que faz o React desenhar de novo depois que o dado chega.
  • Quando Suspense é melhor do que os três estados, e quando não é.

1. A cena: o preço que chega depois

O preço do pão do dia muda toda manhã. O site da Ana pega esse preço de um serviço que ela mesma mantém, e a resposta leva alguns instantes. Até agora, ela resolveu isso do jeito que as aulas de Buscando Dados e Carregando e Erro ensinaram: um estado para o valor, um para o carregando, um para o erro, e um if no JSX escolhendo o que desenhar.

O problema não é o resultado, é a repetição. Cada peça que busca alguma coisa repete os mesmos três estados e os mesmos três if. E quando uma tela tem quatro peças buscando ao mesmo tempo, o carregando de cada uma aparece em um lugar diferente, em um momento diferente, e a tela pisca em quatro lugares.

O Suspense propõe outra divisão de trabalho. Em vez de cada componente decidir o que mostrar enquanto espera, ele simplesmente para — e quem está em volta decide o que aparece no lugar. O componente que lê o dado não sabe que existe um carregando; a fronteira não sabe que dado é aquele. Cada um cuida do seu pedaço.

2. A fronteira e o fallback

Três palavras resolvem o vocabulário. A fronteira é o componente Suspense: ele embrulha um pedaço da árvore. O fallback é o que ele desenha enquanto alguma coisa lá dentro está esperando. E suspender é o ato de um componente avisar “ainda não tenho o que desenhar”.

Suspense
O componente de fronteira: <Suspense fallback={…}>. Ele não busca nada e não guarda dado.
fallback
O JSX que a fronteira mostra enquanto um filho está suspenso. Costuma ser um texto curto ou um esqueleto da tela.
suspender
Lançar uma promessa de dentro do render, em vez de devolver JSX. O React segura aquele pedaço e espera.
recurso
Um objeto com o valor já lido e a promessa do que ainda está vindo. É o cache que a leitura consulta.
fronteira mais próxima
Quando um componente suspende, quem mostra o fallback é o Suspense mais próximo acima dele.
streaming
O envio da página em pedaços, cada um assim que fica pronto. É o Suspense do lado do servidor; aqui o assunto é o lado do navegador.

Duas coisas que o Suspense não faz, e que confundem muita gente. Primeiro: ele não busca dados. Ele não tem endereço, não tem fetch, não sabe o que é preço. Ele só desenha o fallback enquanto um filho está suspenso. Segundo: ele não guarda o resultado. O dado mora no recurso, ou no estado de quem buscou; a fronteira só decide o que aparece na espera.

Quem suspende é o componente que lê. E ele suspende de um jeito estranho à primeira vista: em vez de devolver JSX, ele lança uma promessa. O React reconhece esse lançamento, procura a fronteira mais próxima e mostra o fallback dela. Quando a promessa termina, o React tenta desenhar o componente de novo — e, se agora a leitura devolver valor, o conteúdo aparece.

3. A caixa: o fallback só sai quando a leitura devolve valor

Na caixa abaixo, o preço já chegou: o recurso está com pronto: true e o valor é 12. Mas o lerPreco sempre lança a promessa, sem olhar o recurso. Resultado: a fronteira mostra o fallback para sempre, mesmo com o dado na mão.

O lerPreco esqueceu de devolver o valor quando o recurso está pronto. Faça ele devolver recurso.valor nesse caso e clique em Rodar.

const recurso = { pronto: true, valor: 12 };

function lerPreco() {
  throw new Promise(function () {});
}

function Preco() {
  const preco = lerPreco();
  return <p>Pão do dia: R$ {preco},00</p>;
}

function App() {
  return (
    <React.Suspense fallback={<p>Carregando o preço…</p>}>
      <Preco />
    </React.Suspense>
  );
}
<p>Carregando o preço…</p>

const recurso = { pronto: true, valor: 12 };

function lerPreco() {
  if (recurso.pronto) return recurso.valor;
  throw new Promise(function () {});
}

function Preco() {
  const preco = lerPreco();
  return <p>Pão do dia: R$ {preco},00</p>;
}

function App() {
  return (
    <React.Suspense fallback={<p>Carregando o preço…</p>}>
      <Preco />
    </React.Suspense>
  );
}

Repare no painel: ele mostra o fallback, e isso está certo — é o que a tela desenha enquanto a leitura não devolve valor. O erro é que a leitura nunca devolve. Com uma linha de if, o componente passa a devolver o preço, e o React troca o fallback pelo conteúdo.

Guarde a forma da função, porque ela é o coração do assunto. A leitura tem três saídas possíveis: devolver o valor quando ele já está no recurso, lançar a promessa quando ainda não está, e devolver o valor quando a promessa termina. A primeira e a última são iguais — o valor está lá, então devolve. A do meio é a única que suspende.

4. De onde vem a promessa

Na caixa, a promessa nunca termina, para você ver o fallback parado. Num projeto de verdade, quem cria a promessa é o pedido, e quem guarda o estado é o recurso. O arquivo costuma ficar assim:

const recurso = { pronto: false, valor: null, promessa: null };

export function carregarPreco() {
  if (recurso.pronto) return recurso.valor;
  if (!recurso.promessa) {
    recurso.promessa = fetch("/api/preco-do-dia")
      .then(function (resposta) { return resposta.json(); })
      .then(function (dados) {
        recurso.valor = dados.preco;
        recurso.pronto = true;
        return dados.preco;
      });
  }
  throw recurso.promessa;
}

A primeira chamada cria a promessa e lança. A segunda, depois que a promessa termina, encontra pronto: true e devolve o número. Repare que o fetch fica dentro do if: sem isso, cada desenho dispararia um pedido novo — o tropeço clássico de quem transforma busca em suspensão.

No React 19 existe um atalho para a leitura: o hook use, que aceita uma promessa e devolve o valor dela, suspendendo enquanto ela não termina. Nas caixas deste guia ele não está no escopo, então o nome completo é React.use. O componente fica assim:

function Preco() {
  const dados = React.use(recurso.promessa);
  return <p>Pão do dia: R$ {dados.preco},00</p>;
}

É mais curto, e é a forma que você vai encontrar em código novo. O que ele faz por dentro é exatamente o que a caixa mostra: guarda a promessa, lança enquanto está pendente e devolve o valor quando termina. Entender a versão longa primeiro é o que permite reconhecer o padrão quando ele aparece escondido dentro de uma biblioteca.

5. Uma fronteira por peça

Agora o detalhe que decide a qualidade da tela. Quando um componente suspende, ele derruba tudo que está dentro da mesma fronteira. Se o preço já chegou e o estoque não, e os dois estão na mesma fronteira, o visitante vê o fallback dos dois — perdendo a informação que já estava pronta.

O preço já chegou, mas o estoque não, e os dois dividem a mesma fronteira: a tela inteira espera. Ponha uma <React.Suspense> em volta de cada peça, com o fallback certo para cada uma.

const preco = { pronto: true, valor: 12 };
const estoque = { pronto: false, quantos: 0 };

function Preco() {
  if (!preco.pronto) throw new Promise(function () {});
  return <p className="preco">R$ {preco.valor},00</p>;
}

function Estoque() {
  if (!estoque.pronto) throw new Promise(function () {});
  return <p>{estoque.quantos} unidades</p>;
}

function App() {
  return (
    <React.Suspense fallback={<p>Carregando…</p>}>
      <Preco />
      <Estoque />
    </React.Suspense>
  );
}

}

O painel agora mostra duas coisas ao mesmo tempo: o preço que chegou e o fallback do estoque. É exatamente o que a pessoa vê, e é muito melhor do que uma tela vazia esperando o pedaço mais lento. A regra prática: fronteira em volta do que aparece junto. Se duas informações chegam em momentos diferentes, elas não podem dividir a mesma espera.

Há um detalhe a mais quando a peça pode trocar de dado: um Suspense guarda o estado da espera. Se o Preco passa a ler outro produto, a fronteira continua mostrando o conteúdo antigo até o novo chegar. Para começar do zero, dê uma key à fronteira com o identificador do dado — key={produto.id} — e o React trata aquilo como uma fronteira nova, com o fallback do começo.

Existe um custo nisso. Muitas fronteiras pequenas produzem uma tela que “monta em pedaços”, com saltos de layout a cada fallback que some. A saída costuma ser combinar: uma fronteira por área da tela, e o fallback com o mesmo tamanho do conteúdo para o layout não pular. Suspense não é sobre ter uma fronteira por componente; é sobre ter a fronteira no lugar em que a espera faz sentido.

6. Quando o dado chega, alguém precisa desenhar de novo

O Suspense não fica vigiando o recurso. Ele mostra o fallback e espera por um novo desenho: o React tenta de novo quando a promessa que foi lançada termina. Se o valor aparece no recurso por outro caminho — uma resposta que já chegou, um cache preenchido por fora —, nada acontece até alguém pedir um novo desenho.

O botão preenche o recurso, mas a tela continua no fallback: falta um estado que peça ao React para desenhar de novo. Acrescente setVersao(versao + 1) no fim do chegarPedido.

const recurso = { pronto: false, valor: null };

function lerPreco() {
  if (recurso.pronto) return recurso.valor;
  throw new Promise(function () {});
}

function Preco() {
  const preco = lerPreco();
  return <p>Pão do dia: R$ {preco},00</p>;
}

function App() {
  const [versao, setVersao] = useState(0);

  function chegarPedido() {
    recurso.pronto = true;
    recurso.valor = 12;
  }

  return (
    <div>
      <button onClick={chegarPedido}>Chegou o preço</button>
      <React.Suspense fallback={<p>Carregando o preço…</p>}>
        <Preco />
      </React.Suspense>
    </div>
  );
}
<div>

</div>

    </div>

}

Depois do clique, o React desenha de novo, o lerPreco encontra o valor e o fallback sai de cena. No projeto de verdade você não precisa desse botão: quem avisa é a promessa lançada, que o React observa. A caixa usa um botão só para você ver o mecanismo com os próprios olhos — sem promessa terminando, o único jeito de pedir outro desenho é mudar o estado.

Vale reparar em um detalhe: a variável versao não aparece em lugar nenhum do JSX. Ela existe só para o React saber que algo mudou. É o mesmo truque de “atualizar a tela” que você já viu em outras aulas, e ele aparece em bibliotecas de dados o tempo todo: um contador interno que força o redesenho depois que o cache mudou.

7. Suspense ou os três estados?

As duas abordagens continuam válidas, e a escolha depende de onde a espera mora. Os três estados são locais: cada componente sabe que está esperando e desenha o próprio aviso. O Suspense é da árvore: quem está em volta decide a espera, e o componente que lê não precisa saber que existe um carregando.

PerguntaTrês estadosSuspense
quem decide o que aparece na espera?o próprio componentea fronteira acima dele
onde fica o dado?no useState do componenteno recurso, fora do componente
quantos if a tela tem?um por peça que buscanenhum dentro da peça
o que acontece se um pedido falhar?o componente desenha o erroprecisa de um error boundary por perto
quando é a escolha natural?uma peça buscando sozinhavárias peças, cada uma com seu tempo

Um efeito colateral bom do recurso é que ele sobrevive à navegação. Se a Ana sai da tela de preços e volta, a segunda visita não espera nada: o valor já está no cache e a leitura devolve na hora. Com os três estados, o useState morre junto com o componente e o pedido recomeça. Esse é o tipo de ganho que aparece sem você pedir, só por guardar o dado no lugar certo.

Repare na quarta linha, que costuma ser esquecida: Suspense não trata erro. Uma promessa que rejeita não vira “deu errado” na tela — ela precisa de um error boundary, um componente que captura o erro de um ramo da árvore. No React, isso ainda é uma classe com componentDidCatch, e é assunto para outra aula. Por enquanto, guarde a regra: fronteira para a espera, boundary para o erro.

8. As armadilhas

Quatro erros aparecem em quase toda primeira implementação. Nenhum deles dá mensagem clara — o sintoma é sempre uma tela que fica no fallback ou que pisca sem parar.

SintomaCausaConserto
o fallback nunca saia leitura sempre lança, mesmo com o valor prontodevolver o valor quando o recurso estiver pronto
a tela pisca sem pararo fetch está fora do if: nova promessa a cada desenhocriar a promessa uma vez e guardar no recurso
a peça pronta some juntoas duas peças dividem a mesma fronteirauma fronteira por área da tela
o erro derruba tudopromessa rejeitada sem error boundaryenvolver o ramo com um boundary

A segunda linha é a mais traiçoeira, porque o código parece certo. Se cada desenho cria uma promessa nova, o React lança, espera, tenta de novo, cria outra promessa e lança outra vez — para sempre. O sintoma é um fallback que pisca em ritmo de batida. A cura é o recurso lembrar da promessa:

pedindo o preço…
preço chegou: 12
desenhando: R$ 12,00

Já a versão quebrada repete o pedido a cada desenho, e o console denuncia na hora:

pedindo o preço…
pedindo o preço…
pedindo o preço…
pedindo o preço…

Quatro linhas iguais em um segundo querem dizer que a promessa está sendo criada dentro do render, e não dentro do recurso. É o mesmo sintoma de uma tela que pisca: cada tentativa começa do zero.

As três linhas de antes vêm de um recurso com um console.log na criação da promessa e outro no componente. Repare que “pedindo o preço” aparece uma vez só: a promessa foi criada na primeira leitura e reaproveitada nas seguintes. Se a sua aparecer repetida, o cache está sendo refeito a cada desenho.

9. Cenários do dia a dia

Cenário 1: o carrinho que esperava o frete

O carrinho da Ana mostrava os itens e o frete. Os itens vinham do estado, o frete de um serviço externo, e os dois estavam na mesma fronteira: enquanto o frete não chegava, o visitante não via nem os itens. Separar em duas fronteiras devolveu a lista na hora e deixou o frete com o seu próprio “calculando…”.

Cenário 2: o preço que voltava ao carregando

Ela colocou o fetch dentro do componente, no corpo do render. Cada desenho criava uma promessa nova, o componente suspendia de novo e a tela piscava sem parar. A correção foi mover o pedido para o recurso, com a promessa guardada e a leitura devolvendo o valor assim que ele chega.

Cenário 3: o erro que virou tela em branco

A promessa do estoque rejeitou porque o serviço estava fora do ar, e a tela ficou em branco: sem error boundary, um erro de render derruba o ramo inteiro. Ela aprendeu a diferença na prática — Suspense cuida da espera, o boundary cuida da falha, e os dois costumam andar juntos.

Exercício: a leitura que devolve o valor

Complete a função de leitura para ela não suspender quando o recurso já estiver pronto.

function lerPreco() { if (recurso.pronto) return ; throw recurso.promessa; }

Dica: é o campo onde a resposta já está guardada. Sem essa linha, o componente lança a promessa para sempre e o fallback nunca sai.

11. Resumo

Suspense é uma fronteira, não uma busca. Ele embrulha um pedaço da árvore e mostra o fallback enquanto algum filho está suspenso. Quem suspende é o componente que lê o dado, lançando a promessa em vez de devolver JSX. Quando a promessa termina, o React tenta desenhar de novo; se a leitura agora devolve valor, o conteúdo entra no lugar do fallback.

O dado mora no recurso, fora do componente: o valor já lido, a promessa em andamento e um jeito de saber qual dos dois usar. A leitura tem sempre a mesma forma — devolve se tem, lança se não tem. E a promessa é criada uma vez, dentro do if; criá-la a cada desenho é o que faz a tela piscar.

O resto é posicionamento de fronteira: em volta do que aparece junto, não em volta de cada componente. Uma peça pronta não deve esperar pela peça lenta, e um erro não se resolve com fallback — se resolve com error boundary. Na próxima aula o assunto continua no React 19, agora do lado dos formulários: como o atributo action substitui o onSubmit em Formulários com Actions.

Para lembrar

  • Suspense é fronteira: mostra o fallback enquanto um filho espera.
  • Quem suspende lança a promessa no render; não devolve JSX.
  • A leitura devolve o valor se ele já está no recurso; senão, lança.
  • A promessa se cria uma vez, guardada no recurso.
  • Cada área da tela merece a sua fronteira.
  • O React redesenha quando a promessa lançada termina.
  • Sem promessa terminando, só um novo desenho (estado) faz o valor aparecer.
  • Erro não é espera: precisa de error boundary.
  • Fallback do tamanho do conteúdo evita o salto de layout.
  • Três estados para uma peça; Suspense quando várias esperam em tempos diferentes.
