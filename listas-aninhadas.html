Listas Aninhadas

A Ana organiza as encomendas por cliente: cada pessoa tem uma lista de pães, e cada pão tem preço. Na tela, isso vira uma lista dentro de outra — Maria com dois pedidos, João com um, Bia com dois. Ela tenta escrever um map dentro do outro e o resultado é uma bagunça de chaves e parâmetros com o mesmo nome. Nesta aula ela aprende a desenhar listas aninhadas sem se perder: onde fica cada map, onde fica cada key e como calcular o total de cada grupo.

Você vai aprender
  • Como é um dado aninhado: array de objetos que contêm arrays.
  • Como escrever um map dentro de outro sem embolar os nomes.
  • Por que a lista interna fica dentro de um <li>, e não solta dentro do <ul>.
  • Que cada nível precisa da sua própria key.
  • Como somar e contar por grupo com reduce.
  • O que fazer com grupo vazio e com grupo que o filtro esvaziou.
  • Quando achatar tudo com flatMap.

1. A cena: o caderno por cliente

No caderno da Ana, cada página é de um cliente. No topo, o nome; abaixo, os pães que aquela pessoa encomendou. Maria levou brioche e sonho. João levou pão de queijo. Bia levou croissant e broa. É uma lista de listas, e essa forma não é invenção do React: é como os dados chegam de qualquer sistema de pedidos.

Na aula Listas com map, a lista era de textos e um map resolvia. Aqui cada item tem um pedaço que também é lista. Desenhar isso exige dois map: um para percorrer os clientes, outro, dentro do primeiro, para percorrer os pedidos de cada cliente.

O resultado na tela é uma lista aninhada — e a estrutura do HTML precisa acompanhar. Um <ul> dentro de outro <ul> é inválido; a lista interna mora dentro do <li> do cliente. O navegador até “conserta” o inválido, mas o conserto dele não é o que você escreveu, e aí o CSS e os leitores de tela se perdem.

O desafio real não é a sintaxe: é não se perder nos nomes. Dois map aninhados com o parâmetro chamado item nos dois níveis é a receita para usar o item errado. Nomes específicos resolvem mais do que qualquer truque.

2. O dado aninhado

Antes da tela, o dado. Cada cliente é um objeto com id, nome e uma propriedade pedidos que é um array:

const clientes = [
  { id: 1, nome: "Maria", pedidos: [
    { id: 11, pao: "Brioche", valor: 8 },
    { id: 12, pao: "Sonho", valor: 5 }
  ] },
  { id: 2, nome: "João", pedidos: [
    { id: 21, pao: "Pão de queijo", valor: 4 }
  ] },
  { id: 3, nome: "Bia", pedidos: [
    { id: 31, pao: "Croissant", valor: 7 },
    { id: 32, pao: "Broa de fubá", valor: 6 }
  ] }
];

Três clientes, cinco pedidos no total. Repare que os id são diferentes em cada nível: 1, 2 e 3 para clientes; 11, 12, 21, 31, 32 para pedidos. Essa numeração separada não é capricho — é o que permite usar o id como key sem colisão entre listas diferentes.

> clientes.length
3
> clientes[0].pedidos.length
2
> clientes.map((c) => c.pedidos.length)
[2, 1, 2]

Três grupos e cinco pedidos: é essa a conta que o JSX precisa reproduzir. Quando o número de itens na tela não bate com a soma dos tamanhos, há um map faltando ou um array errado no lugar.

Uma pergunta que sempre aparece: “por que não uma lista só, com o nome do cliente repetido em cada pedido?”. Dá para fazer, e às vezes é o formato que a API entrega. A diferença é de leitura: agrupado, “quanto a Maria deve” é cliente.pedidos; achatado, é um filter por nome seguido de uma soma. Os dois modelos funcionam, e a seção 8 mostra como converter um no outro.

O importante agora é reconhecer o formato. Se o seu dado tem arrays dentro de arrays, você vai precisar de map aninhado — ou de um achatamento antes de desenhar.

3. O map dentro do map

Comece pelo nível de fora, como sempre. Para cada cliente, um <li> com o nome e uma lista interna. Dentro dessa lista interna, o segundo map percorre os pedidos:

<ul>
  {clientes.map((cliente) => (
    <li className="grupo" key={cliente.id}>
      <strong>{cliente.nome}</strong>
      <ul>
        {cliente.pedidos.map((pedido) => (
          <li className="item" key={pedido.id}>{pedido.pao}</li>
        ))}
      </ul>
    </li>
  ))}
</ul>

clientes (array)<ul>o componente
cliente (objeto)<li className="grupo">o <ul> externo
cliente.pedidos (array)<ul>o <li> do cliente
pedido (objeto)<li className="item">o <ul> interno

Leia de fora para dentro: o primeiro map recebe um cliente por vez; o segundo recebe cliente.pedidos, que é o array daquele cliente. O parâmetro pedido existe só ali dentro. No fim, o HTML tem uma lista externa com três itens, e cada item carrega uma lista interna.

A estrutura é o que garante que o navegador entenda. Se você colocar o <ul> interno como irmão do <li>, e não dentro dele, o HTML fica inválido e o leitor de tela perde a relação entre cliente e pedidos. A regra é simples: lista dentro de item, nunca lista dentro de lista direto.

E por que não desenhar os pedidos como texto separado por vírgula? Para dois pães, funciona. Para dez, vira um parágrafo ilegível, e você perde a capacidade de dar key, clicar em cada pedido ou remover um só. A lista interna é o que mantém cada pedido sendo um pedido.

A tela mostra só os nomes dos clientes. Desenhe, dentro de cada grupo, a lista dos pedidos daquele cliente — com classe item em cada pedido.

4. Uma key em cada nível

São duas listas, então são duas key. A do cliente identifica o <li> externo; a do pedido identifica o <li> interno. Esquecer a de dentro não quebra a tela, mas deixa o React sem saber qual pedido é qual quando a lista muda.

O erro clássico é usar a mesma chave para todos os níveis. Se dois clientes têm o pedido de id 1, não há problema: as chaves só precisam ser únicas entre irmãos. O React compara as chaves dentro da mesma lista; listas diferentes vivem em espaços diferentes. É por isso que a numeração separada do exemplo funciona.

O segundo erro clássico é usar o índice do map interno. Quando a Ana remove o primeiro pedido da Maria, todos os índices mudam e o React reaproveita os elementos errados — o foco do teclado salta, a animação vai para o lugar errado. Use o id do pedido; é para isso que ele existe.

Uma terceira opção é uma chave composta, como ${cliente.id}-${pedido.id}, útil quando os ids vêm de fontes diferentes e podem coincidir dentro do mesmo nível. Se você chegou a precisar disso, o código já está pedindo um id único de verdade — mas funciona.

5. Nomes que não se perdem

Dois map aninhados com o mesmo nome de parâmetro é a fonte de metade dos bugs desta aula. Se os dois se chamam item, o de dentro esconde o de fora, e uma referência a item.nome pode estar falando do pedido em vez do cliente. O código compila, roda e mostra errado.

A convenção que salva: plural no array, singular no parâmetro. clientes vira cliente; pedidos vira pedido. Quando os nomes são específicos, você lê a linha e sabe de quem está falando sem procurar onde o parâmetro foi declarado.

Vale também nomear o nível intermediário quando o JSX cresce. Em vez de escrever tudo num return gigante, extraia um componente GrupoDePedidos que recebe um cliente e desenha o grupo. O componente de fora fica com um map só, e o de dentro com outro — cada um no seu escopo, cada um com seus nomes. O guia trata dessa divisão em Quando Quebrar em Componentes.

Esse movimento tem um bônus: o grupo passa a ser testável e reutilizável. A mesma lista aninhada pode aparecer no painel, no recibo e no e-mail de confirmação, com o mesmo componente e dados diferentes.

6. Contar e somar por grupo

Com listas aninhadas, as perguntas ficam por grupo: quantos pedidos a Maria fez? Quanto ela vai pagar? As duas respostas são contas sobre cliente.pedidos, feitas na hora de desenhar.

const total = cliente.pedidos.reduce(
  (soma, pedido) => soma + pedido.valor,
  0
);

<strong>{cliente.nome} — R$ {total}</strong>
> clientes[0].pedidos.reduce((soma, p) => soma + p.valor, 0)
13
> clientes.flatMap((c) => c.pedidos).length
5

O reduce percorre o array e vai acumulando. O primeiro parâmetro é o acumulador — aqui, soma —; o segundo é o item; e o 0 no fim é o valor inicial. Sem o zero, o reduce começa pelo primeiro item e o resultado de uma lista vazia é um erro. Com o zero, lista vazia soma zero, que é a resposta honesta.

O total é derivado: não vai para o estado. Se ele fosse guardado, cada pedido novo exigiria atualizar dois lugares, e mais cedo ou mais tarde um deles ficaria para trás. Calcular no render é sempre coerente, porque parte do mesmo array que está na tela.

Cada grupo mostra o nome, mas não o total. Acrescente ao nome o valor somado dos pedidos, no formato “Maria — R$ 13”, usando reduce com valor inicial zero.

Aqui o map deixou de ter retorno implícito: como precisamos calcular o total antes do return, o callback ganhou chaves e um return explícito. Dado em que um item contém outro array. Clientes com pedidos dentro é o exemplo da aula.
map interno
O segundo map, que percorre cliente.pedidos e roda uma vez por grupo.
reduce
Percorre o array acumulando um valor: reduce((soma, item) => soma + item.valor, 0).
flatMap
Transforma cada grupo e junta tudo num array só — o achatamento do aninhado.

Chave formada por dois ids, como cliente.id + "-" + pedido.id, quando um id só não é único no nível.

7. Grupo vazio e grupo escondido

Um cliente sem pedidos ainda é um cliente: ele aparece na lista, com o nome e uma frase no lugar da lista interna. Isso é diferente de um grupo que ficou vazio porque o filtro não achou nada nele — e a diferença decide se o grupo aparece ou desaparece.

<ul>
  {cliente.pedidos.length === 0 ? (
    <li className="vazio">Sem pedidos nesta semana.</li>
  ) : (
    cliente.pedidos.map((pedido) => (
      <li className="item" key={pedido.id}>{pedido.pao}</li>
    ))
  )}
</ul>

Já na busca, o comportamento esperado é outro: grupos sem nenhum pedido que combine não devem ocupar espaço. A solução é filtrar os clientes antes de desenhar, montando uma lista derivada em que cada cliente carrega só os pedidos que passaram no teste:

const grupos = clientes
  .map((cliente) => ({
    ...cliente,
    pedidos: cliente.pedidos.filter((pedido) =>
      pedido.pao.toLowerCase().includes(busca.toLowerCase())
    )
  }))
  .filter((cliente) => cliente.pedidos.length > 0);

São duas etapas de propósito: primeiro cada grupo é reduzido aos pedidos que combinam; depois os grupos que sobraram vazios são descartados. Inverter a ordem — filtrar clientes primeiro — não funciona, porque o teste é sobre o pedido, não sobre o cliente.

Digite “queijo”: o pedido certo aparece, mas os grupos dos outros clientes continuam na tela, vazios. Filtre os grupos vazios depois de filtrar os pedidos, para sobrar só o grupo do João.

Se você digitar “queijo” e continuar vendo três grupos, falta o segundo filter; se a tela ficar sem nada, o filtro de pedidos está comparando o campo errado. E se nenhum grupo aparecer com a busca vazia, o segundo filter está olhando a lista errada — provavelmente clientes, que nunca fica vazia.

8. Achatar quando a tela é uma lista só

Nem toda tela quer o agrupamento. Às vezes você precisa de todos os pedidos numa sequência única: para somar o faturamento do dia, para ordenar por preço ou para mostrar um recibo. O flatMap faz isso em uma passada: transforma cada cliente no seu array de pedidos e junta tudo num array só.

const todos = clientes.flatMap((cliente) => cliente.pedidos);

const faturamento = todos.reduce((soma, pedido) => soma + pedido.valor, 0);

Cinco pedidos, um array. A partir daí valem as ferramentas de sempre: filter para a busca, sort para a ordem, map para desenhar. Se você precisar saber de quem é cada pedido depois do achatamento, inclua o nome no objeto antes de juntar:

const todos = clientes.flatMap((cliente) =>
  cliente.pedidos.map((pedido) => ({ ...pedido, cliente: cliente.nome }))
);

Esse é o caminho inverso do agrupamento: o dado achatado é melhor para somar e comparar; o agrupado é melhor para mostrar quem pediu o quê. Converter entre os dois é barato — e fazer isso no render, com dados derivados, evita manter duas versões da verdade.

MétodoO que devolvePara que serve aqui

Uma ressalva: achatar por achar mais simples pode custar a informação de grupo. Se a tela precisa de “Maria com dois pedidos”, não achate. Escolha o formato pela pergunta que a tela responde, não pela facilidade do código.

9. Cenários do dia a dia

Cenário 1: o HTML sai com um “ul” solto

A Ana colocou o <ul> interno como irmão do <li>, fora dele. O navegador reorganiza o HTML por conta própria, e o CSS deixa de encontrar a lista dentro do item. Lista interna mora dentro do <li> do grupo — sempre.

Cenário 2: todos os pedidos aparecem no primeiro cliente

Ela percorreu clientes no segundo map, em vez de cliente.pedidos. O resultado é a lista inteira repetida em cada grupo — cinco pedidos em cada um. O parâmetro do map interno deve ser o array do cliente atual.

Cenário 3: a busca esconde os pedidos, mas não os grupos

O filtro foi aplicado só no map interno, então cada cliente continua na tela, alguns com a lista vazia. Filtre os pedidos e depois descarte os grupos sem pedidos. O vazio que sobra é de busca, e a mensagem geral dele é assunto da aula Estados Vazios.

11. Resumo

Lista aninhada é dado aninhado, e o desenho acompanha: um map para os grupos e outro, dentro do <li> de cada grupo, para os itens. A lista interna fica dentro do item, nunca como irmã dele. Cada nível ganha a sua key, com o id daquele nível.

Nomes específicos — cliente, pedido — evitam que um parâmetro esconda o outro. Totais por grupo saem de reduce com valor inicial zero, calculados no render: o total é consequência dos pedidos, não um estado separado.

Grupo vazio de verdade mostra uma frase; grupo esvaziado pelo filtro desaparece. E quando a tela pede uma lista só, flatMap achata o aninhado — lembrando que o formato do dado deve seguir a pergunta da tela.

Com isso você fechou o conjunto de listas do nível: desenhar, dar key, filtrar, ordenar, paginar e aninhar. Tabela, estado vazio e busca aparecem em cada uma delas, e sempre com a mesma ideia por baixo — o estado guarda o mínimo, o render calcula o resto, e a tela é consequência.

Para lembrar

  • Aninhado pede map dentro de map.
  • O ul interno fica dentro do li do grupo.
  • Uma key por nível, com o id daquele nível.
  • Plural no array, singular no parâmetro: clientes / cliente.
  • Total do grupo: reduce((soma, item) => soma + item.valor, 0).
  • Calcule totais no render; não os guarde no estado.
  • Grupo sem itens por natureza mostra mensagem; grupo esvaziado por filtro some.
  • Filtre os itens e depois descarte os grupos vazios.
  • flatMap junta os arrays num só; use quando a tela é uma lista única.
  • Achatar é barato, mas perde o agrupamento: escolha pelo que a tela responde.
