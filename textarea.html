Textarea

O bolo de aniversário da padaria da Ana vem com um recado escrito na cobertura, e o cliente precisa de espaço para escrever mais de uma linha: "Parabéns, Ana" numa linha e "com muito carinho da família" na outra. O campo de uma linha do cadastro não serve — ele esconde o texto quando passa da largura e não aceita Enter. Nesta aula a Ana troca o input pelo textarea, aprende onde o texto mora (e onde ele não mora), conta os caracteres e faz a prévia respeitar as quebras de linha.

Você vai aprender

  • Como ligar o textarea ao estado com value e onChange.
  • Por que o texto não vai entre as tags no React.
  • Como contar os caracteres e limitar com maxLength.

  • Como controlar altura com rows e com CSS.

1. A cena: o recado que precisa de linhas

A padaria vende bolo por encomenda e o cliente escolhe a mensagem escrita na cobertura. A Ana começou com um input comum, do mesmo tipo que ela já usa no cadastro. O primeiro cliente escreveu "Parabéns, Ana. Com muito carinho, vó Maria e toda a família" — e o campo engoliu a frase numa linha só, rolando para a direita, com o começo escondido. Quando ela imprimiu a comanda, o recado saiu cortado.

O problema não é o tamanho do campo, é a tag. Um input é, por definição, uma linha: o Enter não cria linha nova e o texto longo escorre para fora da vista. Para várias linhas existe o textarea, um elemento próprio, com altura, rolagem interna e quebras de linha de verdade. A troca parece pequena no código e muda bastante a experiência de quem escreve.

A boa notícia é que o mecanismo de estado continua o mesmo: value mostrando e onChange devolvendo o texto. O textarea tem, porém, duas manias que atrapalham quem vem do HTML puro: o valor não é atributo e o texto não vai entre as tags. É sobre isso que a aula trata, além do que fazer com as linhas.

2. O que muda em relação ao input

No HTML antigo, um textarea recebia o texto inicial entre as tags: <textarea>oi</textarea>. No React isso não funciona como valor; o valor vem do estado, e as tags ficam vazias. Guarde essa diferença, porque ela é a origem do erro mais comum da aula. As demais peças são parecidas:

textarea
A tag de campo com várias linhas. Tem abertura e fechamento — não é uma tag vazia como input.
rows
Quantas linhas de altura o campo mostra de saída. É uma dica de tamanho, não um limite de conteúdo.
value e onChange
O mesmo par do input: o valor vem do estado e cada tecla devolve o texto novo.
quebra de linha
O caractere \n que o Enter insere no texto. Existe no valor, mas não aparece sozinho na tela.
maxLength
O limite de caracteres que o navegador deixa digitar. Conta letra, espaço e quebra de linha.

Repare que não existe type no textarea. Quem decide que ele é de várias linhas é a própria tag. Se você escrever type="text" nele, o atributo é ignorado — e um aviso aparece no console em modo de desenvolvimento. Do mesmo jeito, placeholder, maxLength, readOnly e disabled funcionam igual aos do input, porque são atributos comuns de campo.

A tabela abaixo resume a troca, para você consultar quando estiver em dúvida sobre qual tag usar:

Essa diferença de comportamento no Enter não é detalhe: num formulário de contato, apertar Enter no input envia a mensagem, e apertar Enter no textarea só desce uma linha. Quem preenche um recado precisa dessa segunda opção, e quem preenche um campo curto agradece a primeira. A tag certa dá o comportamento certo de graça.

3. Ligando o textarea ao estado

A primeira missão da Ana é a mais direta: pegar o textarea que ela já desenhou e ligá-lo ao estado, mostrando o recado embaixo. O componente abaixo tem o campo e o rótulo, mas o parágrafo está fixo — do jeito que está, o que o cliente escreve fica só dentro do campo:

O recado não chega ao parágrafo. Crie o estado recado, ligue o textarea com value e onChange e mostre Recado: {recado}.

function App() {
  return (
    <div>
      <label htmlFor="recado">Recado no bolo</label>
      <textarea id="recado" rows="3"></textarea>
      <p>Recado: (vazio)</p>
    </div>
  );
}
<div>
  <label for="recado">Recado no bolo</label>
  <textarea id="recado" rows="3"></textarea>
  <p>Recado: (vazio)</p>
</div>

function App() {
  const [recado, setRecado] = useState("");
  return (
    <div>
      <label htmlFor="recado">Recado no bolo</label>
      <textarea
        id="recado"
        rows="3"
        value={recado}
        onChange={(e) => setRecado(e.target.value)}
      ></textarea>
      <p>Recado: {recado}</p>
    </div>
  );
}

Note que o textarea tem fechamento: </textarea>. Não dá para escrever <textarea /> como se faz com o input, porque o React precisa das duas tags para montar o elemento direito. As tags ficam vazias — o conteúdo vem do estado. No painel, depois de rodar, você vê o campo assim: <textarea rows="3"></textarea>. Digite na prévia e o parágrafo acompanha.

Esse "digite e acompanhe" é a melhor forma de confirmar que a ligação está completa. Se o parágrafo muda mas o campo não acompanha, falta o value. Se o campo aceita texto mas o parágrafo fica parado, falta o onChange ou o setRecado não está sendo chamado. Com os dois, o recado aparece nos dois lugares ao mesmo tempo.

4. O erro clássico: texto entre as tags

Quem aprendeu HTML antes do React escreve isto por reflexo:

function App() {
  const [recado, setRecado] = useState("Bom dia");

  return (
    <textarea>{recado}</textarea>
  );
}

O campo até mostra "Bom dia" na primeira renderização, e é aí que o problema se esconde: ao digitar, o texto novo fica no DOM mas o estado não muda, e a ligação quebra. No modo de desenvolvimento, o React avisa no console que o conteúdo de um textarea deve vir de value ou de defaultValue, e não de filhos. O aviso, em resumo, é este:

Warning: Use the defaultValue or value props instead of setting children on textarea.

O conserto é tirar o texto de dentro das tags e colocar no value: <textarea value={recado} onChange={...} /> — com as duas tags vazias, mas com o valor vindo do estado. Isso vale também para o caso de "começar preenchido": o valor inicial é o useState("Bom dia"), não o texto entre as tags.

Há uma exceção: defaultValue serve para um campo não controlado começar com texto. Só que aí você abre mão de acompanhar cada tecla, e a conversa de controlado e não controlado tem aula própria mais adiante no nível. Para o recado do bolo, controlado é o que interessa: a Ana quer o contador, a prévia e a validação de tamanho funcionando juntos.

5. Contar caracteres e limitar com maxLength

O bolo tem espaço para 40 caracteres no topo. Passou disso, a confeiteira corta a frase — e a Ana prefere avisar antes. Duas coisas resolvem: um contador que mostra quanto já foi digitado e um maxLength que impede o excesso no teclado. O contador é só o tamanho do estado, e o tamanho de uma string em JavaScript se lê com .length.

Mostre quantos caracteres já foram digitados, no formato 7/40 caracteres, e coloque maxLength={40} no campo.

function App() {
  const [recado, setRecado] = useState("");
  return (
    <div>
      <label htmlFor="recado">Recado no bolo (até 40 caracteres)</label>
      <textarea
        id="recado"
        rows="3"
        value={recado}
        onChange={(e) => setRecado(e.target.value)}
      ></textarea>
    </div>
  );
}
<div>

  <textarea id="recado" rows="3"></textarea>
</div>

    </div>

Depois do conserto, o painel mostra o atributo maxlength="40" e o textarea vazio. Digite "Bom dia" na prévia: são 7 caracteres, incluindo o espaço. O contador é uma conta feita no desenho, não um estado novo — se você criasse um useState para o número, teria de lembrar de atualizá-lo em todo lugar e um dia esqueceria.

O maxLength é uma trava do navegador, e trava só o que é digitado. Texto colado por código (um valor vindo de outro campo, por exemplo) passa por cima dele. Por isso a contagem e a trava de verdade também aparecem na validação, mais adiante. Aqui, o par contador + maxLength já resolve a experiência de quem escreve: a pessoa vê o limite chegando e não perde o texto que digitou.

Se quiser variar a mensagem conforme o espaço, dá para usar o próprio número: {recado.length > 30 ? "falta pouco" : ""}. É a mesma ideia de renderização condicional que você já viu, aplicada a uma conta simples. O importante é não transformar cada detalhe da tela num estado separado.

6. As quebras de linha e o white-space

Agora a mania mais confusa do textarea. Quando o cliente aperta Enter, o texto ganha um caractere invisível: \n. Esse caractere existe no valor do estado e você consegue vê-lo em um console.log. Mas o HTML trata espaços e quebras de linha como um espaço só na hora de exibir — é por isso que a prévia mostra o recado todo grudado, mesmo com o valor certo.

A Ana quer que a comanda mostre o recado do jeito que o cliente escreveu. O componente abaixo guarda duas linhas, mas a prévia junta tudo com " / " para contornar o problema:

A prévia está juntando as linhas com " / ". Troque o join(" / ") por {recado} e acrescente style={{ whiteSpace: "pre-line" }} no parágrafo para as quebras aparecerem.

function App() {
  const [recado, setRecado] = useState("Bom dia\nPão quentinho às 7h");
  return (
    <div>
      <label htmlFor="recado">Recado no bolo</label>
      <textarea
        id="recado"
        rows="3"
        value={recado}
        onChange={(e) => setRecado(e.target.value)}
      ></textarea>
      <p id="previa">{recado.split("\n").join(" / ")}</p>
    </div>
  );
}
<div>

Pão quentinho às 7h</textarea>

function App() {
  const [recado, setRecado] = useState("Bom dia\nPão quentinho às 7h");
  return (
    <div>
      <label htmlFor="recado">Recado no bolo</label>
      <textarea
        id="recado"
        rows="3"
        value={recado}
        onChange={(e) => setRecado(e.target.value)}
      ></textarea>
      <p id="previa" style={{ whiteSpace: "pre-line" }}>{recado}</p>
    </div>
  );
}

white-space: "pre-line" diz ao navegador para respeitar as quebras de linha do texto. Sem ele, o HTML colapsa as quebras em espaço; com ele, cada \n vira uma linha na tela. Existem outros valores: normal (o padrão, que junta tudo), pre (respeita quebras e espaços, mas não quebra linha sozinho) e pre-wrap (respeita os dois e ainda quebra quando passa da largura). Para recado de bolo, pre-line é o mais equilibrado.

Para ver o que o estado guarda de verdade, um console.log com o valor dividido por quebra de linha mostra o texto em pedaços:

recado.split("\n")
["Bom dia", "Pão quentinho às 7h"]
recado.length: 31

O CSS está escrito ali no próprio JSX, com duas chaves e um objeto, porque é um caso de uma regra só. A sintaxe é style={{ whiteSpace: "pre-line" }}: a chave de fora é a expressão do JSX, a de dentro é o objeto de estilo, e a propriedade usa o nome em camelCase — whiteSpace, não white-space. A aula de estilo inline cobre o assunto com calma; aqui basta saber que essa linha é a diferença entre um recado legível e um parágrafo grudado.

7. Altura, rows e o redimensionamento

O rows define quantas linhas o campo mostra quando aparece. Não é um limite de conteúdo: se a pessoa escrever mais, o campo ganha uma barra de rolagem interna. O padrão do navegador é rows="2", o que costuma ser apertado para um recado; a Ana usa rows="3" ou rows="4" e ajusta o resto com CSS.

Por padrão, o canto do textarea pode ser arrastado para aumentar ou diminuir a altura. Isso é útil em algumas telas e desastroso em outras: o leitor arrasta sem querer, o formulário desalinha e o layout quebra. O CSS resize controla esse comportamento — resize: none desliga a alça, resize: vertical deixa só aumentar para baixo. Como isso é estilo, não estado, vai no CSS ou no style do componente.

  return (
    <div>
      <label htmlFor="recado">Recado no bolo</label>
      <textarea
        id="recado"
        rows="4"

    </div>

}

Três decisões aparecem nesse arquivo: a altura inicial com rows, o limite com maxLength e a largura com width: "100%", para o campo acompanhar a coluna em vez de ter uma largura fixa em pixels. Em tela de celular, largura fixa é a receita para a página rolar de lado — e o guia inteiro é testado a 375 px por causa disso.

Uma tentação comum é tentar fazer o campo crescer sozinho conforme o texto, mexendo na altura a cada tecla. Dá para fazer, mas exige medir o conteúdo com useRef e efeito, e a aula de useRef é o lugar certo para isso. Para o recado de 40 caracteres, um campo de quatro linhas resolve sem nenhum código extra.

8. Enter, Shift+Enter e o envio

Dentro do textarea, Enter quebra a linha e Shift+Enter também — os dois funcionam igual, porque não existe atalho de envio aqui. Quem envia é o botão, e o envio de formulário tem aula própria, logo depois da validação. Por enquanto, vale saber que o recado com quebras de linha vai para o estado do mesmo jeito que qualquer texto: uma string com caracteres \n no meio.

Se você quiser impedir Enter em um campo específico — por exemplo, um campo curto que não deve ter quebra —, dá para escutar o onKeyDown e chamar e.preventDefault() quando a tecla for "Enter". Isso é exceção, não regra. E é bom lembrar que o textarea não valida formato: ele aceita qualquer caractere, inclusive emoji, acento e quebra de linha. Se o recado tem limite, quem conta é você.

Também vale saber que o valor do textarea chega no e.target.value como uma string normal, com os \n preservados. Se você fizer recado.length, cada quebra de linha conta como um caractere. Uma frase de duas linhas com 20 letras cada tem 41 caracteres, não 40 — e esse detalhe já estourou mais limite de campo do que qualquer outro.

9. Cenários do dia a dia

Cenário 1: o campo começa preenchido e não deixa apagar

A Ana escreveu o texto entre as tags para o campo começar com "Bom dia" e, na primeira tecla, o texto voltou. Era o clássico <textarea>{recado}</textarea> com um estado que nunca mudava. O valor inicial se define no useState; as tags ficam vazias. Depois do conserto, o campo começa com o texto e apaga normalmente.

Cenário 2: o recado aparece todo grudado na comanda

O estado tinha as duas linhas, o campo mostrava as duas linhas e o parágrafo de conferência mostrava tudo junto. Não era bug do textarea: o HTML colapsa quebras de linha na exibição. A solução foi white-space: "pre-line" no parágrafo. Se a comanda for um pre ou um e-mail, o mesmo texto precisa de um tratamento parecido.

Cenário 3: o contador passa do limite

Ela pôs maxLength={40} e o contador mostrando {recado.length}/40. Um teste com texto colado pelo console passou de 40 e o contador mostrou 47/40. O atributo limita a digitação, não o valor que entra por código. Se o limite é regra de negócio, valide no envio também — e mostre a mensagem antes de cortar o texto do cliente.

Exercício: fechar a tag

O campo abaixo está sem o fechamento e sem o valor vindo do estado. Complete a tag de fechamento, escrevendo só o nome do elemento:

<textarea value={recado} onChange={(e) => setRecado(e.target.value)}></>

Dica: é o mesmo nome da tag de abertura, em minúsculas. Se você escrever só />, o JSX não compila; o textarea precisa das duas tags, mesmo vazio.

11. Resumo

O textarea é o campo de várias linhas, e no React ele é controlado como qualquer outro: value vindo do estado e onChange devolvendo o texto. O texto não vai entre as tags; as tags ficam vazias e o valor inicial mora no useState. rows dá a altura inicial, maxLength trava a digitação e o contador é uma conta com .length.

As quebras de linha do Enter viram \n no valor e não aparecem sozinhas na tela: o HTML junta tudo. Para exibir o recado com as linhas certas, use white-space: "pre-line" no elemento que mostra o texto. E lembre que cada \n conta como um caractere no limite.

Com isso, o formulário da padaria já tem campo curto e campo longo. Falta a escolha entre opções fixas — o sabor do pão, a forma de entrega, o horário da retirada. É o assunto da próxima aula, o select, que tem uma diferença importante: o valor não fica no campo, fica na opção escolhida. O par value e onChange continua o mesmo, mas o lugar de ler o valor muda. Se quiser comparar os dois campos lado a lado, a aula do input controlado mostra o irmão de uma linha.

Para lembrar

  • textarea tem abertura e fechamento; não existe <textarea />.
  • O valor vem de value; texto entre as tags não é valor no React.
  • O valor inicial se define no useState, não no HTML.
  • rows é altura inicial, não limite de linhas.
  • maxLength trava a digitação, mas não o texto colocado por código.
  • Contador é {recado.length}, uma conta no render.
  • Enter vira \n no estado e conta como caractere.
  • Para mostrar as quebras: white-space: "pre-line".
  • No JSX, estilo é style={{ whiteSpace: "pre-line" }}.
  • resize no CSS controla a alça de redimensionar.
