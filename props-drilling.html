Props Drilling

O desconto da padaria depende de quem está comprando. A Ana guarda o nome do cliente lá no topo da tela, no App, mas o preço com desconto é desenhado três níveis abaixo, dentro de um cartão. Para o dado chegar até lá, cada componente do caminho precisa receber a prop e repassar — mesmo os que não fazem ideia do que seja um cliente. Nesta aula ela entende esse encanamento, vê o preço que ele cobra e conhece as saídas.

Você vai aprender
  • O que é props drilling, com nome e sobrenome.
  • Por que o dado desce e nunca sobe por props.
  • O custo real: cada nível do caminho precisa repassar a prop.
  • Por que o componente do meio vira um repassador sem assunto.
  • A primeira saída: montar a peça onde o dado existe e passar por children.
  • As outras duas saídas, e quando cada uma é a certa.
  • Como provar no painel que o valor chegou (ou não) ao fim da linha.

1. A cena: o desconto mora no topo

A tela do dia na padaria é uma árvore de três andares. No topo, o App sabe quem está comprando: hoje é a Ana, cliente cadastrada desde 2019. No meio, o PainelDoDia organiza o assunto do dia. Embaixo, o CartaoDePao mostra um pão, e dentro dele o Preco escreve o valor. O desconto é uma regra do preço: cliente cadastrado paga menos.

Só que o Preco não tem como saber quem é o cliente. Componente não enxerga a variável do vizinho, muito menos a do avô. A única forma de um dado descer a árvore é por props: quem tem o valor passa para o filho, o filho passa para o neto. É exatamente isso que a Ana fez — e o resultado é uma prop cliente que aparece em três assinaturas de função, sendo que só a última usa o valor.

function App() {
  const cliente = "Ana";
  return <PainelDoDia cliente={cliente} />;
}

function PainelDoDia({ cliente }) {
  return <CartaoDePao cliente={cliente} titulo="Pão do dia" preco="10,00" />;
}

function CartaoDePao({ cliente, titulo, preco }) {
  return (
    <article>
      <h2>{titulo}</h2>
      <Preco cliente={cliente} preco={preco} />
    </article>
  );
}

function Preco({ cliente, preco }) {
  return <p>R$ {preco} para {cliente}</p>;
}

Funciona. E é importante dizer isso antes de criticar: passar props é o jeito normal e correto de mover dados em React. O problema não é o mecanismo, é o volume. O PainelDoDia e o CartaoDePao recebem uma prop que não usam para nada — só seguram a porta para o dado passar. Quando esse trecho se repete em dez componentes, qualquer mudança no nome ou no formato do dado vira uma caçada.

2. O encanamento tem nome

Esse repasse em cadeia se chama props drilling — em português, algo como “perfuração por props”. O nome é feio de propósito: descreve o cano que você abre atravessando camadas que não têm nada a ver com o assunto. A água chega, mas o cano passa no meio da sala.

props drilling
Passar um dado de um componente para outro através de componentes intermediários que não usam esse dado.
repassador
O componente do meio, que recebe a prop só para entregar ao filho. Não lê o valor, não decide nada com ele.
dado de tela
Um valor que pertence a uma tela inteira, não a uma peça: quem está logado, o tema, a moeda, o carrinho.
fluxo de cima para baixo
Em React, dados descem por props e eventos sobem por funções. Não existe prop que volta para o pai.
profundidade
Quantos níveis o dado atravessa até ser usado. Dois é confortável; cinco é sinal de que algo pode morar mais perto.

Uma calibragem importante, para não sair por aí com medo de prop: passar um dado para o filho direto é normal e continua sendo o jeito preferido do React. Dois níveis de repasse, com um componente que realmente usa o valor no meio, não é drilling — é a arquitetura funcionando. O nome feio só entra quando o intermediário não tem nada a ver com o dado e passa a existir para carregá-lo.

Vale entender por que o dado não sobe. Se o Preco pudesse escrever direto na variável do App, qualquer peça da tela poderia mudar qualquer coisa, e descobrir quem mudou viraria arqueologia. O React fecha essa porta de propósito: quem manda no valor é o dono do estado, e o filho só avisa por uma função. O preço dessa escolha é o encanamento que você está vendo.

3. O dado desce: uma prop, quatro componentes

Na caixa abaixo, a cadeia inteira já está montada. O App tem o cliente, o PainelDoDia repassa, o CartaoDePao repassa e o Preco usa. Falta só o primeiro passo: o App não passa nada para o painel, e por isso o cliente chega vazio no fim da linha.

O App tem a variável cliente, mas chama <PainelDoDia /> sem passar nada. Passe cliente={cliente} e clique em Rodar.

Uma linha resolveu a cadeia inteira, porque o meio já estava preparado para repassar. E aqui está a observação mais importante da aula: o dado estava errado antes do conserto, mas a tela não quebrou. Ela mostrou R$ 10,00 para, com um buraco no lugar do nome. Props ausentes viram undefined, e o React desenha o que der. O sintoma é sempre uma tela quase certa.

Outro detalhe que passa batido: o desconto não é calculado no Preco. O App sabe quem é o cliente, mas o valor “10,00” está escrito à mão no JSX do painel. Se a regra mudar, muda no meio. Não é o assunto desta aula, mas vale reparar: prop é dado, não regra de negócio escondida.

4. O custo está no componente do meio

Agora o tropeço que dá nome ao problema. O CartaoDePao até recebe o cliente, mas esqueceu de repassar para o Preco. O preço aparece, o selo de cliente não. E o cartão não usa o valor para nada — ele só deveria entregar. É esse tipo de edição, feita num componente que não tem interesse no dado, que se multiplica pela árvore.

O botão troca o cliente no topo, mas o selo lá embaixo continua dizendo “visitante”: falta o Cartao repassar o cliente para o Preco. Conserte o repasse e clique em “Trocar cliente”.

function Selo({ cliente }) {
  return <span className="selo">{cliente ? "cliente " + cliente : "visitante"}</span>;
}

function Preco({ preco, cliente }) {
  return (
    <p>R$ {preco} <Selo cliente={cliente} /></p>
  );
}

  return (

O clique mostra as duas metades da verdade. Primeiro: o fluxo funciona — o estado mudou no App, a prop desceu e o selo mudou de nome sem nenhum código extra. Segundo: para isso acontecer, cada componente do caminho teve de estar com a porta aberta. Um esquecimento no meio e o valor para de descer, mesmo que o topo esteja perfeito.

É por isso que o drilling cansa. Não é escrever a prop uma vez; é lembrar dela em cada andar, em cada arquivo, cada vez que a árvore ganha um nível novo. E o nome da prop precisa ser o mesmo em todos, senão o dado some silenciosamente.

5. O que o console mostra em cada nível

Quando o valor não chega, o console é o melhor detetive. Coloque uma linha de log no componente do meio e imprima o objeto de props inteiro:

function Cartao(props) {
  console.log("Cartao recebeu: " + JSON.stringify(props));
  return <article><Preco preco={props.preco} /></article>;
}

Com o repasse faltando, o log mostra o cartão sem a prop que o preço espera. Com o repasse no lugar, a mesma linha mostra tudo:

Cartao recebeu: {"titulo":"Baguete","preco":"9,00"}
Cartao recebeu: {"titulo":"Baguete","preco":"9,00","cliente":"Beatriz"}

Repare que o componente não reclama de receber cliente sem usar. Props a mais são ignoradas; props a menos viram undefined. Nenhum dos dois casos é erro para o React — e é justamente por isso que o encanamento quebrado passa despercebido. O console não aponta o culpado; ele mostra o que cada andar recebeu, e você compara.

Um hábito que economiza horas: logar no componente que usa o dado, não no que repassa. Se o Preco imprime undefined, o problema está acima dele. Se imprime o valor certo mas a tela não muda, o problema está no JSX abaixo do log.

6. A saída mais simples: montar onde o dado está

Antes de qualquer ferramenta nova, existe uma saída que resolve boa parte dos casos e não pede nada além de composição. Se o App já tem o cliente, por que não monta ele mesmo a peça que precisa do cliente e entrega a peça pronta para o painel? O painel continua posicionando o conteúdo, mas não precisa saber o que é um cliente.

O PainelDoDia recebe cliente e não usa: ele não tem como repassar. Tire essa prop e passe o preço pronto como filho: <PrecoComDesconto preco="10,00" cliente={cliente} /> dentro do painel.

function PrecoComDesconto({ preco, cliente }) {
  return <p className="preco">R$ {preco} para {cliente}</p>;
}

function PainelDoDia({ titulo, children }) {
  return (
    <section className="painel">
      <h2>{titulo}</h2>
      {children}
    </section>
  );
}

function App() {
  const cliente = "Ana";

  return (
    <PainelDoDia titulo="Pão do dia" cliente={cliente}>
      <p>Sai quentinho às 7h</p>
    </PainelDoDia>
  );
}
<section class="painel">
  <h2>Pão do dia</h2>
  <p>Sai quentinho às 7h</p>
</section>

O painel FICOU mais simples: ele recebe um título e um miolo, e não tem prop cliente nenhuma. Quem tem o dado montou a peça. Isso é composição aplicada ao problema do drilling — e é a primeira coisa a tentar, porque não cria conceito novo, não precisa de import e não muda o fluxo dos dados.

Existe uma razão a mais para essa saída ser a preferida: ela deixa a dependência visível na assinatura. O PainelDoDia declara titulo e children e nada mais; lendo essas duas palavras, você sabe exatamente do que ele depende. Com o repasse, a assinatura ganha uma prop que o corpo nunca menciona — uma promessa que o componente não cumpre. Código em que a assinatura mente sobre o conteúdo envelhece mal.

Nem sempre dá. Se o dado precisa ser lido em dez pontos distantes da árvore, montar dez peças no topo deixa o App gigante e cheio de detalhe que não é dele. Aí vale outra ferramenta. Mas repare: a decisão não é “drilling ou contexto”. É “esse dado pertence a esta tela e a poucos lugares, ou pertence ao aplicativo inteiro?”. Só a segunda resposta pede contexto.

7. Como reconhecer que o encanamento passou do ponto

Ninguém acorda e decide fazer drilling. Ele aparece aos poucos, um nível por vez, sempre parecendo razoável. Estes são os sinais de que o cano ficou longo demais:

SinalO que ele quer dizerPrimeiro remédio
a mesma prop em 3 assinaturas, usada em 1dois repassadores sem assuntomontar a peça onde o dado está
componente recebe prop e não usaele virou canocompor com children
nome da prop muda no meio do caminhoo dado some em silênciopadronizar o nome ou parar de passar
a prop é o mesmo dado em 8 telasé dado do aplicativo, não da telacontexto
a árvore tem 6 níveiso problema é a estrutura, não a propachatar a árvore

A última linha merece atenção. Muita dor de drilling é sintoma de uma árvore funda demais: um componente que só embrulha outro, que embrulha outro. Antes de instalar uma solução de dados, vale perguntar se aqueles três níveis precisam existir. Cortar um nível resolve mais do que passar o valor adiante com mais elegância.

8. As três saídas, em ordem de custo

Existem três caminhos, e eles não são equivalentes. Comece sempre pelo mais barato. O contexto — aula seguinte — é o mais poderoso e o mais fácil de usar errado.

SaídaCustoCombine quando
compor com childrennenhum conceito novopoucos consumidores, perto de quem tem o dado
mover o estado para mais pertoreorganizar a telao dado só serve a um galho da árvore
contextoum provider e um consumidoro dado vale para a aplicação inteira e é lido em muitos pontos

O contexto não é um elevador de props. Ele serve para um dado que a árvore inteira compartilha, como quem está logado, o tema claro ou escuro, a moeda da loja. Usar contexto para o preço de um pão específico é trocar um cano visível por um cano escondido: o componente passa a depender de algo que não aparece na assinatura nem no JSX de quem o chama. A regra prática é simples — se o dado muda de tela para tela, ele não é contexto.

Há também uma saída que não é saída: passar {...props} em todo componente do caminho. É rápido de escrever e péssimo de ler, porque o componente passa a aceitar tudo sem declarar nada. O leitor não descobre quais dados a peça usa olhando a assinatura; precisa caçar no JSX. Se o objetivo é encurtar o encanamento, o spread só esconde o cano.

Preco recebeu: undefined
Preco recebeu: "Ana"

As duas linhas acima são o mesmo componente antes e depois de um repasse consertado. É o teste mais rápido que existe: se o valor chega undefined, o problema está acima; se chega certo e a tela não muda, o problema está no seu JSX.

9. Cenários do dia a dia

Cenário 1: o selo que nunca aparecia

A Ana passou cliente do App para o Painel, do Painel para o Cartao e esqueceu o último salto, do Cartao para o Preco. O selo dizia “visitante” para uma cliente de cinco anos. Nenhum erro no console, só uma tela quase certa — o sintoma clássico de prop que parou no meio do caminho.

Cenário 2: renomear virou um dia de trabalho

Ela decidiu que cliente era um nome ruim e trocou por comprador. Em vez de três arquivos, teve de mexer em nove, porque a prop atravessava componentes que não tinham nada a ver com a compra. Depois disso, ela passou a montar a peça no topo sempre que o dado era usado em um lugar só.

Cenário 3: o dado que não era da tela

O nome do cliente começou a ser necessário em cinco telas diferentes do site: carrinho, perfil, encomendas, histórico e nota fiscal. Aí não era mais drilling de uma tela, era dado do aplicativo. Nesse caso, o contexto resolve — e é o assunto da próxima aula. A pista foi a palavra “cinco telas”, não o número de níveis.

11. Resumo

Props drilling é o nome honesto de uma coisa comum: um dado que desce a árvore atravessando componentes que não o usam. O mecanismo está certo — em React, dados descem por props e quem manda no valor é quem o guarda. O que incomoda é o volume de portas que precisam ficar abertas.

Antes de trocar de ferramenta, tente o barato. Monte a peça que precisa do dado lá em cima, onde o valor existe, e entregue a peça pronta por children: o componente do meio posiciona sem saber de nada. Se o dado só serve a um galho da árvore, mova o estado para mais perto desse galho. Se o dado vale para a aplicação inteira e é lido em muitos pontos distantes, aí sim vale um contexto — que é exatamente a próxima aula.

E guarde o detetive: quando uma tela aparece quase certa, com um buraco onde deveria ter texto, o suspeito número um é uma prop que parou no meio do caminho. Um console.log no componente que usa o dado resolve em trinta segundos a dúvida entre “não chegou” e “chegou e eu desenhei errado”.

Para lembrar

  • Props drilling: dado atravessando níveis que não o usam.
  • Props descem; eventos sobem por funções. Nada volta sozinho.
  • Prop ausente vira undefined e a tela mostra um buraco, sem erro.
  • O componente do meio que só repassa é um cano: ele não tem assunto.
  • Saída 1: montar a peça onde o dado está e passar por children.
  • Saída 2: mover o estado para mais perto de quem usa.
  • Saída 3: contexto, quando o dado é do aplicativo inteiro.
  • O nome da prop precisa ser igual em todos os níveis; diferente, o dado some.
  • {...props} esconde o cano em vez de encurtá-lo.
  • Para achar o culpado, logue no componente que usa: undefined aponta para cima.
