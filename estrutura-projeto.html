Estrutura do Projeto

A vitrine de encomendas da Ana passou de dez arquivos para trinta e quatro, e a pasta src virou um depósito: componentes misturados com imagens, uma função de data perdida no meio de um arquivo de tela, imports com quatro ../ seguidos. Nesta aula ela organiza o projeto com critério — e descobre por que duas pastas parecem guardar imagens, por que o Linux recusa um import que o Windows aceitava e quando um index.js ajuda ou atrapalha.

Você vai aprender
  • As duas formas de agrupar arquivos e quando cada uma vale a pena.
  • O que é tela (pages) e o que é peça (components).
  • Onde guardar lógica reaproveitável: hooks e lib.
  • A diferença entre src/assets e public — e por que existem as duas.
  • Como criar o atalho @ para não escrever ../../...
  • Por que maiúscula em nome de arquivo derruba o build no servidor.

1. A cena: a pasta que virou depósito

No começo era fácil: src/App.jsx, src/main.jsx e mais dois ou três componentes. Trinta e quatro arquivos depois, a Ana abre a pasta e não sabe onde está nada. O botão que ela procura chama Botao.jsx e está ao lado de logo.svg, de formatarData.js e de uma cópia de Cardapio.jsx que ela não lembra de ter feito.

Organizar não é enfeite: é o que decide se você acha um arquivo em cinco segundos ou em cinco minutos, e se o próximo a mexer no projeto vai entender o mapa sem perguntar. Também não é uma ciência exata — não existe uma estrutura "oficial" do React. O que existe são convenções que funcionam, e o critério para escolher entre elas.

2. As duas perguntas antes de criar uma pasta

Toda pasta responde a uma pergunta sobre os arquivos que guarda. Há duas formas de responder. A primeira é por tipo: tudo o que é componente em components/, tudo o que é gancho em hooks/, tudo o que é utilitário em lib/. A segunda é por assunto: tudo o que é da vitrine em vitrine/, tudo o que é do cardápio em cardapio/ — cada pasta com os componentes, o CSS e as funções daquele assunto.

Projetos pequenos e médios vivem bem com a divisão por tipo: é simples, previsível e todo mundo reconhece. A divisão por assunto brilha quando o projeto tem áreas bem separadas e muita gente mexendo ao mesmo tempo — cada pessoa trabalha na sua pasta. O erro comum é misturar as duas sem critério: uma pasta components com subpastas por assunto, e outra features fazendo a mesma coisa.

módulo
Cada arquivo que exporta alguma coisa e pode ser importado por outro.
página
O componente que representa uma tela inteira: Cardapio.jsx, Encomendas.jsx.
hook
Função que usa estado ou efeito e começa com use: useEncomendas.js.
alias
Um apelido de caminho, como @, que aponta sempre para a mesma pasta.
asset
Um arquivo que não é código: imagem, fonte, ícone. Passa pelo build quando está em src.
barrel
Um index.js que reexporta os irmãos da pasta para encurtar imports.

Para o projeto da Ana, a divisão por tipo resolve. O mapa fica assim:

├── src/

Falta combinar o que não pertence ao código. node_modules é depósito do npm e não vai para o Git. dist é resultado do build e não vai para o Git — ele é gerado de novo a cada publicação. Arquivos .env com valores locais não vão para o Git. E nada disso deve ficar dentro de src, porque src é o que você escreve, não o que a ferramenta gera.

node_modules
dist
.env.local
*.log

O .gitignore do template do Vite já vem com node_modules e dist. Acrescentar .env.local e arquivos de log é o ajuste que quase todo projeto precisa. E vale conferir de vez em quando: um dist versionado por engano faz o repositório crescer sem parar e esconde o fato de que o build está sendo gerado.

O que pode ficar na raiz: README.md, .gitignore, index.html, package.json, vite.config.js, jsconfig.json e as pastas public e src. Se uma pasta nova aparecer na raiz, pergunte a que ferramenta ela pertence — se a resposta for "a nenhuma", o lugar dela provavelmente é src.

Repare no que está na raiz e no que está dentro de src. Na raiz ficam os arquivos que configuram o projeto e a pasta pública. Dentro de src fica o código que vira o site. Essa separação é o primeiro filtro: se o arquivo é código de aplicação, é src; se é configuração, imagem pública ou documentação, é raiz.

3. components e pages

Um componente é uma peça que pode aparecer em qualquer lugar: o botão, o cabeçalho, o cartão de pão. Uma página é a tela inteira de uma rota: o cardápio, as encomendas, o contato. A distinção parece óbvia e economiza muita confusão, porque as duas coisas se parecem no código — as duas são funções que devolvem JSX.

O critério é o que a peça conhece. Um componente recebe props e não sabe onde está sendo usado. Uma página conhece os dados da tela, chama as peças e monta o layout. Se você tem dificuldade de decidir, pergunte: "isso aparece em duas telas?". Se sim, é componente. Se só existe em uma, é página.

A árvore mostra só o primeiro nível: os filhos das pastas não aparecem. Faça o componente No desenhar os filhos chamando a si mesmo — a árvore precisa ter nove itens e mostrar Botao.jsx e useEncomendas.js.

O componente que se chama a si mesmo é a forma natural de desenhar uma árvore: cada nó sabe desenhar o seu nome e delega os filhos para outro nó igual a ele. A key continua sendo o nome, e a condição item.filhos && ... evita o ul vazio nos arquivos. É o mesmo padrão que aparece em menu lateral, comentários com respostas e qualquer estrutura em níveis.

Na prática, o que muda de components para pages é a responsabilidade. A página pode importar da pasta de componentes, mas o componente nunca importa da pasta de páginas — se importar, você criou um ciclo e o mapa perde o sentido. Essa direção única é a regra que mantém o projeto legível.

4. hooks e lib

Nem tudo é componente. A lógica que usa estado e efeito e é reaproveitada por mais de uma tela vira um hook, numa pasta com esse nome, e o arquivo começa com use: useEncomendas.js, useCardapio.js. O prefixo não é enfeite: é o que permite ao React (e ao lint) reconhecer que ali dentro existem hooks e aplicar as regras deles.

import { useEffect, useState } from "react";

export function useEncomendas() {
  const [encomendas, setEncomendas] = useState([]);
  const [carregando, setCarregando] = useState(true);

  useEffect(() => {
    let ativo = true;

    fetch("/api/encomendas")
      .then((r) => r.json())
      .then((dados) => {
        if (ativo) {
          setEncomendas(dados);
          setCarregando(false);
        }
      });

    return () => {
      ativo = false;
    };
  }, []);

  return { encomendas, carregando };
}

O que não usa estado nem efeito é função pura e vai para lib/ (ou utils/, o nome é escolha do time): formatar data, calcular total, validar telefone. São as peças mais fáceis de testar, porque recebem dados e devolvem dados, sem depender da tela. Uma regra prática: se a função não chama hook nenhum, ela não pertence a hooks/.

Colocar essas funções em arquivos próprios tem um efeito colateral bom: você para de copiar a mesma conta em três telas. Quando o preço mudar de regra, muda num lugar só. E o teste, quando chegar, não precisa de navegador.

5. src/assets e public: dois lugares para imagens

Aqui está a confusão que quase todo mundo tem no começo: por que existem duas pastas para guardar arquivos? A resposta está no que acontece com eles no build. O que está em src/assets passa pelo processo: o Vite lê o arquivo, copia para a saída com um nome novo que inclui um hash do conteúdo e devolve a URL final para o seu import. O que está em public é copiado como está, com o mesmo nome, e fica acessível pela raiz do site.

src/assetspublic
Como se usaimport pao from "./assets/pao.jpg"src="/favicon.svg"
Passa pelo buildsim: é processado e renomeado com hashnão: é copiado igual
Nome finalpao-a1b2c3.jpgfavicon.svg
Bom paraimagens que o código importa e usa em componentesfavicon, robots.txt, imagem de compartilhamento

O hash no nome existe por causa do cache do navegador: se o arquivo muda, o nome muda, e o navegador é obrigado a baixar de novo. Se o arquivo não muda, o nome fica igual e o cache continua valendo. Já o arquivo em public mantém o nome — ótimo para o que precisa de endereço fixo, como /favicon.svg e /robots.txt, e arriscado para imagem que muda com frequência, porque o navegador pode continuar mostrando a antiga.

As duas listas estão repetindo os quatro arquivos. Separe pelo caminho: quem começa com public/ é copiado como está; quem começa com src/assets/ passa pelo build. Cada lista precisa ficar com dois itens.

const arquivos = [

6. O atalho @ nos imports

Com pastas, vêm os caminhos relativos. Um componente em src/pages/Cardapio.jsx que importa o botão escreve import Botao from "../components/Botao". Se amanhã esse arquivo mudar de pasta, o caminho quebra. Pior: quando o projeto tem quatro níveis, o import vira "../../../components/Botao" e ninguém sabe mais onde está.

A solução é um alias: um apelido que aponta para uma pasta fixa. Você escreve @/components/Botao de qualquer lugar, e a ferramenta resolve para src. São duas configurações — uma para o Vite, que monta o site, e outra para o editor, que precisa entender o mesmo atalho para não marcar o import como erro.

import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";
import path from "node:path";

export default defineConfig({
  plugins: [react()],
  resolve: {
    alias: {
      "@": path.resolve(__dirname, "src")
    }
  }
});

O path.resolve(__dirname, "src") transforma o caminho relativo em absoluto, que é o que o Vite espera. Para o editor, o mesmo apelido vai num jsconfig.json na raiz — um arquivo só com os caminhos, que o VS Code lê:

{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]
    }
  }
}

Vale a pena? Em projeto com poucas pastas, o relativo resolve. A partir do momento em que você escreve três ../ seguidos, o atalho se paga: o import fica igual em todo lugar, e mover arquivo deixa de quebrar caminho. O custo é essa configuração dupla e a surpresa de quem abre o projeto e não encontra node_modules/@.

A função resolver deveria trocar o prefixo @/ por src/, mas está devolvendo o caminho como veio. Corrija para os dois imports com @ aparecerem resolvidos — e o relativo ./App.css continuar intacto.

const imports = [
  "@/components/Botao",
  "@/hooks/useEncomendas",
  "./App.css"
];

function resolver(caminho) {
  return caminho;
}

function App() {
  return (
    <ul>
      {imports.map((i) => (
        <li key={i}>
          {i} → {resolver(i)}
        </li>
      ))}
    </ul>
  );
}
<ul>
  <li>@/components/Botao → @/components/Botao</li>
  <li>@/hooks/useEncomendas → @/hooks/useEncomendas</li>
  <li>./App.css → ./App.css</li>
</ul>

const imports = [
  "@/components/Botao",
  "@/hooks/useEncomendas",
  "./App.css"
];

function resolver(caminho) {
  if (caminho.startsWith("@/")) {
    return "src/" + caminho.slice(2);
  }

  return caminho;
}

function App() {
  return (
    <ul>
      {imports.map((i) => (
        <li key={i}>
          {i} → {resolver(i)}
        </li>
      ))}
    </ul>
  );
}

O slice(2) corta os dois caracteres do prefixo, e o resto do caminho vem junto. Quem não começa com @/ volta igual — é o caso do CSS relativo, que continua sendo relativo. Se você errar o apelido no projeto de verdade, o Vite responde com uma mensagem bem específica:

Failed to resolve import "@/components/Botao" from "src/pages/Cardapio.jsx".
Does the file exist?

Essa mensagem diz duas coisas úteis: qual import não resolveu e de qual arquivo ele veio. Com o alias configurado, ela costuma aparecer quando o caminho tem um erro de maiúscula ou quando a pasta src não é a que você pensou.

7. O index.js que reexporta

Existe um truque para encurtar imports: um arquivo index.js dentro da pasta que reexporta todos os irmãos. Aí import { Botao, Cabecalho } from "@/components" funciona, e você não precisa lembrar o nome do arquivo.

export { Botao } from "./Botao";
export { Cabecalho } from "./Cabecalho";
export { CartaoDePao } from "./CartaoDePao";

O nome desse padrão é barrel. Ele tem um custo escondido: o arquivo index.js importa todos os componentes da pasta, então quem importa um acaba puxando a lista inteira para o grafo de dependências. No desenvolvimento isso quase não aparece; no build, o empacotador consegue descartar o que não é usado, mas nem sempre — e o resultado é um pacote maior do que precisava. Há também o risco de import circular.

A recomendação prática: barrel é confortável em pastas pequenas e estáveis, e vira armadilha em pastas grandes. Se o time já usa, siga; se está começando, importe direto do arquivo — é mais explícito e o editor autocompleta de qualquer jeito. O que não vale é ter as duas formas convivendo sem regra.

8. Nomes, maiúsculas e o Linux que reprova

O sistema de arquivos do Windows e do macOS, por padrão, não diferencia maiúsculas de minúsculas: Botao.jsx e botao.jsx são o mesmo arquivo. O Linux do servidor diferencia. O resultado é um clássico: funciona na máquina da Ana e quebra no build, com a mensagem "Could not resolve ... from ...". O culpado é um import escrito com minúscula.

Por isso a convenção não é decoração: componente em PascalCase e arquivo com o mesmo nome do componente (Botao.jsx exporta Botao), hook começando com use e o resto em camelCase. O import tem de repetir o nome exato, letra por letra.

$ npm run build

vite v7.1.0 building for production...
✓ 34 modules transformed.
✗ Build failed in 812ms
error during build:
Could not resolve "../components/botao" from "src/pages/Cardapio.jsx"

A mensagem aponta o arquivo que pediu e o caminho que não foi encontrado — e o erro está na letra b. No Windows, o mesmo import abria a página sem reclamar; no Linux do build, o arquivo botao.jsx simplesmente não existe, porque o sistema diferencia maiúsculas. É o tipo de erro que só aparece no servidor, e é por isso que ele assusta: o código "funcionava".

Teste ao lado do componente é outra escolha que vale explicar: manter Botao.test.jsx na mesma pasta de Botao.jsx faz o teste ser movido junto, renomeado junto e encontrado junto. Uma pasta tests espelhando src também funciona, e é preferida por quem gosta de ver a árvore de código limpa. Qualquer uma serve, desde que seja consistente.

Um detalhe que se torna hábito: ao criar um componente, crie o arquivo com o nome já em PascalCase e importe-o imediatamente. O editor completa o caminho, e você nunca escreve o nome à mão — o que elimina 99% dos erros de maiúscula.

9. Cenários do dia a dia

Cenário 1: o componente que importa a página

Para mostrar uma prévia do cardápio dentro do cabeçalho, a Ana importou Cardapio.jsx no Cabecalho.jsx. Funcionou até o cardápio importar o cabeçalho de volta: o Vite passou a avisar de import circular, e a página começou a renderizar pela metade. O caminho é sempre descer: página importa componente, componente não importa página.

Cenário 2: a imagem que não atualiza

Ela trocou a foto do pão em public/pao.jpg e o navegador continuou mostrando a antiga. Como o arquivo em public mantém o nome, o cache não teve motivo para baixar de novo. A solução foi mover a foto para src/assets, onde o build gera um nome com hash — mudou o conteúdo, mudou o nome, mudou o cache.

Cenário 3: funciona no notebook, quebra no build

O import dizia "../components/botao", com minúscula, e no Windows abria normalmente. No Linux da hospedagem, o build parou com "Could not resolve". O conserto foi renomear o import para "../components/Botao". Para não repetir o susto, ela passou a criar o arquivo e o import pelo autocompletar do editor.

11. Resumo

Estrutura é uma decisão sobre onde as coisas moram, e existem duas formas de agrupar: por tipo ou por assunto. Projetos pequenos e médios vivem bem por tipo — components, pages, hooks, lib, styles —, e a regra de ouro é a direção dos imports: página importa componente, componente nunca importa página.

Imagens têm dois destinos: src/assets passa pelo build, ganha hash e é importada no código; public é copiado como está e é referenciado por URL. O atalho @ substitui os ../ e exige configuração no Vite e no editor. Barrels encurtam imports e custam peso no pacote; use com parcimônia.

E o detalhe que derruba build: nomes de arquivo seguem a convenção, e o import repete o nome exato. O Linux do servidor diferencia maiúsculas, o Windows da sua máquina não. Com o mapa arrumado, o projeto está pronto para receber os comandos do dia a dia — e é sobre eles, os scripts do package.json, que trata a próxima aula.

Para lembrar

  • Duas formas de agrupar: por tipo ou por assunto. Escolha uma e mantenha.
  • Página é tela; componente é peça. Página importa componente, nunca o contrário.
  • Lógica com estado e efeito: hooks/, arquivo começando com use.
  • Função pura: lib/ (ou utils/), sem hook nenhum.
  • src/assets passa pelo build e ganha hash; public é copiado igual.
