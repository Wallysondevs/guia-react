Introdução ao Contexto

O nome do cliente virou assunto de cinco cantos da tela da Ana: o cabeçalho cumprimenta, o carrinho assina, o rodapé avisa o atendimento, o selo marca quem é cadastrado e a nota fiscal imprime. Passar a prop cliente por todos esses caminhos faria o site dela virar um mapa de canos. Nesta aula ela conhece o contexto: um canal que fica no alto da árvore e que qualquer componente abaixo pode abrir, sem pedir licença para os níveis do meio.

Você vai aprender
  • O que é contexto, em uma frase que você pode repetir.
  • Como criar um canal com createContext e o que é o valor padrão.
  • Como o Provider abastece o canal para uma região da árvore.
  • Como um componente lê o valor com useContext.
  • Por que o provider não aparece no HTML gerado.
  • Como o valor vem do estado, e o que acontece quando ele muda.
  • Quando o contexto é a resposta errada e a prop continua sendo melhor.

1. A cena: o cliente em cinco lugares

Na aula anterior, a Ana resolveu o desconto montando o preço pronto lá em cima e entregando a peça pelo children. Funcionou para um cartão. Agora o nome do cliente aparece em cinco pontos distantes da tela, e alguns deles estão dentro de componentes que ela não controla — o rodapé, por exemplo, é usado em três telas diferentes.

Continuar com props significaria passar cliente para o Rodape, para o Cabecalho, para o Carrinho, para o Selo e para a NotaFiscal, e também para todos os pais deles. São nove assinaturas para um dado que só muda num lugar. Pior: no dia em que o cliente sair, cada um desses nove pontos precisa saber que o valor virou nulo.

O contexto resolve isso com uma ideia simples: em vez de entregar o dado de mão em mão, alguém abastece um canal no alto da árvore, e qualquer componente abaixo dele abre a torneira quando quiser. O canal tem nome, o valor tem dono, e os componentes do meio não ficam sabendo de nada.

2. Um canal, uma torneira

Contexto em React é isso: um canal nomeado que carrega um valor para uma região da árvore. Três peças o montam — a criação do canal, o fornecimento do valor e a leitura dentro do componente. As três têm nomes próprios, e vale decorar porque você vai digitá-los muitas vezes.

contexto
Um canal nomeado que leva um valor para todos os componentes abaixo dele. ClienteContexto, TemaContexto.
createContext
Cria o canal e recebe um valor padrão: createContext("visitante"). Fica fora do componente, no topo do arquivo.
Provider
O componente que abastece o canal para os seus descendentes: <ClienteContexto.Provider value={cliente}>.
value
O valor que o provider coloca no canal. Pode ser texto, número, objeto ou função — e normalmente vem de um estado.
useContext
A leitura: const cliente = useContext(ClienteContexto) devolve o valor do provider mais próximo acima.
valor padrão
O que o consumidor recebe quando não existe nenhum provider acima dele. Não é “carregando”: é “não tem provedor”.

Esse último termo confunde muita gente. O valor padrão não é um plano B para quando o dado ainda não chegou; é o valor de quem está fora da área abastecida. Se o seu selo aparece como “visitante” mesmo depois de você passar o cliente, o problema quase sempre é o provider estar no lugar errado — fora do ramo da árvore onde o selo mora.

Uma nota de versão: no React 19 dá para usar o próprio canal como provider, sem o .Provider: <ClienteContexto value={cliente}>. As duas formas funcionam e fazem a mesma coisa. Vou usar a forma clássica, com .Provider, porque é a que você encontra na maioria dos exemplos e a que funciona também em versões anteriores.

3. A caixa: criar, abastecer, ler

Vamos montar o canal do cliente. O ClienteContexto já existe, com o valor padrão “visitante”. O selo lá embaixo já lê o canal. O que falta é o provider: ninguém abasteceu o canal, então o selo recebe o padrão e mostra “Cliente: visitante” para uma cliente de cinco anos.

Envolva o <Cartao /> com <ClienteContexto.Provider value={cliente}> e </ClienteContexto.Provider>, e clique em Rodar.

const ClienteContexto = createContext("visitante");

function SeloDoCliente() {
  const cliente = useContext(ClienteContexto);
  return <p>Cliente: {cliente}</p>;
}

function Cartao() {
  return (
    <article className="cartao">
      <h2>Baguete</h2>
      <SeloDoCliente />
    </article>
  );
}

function App() {
  const cliente = "Ana";
  return <Cartao />;
}

  <h2>Baguete</h2>
  <p>Cliente: visitante</p>
</article>

Repare no painel: ele mostra o article e nada mais. O provider não vira elemento nenhum no HTML — ele é uma peça invisível que só serve para colocar um valor à disposição. Isso é diferente de uma div de moldura, que aparece no HTML e ocupa espaço na tela. O provider não ocupa nada: ele só muda o que os filhos conseguem ler.

Repare também no que não mudou. O Cartao continua igual, sem nenhuma prop nova. O SeloDoCliente continua lendo o canal do mesmo jeito. Toda a mudança aconteceu no App, que é quem tem o valor. É esse o ganho: quando o dado é do canal, os componentes do meio não precisam existir para carregá-lo.

Onde criar o canal, num projeto de verdade? O lugar natural é um arquivo próprio, como src/ClienteContexto.js, com uma linha: export const ClienteContexto = createContext(null). Quem precisa ler importa o canal; quem abastece também. Assim o canal tem um endereço só, e ninguém corre o risco de criar um segundo por engano. Aqui na caixa tudo fica no mesmo lugar só para você ver as três peças juntas, na ordem em que elas conversam.

4. O provider delimita uma região

O provider não abastece a página inteira: ele abastece o que está dentro dele. Isso parece detalhe e é a origem de quase todo bug de contexto. Abaixo, um dos cartões está dentro do provider e o outro ficou fora. O de dentro mostra a cliente; o de fora mostra o valor padrão, porque para ele não existe canal abastecido.

O segundo cartão ficou fora do provider e mostra “visitante”. Coloque os dois cartões dentro do mesmo Provider.

const ClienteContexto = createContext(null);

function Selo() {
  const cliente = useContext(ClienteContexto);
  if (!cliente) return <span className="selo visitante">visitante</span>;
  return <span className="selo logado">cliente {cliente}</span>;
}

function Cartao({ titulo }) {
  return (
    <article className="cartao">
      <h2>{titulo}</h2>
      <Selo />
    </article>
  );
}

function App() {
  const cliente = "Ana";

  return (
    <div>
      <ClienteContexto.Provider value={cliente}>
        <Cartao titulo="Baguete" />
      </ClienteContexto.Provider>
      <Cartao titulo="Pão de queijo" />
    </div>
  );
}

Duas coisas ficam claras nesse exercício. Primeiro, um provider pode abastecer quantos consumidores você quiser: todos os Selo dentro dele leem o mesmo valor, sem nenhuma prop. Segundo, dois providers diferentes podem conviver na mesma tela com valores diferentes — é o que permite ter um cabeçalho “da loja” e um “do painel” no mesmo aplicativo.

O valor padrão do createContext aparece só nesse caso de ausência. Por isso é comum criá-lo com um valor neutro e reconhecível, como null, em vez de um valor de negócio: se algo mostrar “null” na tela, você sabe na hora que faltou provider. Se o padrão for “visitante”, o bug se disfarça de funcionalidade.

5. O que o console mostra quando o valor é lido

Um jeito de ver o canal funcionando é logar dentro do consumidor. Cada componente que lê o contexto imprime o valor que recebeu, e a ordem das linhas conta a história da renderização:

function Selo() {
  const cliente = useContext(ClienteContexto);
  console.log("Selo leu: " + cliente);
  return <span className="selo">{cliente}</span>;
}

Com o provider no lugar certo e dois cartões dentro dele, o console mostra duas linhas iguais. Sem o provider, mostra o valor padrão:

Selo leu: visitante
Selo leu: Ana
Selo leu: Ana

A primeira linha é a versão antiga, sem provider; as duas seguintes são a versão consertada, com os dois cartões dentro. Duas leituras, dois cartões: cada consumidor lê por conta própria, no momento em que é desenhado. Não existe “valor guardado no componente” — existe leitura do que o provider oferece agora.

Isso tem uma consequência prática que vale guardar: o contexto não substitui o estado. Ele é um transporte. Quem guarda o valor é o useState de alguém; o provider só publica esse valor para baixo. Se ninguém tem estado, o contexto carrega uma constante — útil para configuração, inútil para interação.

Existe um detalhe de desempenho que vale saber desde já, mesmo sem medir nada: o contexto não tem seletor. Quem chama useContext recebe o valor inteiro e é redesenhado sempre que esse valor muda de identidade. Se o canal carrega um objeto com cinco campos e só um deles mudou, todos os consumidores são desenhados de novo. Por isso a recomendação é separar por assunto — um canal para o cliente, outro para o tema — em vez de um canal único com o “estado do mundo”.

6. O valor vem do estado, e todos acompanham

O caso real quase sempre tem interação: o cliente entra, sai, troca de conta. Como o valor do provider é só uma expressão, ele pode ser o estado do App. Quando esse estado muda, todos os consumidores abaixo são desenhados de novo com o valor novo.

O botão muda o estado, mas o provider está com o texto fixo value="visitante" e nada acontece na tela. Troque por value={cliente} e clique em “Entrar como Ana”.

const ClienteContexto = createContext("visitante");

function Cabecalho() {
  const cliente = useContext(ClienteContexto);
  return (
    <header>
      <h1>Padaria da Ana</h1>
      <p>Olá, {cliente}</p>
    </header>
  );
}

function Carrinho() {
  const cliente = useContext(ClienteContexto);
  return <p>Carrinho de {cliente}</p>;
}

function App() {
  const [cliente, setCliente] = useState("visitante");

  return (
    <div>
      <button onClick={() => setCliente("Ana")}>Entrar como Ana</button>
      <ClienteContexto.Provider value="visitante">
        <Cabecalho />
        <Carrinho />
      </ClienteContexto.Provider>
    </div>
  );
}

  <header>
    <h1>Padaria da Ana</h1>
    <p>Olá, visitante</p>
  </header>

</div>

Um clique mudou dois componentes que não têm relação nenhuma entre si. O Cabecalho não sabe que o Carrinho existe, e vice-versa; os dois só sabem que existe um canal chamado ClienteContexto. Essa independência é o que torna o contexto útil em telas grandes.

E aqui está a armadilha que a caixa mostra antes do conserto: o provider com valor fixo. O estado mudava, o botão funcionava, e a tela ficava parada — porque o valor publicado no canal era o texto “visitante”, não a variável. Quando um clique não muda nada, olhe o value do provider antes de suspeitar do consumidor.

Uma dúvida que aparece no dia seguinte: será que o setCliente também deveria ir pelo contexto? Pode, e às vezes é o certo — mas comece simples. Enquanto o botão que troca o cliente está na mesma tela do provider, passar a função por prop é mais direto e deixa claro quem muda o quê. Colocar tudo no canal de uma vez é como mudar de casa levando a geladeira ligada: funciona, mas ninguém sabe onde está o plugue.

7. Prop ou contexto?

As duas coisas continuam existindo, e a escolha não é ideológica. A pergunta é de quem é o dado. Se ele pertence a uma peça e a poucos vizinhos, é prop. Se ele pertence à tela inteira e é lido em pontos distantes, é contexto.

PerguntaPropContexto
quem usa o dado?um filho diretovários, em pontos distantes
como o componente declara a dependência?na assinatura, à vistadentro do corpo, com useContext
quem consegue trocar o valor?o pai, passando outra coisao provider, mudando o value
o que quebra se o dado sumir?a prop vira undefined, e você vêo consumidor recebe o padrão, em silêncio

Promover um dado a contexto é uma decisão de arquitetura, não um ajuste de sintaxe. O sinal de que chegou a hora costuma ser duplo: você já repassou a mesma prop por dois ou três componentes que não a usam, e os pontos que precisam do valor não compartilham um pai próximo. Faltando qualquer um dos dois, props resolvem — e resolvem com menos mistério.

Repare na última linha: o contexto é mais confortável e mais invisível. Um componente que lê contexto não revela a dependência para quem o usa — ele parece independente e não é. Por isso a recomendação é começar por props e só promover um dado a contexto quando o desconforto do drilling for real. Dado que muda de tela para tela não é contexto; dado que a tela inteira compartilha, sim.

8. As armadilhas do contexto

Quatro erros concentram quase todos os problemas. Vale ler com atenção, porque nenhum deles dá erro no console — todos aparecem como tela estranha.

O que aconteceuPor quêConserto

O último caso é o mais sutil. Se o createContext fica dentro da função do componente, cada desenho cria um canal novo; os consumidores passam a olhar para um canal diferente do que o provider abasteceu e caem no valor padrão. A regra é simples: canal se cria uma vez, no topo do arquivo, do lado de fora — igualzinho ao que a caixa mostra.

Vale também resistir à tentação de transformar tudo em contexto. Um valor que nunca muda — a versão do site, o nome da padaria, a lista de estados brasileiros — não precisa de canal: é constante importada, e o componente lê direto. Contexto serve para distribuir um valor que muda e que muita gente precisa acompanhar; para o resto, ele só acrescenta uma camada para o leitor atravessar.

E o primeiro caso, no mundo real, costuma vir com um erro de escopo. createContext não é uma função que existe por acaso no navegador; ela vem do React. Nas caixas deste guia ela já está no escopo, mas num projeto de verdade você precisa importar:

Uncaught ReferenceError: createContext is not defined

Essa mensagem quer dizer que o nome não foi importado. No projeto, a primeira linha do arquivo é import { createContext, useContext } from "react"; veja Criar o Projeto para o arquivo completo, com os imports no topo.

9. Cenários do dia a dia

Cenário 1: o selo que dizia “visitante”

A Ana criou o canal, passou o valor, e o selo continuou mostrando “visitante”. O provider estava dentro do Cartao, envolvendo só o preço, e o selo morava no rodapé, fora dele. Subir o provider dois níveis resolveu. Nenhum aviso no console — só o valor padrão aparecendo no lugar do dado.

Cenário 2: a loja e o painel na mesma tela

O site dela tem uma prévia da loja dentro do painel de administração. Dois providers do mesmo canal, um com o cliente logado e outro com “visitante”, deixam a prévia mostrar a experiência de quem não entrou sem duplicar componente nenhum. É o uso legítimo de dois valores ao mesmo tempo.

Cenário 3: o canal para o preço de um pão

Empolgada, ela criou um contexto para o preço da baguete. Funcionou, e depois ficou impossível saber de onde vinha o preço na hora de ler o código. Voltou para prop: um dado que só um cartão usa não merece canal. Contexto é para o que a tela inteira compartilha, não para fugir de uma prop chata.

11. Resumo

Contexto é um canal nomeado que leva um valor para uma região da árvore. Você cria o canal com createContext, abastece com um Provider e lê com useContext. Quem está abaixo do provider recebe o valor; quem está fora recebe o padrão. O provider não desenha nada no HTML — ele só muda o que os filhos conseguem ler.

O valor pode vir de um estado, e é aí que o contexto fica interessante: um clique no topo redesenha todos os consumidores, mesmo os que estão em galhos distantes e não têm relação entre si. O preço disso é que a dependência fica escondida — quem lê o componente não vê, na assinatura, de onde vem o valor.

Por isso a ordem prática continua a mesma da aula anterior: prop primeiro, composição quando o dado precisa de um lugar só, contexto quando o dado é da tela inteira. O contexto é uma ferramenta de distribuição, não um atalho para evitar props chatas. Na próxima aula o assunto muda de dados para organização: onde cada componente mora no projeto, em Pastas e Arquivos.

Para lembrar

  • Contexto: canal nomeado que leva um valor para uma região da árvore.
  • createContext(padrão) cria o canal; fica fora do componente, no topo do arquivo.
  • Provider value={...} abastece; sem ele, o consumidor recebe o padrão.
  • O provider delimita a região: filho fora dele não vê o valor.
  • useContext(Canal) lê o valor do provider mais próximo.
  • O provider não vira elemento no HTML: o painel mostra só os filhos.
  • O valor pode ser estado; quando muda, todos os consumidores redesenham.
  • Valor fixo no value congela a tela, mesmo com o estado mudando.
  • Contexto não guarda dado: ele transporta. O estado continua sendo do useState.
  • Se o dado muda de tela para tela, ainda é prop — não é contexto.
