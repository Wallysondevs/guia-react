Formulários

Formulário em React é sempre o mesmo circuito: um valor mora no estado, o campo mostra esse valor e o evento de mudança troca o estado. O que varia é o tipo de campo — texto, número, escolha única, marcação — e o que se faz com o valor no fim: validar, enviar, limpar. Esta página é a consulta da Ana para quando ela está escrevendo o formulário de encomenda e não quer reler quatro aulas para lembrar se checkbox usa checked ou value.

Como usar esta página
  • Comece pela seção 1 se você só quer o padrão; vá direto à tabela da seção 2 se o campo é de outro tipo.
  • Cada linha das tabelas aponta a aula que ensina o caso completo.
  • As duas caixas rodam com React 19: edite, clique em Rodar e leia o painel.
  • Os trechos de arquivo mostram o código como ele fica no projeto, com import.

1. O padrão: valor no estado, mudança no evento

Um campo é controlado quando o React manda no que ele mostra. Isso significa duas coisas escritas juntas: value recebendo o estado e onChange trocando o estado. Sem o primeiro, o campo não reflete o dado; sem o segundo, o campo nem aceita digitação.

import { useState } from "react";

export function CampoDeNome() {
  const [nome, setNome] = useState("");

  return (
    <div>
      <label htmlFor="nome">Nome</label>
      <input
        id="nome"
        value={nome}
        onChange={(e) => setNome(e.target.value)}
      />
      <p>Você digitou: {nome}</p>
    </div>
  );
}

O evento chega como um objeto, e o valor digitado está em e.target.value — sempre texto, em qualquer tipo de campo. Quem define o que o estado guarda é você: e.target.value cru para texto, Number(e.target.value) para número, e.target.checked para marcação. Essa escolha aparece na seção 3 e é a origem da maior parte dos bugs de comparação em formulário.

campo controlado
Campo cujo valor visível vem do estado do componente, via value, e cuja mudança volta pelo onChange.
value
O que o campo mostra. No JSX é sempre a variável do estado — nunca o valor digitado direto.
onChange
A função que roda a cada alteração. Recebe o evento e chama a função do useState.
evento
O objeto que o navegador entrega: e.target.value para texto, e.target.checked para checkbox e radio.
name
O nome do campo no HTML. Agrupa radios e é o que aparece num envio de formulário tradicional.
submit
O evento de envio do <form>, tratado com onSubmit mais e.preventDefault().

Se você escrever value e esquecer o onChange, o campo fica somente leitura e o console do navegador avisa. É um dos avisos mais úteis do React, porque o sintoma na tela — “o campo não aceita nada” — parece problema de CSS:

Warning: You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field.

O caminho de volta também confunde. Se você escrever só onChange, sem value, o campo aceita digitação e mostra o que o navegador quiser — o estado muda, mas a tela não obedece. É o modo não controlado, legítimo em formulários simples, e assunto da seção 7.

Duas escolhas do evento merecem ser conhecidas desde o começo. O onChange do React dispara a cada tecla — é o evento input do navegador, e não o change que só dispara ao sair do campo. Quem quer validar no fim da digitação usa onBlur, que roda quando o campo perde o foco. E o valor pode ser lido de e.target (o elemento que disparou) ou de e.currentTarget (o elemento que tem o manipulador). Em campo simples os dois apontam para o mesmo lugar; em formulário com campos aninhados, currentTarget é o que você quer.

2. Um campo de cada tipo

A regra é a mesma para todos; o que muda é o atributo que carrega o valor e o lugar de onde ele vem no evento. Esta tabela é a consulta rápida:

CampoO atributoO que guardarAula
<input type="text">valuee.target.value (texto)Input Controlado
<input type="number">valueNumber(e.target.value)Entrada Controlada
<textarea>valuee.target.value (nunca por filhos)Textarea
<select>valueo value da opção escolhidaSelect
<input type="checkbox">checkede.target.checked (booleano)Checkbox
<input type="radio">checkedo valor da opção, comparado no checkedRadio
<input type="file">nenhume.target.files — o valor é só leituraControlado e Não Controlado

Duas linhas dessa tabela explicam quase todos os bugs de formulário. A do checkbox: marcar não muda value, muda checked — quem lê e.target.value num checkbox recebe "on", que é o valor padrão do HTML. A do arquivo: por segurança, o navegador não deixa o React definir o conteúdo de um seletor de arquivo, então ele não é controlado em nenhuma versão.

O atributo name, que parece enfeite em formulário controlado, é o que permite ler o formulário inteiro de uma vez: new FormData(e.currentTarget) devolve um objeto com o valor de cada campo nomeado, pronto para Object.fromEntries. Em formulário controlado o estado já tem tudo, então o name fica para a acessibilidade e para o envio tradicional; em formulário não controlado, ele é o caminho de leitura. Os dois podem conviver na mesma tela, campo a campo.

3. Texto, número e área de texto

Campo de texto é o caso direto: value={texto} e onChange guardando e.target.value. O cuidado está no número. O navegador entrega texto mesmo em type="number", e a diferença aparece na primeira conta.

typeof e.target.value: string
"3" + 1 = "31"
"3" * 1 = 3

Por isso a conversão é explícita: setQuantidade(Number(e.target.value)). Se o campo puder ficar vazio durante a digitação, Number("") devolve 0 — e o total pisca para zero enquanto a pessoa apaga. Guardar o texto e converter no cálculo é a alternativa que evita o pisca; guardar o número é mais simples e serve quando o campo não é apagado no meio da edição.

O campo guarda o valor inicial, mas não é controlado: digitar não muda o total. Ligue o campo ao estado com value={quantidade} e onChange={(e) => setQuantidade(Number(e.target.value))}.

function App() {
  const [quantidade, setQuantidade] = useState(1);
  const preco = 6;

  return (
    <div>
      <label htmlFor="qtd">Quantidade de pães</label>
      <input id="qtd" type="number" defaultValue={quantidade} />
      <p>Total: R$ {quantidade * preco + ",00"}</p>
    </div>
  );
}
<div>
  <label for="qtd">Quantidade de pães</label>
  <input id="qtd" type="number" value="1">
  <p>Total: R$ 6,00</p>
</div>

Repare no + ",00": dinheiro formatado à mão é o que aparece em exemplo de guia, e é o que menos dá problema quando os preços são redondos. Para valores com centavos, use valor.toFixed(2).replace(".", ",") ou um formatador de moeda — o assunto não é React, é apresentação.

Se o seu formulário aceita preço digitado pelo cliente, o problema é outro: no Brasil se escreve 12,50, e Number("12,50") devolve NaN. As saídas são guardar o texto e converter trocando a vírgula por ponto no momento do cálculo, ou usar inputMode="decimal" para o teclado do celular abrir com vírgula e tratar a conversão na função do onChange. O que não funciona é confiar no type="number": ele recusa a vírgula em alguns navegadores e engole o valor em outros.

A <textarea> tem uma diferença de HTML que confunde quem vem de fora: o conteúdo não vai entre as tags, vai no value. Escrever <textarea>texto</textarea> no JSX não funciona como valor controlado; o React trata o que está entre as tags como valor inicial e avisa. A aula Textarea mostra o campo de observação da encomenda, com contagem de caracteres.

4. Escolhas: select, checkbox e radio

Os três campos de escolha parecem parentes e funcionam de formas diferentes. A confusão nasce do mesmo lugar: value serve para o campo que guarda um valor entre vários; checked serve para o campo que guarda um sim ou não.

CampoComo fica no JSXNo evento
select simples<select value={tamanho} onChange={...}> com <option value="G">e.target.value
select múltiplo<select multiple value={escolhas}>Array.from(e.target.selectedOptions, (o) => o.value) — Select
checkbox único<input type="checkbox" checked={aceito} onChange={...} />e.target.checked — Checkbox
lista de checkboxeschecked={marcados.includes(id)}novo array com o id dentro ou fora — Estado com Array
radio (grupo)checked={pagamento === "pix"} mais name="pagamento"setPagamento("pix") — Radio

No select, o valor do estado é o value da <option>, não o texto que aparece. Se você esquecer o value na opção, o navegador usa o texto como valor — e o código passa a comparar com “Pix” maiúsculo sem ninguém entender por quê. No radio, o name igual em todas as opções é o que faz o navegador tratar o grupo como um só; o checked é uma comparação, e o onChange grava o valor daquela opção.

Para listas de checkbox, o estado é um array de ids, e a função de troca devolve um array novo: dentro se o id não estava, fora se estava. Mutar o array com push não redesenha, pelo mesmo motivo de sempre — o React compara a referência. A aula Checkbox traz a versão com “marcar todos”, e a Radio mostra o grupo com fieldset e legend.

Um detalhe que morde em formulário de edição: select com valor que não existe entre as opções mostra a primeira da lista, sem aviso. Se o estado guarda "G" e as opções são "P", "M" e "GG", a tela mente. O mesmo vale para o radio: nenhuma opção marcada quando o valor do estado não bate com nenhum checked. Ao carregar dados de fora, garanta que o valor do estado é um dos valores possíveis — ou inclua uma opção vazia com <option value="">Escolha</option> para o caso “ainda não escolhi”.

5. Envio: onSubmit, preventDefault e o botão certo

O envio é um evento do <form>, não do botão. Você escreve <form onSubmit={enviar}>, e o navegador chama enviar quando alguém clica no botão de envio ou aperta Enter dentro de um campo. A primeira linha do manipulador precisa ser e.preventDefault(): sem ela, o navegador faz o envio tradicional, recarrega a página e o estado todo se perde.

O formulário envia vazio. Valide antes: se nome.trim() === "", mostre Digite seu nome e pare; se estiver preenchido, mostre "Pedido de " + nome + " enviado".

function App() {
  const [nome, setNome] = useState("");
  const [enviado, setEnviado] = useState("");

  function enviar(e) {
    e.preventDefault();
    setEnviado("Pedido de " + nome + " enviado");
  }

  return (
    <form onSubmit={enviar}>
      <label htmlFor="nome">Nome</label>
      <input
        id="nome"
        value={nome}
        onChange={(e) => setNome(e.target.value)}
      />
      <button>Enviar pedido</button>
      <p>{enviado}</p>
    </form>
  );
}
<form>
  <label for="nome">Nome</label>
  <input id="nome" value="">
  <button>Enviar pedido</button>
  <p></p>
</form>

function App() {
  const [nome, setNome] = useState("");
  const [erro, setErro] = useState("");
  const [enviado, setEnviado] = useState("");

  function enviar(e) {
    e.preventDefault();

    if (nome.trim() === "") {
      setErro("Digite seu nome");
      return;
    }

    setErro("");
    setEnviado("Pedido de " + nome + " enviado");
  }

  return (
    <form onSubmit={enviar}>
      <label htmlFor="nome">Nome</label>
      <input
        id="nome"
        value={nome}
        onChange={(e) => setNome(e.target.value)}
      />
      {erro ? <p>{erro}</p> : null}
      <button>Enviar pedido</button>
      <p>{enviado}</p>
    </form>
  );
}

Três detalhes que a caixa deixa visíveis. O return antecipado dentro do manipulador é legítimo — ele não é hook, então não quebra regra nenhuma. O trim() existe porque um espaço não é nome. E o botão dentro de um <form> já é type="submit" por padrão; se você quiser um botão que não envie, escreva type="button", senão ele dispara o envio sem querer.

Quando o envio espera o servidor, o padrão é travar o botão e mostrar o que está acontecendo — o mesmo pendente da aula O useTransition. A aula Envio de Formulário faz o caminho completo com espera simulada e mensagem de erro.

Depois do envio bem-sucedido, limpar é uma decisão de produto. Em formulário controlado, limpar é chamar a função do estado com o valor inicial: setNome(""), setQuantidade(1). Em formulário não controlado, é e.currentTarget.reset(), que devolve cada campo ao defaultValue. O que não se faz é limpar só alguns campos e deixar o resto — a pessoa vê metade do pedido anterior na tela e não sabe se enviou ou não.

6. Validação e mensagens que o leitor de tela ouve

Existem duas validações e elas convivem. A do navegador é declarativa — required, minLength, type="email" — e mostra o balão nativo antes de o onSubmit rodar. A do componente é sua: roda no envio, guarda a mensagem em estado e aparece na tela. A nativa cobre o básico; a do componente cobre o que o HTML não sabe, como “esse CEP não é da nossa área”.

Para a mensagem ser acessível, três coisas: o campo tem id e label ligados por htmlFor; a mensagem tem um id próprio e o campo aponta para ela com aria-describedby; e o campo recebe aria-invalid={Boolean(erro)} para o leitor de tela anunciar o estado. Sem isso, a mensagem vermelha existe só para quem enxerga.

const id = useId();
const erro = email.includes("@") ? "" : "Falta o @ no e-mail";

<label htmlFor={"email-" + id}>E-mail</label>
<input
  id={"email-" + id}
  value={email}
  onChange={(e) => setEmail(e.target.value)}
  aria-invalid={Boolean(erro)}
  aria-describedby={erro ? "erro-" + id : undefined}
/>
{erro ? <p id={"erro-" + id}>{erro}</p> : null}

O useId entra porque o componente pode aparecer duas vezes na mesma página — veja O useId.

A validação nativa tem um comportamento que surpreende em teste: o balão do navegador só aparece quando o formulário tenta enviar, e não quando o campo perde o foco. Se você quiser controlar a mensagem, pode desligar a nativa com noValidate no <form> e assumir a validação toda no onSubmit — é o que a maioria dos formulários com mensagem própria faz. O preço é reimplementar o básico: campo obrigatório, tamanho mínimo, formato de e-mail.

E a validação não deve rodar a cada letra sem critério: mostrar “e-mail inválido” enquanto a pessoa digitou a primeira letra é hostil. Valide no envio, ou depois que o campo perde o foco; a aula Validação compara os momentos e mostra a mensagem que aparece na hora certa.

7. Controlado, não controlado e o que o React 19 muda

Nem todo campo precisa de estado. Um formulário de uma linha, que só é lido no envio, pode usar defaultValue e ler os valores do próprio formulário. A escolha é entre ter o valor sempre à mão (controlado) e ter menos código (não controlado).

Você precisa…ControladoNão controlado
validar enquanto digitasim, é o ponto fortenão sem gambiarra
habilitar botão só com formulário válidosimnão
limpar o formulário depois do enviosetValor("")form.reset() ou e.target.reset() — Envio de Formulário
ler um arquivoimpossívele.target.files — Controlado e Não Controlado
formulário grande, sem regra dinâmicamais códigomais simples

O React 19 acrescentou um terceiro caminho: passar uma função para o action do formulário — <form action={enviar}> — e deixar o React cuidar do envio, do estado pendente e do resultado. É a base das ações, que a aula Formulários com Actions mostra com o mesmo formulário de encomenda. Para quem está começando, o caminho controlado continua sendo o que ensina o mecanismo; o action é a conveniência que vem depois.

Um cuidado que vale para os dois: não misture value com defaultValue no mesmo campo, e não troque um pelo outro no meio da vida do componente. O React trata a troca como mudança de modo e avisa no console; o campo pode perder o que estava digitado.

Se você escolher o caminho não controlado, o formulário continua tendo estado — só que ele mora no DOM. A leitura acontece no envio, com new FormData(e.currentTarget), e o resultado é um FormData de onde se lê dados.get("nome"). A vantagem é menos código; a desvantagem é que qualquer regra “o botão só habilita com tudo preenchido” exige um estado paralelo só para isso. Por isso o guia começa pelo controlado: ele custa duas linhas e evita a segunda fonte de verdade.

8. Erros comuns

Cinco sintomas cobrem a maior parte dos formulários quebrados. A tabela vai do que aparece na tela ao conserto.

SintomaCausaConserto
o campo não aceita digitaçãovalue sem onChangeligar o onChange ao estado — Input Controlado
a página recarrega ao enviarfalta e.preventDefault()primeira linha do onSubmit — Envio de Formulário
o checkbox nunca marcavalue em vez de checkedchecked={marcado} e e.target.checked
o select mostra sempre a primeira opçãoselected na <option>value no <select> — Select
a comparação de número falhae.target.value é textoNumber(...) ou valueAsNumber — Entrada Controlada

O caso do selected merece uma nota: no HTML puro, a opção escolhida é marcada com selected. No JSX controlado, quem manda é o value do select; escrever selected na opção faz o React tratar aquilo como valor inicial e brigar com o estado. Mesma ideia do checked em radio: o atributo existe, mas não é ele que você escreve.

E o erro que não é erro: campo com type="number" aceitando letra no teclado do computador. O navegador filtra o que dá, mas deixa digitar e, + e -, porque são parte de notação científica. Se você precisa de um número inteiro positivo, valide no envio; o atributo type é uma dica, não uma garantia.

Outro que não dá erro e confunde: o formulário que “não limpa”. Quase sempre o campo é controlado e o estado foi definido com o valor inicial fora do componente — uma constante que sobrevive entre montagens. Ao remontar a tela, o estado volta com o valor da constante e a impressão é de que o envio não terminou. O conserto é o valor inicial ser simples ("", 0, false) e o dado carregado entrar por prop, com um efeito que copia uma vez só.

Resumo

Campo controlado é value mais onChange, com o estado mandando no que aparece. Texto e textarea guardam e.target.value; número precisa de Number(...); select guarda o value da opção; checkbox e radio usam checked e e.target.checked. Arquivo não é controlado.

O envio é do <form>: onSubmit, preventDefault() na primeira linha e o botão de envio dentro dele. A validação do navegador cobre o básico; a do componente cobre o resto e precisa de label ligado, aria-describedby para a mensagem e aria-invalid para o estado. Formulário simples pode ser não controlado, com defaultValue; o React 19 ainda oferece action no formulário, que a aula de actions detalha.

Para lembrar

  • value sem onChange vira campo somente leitura.
  • e.target.value é sempre texto; converta número com Number.
  • textarea usa value, não conteúdo entre tags.
  • select usa value no select, não selected na opção.
  • Checkbox e radio usam checked; lista de checkbox usa array de ids.
  • Radio se agrupa pelo name igual em todas as opções.
  • Envio: onSubmit mais preventDefault(), sempre.
  • Mensagem de erro com id e aria-describedby no campo.
  • Arquivo é sempre não controlado: leia e.target.files.
  • Não misture value e defaultValue no mesmo campo.
