Props

Props são os dados que entram num componente: o que quem chama manda e o componente recebe como um objeto. Esta página é a consulta rápida do assunto — como passar texto, número, objeto, array e função, como receber com desestruturação e valor padrão, o que é children, quando o repasse vira drilling e quais erros aparecem no caminho. A Ana usa props desde que separou o cabeçalho da padaria em um componente; aqui está o resumo que ela consulta antes de desenhar um componente novo.

Como usar esta página
  • As tabelas são para consultar no meio do código; cada linha aponta para a aula completa.
  • As duas caixas rodam React 19: edite, clique em Rodar e leia o HTML gerado no painel.
  • A ordem das seções vai do "como se passa" ao "como se desenha o contrato" de um componente.

1. O que são props

Prop é o dado que um componente recebe de fora. Quem chama escreve os valores como atributos no JSX; o React junta tudo num objeto e entrega como primeiro parâmetro da função. É por isso que <Cartao nome="Ana" preco={2.5} /> chega no componente como { nome: "Ana", preco: 2.5 }.

Duas consequências vêm junto com essa definição. A primeira: props são somente leitura. O componente usa os valores, mas não os altera — quem manda no dado é quem chama. A segunda: mudar uma prop muda o componente, porque o React chama a função de novo com o objeto novo. Não existe "atualizar props" de dentro: existe outro render, com outros valores, vindo do pai.

function Cartao(props) {
  return (
    <div className="cartao">
      <h3>{props.nome}</h3>
      <p>R$ {props.preco.toFixed(2)}</p>
    </div>
  );
}

function App() {
  return (
    <div>
      <Cartao nome="pão francês" preco={0.9} />
      <Cartao nome="pão de queijo" preco={2.5} />
    </div>
  );
}

O objeto de props é montado pelo React, não por você. Ele não tem métodos nem campos mágicos: é o que você escreveu, com as chaves iguais aos nomes dos atributos. key é a exceção — o React a consome para identificar o item e não a repassa. Se precisar do identificador dentro do componente, passe outro atributo, como id.

Para conferir o que chegou, um console.log(props) na primeira linha do componente resolve. No console do navegador, o objeto aparece com as chaves na ordem em que foram escritas:

props: { nome: "pão de queijo", preco: 2.5, destaque: true }

É um jeito rápido de descobrir o nome errado de uma prop: se a chave que você espera não está no objeto, o problema está na chamada, não no componente.

prop
Um valor passado a um componente: nome="Ana", preco={2.5}.
props
O objeto com todas as props recebidas. É o primeiro parâmetro da função componente.
desestruturar
Tirar os campos do objeto direto no parâmetro: function Cartao({ nome, preco }).
children
O que fica entre a abertura e o fechamento da tag. Chega como uma prop chamada children.
callback
Uma função passada como prop, que o filho chama para avisar o pai: aoSalvar.

Um detalhe de leitura: o nome da prop é livre, mas o objeto que chega é sempre um só. Não existe "segundo parâmetro" nem "props posicionais". Se o componente precisa de dois valores, são duas chaves do mesmo objeto.

2. Passando props

A regra é a mesma do JSX para qualquer atributo: aspas entregam texto, chaves entregam JavaScript. nome="Ana" passa a string; preco={2.5} passa o número; itens={lista} passa o array; aoSalvar={salvar} passa a função — sem parênteses, senão o que chega é o retorno dela.

Booleanos têm atalho. <Cartao destaque /> é o mesmo que destaque={true}, e destaque={false} desliga. Já para um valor que pode ser null ou undefined, não existe atalho: escreva a chave com o valor.

<Cartao nome="pão de queijo" preco={2.5} />
<Cartao nome={produto.nome} preco={produto.preco} destaque />
<Cartao {...produto} />            {/* repassa nome, preco e o que mais houver */}
<Cartao nome={nome || "sem nome"} />

{/* key é da lista, não é prop */}
{produtos.map((p) => <Cartao key={p.id} nome={p.nome} />)}

O spread {...produto} é útil quando o objeto já tem as chaves certas, e perigoso quando não tem: ele passa tudo, inclusive campos que o componente não espera. Em código de time, prefira listar as props que importam — quem lê a chamada entende o contrato sem abrir o objeto.

Esses parênteses a mais são um dos erros mais comuns do React, e o sintoma é estranho: a função roda sem clique, ou o componente quebra com um valor que não é função.

3. Recebendo props

Você pode receber o objeto inteiro e acessar cada campo, ou desestruturar no parâmetro. O segundo jeito é o mais usado porque deixa o corpo do componente limpo e o contrato visível na primeira linha.

// objeto inteiro
function Cartao(props) {
  return <p>{props.nome} — R$ {props.preco}</p>;
}

// desestruturado no parâmetro (o mais comum)
function Cartao({ nome, preco }) {
  return <p>{nome} — R$ {preco}</p>;
}

// com valor padrão e renomeação
function Cartao({ nome = "pão francês", preco: valor }) {
  return <p>{nome} — R$ {valor}</p>;
}

O nome props é convenção, não regra: qualquer nome serve, porque o parâmetro é só o primeiro argumento da função. A convenção existe para quem lê. Ao desestruturar, você troca o nome genérico pela lista de campos — e o contrato do componente aparece na primeira linha, sem precisar procurar props. pelo corpo.

O valor padrão só vale quando a prop chega undefined — que é o caso de quem não passa nada. Se chegar null, o padrão não entra; para cobrir os dois, use nome ?? "pão francês" (o operador que só troca null e undefined). E cuidado com padrão em objeto: { pedido = {} } protege contra undefined, mas não contra um objeto sem os campos — aí a proteção é no acesso, pedido.nome ?? "sem nome".

Um cuidado ao desestruturar: você está lendo os campos, não copiando os valores. Se a prop é um objeto e o componente faz const { pedido } = props, pedido continua sendo o mesmo objeto do pai — mexer nele é mexer no estado de quem chamou. Desestruturar deixa o código mais curto, mas não protege contra mutação; quem protege é a disciplina de tratar prop como somente leitura.

Vale saber também que o objeto de props é novo a cada render do pai. Isso não muda nada para texto e número, mas importa quando a prop é objeto, array ou função: a identidade muda, e componentes embrulhados em memo redesenham. O assunto é das aulas de useMemo e useCallback; na prática, o que se estabiliza é o valor, não a prop.

O primeiro erro de prop: o nome não bate

Se quem chama escreve nomeCompleto e o componente lê nome, a prop chega undefined. Não há erro de compilação: o JSX aceita qualquer atributo. O sintoma é uma tela com buraco ou um TypeError ao acessar um campo de algo que não existe.

TypeError: Cannot read properties of undefined (reading 'nome')

A leitura: em algum lugar você fez props.pedido.nome e props.pedido é undefined — ou a prop não foi passada, ou o nome está diferente. Confira os dois lados: a chave na chamada e a chave no parâmetro. Em projeto com TypeScript, esse erro é pego no editor; em JavaScript puro, é o console que avisa, tarde.

4. Props com objetos, arrays e funções

Props não são só texto. Um objeto inteiro pode ir como prop, e o componente decide o que mostrar dele. A vantagem é passar uma coisa só; a desvantagem é que o contrato fica escondido — quem lê o componente precisa saber quais campos o objeto tem. Para dois ou três campos, listar as props costuma ser mais claro.

function Resumo({ pedido }) {
  return (
    <div>
      <p>{pedido.nome} — {pedido.itens.length} itens</p>
      <p>total: R$ {pedido.total.toFixed(2)}</p>
    </div>
  );
}

Array entra do mesmo jeito, e o componente costuma usar map — com key, como manda o JSX. Função entra para o filho avisar o pai: o filho recebe aoSalvar e chama no clique; quem sabe o que fazer com o dado é o pai, que é o dono do estado. Esse é o caminho normal para "o filho pediu, o pai mudou".

function Linha({ pao, aoPedir }) {
  return (
    <li>
      {pao.nome}
      <button onClick={() => aoPedir(pao.id)}>Pedir</button>
    </li>
  );
}

function Lista() {

Repare no onClick={() => aoPedir(pao.id)}: sem a função intermediária, o aoPedir rodaria no render. É o mesmo cuidado do salvar() com parênteses, agora com um argumento. A função nova a cada render não é problema aqui, porque ela não atravessa um memo; se atravessar, a aula de useCallback explica o que fazer.

O botão recebe aoPedir, mas o App não passa nada. Passe aoPedir={pedir} e clique em Pedir: o aviso tem de aparecer.

}

Sem a prop, aoPedir é undefined e o onClick fica sem função: o clique não faz nada e não há erro. Com a prop, o filho chama a função do pai, o pai muda o estado e o aviso aparece. Repare que o filho não sabe o que é "pedido feito" — ele só avisa; quem decide o texto é quem é dono do estado.

5. children: o conteúdo entre as tags

O que você escreve entre a abertura e o fechamento de um componente vira a prop children. Serve para o componente embrulhar conteúdo que ele não conhece: um cartão, um painel, um modal. O componente cuida da moldura; quem chama decide o miolo.

function Cartao({ titulo, children }) {
  return (
    <section className="cartao">
      <h3>{titulo}</h3>
      {children}
    </section>
  );
}

function App() {
  return (
    <Cartao titulo="Promoções">
      <p>pão de queijo pela metade do preço</p>
      <button>Aproveitar</button>
    </Cartao>
  );
}

children pode ser texto, um elemento ou vários — nesse caso, um array. Se o componente precisa de mais de um "buraco", use props normais com nomes próprios (cabecalho, rodape) e passe elementos por elas; é o padrão de slots da aula de slots com children. O que não vale é tentar adivinhar: se o componente precisa saber o que está em volta, o desenho está errado.

Um detalhe que evita surpresa: nem sempre há children. Num componente usado como <Cartao titulo="Promoções" />, a prop chega undefined — e desenhar {children} não quebra, porque undefined não vira texto. Só não conte com ele para medir altura, contar itens ou aplicar estilo: se o componente depende do conteúdo, peça o dado por prop e deixe o children para o que é decorativo ou opcional.

6. Props drilling e as saídas

Quando um dado precisa descer três ou quatro níveis, cada componente intermediário vira um carteiro: recebe a prop, não usa, repassa. Isso se chama props drilling. Com um nível ou dois, é o jeito mais simples e mais explícito; com cinco, vira ruído e todo mundo mexe em componentes que não têm nada a ver com o dado.

As saídas são conhecidas. A primeira é composição: em vez de passar o dado até o fundo, passe o elemento pronto — quem está embaixo recebe o JSX e nem sabe de onde veio. A segunda é contexto: um valor disponível para toda a árvore, sem intermediários, bom para tema, idioma e usuário logado. A terceira é elevar o estado para um ancestral comum que faça o dado circular menos.

function Painel() {
  const [usuario, setUsuario] = useState("Ana");

  return <Barra usuario={usuario} />;
}

function Barra({ usuario }) {
  // não usa usuario: só repassa
  return <Saudacao usuario={usuario} />;
}

function Saudacao({ usuario }) {
  return <p>Olá, {usuario}</p>;
}

Esse é o drilling em forma pura: Barra recebe e entrega, sem usar. Um nível assim é aceitável; três iguais já pedem uma decisão. Se Barra só existe para posicionar Saudacao, a composição resolve — <Barra><Saudacao usuario={usuario} /></Barra> —, porque o dado deixa de atravessar quem não o usa.

O critério prático: enquanto a prop é usada por quem a recebe, ela é informação. Quando ela só passa adiante, é transporte — e transporte em excesso pede uma das saídas acima. Não comece com contexto por precaução: comece passando props e mude quando o repasse doer de verdade.

8. Desenhando o contrato de um componente

Antes de escrever o componente, responda quatro perguntas. Quais dados ele precisa para desenhar? Quais são opcionais e têm padrão? Ele precisa avisar o pai de algo, e por meio de qual função? Ele embrulha conteúdo de fora (children) ou é fechado?

As respostas viram o parâmetro desestruturado. Um componente com duas props e um callback é fácil de usar e de testar; um com doze props é um formulário disfarçado. Se o número crescer, agrupe o que anda junto num objeto — mas só quando o objeto tiver um nome que faça sentido no domínio (pedido, cliente), não um config genérico.

function Botao({
  texto = "Salvar",
  tipo = "button",
  carregando = false,
  aoClicar,
  children,
}) {
  return (
    <button type={tipo} disabled={carregando} onClick={aoClicar}>
      {carregando ? "Salvando..." : texto}
      {children}
    </button>
  );
}

Três convenções que economizam conversa no time. Primeira: nome de callback começa com ao — aoSalvar, aoPedir, aoFechar —, o que deixa claro que é uma função, e não um dado. Segunda: prop booleana tem nome positivo (aberto, não naoFechado), porque aberto={false} lê melhor que uma negação dupla. Terceira: valor padrão para tudo que é opcional, na própria desestruturação, para o componente nunca receber undefined onde espera texto.

Com o contrato definido, o componente não precisa saber quem o chama. Ele recebe, desenha e avisa. Essa separação é o que permite reaproveitar o mesmo cartão na padaria, na livraria e no painel de pedidos: o dado muda, o componente não.

Resumo

Props são o objeto que o componente recebe de fora, montado a partir dos atributos do JSX. Aspas passam texto, chaves passam JavaScript; booleanos têm atalho e spread repassa um objeto inteiro. Do lado de dentro, desestruturar no parâmetro é o padrão, com valor padrão para o que é opcional e ?? quando o null é possível.

Objetos, arrays e funções também são props. Função é o caminho do filho avisar o pai — sempre passada como referência, nunca chamada na hora. children é o conteúdo entre as tags e serve para embrulhar o que o componente não conhece. Quando o repasse de props vira transporte em vários níveis, as saídas são composição, contexto ou elevar o estado.

Os erros vêm sempre do mesmo lugar: nome que não bate, função chamada com parênteses, key esperada como prop, prop mutada. Se o componente mostra undefined, confira primeiro a chamada; se quebra ao acessar um campo, confira se o objeto chegou; se a função roda sozinha, procure os parênteses.

Para lembrar

  • Props chegam como um objeto só: o primeiro parâmetro da função.
  • Props são somente leitura; quem muda o valor é quem chama.
  • Aspas = texto; chaves = JavaScript; {funcao} sem parênteses.
  • Desestruturar no parâmetro deixa o contrato visível.
  • Valor padrão só cobre undefined; para null, use ??.
  • children é o que fica entre as tags.
  • Callback com prefixo ao e passado por referência.
  • key não é prop: passe id se precisar do valor.
  • Drilling de um ou dois níveis é normal; acima disso, composição ou contexto.
  • Prop mutada funciona até o próximo render — e depois vira bug.
