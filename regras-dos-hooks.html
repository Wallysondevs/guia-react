As Regras dos Hooks

O painel da Ana funcionava. Ela acrescentou um desconto que só aparece quando o cupom está ativo, e o botão “Aplicar cupom” parou de fazer qualquer coisa — sem erro na tela, sem borda vermelha, sem nada. Depois foi a lista de pães, que quebrou ao receber o segundo item. Nesta aula a Ana entende por que essas duas coisas têm a mesma causa: o React não procura os hooks pelo nome, ele os conta pela ordem. Entender essa frase resolve os três erros que mais aparecem em código de quem está começando.

Você vai aprender
  • Como o React reconhece cada hook: por posição, não por nome.
  • Por que um hook fora de componente ou de hook próprio não funciona.
  • O que acontece quando um hook fica dentro de um if.
  • Por que hook dentro de laço quebra quando a lista cresce, e a saída de extrair um componente.
  • O que o return antecipado faz com a lista de hooks.
  • Como reescrever cada caso sem perder a lógica.
  • Que mensagens o ESLint e o React dão — e o que elas querem dizer.

1. A cena: o cupom que derrubou o painel

A Ana quis mostrar um desconto de 10% quando o cupom estivesse aplicado. Escreveu o estado do cupom, depois um if e, dentro do if, guardou o valor do desconto em um useState. A tela inicial ficou perfeita: “Desconto: 0%”. Clicou em “Aplicar cupom” e o painel congelou — o número não mudou, o botão não respondeu mais, e nenhum aviso apareceu.

No mesmo dia, a lista de pães quebrou. Ela guardava o “curtir” de cada pão dentro do map, um useState por item. Com um pão, tudo certo. Com dois, a tela sumiu. Duas telas diferentes, dois sintomas parecidos, uma causa só: em React, os hooks de um componente são identificados pela ordem em que são chamados. Quando a ordem ou a quantidade muda de um desenho para o outro, o React deixa de saber qual estado é qual.

Vale dizer desde já o que não é a causa: não é cache, não é “o React perdido”, não é bug da biblioteca. É uma decisão de projeto que permite ao React guardar estado sem que você nomeie nada. O preço dessa economia é uma regra simples de seguir e difícil de adivinhar quando se está começando.

2. Como o React reconhece um hook

Quando um componente é desenhado pela primeira vez, o React abre uma ficha para aquela instância e vai anotando, na ordem: “posição 1: um useState com o valor 0”, “posição 2: um useEffect com estas dependências”, “posição 3: um useId”. No desenho seguinte, ele percorre a mesma ficha na mesma ordem e entrega a cada chamada o que estava guardado naquela posição.

Repare no que não entra na conta: o nome da variável, o nome da função, o valor que está dentro. Só a posição. É por isso que const [a, setA] = useState(0) e const [b, setB] = useState(0) são indistinguíveis para o React — os dois são “o primeiro hook deste componente”.

hook
Cada chamada de uma função que começa com use: useState, useEffect, useContext, useId, e os seus.
ordem das chamadas
A sequência em que os hooks aparecem no corpo do componente. É a identidade de cada um: posição 1, posição 2, e assim por diante.
desenho
Cada execução do corpo do componente. O React espera a mesma sequência de hooks em todos os desenhos.
condição
Um if, um ?, um && que muda quantos hooks rodam. É a fonte número um de erro de ordem.
return antecipado
Um return antes de algum hook. No desenho em que ele acontece, os hooks de baixo não rodam.
laço
map, for, while. Se a lista muda de tamanho, o número de hooks muda junto.

Duas regras resumem tudo, e as duas são sobre a mesma coisa: a sequência tem de ser previsível. A primeira: chame hooks somente no corpo de um componente ou de um hook próprio. A segunda: chame sempre na mesma ordem, sem condição, sem laço e sem return no meio. As três caixas desta aula quebram uma regra de cada vez, de propósito, para você ver o estrago.

3. Regra 1: só em componente ou em hook próprio

Hook só funciona durante o desenho de um componente. Fora disso — no topo do arquivo, dentro de um onClick, de um setTimeout, de uma função auxiliar chamada na hora errada —, não há ficha aberta para anotar nada, e a chamada falha. A caixa mostra o caso mais comum de todos: o estado escrito acima do componente, porque parece que “fica mais organizado assim”.

O useState está no topo do arquivo, fora do componente, e a caixa nem desenha. Mova o estado para dentro do App e faça o botão alternar entre R$ e €.

const [moeda, setMoeda] = useState("R$");

function App() {
  return (
    <div>
      <p>Total: {moeda} 12,50</p>
      <button onClick={() => setMoeda(moeda === "R$" ? "€" : "R$")}>
        Trocar moeda
      </button>
    </div>
  );
}
Erro: Cannot read properties of null (reading 'useState')

O painel inicial mostra o erro, e é bom olhar para ele com calma porque a mensagem não fala de hook fora de componente. Ela fala de null:

Erro: Cannot read properties of null (reading 'useState')

A explicação: o useState que existe dentro do React olha para uma variável interna que só tem valor durante o desenho de um componente. Fora do desenho, essa variável é null, e ler useState de null dá exatamente esse erro. Em um projeto rodando em modo de desenvolvimento, a mensagem é mais amigável e fala o nome do problema:

Uncaught Error: Invalid hook call. Hooks can only be called inside of the body of a function component.

As duas querem dizer a mesma coisa: “aqui não é lugar de hook”. Quando você vir isso no seu projeto, procure a chamada que está fora do corpo de um componente. Os casos que eu já vi: estado no topo do arquivo, useState dentro de um onClick para guardar um resultado, e hook chamado em uma função auxiliar que também é usada fora do desenho.

4. Regra 2: sempre no topo, nunca dentro de condição

Agora o caso da Ana. Ela queria o desconto só quando o cupom existisse, e colocou o useState dentro do if. No primeiro desenho, o cupom é falso, então o hook nem é chamado: a ficha fica com um hook só. No desenho seguinte, o cupom é verdadeiro, o hook é chamado e a ficha precisa de dois. O React percebe a diferença e aborta o desenho.

O useState(10) está dentro do if, e clicar em “Aplicar cupom” derruba o painel. Suba o hook para o topo e use o valor só na hora de montar o texto: {cupom ? desconto : 0}%.

function App() {
  const [cupom, setCupom] = useState(false);
  let desconto = 0;

  if (cupom) {
    const [d] = useState(10);
    desconto = d;
  }

  return (
    <div>
      <button onClick={() => setCupom(true)}>Aplicar cupom</button>
      <p>Desconto: {desconto}%</p>
    </div>
  );
}
<div>

  <p>Desconto: 0 %</p>
</div>

function App() {
  const [cupom, setCupom] = useState(false);
  const [desconto] = useState(10);

  return (
    <div>

      <p>Desconto: {cupom ? desconto : 0}%</p>
    </div>
  );
}

Clique em “Aplicar cupom” com o código original: o painel não muda mais, e o botão fica morto. O React desmontou a árvore porque a lista de hooks mudou de tamanho. Em modo de desenvolvimento, o console diz qual é o problema:

Rendered more hooks than during the previous render.

“Desenhou mais hooks do que no desenho anterior.” O inverso também existe — Rendered fewer hooks than expected, quando um desenho tem menos hooks que o anterior — e aparece no caso do return antecipado, que vem já já. Em ambos, o conserto é o mesmo: todos os hooks no topo, sempre chamados, e a condição decidindo apenas o que aparece na tela.

Existe um jeito de ler isso que ajuda a não errar mais: hook é declaração, não ação. Você declara “este componente tem um estado de cupom e um estado de desconto” no começo, e usa esses valores onde quiser. O if não pode decidir se a declaração existe; ele decide o que ela mostra.

E o mesmo vale para o ? e para o &&: cupom && useState(10) é o mesmo erro escrito em uma linha. Também vale para try/catch e para qualquer bloco que possa não rodar.

5. Regra 3: nada de laço — extraia um componente

O terceiro caso é o mais traiçoeiro, porque funciona enquanto a lista tem o mesmo tamanho. A Ana queria que cada pão pudesse ser curtido, e guardou o estado de cada um dentro do map. Com um pão, uma ficha com dois hooks. Ela adiciona o segundo pão, o map roda duas vezes, e a ficha passa a precisar de três hooks. O React reclama e a tela desaparece.

O useState está dentro do map: ao adicionar o segundo pão, o painel apaga. Crie um componente Item que recebe nome e guarda o próprio “curtido”, e use <Item key={item} nome={item} /> no mapa.

function App() {
  const [itens, setItens] = useState(["Pão"]);

  return (
    <div>
      <button onClick={() => setItens([...itens, "Pão " + (itens.length + 1)])}>
        Adicionar
      </button>
      {itens.map((item) => {
        const [curtido, setCurtido] = useState(false);
        return (
          <p key={item}>
            {item}{" "}
            <button onClick={() => setCurtido(true)}>
              {curtido ? "curtido" : "curtir"}
            </button>
          </p>
        );
      })}
    </div>
  );
}
<div>

      </button>

        <Item key={item} nome={item} />
      ))}
    </div>
  );
}

Depois do conserto, adicione dois pães e o painel mostra três parágrafos. Cada Item tem a sua própria ficha, com um hook só, e a lista pode crescer à vontade. Repare que o estado não mudou de lugar por acaso: ele passou a pertencer a um componente, que é onde o React sabe guardá-lo. Extrair o componente não é estilo — é a única forma de dar estado a cada item.

Se o estado não é por item, e sim da lista, a resposta é outra: guarde o conjunto no componente de cima, como um objeto ou um array de ids curtidos, e passe para o item o que ele precisa saber e a função que ele chama. A regra é a mesma nos dois caminhos: o hook fica no corpo de um componente, nunca dentro do map.

6. O return antecipado e o “carregando”

Existe uma variação do caso do if que pega gente experiente: o return antecipado. É comum escrever o estado de carregamento no topo e, logo abaixo, um if (!dados) return <p>Carregando…</p> antes de declarar o resto dos hooks. No primeiro desenho, metade dos hooks roda. Quando os dados chegam, a outra metade aparece — e a ficha não fecha.

function Pedidos() {
  const [dados, setDados] = useState(null);
  const [filtro, setFiltro] = useState("");

  if (!dados) {
    return <p>Carregando…</p>;
  }

  const ordenados = useMemo(() => ordenar(dados, filtro), [dados, filtro]);
  ...
}

O useMemo da linha 8 é o problema: ele só existe depois que os dados chegam. O conserto é mover o return para baixo de todos os hooks — ou seja, declarar tudo primeiro e decidir o que desenhar por último:

function Pedidos() {
  const [dados, setDados] = useState(null);
  const [filtro, setFiltro] = useState("");
  const ordenados = useMemo(() => ordenar(dados, filtro), [dados, filtro]);

  if (!dados) {
    return <p>Carregando…</p>;
  }

  return <Lista itens={ordenados} />;
}

Nessa versão o useMemo recebe dados nulo e devolve uma lista vazia no primeiro desenho — nada quebra, e a ficha fica sempre com o mesmo número de hooks. É a mesma ideia da caixa anterior aplicada a um return: a ordem das linhas de hook não pode depender de nada.

Quando o componente fica grande demais com essa ginástica, a saída é dividir: um componente Carregando e um Lista, e o pai decide qual dos dois desenhar. A condição continua existindo — só não fica mais no meio da lista de hooks.

7. Como sair de cada aperto

Quase todo desejo legítimo tem um jeito certo que não envolve hook condicional. Esta tabela é a que eu consulto quando esqueço:

O que você querO jeito que quebraO jeito certo
só ter estado quando o cupom existeif (cupom) { useState(10) }declarar o estado sempre e usar condicionalmente no JSX
estado por item de listaitens.map(() => useState())extrair <Item />, cada um com o seu hook

efeito só quando a aba está abertaif (aberta) { useEffect(...) }useEffect sempre, com a checagem dentro
lógica igual em dois componentescopiar o useState e ajustarum hook próprio, chamado no topo dos dois

As duas últimas linhas merecem um comentário. No caso do efeito, a checagem vai dentro da função do efeito: o hook é declarado sempre, e quem decide se faz algo é o corpo dele. No caso do hook próprio, a regra viaja junto: se o seu useContador é chamado dentro de um if, o problema continua sendo seu, e o React aponta o componente que chamou.

Há ainda um vício de quem vem de outras linguagens: querer chamar useState dentro de um manipulador de evento para “guardar o resultado do clique”. Em React, estado é declarado no corpo; o manipulador só chama a função de troca. Se você se pegar escrevendo useState dentro de um onClick, pare: o valor precisa existir antes do clique.

8. O ESLint e as mensagens que você vai ver

O React não consegue impedir uma chamada condicional em tempo de compilação, mas o ESLint consegue — e é ele que segura a maior parte dos erros antes de você rodar a página. O plugin eslint-plugin-react-hooks vem configurado nos projetos criados com Vite e Next.js e cobra as duas regras. Quando ele reclama, a mensagem costuma apontar a linha exata.

MensagemO que significaOnde procurar
React Hook "useState" is called conditionallyo hook está dentro de um if ou de um ?suba a chamada para o topo
React Hook "useEffect" is called in function ... that is neither a React function component nor a custom React Hooko hook está em uma função comummova para o componente ou renomeie para use...
React Hook "useState" cannot be called inside a callbacko hook está em map, onClick ou setTimeoutextraia um componente
React Hook useEffect has a missing dependencyo efeito usa um valor que não está na lista de dependênciasveja As Dependências

As três primeiras linhas são as regras desta aula. A quarta é outro assunto — dependências de efeito — e aparece aqui só para você não confundir: ela não é erro de ordem, é aviso de que o efeito pode estar lendo um valor desatualizado. O aviso não impede a página de rodar; o erro de ordem impede.

Uma diferença prática entre os dois mundos: o ESLint reclama antes de rodar e explica; o React reclama durante o desenho e derruba a árvore. Se a sua página ficou em branco depois de um clique, desconfie da ordem dos hooks antes de desconfiar do CSS. E se o painel das caixas parar de responder, é o mesmo sintoma: o React abortou o desenho e o HTML antigo ficou na tela.

9. Cenários do dia a dia

Cenário 1: o cupom que só existia às vezes

A Ana tinha um useState dentro do if (cupom). A tela inicial funcionava porque o cupom começava falso e o hook não rodava; ao aplicar o cupom, o React viu um hook a mais e desmontou o painel. Subir o hook para o topo e usar cupom ? desconto : 0 no texto resolveu. O estado passou a existir desde o primeiro desenho, o que é exatamente o que o React espera.

Cenário 2: o “curtir” que morava no map

Ela queria marcar cada pão como curtido e guardou o estado dentro do map. Com um pão, tudo bem; com dois, a lista desapareceu. O conserto foi extrair Item, com o useState dentro dele. A lista passou a poder crescer sem limite, e o estado de cada pão ficou onde devia: na ficha daquele item.

Cenário 3: o carregando no lugar errado

No painel de pedidos, o return <p>Carregando…</p> estava antes de um useMemo. Enquanto os dados não chegavam, o componente tinha três hooks; quando chegavam, tinha quatro. A página quebrava no momento em que os dados apareciam — o pior momento possível para depurar. Mover o return para baixo de todos os hooks resolveu, e o componente ficou até mais fácil de ler.

11. Resumo

O React identifica cada hook pela posição na sequência de chamadas do componente. Essa é a decisão que explica todas as regras: a mesma quantidade de hooks, na mesma ordem, em todo desenho. Hook fora de componente não tem ficha onde anotar; hook dentro de if aparece em alguns desenhos e não em outros; hook dentro de map multiplica quando a lista cresce; return antes de um hook corta a sequência pela metade.

Os três consertos são sempre os mesmos: subir a chamada para o topo, mover o return para depois de todos os hooks e extrair um componente quando o estado precisa ser por item. Nenhum deles exige truque, e todos deixam o código mais fácil de ler — o que é um bom sinal de que a regra não é arbitrária.

O ESLint avisa antes de rodar e o React derruba a árvore durante o desenho. Se a página ficar em branco depois de um clique, ou se o painel das caixas congelar, a ordem dos hooks é a primeira suspeita. E lembre que a regra vale também dentro dos seus hooks próprios: eles não são um lugar onde a regra deixa de valer.

Para lembrar

  • Hooks são identificados por posição, não por nome.
  • Mesma quantidade e mesma ordem em todos os desenhos do componente.
  • Hook só no corpo de um componente ou de um hook próprio.
  • Nada de if, ?, &&, try ou laço em volta de um hook.
  • return antecipado só depois de todos os hooks.
  • Estado por item: extraia um componente e ponha o hook dentro dele.
  • Estado que aparece e some não existe: declare sempre e decida no JSX.
  • O ESLint cobra as regras antes de a página rodar; o React derruba a árvore se elas forem quebradas.
  • O erro de null na leitura de useState quer dizer “hook fora do desenho”.
  • A regra vale dentro dos seus hooks próprios também.
