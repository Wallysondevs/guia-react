Hooks

Hooks são as funções que dão ao componente acesso ao que o React guarda: estado, efeitos, referências, contexto, memória de cálculo. Todos começam com use e todos obedecem às mesmas duas regras de posição. Esta página é a consulta rápida: a lista completa com a função de cada um, as regras que o ESLint cobra, os pares que se confundem e onde está a aula de cada hook. A Ana já usou useState, useEffect e useRef no painel da padaria; aqui está o mapa do resto.

  • As seções seguintes agrupam os hooks por assunto, com o critério de escolha de cada grupo.

1. O que é um hook e a lista completa

Hook é uma função do React que dá a um componente um recurso que ele não teria sozinho. O useState dá memória entre renders; o useEffect dá um lugar para sincronizar com fora; o useRef dá uma caixa que sobrevive sem redesenhar. Todos começam com use — e esse prefixo não é decoração: é como o ESLint e o próprio React reconhecem que ali existe um hook.

function Painel() {
  const [pedidos, setPedidos] = useState([]);      // estado
  const [erro, setErro] = useState("");            // estado
  const campoBusca = useRef(null);                 // referência

  useEffect(() => {                                // efeito
    console.log("montou o painel");
    return () => console.log("saiu da tela");
  }, []);

  return <div ref={campoBusca}>{erro}</div>;
}

O React não guarda "o estado do primeiro useState" pelo nome: ele guarda pela ordem das chamadas. A primeira chamada de hook do componente ocupa o primeiro espaço, a segunda ocupa o segundo, e assim por diante. É por isso que a ordem não pode mudar entre um render e outro — o assunto da próxima seção e a causa dos erros mais confusos do React.

Fora dessa lista, mas no mesmo assunto, ficam três nomes que não são hooks: createContext cria o contexto, memo embrulha o componente e Fragment agrupa irmãos. Saber a diferença evita a pergunta "posso chamar memo dentro de um if?" — memo não é hook, mas também não é chamado dentro de componente: ele embrulha a função na hora de declarar.

2. As regras dos hooks

São duas, e as duas existem por causa da ordem. Primeira: chame hooks só no topo do componente ou de outro hook, nunca dentro de if, for, while ou função interna. Segunda: chame sempre na mesma ordem em todo render — nada de hook condicional. O React depende da ordem para saber qual estado pertence a qual chamada.

function Painel({ logado }) {
  if (logado) {
    const [nome, setNome] = useState("Ana");   // erro: hook condicional
  }

  useEffect(() => { ... }, []);                 // fora do if, mas depois
  return <p>oi</p>;
}

No editor, o ESLint avisa antes de rodar; no navegador, o React reclama no console durante o desenvolvimento e, em produção, quebra quando a contagem de hooks muda entre renders. As duas mensagens abaixo são as que você vai encontrar.

React Hook "useState" is called conditionally. React Hooks must be called in the exact same order in every component render.

A segunda aparece em produção, quando o número de hooks muda de um render para outro:

Para sair de cada aperto: se o hook está dentro de um if, mova a condição para dentro do hook (useEffect(() => { if (!logado) return; ... })) ou extraia um componente para o caso condicional. Se o componente tem um return antecipado, coloque todos os hooks antes dele. Se o hook está dentro de um map, extraia o item para um componente — o item é que pode ter hooks.

3. Estado: useState e useReducer

Os dois guardam valores entre renders. O useState é o padrão: um valor, um setter, uma linha. O useReducer entra quando o estado tem regras — vários campos que mudam juntos ou uma transição que depende da situação anterior.

Com useState, atualize com a forma de função quando a conta depende do valor atual: setTotal((t) => t + 1). Com objeto ou array, substitua em vez de mutar. Com useReducer, o componente recebe dispatch e manda ações nomeadas; quem decide o que cada ação faz é uma função pura, fora do componente.

function reducer(estado, acao) {
  if (acao.type === "pagar") {
    return { ...estado, pago: true, status: "pago" };
  }
  return estado;
}

function Pedido() {
  const [pedido, dispatch] = useReducer(reducer, {
    pago: false,
    status: "novo",
  });

  return (
    <button onClick={() => dispatch({ type: "pagar" })}>
      Pagar
    </button>
  );
}

O clique muda só o status e esquece o pagamento. Troque os dois useState por um useReducer com a ação pagar, que devolve { pago: true, status: "pago" }.

function App() {
  const [pago, setPago] = useState(false);
  const [status, setStatus] = useState("novo");

  function pagar() {
    setStatus("pago");
  }

  return (
    <div>
      <p>pago: {pago ? "sim" : "não"} - status: {status}</p>
      <button id="pagar" onClick={pagar}>Pagar</button>
    </div>
  );
}

No código inicial, o clique deixa "pago: não - status: pago": dois estados, uma transição pela metade. Na solução, a ação muda os dois campos de uma vez, porque quem decide é o reducer. O critério é sempre o mesmo: um valor simples, useState; um conjunto que precisa concordar, useReducer.

4. Efeitos: useEffect e useLayoutEffect

Efeito é para sincronizar o componente com algo fora do React: rede, timer, listener, título da aba, localStorage. O useEffect roda depois da pintura; o useLayoutEffect roda depois do DOM e antes da pintura, para medir ou ajustar algo sem a tela piscar. Na dúvida, use useEffect; o useLayoutEffect é para medição.

useEffect(() => {
  const id = setInterval(() => setHora(new Date()), 1000);
  return () => clearInterval(id);       // cleanup
}, []);                                  // uma vez, na montagem

O array de dependências define quando o efeito roda: [] na montagem, [busca] quando a busca muda, sem array em todo render. A função de retorno é o cleanup: ela limpa o que o efeito criou, e roda antes da próxima execução e quando o componente sai da tela. Sem ela, timers e listeners se acumulam.

Efeito não é lugar de calcular. Total, lista filtrada e mensagem de erro se calculam no render; efeito que só copia estado para estado é código que pode sair. A pergunta que resolve: "isso precisa acontecer depois que a tela apareceu?". Se a resposta for não, não é efeito.

Buscar dados merece um cuidado: a resposta pode chegar depois que a busca mudou. Guarde uma flag ou use AbortController para descartar a resposta velha, e trate os três estados — carregando, dados e erro. A aula de buscando dados mostra o padrão completo.

5. Referências: useRef e useImperativeHandle

useRef cria uma caixa com .current que dura entre renders e não provoca redesenho. Serve para falar com o DOM (campo.current.focus()) e para guardar o que é bastidor: id de timer, "já enviei", valor anterior. Não serve para o que a tela mostra — se o valor aparece no JSX, ele é estado.

useImperativeHandle entra quando o componente quer expor só alguns métodos para o pai em vez do elemento inteiro. Em vez de o pai receber o input e poder fazer qualquer coisa, recebe um objeto com focus() e limpar(). É uma API imperativa de propósito, para casos como foco, rolagem e animação — não para passar dados.

const Campo = ({ ref }) => {
  const interno = useRef(null);

  useImperativeHandle(ref, () => ({
    focus: () => interno.current.focus(),
    limpar: () => {
      interno.current.value = "";
    },
  }));

  return <input ref={interno} />;
};

No React 19, ref chega como uma prop comum em componente de função — não é preciso forwardRef. O useImperativeHandle continua valendo para escolher o que essa ref entrega. Se você só precisa focar um campo do próprio componente, useRef basta.

6. Memória: useMemo, useCallback e memo

Os dois hooks guardam trabalho entre renders. useMemo guarda o resultado de um cálculo; useCallback guarda a função. O terceiro nome, memo, não é hook: embrulha o componente para ele não redesenhar quando as props não mudam.

const itens = useMemo(
  () => PAES.filter((p) => p.tipo === filtro),
  [filtro]
);

const salvar = useCallback((id) => {
  setPedidos((lista) => [...lista, id]);
}, []);

const Linha = memo(function Linha({ pao, aoSalvar }) { ... });

A regra prática: só memoize quando a conta é caro ou quando a identidade atravessa uma fronteira — prop de filho com memo ou dependência de efeito. Em cálculo barato, o custo do hook é maior que a economia, e o código fica mais difícil de ler. Com useCallback, o cuidado extra é o valor capturado: a função guardada enxerga os valores do render em que nasceu, então as dependências precisam estar completas.

O React 19 traz o compilador, que memoiza automaticamente muitos casos. Isso não aposenta os hooks: eles continuam sendo a forma explícita de dizer "reaproveite", e aparecem em todo código escrito à mão. O que muda é a expectativa — você não precisa memoizar por precaução.

7. Contexto e identidade: useContext e useId

createContext cria o canal; useContext lê o valor mais próximo na árvore. É o jeito de evitar passar a mesma prop por cinco níveis: tema, idioma, usuário logado, carrinho. O valor do provider muda, e todos os componentes que leem aquele contexto redesenham — por isso o contexto é para dado estável e amplo, não para tudo.

O Endereco tem o nome da loja escrito à mão, mas o valor certo está no provider. Leia com useContext(Loja) em vez de usar a string fixa.

const Loja = createContext("padaria");

function Endereco() {
  const nome = "padaria";
  return <p>loja: {nome}</p>;
}

function App() {
  return (
    <Loja.Provider value="padaria da Ana">
      <Endereco />
    </Loja.Provider>
  );
}
<p>loja: padaria</p>

const Loja = createContext("padaria");

function Endereco() {
  const nome = useContext(Loja);
  return <p>loja: {nome}</p>;
}

function App() {
  return (
    <Loja.Provider value="padaria da Ana">
      <Endereco />
    </Loja.Provider>
  );
}

No inicial, o filho ignora o provider e mostra o valor padrão. Na solução, ele lê o valor mais próximo e acompanha qualquer troca. Repare que o componente do meio não precisou existir: o contexto é para distância, e a prop continua sendo melhor para um nível.

useId gera um identificador único e estável, útil para ligar label e campo quando há vários formulários iguais na página. Ele serve para atributos de acessibilidade, não para key de lista — a key vem do dado. O formato do id é opaco de propósito: use como string, sem tentar interpretar.

Um detalhe do contexto que evita erro silencioso: createContext(valorPadrão) define o que o useContext devolve quando não há provider acima. Esse padrão serve para o componente funcionar sozinho em teste; em produção, se ele aparecer na tela, falta o provider em algum lugar. Se o padrão for undefined, o componente quebra ao acessar um campo — o que é melhor do que mostrar um valor errado sem avisar.

8. Concorrência e hooks próprios

useTransition e useDeferredValue tratam de trabalho pesado sem travar a digitação. O primeiro envolve uma atualização e devolve isPending, para você mostrar que algo está em andamento; o segundo entrega uma versão atrasada do valor, para a lista grande acompanhar a busca com um passo de atraso em vez de a cada tecla. Nenhum dos dois substitui useMemo: eles mudam a prioridade do trabalho, não a quantidade.

const [texto, setTexto] = useState("");
const [isPending, startTransition] = useTransition();

function mudou(e) {
  setTexto(e.target.value);                       // urgente: o campo
  startTransition(() => setFiltro(e.target.value)); // não urgente: a lista
}

Hooks próprios são funções useAlgo que juntam hooks e lógica para reaproveitar. Um usePedido() pode guardar carregando, dados e erro e devolver os três; um useLocalStorage(chave) pode ler, gravar e sincronizar. As regras são as mesmas de um hook do React: topo do hook, ordem estável, nome com use. O que muda é o dono.

Existem hooks do React 19 que ainda não têm aula neste guia, mas aparecem em código por aí: useActionState, useOptimistic, useSyncExternalStore e useDebugValue. Nas caixas do guia, eles não estão no escopo direto — use o prefixo React (React.useOptimistic) se precisar experimentar. São assuntos de formulário com actions e de estado otimista, cobertos nas aulas de formulários com actions e atualização otimista.

Resumo

Hooks dão recursos ao componente e são reconhecidos pela ordem das chamadas. Por isso valem as duas regras: só no topo do componente ou de um hook próprio, e sempre na mesma ordem — nada de hook dentro de if, laço ou função interna. O ESLint avisa no editor; o React quebra em produção quando a contagem muda.

Para estado, useState e, quando há regras, useReducer. Para sincronizar, useEffect e, quando precisa medir antes da pintura, useLayoutEffect. Para falar com o DOM ou guardar bastidor, useRef; para expor uma API pequena ao pai, useImperativeHandle. Para economizar trabalho, useMemo e useCallback, com memo no filho. Para distância, useContext; para ids acessíveis, useId; para não travar a digitação, useTransition e useDeferredValue.

Na dúvida, escolha o hook mais simples que resolve o problema e só troque quando a dor aparecer: estado demais vira reducer, efeito demais vira conta no render, memoização demais vira ruído. Hooks próprios existem para juntar o que se repete — e são a melhor forma de esconder complexidade sem esconder comportamento.

Para lembrar

  • Hook começa com use e só roda no topo do componente ou de outro hook.
  • A ordem das chamadas é a identidade do estado: nunca mude entre renders.
  • useState para valor simples; useReducer para transições.
  • useEffect para fora do React; useLayoutEffect para medir.
  • Cleanup no retorno do efeito: timer, listener e requisição.
  • useRef para DOM e bastidor; não para o que aparece na tela.
  • useMemo guarda valor; useCallback guarda função; memo guarda o desenho.
  • useContext para distância; prop para um nível.
  • useId para acessibilidade, não para key.
  • A mensagem "Rendered more hooks" é ordem de hooks, não estado errado.
