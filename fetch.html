O fetch

A Ana ficou surpresa ao descobrir que o fetch não devolve os pães: devolve uma espécie de senha de balcão. Ela pede, recebe um papel dizendo "seu pedido está sendo preparado" e só depois de um tempo chega a bandeja — e a bandeja ainda vem embrulhada, com a etiqueta da entrega por fora. Nesta aula ela vai abrir esse embrulho: entender o que a função devolve, o que vem dentro da resposta, por que um 404 não é o mesmo que ficar sem internet, e por que tentar ler o corpo duas vezes dá erro.

Você vai aprender
  • O que o fetch devolve e o que ele não devolve.
  • O objeto Response: ok, status, headers.
  • Por que o corpo exige um segundo passo, com json().
  • Erro de rede x resposta 404: quem rejeita e quem não rejeita.
  • O corpo se lê uma vez só, e o que fazer com isso.
  • A URL: caminho relativo, domínio e parâmetros de busca.

1. A cena: a senha do balcão

Na padaria, quando o pedido é grande, a Ana não entrega na hora: dá uma senha e chama quando estiver pronto. O fetch funciona assim. Você chama, ele responde imediatamente com uma promessa — "vou te avisar quando tiver notícia" — e segue a vida. Quem precisa do resultado espera essa promessa se cumprir.

Só que a notícia que chega primeiro não é o pão: é a confirmação de que o servidor respondeu. Vem com número de status, cabeçalhos e a promessa do corpo. O pão de verdade, a lista de produtos, o preço — isso é o corpo, e ele chega num segundo momento, que você precisa pedir explicitamente. Duas etapas, dois await. Quem entende isso para de brigar com o fetch.

A aula de Buscando Dados já mostrou o desenho completo: estado, efeito e .then. Aqui o assunto é a ferramenta em si — o que ela entrega em cada etapa e como não se enganar com o que parece ter dado certo.

2. O que a função devolve

fetch recebe uma URL e, opcionalmente, um objeto de opções. Devolve sempre uma Promise. Não devolve lista, não devolve texto, não devolve objeto com os dados: devolve a promessa de uma resposta.

const resposta = await fetch("https://loja.test/api/paes");

Se você não usar await, o que fica na variável é a promessa, e não a resposta. É o erro número um de quem começa: const resposta = fetch(url), seguido de uma tela que mostra undefined ou quebra ao tentar ler uma propriedade. A promessa é um objeto que representa "vai chegar"; ela não tem status nem json().

A URL pode ser absoluta ou relativa. Absoluta, como https://loja.test/api/paes, aponta para outro servidor e está sujeita a CORS — o navegador só entrega a resposta se aquele servidor autorizar o seu site. Relativa, como /api/paes, aponta para o mesmo servidor que serviu a página, e é o caso mais comum em projeto real: o front e a API no mesmo domínio.

pedido
A chamada fetch(url). Sai na hora e volta na hora, com uma promessa na mão.
Promise
O objeto que representa "ainda vai chegar". Não tem dados dentro; tem a promessa de um resultado.
Response
O que chega quando a promessa se cumpre: status, cabeçalhos e o direito de ler o corpo.
corpo
O conteúdo de verdade, que viaja em pedaços e é lido uma única vez, com json() ou text().
ok
Atalho booleano para "o status está entre 200 e 299". É ele que separa sucesso de resposta de erro.
JSON
O formato de texto que vira objeto quando lido: { "titulo": "Pão de queijo" }.

3. A resposta não é o dado

Quando a promessa se cumpre, você recebe um objeto Response. Ele descreve a entrega: status, cabeçalhos, endereço final. O conteúdo — a lista de pães, o preço, a mensagem de erro — está no corpo, e o corpo é um fluxo de bytes que precisa ser lido. No caso mais comum, lido e convertido de JSON para objeto com json().

Na caixa abaixo, o pedido é feito do jeito certo, mas o código procura o título dentro da resposta. O resultado é uma linha com "Produto:" e nada depois. A missão é abrir o embrulho.

O título não está na resposta: está no corpo. Use resposta.json() e leia o campo titulo do objeto que ela devolve.

function buscarPao() {
  return new Promise((ok) => {
    setTimeout(() => {
      ok({
        ok: true,
        status: 200,
        json: () => Promise.resolve({ titulo: "Pão de queijo", preco: 6 })
      });
    }, 10);
  });
}

function App() {
  const [titulo, setTitulo] = useState("(nada)");

  useEffect(() => {
    buscarPao().then((resposta) => {
      setTitulo(resposta.titulo);
    });
  }, []);

  return (
    <div>
      <h1>Padaria da Ana</h1>
      <p>Produto: {titulo}</p>
    </div>
  );
}

Repare que a resposta nem tem campo titulo: ela tem ok, status e json. Procurar dado dentro da resposta é procurar pão dentro da senha. O dado vem do json(), que também é assíncrono — por isso o segundo .then, e por isso dois await quando se usa await.

O json() faz duas coisas de uma vez: lê todos os bytes do corpo e transforma o texto em objeto JavaScript. Se o corpo não for JSON, ele não devolve texto: ele rejeita com SyntaxError. É um erro diferente dos outros, e vale reconhecer pelo nome.

4. O que vem na resposta

O objeto Response tem poucos campos e todos úteis. Esta é a tabela para consultar quando bater dúvida sobre o que dá para perguntar antes de ler o corpo.

CampoExemploPara que serve
oktrue ou falsedizer se o status está entre 200 e 299, sem decorar números
status200, 404, 500mostrar o código e tratar casos específicos
statusText"Not Found"texto do servidor; bom para log, ruim para a tela
headers.get()"application/json"conferir o tipo antes de escolher como ler
json(){ titulo: "Pão" }ler o corpo como JSON, em uma Promise
text()"<p>Oi</p>"ler o corpo cru, quando não é JSON
urlo endereço finaldescobrir se houve redirecionamento

Dois detalhes de quem já apanhou. Primeiro: headers não é um objeto comum — é um Headers, e se lê com .get("content-type"), não com headers["content-type"]. Segundo: status é número, então comparar com "200" entre aspas nunca dá certo. O hábito saudável é usar ok para decidir e guardar status só para exibir ou registrar.

5. Erro de rede x resposta de erro

Aqui está a confusão que faz mais gente perder uma tarde. O fetch só considera fracasso quando o pedido não chegou a lugar nenhum: sem internet, domínio que não existe, servidor fora do ar, CORS bloqueado. Nesses casos, a promessa é rejeitada e o .catch roda.

Se o servidor respondeu — mesmo respondendo "não encontrado" ou "erro interno" —, o fetch considera sucesso: a promessa se cumpre e o .then roda normalmente. Um 404 não cai no .catch. Quem decide se a resposta serve é você, olhando ok.

O servidor respondeu 404 com a mensagem no corpo. O código lê o corpo e mostra dados.titulo, que não existe nesse caso. Confira resposta.ok e mostre dados.erro quando a resposta não for boa.

function buscarPao(nome) {
  return new Promise((ok) => {
    setTimeout(() => {
      if (nome === "brioche") {
        ok({
          ok: false,
          status: 404,
          json: () => Promise.resolve({ erro: "Pão não encontrado" })
        });
      } else {
        ok({
          ok: true,
          status: 200,
          json: () => Promise.resolve({ titulo: "Pão de queijo" })
        });
      }
    }, 10);
  });
}

function App() {
  const [mensagem, setMensagem] = useState("Buscando...");

  useEffect(() => {
    buscarPao("brioche")
      .then((resposta) => resposta.json())
      .then((dados) => setMensagem(dados.titulo));
  }, []);

  return (
    <div>
      <h1>Busca</h1>
      <p>{mensagem}</p>
    </div>
  );
}

A API de resposta de erro é comum e é uma boa notícia: mesmo quando o status é 404 ou 400, o servidor costuma mandar um corpo explicando o motivo. Ler esse corpo é o que permite dizer "Pão não encontrado" em vez de um genérico "deu erro". O ok decide o caminho; o corpo dá o texto.

Quando a resposta é boa, ok é true e o corpo tem os dados. Quando é ruim, ok é false e o corpo tem a explicação. Nos dois casos o json() funciona — o que muda é o campo que você vai usar. E, em ambos, o .catch continua reservado para o que nem chegou.

Vale reparar na primeira e na terceira linha: o mesmo .catch que pega "sem internet" não pega "404". São caminhos diferentes, e tratar os dois como se fossem um só é o que produz telas dizendo "verifique sua conexão" quando o problema era o nome do pão no endereço.

6. O corpo se lê uma vez só

O corpo de uma resposta é um fluxo: sai do servidor em pedaços e é consumido enquanto é lido. Por isso ele só pode ser lido uma vez. Chamar json() duas vezes na mesma resposta não devolve os dados de novo: a segunda chamada rejeita com TypeError, dizendo que o fluxo já foi lido.

O código lê o corpo duas vezes: uma para a loja e outra para os itens. Leia uma vez só, guarde o resultado numa variável e mostre as duas informações.

function buscarCardapio() {
  return new Promise((ok) => {
    setTimeout(() => {
      let lido = false;
      ok({
        ok: true,
        status: 200,
        json: () => {
          if (lido) {
            return Promise.reject(
              new TypeError("Failed to execute 'json' on 'Response': body stream already read")
            );
          }
          lido = true;
          return Promise.resolve({ loja: "Padaria da Ana", itens: ["pão", "croissant"] });
        }
      });
    }, 10);
  });
}

function App() {
  const [linha, setLinha] = useState("Carregando...");

  useEffect(() => {
    buscarCardapio().then((resposta) => {
      resposta.json().then((dados) => {
        setLinha("Loja: " + dados.loja);
      });
      resposta.json().then((dados) => {
        setLinha("itens: " + dados.itens.length);
      });
    });
  }, []);

  return (
    <div>
      <h1>Cardápio</h1>
      <p>{linha}</p>
    </div>
  );
}

No console do navegador, o sintoma é este:

Uncaught (in promise) TypeError: Failed to execute 'json' on 'Response': body stream already read

A correção é sempre a mesma: ler uma vez, guardar numa variável e usar quantas vezes precisar. Quando o corpo tem várias informações e você quer duas, o caminho é ler o objeto inteiro e depois acessar dados.loja e dados.itens. Não se lê o fluxo duas vezes; lê-se o objeto.

Existe um irmão desse erro, e ele confunde porque fala de JSON: quando o servidor devolve HTML — uma página de erro, por exemplo — e você chama json(), a conversão falha. A mensagem mostra o começo do corpo para você perceber o engano:

Uncaught (in promise) SyntaxError: Unexpected token '<', "<!doctype "... is not valid JSON

A tradução é direta: o corpo começa com <!doctype, então é HTML, não JSON. Nesse caso, vale conferir headers.get("content-type") ou simplesmente usar text() para ver o que veio antes de tentar converter.

7. A URL e os parâmetros de busca

Um fetch de GET carrega os dados na própria URL. O endereço é uma string, e o que vem depois da interrogação são os parâmetros: /api/paes?busca=queijo&limite=10. Cada par é nome=valor, separados por &, e o valor precisa ir codificado — espaço vira %20, acento vira código, & vira %26.

Fazer isso na mão com concatenação funciona até o dia em que a Ana digita "pão & queijo" e a URL se quebra em dois parâmetros. O jeito seguro é o URLSearchParams, que monta a string codificada para você:

const parametros = new URLSearchParams({ busca: "pão & queijo", limite: 10 });
const resposta = await fetch("/api/paes?" + parametros);
// /api/paes?busca=p%C3%A3o+%26+queijo&limite=10

Duas observações práticas. O caminho relativo /api/paes começa com barra e aponta para a raiz do mesmo servidor; sem a barra, o caminho é relativo à página atual, o que gera endereços errados em páginas mais profundas. E a URL que você escreve não é necessariamente a que responde: redirecionamentos podem levar a outro endereço, e o campo url da resposta mostra o endereço final.

8. O segundo argumento e o que vem depois

Até aqui, todos os pedidos foram GET. O segundo argumento do fetch é um objeto de opções, e é ele que muda o método, manda cabeçalhos e carrega o corpo:

const resposta = await fetch("https://loja.test/api/pedidos", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ pao: "brioche", quantidade: 2 })
});

São três peças que andam juntas: o método, o cabeçalho avisando que o corpo é JSON e o corpo de verdade, sempre como texto — JSON.stringify. Mandar objeto sem transformar em texto faz o servidor receber "[object Object]" e recusar. POST tem a sua própria aula mais adiante, com o que a API responde e como tratar erro de validação.

Duas opções úteis que não envolvem método: signal, que permite cancelar o pedido (duas aulas à frente), e credentials, que decide se os cookies vão junto. Em projeto com login, sem credentials: "include" o servidor não reconhece quem está pedindo. E vale saber que o fetch não tem timeout: se o servidor demorar para sempre, o pedido fica pendurado. Quem resolve isso é o AbortSignal.timeout, também na aula de cancelamento.

9. Cenários do dia a dia

Cenário 1: a lista que veio como objeto estranho

A Ana guardou a resposta no estado e a tela virou um texto sem sentido, cheio de campos internos. Foi o esquecimento do json(): o que estava guardado era o objeto Response, não a lista. O conserto é o segundo passo — resposta.json() — e a lição é que guardar a resposta inteira no estado é sempre sinal de que faltou abrir o embrulho.

Cenário 2: o catch que nunca roda

Ela escreveu um .catch para tratar "pão não encontrado" e o catch nunca era chamado. O servidor respondia 404, e 404 é resposta, não falha de rede: a promessa se cumpre e o .then roda. A correção foi olhar resposta.ok e tratar o caso dentro do próprio fluxo. O .catch ficou para o que ele faz de verdade — internet fora, domínio errado, pedido cancelado.

Cenário 3: a página de erro do servidor dentro do json()

Em produção, o pedido a uma rota errada devolveu a página HTML de erro, e o json() estourou com SyntaxError. O código tratava o erro como se o servidor tivesse caído, mas o servidor estava lá, respondendo 404 em HTML. O hábito que resolve: conferir resposta.status antes de converter e, quando o content-type não for JSON, ler com text() para ver o que realmente veio.

11. Resumo

fetch(url) devolve uma Promise que se cumpre com um objeto Response. Esse objeto descreve a entrega — ok, status, headers — e o conteúdo está no corpo, que precisa ser lido com json() (ou text()), num segundo passo assíncrono. Dois passos, dois await: sem o segundo, o que fica na variável é a resposta, não o dado.

O fetch só rejeita quando o pedido não chega a lugar nenhum: rede, DNS, CORS. Resposta 404 ou 500 é sucesso do ponto de vista dele, e quem separa o joio do trigo é resposta.ok. Corpo que não é JSON faz o json() rejeitar com SyntaxError — nesse caso, ler com text() mostra o que veio de verdade.

E o corpo é um fluxo: lê-se uma vez. Ler duas vezes rejeita com TypeError; ler uma vez, guardar o objeto e usar os campos é o jeito certo. A URL também merece cuidado: parâmetro com espaço ou acento precisa de codificação, e o URLSearchParams faz isso por você.

Na próxima aula, a sintaxe que deixa tudo isso mais legível: async e await, com try, catch e a diferença entre esperar em série e esperar em paralelo.

Para lembrar

  • fetch devolve Promise, não dados.
  • A resposta se chama Response; o dado está no corpo.
  • json() é o segundo passo, e também é assíncrono.
  • ok decide sucesso; status é para exibir.
  • 404 não rejeita; só falha de rede rejeita.
  • O corpo se lê uma vez só: TypeError na segunda.
  • Corpo em HTML no json() dá SyntaxError.
  • Parâmetro de URL vai codificado: use URLSearchParams.
