Polling: perguntar de novo

O painel de encomendas da Ana mostra as encomendas do dia. O problema não é mostrar: é manter atualizado. Quando um cliente faz um pedido pelo celular, o painel que está aberto no balcão não fica sabendo — e a Ana só descobre a encomenda nova porque aperta F5. Ela aperta F5 dez vezes por hora, e já perdeu um pedido de bolo de aniversário assim. Nesta aula o painel passa a se atualizar sozinho, de tempos em tempos, com a técnica mais simples que existe para isso: perguntar de novo.

Você vai aprender
  • O que é polling e por que ele existe, mesmo sendo “menos elegante” que outras técnicas.
  • Por que a função de atualizar fica separada do efeito que a agenda.
  • Como o intervalo depende de um estado — e o que acontece com as dependências.
  • O que fazer quando a resposta antiga chega depois da nova.
  • Como pausar e retomar as atualizações sem deixar intervalo solto.
  • Como escolher o intervalo: custo no servidor contra frescor do dado.
  • Quando polling é a resposta errada.

1. A cena: o F5 dez vezes por hora

O painel de encomendas é um componente que busca a lista e desenha cada pedido. Foi escrito com o que já sabemos: estado para a lista, efeito que busca uma vez, map para desenhar. Funciona — uma vez. Quando a página abre, a foto é daquele instante e não muda mais.

function App() {
  const [encomendas, setEncomendas] = useState([]);

  useEffect(() => {
    buscarEncomendas().then((lista) => setEncomendas(lista));
  }, []);

  return <ul>{encomendas.map((e) => <li key={e.id}>{e.cliente}</li>)}</ul>;
}

A Ana resolveu do jeito que dava: F5. E aí apareceram dois problemas. O primeiro é que apertar F5 perde a posição de rolagem e o que estava digitado. O segundo é que ela esquece — em dia cheio, o painel fica parado meia hora, e o pedido entra por telefone enquanto a tela mostra o quadro de uma hora atrás.

O que a Ana quer é o que todo painel quer: que a tela pergunte de novo sozinha. Isso tem nome — polling, de “sondar”, “consultar repetidamente”. O programa faz a mesma pergunta em intervalos regulares e atualiza a tela com o que voltar. Simples, sem servidor especial, sem biblioteca nova: só a sua busca de sempre, repetida.

2. O que é polling, na prática

A ideia central é que ninguém avisa quando algo muda. O servidor da padaria não tem como cutucar o navegador da Ana dizendo “chegou pedido novo”. Sem esse aviso, resta ao navegador perguntar. Polling é isso: perguntar em intervalos regulares, aceitando o custo de perguntar às vezes sem novidade nenhuma.

O desenho tem três peças e vale conhecê-las pelos nomes. Primeiro, a busca: uma função que pede a lista e guarda no estado. Segundo, o agendamento: um setInterval que chama essa busca de tempos em tempos. Terceiro, a rodada: um contador de quantas vezes já perguntamos — útil para mostrar “atualizado 3 vezes” na tela e para resolver resposta atrasada, como a seção 5 mostra.

polling
Perguntar de novo em intervalos regulares. A tela se atualiza porque pergunta, não porque foi avisada.
intervalo
O tempo entre uma pergunta e a próxima: 5 segundos, 30 segundos, 5 minutos. Quanto menor, mais fresco o dado e maior o custo no servidor.
rodada
O número da pergunta atual. Serve para mostrar na tela e para descartar resposta que chegou fora de ordem.
tique
Cada disparo do intervalo. Um tique, uma busca — é o nome que se usa quando se fala de relógio.
pausar
Parar de agendar temporariamente, sem desmontar o componente. Serve para economizar quando a aba está escondida ou quando a pessoa pausou de propósito.

3. A função que atualiza, separada do efeito

O primeiro passo não tem nada de intervalo: é separar a busca numa função com nome, em vez de deixá-la solta dentro do efeito. Essa função passa a ser a única responsável por “pegar a lista e guardar no estado”. Depois, quem chama essa função pode ser o efeito, um botão, um intervalo — tanto faz.

O botão soma 1 no estado rodada, mas o efeito tem lista de dependências vazia e nunca roda de novo. Faça o efeito depender de rodada para que a busca aconteça a cada clique: o painel tem de mostrar atualizações: 2 e pendências: 3.

function buscarPendencias(rodada) {
  return new Promise((ok) => setTimeout(() => ok(2 + rodada), 0));
}

function App() {
  const [rodada, setRodada] = useState(0);
  const [pendentes, setPendentes] = useState(0);
  const [atualizacoes, setAtualizacoes] = useState(0);

  useEffect(() => {
    buscarPendencias(rodada).then((total) => {
      setPendentes(total);
      setAtualizacoes((n) => n + 1);
    });
  }, []);

  return (
    <div>
      <button id="atualizar" onClick={() => setRodada(rodada + 1)}>atualizar agora</button>
      <p>atualizações: {atualizacoes}</p>
      <p>pendências: {pendentes}</p>
    </div>
  );
}

A diferença entre os dois códigos é um par de colchetes: [] virou [rodada]. Com a lista vazia, o efeito roda uma vez na vida e ignora o resto. Com [rodada], ele roda quando o componente monta e de novo sempre que rodada muda. É o mesmo mecanismo da aula de efeitos, agora com uma consequência que interessa: um botão passa a significar “busque de novo”.

Só que o botão é justamente o que a Ana não quer apertar. O passo seguinte é trocar o dedo dela por um relógio: em vez de esperar o clique, um setInterval incrementa a rodada a cada 30 segundos. O efeito, que já sabe reagir à rodada, busca sozinho. Repare na divisão de trabalho — o relógio muda o estado, o efeito busca. Nenhuma peça faz duas coisas.

4. O intervalo dentro do efeito

O efeito que agenda o intervalo tem três cuidados que já apareceram nas aulas de timers e de limpeza: agendar uma vez, chamar a busca, e desfazer o agendamento quando o componente sai da tela. O código real do painel fica assim:

useEffect(() => {
  const id = setInterval(() => {
    setRodada((r) => r + 1);
  }, 30000);

  return () => clearInterval(id);
}, []);

Três detalhes que parecem pequenos e não são. A lista de dependências é [], porque o intervalo deve ser criado uma vez só — se você colocar rodada ali, cada busca agenda um intervalo novo, e em poucos minutos existem vinte relógios correndo. A atualização usa a forma funcional (r) => r + 1, porque a função do intervalo guarda o valor antigo da rodada. E o return limpa o intervalo, senão ele continua correndo depois que o painel sai da tela.

Uma alternativa comum é fazer o intervalo chamar a busca direto, sem passar por estado: setInterval(atualizar, 30000). Funciona no começo e começa a mentir depois: a função atualizar guardada pelo intervalo é a do primeiro desenho, com o estado daquele momento. Se ela usa pendentes ou qualquer outro valor que mudou, vai ler o valor velho. Passar por um contador de rodada evita esse problema de graça, porque o efeito sempre roda com os valores atuais.

5. A resposta que chega fora de ordem

Aqui está a parte que morde. Com polling, várias buscas ficam em voo ao mesmo tempo. Se a rede está lenta, a resposta da rodada 1 pode chegar depois da resposta da rodada 2 — e, se a tela aceitar tudo que chega, ela termina mostrando um dado mais velho do que o que já tinha. A Ana viu isso como “o número pisca e volta”: o total cai de 12 para 10 sozinho, e depois de trinta segundos sobe de novo.

A defesa é a mesma em qualquer lugar do mundo: numere as perguntas e guarde o número da última resposta aceita. Se chegar uma resposta de rodada menor, ela é velha — descarte, mesmo que tenha chegado agora.

O botão dispara duas buscas ao mesmo tempo; a rodada 1 demora 60 ms e a 2 responde na hora, então a antiga chega por último e sobrescreve a nova. Guarde numa useRef a maior rodada já recebida e ignore as respostas mais antigas: a tela tem de mostrar mostrando a rodada 2.

function buscar(rodada) {
  const atraso = rodada === 1 ? 60 : 0;
  return new Promise((ok) => setTimeout(() => ok({ rodada: rodada, total: 10 + rodada }), atraso));
}

function App() {
  const [mostrando, setMostrando] = useState(0);

  function atualizar() {
    buscar(1).then((r) => setMostrando(r.rodada));
    buscar(2).then((r) => setMostrando(r.rodada));
  }

  return (
    <div>
      <button id="atualizar" onClick={atualizar}>atualizar duas vezes</button>
      <p>mostrando a rodada {mostrando}</p>
    </div>
  );
}

function App() {
  const [mostrando, setMostrando] = useState(0);
  const maiorRodada = useRef(0);

  function receber(resposta) {
    if (resposta.rodada < maiorRodada.current) return;
    maiorRodada.current = resposta.rodada;
    setMostrando(resposta.rodada);
  }

  function atualizar() {
    buscar(1).then(receber);
    buscar(2).then(receber);
  }

  return (
    <div>
      <button id="atualizar" onClick={atualizar}>atualizar duas vezes</button>
      <p>mostrando a rodada {mostrando}</p>
    </div>
  );
}

Por que useRef e não outro estado? Porque a comparação precisa acontecer dentro do callback, que guarda os valores do desenho em que foi criado. Um estado lido ali dentro pode estar velho; a ref não, porque é sempre o mesmo objeto compartilhado. É o mesmo raciocínio do timer, aplicado a dado que chega de fora.

6. Pausar e retomar

Polling de trinta segundos por hora aberta é seis mil perguntas por dia por pessoa. Se a Ana minimiza a aba e vai atender o balcão, essas perguntas continuam. A defesa é pausar: um estado que diz se o polling está ligado, e um efeito que só agenda quando ele está.

O botão “pausar” muda o estado, mas cada tique continua atualizando. Faça o efeito não agendar quando ligado for falso e o tique parar de contar: depois de pausar e simular um tique, a tela tem de mostrar status: pausado e atualizações: 1.

function buscar() {
  return new Promise((ok) => setTimeout(() => ok(10), 0));
}

function App() {
  const [ligado, setLigado] = useState(true);
  const [atualizacoes, setAtualizacoes] = useState(0);

  function tique() {
    buscar().then(() => setAtualizacoes((n) => n + 1));
  }

  useEffect(() => {
    tique();
    const id = setInterval(tique, 5000);
    return () => clearInterval(id);
  }, []);

  return (
    <div>
      <button id="pausar" onClick={() => setLigado(false)}>pausar</button>
      <button id="tique" onClick={tique}>simular um tique</button>
      <p>status: {ligado ? "ligado" : "pausado"}</p>
      <p>atualizações: {atualizacoes}</p>
    </div>
  );
}

function App() {
  const [ligado, setLigado] = useState(true);
  const [atualizacoes, setAtualizacoes] = useState(0);

  function tique() {
    if (!ligado) return;
    buscar().then(() => setAtualizacoes((n) => n + 1));
  }

  useEffect(() => {
    if (!ligado) return;
    tique();
    const id = setInterval(tique, 5000);
    return () => clearInterval(id);
  }, [ligado]);

  return (
    <div>
      <button id="pausar" onClick={() => setLigado(false)}>pausar</button>
      <button id="tique" onClick={tique}>simular um tique</button>
      <p>status: {ligado ? "ligado" : "pausado"}</p>
      <p>atualizações: {atualizacoes}</p>
    </div>
  );
}

Duas guardas, e as duas são necessárias. A do efeito impede que o relógio seja criado quando está pausado — e, como a dependência é ligado, o React roda o cleanup da versão anterior assim que o valor muda, o que limpa o intervalo antigo na hora. A do tique impede que uma chamada que já estava no caminho continue contando. Sem a primeira, o intervalo sobrevive à pausa; sem a segunda, uma busca agendada antes da pausa ainda derruba o estado.

Nas caixas deste guia o intervalo é de 5 segundos, e por isso ele nunca dispara durante o teste — o botão “simular um tique” faz o papel dele na hora. A chamada tique() logo no começo do efeito é a busca do primeiro desenho: sem ela, o painel abriria vazio esperando o primeiro relógio. No painel de verdade, com intervalo de 30 segundos, o efeito é o mesmo: cada tique é uma atualização.

7. De quanto em quanto tempo?

A escolha do intervalo não é técnica, é de produto. Ela equilibra quanto o dado pode envelhecer contra quanto o servidor aguenta. A tabela é um ponto de partida:

IntervaloO dado envelheceCustoFaz sentido para
1 squase nada60 pedidos por minuto por pessoafila de atendimento em tempo real; use com cautela
10 spouco6 pedidos por minutopainel de pedidos de uma loja pequena
30 smédio2 pedidos por minutovitrine, estoque, status de encomenda
5 minbastante12 pedidos por horanúmero que muda devagar, como contagem de avaliações

Duas regras ajudam a decidir. A primeira: pergunte com que atraso o dado pode aparecer sem prejuízo. Se uma encomenda pode esperar meio minuto para aparecer no painel, o intervalo é 30 segundos — não 2. A segunda: cada aba aberta é uma pessoa perguntando. Cinquenta abas com intervalo de 1 segundo são 3.000 pedidos por minuto, e esse número derruba servidor pequeno.

8. Os tropeços do polling

O tropeço número um é o intervalo que nunca para. Ele nasce dentro do efeito, o componente sai da tela e o relógio continua chamando setState num componente que já não existe. No começo não dá nada; depois de navegar entre páginas, o console se enche de avisos e a memória cresce. A limpeza da aula de cleanup existe exatamente para isso — e, se você seguir o padrão da seção 4, ela já vem de graça.

O tropeço número dois é o intervalo com dependência errada: [rodada] no efeito que cria o relógio. A cada tique nasce um relógio novo, e o número de buscas por minuto dobra, triplica, explode. O sintoma é uma tela que pisca cada vez mais rápido. O terceiro é confiar que a resposta chega na ordem — o assunto da seção 5.

9. Cenários do dia a dia

Cenário 1: o painel do balcão

Com intervalo de 30 segundos, o painel da Ana passou a mostrar a encomenda sozinho. O atraso máximo é meio minuto, o que ninguém percebe no balcão. O F5 virou exceção, e o pedido de bolo que ela perdeu naquele sábado não se repetiu: quando o cliente enviou, o painel acendeu sozinho.

Cenário 2: a aba esquecida

Um sábado ela deixou o painel aberto no notebook e foi para o balcão por três horas. O servidor recebeu 360 pedidos daquela aba parada — e a fatura do serviço de hospedagem subiu. A guarda de pausa, ligada a um botão e ao evento de aba escondida, resolveu: com a aba minimizada, o polling dorme.

Cenário 3: o número que voltava

No dia de entrega, o contador de encomendas pendentes caía de 12 para 10 sem ninguém despachar nada. Era a resposta da rodada anterior chegando atrasada e sobrescrevendo a nova. Depois da guarda com useRef, o número passou a andar só para frente — e a Ana passou a confiar no painel de novo.

1. Qual é o papel do setInterval no polling?

2. O efeito que cria o intervalo tem [rodada] nas dependências e a rodada muda a cada tique. O que acontece?

3. A resposta da rodada 1 chega depois da rodada 2. O que fazer?

Exercício: o relógio que precisa parar

O efeito abaixo agenda o intervalo do polling, mas o relógio continua rodando depois que o painel sai da tela. Complete o return com a função que desfaz o agendamento:

useEffect(() => { const id = setInterval(tique, 30000); return () => (id); }, []);

Dica: é a função irmã de setInterval — o mesmo nome, com clear no lugar de set. Ela recebe o identificador devolvido pelo agendamento e cancela a repetição.

11. Resumo

Polling é perguntar de novo em intervalos regulares, porque o servidor não avisa quando algo muda. A receita tem três peças: uma função de atualizar com nome, um contador de rodada que o efeito observa, e um setInterval que incrementa a rodada. O efeito que cria o relógio leva [] nas dependências e limpa o intervalo no return.

Com várias buscas em voo, resposta fora de ordem é questão de tempo: numere as perguntas e ignore o que chega com rodada menor, guardando a maior numa useRef. Pausar é uma guarda no efeito e no tique, ligada a um estado. E o intervalo é decisão de produto: o menor tempo que o dado pode envelhecer sem prejuízo, não o menor tempo possível.

Para lembrar

  • Polling = busca repetida; o servidor não avisa, então o navegador pergunta.
  • Separe a busca numa função; o efeito só agenda.
  • O efeito do intervalo leva []; a rodada sobe com a forma funcional.
  • Numere as rodadas e descarte resposta antiga com useRef.
  • Pausar exige duas guardas: no efeito e no tique.
  • Intervalo curto custa caro: multiplique por abas e por horas.
  • clearInterval no return, sempre.
  • Log com número de rodada é o melhor amigo da depuração.
