Atualização otimista

O botão “encomendar” do site da Ana demora três segundos para responder. Nesses três segundos não acontece nada na tela: ninguém sabe se o clique funcionou, e a Ana já viu cliente clicando três vezes e recebendo três pães de queijo. O servidor estava certo; a tela é que ficava muda esperando a confirmação. Nesta aula a lista mostra a encomenda na hora e confirma depois — e, quando o envio falha, desfaz com elegância.

Você vai aprender
  • O que é atualização otimista e por que ela melhora a sensação de velocidade.
  • A ordem certa: pintar agora, enviar, confirmar depois.
  • Como marcar um item como “enviando” e trocar por “confirmado”.
  • Como desfazer quando o servidor recusa, voltando à lista anterior.
  • O que fazer com o identificador provisório do item que ainda não existe no servidor.
  • Quando não ser otimista: dinheiro, estoque, exclusão.
  • Os tropeços que deixam item fantasma na tela.

1. A cena: três segundos de tela parada

A versão atual do botão é a mais honesta que existe: espera. Ela manda o pedido, fica com o botão desligado, e só acrescenta a encomenda à lista quando o servidor confirma. Se a rede é rápida, o atraso é imperceptível. Se a rede é a do 3G da feira, são três segundos em que a tela não muda.

async function encomendar() {
  setEnviando(true);
  const resposta = await fetch("https://loja.test/api/encomendas", {
    method: "POST",
    body: JSON.stringify({ pao: "pão de queijo", qtd: 2 })
  });
  const salva = await resposta.json();
  setEncomendas([...encomendas, salva]);
  setEnviando(false);
}

Três segundos de silêncio produzem três comportamentos previsíveis. O primeiro: a pessoa clica de novo, achando que o primeiro clique não pegou. O segundo: ela sai da página no meio. O terceiro: ela pergunta no WhatsApp se o pedido entrou. Nenhum dos três é problema de código — é problema de expectativa, e a tela é quem cria a expectativa.

A atualização otimista resolve isso mudando a ordem das coisas. Em vez de esperar a confirmação para mostrar o resultado, a tela mostra o resultado imediatamente e envia o pedido em paralelo. A aposta é que vai dar certo — e, quando não dá, a tela desfaz. “Otimista” é literalmente isso: assumir o melhor e ter um plano para o pior.

2. A ideia: pintar antes de confirmar

Vale separar duas coisas que costumam andar juntas na cabeça de quem está começando: o dado que está no servidor e o dado que está na tela. No modo tradicional, os dois mudam no mesmo instante — a tela só muda depois que o servidor respondeu. No modo otimista, a tela muda primeiro e o servidor alcança depois.

Essa diferença de ordem tem uma consequência prática: durante alguns instantes, a tela mostra algo que ainda não é verdade. Isso é aceitável quando o dado é “a sua encomenda entrou na lista”, e não é aceitável quando é “seu pagamento foi aprovado”. A escolha é de produto, não de código.

otimista
Atualização que acontece na tela antes da confirmação do servidor, na aposta de que a operação vai funcionar.
pendente
O estado do item entre o clique e a resposta. A tela mostra o item, mas marcado — “enviando…” —, para ninguém achar que está tudo confirmado.
confirmar
Trocar o item pendente pelo que o servidor devolveu, que é a versão oficial do dado, com identificador de verdade.
desfazer
Voltar ao estado anterior quando a operação falha. Sem desfazer, otimismo vira item fantasma na lista.
provisório
Identificador temporário do item que ainda não existe no servidor. Serve para achar o item na lista enquanto a resposta não chega.

3. Pintar agora, confirmar depois

O primeiro passo é a lista mostrar o item antes de qualquer resposta. A caixa usa um servidor controlado por você: o pedido fica pendurado até o botão “servidor aceita”, e assim dá para ver os dois momentos sem correr contra o relógio.

Hoje a encomenda só entra na lista depois da resposta. Acrescente o pão ao estado pedidos antes de esperar o servidor, marcado com pendente: true — e, quando a resposta chegar, marque como confirmada.

let responder = null;

function enviarPedido(pao) {
  return new Promise((ok) => {
    responder = () => ok({ id: 42, pao: pao });
  });
}

function App() {
  const [pedidos, setPedidos] = useState([]);

  async function encomendar() {
    const salvo = await enviarPedido("pão de queijo");
    setPedidos([...pedidos, { id: salvo.id, pao: salvo.pao, pendente: false }]);
  }

  return (
    <div>
      <button id="pedir" onClick={encomendar}>encomendar pão de queijo</button>
      <button id="ok" onClick={() => responder && responder()}>servidor aceita</button>
      <ul className="pedidos">
        {pedidos.map((p) => (
          <li key={p.id}>{p.pao} — {p.pendente ? "enviando" : "confirmado"}</li>
        ))}
      </ul>
    </div>
  );
}

Duas linhas fazem o serviço. A primeira acrescenta o item provisório com pendente: true — ela roda antes do await, então a tela pinta na hora. A segunda, depois da resposta, troca o provisório pela versão do servidor usando map e comparação por identificador: o item de id "temp-1" vira o item de id 42 que veio de lá.

Repare no setPedidos((lista) => ...) com função. A lista anterior entrou numa variável fechada no clique, e quando a resposta chega ela pode estar desatualizada — outra encomenda pode ter entrado no meio. A forma funcional recebe a lista do momento, que é exatamente o que se quer para trocar um item.

4. Quando dá errado: desfazer

Ser otimista sem plano de desfazer é o erro mais comum do assunto. A tela mostra a encomenda, o servidor recusa (pão esgotado, por exemplo), e o item fica ali para sempre, como se existisse. Pior: a pessoa acha que encomendou e aparece na padaria esperando o pão.

O plano tem duas partes: guardar a lista anterior antes de mexer nela e devolvê-la no catch. Como o item provisório foi criado por você, não é preciso procurar nada — basta voltar ao estado de antes.

O item é acrescentado na hora, mas quando o servidor recusa ele fica na lista como se existisse. Guarde a lista anterior antes de acrescentar, devolva no erro e mostre a mensagem Pedido não enviado.

let recusar = null;

function enviarPedido(pao) {
  return new Promise((ok, erro) => {
    recusar = () => erro(new Error("sem estoque"));
  });
}

function App() {
  const [pedidos, setPedidos] = useState([]);
  const [aviso, setAviso] = useState("");

  async function encomendar() {
    setPedidos([...pedidos, { id: "temp-1", pao: "pão de queijo", pendente: true }]);

    try {
      await enviarPedido("pão de queijo");
    } catch (e) {
      setAviso("nada");
    }
  }

  return (
    <div>
      <button id="pedir" onClick={encomendar}>encomendar</button>
      <button id="recusar" onClick={() => recusar && recusar()}>servidor recusa</button>
      <p>{aviso}</p>
      <ul className="pedidos">
        {pedidos.map((p) => <li key={p.id}>{p.pao}</li>)}
      </ul>
    </div>
  );
}

Se o código usasse push na lista, o tal anterior já estaria modificado e o desfazer não desfaria nada.

5. O item provisório e o definitivo

Todo item otimista nasce sem identificador de verdade. O servidor é quem numera; na tela, você inventa um provisório — "temp-1", "temp-2" — só para conseguir achá-lo depois. Quando a resposta chega, o provisório é substituído pelo definitivo. Essa troca é a parte que mais confunde, porque envolve três coisas ao mesmo tempo: sumir com o provisório, guardar o definitivo e não duplicar a linha.

A resposta do servidor é acrescentada como item novo, então a lista acaba com dois pães de queijo. Troque o item provisório pelo que o servidor devolveu, sem duplicar: a lista tem de ficar com um item, mostrando salvo.

let responder = null;

function enviarPedido(pao) {
  return new Promise((ok) => {
    responder = () => ok({ id: 42, pao: "pão de queijo (2 un)" });

}

A troca tem um detalhe de key: o item provisório tinha key="temp-1" e passa a ter key={42}. Para o React, é outro elemento — o antigo sai, o novo entra. Isso é o correto: são dados diferentes. O que não pode é o novo entrar sem o antigo sair, que é o que produz a linha duplicada da caixa.

Um detalhe que evita susto: a lista pode ficar com dois itens iguais por alguns instantes, se a mesma encomenda for feita duas vezes. Não é bug do otimismo, é o servidor devolvendo duas encomendas de verdade. O que separa um caso do outro é o identificador: duas linhas com "temp-1" são um erro de código; duas linhas com ids 41 e 42 são dois pedidos que existem.

6. Os três estados de um item otimista

Um item otimista passa por até três estados, e a tela precisa saber desenhar os três. Esquecer o terceiro é o que deixa a lista com um item eternamente “enviando”.

EstadoO que a tela mostraO que acontece depois
pendenteo item, marcado “enviando…”ou confirma, ou falha
confirmadoo item com os dados do servidor, sem marcanada: é a versão oficial
falhouo item sai e aparece a mensagem de erroa pessoa tenta de novo

Há duas formas de desenhar o “falhou”. A primeira é tirar o item da lista e mostrar um aviso — é o que a seção 4 fez, e é a mais simples. A segunda é deixar o item na lista marcado como “não enviado”, com um botão de tentar de novo. A segunda é melhor quando o texto digitado é longo: ninguém quer redigitar um pedido porque a rede caiu. O que não serve é o silêncio.

O marcador de pendente também rende um detalhe de acessibilidade: ele deve estar no texto, e não só numa cor. “Enviando…” escrito à mão é lido por leitor de tela; uma bolinha amarela não é. E quem está no computador do balcão, com sol na tela, também agradece.

Um efeito colateral bom do otimismo é que ele obriga a pensar no erro. Quem escreve o caminho feliz apenas, nunca precisou decidir o que a tela faz quando o servidor diz não — e é justamente aí que o usuário fica sem saber o que aconteceu. Escrever o desfazer primeiro, antes do caminho bonito, costuma render um componente mais honesto.

7. Otimista demais

Atualização otimista é uma aposta, e aposta tem lugar. A regra prática: seja otimista quando o dado é seu e o erro é reversível; seja conservador quando o dado envolve dinheiro, estoque ou outra pessoa.

SituaçãoOtimista?Por quê
acrescentar encomenda à própria listasimse falhar, o desfazer devolve a lista anterior e nada se perde
marcar um recado como lidosimo custo do erro é baixo e o gesto parece instantâneo
“curtir” um pão do diasimo número pode voltar sozinho se falhar

baixar estoquenãodois balcões podem vender o último pão ao mesmo tempo

Existe um caso intermediário que resolve muita coisa: otimista no que a pessoa vê, conservador no que ela confirma por escrito. A lista mostra a encomenda na hora, o item diz “enviando”, e a confirmação com número de pedido aparece quando o servidor responde. A pessoa não espera para ver o efeito do clique, mas também não recebe como certo o que ainda não é.

8. Os tropeços de quem é otimista

O primeiro tropeço é esquecer o catch. Sem ele, a falha não chega em lugar nenhum, o item provisório fica na lista para sempre e o console registra um erro que ninguém leu. O segundo é desfazer errado: em vez de voltar à lista anterior, o código tenta remover o item pelo índice, e se outra encomenda entrou no meio o índice aponta para o pão errado.

O terceiro é duplicar: acrescentar a resposta do servidor como item novo, sem tirar o provisório. O sintoma é uma lista que cresce com pares de pão de queijo. O quarto é usar a lista fechada do clique dentro do catch — quase sempre funciona, mas quando duas encomendas entram juntas, a segunda desfaz a primeira. A cura é sempre a mesma: forma funcional no set.

console: pedido provisório criado: temp-1

Essa linha, escrita logo antes do await, mostra o item nascendo com identificador inventado. É o par dela que fecha o ciclo:

console: pedido confirmado: 42

Quando as duas aparecem no console, o caminho otimista inteiro rodou: provisório criado, resposta aceita, item trocado. Quando só a primeira aparece, o pedido ficou pendurado — ou o await nunca voltou, ou o catch engoliu o erro sem avisar ninguém.

9. Cenários do dia a dia

Cenário 1: os três pães de queijo

A cliente clicou três vezes porque a tela demorava. O servidor registrou três encomendas, a Ana assou seis pães de queijo e dois sobraram. Depois da atualização otimista, o item aparece no primeiro clique e o botão se desabilita enquanto o pedido está pendente: um clique, um pedido, e ninguém fica no escuro.

Cenário 2: o pão que acabou no meio do caminho

O pão de queijo acabou às dez da manhã e a cliente encomendou pelo site às dez e um. Com o desfazer, o item desapareceu da lista e a mensagem “Pedido não enviado” explicou o motivo. A Ana prefere assim: a tela errou por dois segundos e se corrigiu, em vez de prometer um pão que não existe.

Cenário 3: o recado que não queria perder

No formulário de recado, o texto digitado é longo e a rede do balcão cai. Em vez de tirar o item da lista, a tela passou a deixá-lo marcado como “não enviado”, com um botão de tentar de novo. A atualização otimista continua, e o trabalho de digitar não se perde.

Exercício: o desfazer que faltou

O envio está otimista, mas a falha não volta a lista ao que era. Complete o bloco que trata o erro:

const anterior = pedidos; setPedidos([...pedidos, { id: "temp-1", pao: "brioche", pendente: true }]); try { await enviarPedido("brioche"); } (e) { setPedidos(anterior); }

Dica: é a palavra que acompanha o try quando o assunto é erro — a mesma das aulas de tratamento de erro, que pega o problema em vez de deixar a tela muda.

11. Resumo

Atualização otimista é mostrar o resultado antes da confirmação e desfazer se o servidor recusar. A ordem é sempre: guarde a lista anterior, acrescente o item marcado como pendente, envie, e no sucesso troque o provisório pela versão do servidor; no erro, volte à lista guardada e avise.

O item provisório precisa de um identificador inventado para ser encontrado depois, e a troca é feita com map comparando id. Seja otimista no que é reversível e conservador em dinheiro, estoque e exclusão. E nunca deixe um item em “enviando” para sempre: pendente é estado de passagem, não destino.

Para lembrar

  • Otimista = tela primeiro, servidor depois, desfazer se falhar.
  • Guarde a lista anterior antes de acrescentar.
  • Marque o item com pendente: true e troque por “confirmado” na resposta.
  • Identificador provisório ("temp-1") serve para achar o item depois.
  • Troque com map e id; nunca acrescente a resposta como item novo.
  • No erro: setPedidos(anterior) e uma mensagem visível.
  • Desabilite o botão enquanto pendente: evita clique triplo.
  • Dinheiro, estoque e exclusão pedem confirmação antes da tela.
