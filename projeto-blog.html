Blog

A Ana escreve sobre pão há anos — em três cadernos, num bloco de notas e em dois papéis colados na parede da cozinha. Ela quer um blog de verdade: uma lista de posts, um campo de busca e uma página para ler cada receita inteira. Neste projeto você monta esse blog com ela, na ordem em que as coisas precisam ser feitas: os dados primeiro, os componentes depois, o estado no fim — e cada pedaço roda aqui na caixa, com o React de verdade.

Você vai aprender
  • Como transformar uma ideia de tela em uma lista de dados antes de escrever componente.
  • Quais estados um blog precisa e onde cada um deve morar.
  • Como montar o cartão de um post com título, resumo, tag e data.
  • Como ligar um campo de busca à lista sem estragar os dados originais.
  • Como abrir um post guardando o id, e não o objeto inteiro.
  • A ordem de montagem que evita retrabalho: dado, lista, filtro, detalhe.
  • O que costuma quebrar num blog e como perceber pelo sintoma.

1. A cena: as receitas espalhadas em três cadernos

A Ana tem sete textos prontos. Dois sobre fermentação, dois sobre fornos, três com receitas que ela vende no balcão. O problema não é escrever: é que ninguém acha nada. Quem quer a receita do pão de queijo pergunta no balcão; quem quer saber do forno novo nunca fica sabendo.

Um blog resolve isso com três telas bem pequenas. A primeira é uma lista: todos os posts, do mais novo para o mais antigo, cada um com título, resumo, tag e data. A segunda é uma busca: a mesma lista, filtrada pelo que a pessoa digita. A terceira é a leitura: um post inteiro, aberto depois de um clique.

É tentador começar pela tela mais bonita. Não faça isso. A ordem que funciona é a ordem dos dados: primeiro decidir o que é um post, depois desenhar a lista, depois o filtro, depois a leitura. Cada etapa usa a anterior, e nenhuma precisa ser desfeita. Nas próximas seções você vai montar exatamente nessa ordem.

2. O desenho antes do código: as três telas

Antes de escrever JSX, a Ana desenhou as três telas no papel. Esse passo parece perda de tempo e economiza horas: no papel ela descobre que a busca precisa do mesmo dado da lista, que a leitura precisa achar um post pelo id, e que a tag aparece nas três telas. Tudo isso vira uma decisão de dados, não de CSS.

TelaO que mostraQue dado precisa
Listatodos os posts, do mais novo ao mais antigoo array de posts, já ordenado
Buscaos posts que casam com o texto digitadoo array + o texto da busca
Leituraum post inteiro, com o corpoo array + o id do post aberto
Filtro por tagsó os posts de uma tago array + a tag escolhida

Repare no que não aparece na tabela: nenhuma tela precisa de uma cópia própria da lista. As quatro leem o mesmo array e mudam só o que está em volta: uma ordenação, um texto, um id, uma tag. Essa é a decisão mais importante do projeto inteiro — e a que mais gente erra, guardando uma lista filtrada dentro do estado e ficando com duas verdades.

O desenho também resolve uma dúvida de navegação: o blog é uma página só, que troca de conteúdo conforme o estado. Não há rota, não há endereço novo, não há recarregamento. Isso simplifica muito para quem está começando; quando o projeto crescer, a aula de Rotas com Estado mostra como transformar esses estados em endereços de verdade.

3. O post é um objeto: os dados do blog

Um post não é um título solto. Ele tem um identificador, um título, uma data, uma tag, um resumo curto que aparece na lista e um corpo longo que aparece na leitura. Cinco minutos escolhendo esses campos evitam um mês de remendo.

id
O número que identifica o post. Não muda nunca e serve de key na lista e de critério para achar o post aberto.
titulo
O texto que aparece no cartão e no topo da leitura. Curto, direto, sem ponto final.
tag
A categoria do post: receitas, bastidores. É o que o filtro usa depois; por enquanto, é só um texto no cartão.
resumo
Uma frase que dá vontade de clicar. Aparece no cartão; nunca substitui o corpo.
corpo
O texto inteiro do post. Fica só na tela de leitura — se você desenhar o corpo na lista, a página vira um rolo.

Escreva os posts em um arquivo separado, dados/posts.js, exportando o array. Isso não é organização por gosto: é o que permite trocar o array fixo por dados vindos de uma API depois, sem tocar nos componentes. Enquanto são sete posts, o arquivo é uma constante; no dia em que forem setecentos, ele vira uma chamada de rede e nenhum componente muda.

export const posts = [
  {
    id: 1,
    titulo: "Pão de fermentação natural",
    data: "12/03/2026",
    tag: "receitas",
    resumo: "Doze horas de espera e três ingredientes.",
    corpo: "Misture a farinha e a água e deixe descansar por doze horas."
  },
  {
    id: 2,
    titulo: "Como escolher o forno da padaria",
    data: "05/03/2026",
    tag: "bastidores",
    resumo: "O que a Ana aprendeu com dois fornos.",
    corpo: "Dois fornos, duas contas de luz, uma decisão."
  }
];

Para conferir se o modelo está completo, um console.log com as chaves do primeiro post resolve — se falta um campo que a tela precisa, aparece aqui:

console.log("campos do post: " + Object.keys(posts[0]).join(", "));
console: campos do post: id, titulo, data, tag, resumo, corpo

Com o modelo na mão, o resto do projeto é decidir onde cada pedaço mora. Duas telas que leem o mesmo array não precisam de duas cópias; uma tela que muda com o clique precisa de um estado.

4. A árvore de componentes e onde mora cada estado

O blog inteiro cabe em quatro componentes. App guarda o estado e os dados; ListaDePosts recebe os posts já prontos para desenhar; CartaoDePost desenha um post; Leitura recebe um post e mostra o corpo. A busca é um <input> dentro do App, porque o valor dela muda a lista — e o estado que muda a lista mora acima dela.

PeçaOnde moraPor quê
os postsarquivo de dadosé conteúdo, não muda durante a sessão
o texto da buscaestado no Appmuda a cada letra e filtra a lista
a tag escolhidaestado no Appmuda no clique e filtra a lista
o post abertoestado no Appmuda no clique e troca a tela de leitura
a lista visívelderivada no desenhoé consequência dos três de cima

Três estados, uma derivada. É pouco para um app inteiro, e essa é a graça: quanto menos estado, menos coisa pode ficar fora de sincronia. Toda vez que você sentir vontade de criar um quarto useState para "a lista filtrada", releia a última linha da tabela — ela quase sempre resolve com uma const.

A escolha de guardar o id do post aberto, e não o objeto, merece destaque. Se você guarda o objeto, o blog congela aquele post no momento do clique: quando o texto for editado, a leitura continua mostrando a versão velha. Guardando o id, você acha o post de novo a cada desenho e sempre vê a versão atual. É a mesma lição da aula de Estado Derivado, aplicada a uma tela de detalhe.

5. Primeiro pedaço: o cartão de post

Comece pelo que a pessoa vê primeiro. O cartão é um <li> com quatro informações: título, resumo, tag e data. Ele não busca nada, não decide nada — recebe um post por prop e desenha. Essa divisão deixa o componente testável e reaproveitável na lista, na busca e no filtro por tag.

título
Um h2 dentro do item da lista. É o que dá hierarquia à página e o que o leitor de tela anuncia primeiro.
resumo
Um parágrafo curto, com classe própria para o CSS limitar a duas linhas.
tag
Um span com classe tag. Vira botão de filtro depois; hoje é só rótulo.
data
Texto guardado no dado, no formato brasileiro. Simples e sem susto de fuso.
key
O id do post, no <CartaoDePost> que o map devolve.

A lista mostra só o título. Use o componente CartaoDePost, que já existe, dentro do map — passando o post na prop e o id na key.

const posts = [
  { id: 1, titulo: "Pão de fermentação natural", data: "12/03/2026", tag: "receitas", resumo: "Doze horas de espera e três ingredientes." },

O painel mostra três <li class="post">, cada um com título, resumo e a linha da tag com a data. Repare que a key foi para o <CartaoDePost>, e não para o <li> de dentro: quem percorre a lista é o App, então é ele que sabe qual é a identidade de cada linha. É a regra da aula de Chaves Estáveis, aplicada a um componente em vez de uma tag.

Se você desenhar o corpo no cartão, a lista vira um rolo e ninguém acha nada. Resumo é resumo: uma frase, no máximo duas. O corpo tem a sua tela, e é o próximo pedaço.

Duas decisões de acabamento cabem já aqui, no cartão. A primeira é a data: guarde em texto, no formato brasileiro. Parece preguiça e é prudência — uma data ISO como 2026-03-12 é lida como meia-noite em UTC, e no fuso de São Paulo isso é 21h do dia anterior, então a tela mostraria 11/03. Se um dia você guardar datas em ISO, converta com cuidado e teste no fuso certo.

A segunda é o tempo de leitura, que avisa o tamanho do texto antes do clique. A conta é grosseira e honesta: duzentas palavras por minuto, arredondando para cima.

export function tempoDeLeitura(corpo) {
  const palavras = corpo.split(" ").filter(Boolean).length;
  return Math.ceil(palavras / 200) + " min de leitura";
}

console.log(tempoDeLeitura(posts[0].corpo));

Com um corpo de 412 palavras, o console mostra:

console: 3 min de leitura

Repare no formato: isso não é componente nem estado, é uma função de texto que roda na hora de desenhar. O cartão chama tempoDeLeitura(post.corpo) e mostra o resultado ao lado da data.

6. Segundo pedaço: a busca que filtra sem estragar

Agora o campo que faz o blog ser útil. A busca é um estado de texto mais um filter derivado — nada de guardar a lista filtrada. A cada letra digitada, o estado muda, o filter roda e a lista desenha menos itens. O array original continua inteiro o tempo todo.

O campo não está ligado a nada e a lista mostra os três posts. Controle o campo com busca e filtre os títulos por includes, sem diferenciar maiúsculas. Depois digite queijo.

const posts = [
  { id: 1, titulo: "Pão de fermentação natural" },
  { id: 2, titulo: "Como escolher o forno da padaria" },
  { id: 3, titulo: "O pão de queijo que vende antes das 8h" }
];

function App() {
  const [busca, setBusca] = useState("");

  return (
    <div>
      <input placeholder="buscar no blog" />
      <ul>
        {posts.map((p) => <li key={p.id}>{p.titulo}</li>)}
      </ul>
    </div>
  );
}

const posts = [
  { id: 1, titulo: "Pão de fermentação natural" },
  { id: 2, titulo: "Como escolher o forno da padaria" },
  { id: 3, titulo: "O pão de queijo que vende antes das 8h" }

function App() {
  const [busca, setBusca] = useState("");
  const visiveis = posts.filter((p) => p.titulo.toLowerCase().includes(busca.toLowerCase()));

  return (
    <div>
      <input
        placeholder="buscar no blog"
        value={busca}
        onChange={(e) => setBusca(e.target.value)}
      />
      <ul>
        {visiveis.map((p) => <li key={p.id}>{p.titulo}</li>)}
      </ul>
    </div>
  );
}

Depois de digitar "queijo", o painel mostra um <li> só, com o value do campo atualizado. Três detalhes fazem a diferença. O primeiro é value={busca} junto com onChange: sem os dois, o campo é do navegador, não do React, e o valor some no próximo desenho. O segundo é toLowerCase() nos dois lados, para "Queijo" e "queijo" darem no mesmo. O terceiro é filtrar antes do map, como a aula de Filtrar explica.

Um log simples mostra a conta que a tela está fazendo:

const visiveis = posts.filter((p) => p.titulo.toLowerCase().includes(busca.toLowerCase()));
console.log(visiveis.length + " de " + posts.length + " posts");

Digitando "queijo" em um blog de três posts, o console mostra:

console: 1 de 3 posts

Se o número da esquerda nunca muda, o filter está no lugar errado — ou o campo não está controlado. Se muda e a lista não, você filtrou uma variável que o JSX não usa. Esse par de números é o teste mais rápido de uma busca.

Falta um detalhe que custa uma linha: o campo precisa de um label de verdade, ligado por htmlFor e id. Placeholder não é rótulo — ele desaparece quando a pessoa digita e nem todo leitor de tela o anuncia.

7. Terceiro pedaço: abrir um post

Falta a leitura. O estado guarda o id do post aberto; o componente acha o post com find; a área de leitura mostra título e corpo. Antes do primeiro clique, a área mostra um convite — não um espaço vazio, que parece defeito.

O botão já guarda o id em aberto e o find já acha o post, mas a área de leitura está vazia. Mostre o post aberto ali dentro — e um convite quando nada estiver aberto.

const posts = [
  { id: 1, titulo: "Pão de fermentação natural", corpo: "Misture a farinha e a água e deixe descansar por doze horas." },
  { id: 2, titulo: "Como escolher o forno da padaria", corpo: "Dois fornos, duas contas de luz, uma decisão." }
];

function App() {
  const [aberto, setAberto] = useState(null);
  const post = posts.find((p) => p.id === aberto);

  return (
    <div>
      <ul>
        {posts.map((p) => (
          <li key={p.id}>
            <button className="abrir" onClick={() => setAberto(p.id)}>{p.titulo}</button>
          </li>
        ))}
      </ul>
      <div className="leitura"></div>
    </div>
  );
}

Clique no primeiro botão e a área de leitura ganha um <h3> com o título e o corpo. O ternário tem dois lados por um motivo: post é undefined enquanto ninguém clicou, e desenhar post.titulo nesse momento derrubaria o componente. É a mesma proteção da aula de Renderização Condicional.

Note também que o botão guarda p.id, não p. Parece detalhe e não é: o id é uma chave estável; o objeto é uma foto do momento. Guardando o id, qualquer mudança no post aparece na leitura sem você fazer nada. Guardando o objeto, a leitura fica congelada no dia do clique.

Duas linhas de acessibilidade fecham a leitura. O botão que abre o post é um button de verdade, então o teclado já funciona de graça. E a área de leitura ganha aria-live="polite", para o leitor de tela anunciar o texto novo quando ele troca sem recarregar a página — a aula de Acessibilidade explica o resto.

8. A ordem de montagem e o que quebra

Com os três pedaços prontos, a ordem de montagem do projeto fica óbvia — e ela é sempre a mesma em qualquer app de lista com detalhe. Vale escrever no papel antes de abrir o editor.

src/
  dados/posts.js          os posts, sem React nenhum
  App.jsx                 o estado e a lista
  componentes/CartaoDePost.jsx
  componentes/ListaDePosts.jsx
  componentes/Leitura.jsx
  componentes/Busca.jsx

Monte nesta ordem: dados, cartão, lista, busca, leitura. Cada passo tem uma tela que você consegue olhar. Se você começar pela leitura, vai precisar inventar um post para testar; se começar pela busca, vai filtrar uma lista que ainda não existe. A ordem certa é a que deixa a tela funcionando a cada passo.

Falta um estado que o desenho previu e as caixas não precisaram: a tag escolhida. Ela entra por último, e a receita é a mesma da busca — um useState começando em "todas", um botão por tag e mais uma condição no filter. Duas mudanças pequenas, nenhuma estrutura nova.

Cenário 1: a busca apaga quando abro um post

A Ana digitou "fermentação", abriu um post e o campo voltou vazio. Ela tinha desenhado a busca dentro de um bloco que só aparece na lista — e ao trocar para a leitura, o campo foi desmontado, levando o estado junto. O conserto é manter a busca acima da troca de tela, no App, para o estado sobreviver à navegação.

Cenário 2: a leitura mostra a versão antiga do texto

Ela corrigiu um post no arquivo de dados e a tela de leitura continuou com o texto anterior. O estado guardava o objeto inteiro, capturado no clique. Guardando o id e fazendo find a cada desenho, a leitura passa a refletir o dado atual. Em app de verdade, é a diferença entre ver o pedido como ele está e vê-lo como estava.

Cenário 3: o blog inteiro numa rolagem só

Ela desenhou o corpo do post dentro do cartão. Com dois posts ficou bonito; com sete, ninguém chegava ao segundo. O resumo existe para isso: o cartão dá vontade de clicar, a leitura entrega o texto. Quando a lista fica longa, a aula de Paginação mostra como fatiar sem mudar nada.

10. Resumo

Um blog é uma lista, uma busca e uma leitura sobre o mesmo array de posts. O projeto começa pelos dados: id, título, data, tag, resumo e corpo. Depois vem o cartão, que recebe um post por prop; depois a lista, que percorre com map e key igual ao id; depois a busca, que é um estado de texto mais um filter derivado; por último a leitura, que guarda o id aberto e acha o post com find.

Três estados resolvem o app inteiro — busca, tag e post aberto — e a lista visível é sempre conta, nunca estado. Guardar o id em vez do objeto mantém a leitura atualizada; guardar a lista filtrada cria uma segunda verdade que envelhece. E a ordem de montagem (dado, cartão, lista, busca, leitura) garante uma tela funcionando em cada passo, o que é a melhor forma de descobrir um erro cedo.

O acabamento é curto e faz diferença: data guardada em texto no formato brasileiro, tempo de leitura calculado a partir do corpo, botão de verdade para abrir o post, área de leitura anunciada com aria-live e um label na busca. Nada disso é enfeite: é o que transforma uma lista de textos em um blog que as pessoas conseguem usar.

Quando o blog crescer, os próximos passos já têm aula: paginar a lista, ordenar por data com sort, trocar o array fixo por dados de uma API com useEffect e transformar o post aberto em endereço com rotas. O desenho que você fez aqui continua o mesmo — muda só de onde os dados vêm.

Para lembrar

  • Projeto começa pelos dados: os campos do post antes de qualquer componente.
  • Um array de posts serve a todas as telas; nenhuma precisa de cópia própria.
  • Cartão recebe um post por prop; a key é o id, no componente que o map devolve.
  • Busca é estado de texto + filter derivado, com toLowerCase nos dois lados.
  • Campo controlado precisa de value e onChange juntos.
  • Guarde o id do post aberto; ache o post com find a cada desenho.
  • Leitura sem post escolhido mostra um convite, não uma área vazia.
  • Ordem de montagem: dados, cartão, lista, busca, leitura.
  • Data em texto no formato brasileiro evita o deslocamento de fuso do ISO.
  • Botão para abrir, aria-live na leitura e label na busca: acessibilidade barata.
