Controlado e Não Controlado

No formulário de encomenda da Ana há um campo para o nome do cliente e outro para a observação. Ela converteu os dois em controlados, com estado e onChange, porque era assim que sabia fazer — e agora o telefone dela engasga a cada letra da observação, que só é usada no fim, quando o botão é clicado. Nesta aula a Ana aprende que existem dois jeitos de um campo guardar o que foi digitado, que os dois convivem no mesmo formulário e que a escolha certa depende de uma pergunta só: alguém precisa desse valor antes do envio?

Você vai aprender
  • Quem guarda o texto em cada um dos dois estilos: o navegador ou o estado.
  • Como ler um campo não controlado com FormData no envio, e por que o name é obrigatório.
  • Como um valor controlado alimenta outra parte da tela na mesma tecla.
  • Os dois estilos no mesmo formulário, cada um no seu lugar.
  • Como reiniciar um formulário não controlado com a key, sem um estado por campo.
  • O que quebra ao trocar de um estilo para o outro no meio da vida do componente.
  • Os casos em que não controlado é a única opção, como o campo de arquivo.

1. A cena: dois campos, duas necessidades

O nome do cliente e a observação são campos de texto iguais na aparência e diferentes no uso. O nome é usado três vezes enquanto a pessoa digita: o cabeçalho cumprimenta, o resumo da encomenda mostra "Cliente: …" e o botão muda de cor quando o campo tem mais de duas letras. A observação, ao contrário, só importa no instante do envio: "sem açúcar", "deixar na portaria", "cortar em fatias". Ninguém precisa dela durante a digitação.

A Ana fez os dois com estado porque é o estilo que ela aprendeu primeiro, e o resultado tem um custo que não aparece em tela pequena: cada tecla na observação provoca um desenho do componente inteiro, com validação, formatação e uma lista de produtos na mesma árvore. Num notebook não se nota; num telefone simples, o campo trava de vez em quando. E a observação nem precisava disso.

A regra que resolve o caso é curta: se alguém precisa do valor enquanto a pessoa digita, o estado é o dono; se o valor só é lido no envio, o navegador é o dono. As duas formas têm nome e você já viu a primeira na aula de entrada controlada. Agora vamos ver a segunda com calma, porque ela é mais antiga que o React e continua sendo a certa em vários casos.

2. Dois donos para o mesmo texto

Todo campo de texto tem um valor, e esse valor mora em algum lugar. No estilo não controlado, mora dentro do próprio elemento do DOM: o navegador guarda o texto, cuida do cursor e da seleção. O React só descobre o que está lá quando alguém vai buscar. No estilo controlado, o valor mora no estado do componente, e o elemento é um espelho que não tem memória própria.

controlado
O estado é o dono: value={texto} mostra e onChange devolve cada tecla para o estado. O React sabe tudo, a cada instante.
não controlado
O DOM é o dono: você escreve defaultValue (ou nada) e o campo cuida de si. O React só lê quando precisa.
defaultValue
O valor inicial de um campo não controlado. Ele é aplicado quando o elemento é criado e não muda o que a pessoa digita depois.
name
O nome do campo dentro do formulário. É a chave com que o envio lê o valor: sem name, o campo não existe para o formulário.
FormData
A leitura de todos os campos de um formulário de uma vez, na hora do onSubmit: new FormData(evento.target).
key
A identidade de um elemento para o React. Trocar a key joga o elemento fora e cria outro, com o valor de fábrica.

Nenhum dos dois é o jeito "certo" em geral. O controlado dá controle — validação ao vivo, máscara, botão que só habilita com o formulário completo, limpar com um clique. O não controlado dá leveza — menos estado, menos desenho, menos código. O erro é escolher por hábito em vez de escolher pela necessidade, e é isso que a aula conserta.

3. O campo que o navegador guarda

O primeiro caso é o formulário de encomenda com um campo de nome. Ele não tem value nem onChange: no envio, o código lê o formulário inteiro com FormData e pega o campo pelo nome. No código inicial, o campo está sem name, então o formulário não tem o que procurar e o recado sai "Encomenda de null". A missão é dar nome ao campo.

O campo não tem name, e o FormData não consegue achá-lo. Acrescente name="nome" ao input, digite Maria e clique em "Encomendar".

function App() {
  const [enviado, setEnviado] = useState("Nada enviado");

  function aoEnviar(evento) {
    evento.preventDefault();
    const dados = new FormData(evento.target);
    setEnviado("Encomenda de " + dados.get("nome"));
  }

  return (
    <form onSubmit={aoEnviar}>
      <input placeholder="Nome do cliente" />
      <button type="submit">Encomendar</button>
      <p>{enviado}</p>
    </form>
  );
}

Repare no que o componente não tem: nenhum estado para o texto, nenhum onChange, nenhum desenho por tecla. O que ele tem é um caminho de leitura no momento certo. O evento.preventDefault() impede o envio de verdade do formulário — no navegador comum ele recarregaria a página — e o FormData monta uma lista de pares nome/valor com todos os campos que têm name.

A utilidade do name não é um detalhe do React: é o mesmo atributo que o HTML usa desde sempre para enviar formulários. Um campo sem name não é enviado, e é por isso que dados.get("nome") devolve null. Se o seu campo não controlado "não chega", a primeira coisa a conferir é o nome; a segunda, se ele está dentro do <form>.

Uma armadilha de leitura: dados.get() devolve sempre texto, mesmo em campo numérico. Se você precisa de número, converta com Number(...) e trate o caso vazio, porque Number("") é zero e some com a diferença entre "não preencheu" e "preencheu zero". A aula de envio de formulário mostra o formulário completo, com vários campos e o resumo depois do envio.

4. O campo que vive no estado

O segundo caso é a quantidade de pães. Aqui o valor precisa aparecer fora do campo, no total, e precisa aparecer enquanto a pessoa digita. Não há como fazer isso com um campo que só conta o valor no fim: o total tem de ser recalculado a cada mudança, e para o React recalcular ele precisa saber que algo mudou. Estado é o mecanismo que avisa.

O campo é não controlado e o total é um texto fixo. Ligue o campo a um estado qtd (com value e onChange) e calcule Number(qtd) * 2 para o total. Digite 3 no campo.

function App() {
  return (
    <div>
      <label>Pães <input id="qtd" defaultValue="1" /></label>
      <p>Total: R$ 2,00</p>
    </div>
  );
}
<div>
  <label>
    Pães
    <input id="qtd" value="1">

function App() {
  const [qtd, setQtd] = useState("1");
  const total = Number(qtd) * 2;

  return (
    <div>
      <label>Pães <input value={qtd} onChange={(e) => setQtd(e.target.value)} /></label>
      <p>Total: R$ {total.toFixed(2).replace(".", ",")}</p>
    </div>
  );
}

O total não é um estado: é uma conta feita no desenho, a partir de qtd. Guardar o total num segundo useState funcionaria hoje e criaria duas verdades amanhã — a aula de estado derivado é toda sobre isso. A regra é: guarde o que só existe porque a pessoa fez algo; calcule o que pode ser calculado.

Vale notar o que o defaultValue fazia e não faz. Ele põe um valor inicial no elemento, uma vez. Se você mudar o estado e o elemento for não controlado, o texto na tela não muda — e é aí que o iniciante conclui que "o React não atualiza o campo". Não é bug: é o navegador cuidando do que é dele. Para o React mandar no que aparece, o campo precisa receber value.

5. Os dois no mesmo formulário

A decisão não é do formulário, é de cada campo. O formulário de encomenda da Ana termina com os dois estilos lado a lado, e o código abaixo é o que roda hoje no site dela: a observação não controlada, lida no envio, e a quantidade controlada, que alimenta o total ao vivo. Um único estado, o do total, para os dois campos que precisam dele.

function FormularioEncomenda() {
  const [qtd, setQtd] = useState("1");
  const [obs, setObs] = useState("");
  const total = Number(qtd) * 2;

  function aoEnviar(evento) {
    evento.preventDefault();
    const dados = new FormData(evento.target);
    console.log("qtd: " + dados.get("qtd"));
    console.log("obs: " + (dados.get("obs") || "(vazio)"));
  }

  return (
    <form onSubmit={aoEnviar}>
      <input name="qtd" value={qtd} onChange={(e) => setQtd(e.target.value)} />
      <p>Total: R$ {total.toFixed(2)}</p>

      <input name="obs" placeholder="Observação" />
      <button type="submit">Encomendar</button>
    </form>
  );
}

Aqui está a graça do FormData: ele não liga para quem controla o campo. No envio, ele lê o valor atual dos dois — o que o React mantém em qtd e o que o navegador mantém em obs — e devolve tudo junto, pelo name. Você pode misturar os estilos sem criar uma exceção no envio. A diferença fica no meio do caminho: o controlado passou pelo estado a cada tecla, o outro não.

O console.log com o resultado do envio é o jeito mais rápido de descobrir por que um campo chega vazio. Se o nome aparece no log, o campo está certo e o problema está depois; se aparece null, o campo está fora do formulário ou sem name. No navegador do dia a dia isso sai no console do DevTools, com a tecla F12:

qtd: 3
obs: (vazio)

Duas notas sobre esta mistura. A primeira: o campo controlado também precisa de name se você for ler o formulário no envio — o React não muda essa regra do HTML. A segunda: o estado obs do exemplo existe só para mostrar que ele seria inútil; tirando a linha, o componente fica menor e faz a mesma coisa. Código que não serve para nada é código que alguém vai manter.

O problema é o tamanho do que redesenha: se o estado mora no topo de uma árvore grande, cada tecla custa caro. Um jeito de amenizar é deixar o estado no menor componente possível, perto do campo, e mandar para cima só o que interessa. É o assunto da aula de elevar o estado.

6. Reiniciar sem estado: a chave

Falta o problema do fim do formulário: depois de enviar, o campo tem de voltar ao ponto de partida. No campo controlado, um setTexto("") resolve. No não controlado, não existe estado para zerar — e é aí que entra o key, aquela prop que você já viu em listas e que aqui faz um trabalho diferente: dizer ao React que aquele elemento é outro elemento.

Quando a key muda, o React não atualiza o elemento: ele joga fora e cria de novo, do zero. Um elemento novo, com defaultValue de fábrica, começa vazio. Na caixa, a Ana já contava os envios e já tinha o número na mão; faltou usar como key do campo.

Depois do primeiro envio, o campo continua com "Ana" e um segundo clique manda o mesmo nome de novo. Ponha key={envios} no input, digite Ana e clique em "Encomendar" duas vezes.

function App() {
  const [envios, setEnvios] = useState(0);
  const [recado, setRecado] = useState("Nada enviado");

  function aoEnviar(evento) {
    evento.preventDefault();
    const dados = new FormData(evento.target);
    const nome = dados.get("nome");
    setRecado("Encomenda de " + (nome || "(vazio)"));
    setEnvios(envios + 1);
  }

  return (
    <form onSubmit={aoEnviar}>
      <input name="nome" placeholder="Nome do cliente" />
      <button type="submit">Encomendar</button>
      <p>{recado}</p>
      <p>Envios: {envios}</p>
    </form>
  );
}

O segundo clique é a prova: sem a key, o campo ainda tem "Ana" e o recado repete o nome; com ela, o campo é outro e o formulário manda vazio. Esse truque tem um preço e vale conhecê-lo: o elemento novo perde o foco, perde a seleção, perde a posição do cursor e perde qualquer mensagem de erro que estivesse pendurada nele. Para reiniciar um formulário inteiro depois do envio, é exatamente o que se quer; para "atualizar" um campo no meio da digitação, é um desastre.

Existe uma alternativa nativa para o formulário todo: chamar evento.target.reset() no onSubmit. Ele devolve os campos aos valores de fábrica e não troca elementos, então o foco continua onde está. A key é mais útil quando você quer reiniciar uma parte — um campo, um grupo, um subformulário — e não o formulário inteiro. As duas soluções são válidas; a diferença é o tamanho do que se quer jogar fora.

7. A migração: o que quebra ao trocar de estilo

Trocar de não controlado para controlado é uma decisão de uma linha e um erro clássico: deixar o defaultValue no lugar e acrescentar o value, ou pôr o value e esquecer o onChange. O primeiro caso dá um campo que "não obedece"; o segundo, um campo que não aceita digitação nenhuma, porque o estado nunca muda e o campo é desenhado sempre com o mesmo texto.

Existe um terceiro caso, mais sutil, que só aparece em desenvolvimento: o valor começa undefined e depois vira texto. No primeiro desenho o campo é não controlado; no segundo, vira controlado. O React avisa, porque a mudança de natureza no meio da vida do elemento confunde o navegador:

Warning: A component is changing an uncontrolled input to be controlled. This is likely caused by the value changing from undefined to a defined value.

Esse aviso não aparece nas caixas deste guia, que rodam build de produção — é um recado do modo de desenvolvimento. Mas ele aparece no seu projeto, e a leitura é direta: comece o estado com uma string, mesmo vazia. useState("") em vez de useState(). Se o dado pode faltar, o valor do campo pode ser "", e a diferença entre "não preenchido" e "preenchido" fica numa variável separada.

O caminho contrário, de controlado para não controlado, é mais raro e tem um erro próprio: manter o estado e o onChange "só para não quebrar". Aí você tem o custo dos dois estilos e o benefício de nenhum. Se ninguém lê o valor durante a digitação, apague o estado, o onChange e o value — e ponha defaultValue e name.

8. Os casos que só existem de um jeito

Alguns campos não têm escolha. O campo de arquivo (type="file") é sempre não controlado: por segurança, o navegador não deixa o JavaScript definir o arquivo escolhido. Você lê o que está lá com evento.target.files ou com FormData, e não existe value= para ele. Quem tenta controlar um campo de arquivo recebe um aviso e um campo que ignora o valor.

O mesmo vale para campos que só são lidos no envio por natureza: busca de CEP, upload, assinatura em canvas, leitor de código de barras. Nesses, o estado ao vivo não agrega nada. Já o oposto — o campo que precisa de máscara enquanto digita, como telefone e CPF — é caso de controlado, sempre, porque a formatação acontece a cada tecla e o cursor precisa ser respeitado. A aula de input controlado entra nesse detalhe.

Vale também desconfiar do useRef como atalho. Ele funciona para ler o campo no clique — busca.current.value —, e é o mesmo mecanismo do FormData, só que para um campo. O problema é que essa leitura não avisa ninguém: se outra parte da tela depende do valor, ela não vai saber que ele mudou. Use ref quando o valor é usado uma vez, no mesmo instante, e estado quando ele precisa circular.

9. Cenários do dia a dia

Cenário 1: o cupom de desconto

O campo de cupom é lido só quando o cliente clica em "Aplicar". Não há nada para validar enquanto ele digita: o código é conferido no servidor. Não controlado, com name="cupom" e FormData no envio, resolve com três linhas e nenhum estado. Se depois a Ana quiser aplicar o cupom automaticamente ao sair do campo, aí a leitura passa a acontecer em outro evento — e continua sem precisar de estado.

Cenário 2: o CPF com máscara

O CPF precisa aparecer formatado enquanto o cliente digita, com pontos e traço. Isso é transformação a cada tecla: estado, value e onChange, com a função de máscara no meio. Controlado é a única opção viável, e o cuidado é não mover o cursor para o começo quando o texto muda de tamanho — um detalhe chato, mas com receita conhecida.

Cenário 3: a lista de ingredientes do bolo

O cliente escolhe até cinco ingredientes e vê a lista se montando na tela. Aqui cada escolha muda outra parte da tela imediatamente, então o estado é necessário — mas o estado pode morar no componente da lista, e não na página inteira. Quanto menor o componente que guarda, menos coisa redesenha por tecla, e o formulário continua leve mesmo com dez campos controlados.

Exercício: ler o formulário no envio

Complete a linha que lê o valor do campo nome no momento do envio, sabendo que dados já é o FormData do formulário:

const nome = dados.("nome");

Dica: é o método que busca o valor pela chave, ou seja, pelo name do campo. Não é querySelector — o FormData não conhece o DOM.

11. Resumo

Controlado e não controlado respondem à mesma pergunta com donos diferentes: quem guarda o texto que a pessoa digitou. No controlado, o estado guarda, o campo mostra value e cada tecla volta pelo onChange — o React sabe de tudo e pode reagir na hora. No não controlado, o navegador guarda, o componente escreve defaultValue uma vez e lê o valor quando precisa, com FormData ou com uma ref.

A escolha não é de gosto: é "alguém usa esse valor antes do envio?". Se sim, controlado — validação ao vivo, máscara, total que acompanha, botão que habilita. Se não, não controlado — menos estado, menos desenho, menos código. Os dois convivem no mesmo formulário, porque o FormData lê os dois pelo name, e é comum um formulário ter os dois estilos em campos vizinhos.

Para reiniciar, cada estilo tem sua ferramenta: estado zerado no controlado, reset() ou key nova no não controlado. E a migração tem duas regras que evitam quase todo bug: nunca value sem onChange, e nunca começar o estado com undefined. Com essas duas, o campo obedece; sem elas, você passa a tarde achando que o React está quebrado.

Para lembrar

  • Controlado: value + onChange; o estado é o dono.
  • Não controlado: defaultValue + name; o DOM é o dono.
  • FormData lê todos os campos no onSubmit, pelo name.
  • Campo sem name não entra no FormData.
  • defaultValue vale uma vez; não sincroniza com o estado.
  • Controlado desenha a cada tecla: guarde o estado perto do campo.
  • Total, contagem e validação são contas — calcule no render, não guarde em outro estado.
  • key nova joga o elemento fora e o recria vazio; perde foco e seleção.
  • evento.target.reset() limpa o formulário sem trocar elementos.
  • Campo de arquivo é sempre não controlado.
