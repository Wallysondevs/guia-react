O useContext

A Ana já sabe criar o canal e abastecê-lo: a aula de introdução ao contexto deixou o ClienteContexto funcionando na loja dela. Agora o problema mudou de lado. O selo do balcão precisa mostrar o cliente do balcão, que é outro; o aviso do pedido precisa combinar o nome do cliente com o tema da tela; e o cartão de preço está sendo redesenhado a cada clique num botão que não tem nada a ver com ele. Nesta aula a Ana aprende a ler o canal com calma: de onde vem o valor, quem é desenhado de novo, e por que um objeto novo no lugar errado faz a tela inteira trabalhar à toa.

Você vai aprender
  • O que o useContext devolve e o que ele faz com o seu componente.
  • Por que, com dois providers do mesmo canal, o mais próximo é o que manda.
  • Como ler dois canais no mesmo componente e usar os dois valores juntos.
  • O que é a identidade de um valor e por que ela decide quem redesenha.
  • Como separar os dados das ações em dois canais.
  • Como o valor padrão do canal funciona como rede de segurança.
  • As armadilhas de leitura que não dão erro nenhum e só aparecem como tela estranha.

1. A cena: o selo do balcão e o selo da loja

A padaria da Ana tem dois pontos de venda: o balcão, onde o Bento atende, e a loja, onde a Ana mesma atende. O site mostra um selo com o nome de quem está atendendo, e o selo é o mesmo componente nas duas áreas. O canal do cliente já existe e já está abastecido com “Ana”. O selo do balcão, então, mostra “Ana” — e deveria mostrar “Bento”.

A primeira ideia é trocar o valor do provider de fora. Mas aí o selo da loja também vira “Bento”, e a Ana aparece como se fosse o Bento na própria loja. O que ela precisa é de dois valores ao mesmo tempo, um em cada ramo da tela. E é exatamente isso que o React permite: providers podem ser aninhados, e cada consumidor lê o provider mais próximo acima dele.

Antes da caixa, vale relembrar o desenho que a aula anterior deixou: createContext cria o canal, o .Provider abastece uma região da árvore, e o useContext abre a torneira dentro do componente. As três peças continuam as mesmas. O que esta aula destrincha é a terceira — a leitura —, que é onde mora a maior parte das surpresas.

2. O que o useContext devolve

Uma linha, e é só isso: const cliente = useContext(ClienteContexto). O que volta é o value do provider mais próximo acima daquele componente. Se não houver nenhum provider acima, volta o valor padrão que você passou para o createContext. Não existe “carregando”, não existe promessa, não existe espera: a leitura é síncrona e sempre devolve alguma coisa.

useContext
A função que lê o canal de dentro do componente: useContext(ClienteContexto). Vem do React e, nas caixas deste guia, já está no escopo.
consumidor
Todo componente que chama useContext. Ele vira assinante do canal: quando o valor muda, ele é desenhado de novo, mesmo que o pai dele não tenha mudado nada.
provider mais próximo
O .Provider mais perto do consumidor na árvore. Se houver dois, o de dentro ganha — o de fora continua valendo para o resto da tela.
valor padrão
O que o createContext recebeu. Só aparece quando não há provider acima. Não é um plano B para dado que ainda não chegou.
identidade do valor
O React compara o valor novo com o antigo usando igualdade de referência. Um objeto recriado a cada desenho é sempre “outro” valor, mesmo com o mesmo conteúdo.
consumo no topo
useContext é um hook: fica no topo do componente, junto dos outros, nunca dentro de um if ou de um laço.

Repare no termo “consumidor”. Ele não é enfeite: é o que explica o comportamento. Um componente que lê o canal entra numa lista de assinantes daquele canal. Quando o provider publica um valor diferente, o React percorre essa lista e desenha de novo cada assinante. O pai do selo não precisa saber de nada, e é por isso que o contexto funciona em pontos distantes da árvore.

A quarta linha é a que mais engana. Passar value={undefined} não faz o consumidor cair no padrão: o provider existe, então o valor publicado é undefined mesmo. Se o seu código faz cliente.nome, o resultado é um erro de leitura em cima de undefined. Para o padrão aparecer, não pode existir provider acima — não existe meio-termo.

3. A caixa: o provider mais próximo manda

Vamos ao caso do balcão. O App abastece o canal com “Ana”, e o mesmo SeloDoCliente aparece duas vezes: dentro do SetorDoBalcao e solto na loja. Os dois mostram “Ana”, porque os dois estão embaixo do mesmo provider. A missão é dar ao balcão o seu próprio provider, com o valor “Bento”, sem tocar no provider de fora.

Dentro de SetorDoBalcao, envolva o <SeloDoCliente /> com <ClienteContexto.Provider value="Bento"> e o fechamento correspondente. O selo da loja continua sendo “Ana”.

const ClienteContexto = createContext("visitante");

function SeloDoCliente() {
  const cliente = useContext(ClienteContexto);
  return <p>Cliente: {cliente}</p>;
}

function SetorDoBalcao() {
  return (
    <section>
      <h2>Balcão</h2>
      <SeloDoCliente />
    </section>
  );
}

function App() {
  return (
    <ClienteContexto.Provider value="Ana">
      <h1>Padaria da Ana</h1>
      <SetorDoBalcao />
      <SeloDoCliente />
    </ClienteContexto.Provider>
  );
}

Depois do conserto, o painel mostra dois selos com valores diferentes: “Bento” dentro da seção do balcão e “Ana” no fim. O componente é o mesmo, o canal é o mesmo, e a diferença está só na posição da árvore. É a resposta mais limpa para “preciso de dois valores do mesmo dado na mesma tela” — e, de quebra, é assim que se monta uma prévia de “como o visitante vê” dentro de um painel de administração.

Vale notar o que não muda: o provider de fora continua abastecendo tudo o que está fora do balcão. Aninhar não desliga o de cima; só cobre um pedaço. Se você esquecer de fechar o provider de dentro, o erro de compilação aparece na hora — e o painel avisa “não compilou”, com a linha.

Há um detalhe de versão que vale saber: no React 19, o próprio objeto do canal serve de provider, sem o .Provider, como em <ClienteContexto value="Bento">. As duas formas convivem e fazem a mesma coisa. Este guia usa .Provider porque é o que você encontra na maioria dos projetos e o que funciona também em versões anteriores.

4. Dois canais no mesmo componente

O aviso de pedido pronto precisa de duas informações que moram em canais separados: o nome do cliente e o tema da tela. Ler os dois é simplesmente chamar o hook duas vezes, uma linha para cada canal:

const tema = useContext(TemaContexto);
const cliente = useContext(ClienteContexto);
return <p className={"aviso tema-" + tema}>{cliente + ", seu pedido está pronto."}</p>;

A ordem dessas duas linhas é fixa: o React identifica cada hook pela posição na lista de chamadas do componente. Por isso as leituras ficam sempre no topo, junto do useState e dos outros hooks. Se você puser um useContext dentro de um if, os canais se misturam quando a condição mudar — e o React reclama com um erro que fala de “ordem dos hooks”. Essa história tem aula própria: As Regras dos Hooks.

O componente Aviso já lê o canal do cliente, mas o tema ele ignora. Leia também o TemaContexto e monte o className como className={"aviso tema-" + tema}.

const TemaContexto = createContext("claro");
const ClienteContexto = createContext("visitante");

function Aviso() {
  const cliente = useContext(ClienteContexto);
  return <p className="aviso">{cliente + ", seu pedido está pronto."}</p>;
}

function App() {
  return (
    <TemaContexto.Provider value="escuro">
      <ClienteContexto.Provider value="Ana">
        <Aviso />
      </ClienteContexto.Provider>
    </TemaContexto.Provider>
  );
}
<p class="aviso">Ana, seu pedido está pronto.</p>

Confira no painel: o parágrafo sai com class="aviso tema-escuro" e com o texto montado a partir do outro canal. Dois canais, dois hooks, um componente. Nada impede ler três ou quatro — mas se um componente começa a chamar seis canais, vale perguntar se ele não está fazendo trabalho demais.

Outro jeito de escrever o mesmo className é com molde de texto: {`aviso tema-${tema}`}. Escolha um e mantenha; misturar concatenação e molde na mesma função não quebra nada, mas atrapalha a leitura de quem vem depois.

5. A identidade do valor decide quem redesenha

Aqui está a parte que separa quem usa contexto de quem entende contexto. O React não compara o conteúdo do valor: ele compara a referência. Dois objetos com o mesmo nome e o mesmo preço, criados em desenhos diferentes, são valores diferentes para o React. E valor diferente quer dizer todos os assinantes desenhados de novo.

O caso clássico é passar o objeto direto no JSX: value={{ nome: "Padaria da Ana" }}. Esse objeto nasce de novo a cada desenho do App. Se o App desenha por qualquer outro motivo — um relógio, um campo de texto, um botão de horário —, o valor do canal muda de identidade e todo consumidor abaixo é chamado de volta, mesmo que nada tenha mudado no conteúdo.

A caixa prova isso com um contador. O Selo está embrulhado em memo, que é um aviso ao React: “só me desenhe de novo se as props mudarem”. Como o Selo não recebe prop nenhuma, sem contexto ele nunca redesenharia. Mas ele lê o canal, e o canal entrega um objeto novo a cada clique no botão do horário. Resultado: o selo desenha de novo, e o contador sobe.

Clique em “Trocar horário”: o selo conta 2 desenhos, porque o objeto do value é novo a cada desenho. Guarde o objeto em const loja = useMemo(() => ({ nome: "Padaria da Ana" }), []) e passe value={loja}.

const LojaContexto = createContext(null);
let desenhos = 0;

const Selo = memo(function Selo() {
  desenhos = desenhos + 1;
  const loja = useContext(LojaContexto);
  return <p>Selo de {loja.nome} — desenhos do selo: {desenhos}</p>;
});

function App() {
  const [hora, setHora] = useState("6h");
  return (
    <LojaContexto.Provider value={{ nome: "Padaria da Ana" }}>
      <button onClick={() => setHora(hora === "6h" ? "7h" : "6h")}>Trocar horário</button>
      <p>Aberto às {hora}</p>
      <Selo />
    </LojaContexto.Provider>
  );
}

Com o useMemo, o objeto é criado uma vez e reaproveitado em todos os desenhos. O valor do canal passa a ter sempre a mesma identidade, então o memo segura o selo: o contador fica em 1 enquanto o horário muda à vontade. O useMemo recebe uma função que devolve o valor e uma lista de dependências: se alguma delas mudar, o valor é criado de novo. Lista vazia quer dizer “nunca recrie”.

Se o objeto for realmente constante, nem useMemo é necessário: crie fora do componente, const LOJA = { nome: "Padaria da Ana" }, no topo do arquivo. Aí a identidade é a mesma para sempre, e o problema nem nasce. O useMemo entra quando o objeto depende de estado ou de props.

Uma ressalva honesta: o contador no meio do texto é um truque de aula, porque ele conta desenhos dentro do corpo do componente. Em código de produção você não faz isso. O que fica é a lição: o valor do canal é comparado por referência, então objetos, arrays e funções criados durante o desenho merecem atenção.

6. Separar dados de ações

O canal do cliente carrega duas coisas diferentes: o nome (que muda quando alguém entra ou sai) e a função entrar (que é sempre a mesma durante a vida do componente). Juntar as duas no mesmo objeto significa que qualquer mudança de nome troca a identidade do objeto inteiro — e todo consumidor redesenha, inclusive o botão que só precisa da função.

A saída é dividir em dois canais: um para os dados, outro para as ações. O provider de dados muda quando o cliente muda; o de ações fica estável, porque as funções que vêm do useState já são estáveis. Quem só chama a ação não é incomodado pelo dado novo.

const ClienteContexto = createContext(null);
const AcoesContexto = createContext(null);

function LojaProvider({ children }) {
  const [cliente, setCliente] = useState("visitante");

  function entrar(nome) {
    setCliente(nome);
  }

  return (
    <AcoesContexto.Provider value={{ entrar }}>
      <ClienteContexto.Provider value={cliente}>
        {children}
      </ClienteContexto.Provider>
    </AcoesContexto.Provider>
  );
}

O objeto { entrar } também é novo a cada desenho, e isso é um detalhe que a aula de useMemo resolve. Para quem está começando, o ganho já aparece com dois canais simples assim: o consumidor escolhe o que quer acompanhar. Quem só lê o nome não redesenha quando a ação muda, e quem só chama a ação não redesenha quando o nome muda.

Esse padrão tem nome na comunidade — dados e ações separados — e é a diferença entre um contexto que escala e um contexto que vira um balde. Quando o canal começa a ter seis campos com ritmos de mudança diferentes, a pergunta certa não é “como otimizar”, e sim “por que tudo isso é o mesmo canal”.

7. O valor padrão é a rede de segurança

Um canal criado com createContext(null) devolve null para quem estiver fora do provider. Isso não é um problema: é a chance de falhar com uma mensagem clara, em vez de mostrar “null” na tela e ninguém entender por quê. O truque é fazer a checagem em um lugar só — dentro de um hook próprio:

const ClienteContexto = createContext(null);

export function useCliente() {
  const cliente = useContext(ClienteContexto);
  if (cliente === null) {
    throw new Error("useCliente precisa estar dentro de LojaProvider");
  }
  return cliente;
}

Agora quem usa o dado chama useCliente() e nunca vê null. Se alguém montar o componente fora do provider, o erro aparece na hora, com o nome do problema. É a diferença entre descobrir o defeito em dois minutos e descobrir três telas depois. O assunto de hook próprio tem aula inteira em Hooks Próprios; aqui basta reconhecer o formato.

Sem essa rede, o sintoma é um erro de leitura no console do navegador, apontando para a linha onde você tentou acessar uma propriedade de null:

Uncaught TypeError: Cannot read properties of null (reading 'nome')

Essa mensagem quer dizer uma coisa só: o componente está lendo o canal fora da área abastecida, ou o provider está passando null. Antes de suspeitar do consumidor, suba a árvore e procure o provider. E note que o padrão também serve como documentação: createContext(null) diz “aqui não existe valor razoável por conta própria”, enquanto createContext("visitante") diz “fora do provider, trate como visitante”.

8. As armadilhas da leitura

Quase todo problema de useContext cai em uma destas linhas. Nenhuma delas dá aviso no console: todas aparecem como tela com o valor errado, ou como tela que atualiza demais.

A quarta linha merece um exemplo, porque é a que mais engana quem vem de outras linguagens. Se o provider faz cliente.nome = "Bento" e publica o mesmo objeto, o React compara a referência, encontra a mesma e conclui que nada mudou. A tela fica parada mesmo com o dado alterado. Em React, dado que muda é dado novo: setCliente({ ...cliente, nome: "Bento" }), e não uma alteração por dentro.

No console do navegador, um consumidor que registra cada desenho mostra bem o efeito da identidade. Com o objeto recriado a cada clique, cada clique imprime uma linha nova:

desenho do selo: 1
desenho do selo: 2
desenho do selo: 3

Com o valor guardado, o número para de subir. Esse é o teste mais rápido para saber se o seu provider está publicando um valor estável: abra o console, clique em algo que não tem relação com o dado e veja se o consumidor aparece de novo.

9. Cenários do dia a dia

Cenário 1: a prévia da loja dentro do painel

A Ana queria ver como a loja fica para quem não entrou, sem sair da conta dela. Dois providers do mesmo canal resolveram: o painel fica com “Ana”, e a prévia, dentro de um provider com “visitante”, desenha como visitante. Nenhum componente foi duplicado, e o botão de sair continua funcionando nos dois lugares.

Cenário 2: o selo que redesenhava a cada letra

O campo de busca da Ana guardava o texto no App, e o provider do cliente publicava value={{ nome: cliente }} — um objeto novo a cada tecla. O selo do rodapé, que só mostrava o nome, redesenhava a cada letra. Guardar o objeto com useMemo, dependendo de cliente, resolveu. O sintoma era “o site está pesado”, e a causa era uma chave a mais no provider.

Cenário 3: o cliente que nunca aparecia

Ela criou o ClienteContexto dentro do App, abasteceu, e o selo continuou mostrando “visitante”. O canal era criado de novo a cada desenho: o provider abastecia um canal, e o consumidor lia outro. Mover o createContext para o topo do arquivo acabou com o mistério — e é a mesma regra da aula anterior, agora vista do lado de quem lê.

11. Resumo

useContext é a leitura do canal, e a leitura tem consequências. Ele devolve o valor do provider mais próximo, ou o padrão quando não existe provider acima — e transforma o componente em assinante: quando o valor publicado muda de identidade, o componente é desenhado de novo. Providers aninhados resolvem o caso de dois valores do mesmo dado na mesma tela, e o de dentro é sempre o que ganha.

A parte que dá trabalho não é a sintaxe, é a identidade. Objetos, arrays e funções criados durante o desenho são valores novos a cada desenho, e todo consumidor paga a conta. Guardar o objeto com useMemo ou criá-lo fora do componente mantém a referência estável e deixa o React fazer o trabalho de menos. E separar dados de ações em dois canais evita que quem só chama uma função seja arrastado por uma mudança de nome.

Por último, leia sempre no topo. useContext é um hook como os outros: ordem fixa, fora de condições, fora de laços. Se você precisar do valor dentro de um if, leia antes e use a variável dentro — o resultado é o mesmo e a ordem continua previsível.

Uma nota sobre o React 19, para quando você encontrar em código alheio: a função use lê um canal (e uma promessa) e pode ser chamada dentro de condições, ao contrário do useContext. É uma alternativa nova, não um substituto obrigatório. Enquanto o seu código não precisar dela, o useContext continua sendo a forma mais direta e a que todo exemplo usa.

Para lembrar

  • useContext(Canal) devolve o valor do provider mais próximo acima.
  • Sem provider acima, volta o valor padrão do createContext.
  • Provider com value={undefined} publica undefined; não cai no padrão.
  • Dois providers do mesmo canal: o de dentro cobre só o ramo dele.
  • Ler dois canais é chamar o hook duas vezes, no topo do componente.
  • O React compara o valor por referência: objeto novo a cada desenho redesenha todos os consumidores.
  • Objeto constante: crie fora do componente; dependente de estado: useMemo.
  • Separar dados e ações em dois canais deixa cada consumidor acompanhar só o que usa.
  • createContext(null) mais um hook que lança erro é a rede de segurança do canal.
  • Nunca altere o objeto do valor no lugar: crie um novo, com as propriedades novas.
