Render Props

A Ana tem três lugares no site que mostram a mesma lista de pães: a vitrine da página inicial, os cartões da página de encomendas e a tabela do painel dela. O laço que percorre a lista é sempre igual; o desenho de cada pão muda em cada lugar. Nesta aula ela aprende a passar o desenho como uma função, do lado de fora do componente, e a deixar dentro dele só o que não muda: o laço, o estado e a decisão. É o padrão que o React chama de render props.

Você vai aprender
  • Por que um componente que desenha tudo precisa de uma prop nova a cada variação.
  • O que é uma render prop: uma prop cujo valor é uma função que devolve JSX.
  • Como o componente chama essa função, uma vez por item, e o que ele passa para ela.
  • O mesmo padrão escrito com children, quando o desenho fica entre as tags.
  • A diferença entre {desenhar}, {desenhar(p)} e <desenhar />.
  • Como o estado pode morar no componente enquanto o botão mora na página.
  • Por que os hooks tomaram parte desse trabalho e onde as render props continuam valendo.

1. A cena: o mesmo laço, três desenhos

Na aula de Listas com map, a Ana aprendeu a transformar um array de pães em uma lista de elementos. Na aula de Composição, aprendeu a colocar um pedaço de tela dentro de outro pelo children. Agora as duas ideias se encontram e aparece um problema novo, bem concreto: o laço é sempre o mesmo, mas o desenho de cada item muda.

Na página inicial, cada pão vira um <li> com o nome. Na página de encomendas, vira um cartão com nome, preço e um botão. No painel dela, vira uma linha de tabela com nome, estoque e um aviso. Três desenhos diferentes, três map copiados no código. Quando ela muda a ordem dos pães, precisa mudar nos três lugares.

A primeira tentativa é a mais natural: extrair um componente Lista que recebe os pães e desenha. Só que aí o componente precisa saber que na página de encomendas existe preço, que no painel existe estoque, que a vitrine não tem botão. Ela começa a encher o componente de props: mostrarPreco, mostrarBotao, mostrarEstoque, modoCartao. Cada página nova pede mais uma prop. É o caminho que a aula de Componente Reutilizável já avisou que não termina bem.

O que ela quer de verdade é separar duas responsabilidades. Uma: percorrer a lista e dar uma key para cada item — isso é igual em todo lugar. Outra: decidir o que aparece na tela para cada pão — isso é diferente em cada lugar. O componente deve ficar com a primeira; a página, com a segunda.

2. O que falta quando o componente desenha tudo

Repare no que a Lista precisa saber para desenhar um cartão: o nome do pão, o preço, se tem botão, o texto do botão, o que o botão faz quando alguém clica. Isso tudo é informação da página de encomendas, não da lista. Um componente que recebe dados e também decide o desenho acaba virando uma cópia da página inteira, com um nome mais genérico.

Existe uma saída que não exige inventar props: passar o desenho pronto. Já dá para fazer isso com elementos — é o que a aula de composição mostrou, mandando <p>Sai às 6h</p> para dentro de uma moldura. Só que um elemento já está desenhado: ele não sabe que existem cinco pães diferentes. Falta o componente poder dizer "desenhe este aqui, agora" para cada item.

E é exatamente isso que uma função faz. Uma função é uma receita guardada, que só vira tela quando alguém chama. Se a página passa a receita e a lista chama a receita item por item, os dois lados ficam com o que é deles: a lista percorre, a página desenha. O React chama esse arranjo de render prop: uma prop cujo valor é uma função que devolve JSX.

render prop
Uma prop cujo valor é uma função que devolve JSX, em vez de um texto ou de um elemento pronto. O nome da prop é escolha sua: desenhar, render, item.
função de desenho
A função que a página passa. Recebe o que o componente mandar (um pão, um total, um par de valores) e devolve o JSX daquele pedaço.
chamar
Usar a função com parênteses: desenhar(pao). Isso executa a receita e devolve o JSX, que o React então desenha.
inversão de controle
O componente deixa de decidir o desenho e passa essa decisão para quem o usa. Quem chama manda no "como"; o componente cuida do "quando" e do "quantas vezes".
headless
Nome que se dá a um componente sem visual próprio: ele só entrega dados e comportamento, e o desenho vem de fora. Uma lista com render prop é um componente assim.

3. A primeira render prop: uma função no lugar de um item

Olhe o código abaixo. A Lista recebe os pães e uma prop chamada desenhar. Dentro do map, ela chama desenhar(p) e entrega o resultado ao React. O Fragment com key em volta existe porque a função devolve um elemento e a key precisa ficar no item que o map produz — quem percorre a lista é quem sabe qual é a identidade de cada linha.

A função desenhar está escrita mas ignora o pão que recebe: os dois itens mostram a mesma palavra. Use o parâmetro para mostrar o nome e o preço de cada um e clique em Rodar.

function Lista({ itens, desenhar }) {
  return (
    <ul>
      {itens.map((p) => (
        <Fragment key={p.id}>{desenhar(p)}</Fragment>
      ))}
    </ul>
  );
}

function App() {
  const paes = [
    { id: 1, nome: "Pão francês", preco: "R$ 7,00" },
    { id: 2, nome: "Broa de milho", preco: "R$ 9,00" }
  ];
  return <Lista itens={paes} desenhar={() => <li>pão</li>} />;
}
<ul>
  <li>pão</li>
  <li>pão</li>
</ul>

  return <Lista itens={paes} desenhar={(p) => <li>{p.nome} — {p.preco}</li>} />;
}

O painel mostra dois <li> com nome e preço. Repare no caminho: o App não desenhou nada da lista. Ele entregou uma função. A Lista percorreu os pães e chamou a função duas vezes, uma por pão. Cada chamada devolveu um <li> diferente. O React recebeu esses elementos e montou a página.

Quem manda no quê: itens é dado, desenhar é comportamento que produz desenho. Os dois são props comuns aos olhos do React — a diferença é que uma chega como array e a outra chega como função. Nada mágico, nada novo na linguagem: só uma função guardada dentro de um objeto de props.

Um detalhe que evita bug: a função de desenho não deve ter efeito colateral. Ela é chamada durante o desenho do componente, como um cálculo. Chamar setAlgumaCoisa dali dentro pode virar laço infinito; buscar dados dali dentro vira pedido repetido. Ela recebe, devolve JSX e acabou.

4. O mesmo padrão pelo children

Escrever desenhar={...} funciona, mas tem uma posição mais confortável para a função: entre as tags do componente. Quando você escreve <Vitrine>{...}</Vitrine>, o que está ali dentro chega como children — e nada impede que seja uma função. O componente só precisa chamá-la com parênteses, como qualquer outra.

A Vitrine chama children(p) e já recebe o pão certo, mas o cartão só mostra o nome. Acrescente o preço, separado por um traço, e clique em Rodar.

function Vitrine({ itens, children }) {
  return (
    <div className="vitrine">
      {itens.map((p) => (
        <Fragment key={p.id}>{children(p)}</Fragment>
      ))}
    </div>
  );
}

function App() {
  const doces = [
    { id: 1, nome: "Pão de queijo", preco: "R$ 3,00" },
    { id: 2, nome: "Bolo de fubá", preco: "R$ 5,00" }
  ];
  return (
    <Vitrine itens={doces}>
      {(p) => <p className="cartao">{p.nome}</p>}
    </Vitrine>
  );
}
<div class="vitrine">

Note as duas chaves: {(p) => ...} está dentro de { } porque é uma expressão JavaScript, e o corpo da função devolve JSX. Quem lê rápido acha que é um elemento dentro do componente; não é. É uma função esperando ser chamada. A Vitrine chama essa função uma vez para cada doce, e o resultado aparece no painel como dois parágrafos com a classe cartao.

Este formato — children como função — é o mesmo padrão com outra roupa. A vantagem é de leitura: o desenho fica onde você procuraria por ele, embaixo do componente que o usa. A desvantagem é que só existe um children: se você precisar de dois desenhos diferentes na mesma chamada, volta a usar props com nome.

Na aula de O children, o conteúdo entre as tags era um parágrafo. Aqui é uma função. O React não liga: para ele, children é só mais uma prop, e o valor pode ser texto, elemento, lista de elementos ou função. Quem decide o que fazer com esse valor é o componente que o recebe.

Quer ver com os próprios olhos que a função roda uma vez por item? Ponha um console.log dentro do laço, antes de chamar children:

function Vitrine({ itens, children }) {
  return (
    <div>
      {itens.map((p) => {
        console.log("desenhando " + p.nome);
        return <Fragment key={p.id}>{children(p)}</Fragment>;
      })}
    </div>
  );
}

Com os dois doces da caixa e esse log no lugar, o painel mostra as duas linhas, na ordem do array:

console: desenhando Pão de queijo
console: desenhando Bolo de fubá

Duas linhas, dois itens: o map passou duas vezes e sua função foi chamada duas vezes. Se o console mostra uma linha só, o array tem um item — ou o map está no lugar errado. Se mostra mais linhas do que itens, alguém está chamando a função fora do laço.

5. Onde a função é chamada (e onde não é)

Este é o ponto em que quase todo mundo tropeça, e o sintoma é sempre o mesmo: um pedaço da tela que não aparece, sem erro. A confusão nasce porque desenhar é uma função, e em JSX função aparece de três jeitos com resultados bem diferentes. Vale desenhar os três lado a lado.

A terceira linha é a mais traiçoeira, porque parece elegante. O React separa componente de tag pela primeira letra do nome — a mesma regra da primeira aula. <desenhar /> começa com minúscula, então vira uma tag qualquer, que o navegador aceita e desenha vazia. Nada acontece, nada reclama. Se a sua função de desenho tem nome minúsculo e você quiser usá-la como componente, ela precisa ser outra coisa: uma função que devolve um componente, como no HOC da aula de Higher-Order Components.

Para saber o que chegou, um console.log resolve mais rápido do que reler o arquivo:

function Lista({ itens, desenhar }) {
  console.log("typeof desenhar: " + typeof desenhar);
  console.log("quantos itens: " + itens.length);
  return <ul>{itens.map((p) => <Fragment key={p.id}>{desenhar(p)}</Fragment>)}</ul>;
}

Com dois pães, o console do navegador mostra:

typeof desenhar: function
quantos itens: 2

Esse hábito — imprimir o tipo antes de suspeitar do JSX — economiza muito tempo. Se o console diz typeof desenhar: undefined, o problema está na chamada, não no componente. Se diz object, você passou um elemento onde o componente espera uma função, e a tela vai ficar vazia no lugar daquele trecho.

6. A vantagem de verdade: o estado fica no componente

Até aqui a render prop economizou código. O ganho grande aparece quando o componente tem estado. Aí a divisão fica clara: o componente guarda o número e a regra de mudar; a página decide onde o número aparece e onde fica o botão. O componente não sabe se existe botão. A página não sabe como o número muda.

A Fornada guarda o total e entrega, para a função de desenho, o número e a ação de assar mais um. Mostre um botão "Assar mais um" que chame essa ação.

function Fornada({ children }) {
  const [paes, setPaes] = useState(2);

  return (
    <div>
      <h2>Fornada</h2>
      {children(paes, () => setPaes(paes + 1))}
    </div>
  );
}

function App() {
  return <Fornada>{(total) => <p>{total} pães na bandeja</p>}</Fornada>;
}
<div>
  <h2>Fornada</h2>
  <p>2 pães na bandeja</p>
</div>

  return (
    <div>
      <h2>Fornada</h2>
      {children(paes, () => setPaes(paes + 1))}
    </div>

function App() {
  return (
    <Fornada>
      {(total, assar) => (
        <div>
          <p>{total} pães na bandeja</p>
          <button onClick={assar}>Assar mais um</button>
        </div>
      )}
    </Fornada>
  );
}

Clique no botão e o painel passa a mostrar três pães. O clique não tocou no estado da Fornada diretamente: chamou a função que ela entregou, e essa função chamou setPaes. O estado continua morando dentro do componente — a página só recebeu a chave.

Por que não deixar a página guardar o estado? Porque aí cada página que quisesse uma fornada reescreveria a regra, e a regra é justamente o que se quer reaproveitar. Esse é o tipo de componente que bibliotecas chamam de headless: ele não tem visual próprio. Ele entrega dados e comportamento; o visual é seu.

Uma armadilha de hooks vale o aviso: nunca chame useState dentro da função de desenho. A função não é um componente — o React não abre um espaço de estado para ela. Hooks só no começo de componentes e de hooks próprios — uma regra que o guia destrincha na parte de hooks, quando chegar a vez dela.

7. Render props × hooks: por que hoje se usa menos

Vale saber a história, porque ela explica por que você vê pouco esse padrão em código novo. Antes de 2019, não existia useState. A única forma de reaproveitar lógica com estado era um componente que guardava o estado e entregava os valores para uma função de desenho. Quase toda biblioteca da época tinha uma API assim. O React Router tinha a prop render da Route; as animações do react-motion entregavam valores interpolados por função.

Com os hooks, a mesma conta ficou direta. Se você quer um contador, escreva useState no seu componente. Não precisa de um componente de fora segurando o número. Por isso as render props encolheram: viraram ferramenta de caso específico, não o jeito padrão de compartilhar lógica.

Onde elas continuam boas? Quando o componente precisa controlar quando e com que dados a função é chamada, e você precisa do controle total do desenho. Uma lista virtualizada que só desenha as linhas visíveis, um medidor que entrega a largura medida do elemento, um campo de busca que entrega o resultado pronto e deixa você montar cada sugestão. Nesses casos, a função de desenho é mais expressiva do que uma pilha de props.

8. Os tropeços

Chamar a função cedo demais. Se o App chama desenhar(paes[0]) e passa o resultado, a lista recebe um elemento só e desenha o mesmo em todas as linhas. A função tem de ser chamada pelo componente, dentro do laço, com o item daquele momento.

Usar chaves no lugar de parênteses. Uma seta com chaves precisa de return. Sem ele, a função devolve undefined e a lista fica vazia:

// errado: as chaves escondem o JSX
desenhar={(p) => { <li>{p.nome}</li> }}

// certo: parênteses devolvem o JSX
desenhar={(p) => (<li>{p.nome}</li>)}

// certo também: return explícito
desenhar={(p) => { return <li>{p.nome}</li>; }}

Devolver mais de um elemento. A função de desenho devolve um elemento, como qualquer componente. Se o cartão tem título, preço e botão, embrulhe tudo em uma <div> ou em um Fragment. Um return com dois irmãos soltos não compila, e a mensagem fala em elementos adjacentes.

Repassar a key para dentro da função. A key não chega ao componente como prop. Quem percorre a lista é quem coloca a key, no elemento que o map devolve — por isso o Fragment em volta de {desenhar(p)}. Se você deixar a key para a função de desenho, o React reclama no console de desenvolvimento e o estado das linhas passa a se misturar. A história completa está em A key.

Recriar a função e culpar o componente. Cada desenho do App cria uma função nova, e isso é normal. Só vira problema quando o componente é embrulhado em memo e você espera que ele pare de redesenhar: a função nova invalida a comparação. Se um dia precisar, a saída é useCallback, assunto de desempenho mais adiante.

9. Cenários do dia a dia

Cenário 1: a lista aparece vazia

A Ana trocou desenhar={...} por desenhar={Cartao} para "ficar mais curto". O componente passou a chamar desenhar(p) — e Cartao é um componente, que espera um objeto de props, não um pão solto. O resultado foi uma tela em branco. Componente e função de desenho têm assinaturas diferentes: um recebe props, o outro recebe o que o componente decidir mandar. Se você tem um componente e quer usá-lo por item, escreva desenhar={(p) => <Cartao pao={p} />}.

Cenário 2: o botão aparece no lugar errado

Ela queria o botão "Adicionar" embaixo do preço, mas ele ficou antes do nome. Isso não é problema de estado: é o lugar onde ela escreveu, dentro da função de desenho. A ordem dos elementos é exatamente a ordem do seu JSX. O botão em si continua funcionando porque a ação vem de fora, pela função entregue pelo componente — e essa parte ela não precisa reescrever quando muda o desenho.

Cenário 3: dois desenhos na mesma tela

Na página de encomendas ela quer uma lista de cartões e, embaixo, a mesma lista em tabela. Com children só cabe um desenho por chamada. A saída é usar duas props com nome — desenharCartao e desenharLinha — ou chamar o componente duas vezes, uma para cada formato. Props com nome existem justamente para quando um slot não basta; a aula de Slots com children aprofunda essa escolha.

11. Resumo

Render prop é uma prop cujo valor é uma função que devolve JSX. O componente percorre os dados e chama essa função item por item, passando o que ele sabe; a página decide o desenho com o que recebe. O laço, a key e o estado ficam no componente; o visual, fora dele. O mesmo padrão aparece com children quando a função é escrita entre as tags.

O que faz esse arranjo funcionar é uma coisa só: em JavaScript, função é um valor como outro qualquer. Pode ir dentro de um objeto de props, pode ser guardada em uma variável, pode ser chamada depois. O React não inventou nada disso — só escolheu chamar a sua função no momento certo do desenho. Quando você entende que {desenhar(p)} executa e {desenhar} só entrega, a maioria dos "não apareceu nada" deixa de ser mistério.

Hoje os hooks cobrem boa parte do que as render props faziam: estado compartilhado virou useState, e lógica repetida virou hook próprio. O padrão continua útil quando o componente precisa mandar no quando — listas grandes, medidas, bibliotecas que dão controle do desenho. E continua ótimo para aprender: ele mostra, de forma crua, a divisão entre dado, comportamento e desenho que sustenta todo o resto do React.

Guarde também o critério de escolha: se o conteúdo já está pronto, passe um elemento; se o componente precisa produzir um pedaço por item, passe uma função; se são vários lugares reservados, use props com nome. Três perguntas, três respostas diferentes — e nenhuma delas exige decorar nome de API.

Para lembrar

  • Render prop é uma prop que recebe função; a função devolve JSX.
  • O componente chama a função uma vez por item, com o item como argumento.
  • children também pode ser função: <Lista>{(p) => ...}</Lista>.
  • {desenhar(p)} chama; {desenhar} não desenha nada; <desenhar /> vira tag vazia.
  • A key fica no elemento que o map devolve, não dentro da função de desenho.
  • A função de desenho é pura: sem hook, sem efeito colateral, sem buscar dados.
  • Seta com chaves precisa de return; com parênteses, o JSX volta sozinho.
  • Estado e comportamento ficam no componente; o desenho fica em quem chama.
  • Um slot só: children. Dois ou mais: props com nome.
  • Hooks cobrem a maior parte dos casos; render props continuam valendo quando o componente manda no quando.
