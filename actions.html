As Actions

O formulário de encomenda da Ana tem quatro campos, três estados, um preventDefault e quarenta linhas para fazer uma coisa só: ler o que a pessoa digitou e mandar. No React 19, esse trabalho cabe em um atributo. Nesta aula ela conhece as Actions: a prop action do formulário recebendo uma função, os campos chegando prontos pelo FormData e o formulário se limpando sozinho depois do envio.

Você vai aprender
  • O que muda quando o formulário chama uma função em vez de escutar um evento.
  • Como ler os campos pelo FormData, sem um estado para cada um.
  • A dar uma ação diferente para cada botão do mesmo formulário.
  • Por que o formulário se limpa sozinho depois do envio.
  • Como mostrar “enviando…” com o useFormStatus.
  • A diferença entre ação de cliente e ação de servidor.
  • As armadilhas: campo controlado, botão sem type, erro não tratado.

1. A cena: quarenta linhas para uma encomenda

O formulário de encomenda da Ana tem quatro campos: nome, pão, quantidade e observação. Para cada campo, um useState; para o envio, um useState de “enviando”; para o onSubmit, um preventDefault e uma chamada assíncrona. Funciona — e tem quarenta linhas que ela relê toda vez que precisa mexer em alguma coisa.

O React 19 traz para esse caso uma ideia simples: em vez de o formulário avisar “aconteceu um envio”, ele chama uma função — a ação. O atributo action, que no HTML é o endereço para onde o formulário vai, passa a aceitar uma função: o React intercepta o envio, monta os dados e chama a sua função com eles. Nada de preventDefault, porque ninguém está navegando.

A diferença não é só de sintaxe. Quando o React controla o envio, ele sabe quando a ação começou e quando terminou — e usa isso para três coisas que antes eram suas: desabilitar o formulário enquanto roda, limpar os campos depois do sucesso e ligar o aviso de “enviando” ao botão certo. Uma delas você vê nesta aula; as outras duas são o assunto das próximas.

Vale o aviso de sempre: action não substitui formulário controlado. Se você precisa validar a cada tecla, formatar o telefone enquanto digita ou mostrar a contagem de caracteres, o estado por campo continua sendo o caminho. A ação brilha no envio — ler os campos de uma vez, mandar, limpar, avisar.

2. O que é uma Action

Uma ação é uma função que recebe os dados do formulário e faz o trabalho: chamar a API, gravar, responder. Ela pode ser assíncrona, e o React espera a promessa terminar antes de considerar o envio concluído — é essa espera que permite desabilitar o botão e limpar o formulário na hora certa.

action
A prop do form que recebe uma função. Quando alguém envia, o React chama essa função com um FormData.
FormData
O pacote de campos do formulário, montado pelo navegador. Lê-se com dados.get("nome").
ação assíncrona
Função async passada para action. O React acompanha a promessa até o fim.
formAction
A mesma ideia no botão: cada botão de envio aponta para a sua própria ação.
pendente
O intervalo entre o envio e a resposta. É o que o useFormStatus informa ao botão.

A tabela abaixo mostra o que sai do seu código quando o formulário passa a usar uma ação. Repare que a coluna da direita não é “menos poder”: é o mesmo trabalho, feito pelo React, com menos lugares para errar.

Um detalhe de leitura que vai aparecer no painel de todas as caixas: o React troca o action do HTML por um guarda, aquela linha enorme começando com javascript:throw new Error(…). É de propósito. Sem esse guarda, um envio que escapasse do controle do React faria o navegador navegar para outra página e você perderia a tela. 3. Os campos chegam pelo FormData

No jeito antigo, o componente precisa saber o que está em cada campo, e para isso mantém um estado por campo, com value e onChange. Na ação, quem guarda o valor é o próprio navegador: o campo tem name, e o FormData entrega tudo junto no envio. O componente só precisa do que ele mostra depois.

A caixa começa com o tropeço clássico: o campo não é controlado e o componente lê um estado que ninguém atualiza. O texto chega ao campo, o estado continua vazio, e o recado sai sem o nome. A missão é passar o envio para uma ação.

O campo tem name, mas o componente lê o estado nome, que ninguém atualiza — o recado sai vazio. Transforme o envio em uma action e leia o valor com dados.get("nome").

function App() {
  const [nome, setNome] = useState("");
  const [recado, setRecado] = useState("nada");

  function enviar() {
    setRecado("recebido: " + nome);
  }

  return (
    <div>
      <input name="nome" />
      <button onClick={enviar}>Encomendar</button>
      <p>{recado}</p>
    </div>
  );
}

function App() {
  const [recado, setRecado] = useState("nada");

  async function enviar(dados) {
    setRecado("recebido: " + dados.get("nome"));
  }

  return (
    <form action={enviar}>
      <input name="nome" />
      <button type="submit">Encomendar</button>
      <p>{recado}</p>
    </form>
  );
}

Na solução, digitar “Maria” e clicar já mostra recebido: Maria. O estado nome sumiu do código: quem guarda o valor é o campo, e a ação recebe o pacote no momento do envio. É por isso que esse estilo é chamado de formulário não controlado — o React não acompanha cada tecla, só o resultado.

Duas regras práticas para o FormData. A primeira: todo campo precisa de name; sem ele, o valor não entra no pacote e get devolve null. A segunda: tudo o que sai do FormData é texto — quantidade chega como "20", não como 20. Converta na ação, com Number(dados.get("quantidade")), antes de somar.

No console do navegador, o pacote é fácil de inspecionar, e vale conhecer os métodos: get traz um campo, getAll traz todos os de mesmo nome (útil para caixas de seleção múltiplas) e has diz se o campo veio.

4. Cada botão com a sua ação

Um formulário com dois botões — “encomendar” e “apagar” — é comum e sempre deu trabalho: os dois enviam, e o onSubmit precisa descobrir qual foi clicado. O React 19 resolve com formAction: a ação pode ficar no botão, e cada botão aponta para a sua.

O que chega na ação é o mesmo FormData do formulário inteiro. A diferença é qual função roda. É a solução mais limpa para o par “salvar” e “excluir” sem gambiarra de estado dizendo qual botão foi pressionado.

Os dois botões fazem a mesma coisa: o onSubmit sempre registra uma encomenda. Dê a cada botão a sua ação com formAction, para “Apagar” chamar a função apagar.

function App() {
  const [recado, setRecado] = useState("nada");

  async function encomendar(dados) {
    setRecado("encomendado: " + dados.get("nome"));
  }

  async function apagar(dados) {
    setRecado("apagado: " + dados.get("nome"));
  }

  function enviar(evento) {
    evento.preventDefault();
    encomendar(new FormData(evento.target));
  }

  return (
    <form onSubmit={enviar}>
      <input name="nome" />
      <button className="encomendar" type="submit">Encomendar</button>
      <button className="apagar" type="button">Apagar</button>
      <p>{recado}</p>
    </form>
  );
}

No código inicial, o botão “Apagar” tem type="button" para não enviar — e por isso não faz nada. Na solução, os dois viram botões de envio com ações diferentes: clicar em “Apagar” com “Maria” no campo mostra apagado: Maria, sem nenhum estado dizendo qual botão foi clicado.

Repare em um detalhe: os botões da solução não têm type escrito. Dentro de um formulário, o type padrão de um botão é submit, então ambos enviam — e é o formAction que decide para onde. Isso só é verdade para botões de envio; um <button type="button"> continua sendo o certo para o botão que não envia nada, como “limpar o formulário”.

E quando a ação não é de envio? Se o botão abre um modal ou alterna uma aba, ele não deveria estar dentro de um formulário, ou deveria ter type="button". Ação é para o que grava, envia, apaga — o que mexe em dados do outro lado.

5. O formulário se limpa sozinho

Este é o comportamento que mais surpreende e mais economiza linha. Quando a ação termina sem erro, o React limpa os campos não controlados do formulário. Não é mágica: ele sabe que o envio acabou, sabe quais campos eram do formulário e devolve cada um ao valor inicial do HTML.

A caixa compara os dois mundos. No código inicial, o envio lê o FormData e mostra o recado, mas o campo continua com o texto — quem envia duas vezes manda “Maria” duas vezes. Na solução, o mesmo envio vira uma ação e o campo se limpa depois do primeiro: o segundo clique manda vazio.

Depois de enviar, o campo continua com o nome digitado, e o segundo envio repete a mesma encomenda. Troque o onSubmit por action e veja o React limpar o campo sozinho: o segundo clique deve mostrar recebido: (vazio).

function App() {
  const [recado, setRecado] = useState("nada");

  function enviar(evento) {
    evento.preventDefault();
    const dados = new FormData(evento.target);
    const nome = String(dados.get("nome") || "");
    setRecado("recebido: " + (nome || "(vazio)"));
  }

  return (
    <form onSubmit={enviar}>
      <input name="nome" />
      <button type="submit">Encomendar</button>
      <p>{recado}</p>
    </form>
  );
}

O painel inicial mostra recebido: Maria duas vezes, porque o campo guarda o que foi digitado. Na solução, o primeiro clique mostra recebido: Maria e o segundo mostra recebido: (vazio): a limpeza aconteceu entre os dois, feita pelo React.

A ressalva importante: a limpeza vale para campos não controlados. Se o campo tem value amarrado a um estado, o React não mexe nele — o valor continua vindo do estado, e limpar é trabalho seu. É por isso que misturar os dois estilos no mesmo formulário costuma confundir: metade dos campos se limpa, metade não.

Outra ressalva: a limpeza acontece quando a ação termina sem erro. Se a ação lança uma exceção, o React considera o envio falho e os campos ficam como estavam — o que é o comportamento certo, porque ninguém quer perder o que digitou por causa de uma falha de rede. Trate o erro dentro da ação se quiser mostrar uma mensagem em vez de derrubar a página.

6. O durante: sabendo que está enviando

Falta o intervalo entre o clique e a resposta. Em uma conexão ruim, são segundos em que a pessoa não sabe se o envio aconteceu — e clica de novo. A solução do React é o useFormStatus, um hook que lê o estado do formulário de dentro de um filho: ele devolve { pendente, dados, método, ação } e não recebe argumento nenhum.

O detalhe que pega todo mundo: o useFormStatus só funciona em um componente dentro do formulário. Se você chamar no mesmo componente que tem o <form>, ele sempre responde pendente: false. É por isso que o botão de envio vira um componente separado — e é uma boa notícia, porque esse botão passa a servir em qualquer formulário do site.

"use client";

import { useFormStatus } from "react-dom";

export default function BotaoEnviar() {
  const { pending } = useFormStatus();

  return (
    <button type="submit" disabled={pending}>
      {pending ? "Enviando…" : "Encomendar"}
    </button>
  );
}

Com um console.log no botão, a sequência de um envio aparece assim no console do navegador — e é ela que explica por que o disabled funciona:

pendente: true
resposta do servidor: encomenda 42
pendente: false

Repare que o componente não recebe prop nenhuma: ele pergunta ao formulário em que está inserido. Isso é o oposto do padrão de props que você conhece, e é o preço de o status morar no formulário. O ganho é que o botão não precisa de nada do pai — nem pendente, nem setPendente.

Nesta caixa do guia o useFormStatus não está no escopo do motor, porque ele vem do react-dom e o motor expõe apenas os hooks do react. No seu projeto, o import está na primeira linha, como no arquivo acima. A aula seguinte mostra o outro caminho para ler o pendente: o useActionState, que traz o estado, a ação e o pendente de uma vez.

Há ainda a versão de servidor, com "use server" na primeira linha da função. Nesse caso a ação roda no servidor, e o formulário funciona até antes de o JavaScript carregar — o navegador envia do jeito tradicional e o servidor responde com a página nova. É o tal do aprimoramento progressivo: quem tem JavaScript ganha a experiência boa, quem não tem ainda consegue encomendar o pão.

7. Ação de cliente e ação de servidor

As duas formas têm a mesma assinatura — uma função que recebe FormData — e diferem em onde rodam. A ação de cliente é uma função comum do seu componente: roda no navegador, pode chamar fetch, mexer no estado, mostrar mensagem. A ação de servidor é marcada com "use server": roda no servidor, pode falar com o banco e usar segredo.

A escolha segue a mesma lógica dos Server Components. Se o trabalho precisa de banco, chave de API ou arquivo, ele é de servidor. Se precisa mexer no estado da tela — fechar o modal, limpar a seleção, mostrar o total —, é de cliente. Um formulário real costuma ter as duas: a ação de servidor grava, e o cliente reage ao resultado.

Não confunda, porém, ação de servidor com “chamar a API no servidor”. A diferença é o que atravessa a rede: na ação de servidor, você escreve uma função e chama como se fosse local; o React cuida do transporte. Na ação de cliente, você mesmo faz o fetch para o endereço que quiser. As duas funcionam; a de servidor economiza código quando o projeto já tem servidor React.

8. As armadilhas

Quatro problemas aparecem sempre que alguém adota ações. Todos têm sintoma claro e conserto curto — e todos são mais fáceis de diagnosticar quando você sabe que a causa é a mistura de dois estilos.

A primeira linha é a que mais aparece, porque a intuição manda controlar todos os campos. Se você precisa de validação a cada tecla, tudo bem controlar — mas então a limpeza é sua, e o React não vai ajudar. Escolha por formulário, não por campo: ou os campos guardam o próprio valor e o React cuida do ciclo, ou o estado guarda e você cuida.

A quarta linha é uma armadilha de leitura de código: um onSubmit esquecido junto com action faz o navegador enviar de verdade quando a ação termina, e a página troca. O React tenta impedir com o guarda que você viu no painel, mas o certo é não ter os dois. Envio é action ou onSubmit.

9. Cenários do dia a dia

Cenário 1: o formulário que se limpava no meio do erro

A Ana trocou o envio por uma ação e comemorou a limpeza automática — até o dia em que a API recusou uma encomenda e o cliente perdeu tudo o que tinha digitado. A limpeza só acontece quando a ação termina sem erro; no caso dela, a ação engolia a exceção e devolvia sucesso. O conserto foi deixar o erro subir ou tratar dentro da ação e devolver uma mensagem, mantendo os campos.

Cenário 2: o botão que enviava duas vezes

Sem o aviso de pendente, a cliente clicou três vezes em “Encomendar” e a padaria recebeu três encomendas iguais. Com useFormStatus dentro do botão, o disabled entra no primeiro clique e os outros dois não acontecem. O botão não precisa saber de nada: ele pergunta ao formulário.

Cenário 3: a ação que não recebia os campos

A ação rodava, mas dados.get("pao") voltava null. O campo existia, o name estava escrito com acento — name="pão" — e a ação procurava por "pao". Nome de campo é identificador, não texto de tela: sem acento, sem espaço, igual nos dois lados. O erro não aparece em lugar nenhum; o valor simplesmente não chega.

Exercício: a ação e os campos

Complete as duas linhas. Na primeira, a prop que recebe a função no formulário; na segunda, a leitura de um campo do FormData:

<form ={enviar}> async function enviar(dados) { const nome = dados.("nome"); }

Dica: a primeira é o nome da prop — a mesma palavra que existe no HTML, mas agora apontando para uma função. A segunda é o método do FormData que busca um campo pelo name; existe também o getAll, para quando há vários campos com o mesmo nome.

11. Resumo

A ação é uma função que o formulário chama no lugar de disparar um evento. Ela recebe um FormData com todos os campos que têm name, pode ser assíncrona e o React acompanha a promessa até o fim. Com isso, três coisas saem do seu código: o preventDefault, um estado por campo e a limpeza manual depois do envio.

formAction leva a mesma ideia para o botão, resolvendo o formulário com mais de uma ação sem estado dizendo qual foi clicado. E o useFormStatus, chamado de dentro de um componente que está dentro do formulário, informa se o envio está em andamento — base do botão que se desabilita e do texto “enviando…”.

As armadilhas vêm todas da mistura: campo controlado não é limpo, campo sem name não chega, texto do FormData não é número, onSubmit junto com action recarrega a página. Escolher um estilo por formulário resolve a maior parte delas antes de acontecer.

Falta o outro lado do ciclo: o que a ação devolve e como a tela mostra o resultado — erro de validação, mensagem de sucesso, o estado que sobrevive ao envio. É o assunto da próxima aula, e ele combina com este como a resposta combina com o pedido.

Para lembrar

  • <form action={funcao}>: o React intercepta o envio e chama a função.
  • A função recebe um FormData; os campos precisam de name.
  • dados.get("nome") devolve texto: converta número com Number.
  • formAction no botão dá uma ação por botão, sem estado de “qual cliquei”.
  • Depois do sucesso, o React limpa os campos não controlados.
  • Campo controlado não é limpo: o valor vem do estado e a limpeza é sua.
  • useFormStatus() só funciona dentro do formulário, em um componente filho.
  • "use server" transforma a ação em ação de servidor.
  • Não use onSubmit e action no mesmo formulário.
