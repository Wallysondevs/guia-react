Galeria de Fotos

A Ana fotografa tudo o que sai do forno e quer um mural no site: os pães numa grade, os bolos em outra, e um clique para ver a foto grande com o nome. O problema é que as fotos ainda não estão prontas — a confeiteira prometeu para sexta. Neste projeto a Ana constrói a galeria inteira com dados de mentira: cada foto é um cartão colorido com o nome, e a estrutura já fica pronta para receber as imagens de verdade. No caminho ela aprende a filtrar uma lista de objetos, abrir um detalhe e simular o carregamento sem depender de rede.

Você vai aprender
  • Como modelar uma foto com id, título e categoria.
  • Como montar a grade com map e uma key estável.
  • Como filtrar por categoria sem estragar a lista original.
  • Como guardar a foto selecionada e abrir o detalhe.
  • Como fechar o detalhe com um estado null.
  • Como simular um carregamento com Promise e setTimeout.
  • Como mostrar carregando, erro e vazio sem confundir os três.
  • O que trocar no dia em que as imagens de verdade chegarem.

1. A cena e as decisões do projeto

A padaria tem quatro fotos para mostrar: dois pães e dois bolos. A Ana quer uma grade, um botão por categoria e um detalhe que abre ao clicar. Quer também que a tela não fique vazia enquanto as fotos carregam. São quatro decisões de projeto, e nenhuma delas é sobre CSS: onde os dados moram, como a grade lê os dados, como o filtro escolhe e como o detalhe aparece.

A primeira decisão é ter uma lista de objetos em vez de quatro blocos escritos à mão. Com a lista, o mesmo código desenha quatro ou quarenta fotos, e o filtro passa a ser uma conta em vez de um if para cada cartão. A segunda é separar "todas as fotos" de "fotos visíveis": o filtro não apaga nada, só decide quem aparece.

A terceira é guardar a foto escolhida como um id, e não como o objeto inteiro. Um id é um texto curto, fácil de comparar; o objeto pode ficar desatualizado se a lista mudar. A quarta é ter um estado para cada coisa que a tela mostra de jeitos diferentes: carregando, erro e pronto. São três estados, não um.

O que fica de fora: upload de imagem, curtidas, comentários e ordenação. A galeria é para olhar, e o escopo é esse. Se você tentar entregar tudo de uma vez, não entrega nada — e o projeto perde a graça, que está em ver a tela crescer a cada etapa.

2. Os dados: a forma da foto

Antes da grade, a pergunta de sempre: o que é uma foto neste app? Precisa de um nome para o leitor, de uma categoria para o filtro e de um jeito de desenhar algo na tela enquanto a imagem real não existe. Neste projeto, o "jeito de desenhar" é uma cor de fundo; no dia da imagem, vira um endereço.

foto
Um objeto com os dados de um cartão: { id, titulo, categoria, cor }.
id
Um texto único e estável: "pao-frances", "bolo-cenoura". Serve de key e é o que o detalhe guarda.
titulo
O que o leitor vê: "Pão francês". Pode mudar sem quebrar nada, porque não é identidade.
categoria
O grupo da foto: "paes" ou "bolos". É o que o filtro compara.
cor
O fundo do cartão enquanto a imagem não chega. No app final, este campo vira url.

Com a forma definida, a lista inicial fica assim:

const fotosIniciais = [
  { id: "pao-frances", titulo: "Pão francês", categoria: "paes", cor: "#e8c39e" },
  { id: "pao-queijo", titulo: "Pão de queijo", categoria: "paes", cor: "#f2d59b" },
  { id: "bolo-cenoura", titulo: "Bolo de cenoura", categoria: "bolos", cor: "#d98c4a" },
  { id: "bolo-milho", titulo: "Bolo de milho", categoria: "bolos", cor: "#e0c060" },
];

Repare que a categoria é um código curto, não o texto que aparece na tela. Isso permite traduzir o rótulo — "Pães" com acento e maiúscula — sem mexer nos dados. A tradução fica num objeto à parte, e o filtro compara códigos. É a mesma separação entre valor e rótulo que você viu no select.

Uma observação sobre a cor: ela está ali só porque as imagens não chegaram. Quando chegarem, o campo passa a se chamar url e o cartão troca um div com fundo por um img com src e alt. O resto — lista, filtro, detalhe — não muda. É por isso que vale construir a estrutura antes do conteúdo: a estrutura é o que fica.

3. A grade de cartões

Com a lista pronta, a grade é um map — a mesma ideia da aula de listas com map. Cada objeto vira um botão com a miniatura, o título e uma key estável. Botão, e não div, porque o cartão é clicável: assim ele recebe foco pelo teclado e o leitor de tela anuncia que dá para ativar.

Na caixa abaixo, a grade tem dois cartões escritos à mão e a lista tem quatro fotos. Gere um cartão por foto, com key={foto.id}, a miniatura colorida e o título:

A grade mostra só duas fotos. Gere um button.cartao por item de fotosIniciais, com key={foto.id}, uma span.miniatura com style={{ background: foto.cor }} e o título.

O painel mostra quatro botões, na ordem da lista. A miniatura aparece como um span com style="background: #e8c39e" — é o que dá a cor de cada cartão enquanto não há imagem. Repare na key: ela é o id, não o índice. Numa galeria que depois vai permitir remover fotos e reordenar, o índice muda quando a lista muda, e o React trataria cartões diferentes como se fossem o mesmo. O id é estável, então o cartão do "Bolo de milho" continua sendo ele mesmo em qualquer posição.

Para ver o que a lista guarda, um console.log antes do return resolve a dúvida:

fotos[2].categoria: "bolos"

Se a grade mostrar menos cartões do que o número acima, o problema está no map — e não nos dados. Já aconteceu com quem colocou um filter escondido no meio do map.

4. O filtro por categoria

Filtrar é decidir quem aparece sem apagar ninguém. O estado guarda a categoria escolhida — "todas", "paes" ou "bolos" — e uma conta devolve a lista visível. O erro clássico é guardar a lista filtrada num estado separado: aí você tem duas fontes para a mesma informação e uma delas envelhece.

Na caixa abaixo, os botões mudam o estado do filtro, mas a grade ignora o estado e mostra sempre as quatro fotos. Complete a conta de visiveis:

Os botões mudam filtro, mas a grade mostra sempre tudo. Calcule visiveis a partir de filtro (deixe passar quando for "todas") e use essa lista no map.

A condição é visiveis.length === 0, com um texto diferente para "ainda não há fotos" e "não há fotos nesta categoria". Só a segunda acontece neste app, mas a primeira vai acontecer quando a lista vier da rede e demorar.

5. A foto selecionada e o detalhe

Abrir uma foto é guardar qual foi escolhida. O estado natural é o id, começando em null — nada selecionado. O detalhe é uma conta: procure a foto pelo id e mostre só se achou. O erro comum é começar com a primeira foto selecionada e nunca deixar o detalhe fechar.

Na caixa abaixo, o detalhe abre junto com a página e o botão Fechar volta para a primeira foto em vez de fechar. Conserte os dois:

O detalhe começa aberto e o Fechar não fecha. Comece com useState(null), mostre o bloco só quando foto existir e faça o Fechar voltar para null.

No começo, não há detalhe nenhum. Clique no terceiro cartão: o bloco aparece com "Bolo de cenoura" e "Categoria: Bolos". Clique em Fechar: o bloco sai do HTML — não fica escondido por CSS, some de verdade, porque foto virou undefined e o && não desenha nada.

selecionada
O id da foto aberta, ou null. É o único estado do detalhe.
find
A conta que transforma o id no objeto da foto: fotos.find((f) => f.id === selecionada).
detalhe
O bloco que mostra a foto escolhida. Existe só quando foto é encontrada.
null
O estado de "nada selecionado". Melhor que "" porque um id vazio jamais existiria na lista.
fechar
O botão que devolve o estado para null. Deve estar dentro do bloco, não fora.

A escolha do null não é preciosismo. Com "", o find devolveria undefined do mesmo jeito, mas qualquer comparação distraída com !selecionada funcionaria por acidente — e um id vazio passaria a ser um valor válido na cabeça de quem lê. O null diz "não há nada aqui" sem ambiguidade.

O console mostra o estado e a conta lado a lado:

selecionada: "bolo-cenoura"
foto.titulo: "Bolo de cenoura"
selecionada: null

A última linha é o depois do Fechar. Se o seu detalhe continuar aparecendo com selecionada: null, o problema está na condição: procure um {foto.titulo} fora do &&, que quebra o componente antes mesmo de esconder o bloco.

6. Carregando, erro e pronto

No app de verdade, as fotos vêm de um servidor — e o servidor demora. A aula de carregando e erro conta a mesma história com fetch. Aqui não há rede no quadro da caixa, então a busca é simulada com uma Promise que resolve depois de um setTimeout. A estrutura é a mesma de um fetch: uma função que devolve promessa, um efeito que chama, e três estados para a tela.

function buscarFotos() {
  return new Promise((ok) => {
    setTimeout(() => ok(fotosIniciais), 600);
  });
}

function App() {
  const [fotos, setFotos] = useState([]);
  const [carregando, setCarregando] = useState(true);
  const [erro, setErro] = useState(null);

  useEffect(() => {
    let vivo = true;
    buscarFotos()
      .then((lista) => {
        if (!vivo) return;
        setFotos(lista);
        setErro(null);
      })
      .catch(() => {
        if (vivo) setErro("Não foi possível carregar as fotos");
      })
      .finally(() => {
        if (vivo) setCarregando(false);
      });
    return () => {
      vivo = false;
    };
  }, []);

  if (carregando) return <p>Carregando fotos…</p>;
  if (erro) return <p role="alert">{erro}</p>;
  return <div className="grade">{/* os cartões */}</div>;
}

Três detalhes fazem esse código funcionar. O primeiro é o array de dependências vazio: o efeito roda uma vez, na montagem, e não a cada render. O segundo é a variável vivo, que impede o set depois que o componente saiu da tela — sem ela, uma resposta atrasada pode mexer num estado que já não interessa, e o erro fica silencioso. O terceiro é o finally, que desliga o carregando nos dois caminhos, certo e errado.

EstadoO que a tela mostraComo saber que está certo
carregando"Carregando fotos…"aparece antes dos dados e some no finally
errouma mensagem com role="alert"só aparece quando a promessa rejeita
prontoa grade de cartõessó aparece com a lista preenchida
vazio"Nenhuma foto ainda"pronto, com lista de tamanho zero

O console ajuda a ver a ordem em que as coisas acontecem. Na montagem, carregando é verdadeiro e a lista está vazia; depois do tempo, a lista chega e o carregando desliga:

carregando: true
fotos: []
carregando: false
fotos: 4

Não confunda os quatro estados da tabela. "Carregando" não é "vazio": um mostra que a resposta ainda vem, o outro que ela veio e não tinha nada. "Erro" não é "vazio" também: um pede tentar de novo, o outro pede outra categoria ou outra foto. Quando a Ana juntou carregando e vazio no mesmo if, a tela dizia "Nenhuma foto ainda" enquanto os dados estavam a caminho — e ela achou que a lista tinha se perdido.

7. O que quebra na galeria

Os tropeços deste projeto são poucos e repetem em quase toda lista com detalhe. A tabela serve de diagnóstico rápido quando a tela não faz o que você espera:

SintomaCausa provávelConserto

A quarta linha merece um comentário, porque é uma decisão de produto. Se a Ana abre o "Bolo de cenoura" e depois clica em "Pães", o detalhe continua aberto com uma foto que não está mais na grade. Isso pode ser desejado — a pessoa está vendo a foto, o filtro é da grade — ou confuso. Se for confuso, o onClick do filtro também faz setSelecionada(null). Não existe resposta certa universal; existe a que faz sentido para a sua tela.

A quinta linha é o aviso mais comum de quem começa com efeito e promessa. A guarda não precisa ser sofisticada: uma variável no escopo do efeito, marcada como falsa na função de limpeza, resolve. O cleanup tem aula própria, e vale ler antes de colocar um setTimeout em produção — o padrão é o mesmo.

Por fim, um cuidado com imagens de verdade: alt não é opcional. Uma foto sem alt é invisível para quem usa leitor de tela, e um alt genérico ("foto") não ajuda. O título da foto é um bom começo: alt={foto.titulo} diz o que está na imagem sem descrever cada pixel.

8. Cenários do dia a dia

Cenário 1: os cartões piscam e trocam de lugar ao filtrar

A Ana usou key={indice} e, ao trocar de categoria, o React reaproveitou os cartões na mesma posição: a cor da miniatura ficou de uma foto e o título de outra. Com key={foto.id}, cada cartão mantém a identidade e a troca de filtro vira remoção e criação limpas. Índice serve para lista que nunca muda de ordem; não é o caso aqui.

Cenário 2: o detalhe abre vazio depois do carregamento

Ela guardou o objeto da foto no estado, e o detalhe abria com título certo mas categoria vazia. O objeto guardado era de antes de a lista ser recarregada, e os dados novos estavam no array. Guardando só o id, o find sempre busca a versão atual. A regra vale para qualquer detalhe que dependa de uma lista: guarde a chave, não a cópia.

Cenário 3: a tela diz "nenhuma foto" enquanto carrega

O código testava fotos.length === 0 antes de testar carregando, e a mensagem de vazio aparecia no primeiro segundo. A ordem dos if resolve: carregando primeiro, erro depois, vazio por último. Quando a lista chega, os três já foram resolvidos e a grade aparece. Ordem de condição é parte do design, não detalhe de implementação.

10. Resumo

A galeria começa pelos dados: cada foto é { id, titulo, categoria, cor }, e a lista fica fora do componente porque é o dado de partida. A grade é um map com key={foto.id}, e cada cartão é um botão — clicável, focável e anunciado pelo leitor de tela. O detalhe guarda o id selecionado, começa em null e só aparece quando o find encontra a foto.

O filtro é estado; a lista visível é conta. O carregamento tem três estados separados — carregando, erro e pronto —, e o vazio é um quarto caso, com mensagem própria. A simulação com Promise e setTimeout é a mesma estrutura de um fetch: a diferença é só de onde a resposta vem.

Quando as imagens de verdade chegarem, o campo cor vira url e a span.miniatura vira img com alt. Lista, filtro, seleção e estados continuam iguais — e é por isso que valeu construir a estrutura antes. O próximo projeto leva a mesma base para o carrinho de compras, onde os objetos têm preço e quantidade, e as contas passam a envolver dinheiro.

Para lembrar

  • Foto é { id, titulo, categoria, cor }; a lista fica fora do componente.
  • Grade é map com key={foto.id}; cartão é button.
  • Filtro é estado; lista visível é conta feita com filter.
  • Detalhe guarda o id, começa em null e usa find.
  • {foto && (...)} mostra o detalhe só quando existe foto.
  • Fechar é setSelecionada(null).
  • Carregando, erro e pronto são estados separados; vazio é outro caso.
  • Promise + setTimeout simulam a rede; o finally desliga o carregando.
  • A guarda vivo evita set depois de desmontar.
  • Imagem de verdade pede src e alt.
