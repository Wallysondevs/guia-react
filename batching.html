Atualizações em Lote

A Ana montou o painel do fim do dia: um botão fecha o caixa, zera a quantidade e marca o horário. Ela queria ver o painel passando por "fechando…" antes de chegar em "fechado" — e o painel salta direto para o fim. O mesmo acontece com os console.log: dentro do clique, os valores ainda são os antigos. Nesta aula a Ana entende o lote: as atualizações de um evento entram numa fila e viram um desenho só.

Você vai aprender
  • O que é um lote e por que o React junta atualizações.
  • Como a fila é aplicada: em ordem, e o último pedido vence.
  • Por que a tela nunca mostra um estado intermediário.
  • Como fazer o React desenhar o meio, quando você realmente quer.
  • Onde o lote acontece: evento, promise, setTimeout.
  • Como contar desenhos e o que esse número revela.
  • Quando o React descarta uma atualização sem desenhar.

1. A cena: o painel que pula para o fim

Na aula de atualizar o estado, a Ana aprendeu que dois setters iguais somam um, e que a variável do estado continua valendo o valor antigo até o próximo desenho. Ficou uma pergunta sem resposta: se cada setter pede um desenho, por que ela nunca vê a tela parar no meio?

O painel dela tem três informações: o status do caixa, a quantidade de pães do dia e a hora do fechamento. O clique de fechar faz três coisas de uma vez: muda o status para "fechado", zera a quantidade e grava a hora. O que ela esperava era ver, por um instante, o status "fechando" e os outros dois valores ainda antigos. O que ela vê é o retrato final, direto.

Não é falta de sorte nem de tempo de tela. O React não desenha entre um setter e outro porque não precisa: enquanto o seu código está rodando, ninguém está olhando o DOM. Ele recolhe os pedidos, deixa o seu handler terminar e só então aplica tudo de uma vez. Esse recolhimento é o que se chama de lote.

Entender o lote muda o jeito de depurar. Metade das perguntas do tipo "por que meu log mostrou o valor antigo?" e "por que meu indicador de carregando nunca aparece?" tem a mesma resposta: porque as duas coisas aconteceram dentro da mesma tarefa, e o React desenhou uma vez só, no fim.

2. O lote: uma fila e um render

Quando você chama um setter, o React não redesenha na hora. Ele anota o pedido numa fila. Terminado o handler, ele aplica a fila inteira, calcula o estado final e desenha o componente uma única vez. Se você chamou cinco setters, houve um desenho — não cinco.

lote
O conjunto de atualizações recolhidas durante uma mesma tarefa, aplicadas juntas num render só.
fila
A lista ordenada dos pedidos feitos pelos setters. É aplicada na ordem em que você chamou, do primeiro ao último.
tarefa
Um pedaço de trabalho do navegador: o tratamento de um clique, um setTimeout que disparou, o trecho depois de um await. Cada tarefa tem o seu lote.
render (desenho)
A execução do componente para produzir a nova tela. Um lote termina em um desenho.
flushSync
Uma função do React que aplica a fila na hora e desenha imediatamente, quebrando o lote. Serve para casos raros, como medir um elemento logo depois de mudá-lo.

Há duas razões para o React trabalhar assim. A primeira é velocidade: um clique que mexe em quatro estados custa um desenho, e não quatro. A segunda é coerência: a tela nunca mostra uma combinação impossível, como o nome do cliente novo com o telefone do antigo. Ou tudo de um clique aparece, ou nada aparece.

Vale desfazer uma confusão comum: o lote não é um atraso, e o setter não é "assíncrono" no sentido de esperar a vez. O desenho acontece no mesmo evento, imediatamente depois do handler — antes de a pessoa ver qualquer coisa, porque o navegador ainda nem pintou a tela. O que o lote adia é só a repetição: em vez de desenhar cinco vezes enquanto o seu código roda, ele desenha uma vez quando o código termina.

E o que acontece com a variável durante o handler? Ela continua sendo o retrato do começo do desenho, como a aula anterior mostrou. O lote é o outro lado da mesma moeda: o retrato só é trocado quando a fila inteira é aplicada.

3. A fila é aplicada em ordem

Como a fila é aplicada em ordem, dois setters do mesmo estado se resolvem como uma sequência de substituições. O último pedido é o que fica na tela. Isso explica um bug comum de quem está começando: um valor "aparece" no código e some na tela, porque uma linha posterior o desfez.

O botão preenche o nome com "Bia", mas uma linha antiga do código limpa o campo logo depois — e o lote aplica as duas. Faça o nome ficar preenchido. A missão clica em Preencher e confere o campo e o parágrafo.

function App() {
  const [nome, setNome] = useState("");

  function preencher() {
    setNome("Bia");
    setNome("");
  }

  return (
    <div>
      <button onClick={preencher}>Preencher</button>
      <input value={nome} onChange={(e) => setNome(e.target.value)} />
      <p>Cliente: {nome || "vazio"}</p>
    </div>
  );
}
<div>
  <button>Preencher</button>
  <input value="">
  <p>Cliente: vazio</p>
</div>

4. Por que a tela não mostra o meio

Agora o painel da Ana. Ela queria que o status passasse por "salvando" antes de "pronto". Com as duas chamadas no mesmo handler, a fila tem dois pedidos, o último é "pronto" — e o "salvando" não chega a existir na tela.

O botão grava e volta ao status "pronto" no mesmo instante, então o "salvando" nunca aparece. Faça a volta acontecer meio segundo depois, em outra tarefa. A missão clica em Salvar e confere "Status: salvando".

function App() {
  const [status, setStatus] = useState("pronto");

  function salvar() {
    setStatus("salvando");
    setStatus("pronto");
  }

  return (
    <div>
      <button onClick={salvar}>Salvar</button>
      <p>Status: {status}</p>
    </div>
  );
}
<div>
  <button>Salvar</button>
  <p>Status: pronto</p>
</div>

function App() {
  const [status, setStatus] = useState("pronto");

  function salvar() {
    setStatus("salvando");
    setTimeout(() => setStatus("pronto"), 500);
  }

  return (
    <div>
      <button onClick={salvar}>Salvar</button>
      <p>Status: {status}</p>
    </div>
  );
}

O setTimeout cria uma tarefa nova. O primeiro lote (o do clique) desenha "salvando"; meio segundo depois, o segundo lote (o do temporizador) desenha "pronto". Duas tarefas, dois desenhos, e o estado intermediário existe na tela pelo tempo que você pediu.

É a regra que vale para qualquer indicador: um valor que existe apenas durante um trabalho síncrono não tem como ser visto. Para mostrar "carregando", o trabalho precisa acontecer em outra tarefa — uma requisição de rede, um temporizador —, e não no mesmo handler que liga e desliga o indicador.

Cuidado com o exagero oposto: encher o código de setTimeout só para ver estados intermediários deixa a tela mais lenta e imprevisível. Pergunte se o cliente precisa mesmo ver aquele passo. Na maioria das vezes, o certo é não mostrar nada e trocar o conteúdo no fim.

5. Quando o valor novo depende do anterior

Dentro de um lote, todos os pedidos de valor fixo partem do mesmo retrato e o último vence. Quando o valor novo depende do valor anterior — somar, dobrar, acrescentar numa lista —, o valor fixo não serve, porque ele ignora a fila. A solução já apareceu na aula anterior e vale repetir em uma linha: entregue uma instrução em vez de um valor.

setPaes(paes + 1);          // valor calculado agora: os dois pedidos usam o mesmo paes
setPaes((atual) => atual + 1);   // instrução: cada pedido recebe o valor pendente da fila

O lote é o motivo pelo qual a diferença importa. Sem lote, a segunda chamada já encontraria o estado novo e o problema não existiria. Com lote, as duas chamadas trabalham sobre o mesmo retrato, e quem quiser conversar com a fila tem de usar a forma de função. É por isso que ela é o padrão em contadores, em listas e em qualquer acumulador.

E, quando você precisa do valor novo também fora do setter — num log, num histórico, numa segunda conta —, calcule antes numa variável e passe a variável. A fila não devolve valor nenhum: os setters retornam undefined.

6. Onde o lote acontece

Desde o React 18, o lote não é privilégio dos eventos do React. Qualquer atualização feita dentro da mesma tarefa é agrupada — inclusive depois de uma resposta da rede ou de um temporizador.

Onde você chamou o setterÉ agrupado?Quantas tarefas
Handler de evento (onClick, onChange)simuma: o evento
Depois de uma promise (.then, await)simuma: o retorno da promise
Dentro de setTimeout ou setIntervalsimuma por disparo
Listener nativo (addEventListener)simuma: o evento
Dentro de flushSyncnãoo desenho acontece na hora

Duas chamadas em tarefas diferentes são dois lotes, logo dois desenhos. É o que o setTimeout da seção 4 aproveitou: separar em tarefas é justamente o jeito de fazer o React desenhar no meio. E é também por isso que dois cliques seguidos são dois desenhos, mesmo que rápidos: cada clique é um evento, e cada evento é uma tarefa.

O flushSync existe para o caso de você precisar ler o DOM imediatamente depois de mudar o estado — medir a altura de um elemento que acabou de aparecer, por exemplo. Ele desenha na hora e por isso aparece nas listas de "quase nunca use": quebra a coerência do lote e deixa a tela mais lenta. Se você se pegar querendo desligar o lote para "ver o valor no meio", a resposta é separar em tarefas.

7. Contando desenhos

Como saber quantos desenhos aconteceram? Duas formas. A primeira é um console.log no corpo do componente, antes do return: ele roda uma vez por desenho. A segunda é contar numa variável de fora do componente e mostrar o número na tela — útil quando você quer ver o efeito de um clique sem abrir o console.

O botão soma o pão no clique e o café num temporizador: duas tarefas, dois desenhos. Junte as duas atualizações no mesmo lugar — uma tarefa, um desenho. A missão clica em Pedir e confere "Desenhos: 2".

let desenhos = 0;

function App() {
  desenhos = desenhos + 1;
  const [paes, setPaes] = useState(0);
  const [cafes, setCafes] = useState(0);

  function pedir() {
    setPaes(paes + 1);
    setTimeout(() => setCafes(cafes + 1), 0);
  }

  return (
    <div>
      <button onClick={pedir}>Pedir</button>
      <p>Desenhos: {desenhos}</p>
      <p>{paes} pães e {cafes} cafés</p>
    </div>
  );
}
<div>
  <button>Pedir</button>
  <p>Desenhos: 1</p>
  <p>0 pães e 0 cafés</p>
</div>

A variável desenhos fica fora do componente de propósito: ela precisa sobreviver entre um desenho e outro, e um estado não serviria — mudar o estado causaria outro desenho, e a contagem viraria perseguição. É um instrumento de medida, não um dado da tela.

render — paes: 0, cafes: 0
render — paes: 1, cafes: 1

Duas linhas para o componente inteiro: a montagem e o clique. Na versão que espalha as atualizações por duas tarefas, aparece uma linha intermediária com paes: 1, cafes: 0 — e é exatamente essa linha que mostra que houve dois desenhos em vez de um. Contar desenhos é o teste mais direto para saber se algo está fora do lote.

8. Os tropeços do lote

O setter com o mesmo valor não desenha. Se o estado já vale 5 e você chama setN(5), o React compara, vê que nada muda e descarta a atualização. Nenhum desenho, nenhum log. É o que acontece com o status do painel da Ana quando as duas chamadas terminam no valor atual: a fila é aplicada e o resultado é igual ao que já estava lá.

clique com valor novo:    console: desenhou
clique com o mesmo valor: (nada no console)

Um setter dentro de um efeito gera um desenho extra. Se um efeito observa um estado e chama outro setter para "acompanhar", você tem dois lotes: o do evento e o do efeito. O componente desenha duas vezes, a tela pisca o valor antigo e o número de desenhos dobra. A aula de estado derivado mostra por que quase sempre dá para calcular em vez de sincronizar.

O lote não é uma transação. Ele junta as atualizações de uma tarefa, mas não desfaz nada se uma delas falhar no meio: um erro no meio do handler deixa a fila com o que já foi pedido. Se a ordem das operações importa para o cliente — cobrar e depois reservar, por exemplo —, a garantia tem de vir do seu código, não do lote.

O lote não substitui a forma de função. Juntar atualizações num desenho não faz a segunda enxergar o resultado da primeira. Quem quer a fila como ponto de partida usa (atual) => ...; quem quer o valor final usa um valor calculado antes. São ferramentas diferentes para perguntas diferentes.

9. Cenários do dia a dia

Cenário 1: o indicador que aparece e some no mesmo piscar

Ao enviar um formulário, ela ligava carregando e desligava no fim da mesma função. Como as duas chamadas caem no mesmo lote, o indicador nunca chegou à tela. A correção não é CSS: é colocar o trabalho numa tarefa que demore de verdade — a chamada de rede — e desligar o indicador quando ela responder.

Cenário 2: três desenhos para um clique

O contador de desenhos marcou 3 quando a Ana esperava 2. Havia um efeito que copiava o estado para outro estado a cada mudança: um desenho do clique e mais um do efeito. Medir desenhos é o jeito mais rápido de encontrar esse tipo de vazamento — e a solução costuma ser apagar o estado espelho, não otimizar.

Cenário 3: o campo que "voltava" ao valor anterior

Ela preencheu o formulário e, ao clicar em salvar, o campo voltou ao texto de antes. Não era o lote desfazendo: era um setter posterior, escondido num trecho copiado, que reescrevia o mesmo estado. Como o último pedido vence, a tela mostrou o valor antigo como se o clique não tivesse funcionado.

11. Resumo

O React não desenha a cada setter: ele recolhe os pedidos numa fila, deixa a tarefa terminar e aplica tudo num desenho só. Esse é o lote. A fila é aplicada em ordem, então o último pedido de valor fixo vence — e é por isso que um setStatus("pronto") logo depois de "salvando" apaga o intermediário antes que ele exista.

Para ver um estado intermediário, separe o trabalho em outra tarefa: um setTimeout, uma resposta de rede, um evento. Para conversar com a fila, use a forma de função (atual) => atual + 1, que recebe o valor pendente em vez do retrato do começo. E lembre que o React descarta atualizações que não mudam nada: nenhum desenho, nenhum log.

Contar desenhos é o exame mais simples para descobrir vazamentos: um console.log no corpo do componente ou uma variável fora dele mostram quantas vezes o componente rodou. Um número maior do que o esperado costuma apontar para um efeito que chama setter. Com o lote entendido, a Ana fecha o grupo de estado — e as aulas de efeitos começam exatamente por esse personagem: o efeito que roda depois do desenho.

Para lembrar

  • As atualizações de uma tarefa viram uma fila e um desenho só.
  • A fila é aplicada em ordem: o último pedido vence.
  • Um estado intermediário que só existe dentro do handler não chega à tela.
  • Para mostrar o meio, separe em tarefas: setTimeout, promise, evento.
  • Valor novo que depende do anterior: setX((atual) => atual + 1).
  • React 18 em diante agrupa também em promises, setTimeout e listeners nativos.
  • flushSync quebra o lote e só serve para casos raros.
  • Setter com o mesmo valor não desenha nada.
  • Efeito que chama setter gera um desenho extra: conte desenhos para achar o culpado.
  • Dois cliques, dois eventos, dois desenhos.
