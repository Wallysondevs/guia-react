Buscando Dados

Os pães da vitrine da Ana mudam todo dia, e o preço do dia só existe no servidor da padaria. Escrever essa lista à mão dentro do componente não resolve: amanhã ela está errada. Nesta aula a Ana faz o componente pedir os dados — e descobre por que esse pedido não pode ficar no meio do render, onde ele vive, como guardar a resposta no estado e como encadear dois pedidos sem embolar um com o outro.

Você vai aprender
  • Por que buscar dados é um efeito e não um cálculo do render.
  • A forma básica: um estado para os dados, um efeito com [] e um .then.
  • Como é o fetch de verdade, com resposta.ok e resposta.json().
  • Como fazer um pedido depender do outro com async e await dentro do efeito.
  • Como disparar dois pedidos independentes sem esperar um pelo outro.
  • Os quatro tropeços: guardar a Promise no estado, esquecer o .json(), usar async na função do efeito e pedir duas vezes sem querer.
  • O que a caixa faz no lugar da internet — e por que o resultado aparece no painel.

1. A cena: o preço que muda todo dia

A vitrine da Ana tem quatro pães, e o preço de cada um muda quase toda semana. Enquanto eram dois pães e o preço era fixo, ela escrevia à mão:

function App() {
  return (
    <ul>
      <li>Pão francês — 2 reais</li>
      <li>Croissant — 4 reais</li>
    </ul>
  );
}

Funcionou por três semanas. Depois veio o quarto pão, a promoção de terça, o aumento da farinha. Ela mudava o preço no site, mas o site não é o lugar onde o preço mora: o preço mora no sistema da padaria, que fica em um servidor. O site só deve mostrar o que o servidor diz. E para saber o que o servidor diz, o componente precisa perguntar.

Perguntar é uma ação com o mundo de fora, então já sabemos em qual faixa ela cai: é um efeito. O componente desenha o que tem (uma lista vazia, no começo), e depois de montado pede os dados; quando a resposta chega, ele guarda no estado e desenha de novo, agora com os pães. É o mesmo caminho que você viu na aula do useEffect, com uma diferença importante: a resposta não chega na hora. Leva tempo, e o componente tem de viver com isso.

Essa demora é a fonte de quase toda a confusão daqui para frente. Quem programa em outras linguagens está acostumado a escrever uma linha que busca e devolve na mesma frase. No navegador não é assim: o pedido sai, o JavaScript continua trabalhando, e a resposta chega depois, numa função que você entrega para ser chamada quando ela chegar. Essa função é o .then, ou o código depois do await.

2. Por que o pedido não pode ficar no render

O lugar mais intuitivo para o pedido seria antes do return, junto dos cálculos. E é exatamente o lugar errado. O render precisa ser uma função pura: dado o mesmo estado, devolver o mesmo JSX. Se o pedido estiver ali, três problemas aparecem de uma vez.

Primeiro, o render roda muitas vezes. Cada mudança de estado, cada mudança de prop, cada clique que atualiza algo faz o componente ser chamado de novo — e cada chamada dispararia outro pedido. Segundo, no modo de desenvolvimento o React chama o componente duas vezes de propósito; dois pedidos sem motivo. Terceiro, o pedido não devolve nada na hora: você não pode escrever const lista = buscar() e usar lista no JSX, porque naquele instante lista ainda é uma promessa, não uma lista.

Existe um jeito de pedir dados sem efeito, que é o React moderno com componentes de servidor, onde o componente roda no servidor e pode esperar. Esse jeito é de outro nível e de outro tipo de projeto. No navegador, com o React rodando no cliente — que é o caso deste guia e da padaria —, a regra é: pedido vai no efeito.

3. A forma básica: estado, efeito e .then

Toda busca no React tem a mesma anatomia: um estado para guardar o resultado, um efeito com [] para sair uma vez só, e uma função que espera a resposta para chamar o set. Veja a lista de peças antes do código:

estado dos dados
Onde a resposta vai morar: const [paes, setPaes] = useState([]). Comece com uma lista vazia (ou null, quando "nada ainda" é diferente de "lista vazia").
pedido
A chamada que sai para o servidor. Nesta caixa, uma função buscarPaes() que devolve uma Promise; no projeto de verdade, o fetch.
Promise
O objeto que representa "ainda vai chegar". Ele não tem a lista dentro; tem a promessa de que um dia terá.
.then
A função que você entrega para rodar quando a resposta chegar: .then((lista) => setPaes(lista)).
efeito com []
O que faz o pedido sair uma vez, na montagem, e não a cada render.

Na caixa, a função buscarPaes simula o servidor: ela devolve uma Promise que se resolve 10 milissegundos depois com dois pães. Esse atraso pequeno é de propósito — assim o painel mostra o resultado sem você esperar. O efeito já chama a função, mas joga o resultado fora. A missão é guardar.

O efeito chama buscarPaes() e descarta a resposta. Use o .then para guardar a lista no estado, de modo que o contador mostre 2.

function buscarPaes() {
  return new Promise((ok) => {
    setTimeout(() => ok(["pão francês", "croissant"]), 10);
  });
}

function App() {
  const [paes, setPaes] = useState([]);

  useEffect(() => {
    buscarPaes();
  }, []);

  return (
    <div>
      <h1>Padaria da Ana</h1>
      <p>Pães na vitrine: {paes.length}</p>
    </div>
  );
}
<div>

  <p>Pães na vitrine: 0</p>
</div>

Duas coisas aconteceram. Na montagem, o componente desenhou com a lista vazia e o efeito saiu pedindo os pães. Quando a resposta chegou, o .then rodou, chamou setPaes e o React desenhou de novo, agora com dois itens. O painel mostra o segundo desenho: o estado depois que tudo sossegou.

Repare no []. Sem ele, o efeito rodaria depois de todo render e cada execução chamaria setPaes — que provoca outro render, que pede de novo, num laço de pedidos. É a mesma armadilha da aula de dependências, agora com um custo a mais: além de travar, cada volta seria uma requisição de verdade no servidor da Ana.

Se você colocar um console.log dentro do .then, o console do navegador mostra a lista já convertida — repare que a mensagem aparece depois de a página estar na tela:

carreguei a lista: (2) ['pão francês', 'croissant']

4. O fetch de verdade e o res.json()

No projeto da padaria, a função buscarPaes não existe: quem faz o pedido é o fetch, uma função do navegador. Ela recebe uma URL e devolve uma Promise que se resolve com a resposta — não com os dados. A resposta é um objeto com status, cabeçalhos e um corpo, e o corpo só vira JavaScript quando você pede, com .json(). São dois passos, dois await:

useEffect(() => {
  async function carregar() {
    const resposta = await fetch("https://loja.test/api/paes");
    if (!resposta.ok) {
      throw new Error("o servidor respondeu " + resposta.status);
    }
    const lista = await resposta.json();
    setPaes(lista);
  }

  carregar();
}, []);

A conferência do resposta.ok não é preciosismo. O fetch só rejeita a Promise quando o pedido não sai — sem rede, endereço que não existe, servidor fora do ar. Se o servidor responder "404 página não encontrada" ou "500 deu problema aqui dentro", a Promise se resolve normalmente, com ok: false. Quem escreve resposta.json() sem conferir acaba com um erro estranho de leitura de JSON em vez da mensagem que o servidor mandou.

PedaçoO que éO que devolve
fetch(url)o pedido em siPromise com a resposta (status, cabeçalhos, corpo)
resposta.okse o status está entre 200 e 299verdadeiro ou falso
resposta.statuso código do servidor200, 404, 500…
resposta.json()a leitura do corpo como JSONPromise com o array ou objeto
resposta.json() duas vezeso corpo já foi consumidoerro: "body already read"

O mesmo pedido escrito com .then, que é a forma da caixa anterior, fica assim: dois .then em fila, um para a resposta e outro para os dados. As duas formas funcionam; o async/await costuma ser mais fácil de ler quando há mais de um pedido.

useEffect(() => {
  fetch("https://loja.test/api/paes")
    .then((resposta) => resposta.json())
    .then((lista) => setPaes(lista));
}, []);

5. Um pedido depois do outro: await dentro do efeito

Às vezes o segundo pedido precisa de um dado do primeiro. A Ana quer o horário do forno, mas o endereço do forno depende do identificador da padaria que veio na primeira resposta. Não dá para disparar os dois ao mesmo tempo: um depende do outro. Aí entra o await, e com ele a regra que você já conhece: a função async fica dentro do efeito.

O efeito já busca os pães. Depois dela, faça a segunda busca com await buscarHorario() e guarde o resultado em horario.

function buscarPaes() {
  return new Promise((ok) => {
    setTimeout(() => ok(["pão francês", "croissant"]), 10);
  });
}

function buscarHorario() {
  return new Promise((ok) => {
    setTimeout(() => ok("forno ligado às 5h"), 10);
  });
}

function App() {
  const [paes, setPaes] = useState([]);
  const [horario, setHorario] = useState("");

  useEffect(() => {
    async function carregar() {
      const lista = await buscarPaes();
      setPaes(lista);
    }
    carregar();
  }, []);

  return (
    <div>
      <p>Pães: {paes.join(", ")}</p>
      <p>Horário: {horario}</p>
    </div>
  );
}

A função carregar é declarada dentro do efeito e chamada logo em seguida. Ela pode usar await porque é async; o efeito em si não é, e devolve undefined, que é o que o React espera. Se você escrever useEffect(async () => { ... }), o React avisa que a função devolveu uma Promise — e o aviso não é o pior: você perde o lugar natural para a limpeza, que é a aula depois da próxima.

Note também que setPaes é chamado antes do segundo await. Isso não é detalhe: cada set dispara um render, e os dois valores aparecem na tela em momentos diferentes. Primeiro a lista de pães, depois o horário. Em uma tela com muitos dados, esse efeito "picado" é visível — e é o motivo de a próxima aula existir.

6. Dois pedidos independentes

Quando um pedido não depende do outro, não há por que esperar. A Ana quer os pães e as promoções do dia, e o segundo pedido não usa nada do primeiro. Nesse caso cada pedido segue a sua vida, com o seu próprio .then (ou com um Promise.all, que dispara os dois e espera os dois).

O efeito só busca os pães. Faça também o pedido das promoções, no mesmo efeito, para o contador mostrar 2.

function buscarPaes() {
  return new Promise((ok) => {
    setTimeout(() => ok(["pão francês", "croissant"]), 10);
  });
}

function buscarPromocoes() {
  return new Promise((ok) => {
    setTimeout(() => ok(["pão de queijo", "café coado"]), 10);
  });
}

function App() {
  const [paes, setPaes] = useState([]);
  const [promocoes, setPromocoes] = useState([]);

  useEffect(() => {
    buscarPaes().then((lista) => setPaes(lista));
  }, []);

  return (
    <div>
      <p>Pães na vitrine: {paes.length}</p>
      <p>Promoções do dia: {promocoes.length}</p>
    </div>
  );
}

      <p>Promoções do dia: {promocoes.length}</p>
    </div>
  );
}

Os dois pedidos saem praticamente juntos, e cada um atualiza o seu estado quando a resposta chega. Não importa a ordem em que chegam: cada set mexe em uma parte diferente da tela. Esse é o arranjo mais comum em uma tela de verdade — três ou quatro pedidos independentes no mesmo efeito, cada um com o seu set.

Se você precisar dos dois resultados juntos para fazer uma conta, aí vale o Promise.all: ele recebe um array de Promises e devolve uma Promise com um array de resultados, na mesma ordem. É o mesmo raciocínio de "dois pedidos, uma espera só", com a diferença de que o código depois do await roda uma vez, quando os dois chegaram.

7. Os quatro tropeços de quem busca dados

O primeiro é guardar a Promise no estado. const dados = buscarPaes(); setPaes(dados) parece certo e não é: dados é o objeto que promete, não a lista. O sintoma é uma tela que mostra "undefined" ou quebra ao tentar .map. A correção é sempre esperar: um await ou um .then.

O segundo é esquecer o .json(). Você faz o fetch, guarda o resultado no estado e a tela mostra um objeto cheio de coisas estranhas. O corpo da resposta é um fluxo de bytes que só vira lista depois da leitura; sem ela, você está guardando a embalagem.

O terceiro é o useEffect(async () => { ... }). Funciona, com um aviso no console, e deixa o código sem o lugar natural da limpeza. A forma certa é a da seção 5: uma função async dentro do efeito e uma chamada logo depois. O quarto é pedir duas vezes sem querer, e o sintoma dele engana. Os quatro, com sintoma e conserto, cabem em uma tabela de consulta rápida:

O que você vêProvável causaO conserto
a tela mostra undefined ou quebra no .mapa Promise foi guardada no estado em vez dos dadosespere com .then ou await antes do set
o estado guarda um objeto com status e cabeçalhosfaltou resposta.json()leia o corpo antes de guardar

O quarto tropeço merece um parágrafo à parte, porque o sintoma engana. No modo de desenvolvimento, o StrictMode monta, desmonta e monta de novo cada componente para revelar efeitos que não sabem se limpar. Com um fetch no efeito, isso significa dois pedidos no painel de rede — e, em produção, um pedido só. Se a sua API cobra por requisição ou registra cada acesso, vale saber que o número que você vê no desenvolvimento é o dobro. O conserto de verdade é a limpeza: cancelar o pedido que não interessa mais, o que a aula de cleanup mostra com o AbortController e com uma variável de controle.

GET https://loja.test/api/paes net::ERR_NAME_NOT_RESOLVED
TypeError: Failed to fetch
    at carregar (App.jsx:12:26)

Essa é a cara de um pedido que não saiu. fetch rejeita a Promise e o erro só aparece se você tratar — no código acima, ninguém tratou, e o React registra o erro no console enquanto a tela fica no estado anterior. Tratar esse caso é a aula seguinte, "Carregando e Erro".

8. Como a caixa simula a internet

As caixas deste guia rodam dentro de um quadro isolado, sem rede: não há servidor da padaria para responder. Por isso as funções buscarPaes, buscarHorario e buscarPromocoes existem nos exemplos — elas fazem o papel do fetch, devolvendo uma Promise que se resolve depois de alguns milissegundos com uma lista fixa.

O desenho é o mesmo do fetch em um ponto essencial: a resposta não está disponível na hora. Quando você troca a função simulada por fetch("https://loja.test/api/paes"), nada mais muda no componente: o estado, o efeito, o set e o .then continuam iguais. É por isso que vale aprender com a simulação — o formato do código é o formato de verdade.

E é por isso também que os atrasos são pequenos: 10 milissegundos. O painel espera um instante depois de montar o componente e mostra o resultado; se a simulação demorasse três segundos, o painel mostraria a tela vazia, que é o que o seu navegador mostra enquanto a resposta não chega. Na próxima aula esse intervalo vazio ganha um nome e um tratamento: é o estado de carregando.

9. Cenários do dia a dia

Cenário 1: o componente aparece antes dos dados

É o esperado, não um bug. Todo componente que busca dados passa por um instante com a lista vazia. O que muda de um projeto para outro é o que se mostra nesse instante: nada, um "carregando…", ou um esqueleto cinza do tamanho do conteúdo. Deixar a tela em branco é aceitável em um site pequeno; em uma tela cheia, o leitor acha que a página quebrou.

Cenário 2: os dados chegam e a tela não atualiza

Quase sempre a causa é uma referência perdida: a lista chegou, mas o set foi chamado em uma variável que não é o estado, ou o estado foi declarado no componente de baixo e atualizado no de cima. Outra causa comum é o efeito com [] que roda antes de a URL estar pronta — quando o endereço depende de uma prop, ele precisa estar no array de dependências.

Cenário 3: o pedido que responde fora de ordem

A Ana busca pelo termo "pão" e logo depois muda para "queijo". Dois pedidos saem, e o do "pão" pode voltar depois do "queijo" — a tela mostraria o resultado antigo. Isso se chama corrida, e o conserto é a limpeza do efeito: marcar que aquele pedido não interessa mais quando um novo começa. Guarde o nome; a aula de cleanup resolve com poucas linhas.

Exercício: a busca da promoção

Complete o efeito para guardar no estado o resultado da busca de promoções:

useEffect(() => { buscarPromocoes().((lista) => setPromocoes(lista)); }, []);

Dica: é o método que recebe a função a ser chamada quando a Promise se resolver. Sem ele, a lista nunca chega ao estado.

11. Resumo

Buscar dados é um efeito: o componente desenha o que tem, o efeito pede, a resposta chega e o set provoca um novo desenho. O pedido vive dentro de um useEffect com [] quando deve sair uma vez só, e nunca no corpo do componente — o corpo roda muitas vezes e não pode esperar nada.

Com .then ou com await dentro de uma função async declarada no efeito, o resultado sempre passa por um set. No projeto de verdade, o fetch exige dois passos: a resposta, depois o .json(), com uma conferência de resposta.ok no meio. Dois pedidos independentes saem juntos; dois pedidos em série esperam um pelo outro.

E o intervalo entre pedir e receber é parte do problema, não um acidente: a tela precisa dizer o que está acontecendo nesse meio-tempo, e precisa saber o que fazer quando a resposta é um erro. É exatamente o assunto da próxima aula.

Para lembrar

  • Pedido de dados é efeito: useEffect(() => { ... }, []).
  • O resultado mora em um estado, e só entra nele por set.
  • fetch(url) devolve a resposta; resposta.json() devolve os dados.
  • Confira resposta.ok: erro 404 ou 500 não rejeita a Promise.
  • Promise no estado é bug: espere com .then ou await.
  • async vai na função de dentro do efeito, não no useEffect.
  • Pedidos independentes: cada um com o seu set, sem esperar o outro.
  • Pedido que depende do anterior: await em sequência, na mesma função.
  • No desenvolvimento o efeito roda duas vezes e os pedidos também.
  • Enquanto a resposta não chega, a tela mostra o estado anterior ou um aviso.
