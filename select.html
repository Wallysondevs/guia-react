Select

No pedido da padaria, o cliente precisa escolher entre retirar no balcão e receber em casa. São poucas opções, sempre as mesmas, e só uma pode valer por vez — o caso perfeito para o select, aquela listinha que abre com uma setinha. A Ana já sabe ligar um campo ao estado, mas o select guarda o valor num lugar diferente: não no campo, e sim na opção escolhida. Nesta aula ela aprende a ler esse valor, criar uma opção vazia para o campo começar sem escolha e gerar as opções a partir de uma lista.

Você vai aprender
  • Como o select e as option se organizam.
  • Por que o value fica no select e não em cada opção.
  • Como ligar a escolha ao estado com value e onChange.
  • A diferença entre o valor guardado e o texto que aparece na lista.
  • Como usar uma opção vazia para o campo começar sem escolha.
  • Como gerar as opções a partir de uma lista com map e key.
  • O que fazer com o selected do HTML antigo e com defaultValue.

1. A cena: uma escolha entre poucas opções

A padaria entrega de bicicleta no bairro e atende no balcão. No site, o cliente escolhe: retirar no balcão ou receber em casa. A Ana poderia usar dois checkbox, mas aí o cliente poderia marcar os dois — e não faz sentido retirar e receber ao mesmo tempo. Poderia usar um campo de texto, mas aí alguém escreveria "retirada", "Retirada" ou "vou buscar", e ela teria de adivinhar. O select resolve as duas coisas: mostra só as opções que existem e deixa marcar uma.

O elemento é uma caixa fechada. Fechada, ela mostra a opção escolhida; aberta, mostra a lista. Quem abre é o navegador, não o React, e é por isso que a lista muda de aparência em cada sistema: no celular vira uma rodinha, no computador vira um menu. O que o React controla é qual opção está escolhida, e isso vem do estado.

No começo, a Ana achou que o select seria só mais um campo com value e onChange. É quase isso, com uma pegadinha: o texto que aparece na tela (o rótulo da opção) não é o valor guardado. Quem guarda é o atributo value da option. Separar os dois é o que permite exibir "Retirar no balcão" e guardar "retirada" — um texto curto e previsível para o código usar.

2. As peças do select

O select é o pai; cada option é uma escolha. O React trata o conjunto como um campo só: você escuta a mudança no select, não em cada opção. As peças têm nomes que voltam na documentação:

select
A caixa de escolha. Recebe value (o valor escolhido), onChange e os atributos comuns de campo, como id e name.
option
Cada escolha da lista. O atributo value é o que vai para o estado; o texto entre as tags é o que aparece na tela.
rótulo
O texto visível da opção: "Retirar no balcão". Serve para o olho; não é o valor guardado.
opção vazia
Uma option com value="" e texto "Escolha…". Serve para o campo começar sem escolha e para detectar que a pessoa ainda não decidiu.
map
O jeito de transformar uma lista de dados em uma lista de option, cada uma com a sua key.

A primeira consequência prática é que o value do select precisa casar com o value de alguma opção. Se o estado vale "entrega" e nenhuma opção tem esse valor, o navegador mostra a primeira da lista e você fica com a impressão de que o estado não funciona. Não é bug: é um valor órfão. O console do navegador chega a avisar em modo de desenvolvimento, mas o sintoma visível é a escolha "voltando" para o começo.

O segundo detalhe é a leitura do valor. Como o evento acontece no select, e.target.value entrega o value da opção escolhida — e não o texto dela. É por isso que a Ana planeja os valores com calma: "retirada" e "entrega" são fáceis de comparar e de mandar para o servidor depois.

3. O select controlado

Ligar o select ao estado é o mesmo par de sempre, com uma diferença: o value vai no select, e não em cada option. O componente abaixo já tem o estado e já tem um botão que muda a escolha por código — o que falta é o campo obedecer:

O select está solto e o parágrafo mostra sempre "retirada". Ligue o campo ao estado com value={entrega} e onChange e mostre Você escolheu: {entrega}. Depois clique em Quero entrega.

function App() {
  const [entrega, setEntrega] = useState("retirada");
  return (
    <div>
      <label htmlFor="entrega">Como você quer receber?</label>
      <select id="entrega">
        <option value="retirada">Retirar no balcão</option>
        <option value="entrega">Entrega em casa</option>
      </select>
      <button onClick={() => setEntrega("entrega")}>Quero entrega</button>
      <p>Você escolheu: retirada</p>
    </div>
  );
}

      </select>

    </div>

}

Na prévia, escolha uma opção na setinha e veja o parágrafo mudar junto. O botão faz o mesmo caminho por dentro: chama setEntrega("entrega") e o select se atualiza porque o value dele vem do estado. É a prova mais clara de quem manda no campo — o estado, não o clique. Se você ligar só o select e deixar o parágrafo fixo, a escolha muda na caixa e o texto não acompanha; se ligar só o parágrafo, o texto muda e a caixa fica na opção antiga.

Repare também no que não aparece no painel: nenhuma opção fica com o atributo selected. O React aplica a escolha como propriedade do elemento, do mesmo jeito que faz com o valor de um input. O painel mostra a estrutura; a opção marcada é estado vivo. Por isso a conferência de um select controlado se faz pelo texto que depende dele, não pelo HTML.

4. O valor guardado não é o rótulo

Essa separação entre valor e rótulo é o que dá força ao select. A tabela abaixo mostra as combinações que você vai encontrar, com o que entra no estado em cada uma:

O que você escreveuO que aparece na listaO que vai para o estado
<option value="retirada">Retirar no balcão</option>Retirar no balcão"retirada"
<option value="entrega">Entrega em casa</option>Entrega em casa"entrega"
<option value="">Escolha…</option>Escolha…"" (string vazia)
<option>Pão de queijo</option>Pão de queijoo próprio texto "Pão de queijo"

A última linha é legal e perigosa. Quando a option não tem value, o navegador usa o texto como valor. Funciona, mas amarra o dado ao rótulo: no dia em que você trocar "Pão de queijo" por "Pão de queijo quentinho", todo código que comparava com o texto antigo para de funcionar. Para listas pequenas e fixas, tudo bem; para dados que vêm de uma lista, dê um value próprio — um id, um código, uma palavra curta — e deixe o rótulo só para a tela.

No console, dá para ver os dois lados da escolha — o que aparece e o que é guardado:

e.target.value: "retirada"
typeof e.target.value: string
e.target.selectedOptions[0].text: "Retirar no balcão"

O mesmo cuidado vale para preço. Se a opção guarda o preço, o estado recebe texto ("12.50") e você converte com Number() antes de somar, como fez no campo numérico. Uma alternativa é guardar o id do produto e procurar o preço na lista; é o caminho que a aula de listas segue. Por enquanto, a regra é: o valor é o dado que você quer no código, o rótulo é o que o cliente lê.

5. A opção vazia: o campo que começa sem escolha

Um select sem value inicial mostra a primeira opção, e isso pode enganar: o cliente abre o site e vê "Retirar no balcão" marcado sem ter escolhido nada. Pior: se a primeira opção for "Centro", o frete do Centro aparece antes de o cliente dizer onde mora. A solução é uma opção vazia no começo e um estado inicial vazio. Aí o campo começa pedindo uma escolha e o código sabe que "" significa "ainda não decidiu".

A Ana usa isso no frete: o centro é grátis (ela mesma entrega de bicicleta), os outros bairros pagam R$ 9. Enquanto o cliente não escolher, o site não deve mostrar preço nenhum — deve pedir a escolha.

Enquanto o bairro estiver vazio, mostre Escolha o bairro para ver o frete. Quando for centro, mostre Frete: R$ 0; nos outros, Frete: R$ 9.

function App() {
  const [bairro, setBairro] = useState("");
  return (
    <div>
      <label htmlFor="bairro">Bairro da entrega</label>
      <select
        id="bairro"
        value={bairro}
        onChange={(e) => setBairro(e.target.value)}
      >
        <option value="">Escolha o bairro</option>
        <option value="centro">Centro</option>
        <option value="jardim">Jardim</option>
        <option value="vila">Vila Nova</option>
      </select>
      <p>Frete: R$ 9</p>
    </div>
  );
}

A expressão dentro das chaves é um if de uma linha: condição, interrogação, valor se verdadeiro, dois-pontos, valor se falso. Ela aparece tanto no frete quanto no parágrafo. Se preferir, dá para escrever com if normal antes do return, guardando o texto numa variável. O importante é que a mensagem e o preço venham do mesmo estado — assim nunca aparece "R$ 9" com o campo vazio.

Escolha o Centro na prévia e o texto muda para "Frete: R$ 0". Volte para "Escolha o bairro" e a mensagem volta. Esse vaivém é o teste que pega a maioria dos bugs de select: o estado inicial, a opção vazia e a condição precisam combinar. Quando um dos três está errado, o site mostra frete para quem não escolheu nada ou esconde o valor de quem escolheu.

6. Opções que vêm de uma lista

Enquanto são duas ou três opções, escrever cada option na mão é razoável. Quando a vitrine tem cinco sabores — e amanhã pode ter oito —, vale gerar as opções a partir de uma lista com map. Cada item vira uma option, e o key diz ao React qual item é qual quando a lista muda.

A lista sabores tem cinco itens, mas só dois viraram opção. Gere todas com map, dando key e value iguais ao sabor, e mostre {sabores.length} sabores na vitrine.

const sabores = ["Pão francês", "Pão de queijo", "Croissant", "Brioche", "Sonho"];

function App() {
  const [sabor, setSabor] = useState("Pão francês");
  return (
    <div>
      <label htmlFor="sabor">Sabor</label>
      <select
        id="sabor"
        value={sabor}
        onChange={(e) => setSabor(e.target.value)}
      >
        <option value="Pão francês">Pão francês</option>
        <option value="Pão de queijo">Pão de queijo</option>
      </select>
      <p>Escolhido: {sabor}</p>
    </div>
  );
}

  const [sabor, setSabor] = useState("Pão francês");
  return (

        id="sabor"
        value={sabor}
        onChange={(e) => setSabor(e.target.value)}
      >
        {sabores.map((s) => (
          <option key={s} value={s}>{s}</option>
        ))}
      </select>
      <p>Escolhido: {sabor}</p>

    </div>

}

Uma conferida rápida no console mostra a lista e o valor escolhido:

sabores.length: 5
sabor: "Pão francês"
typeof sabor: string

Rode e conte as opções no painel: são cinco, na ordem da lista. O value e o rótulo são o mesmo texto aqui, porque o sabor já é um nome curto e único. Numa lista de produtos de verdade, o valor seria o código do produto e o rótulo seria o nome com o preço: value={produto.id} e {produto.nome} entre as tags.

Sobre o key: ele não aparece no HTML e não é uma prop que o componente recebe; é uma identidade para o React saber o que mudou entre um desenho e outro. Usar o próprio texto funciona quando os itens são únicos — dois "Pão francês" na lista dariam duas chaves iguais e o React reclamaria no console. Se você já tem um id, use o id. A aula da key cobre os detalhes, e vale reler depois de mexer com listas de verdade.

7. O selected do HTML antigo e o defaultValue

Quem vem do HTML escreve <option selected> para marcar a escolha inicial. No React isso é o caminho errado: quem diz qual opção está marcada é o value do select. Se você deixar selected em uma opção e também passar value, os dois brigam e o React avisa no console em desenvolvimento. A regra é simples: um dono só, o estado.

Existe uma exceção para campo não controlado: defaultValue="entrega" faz o select começar naquela opção, e a partir dali o navegador cuida da escolha. É o equivalente do texto entre as tags do textarea: serve para não controlar. Se você precisa acompanhar a escolha — e quase sempre precisa —, fique com useState + value. A diferença entre os dois caminhos tem aula própria mais adiante, e o resumo é: controlado quando você quer saber, não controlado quando o valor só vai ser lido no envio.

No HTML antigoNo React controladoPor quê
<option selected>value={forma} no selectum dono só para a escolha: o estado

Um caso em que defaultValue aparece com naturalidade é o formulário de edição, que já vem preenchido com o pedido do cliente. Mesmo ali, se a tela mostra um resumo que muda enquanto a pessoa escolhe, o controlado ganha. O critério é sempre o mesmo: a tela depende do valor agora? Então estado.

Vale conhecer também o disabled na option, que serve para mostrar uma escolha indisponível — "Sonho: esgotado" — sem tirá-la da lista. E o name no select, que identifica o campo no envio do formulário, assunto da aula de envio. Nenhum dos dois muda o mecanismo de estado.

8. Um select que muda o resto da tela

O poder do select aparece quando ele decide o que os outros campos fazem. A forma de pagamento é o exemplo clássico: Pix mostra a chave, cartão mostra a maquininha, dinheiro mostra o campo de troco. Cada escolha liga um pedaço diferente da tela, e tudo isso sai de um único estado.

function Pagamento() {
  const [forma, setForma] = useState("pix");

  return (
    <div>
      <label htmlFor="forma">Forma de pagamento</label>
      <select
        id="forma"
        value={forma}
        onChange={(e) => setForma(e.target.value)}
      >
        <option value="pix">Pix</option>
        <option value="cartao">Cartão na entrega</option>
        <option value="dinheiro">Dinheiro</option>
      </select>

      {forma === "pix" && <p>Chave Pix: ana@loja.test</p>}
      {forma === "cartao" && <p>Leve a maquininha</p>}
      {forma === "dinheiro" && <p>Separe o troco, por favor</p>}
    </div>
  );
}

O && é o "e" lógico: se a condição for verdadeira, o React desenha o elemento da direita; se for falsa, não desenha nada. É a mesma renderização condicional que você já viu, aplicada a três casos exclusivos. Como só uma forma pode valer por vez, só um parágrafo aparece por vez — e o select é o interruptor.

Se a lista de formas crescer, dá para guardar um objeto por forma e mostrar o detalhe com formas.find(...). A ideia continua: um estado, uma escolha, o resto derivado. O que você não quer é um estado para o select e outro para o texto que ele deveria determinar — dois donos para o mesmo dado é o começo de uma tela que se contradiz.

9. Cenários do dia a dia

Cenário 1: a escolha volta para a primeira opção

A Ana mudava o estado para "entrega" e a caixa insistia em mostrar "Retirar no balcão". Havia uma opção com o rótulo "Entrega em casa", mas o value estava escrito "Entrega", com maiúscula. O select procura uma opção com valor exatamente igual a "entrega", não acha e cai na primeira. Valor é texto exato: maiúscula, acento e espaço contam.

Cenário 2: o preço do frete aparece antes da escolha

O campo começava na primeira opção ("Centro") e o texto já mostrava "Frete: R$ 0" para quem nunca escolheu nada. A correção foi a opção vazia com value="" e o estado começando em "". Agora o site pede a escolha, e o código distingue "não decidiu" de "escolheu o Centro". Sem a opção vazia, não existe esse estado intermediário.

Cenário 3: as opções vêm de uma lista e a escolha some

Ela passou a gerar as opções com map e a escolha inicial parou de aparecer. O useState guardava "Pão francês" e a lista tinha exatamente esse texto — mas um item era a string "Pão francês" e o outro vinha de um objeto, com a propriedade nome. O valor guardado precisa ser do mesmo tipo e conteúdo do value da opção. Quando a lista é de objetos, guarde o id e compare ids.

Exercício: o valor da opção

O select guarda o valor da opção escolhida. Na opção abaixo, o rótulo é "Retirar no balcão" e o estado deve receber "retirada". Complete o atributo que falta, escrevendo só a palavra que o valor deve ter:

<option ="retirada">Retirar no balcão</option>

Dica: é o atributo que o select lê para saber qual opção está marcada. Sem ele, o navegador usaria o texto "Retirar no balcão" como valor — e aí o estado receberia a frase inteira.

11. Resumo

O select é a caixa de escolha única: um pai select com value e onChange, e várias option com o valor que interessa ao código. O estado guarda o value da opção escolhida, não o rótulo. Para começar sem escolha, use uma opção com value="" e o estado inicial vazio; para listas maiores, gere as opções com map e dê uma key estável a cada uma.

O selected do HTML antigo não se usa: o dono da escolha é o estado. defaultValue existe para o caso não controlado, e o critério para escolher entre os dois é sempre o mesmo — a tela depende do valor agora? Se sim, estado; se o valor só vai ser lido no envio, defaultValue resolve. E cuidado com valores órfãos: o value do select precisa casar exatamente com o value de alguma opção, letra por letra.

O formulário da padaria já tem campo curto (input controlado), campo longo (textarea) e escolha única. Falta o caso em que a resposta é sim ou não, e o caso em que várias respostas podem valer ao mesmo tempo — o checkbox, que guarda um booleano em vez de um texto. A próxima parada é essa, e a primeira surpresa vai ser o e.target.checked, que não existe nos campos que você viu até aqui.

Para lembrar

  • value fica no select; value de cada option é o dado.
  • O rótulo é o texto entre as tags; o valor é o atributo value.
  • O valor precisa casar exatamente com uma das opções; senão a primeira aparece.
  • <option value=""> cria o estado "ainda não escolheu".
  • onChange no select entrega e.target.value.
  • map + key geram as opções a partir de uma lista.
  • Não use selected no JSX controlado; o estado é o dono.
  • defaultValue é para campo não controlado.
  • option sem value usa o texto como valor — evite.
  • Preço vindo de opção é texto: converta com Number().
