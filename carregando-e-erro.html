Carregando e Erro

A Ana colocou a busca no efeito e a vitrine passou a vir do servidor. Só que agora, nos três segundos entre abrir o site e receber os pães, o cliente vê uma tela quase vazia — e não sabe se o site está carregando ou se quebrou. Pior: quando o servidor da padaria cai, a tela fica vazia para sempre, sem uma palavra de explicação. Nesta aula a Ana aprende que toda busca tem três estados e que os dois mais esquecidos são justamente os que o cliente vê.

Você vai aprender
  • Os três estados de qualquer busca: carregando, pronto e erro.
  • Por que o estado inicial é null e não uma lista vazia.
  • Como mostrar um aviso de carregando sem atrapalhar a tela.
  • Como tratar a falha com .catch e com try/catch.
  • Como garantir que o carregando sempre termine, com .finally.
  • Como montar um botão de tentar de novo que realmente refaz o pedido.
  • A diferença entre a mensagem técnica do erro e a mensagem que o cliente entende.

1. A cena: os três segundos de silêncio

O site da Ana agora busca os pães no servidor. No computador dela, na mesma rede da padaria, a resposta chega em 40 milissegundos e ninguém percebe o intervalo. No celular de um cliente na rua, com internet ruim, são três segundos. Durante três segundos a tela mostra o título "Padaria da Ana" e mais nada. O cliente faz o que qualquer pessoa faz: acha que o site quebrou e fecha.

Esse intervalo não é um defeito a ser eliminado — é a natureza de pedir dados pela rede. Nenhuma técnica faz a resposta chegar instantaneamente. O que você controla é o que a tela diz enquanto espera. E a resposta é simples: diz que está esperando. Um parágrafo "Carregando os pães…" resolve mais do que qualquer otimização, porque troca a dúvida por uma informação.

O outro lado do intervalo é o erro. Se o servidor estiver fora do ar, a resposta não vem; se vier, vem com um código de problema. Um componente que só sabe tratar o caso feliz fica travado na tela vazia — e nem o console do cliente nem o seu mostram por quê. Tratar o erro é o que separa um protótipo de um site que a padaria pode deixar no ar no domingo.

2. Os três estados de qualquer busca

Toda busca, em qualquer tela, tem três situações e nunca mais de uma ao mesmo tempo: ainda não sei (carregando), eu sei (pronto), deu problema (erro). O componente precisa saber desenhar as três, e a forma mais simples de fazer isso é guardar cada uma em um estado próprio e decidir no JSX.

carregando
A situação entre o pedido e a resposta. Representada por dados === null ou por um estado booleano separado, carregando.
pronto
A resposta chegou e virou uma lista no estado. É o caso que você já sabe desenhar.
erro
A resposta não veio ou veio com problema. Guarde a mensagem em um estado para poder mostrá-la.
estado inicial
O valor que o estado tem antes da primeira resposta: null para "ainda não sei", [] para "sei, e está vazio".
tentar de novo
Um botão que provoca um novo pedido sem recarregar a página — na prática, um contador nas dependências do efeito.

Existe mais de um jeito de organizar isso. Um deles é um estado booleano carregando mais um estado erro mais um estado dados — três useState. Outro é usar null como "ainda não sei" e um estado erro — dois. Outro ainda é um único estado com um objeto { estado: "carregando" }. Todos funcionam; o importante é que nunca existam dois estados dizendo coisas contraditórias, como "carregando" e "pronto" ao mesmo tempo.

EstadoComo representarO que a tela mostra
carregandodados === null e erro === null"Carregando os pães…"
pronto, com dadosum array no estadoa lista
pronto, vazioum array vazio"hoje não tem pão"

Repare na terceira linha: "pronto, vazio" é diferente de "carregando". Uma lista vazia é uma resposta legítima — a padaria pode não ter pão nenhum naquele dia, e o cliente precisa ler isso, não um aviso de carregando eterno. É por isso que o estado inicial dos dados é null: null é "não sei", [] é "sei, e não tem nada".

3. Mostrando o carregando

A caixa a seguir tem a busca funcionando e o estado começando em null. Rode o código inicial: o painel mostra só o título. A busca desta caixa demora três segundos de propósito — assim você vê o problema que o cliente vê. A missão é mostrar um aviso enquanto paes for null.

Enquanto paes for null, mostre o parágrafo Carregando os pães…. Não mude a busca; mude só o que a tela mostra na espera.

function buscarPaes() {
  return new Promise((ok) => {
    setTimeout(() => ok(["pão francês", "croissant"]), 3000);
  });
}

function App() {
  const [paes, setPaes] = useState(null);

  useEffect(() => {
    buscarPaes().then((lista) => setPaes(lista));
  }, []);

  return (
    <div>
      <h1>Padaria da Ana</h1>
      {paes && <p>Pães na vitrine: {paes.length}</p>}
    </div>
  );
}

Repare que a condição da solução é paes === null, e não !paes. Os dois funcionam aqui, mas === null diz exatamente o que você quer dizer: "ainda não sei". Se o estado fosse uma lista vazia, !paes seria falso e o aviso nunca apareceria; e se fosse undefined, os dois dariam verdadeiro por acidente. Escrever a condição de propósito evita que o código mude de comportamento quando o estado mudar de forma.

O painel mostra o retrato do primeiro instante: <p>Carregando os pães…</p>. Se você esperar três segundos na prévia, os pães aparecem — é o segundo render, quando a resposta chega. Essa troca é o coração do assunto: a mesma tela, dois desenhos diferentes, e o leitor acompanhando sem susto.

Duas decisões de projeto aparecem aqui. A primeira é onde o aviso fica: substituindo o conteúdo inteiro ou só a área dos pães? Se o título e o menu já estão prontos, é melhor trocar só a área — a tela não "pisca". A segunda é o texto: "Carregando…" funciona; "Buscando os pães de hoje…" é melhor, porque diz o que está acontecendo e distrai a espera.

4. Quando a resposta é um erro

Agora o caso que ninguém desenha. O servidor da padaria está fora do ar e a Promise é rejeitada. No código atual, ninguém trata a rejeição: o React não faz nada, a tela continua no estado anterior e o navegador registra um aviso no console que o cliente nunca vai abrir. É o pior tipo de falha, a que não avisa. O aviso é este, e ele fica só ali:

Uncaught (in promise) Error: sem conexão
    at App.jsx:7:31

Tratar significa dizer o que fazer quando a resposta não vier. Com .then, é um .catch no fim da fila. Com async/await, é um try/catch em volta das chamadas. Nos dois casos, o erro vira um estado, e o estado vira um parágrafo na tela.

A busca falha (a Promise é rejeitada) e a tela não avisa nada. Guarde a mensagem do erro em um estado e mostre o parágrafo Deu ruim: sem conexão.

function buscarPaes() {
  return new Promise((ok, falha) => {
    setTimeout(() => falha(new Error("sem conexão")), 20);
  });
}

function App() {
  const [paes, setPaes] = useState(null);

  useEffect(() => {
    buscarPaes().then((lista) => setPaes(lista));
  }, []);

  return (
    <div>
      <h1>Padaria da Ana</h1>
      {paes && <p>Pães na vitrine: {paes.length}</p>}
    </div>
  );
}

O .catch roda quando qualquer coisa antes dele falha — o pedido, a leitura do JSON, ou um throw seu no meio. E o parâmetro e é o objeto do erro; e.message é o texto que descreve o problema. Guardar esse texto em um estado é o que permite mostrar na tela a mesma informação que estava escondida no console.

Cuidado com uma armadilha de ordem: .catch depois do .then certo é o que captura o erro do pedido. Se você inverter — .catch antes, .then depois —, o erro é capturado mas o .then ainda roda, com um valor indefinido. A fila é lida da esquerda para a direita, e cada erro pula os passos até o primeiro .catch.

5. Com async: try, catch e finally

Na forma com await, o mesmo tratamento fica em bloco. O try guarda o código que pode falhar, o catch recebe o erro, e o finally roda de qualquer jeito — dando certo ou não. Esse último é o lugar perfeito para desligar o aviso de carregando, porque ele acontece nos dois caminhos.

useEffect(() => {
  async function carregar() {
    setCarregando(true);
    setErro(null);

    try {
      const resposta = await fetch("https://loja.test/api/paes");
      if (!resposta.ok) {
        throw new Error("o servidor respondeu " + resposta.status);
      }
      const lista = await resposta.json();
      setPaes(lista);
    } catch (e) {
      setErro(e.message);
    } finally {
      setCarregando(false);
    }
  }

  carregar();
}, []);

Repare nos dois set de limpeza: o efeito começa apagando o erro anterior e termina desligando o carregando. Sem o primeiro, uma tentativa nova mostraria a mensagem de erro antiga enquanto tenta de novo. Sem o segundo, um erro deixaria a tela em "carregando" para sempre — o sintoma mais confuso de todos, porque a tela parece lenta e está apenas travada.

6. O botão de tentar de novo

Mostrar o erro é meio caminho. O outro meio é dar ao cliente uma saída. Se o servidor voltou, ele aperta "Tentar de novo" e a lista aparece. Na caixa, o botão já existe e já soma uma tentativa; o que falta é o efeito perceber.

Como o efeito só roda uma vez (o array está vazio), somar a tentativa não provoca nada. O conserto é colocar a tentativa nas dependências: quando ela muda, o efeito roda de novo e um novo pedido sai. Esse truque — um contador como dependência — é a forma mais simples de "refazer o pedido" em React.

O botão Tentar de novo soma uma tentativa, mas o efeito não acompanha. Coloque a tentativa nas dependências do efeito para o segundo pedido acontecer.

function buscarPaes(tentativa) {
  return new Promise((ok, falha) => {
    setTimeout(() => {
      if (tentativa === 1) falha(new Error("sem conexão"));
      else ok(["pão francês", "croissant"]);
    }, 20);
  });
}

function App() {
  const [paes, setPaes] = useState(null);
  const [erro, setErro] = useState(null);
  const [tentativa, setTentativa] = useState(1);

  useEffect(() => {
    setErro(null);
    buscarPaes(tentativa)
      .then((lista) => setPaes(lista))
      .catch((e) => setErro(e.message));
  }, []);

  return (
    <div>
      <h1>Padaria da Ana</h1>
      {erro && <p>Deu ruim: {erro}</p>}
      {paes && <p>Pães na vitrine: {paes.length}</p>}
      <button id="tentar" onClick={() => setTentativa(tentativa + 1)}>
        Tentar de novo
      </button>
    </div>
  );
}

O painel já mostra o estado depois do clique: o erro some, os pães aparecem. A simulação foi montada para falhar na primeira tentativa e funcionar na segunda — do contrário não haveria o que consertar. No mundo de verdade, a segunda tentativa pode falhar também, e o botão continua ali para a terceira.

Note o setErro(null) no começo do efeito. Ele apaga a mensagem antes de pedir de novo, para a tela não mostrar um erro que já está sendo resolvido. E note também que o paes anterior fica no estado durante a nova tentativa: se houvesse dados na tela, eles continuariam visíveis, o que costuma ser melhor do que apagar tudo e mostrar um espaço branco.

7. A mensagem certa para quem lê

O erro que o programador quer ver e o erro que o cliente precisa ver são diferentes. O primeiro é técnico e mora no console; o segundo é uma frase em português que diz o que aconteceu e o que fazer. Mostrar TypeError: Failed to fetch para o cliente da padaria não ajuda ninguém.

Uma prática comum é traduzir na entrada do estado: guardar uma mensagem falada, não o texto cru. Se o problema foi rede, "Não conseguimos falar com o servidor. Confira a internet e tente de novo." Se foi um 404, "Não encontramos essa página." Se foi 500, "A padaria está com um problema aqui. Já estamos consertando." O texto cru continua indo para o console, para você.

try {
  const resposta = await fetch("https://loja.test/api/paes");
  if (!resposta.ok) {
    throw new Error("status " + resposta.status);
  }
  const lista = await resposta.json();
  setPaes(lista);
} catch (e) {
  console.error(e);                            // para você
  setErro("Não conseguimos carregar os pães."); // para o cliente
}

Há ainda um caso que não é deste efeito: o erro de render. Se um componente quebra no meio do JSX — porque um dado veio em formato inesperado, por exemplo —, o React desmonta a árvore inteira e a tela fica em branco. Tratar isso exige um componente especial chamado error boundary, assunto de um nível mais adiante. Vale saber que os dois erros existem e que o .catch do efeito não pega o segundo.

GET https://loja.test/api/paes 500 (Internal Server Error)
Uncaught (in promise) Error: status 500

Essas duas linhas são o que o cliente não deve ver, e é exatamente o que aparece quando o tratamento é esquecido. A primeira é do navegador, mostrando o status que voltou; a segunda é a rejeição da Promise sem .catch. Com o tratamento no lugar, sobra só a frase combinada na tela.

8. Os três estados na mesma tela

Juntando tudo, o desenho completo de um componente que busca dados tem esta forma: dois ou três estados, um efeito que liga o carregando, um catch que guarda a mensagem, um finally que desliga o carregando, e um JSX que escolhe o que mostrar em cada caso.

function App() {
  const [paes, setPaes] = useState(null);
  const [erro, setErro] = useState(null);

  useEffect(() => {
    buscarPaes()
      .then((lista) => setPaes(lista))
      .catch((e) => setErro(e.message));
  }, []);

  if (erro) return <p>Deu ruim: {erro}</p>;
  if (paes === null) return <p>Carregando os pães…</p>;

  return (
    <ul>
      {paes.map((p) => (
        <li key={p.nome}>{p.nome}</li>
      ))}
    </ul>
  );
}

O return antecipado é uma forma limpa de escrever isso: cada condição devolve a tela daquele estado e encerra a função, e o que sobra no fim é o caso feliz. Enquanto houver um return para cada caso, a leitura é de cima para baixo, sem aninhamento de if dentro do JSX. A aula de renderização condicional mostra as outras formas; todas funcionam.

O que não funciona é mostrar os três ao mesmo tempo. Se o estado de erro e o de dados convivem sem regra, o cliente vê a lista antiga com uma mensagem de erro em cima, ou um "carregando" eterno embaixo de uma lista já preenchida. A regra é: um estado por vez, e o JSX escolhe um.

9. Cenários do dia a dia

Cenário 1: o carregando que nunca termina

O cliente vê "Carregando…" para sempre e o servidor está bem. Na maioria dos casos o setCarregando(false) ficou só no .then, e ninguém desligou o aviso no caminho do erro. O .finally resolve porque roda nos dois casos. A outra causa provável é o set sendo chamado em um componente que já saiu da tela — aí a limpeza do efeito é o assunto.

Cenário 2: a mensagem de erro some antes de o cliente ler

Em um projeto com atualização automática, o erro é apagado por um pedido novo que falha de novo, e o texto pisca. O sintoma é a impressão de que "nada acontece". Uma saída é manter a mensagem até uma ação do cliente, e não até o próximo pedido; outra é deixar a mensagem visível enquanto a nova tentativa acontece, no lugar de limpá-la na hora.

Cenário 3: o botão de tentar de novo não faz nada

A causa quase sempre é a mesma: o contador mudou, mas não está no array de dependências do efeito. Sem ele no array, o React compara o array, não vê diferença e pula o efeito — nenhum pedido sai. O segundo suspeito é uma função que muda a cada render dentro do array, que faz o efeito rodar sem parar. A regra da aula de dependências continua valendo: liste o que o efeito lê.

11. Resumo

Toda busca tem três estados, e nenhum deles é opcional: carregando, pronto e erro. O estado inicial dos dados é null para dizer "ainda não sei" e permitir o aviso de espera; uma lista vazia é uma resposta, não uma espera. O erro vira estado por meio de .catch ou try/catch, e o .finally garante que o aviso de carregando desligue nos dois caminhos.

Para refazer o pedido sem recarregar a página, um contador de tentativas entra nas dependências do efeito: cada clique soma um, o React vê a mudança e roda o efeito de novo. E a mensagem que aparece na tela é uma tradução para o cliente, não o texto técnico do erro — esse fica no console, para você.

Com isso, o componente da Ana já pede, espera, mostra, erra e tenta de novo. O que ainda falta é o que acontece quando o componente sai da tela com um pedido no ar: a resposta chega depois, e ninguém está mais ali para receber. É o assunto da próxima aula, o cleanup.

Para lembrar

  • Três estados: carregando, pronto, erro. Um por vez.
  • null é "ainda não sei"; [] é "sei, e está vazio".
  • O aviso de carregando aparece enquanto os dados são null.
  • .catch ou try/catch transformam o erro em estado.
  • .finally roda nos dois caminhos: é o lugar de desligar o carregando.
  • Comece o efeito limpando o erro anterior: setErro(null).
  • Tentar de novo = um contador nas dependências do efeito.
  • Mensagem na tela em português; o erro técnico fica no console.
  • Erro no render não é pego pelo .catch: precisa de error boundary.
  • Um return para cada estado deixa o JSX legível, sem aninhar if.
