Higher-Order Components

A Ana tem três cartões no site — o pão do dia, a encomenda e o aviso de preço — e todos precisam da mesma moldura em volta: uma borda, o nome da padaria no topo e o mesmo espaçamento. Em vez de repetir a moldura em três componentes, ela escreve uma função que recebe um componente e devolve outro, já embrulhado. Esse é o Higher-Order Component, e o nome comprido esconde uma ideia de duas linhas.

Você vai aprender
  • O que é um HOC: uma função que recebe um componente e devolve um componente novo.
  • Como se escreve o primeiro HOC e como se usa o resultado no lugar do componente original.
  • Por que {...props} é obrigatório para o componente de dentro continuar funcionando.
  • Como um HOC injeta dados e como isso pode brigar com as props de quem chama.
  • O que acontece quando o HOC guarda estado: cada uso tem o seu, separado.
  • Como nomear o resultado para não se perder no DevTools.
  • Quando usar HOC, quando usar hook e quando usar render prop.

1. A cena: a mesma moldura em três cartões

No site da Ana, três componentes diferentes aparecem dentro da mesma moldura: um cartão de pão, um cartão de encomenda e um cartão de aviso. A moldura é sempre a mesma — uma div com a classe moldura, o nome da padaria em negrito e o conteúdo embaixo. O que muda é o miolo.

A primeira solução é copiar a moldura nos três arquivos. Funciona até o dia em que ela decide que o nome da padaria fica no rodapé da moldura: três arquivos de novo. A segunda solução é criar um componente Moldura e usá-lo em volta dos outros três, com <Moldura><CartaoDePao /></Moldura>. Essa é boa, e é o assunto da aula de Slots com children: o conteúdo entra pelo buraco.

Só que existe uma terceira forma, mais antiga e ainda muito comum em bibliotecas: uma função que recebe o componente e devolve uma versão dele já embrulhada. Em vez de escrever a moldura em volta de cada uso, você embrulha o componente uma vez e passa a usar o resultado como se fosse o original. É o mesmo raciocínio de uma etiqueta: você não troca a caixa, cola a etiqueta nela.

O nome disso é Higher-Order Component, ou HOC. "Higher-order" é o mesmo termo que aparece em "higher-order function" — uma função que trabalha com outras funções. Um HOC não é um componente: é uma função que fabrica componentes. A distinção parece preciosismo e é a chave para não se perder mais adiante.

2. O que é um HOC, na prática

Um HOC recebe um componente como argumento e devolve uma função componente nova. A nova usa a original por dentro, acrescentando o que quiser em volta. Por convenção, o nome do HOC começa com com (ou with, em inglês) e o resultado ganha um nome que lembra os dois: comMoldura(Cartao) devolve CartaoComMoldura.

HOC
Função que recebe um componente e devolve outro componente. Não desenha nada sozinha: o desenho aparece quando o resultado é usado no JSX.
componente envolvido
O componente que entra no HOC, também chamado de wrapped. É ele que tem o conteúdo real, como o nome do pão.
componente envolvente
O componente que o HOC devolve, também chamado de wrapper. Ele desenha a moldura e chama o envolvido por dentro.
repassar props
Entregar ao componente de dentro as props que o wrapper recebeu, com {...props}. Sem isso, o miolo recebe undefined em tudo.
displayName
Uma propriedade de texto que dá nome ao componente no React DevTools. Serve para o wrapper não aparecer como uma pilha de "Envolvido".

Duas consequências vêm de graça com essa definição. A primeira: o HOC roda uma vez, na hora em que você escreve comMoldura(Cartao) — não a cada desenho. A segunda: o resultado é um componente comum; pode ir para o JSX, pode entrar em outro HOC, pode receber props normalmente.

Para confirmar que os dois lados são funções e que o que muda é o que cada uma aceita, um log com typeof resolve:

console.log("typeof comMoldura: " + typeof comMoldura);
console.log("typeof CartaoComMoldura: " + typeof CartaoComMoldura);
typeof comMoldura: function
typeof CartaoComMoldura: function

As duas linhas dizem function, e isso não é erro: em JavaScript componente também é função. A diferença está no que cada uma recebe. comMoldura recebe um componente; CartaoComMoldura recebe props. Trocar uma pela outra é o erro mais comum da aula, e o sintoma é uma tela vazia.

3. O primeiro HOC: a moldura

Olhe o código. comMoldura recebe Componente e devolve Envolvido, uma função componente normal. Dentro dela, o <Componente {...props} /> desenha o componente original com todas as props que o wrapper recebeu. No fim, const CartaoComMoldura = comMoldura(Cartao) guarda o resultado.

O HOC comMoldura já está escrito, mas o App desenha o Cartao direto, sem moldura. Embrulhe o cartão com o HOC e use o resultado no App.

function Cartao({ nome }) {
  return <p>{nome}</p>;
}

function comMoldura(Componente) {
  return function Envolvido(props) {
    return (
      <div className="moldura">
        <strong>Padaria da Ana</strong>
        <Componente {...props} />
      </div>
    );
  };
}

function App() {
  return <Cartao nome="Pão francês" />;
}
<p>Pão francês</p>

const CartaoComMoldura = comMoldura(Cartao);

}

O painel mostra a div.moldura com o nome da padaria e, dentro, o parágrafo do cartão. O Cartao original não mudou uma linha, e continua podendo ser usado sem moldura em outro lugar do site. É a diferença entre mudar a peça e vestir a peça.

Repare no {...props}. Ele espalha todas as props recebidas pelo wrapper dentro do componente de dentro. Sem essa linha, o nome que o App passou ficaria preso no wrapper, e o Cartao receberia um objeto vazio — desenhando um parágrafo em branco. Parece um detalhe de sintaxe; é a diferença entre um HOC útil e um HOC que engole dados.

4. As props precisam atravessar

Vale ver o problema de perto, porque ele volta em todo HOC. O wrapper é um componente no meio do caminho: tudo o que o App passa chega primeiro a ele. Se ele não repassar, o dado morre ali. E o wrapper não sabe quais props o componente de dentro espera — nome, preco, onClick, o que for. Por isso a resposta certa é sempre repassar todas, com o espalhamento, em vez de listar as que você acha que existem.

Existem três jeitos de escrever a chamada, e a ordem importa quando há colisão de nomes. Escrever <Componente {...props} extra={1} /> faz a prop do HOC vencer; escrever <Componente extra={1} {...props} /> deixa quem chama sobrescrever. Nenhum dos dois está errado: são políticas diferentes. O primeiro garante que a injeção vale sempre; o segundo permite que a página faça exceções.

function comMoldura(Componente) {
  return function Envolvido(props) {
    console.log("props recebidas: " + Object.keys(props).join(", "));
    return (
      <div className="moldura">
        <strong>Padaria da Ana</strong>
        <Componente {...props} />
      </div>
    );
  };
}

Com <CartaoComMoldura nome="Pão francês" />, o console mostra quais props chegaram ao wrapper:

console: props recebidas: nome

Se a lista vier vazia e o miolo aparecer em branco, o problema está na chamada — o App não passou nada. Se vier com nome e o miolo continuar em branco, o problema está no {...props} que faltou dentro do wrapper. Duas perguntas, dois lugares diferentes para olhar.

5. O HOC que injeta dados

Além de embrulhar, um HOC pode acrescentar props. É o caso do desconto da padaria: o preço com 10% é uma regra do negócio, igual para todos os cartões, e não deveria ser digitada em cada página. O HOC injeta desconto e o componente de dentro usa o valor que recebeu.

O Preco recebe desconto={10} do HOC, mas mostra o valor cheio. Mostre o valor já com o desconto aplicado.

function comDesconto(Componente) {
  return function Envolvido(props) {
    return <Componente {...props} desconto={10} />;
  };
}

function Preco({ valor, desconto }) {
  return <p>R$ {valor}</p>;
}

const PrecoComDesconto = comDesconto(Preco);

function App() {
  return <PrecoComDesconto valor={40} />;
}
<p>R$ 40</p>

function comDesconto(Componente) {
  return function Envolvido(props) {
    return <Componente {...props} desconto={10} />;
  };
}

function Preco({ valor, desconto }) {
  return <p>R$ {valor - desconto}</p>;
}

const PrecoComDesconto = comDesconto(Preco);

function App() {
  return <PrecoComDesconto valor={40} />;
}

O painel passa de R$ 40 para R$ 30. O App nunca soube do desconto: passou o valor cheio e recebeu o preço final. É a mesma divisão de responsabilidades da aula anterior, com outra roupa — o HOC decide o dado, o componente decide o desenho.

Essa injeção tem um risco que vale conhecer: o nome da prop injetada não pode brigar com as props naturais do componente. Um HOC chamado comUsuario que injeta usuario quebra no dia em que alguém quiser passar outro usuário. A saída é escolher nomes improváveis (usuarioAtual) ou deixar o HOC receber a configuração: comDesconto(10)(Preco), um HOC que devolve outro HOC. A segunda forma é mais flexível e mais difícil de ler; use quando precisar mesmo.

6. O HOC que guarda estado

HOC também pode ter estado. O wrapper chama useState como qualquer componente e entrega ao de dentro tanto o valor quanto a função que muda. Isso permite reaproveitar comportamento — contar cliques, controlar aberto e fechado, guardar o texto digitado — sem repetir o useState em cada componente.

O HOC comCliques entrega cliques e aoClicar, mas o BotaoDePedido ignora os dois. Mostre o contador no botão e ligue o clique à função recebida.

function comCliques(Componente) {
  return function Envolvido(props) {
    const [cliques, setCliques] = useState(0);
    return <Componente {...props} cliques={cliques} aoClicar={() => setCliques(cliques + 1)} />;
  };
}

function BotaoDePedido({ texto }) {
  return <button>{texto}</button>;
}

const BotaoContado = comCliques(BotaoDePedido);

function App() {
  return <BotaoContado texto="Pão francês" />;
}
<button>Pão francês</button>

function comCliques(Componente) {
  return function Envolvido(props) {
    const [cliques, setCliques] = useState(0);
    return <Componente {...props} cliques={cliques} aoClicar={() => setCliques(cliques + 1)} />;
  };
}

function BotaoDePedido({ texto, cliques, aoClicar }) {
  return (
    <button onClick={aoClicar}>
      {texto} — {cliques}
    </button>
  );
}

const BotaoContado = comCliques(BotaoDePedido);

function App() {
  return <BotaoContado texto="Pão francês" />;
}

Cada clique no botão faz o painel mostrar um número maior. Duas coisas importantes aconteceram. A primeira: o estado vive no wrapper, não no BotaoDePedido — o botão é só o desenho. A segunda: se você usar <BotaoContado /> duas vezes, cada uso ganha o seu contador próprio, porque são duas instâncias do wrapper. Estado em React é sempre por instância.

E aqui está a maior diferença em relação a um hook: o estado do HOC não é acessível de fora. Se a página precisa saber o total de cliques de todos os botões, o HOC não serve — o número teria de subir para o componente pai, como a aula de Elevando o Estado mostra. HOC é bom para comportamento isolado, não para estado compartilhado entre irmãos.

7. Nome e identidade: o que não fazer

O React DevTools mostra a árvore de componentes pelo nome da função. Como todo HOC devolve uma função chamada Envolvido, a árvore vira uma pilha de Envolvido, Envolvido, Envolvido, e você perde a pista de qual é qual. O conserto é dar nome ao resultado com displayName, uma propriedade de texto que só serve para leitura:

function comMoldura(Componente) {
  function Envolvido(props) {
    return (
      <div className="moldura">
        <Componente {...props} />
      </div>
    );
  }
  Envolvido.displayName = "comMoldura(" + (Componente.displayName || Componente.name) + ")";
  return Envolvido;
}

Com isso o DevTools mostra comMoldura(Cartao) em vez de Envolvido. O Componente.name vem do nome da função; o displayName é o nome escolhido à mão, que vale mais quando existe. É um detalhe de depuração, mas economiza minutos toda vez que a árvore cresce.

Agora o erro caro: criar o HOC dentro do componente. Cada desenho do App cria uma função nova, e para o React uma função nova é um componente novo — ele desmonta o antigo e monta o novo do zero. O sintoma é estado que volta ao inicial, campo que perde o foco a cada letra, animação que reinicia. Se o HOC precisa de configuração, chame-o no topo do arquivo, fora de qualquer componente:

// errado: um componente novo a cada desenho do App
function App() {
  const Envolvido = comMoldura(Cartao);
  return <Envolvido nome="Pão francês" />;
}

// certo: criado uma vez, fora do componente
const CartaoComMoldura = comMoldura(Cartao);

function App() {
  return <CartaoComMoldura nome="Pão francês" />;
}

Um terceiro cuidado, mais raro: não altere o componente que entrou. Escrever Componente.novoMetodo = ... ou mexer nas props dele por fora quebra o componente para todos os outros usos. O HOC só pode devolver um componente novo que usa o antigo — nunca modificar o antigo.

Por isso vale a regra de revisão — todo HOC tem espalhamento, nome e criação fora do componente — antes de culpar a biblioteca.

8. HOC × hook × render prop

As três ferramentas resolvem "reaproveitar alguma coisa" e não são intercambiáveis. O hook reaproveita lógica e roda dentro do seu componente, com acesso direto ao estado e às props. A render prop deixa o componente decidir quando chamar a sua função, e você mantém o controle do desenho. O HOC devolve um componente pronto para usar, sem mudar o seu código.

Eu quero…FerramentaO que ela faz

Na prática, o hook venceu a maior parte das disputas, pelo mesmo motivo das render props: com useState à mão, não é preciso um componente de fora segurando o estado. HOC continua útil quando você precisa entregar um componente pronto — em bibliotecas, em rotas que exigem autenticação, em integrações com código que não é seu. Também continua sendo o jeito mais simples de acrescentar a mesma moldura a componentes que você não pode editar.

Escolher é mais fácil com uma pergunta: eu quero escrever um componente que já vem com o comportamento (HOC), ou usar o comportamento dentro do meu componente (hook)? Se a resposta for a segunda, quase sempre o hook é mais direto. Se você precisa que o resultado apareça no JSX como uma peça, o HOC resolve sem inventar nada.

9. Cenários do dia a dia

Cenário 1: o cartão embrulhado aparece vazio

A Ana criou o HOC, usou o resultado no App e o miolo ficou em branco. O culpado era um <Componente /> sem o {...props}: o wrapper recebeu nome e não repassou. O cartão desenhou undefined dentro do parágrafo. A regra é curta — todo HOC que não injeta props repassa todas — e vale a pena escrever assim desde o primeiro dia.

Cenário 2: dois usos do mesmo HOC compartilham o contador

Ela usou <BotaoContado /> em duas páginas e esperava números independentes. Era o que acontecia: cada uso é uma instância, com o seu useState. O problema foi outro — ela tinha criado o HOC dentro do componente pai, e cada desenho do pai remontava os filhos, zerando tudo. A lição: HOC se cria fora, no topo do arquivo, como qualquer componente.

Cenário 3: o nome sumiu do DevTools

Depois de três HOCs aninhados, a árvore mostrava quatro Envolvido seguidos e ela não sabia qual era qual. Acrescentar displayName em cada HOC resolveu em uma linha. Não muda o que aparece na tela — muda o que você consegue ler quando precisa investigar. Em código de equipe, isso é documentação barata.

11. Resumo

Higher-Order Component é uma função que recebe um componente e devolve outro. O componente que volta desenha o que quiser em volta e chama o original por dentro, repassando as props com {...props}. Você usa o resultado no JSX como usaria o componente original — e o original continua disponível, sem uma linha alterada.

As três utilidades do padrão são: acrescentar moldura, injetar dados e acrescentar comportamento com estado. Cada uma tem um cuidado. A moldura exige o repasse de props. A injeção exige nome que não brigue com as props naturais e uma decisão sobre a ordem do espalhamento. O estado é por instância do wrapper, não por componente de dentro, e não sobe para irmãos.

Hoje os hooks cobrem a maior parte do que os HOCs faziam, e é por isso que você vê menos withAlgumaCoisa em código novo. Mas o padrão continua sendo o jeito mais direto de entregar um componente pronto, e aparece em bibliotecas, em rotas protegidas e em qualquer lugar onde você não pode editar o componente que precisa ser embrulhado.

Fica também a lição de leitura que vale para todo padrão deste nível: quando um nome comprido assusta, traduza para uma frase. "Higher-Order Component é uma função que recebe um componente e devolve outro." Se a frase fizer sentido, o código faz sentido — e o inverso também vale.

Para lembrar

  • HOC é função que recebe componente e devolve componente; não é componente.
  • O HOC roda uma vez, na chamada; o resultado é que vira elemento no JSX.
  • Sem {...props}, o componente de dentro perde todas as props.
  • <Componente {...props} extra={x} />: a injeção vence; invertida, quem chama vence.
  • O HOC começa com com; o resultado junta os dois nomes: CartaoComMoldura.
  • Estado do HOC é por instância e não é visível de fora.
  • displayName salva a leitura da árvore no DevTools.
  • Nunca crie o HOC dentro do componente: cada desenho remonta a árvore.
  • Não altere o componente recebido; devolva um novo que usa o antigo.
  • Precisa de lógica dentro do seu componente? Hook. Precisa de uma peça pronta? HOC.
