O useEffect

A Ana já sabe desenhar a tela: os componentes dela mostram os pães, os preços e o horário. Mas nem tudo na vida da padaria é desenho. O título da aba do navegador, a linha que aparece no console, o pedido que vai para o servidor e o relógio do forno acontecem fora da tela — e o React não tem onde colocar isso dentro do return. Nesta aula ela conhece o useEffect, o gancho que roda código depois que o React desenhou a página, e vê no painel da caixa a hora exata em que isso acontece.

Você vai aprender
  • O que é um efeito e por que ele não pode ficar no meio do render.
  • Como se declara o primeiro useEffect e o que significa cada pedaço dele.
  • A ordem das coisas: primeiro o React desenha, depois o efeito roda.
  • Que o efeito pode mudar o estado — e que isso pede um segundo render.
  • Por que um efeito por assunto deixa o componente mais fácil de ler.
  • O que não fazer dentro do efeito: função async direto, efeito dentro de if, cálculo que cabia no render.
  • Os três formatos do array de dependências, só para reconhecer (a próxima aula é sobre eles).

1. A cena: o que não é desenho

A Ana tem um componente que mostra a vitrine: os pães do dia, o preço e o horário de funcionamento. Isso funciona. Mas ela quer mais três coisas, e nenhuma delas é "desenhar um pedaço da tela". Primeira: o título da aba do navegador deve dizer quantos pães estão na vitrine, para ela ver isso de longe, com a aba minimizada. Segunda: ela quer uma linha no console dizendo "a tela apareceu", para conferir que a página carregou. Terceira: ela quer buscar no servidor os preços atualizados, porque o preço de hoje não está escrito no código.

Repare no que essas três coisas têm em comum: elas não devolvem JSX. O título da aba é um objeto do navegador, o console é uma ferramenta do navegador, o servidor está em outro computador. Nenhuma delas cabe dentro do return do componente, que só sabe devolver elementos. E se você tentar colocar o console.log no corpo da função, antes do return, ele até aparece — mas aparece em um momento errado, e possivelmente mais de uma vez, como você vai ver daqui a pouco.

A ideia central desta aula é essa separação. Um componente tem duas faixas de trabalho. Na primeira faixa ele desenha: olha para as props e o estado e devolve JSX. Na segunda faixa ele conversa com o mundo de fora: escreve no console, muda o título da aba, pede dados, liga um timer. A primeira faixa é o render. A segunda é o efeito. O React separa as duas de propósito, e a ferramenta que declara a segunda faixa se chama useEffect.

O nome é literal: use effect, "use o efeito". Você diz ao React "olha, quando a tela já estiver montada, roda esta função para mim". O React guarda essa função e a chama no momento certo, depois do desenho. Você não chama a função do efeito — quem chama é o React.

2. O que é um efeito, na prática

Vamos combinar o vocabulário antes do código, porque ele volta em toda a aula. Efeito é qualquer coisa que o componente faz e que não é devolver JSX. O nome técnico é efeito colateral — um efeito que "escapa" do valor devolvido. Escrever no console é um efeito colateral. Mudar o título da aba é um efeito colateral. Pedir dados a um servidor é um efeito colateral. Até ligar um setInterval é um efeito colateral.

efeito
Qualquer ação do componente que não é devolver JSX: console, título da aba, pedido de dados, listener, timer. O React chama de efeito colateral.
função de efeito
A função que você entrega ao useEffect e que o React chama depois do render: () => { console.log("oi"); }.
montagem
O momento em que o componente entra na página pela primeira vez. É aí que o primeiro efeito roda.
dependências
O segundo argumento do useEffect, o array que decide se o efeito roda de novo. Sem array, roda a cada render; com [], roda só na montagem.
render
O trabalho de chamar o componente e transformar o JSX em elementos. É a faixa pura, que só calcula e devolve.

Uma comparação que costuma ajudar: o render é o desenho da vitrine; o efeito é o que a Ana faz depois de pendurar a placa — ligar as luzes, abrir a porta, avisar no grupo da família que o pão saiu. Se ela fizer essas coisas enquanto desenha a vitrine, atrapalha o desenho e faz tudo duas vezes. Por isso o React divide: primeiro o desenho inteiro fica pronto, depois as ações acontecem.

E por que o React não deixa você simplesmente escrever o código no corpo do componente? Porque o React pode chamar a função do componente muitas vezes: uma vez para a primeira pintura, outra quando o estado muda, e no modo de desenvolvimento ele chama cada componente duas vezes para pegar erros. Se o pedido ao servidor estivesse no corpo, você faria dois pedidos sem querer. Se o console.log estivesse no corpo, apareceriam duas linhas. O efeito existe para você dizer "isso aqui é ação, rode quando fizer sentido".

3. A primeira declaração

O useEffect já está no escopo das caixas deste guia, igual ao useState (no projeto de verdade ele vem de um import, que o preparador do arquivo resolve). A declaração tem sempre a mesma forma: um useEffect(, uma função, uma vírgula e o array de dependências. Nesta primeira caixa o componente tem só o desenho.

function App() {
  const [paes, setPaes] = useState(3);

  return (
    <div>
      <h1>Padaria da Ana</h1>
      <p>Pães saindo do forno: {paes}</p>
    </div>
  );
}

Três lugares onde o efeito não vai. Ele não vai depois do return (código depois do return nunca roda). Ele não vai dentro de um if, nem dentro de um laço — o React precisa que todos os hooks sejam chamados na mesma ordem em todo render, e um efeito que às vezes é chamado e às vezes não quebra essa contagem. E ele não vai dentro de outra função que não seja o componente.

O lugar certo é o começo do componente, junto com os useState: primeiro os estados, depois os efeitos, e por último o return com o JSX. Essa ordem é convenção, não regra do React, mas ela deixa o componente legível: quem lê vê primeiro o que o componente guarda, depois o que ele faz, e por fim o que ele mostra.

Um detalhe de sintaxe que confunde: você passa uma função para o useEffect, não o resultado dela. useEffect(console.log("oi")) está errado — isso chama o console.log na hora e passa undefined para o hook. O certo é embrulhar: useEffect(() => { console.log("oi"); }). A seta e as chaves adiam a execução para o React.

4. O efeito roda depois do render

Chegou a hora de ver a coisa funcionando. A missão é escrever o efeito que registra no console a frase combinada. Repare no painel: as linhas de HTML aparecem primeiro e a linha console: vem depois. Não é coincidência de ordenação, é a ordem real de execução.

Escreva um useEffect que registra no console a frase a tela apareceu: hora de mostrar o pão. Não mexa no que já está escrito e clique em Rodar.

function App() {
  const [paes, setPaes] = useState(3);

  return (

      <h1>Padaria da Ana</h1>
      <p>Pães saindo do forno: {paes}</p>
    </div>
  );
}

  const [paes, setPaes] = useState(3);

    console.log("a tela apareceu: hora de mostrar o pão");

O painel mostra duas coisas: o HTML que o React gerou e o que o seu código escreveu no console. A linha do console vem depois porque o efeito roda depois. Se você tivesse escrito o mesmo console.log no corpo do componente, antes do return, ele apareceria no mesmo lugar do painel — mas teria rodado antes de o React montar o HTML, e rodaria de novo a cada render. A frase é a mesma; o momento não é.

No navegador de verdade, o mesmo código aparece assim na aba Console do DevTools, aberta com F12 — e note que a ordem é a mesma do painel:

a tela apareceu: hora de mostrar o pão

Esse "depois" tem um nome: o React executa os efeitos depois de pintar a tela. Isso significa que a página já está visível quando a sua função roda. A consequência prática é boa: dentro do efeito você pode medir a tela, ler o tamanho de um elemento, consultar o navegador — tudo já está lá. A consequência prática é ruim para quem espera outra coisa: você não pode contar com o efeito para "preparar" dados que o return vai usar na mesma pintura, porque o render já aconteceu quando ele roda.

O segundo argumento que escrevemos ali, o [], diz "rode este efeito uma vez só, na montagem". Sem ele, o efeito rodaria depois de todo render. A aula inteira sobre isso é a próxima, mas guarde desde já a regra prática: um efeito que só faz sentido na entrada do componente leva [].

5. O efeito pode mudar o estado

Agora o passo que confunde muita gente: dentro do efeito, a Ana vai chamar o setPromocao, do mesmo useState que ela já conhece. Pode? Pode. É inclusive o jeito normal de guardar no estado algo que só chegou depois — porque o render só pode desenhar o que ele já sabe, e o efeito é quem descobre as coisas novas.

A sequência fica assim: o React chama o componente, o componente devolve o JSX, o React monta a tela, o efeito roda e chama setPromocao. O estado mudou, então o React chama o componente de novo — um segundo render, agora com a promoção preenchida. É por isso que você vê a frase final no painel e não a tela vazia: o painel mostra o resultado depois de tudo sossegar.

O componente guarda a promoção, mas ninguém a preenche. Escreva um efeito que roda uma vez e define a promoção como pão de queijo pela metade do preço.

function App() {
  const [promocao, setPromocao] = useState("");

  return (
    <div>
      <h1>Padaria da Ana</h1>
      <p>Promoção do dia: {promocao}</p>
    </div>
  );
}
<div>
  <h1>Padaria da Ana</h1>
  <p>Promoção do dia:</p>
</div>

function App() {
  const [promocao, setPromocao] = useState("");

  useEffect(() => {
    setPromocao("pão de queijo pela metade do preço");
  }, []);

  return (
    <div>
      <h1>Padaria da Ana</h1>
      <p>Promoção do dia: {promocao}</p>
    </div>
  );
}

Duas coisas importantes nesse exemplo. A primeira é que o efeito tem []. Sem o array, ele rodaria depois de todo render, e cada execução chamaria setPromocao, que causaria outro render, que chamaria o efeito de novo, e assim para sempre. O React trava esse laço com um erro ("Maximum update depth exceeded") depois de algumas dezenas de tentativas. A receita para não cair nele: se o efeito muda um estado, pergunte-se quando ele deve rodar — e escreva isso no array. O assunto volta na próxima aula, com calma.

A segunda é que existe um caminho mais curto. Se a promoção é sempre a mesma, ela nem precisa de estado: pode ser uma constante calculada no render, e aí não há efeito nenhum. Efeito é para o que vem de fora ou depende do tempo; o que é fixo cabe numa variável. O guia tem uma aula só sobre essa pergunta — Quando Não Usar Efeito —, mas vale guardar o instinto: quanto menos efeito, melhor.

6. Um efeito por assunto

Quando a Ana começou, ela escreveu tudo em um efeito só: registrava os preços, registrava os pães e preenchia o aviso. Funcionou, e ficou ilegível. A recomendação do React é uma por assunto: um efeito para os preços, outro para os pães, outro para o aviso. Assim, quando um deles mudar, você sabe qual mexeu.

Os efeitos de um mesmo componente rodam na ordem em que você os escreveu, de cima para baixo. Não é uma garantia de que dá para construir lógica em cima — quem garante dependência entre efeitos é o código, não a ordem —, mas ajuda a ler o console. Se a saída aparece na ordem contrária da que você esperava, provavelmente o efeito está em outro lugar do componente.

Já existe um efeito para os preços. Escreva um segundo efeito, que roda uma vez, registra no console carreguei o aviso e define o aviso como hoje tem pão de queijo até as 10h.

function App() {
  const [paes, setPaes] = useState(["pão francês", "pão de queijo"]);
  const [aviso, setAviso] = useState("");

  useEffect(() => {
    console.log("carreguei os preços");
  }, []);

  return (
    <div>
      <h1>Padaria da Ana</h1>
      <p>{aviso}</p>
      <ul>
        {paes.map((p) => (
          <li key={p}>{p}</li>
        ))}
      </ul>
    </div>
  );
}

Repare que o painel mostra as duas linhas de console na ordem em que os efeitos foram declarados: primeiro os preços, depois o aviso. E repare também que o parágrafo do aviso aparece vazio no começo do código e preenchido depois da missão cumprida — é o segundo render fazendo seu trabalho.

Um componente com vários efeitos pequenos é mais fácil de manter do que um com um efeito enorme. É a mesma ideia de separar o cabeçalho em um componente: dividir para conseguir mexer em uma parte sem derrubar as outras. Se um efeito precisa de três estados diferentes para trabalhar, provavelmente ele está fazendo três coisas — e o nome dele, se você tivesse de escrever um, sairia com "e" no meio.

7. O que não fazer dentro do efeito

Quatro tropeços aparecem quase sempre, e o primeiro é tentar usar await direto na função do efeito. Não dá: uma função que usa await precisa ser async, e uma função async sempre devolve uma Promise. O React espera que a função do efeito devolva ou nada, ou uma função de limpeza — e uma Promise não é nenhuma das duas. Ele avisa no console:

Warning: An effect function must not return anything besides a function,
which is used for clean-up. You returned: [object Promise].

A saída é criar uma função async dentro do efeito e chamá-la na hora. A função de fora continua devolvendo nada, o React fica satisfeito e o await acontece lá dentro:

useEffect(() => {
  async function carregar() {
    const resposta = await fetch("https://loja.test/paes");
    const lista = await resposta.json();
    setPaes(lista);
  }

  carregar();
}, []);

O segundo tropeço é esquecer que o efeito roda depois: quem tenta ler o valor de um estado dentro do efeito e usá-lo no return da mesma execução não vê o valor novo, porque o render já passou. O terceiro é colocar o efeito dentro de um if ou de um for. O React conta os hooks pela ordem das chamadas; se em um render o efeito é chamado e no outro não, a contagem desanda e o erro aparece como "Rendered fewer hooks than expected". O quarto é o laço infinito da seção anterior.

Há ainda um tropeço mais silencioso: usar efeito para calcular o que daria para calcular no render. Se o total é preco * quantidade e os dois valores já estão no estado, escrever const total = preco * quantidade resolve — sem estado, sem efeito, sem segundo render. Um efeito que só copia um valor para outro estado é uma fonte de tela desatualizada: por um instante, o total antigo aparece junto do preço novo.

8. O array de dependências, em três formatos

Já que ele decide quando o efeito roda, vale conhecer os três formatos. Nesta aula, apenas reconheça; os detalhes, as armadilhas e o que fazer com objetos e funções são a aula seguinte, chamada As Dependências.

Como você escreveQuando o efeito rodaQuando faz sentido
useEffect(funcao)depois de todo renderquando o efeito precisa acompanhar cada mudança — e, nesse caso, ele não deve mudar estado
useEffect(funcao, [])só na montagemcarregar dados uma vez, registrar um aviso de entrada, preparar algo que não depende de nada
useEffect(funcao, [a, b])na montagem e sempre que a ou b mudarrecalcular quando um valor específico muda: o preço, o bairro, o termo da busca

O array não é uma lista de "quando eu quero que rode"; é uma lista de tudo o que o efeito lê de fora da própria função. Se o efeito lê preco, preco tem de estar no array. Se lê preco e quantidade, os dois. O React não consegue adivinhar isso sozinho (o JavaScript não deixa ele olhar dentro da função), então a responsabilidade é sua — e o ESLint do projeto reclama quando você esquece, com o aviso react-hooks/exhaustive-deps.

9. Cenários do dia a dia

Cenário 1: o console mostra tudo duas vezes

Com o projeto criado pelo Vite, o StrictMode monta, desmonta e monta de novo cada componente no modo de desenvolvimento, justamente para revelar efeitos que não sabem se limpar. O resultado é o seu console.log aparecendo duas vezes. Não é bug do seu código e não acontece na versão publicada. Nas caixas deste guia não há StrictMode, então você vê cada linha uma vez só.

Cenário 2: o efeito parece não rodar

A Ana escreveu o useEffect e não viu nada no console. Na maioria das vezes o componente nem chegou a aparecer na tela: o efeito só roda depois da montagem, e um componente que ficou dentro de um if falso nunca monta. A outra causa comum é o erro em outro lugar do componente — se o render quebra, a montagem não termina e o efeito não roda. Nesse caso o console do navegador mostra o erro vermelho antes de qualquer linha sua.

Cenário 3: o efeito que trava a página

O clássico. A Ana escreveu useEffect(() => { setTotal(total + 1); }) — sem array. Cada execução muda o estado, cada mudança de estado pede um render, cada render pede o efeito. O navegador fica lento e o React para com "Maximum update depth exceeded". O conserto é decidir quando o efeito deve rodar e escrever isso no array; se não houver resposta, o efeito provavelmente não devia existir.

11. Resumo

Um componente tem duas faixas de trabalho: o render, que calcula e devolve JSX, e o efeito, que conversa com o mundo de fora. O useEffect declara a segunda faixa; o React chama a sua função depois de montar a tela, nunca durante o render. Se você precisa do console, do título da aba, de um pedido ao servidor ou de um timer, é para lá que o código vai.

O efeito pode mudar o estado. Quando muda, o React faz um segundo render com o valor novo — e é por isso que o painel das caixas mostra o resultado final. O que ele não pode é mudar um estado que ele mesmo observa em cada render sem um array de dependências, porque isso vira um laço. O array é a parte que decide: sem ele, o efeito roda sempre; com [], roda uma vez na montagem; com valores dentro, roda quando algum deles muda.

E a regra de organização: um efeito por assunto, todos no começo do componente, antes do return, nunca dentro de um if. Se um efeito só copia um valor que já estava disponível no render, ele provavelmente não devia existir. O caminho para escrever cada vez menos efeito é justamente entender quando um efeito é necessário — e é o que as próximas aulas destrincham.

Para lembrar

  • Efeito é tudo o que o componente faz fora do return: console, título, dados, timer.
  • useEffect(() => { ... }, []) roda uma vez, depois da montagem.
  • O efeito roda depois do render: a tela já está pintada quando ele começa.
  • Mudar estado dentro do efeito provoca um segundo render — e o painel mostra o resultado dele.
  • Sem array, o efeito roda depois de todo render; sem array e mudando estado, vira laço.
  • Um efeito por assunto; todos antes do return; nunca dentro de if.
  • Função async não vai direto no useEffect: crie uma dentro e chame.
  • O array lista o que o efeito lê: se lê dois valores, os dois entram.
  • No modo de desenvolvimento, o StrictMode roda o efeito duas vezes de propósito.
  • Se o efeito só copia um valor que o render já tinha, não use efeito.
