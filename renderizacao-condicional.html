Renderização Condicional

A página da Ana mostra tudo o que sabe, sempre: o aviso de última fornada mesmo quando o forno está cheio, o "fechado" no domingo de manhã, a lista vazia com um zero solto embaixo do título. Nesta aula ela aprende a deixar a tela decidir — mostrar o aviso só quando ele faz sentido, esconder a lista quando não há nada nela e devolver nada quando o componente não tem o que dizer.

Você vai aprender
  • O que é renderização condicional e por que ela não é CSS escondido.
  • O ternário dentro do JSX: {cond ? a : b}.
  • O atalho && para mostrar ou não mostrar um elemento.
  • Por que um 0 aparece na tela quando você usa && com um número.
  • O retorno antecipado: if (!texto) return null;.
  • Como escolher entre três ou mais opções sem embolar o JSX.
  • Condicional em atributos: className, disabled, aria-hidden.

1. A cena: a página que diz tudo ao mesmo tempo

A página inicial da padaria tem três avisos fixos: "Última fornada do dia", "Encomendas para hoje" e "Fechado aos domingos". A Ana escreveu os três no HTML e nunca mais mexeu. Na terça-feira, com o forno cheio e a loja aberta, o site dizia "última fornada" e "fechado" ao mesmo tempo. O cliente leu, acreditou e foi embora.

O problema não é o texto: é que a página mostra informação que não vale naquele momento. Um site de verdade mostra o aviso quando o aviso é verdade e não mostra quando não é. Isso se chama renderização condicional: o componente decide, na hora de desenhar, se um pedaço de tela entra ou não.

Antes de ver o código, vale entender o que "não entra" significa. Se o elemento não é desenhado, ele não existe no HTML: não ocupa espaço, não recebe clique, não é lido por leitor de tela, não aparece na busca do navegador com Ctrl+F. Isso é diferente de esconder com CSS (display: none): ali o elemento existe e só não é visto. Para um aviso que não vale, o certo é não desenhar — e é isso que as três técnicas desta aula fazem.

Vale reparar no custo de mostrar tudo. O cliente não lê o site como um programador lê: ele lê uma frase de cada vez e acredita no que está escrito. Um aviso que não vale não é neutro — ele desinforma. Por isso a decisão de mostrar precisa estar no código, junto do dado que a sustenta, e não na memória de quem edita o HTML na sexta-feira.

2. A pergunta antes do desenho

Tudo o que você já sabe continua valendo: o componente é uma função, e o return devolve JSX. O que muda é que o JSX pode ser montado a partir de uma pergunta. As chaves { } abrem espaço para JavaScript, e uma condição é JavaScript: dá para perguntar, comparar e escolher antes de devolver.

Há três formas de fazer essa pergunta, e cada uma serve a um caso. O ternário escolhe entre duas coisas. O && mostra uma coisa ou nada. O if com retorno antecipado sai da função antes de desenhar o resto. As três aparecem em qualquer projeto React, muitas vezes no mesmo arquivo.

FormaQuando usarExemplo
ternário ? :duas opções, uma ou outra{temPao ? "Tem pão" : "Acabou"}

if + returnsair do componente antes do JSXif (!texto) return null;

Repare que as três formas devolvem uma expressão: alguma coisa que o JSX aceita dentro das chaves. Um if não é expressão em JavaScript, então ele não pode ficar no meio do JSX — ele fica antes do return. Essa é a razão prática pela qual o ternário e o && existem: eles cabem onde o if não cabe.

Uma condição é qualquer expressão que resulte em verdadeiro ou falso: uma comparação (preco > 10), um pedaço de dado (encomendas.length), uma prop (aberto) ou uma função que devolve booleano. O que ela não pode é ser uma frase de efeito. {temPao ? ...} pergunta pelo valor de temPao, então essa variável precisa existir no escopo — como constante, variável, prop ou resultado de um cálculo feito antes do return.

condição
Uma expressão que resulta em verdadeiro ou falso: aberto, itens.length === 0, preco > 10.
expressão
Qualquer coisa que produza um valor — é o que pode ficar dentro das chaves do JSX.
ternário
A pergunta com duas respostas: cond ? a : b. As duas respostas são obrigatórias.
curto-circuito
O comportamento do &&: se a esquerda é falsa, a direita nem é avaliada — e o resultado é a própria esquerda.
retorno antecipado
Um return no meio da função, que encerra o componente antes do JSX principal.
null
O "nada" oficial do React: não cria elemento nenhum na página.

3. O ternário dentro do JSX

O ternário tem a forma condição ? valorSeVerdadeiro : valorSeFalso. É uma pergunta com duas respostas, e as duas são obrigatórias. No JSX ele aparece dentro das chaves, e cada resposta pode ser um texto, uma variável ou um elemento inteiro.

O painel mostra "Disponível" sempre, porque o texto está escrito à mão. Use um ternário com temPao para mostrar "Disponível" quando for verdadeiro e "Esgotado" quando for falso.

function App() {
  const temPao = false;

  console.log("tem pão? " + temPao);

  return (
    <div>
      <h1>Padaria da Ana</h1>
      <p>Pão de queijo: Disponível</p>
    </div>
  );
}
<div>
  <h1>Padaria da Ana</h1>
  <p>Pão de queijo: Disponível</p>
</div>
console: tem pão? false

function App() {
  const temPao = false;

  console.log("tem pão? " + temPao);

  return (
    <div>
      <h1>Padaria da Ana</h1>
      <p>Pão de queijo: {temPao ? "Disponível" : "Esgotado"}</p>
    </div>
  );
}

O painel agora mostra Pão de queijo: Esgotado, e o HTML gerado é um p com o texto já resolvido — não há rastro do ternário. Quando o React desenha, a pergunta já foi respondida. Troque const temPao = false por true e rode de novo: a mesma linha de código produz o outro texto.

Antes do HTML, o painel mostra a linha que o código escreveu no console — e ela é a prova de que a condição foi avaliada com o valor que você imaginava:

tem pão? false

Se o console dissesse tem pão? true e a tela mostrasse "Esgotado", o problema estaria na expressão, não no dado. Separar as duas coisas — o que a condição vale e o que a tela mostra — é metade do trabalho de depurar JSX.

O ternário também escolhe entre elementos inteiros, não só entre textos:

function Status({ aberto }) {
  return (
    <p className="status">
      {aberto ? <strong>Aberto agora</strong> : <em>Fechado</em>}
    </p>
  );
}

Aqui as duas respostas são elementos diferentes, com tags diferentes. É permitido: o ternário devolve um ou outro, e o React desenha o que veio. O que não vale é esquecer o lado do : — {aberto ? <p>Aberto</p>} é erro de sintaxe, porque o ternário exige as duas respostas. Para "ou nada", existe o &&.

4. O atalho do &&

Quando a resposta falsa é "nada", o ternário fica com um buraco: {temPao ? <p>Saiu agora</p> : null}. O JavaScript resolve isso com o curto-circuito: no condição && valor, se a condição for falsa, o valor nem é avaliado — o resultado é a própria condição. No JSX, um resultado falso não desenha nada, então o efeito é "mostra ou não mostra".

A lista de encomendas está vazia, e o aviso não aparece: no lugar dele o painel mostra um 0 solto. Faça o aviso "Nenhuma encomenda" aparecer quando a lista estiver vazia, sem deixar o zero na tela.

function App() {
  const encomendas = [];

  console.log("tem encomenda? " + (encomendas.length > 0));

  return (
    <div>
      <h1>Encomendas de hoje</h1>
      {encomendas.length && <p className="vazio">Nenhuma encomenda</p>}
    </div>
  );
}
<div>
  <h1>Encomendas de hoje</h1>
  0
</div>
console: tem encomenda? false

function App() {
  const encomendas = [];

  console.log("tem encomenda? " + (encomendas.length > 0));

  return (
    <div>
      <h1>Encomendas de hoje</h1>
      {encomendas.length === 0 && <p className="vazio">Nenhuma encomenda</p>}
    </div>
  );
}

O conserto tem uma linha e uma ideia: o lado esquerdo do && precisa ser um booleano de verdade, não um número. encomendas.length vale 0, e zero é falso — mas o que o && devolve não é o "nada" que o React ignora: é o próprio 0, que o React desenha como texto. Com === 0, o lado esquerdo é true ou false, e aí o atalho funciona como você espera.

5. O zero que aparece do nada

Esse erro é tão comum que merece nome: o "zero renderizado". Ele aparece em qualquer lista que usa o tamanho como condição — encomendas, itens no carrinho, resultados de busca — porque o tamanho é um número, e números podem ser zero.

Encomendas de hoje
0

Essa é a tela que a Ana viu: o título e um zero. O zero não é um bug do React; é o JavaScript fazendo exatamente o que você pediu. O React só desenha o que recebe, e recebeu o número zero. A confusão está em achar que && devolve sempre verdadeiro ou falso. Ele devolve o primeiro valor falso que encontrar, seja ele qual for.

Duas saídas. A primeira é comparar de verdade: encomendas.length === 0, encomendas.length > 0, itens.length !== 0. A segunda é forçar o valor para booleano: Boolean(itens.length) && ... ou !!itens.length && .... As duas funcionam; a comparação explícita é mais fácil de ler e diz ao próximo leitor qual pergunta você está fazendo.

De passagem, um hábito que pega esse erro antes de ele chegar na tela: sempre que escrever &&, pergunte "o lado esquerdo pode valer zero ou string vazia?". Se puder, use comparação. É mais barato do que descobrir pelo cliente reclamando de um zero no rodapé.

6. O retorno antecipado

Nem toda decisão cabe dentro do JSX. Quando o componente inteiro não deve aparecer — porque falta um dado, porque o usuário não está logado, porque ainda está carregando —, o caminho mais claro é sair da função antes do return: o retorno antecipado.

O componente Aviso recebe um texto vazio e desenha um parágrafo em branco. Faça ele devolver null quando não houver texto, para sobrar só o parágrafo do forno.

function Aviso({ texto }) {
  return <p className="aviso">{texto}</p>;
}

function App() {
  return (
    <div>
      <h1>Padaria da Ana</h1>
      <Aviso texto="" />
      <p>Pão saindo do forno às 6h</p>
    </div>
  );
}
<div>
  <h1>Padaria da Ana</h1>
  <p class="aviso"></p>
  <p>Pão saindo do forno às 6h</p>
</div>

function Aviso({ texto }) {
  if (!texto) {
    return null;
  }

  return <p className="aviso">{texto}</p>;
}

function App() {
  return (
    <div>
      <h1>Padaria da Ana</h1>
      <Aviso texto="" />
      <p>Pão saindo do forno às 6h</p>
    </div>
  );
}

O painel perde o parágrafo vazio: sobrou um p só. null é a forma de dizer "não tenho nada para desenhar" — o React aceita e não cria nó nenhum. É diferente de devolver uma string vazia, que também não desenha nada mas engana na leitura, e de devolver undefined por esquecimento, que é o mesmo que não ter return.

Compare as duas soluções para o mesmo problema: {texto && <p>{texto}</p>} resolve dentro do JSX, mas deixa o resto do componente sendo desenhado; if (!texto) return null decide pelo componente inteiro. Use a primeira quando a decisão é local, de um pedaço da tela; use a segunda quando o componente não faz sentido sem aquele dado. Misturar as duas sem critério é o que produz componentes com três níveis de chaves aninhadas e ninguém sabe mais o que aparece quando.

O retorno antecipado é ótimo porque achata o componente: cada caso cedo vira uma linha, e o JSX final fica sendo o caso "normal". A regra prática é colocar os casos de saída no topo, na ordem do mais provável para o menos provável, e deixar o return grande por último. Componentes assim são lidos de cima para baixo sem susto.

7. Escolhendo entre várias opções

Ternário serve para dois casos. Quando são três ou quatro, ternário dentro de ternário vira um ninho ilegível. A saída é voltar ao JavaScript normal antes do return: calcular uma variável com if e else if, ou usar um objeto como tabela de consulta.

function StatusDaPadaria({ situacao }) {
  let rotulo = "Fechado";

  if (situacao === "aberto") {
    rotulo = "Aberto agora";
  } else if (situacao === "ultimas") {
    rotulo = "Últimas unidades";
  } else if (situacao === "feriado") {
    rotulo = "Fechado no feriado";
  }

  return <p className="status">{rotulo}</p>;
}

Esse formato tem uma vantagem enorme: o JSX final é uma linha só, e toda a decisão está no meio, em JavaScript que você já sabe ler. Nada de aninhar três ternários e passar dez minutos procurando qual : falta.

Para listas de opções fixas, um objeto como tabela fica ainda mais curto — e o valor padrão aparece com ||:

const ROTULOS = {
  aberto: "Aberto agora",
  ultimas: "Últimas unidades",
  feriado: "Fechado no feriado"
};

function Status({ situacao }) {
  return <p>{ROTULOS[situacao] || "Fechado"}</p>;
}

Quando a decisão cresce, o sinal é que ela não pertence ao componente. Extraia para uma função com nome — function rotuloDe(situacao) { ... } — e chame no JSX: o componente volta a ser uma lista de elementos, e a regra ganha um lugar só dela, fácil de ler e de testar. Um switch também serve, e costuma ficar mais legível que uma cadeia de else if quando cada caso tem várias linhas.

Cuidado com o ||: ele devolve o lado direito quando o esquerdo é falso, e uma string vazia é falsa. Isso costuma ser o que você quer nesse caso — "sem rótulo, mostra Fechado" — mas é bom saber que o comportamento é esse. Se o valor válido pudesse ser 0 ou "", use ?? (que só troca por null e undefined) ou uma condição explícita.

8. Condicional em atributos

A mesma pergunta que decide se um elemento aparece também decide como ele aparece. Atributos são só valores, e valores podem ser calculados. Os três casos mais comuns são classe, desabilitado e acessibilidade.

function Aba({ nome, ativa }) {
  return (
    <button className={ativa ? "aba ativa" : "aba"} disabled={!ativa}>
      {nome}
    </button>
  );
}

Em className, o ternário troca a string inteira. Quando você só quer acrescentar uma classe, os dois lados precisam conter a parte comum — ou você pode montar a string com um pedaço condicional: {"aba" + (ativa ? " ativa" : "")}. O resultado é o mesmo; a diferença é quanto você repete.

Um tropeço comum é escrever className={ativa} esperando que o React invente a classe. Ele não inventa: o atributo recebe a string "true", e o CSS não encontra nada. Atributo é sempre texto; quem monta o texto é você. O ternário existe justamente para isso.

Em disabled, o valor é booleano e o React cuida do resto: verdadeiro escreve o atributo, falso remove. O mesmo vale para hidden, checked e readOnly. E há um detalhe de acessibilidade que vale ouro: esconder um elemento com CSS não o esconde do leitor de tela; não desenhar, sim. Se o aviso não vale, não desenhe — e, se ele só está visualmente oculto, use aria-hidden="true" para dizer isso em voz alta.

9. Cenários do dia a dia

Cenário 1: a condição que é sempre verdadeira

A Ana escreveu {estoque ? "Tem pão" : "Acabou"} e o aviso nunca mudava. O estoque vinha de um formulário como texto, e a string "0" é verdadeira em JavaScript — só o número 0 é falso. O conserto foi converter antes: Number(estoque) > 0. Sempre que uma condição parecer travada, desconfie do tipo do valor antes de desconfiar do React.

Cenário 2: a tela em branco

Ela trocou o texto de um aviso por um if que devolvia null, mas esqueceu de colocar o return do caso normal. O componente passou a devolver undefined em todos os caminhos e a página ficou vazia. Retorno antecipado só funciona se existir um retorno no fim; na dúvida, leia a função de baixo para cima e confira se o último return está lá.

Cenário 3: o aviso que pisca

O aviso aparecia e desaparecia a cada segundo porque a condição usava Date.now() direto no JSX. Cada desenho calculava um valor novo, e o resultado mudava sozinho. Condição boa é feita de dado, não de relógio: calcule a situação uma vez, guarde numa variável com nome e use essa variável no JSX. Quando o estado entrar na sua vida, na próxima aula, essa separação vai ficar ainda mais importante.

Nos três cenários o conserto foi o mesmo: transformar a pergunta numa expressão booleana explícita e deixá-la perto do dado que a responde. Nada de condição escondida em string, em CSS ou em relógio. Quando a condição é legível, o JSX fica legível — e o contrário também é verdade: um JSX embolado quase sempre esconde uma condição que ninguém conseguiu nomear.

Exercício: o aviso que pode não existir

Complete o componente para que ele não desenhe nada quando o texto estiver vazio. Qual valor o return antecipado devolve?

if (!texto) { return ; }

Dica: é o valor que o React entende como "não tenho nada para desenhar". Não é false, não é "" e não é undefined — embora os três também não desenhem nada, só um deles diz a verdade: não existe conteúdo.

11. Resumo

Renderizar condicionalmente é decidir, dentro do componente, se um pedaço de tela entra no HTML. O ternário escolhe entre duas coisas, o && mostra uma coisa ou nada, e o if com return null sai do componente antes do desenho. As três formas são JavaScript puro dentro das chaves — e é justamente por isso que funcionam: o JSX não tem regra própria de condição, ele usa a linguagem.

O erro clássico é o zero: {itens.length && ...} desenha 0 quando a lista está vazia, porque && devolve o valor da esquerda, não um booleano. Compare de verdade (=== 0, > 0) e o problema some. O segundo erro clássico é confundir esconder com não desenhar: CSS esconde da vista, não do leitor de tela, do teclado nem do HTML. Se não vale, não desenhe.

Também vale guardar o que a aula não resolveu: até aqui, a condição é calculada a partir de constantes e props. A página da Ana ainda não muda sozinha — ela precisa que o leitor clique em algo e que a tela responda. Esse "algo que muda com o tempo" é o estado, e é o assunto da próxima aula. A renderização condicional é a metade visível desse mecanismo: o estado decide o quê, a condição decide se aparece.

Para lembrar

  • Condicional no JSX é uma expressão dentro das chaves: {cond ? a : b}.
  • && é para "mostrar ou nada"; ternário é para "um ou outro".
  • {0 && ...} desenha 0: compare (=== 0, > 0) em vez de usar o número cru.
  • null é o "nada" oficial do componente; undefined é esquecimento.
  • Retorno antecipado achata o componente: casos de saída no topo, JSX normal no fim.
  • Três ou mais opções? Calcule a variável antes do return.
  • Atributos também são condicionais: className, disabled, aria-hidden.
  • Não desenhar ≠ esconder com CSS: o elemento ausente não existe no HTML.
  • Condição boa vem de dado, não de relógio nem de sorteio.
  • Condição travada? Confira o tipo: "0" é verdadeiro, 0 é falso.
