Filtrar

A vitrine da Ana tem cinco pães e três botões: todos, pães e doces. O que ela quer é simples de dizer e fácil de errar — mostrar só os que combinam com o botão escolhido, sem estragar a lista original, e avisar quando não sobra nada. Nesta aula ela aprende a filtrar antes de desenhar, a guardar o filtro como estado e a derivar a lista visível sem tocar nos dados.

Você vai aprender
  • O que o filter faz com um array, sem React no meio.
  • Por que filtrar vem antes do map, e não depois.
  • Que a escolha do filtro é estado, e a lista filtrada é derivada.
  • Como contar o que sobrou e o que mostrar quando não sobra nada.
  • Por que filtrar o próprio estado é o erro caro — e como evitar.
  • Que filtrar não é esconder com CSS, e que filtrar não é buscar por texto.
  • Como a chave estável continua valendo quando a lista encolhe.

1. A cena: cinco pães e três botões

Na vitrine da Ana há cinco itens: pão francês, broa de milho, pão de queijo, bolo de fubá e croissant. Três deles são pães; dois são doces. Ela quer três botões no topo — Todos, Pães, Doces — e que a lista mostre só o que combina com o botão escolhido.

A primeira tentativa é a mais óbvia: cada botão tem o seu próprio if, cada if desenha a sua própria lista. Funciona e dura uma semana. Na semana seguinte ela acrescenta uma categoria — salgados — e agora tem quatro listas quase iguais, quatro lugares para corrigir o preço e quatro chances de esquecer um pão.

A segunda tentativa é a certa: uma lista só, um estado que guarda a categoria escolhida e um filter que reduz o array antes do map. A ideia é a mesma da aula de Estado Derivado — guarde o mínimo e calcule o resto — aplicada a listas.

Três conceitos vão se juntar nesta aula, e vale nomeá-los antes: filtrar é escolher quais itens continuam; estado é o que você guarda entre um desenho e outro; e derivado é o que você calcula na hora, sem guardar. A maior parte dos bugs de filtro nasce de trocar esses papéis.

2. O que o filter faz, sem React no meio

filter é um método de array como map. Ele recebe uma função de teste, roda essa função para cada item e devolve um array novo com os itens em que a função devolveu verdadeiro. O array original não muda: nada sai dele, nada é removido.

const paes = [
  { id: 1, nome: "Pão francês", categoria: "paes" },
  { id: 2, nome: "Broa de milho", categoria: "paes" },
  { id: 3, nome: "Bolo de fubá", categoria: "doces" },
  { id: 4, nome: "Croissant", categoria: "doces" },
  { id: 5, nome: "Pão de queijo", categoria: "paes" }
];

const doces = paes.filter((p) => p.categoria === "doces");
console.log(doces.map((p) => p.nome).join(", "));
console.log(paes.length);

O console mostra a lista filtrada e prova que o original continua inteiro:

Bolo de fubá, Croissant
5

Essa segunda linha é a mais importante da aula. filter não remove nada de paes: ele constrói outro array com os aprovados. Quem remove é splice, pop e companhia — métodos que mudam o array no lugar. Guarde a diferença: filter cria, splice destrói.

filtrar
Escolher quais itens de um array continuam, por uma função de teste. Não altera o array original: devolve outro, menor ou igual.
teste
A função que responde sim ou não para cada item, como (p) => p.categoria === "doces". O nome técnico é predicado.
lista derivada
A lista calculada a partir de outra, a cada desenho. Não é estado: não precisa de useState e nunca fica desatualizada.
fonte de verdade
O lugar único onde o dado mora. No filtro, é a lista completa; a visível é só uma leitura dela.
estado vazio
O que a tela mostra quando o filtro não deixa nenhum item. Precisa de uma frase, não de uma área em branco.

A ordem clássica é filter e depois map: primeiro escolhe quem fica, depois transforma cada um em elemento. Fazer o contrário — map e depois filter — funciona em JavaScript, mas você acaba testando propriedades de elementos JSX, que não têm categoria nem nome. Filtre o dado, não o desenho.

3. Filtrar antes de desenhar

Olhe a caixa. O estado categoria já existe e os botões já mudam esse estado — mas a lista desenha paes inteiro, então nada muda na tela. O conserto é uma linha: derivar visiveis com filter e percorrer essa lista no map.

Os botões mudam o estado categoria, mas a lista mostra sempre os cinco pães. Filtre os pães pela categoria escolhida antes de desenhar e clique em Doces para conferir.

function App() {
  const [categoria, setCategoria] = useState("todos");
  const paes = [
    { id: 1, nome: "Pão francês", categoria: "paes" },
    { id: 2, nome: "Broa de milho", categoria: "paes" },
    { id: 3, nome: "Bolo de fubá", categoria: "doces" },
    { id: 4, nome: "Croissant", categoria: "doces" },
    { id: 5, nome: "Pão de queijo", categoria: "paes" }
  ];

  return (
    <div>
      <button className="todos" onClick={() => setCategoria("todos")}>Todos</button>
      <button className="paes" onClick={() => setCategoria("paes")}>Pães</button>
      <button className="doces" onClick={() => setCategoria("doces")}>Doces</button>
      <ul>
        {paes.map((p) => (
          <li key={p.id}>{p.nome}</li>
        ))}
      </ul>
    </div>
  );
}

        ))}
      </ul>
    </div>
  );
}

Clique em Doces e o painel mostra dois <li>: bolo de fubá e croissant. A condição tem duas partes porque "todos" não é uma categoria de pão — é a ausência de filtro. A primeira parte, categoria === "todos", aprovando todo mundo, resolve isso sem precisar de um if separado.

Repare que a key continua sendo p.id, mesmo com a lista menor. É isso que faz o estado de cada linha acompanhar o pão certo quando o filtro muda, como a aula de Chaves Estáveis explicou. Com índice no lugar do id, filtrar embaralharia os checks.

Também vale notar o lugar do cálculo: visiveis é uma const calculada no corpo do componente, antes do return. Não é estado, não é efeito, não precisa de useMemo em uma lista de cinco itens. Calcular no corpo é o padrão; otimizar vem depois, e só se medir.

4. O filtro escolhido é estado

Das duas coisas envolvidas — a categoria escolhida e a lista filtrada — só a primeira precisa ser guardada. A categoria é uma decisão do usuário que precisa sobreviver entre desenhos: se ela não for estado, cada clique atualiza a tela por um instante e some no desenho seguinte.

A lista filtrada, por outro lado, é consequência. Guardá-la em estado significa criar uma segunda fonte de verdade: no dia em que alguém acrescentar um pão, a lista guardada fica desatualizada; no dia em que o pão mudar de categoria, idem. Todo bug de "a tela não atualizou" começa com duas fontes de verdade para o mesmo dado.

// certo: guarda a escolha, calcula a lista
const [categoria, setCategoria] = useState("todos");
const visiveis = paes.filter((p) => categoria === "todos" || p.categoria === categoria);

// errado: guarda a lista e a escolha, e precisa sincronizar as duas
const [categoria, setCategoria] = useState("todos");
const [visiveis, setVisiveis] = useState(paes);

O padrão do estado também merece atenção: "todos" é uma escolha, não um vazio. Se você usasse null para "sem filtro", cada condição precisaria tratar o nulo. Uma string especial como "todos" deixa a condição curta e o valor legível no DevTools.

Quando a lista original vem de fora, por prop, a conta não muda: a prop é a fonte, o estado é a categoria, e o filter continua sendo derivado. O que não pode acontecer é o componente receber a lista por prop e guardar uma cópia em estado para "poder filtrar" — aí a prop muda e a cópia não.

5. Contar o que sobrou e avisar quando não sobra nada

Uma lista filtrada pode ficar vazia, e lista vazia sem explicação parece bug. A Ana quer duas coisas: uma linha dizendo quantos itens estão à vista e, quando não houver nenhum, uma frase no lugar da lista. As duas contas saem do mesmo array derivado.

O botão "Sem glúten" não tem nenhum pão, e a tela fica em branco. Mostre a contagem (0 de 5) e, quando a lista estiver vazia, a frase "Nenhum pão nessa categoria".

A contagem usa visiveis.length e paes.length — e não dois arrays diferentes. Se você contar a lista completa, o número mente; se contar uma cópia guardada em estado, ele mente um desenho depois. Contagem é sempre derivada da mesma lista que está na tela.

Um log de duas linhas confirma a conta sem precisar olhar a tela:

const visiveis = paes.filter((p) => categoria === "todos" || p.categoria === categoria);
console.log("visíveis: " + visiveis.length + " de " + paes.length);

Com o filtro em "doces" e depois em "sem-gluten", o console mostra:

categoria doces:      console: visíveis: 2 de 5
categoria sem-gluten: console: visíveis: 0 de 5

Se o primeiro número for igual ao segundo, o filtro não está filtrando; se for maior do que o total, alguém duplicou itens no caminho. A contagem é o teste mais rápido de sanidade de uma lista filtrada.

O ternário com visiveis.length === 0 decide entre a frase e a lista. A comparação com zero é explícita de propósito: escrever {visiveis.length && <ul>...</ul>} funciona, mas deixa um 0 aparecendo na tela quando a lista está vazia. É a mesma armadilha da aula de Renderização Condicional, agora em forma de contagem.

Uma frase de estado vazio boa diz duas coisas: o que aconteceu e o que fazer. "Nenhum pão nessa categoria" já é melhor do que uma área em branco; melhor ainda seria "Nenhum pão sem glúten por hoje — veja a vitrine completa" com um botão que volta para "Todos". Um estado vazio com saída é o que separa uma tela que parece quebrada de uma tela que conversa.

6. O tropeço caro: filtrar o estado

Aqui está o erro que a Ana cometeu e que quase todo mundo comete uma vez. Ela clicou em "Pães", viu três itens, clicou em "Todos" e continuaram três. O culpado estava na função do clique: em vez de guardar a categoria e deixar o filter fazer a conta, ela filtrava o estado e guardava o resultado por cima da lista original.

Clique em Pães e depois em Todos: a lista não volta, porque o estado está sendo filtrado. Guarde só a categoria e derive a lista visível sem tocar no array de pães.

function App() {
  const [categoria, setCategoria] = useState("todos");
  const [paes, setPaes] = useState([
    { id: 1, nome: "Pão francês", categoria: "paes" },
    { id: 2, nome: "Broa de milho", categoria: "paes" },
    { id: 3, nome: "Bolo de fubá", categoria: "doces" },
    { id: 4, nome: "Croissant", categoria: "doces" },
    { id: 5, nome: "Pão de queijo", categoria: "paes" }
  ]);

  function escolher(nova) {
    setCategoria(nova);
    setPaes(paes.filter((p) => nova === "todos" || p.categoria === nova));
  }

  return (
    <div>
      <button className="todos" onClick={() => escolher("todos")}>Todos</button>
      <button className="paes" onClick={() => escolher("paes")}>Pães</button>
      <ul>
        {paes.map((p) => (
          <li key={p.id}>{p.nome}</li>
        ))}
      </ul>
    </div>
  );
}

A solução mudou três coisas pequenas. A lista de pães deixou de ser estado e virou uma const no corpo do componente. A função escolher desapareceu: cada botão agora só chama setCategoria. E nasceu a linha do filter, que deriva visiveis a cada desenho. Com isso, "Pães" mostra três e "Todos" volta a mostrar cinco, porque a lista completa nunca foi alterada.

Por que o erro original é tão fácil de cometer? Porque setPaes substitui a lista inteira pela versão filtrada. O React não guarda um histórico do estado: o que você manda é o novo valor. Filtrar o pão francês para fora é definitivo até a página recarregar. Não existe "desfiltrar" — só existe manter o array completo e calcular o que aparece.

E há a versão silenciosa do mesmo erro: paes.sort() dentro do clique. sort muda o array no lugar e devolve a mesma referência; o React pode não perceber a mudança e a tela não atualiza. A regra que cobre os dois casos: não mexa no array que veio do estado; construa outro. A aula de Estado com Array mostra as operações seguras, com espalhamento.

7. Filtrar não é esconder (e não é buscar)

Dois atalhos que parecem filtro e não são. O primeiro é o CSS: em vez de reduzir a lista, esconder os itens que não combinam com display: none. A tela fica certa e o resto errado — os itens continuam no HTML, continuam sendo montados pelo React a cada desenho e, dependendo de como você esconde (opacity: 0, por exemplo), continuam alcançáveis pelo teclado e por leitores de tela. Filtrar é não desenhar; esconder é desenhar sem mostrar.

O segundo atalho é confundir filtrar com buscar. Filtrar por categoria é escolher entre valores fixos: pães, doces, todos. Buscar é comparar texto digitado com o nome do item, e tem as suas próprias armadilhas — maiúsculas, acentos, pedaços de palavra, o tempo entre uma tecla e outra. São duas aulas diferentes por um motivo: o filtro é uma escolha; a busca é uma comparação. As duas se combinam bem — dá para buscar dentro da categoria escolhida — mas é melhor implementá-las separadas.

Há ainda o filtro que não filtra por causa do tipo. Se a categoria no dado é o número 1 e você compara com a string "1", o === reprova todo mundo e a lista fica vazia. Se você escreve p.categoria = "doces" com um sinal de igual, o filter altera o dado e considera todo mundo aprovado — o bug mais confuso dos dois, porque a lista continua completa e o dado fica errado. Em comparação, sempre ===; em atribuição, nunca dentro de condição.

O filtro também pode ficar caro. Com listas grandes, filter roda a cada desenho, e cada tecla digitada na busca gera um desenho. Nesses casos, useMemo evita repetir a conta quando as entradas não mudaram — mas só vale depois de medir. Para cinco pães, o custo é invisível e a complexidade extra só atrapalha.

8. Onde o filtro mora, afinal

Existem três lugares possíveis para o filtro, e a escolha muda o comportamento do site. No estado do componente, o filtro é local: sai da página ao recarregar. Na URL, o filtro é compartilhável: o link "doces" abre a vitrine já filtrada. Na prop, o filtro é controlado por quem está acima: útil quando a mesma escolha vale para vários componentes da tela.

Para a vitrine da Ana, estado local é suficiente e é o mais simples. Se ela quiser mandar o link dos doces para um cliente, a URL vira necessária — e aí o estado passa a ler a URL em vez de nascer com "todos". O importante é que exista uma fonte de verdade: escolher entre estado, URL e prop é decisão de arquitetura; duplicar não é.

Um detalhe de interface que vale desde já: o botão da categoria ativa precisa parecer ativo. Como a categoria está no estado, o className condicional resolve: className={categoria === "doces" ? "ativo" : ""}. Sem esse sinal, o usuário clica e não sabe se a lista mudou por causa do clique ou porque era assim mesmo — especialmente quando o filtro devolve zero itens.

9. Cenários do dia a dia

Cenário 1: a contagem diz 5, a tela mostra 2

A Ana mostrou {paes.length} itens em vez de {visiveis.length} itens. Com o filtro de doces, o número continuou cinco e a lista, dois. Número que não corresponde ao que está na tela destrói a confiança do usuário. A regra é usar sempre a mesma lista: se o map percorre visiveis, a contagem lê visiveis.length.

Cenário 2: o filtro não volta ao clicar em Todos

Ela fez o estado receber a lista filtrada, como na caixa da seção 6. Ao clicar em "Todos", o filter rodou sobre a lista já reduzida e não tinha como recuperar os itens perdidos. O conserto é manter a lista completa intacta e derivar a visível a cada desenho. Filtro é uma lente, não uma tesoura.

Cenário 3: filtrar deixou a lista em branco sem aviso

A categoria "sem glúten" não tinha nenhum pão e a tela ficou vazia, sem uma palavra. O usuário não sabe se a página quebrou ou se não há produto. Uma frase de estado vazio mais a contagem resolvem em duas linhas — e, se possível, um botão que volta para "Todos". Estado vazio é informação, não ausência.

11. Resumo

Filtrar é escolher quais itens continuam, e filter faz isso devolvendo um array novo sem tocar no original. No JSX, o filtro vem antes do map: primeiro você reduz o dado, depois transforma cada item em elemento. Fazer o contrário testa propriedades de elementos, que não existem.

O estado guarda a escolha — a categoria — e a lista visível é derivada no corpo do componente. Guardar as duas é criar duas fontes de verdade, e a segunda sempre atrasa. Contagem e estado vazio saem da mesma lista que está na tela: visiveis.length e um ternário para a frase de "nenhum resultado".

O erro caro é filtrar o próprio estado: a lista encolhe para sempre e "Todos" não recupera nada. Filtrar é uma lente, não uma tesoura. Também não é esconder com CSS — item escondido continua no HTML, no leitor de tela e na busca — nem buscar por texto, que é outra comparação e outra aula.

Por fim, o filtro e a chave trabalham juntos: com key={p.id}, o estado de cada linha acompanha o pão quando a lista encolhe. Com índice, filtrar embaralha. Duas decisões pequenas que, tomadas juntas, fazem uma vitrine que se comporta como o usuário espera.

Para lembrar

  • filter devolve array novo; o original fica intacto.
  • Filtre o dado, depois faça o map; nunca o contrário.
  • Estado: a categoria escolhida. Derivado: a lista visível.
  • "Todos" é uma escolha explícita — trate na condição, não com if separado.
  • Contagem com visiveis.length, a mesma lista que está na tela.
  • Lista vazia pede frase de estado vazio e, se der, uma saída.
  • Filtrar o estado apaga dados para sempre: "Todos" não volta.
  • sort e splice mudam no lugar; no estado, construa outro array.
  • Filtro por categoria não é busca por texto, e esconder com CSS não é filtrar.
  • key={p.id} mantém o estado no item certo quando o filtro muda.
