Radio

Na encomenda da padaria, o cliente escolhe como quer receber: retirar no balcão ou receber em casa. São duas opções visíveis, e só uma pode valer — se ele pudesse marcar as duas, o pedido não faria sentido. O radio existe exatamente para isso: um grupo em que marcar uma opção desmarca as outras. Nesta aula a Ana monta o primeiro grupo controlado, aprende por que o name é obrigatório, gera as opções a partir de uma lista e faz o grupo começar sem escolha.

Você vai aprender
  • O que diferencia um radio de um checkbox.
  • Por que todas as opções do grupo precisam do mesmo name.
  • Como marcar a opção certa com checked={forma === "entrega"}.
  • Como ler o valor escolhido com e.target.value.
  • Como gerar um grupo a partir de uma lista com map.
  • Como deixar o grupo sem nenhuma opção marcada.
  • Quando usar radio e quando usar select.

1. A cena: uma escolha só, entre opções visíveis

A padaria entrega de bicicleta e atende no balcão. No formulário, o cliente precisa escolher uma das duas coisas — e a escolha muda o resto do pedido: no balcão não tem frete, na entrega tem. A Ana poderia usar um select, mas com duas opções a lista fechada esconde uma delas e obriga um clique a mais. O radio mostra as duas na tela, com uma bolinha ao lado de cada uma, e deixa claro que só uma pode ser escolhida.

O nome vem do rádio antigo do carro: você aperta um botão e o anterior se solta. No HTML é a mesma ideia. Um grupo de radio com o mesmo name se comporta como um botão de rádio: ao marcar a segunda opção, a primeira desmarca sozinha. Quem faz esse trabalho é o navegador, não o React. O React cuida de manter o estado em sincronia com a bolinha marcada.

A diferença em relação ao checkbox é essa: a caixa de marcar guarda um booleano por item e permite várias marcações; o radio guarda o valor da escolhida e permite uma só. Se você entender isso, o código fica óbvio: um estado com o valor escolhido, e cada opção marcada quando o valor dela é igual ao estado.

2. O grupo e o name

Um radio sozinho é só uma bolinha. O que transforma várias bolinhas num grupo é o name: opções com o mesmo nome pertencem ao mesmo grupo, e o navegador desmarca as outras quando uma é escolhida. Sem name igual, cada bolinha é um grupo de um item só, e o cliente consegue marcar todas — o que quase sempre é um bug.

radio
O tipo de campo de escolha única. Escreve-se <input type="radio">, sem tag de fechamento.
name
O nome do grupo. Todas as opções que podem ser escolhidas entre si usam exatamente o mesmo name.
value
O texto que vai para o estado quando aquela opção é escolhida. Diferente do checkbox, aqui o value é o dado principal.
checked
Diz se aquela opção é a marcada. No JSX controlado, recebe uma comparação: checked={forma === "entrega"}.
grupo controlado
Um estado só para o grupo inteiro, com uma comparação por opção. Marcar uma desmarca as outras porque o estado muda.

A última linha é a chave do assunto. No grupo controlado, você não guarda "qual bolinha está marcada" em cada opção; você guarda o valor escolhido num estado só, e cada opção pergunta "eu sou o escolhido?". Quando o estado muda, a opção anterior deixa de bater com a comparação e desmarca; a nova passa a bater e marca. O navegador nem precisa entrar na conta.

É por isso que o name continua importante mesmo com o controle no estado. Ele mantém o grupo coerente para o navegador, para o teclado (as setas pulam de opção em opção dentro do grupo) e para o envio de formulário. Um grupo sem name controlado até parece funcionar na tela, mas quebra a navegação por teclado e o envio.

3. O primeiro grupo controlado

O componente abaixo tem o grupo pronto e o parágrafo fixo em "retirada". A missão é criar o estado, comparar em cada opção e mostrar o valor escolhido. Repare que a comparação aparece duas vezes, uma por opção:

O grupo não está ligado ao estado e o parágrafo nunca muda. Crie forma começando em "retirada", use checked={forma === "..."} em cada opção e mostre Você escolheu: {forma}.

function App() {
  return (
    <div>
      <p>Como você quer receber?</p>
      <label>
        <input type="radio" name="recebimento" value="retirada" defaultChecked />
        Retirar no balcão
      </label>
      <label>
        <input type="radio" name="recebimento" value="entrega" />
        Entrega em casa
      </label>
      <p>Você escolheu: retirada</p>
    </div>
  );
}

    Retirar no balcão

function App() {
  const [forma, setForma] = useState("retirada");
  return (
    <div>
      <p>Como você quer receber?</p>
      <label>
        <input
          type="radio"
          name="recebimento"
          value="retirada"
          checked={forma === "retirada"}
          onChange={(e) => setForma(e.target.value)}
        />
        Retirar no balcão
      </label>
      <label>
        <input
          type="radio"
          name="recebimento"
          value="entrega"
          checked={forma === "entrega"}
          onChange={(e) => setForma(e.target.value)}
        />
        Entrega em casa
      </label>
      <p>Você escolheu: {forma}</p>
    </div>
  );
}

Clique em "Entrega em casa": a bolinha muda, a outra desmarca e o parágrafo passa a dizer "Você escolheu: entrega". O onChange é o mesmo nas duas opções, porque e.target.value já diz qual foi escolhida — não é preciso uma função por opção. Esse é um dos motivos de o value ser obrigatório no grupo controlado: sem ele, o evento chegaria com valor vazio.

O defaultChecked do código inicial funcionou para a primeira renderização, mas não acompanha mudanças: ele é a versão não controlada de checked. Assim que o estado entra em cena, o defaultChecked sai. Misturar os dois é uma fonte comum de confusão: a bolinha aparece marcada, você clica em outra, e a primeira volta na próxima renderização.

Os tropeços do grupo controlado são poucos e sempre os mesmos. A tabela serve de diagnóstico rápido quando alguma bolinha se recusa a obedecer:

4. O checked compara, o value guarda

No radio controlado, os dois atributos têm papéis bem separados: value é o dado da opção e checked é a pergunta "é esta?". A tabela mostra os três estados possíveis do grupo, com o que aparece na tela:

Estado formaOpção marcadaO que o resumo mostra
"retirada"Retirar no balcãoVocê escolheu: retirada
"entrega"Entrega em casaVocê escolheu: entrega
""nenhumaEscolha como receber

A terceira linha é a que muita gente esquece. Um estado vazio é uma situação legítima: é assim que o grupo começa antes de o cliente decidir. Com checked={forma === "retirada"} e forma valendo "", nenhuma opção bate e nenhuma aparece marcada. Não é necessário um estado "nenhum"; string vazia já diz isso.

E o valor guardado é sempre texto, mesmo que a opção pareça um número. Um grupo de tamanhos P, M e G guarda "P"; um grupo de porções guarda "2", não 2. Se você precisa do número para calcular, converta com Number(), como fez no campo numérico. A regra do formulário não muda de elemento para elemento.

No console, o evento de um radio mostra o nome do grupo, o valor da opção e se ela ficou marcada:

e.target.name: "recebimento"
e.target.value: "entrega"
e.target.checked: true

Essas três linhas explicam por que o onChange pode ser o mesmo em todas as opções: quem dispara é sempre o radio clicado, e ele carrega o próprio valor. O checked vem true porque a opção clicada é a que acabou de ser marcada.

5. Um grupo gerado por uma lista

Com duas opções, escrever cada label na mão é razoável. Com três formas de pagamento — e com a chance de a padaria aceitar vale-refeição no mês que vem —, vale gerar o grupo a partir de uma lista. Cada item vira um label com o seu input, e o estado continua sendo um só.

A lista formas tem três itens, mas só dois viraram opção. Gere os três com map, marque cada um quando pagamento for o id dele e mostre o detalhe da forma escolhida.

const formas = [
  { id: "pix", rotulo: "Pix", detalhe: "5% de desconto" },
  { id: "cartao", rotulo: "Cartão", detalhe: "Maquininha na entrega" },
  { id: "dinheiro", rotulo: "Dinheiro", detalhe: "Leve troco, por favor" },
];

function App() {
  const [pagamento, setPagamento] = useState("pix");
  const escolhida = formas.find((f) => f.id === pagamento);
  return (
    <div>
      <p>Forma de pagamento:</p>
      <label>
        <input type="radio" name="pagamento" value="pix" />
        Pix
      </label>
      <label>
        <input type="radio" name="pagamento" value="cartao" />
        Cartão
      </label>
      <p>{escolhida.detalhe}</p>
    </div>
  );
}

  { id: "pix", rotulo: "Pix", detalhe: "5% de desconto" },
  { id: "cartao", rotulo: "Cartão", detalhe: "Maquininha na entrega" },
  { id: "dinheiro", rotulo: "Dinheiro", detalhe: "Leve troco, por favor" },
];

function App() {
  const [pagamento, setPagamento] = useState("pix");
  const escolhida = formas.find((f) => f.id === pagamento);
  return (
    <div>
      <p>Forma de pagamento:</p>
      {formas.map((f) => (
        <label key={f.id}>
          <input
            type="radio"
            name="pagamento"
            value={f.id}
            checked={pagamento === f.id}
            onChange={(e) => setPagamento(e.target.value)}
          />
          {f.rotulo}
        </label>
      ))}
      <p>{escolhida.detalhe}</p>
    </div>
  );
}

Clique em "Dinheiro" e o detalhe muda para "Leve troco, por favor". O find procura na lista o objeto cujo id é igual ao estado; o detalhe vem daí. Se o estado tivesse um valor que não existe na lista, o find devolveria undefined e o acesso a .detalhe quebraria o componente — por isso é bom começar com um valor que existe, como "pix".

Repare na diferença entre o valor guardado e o rótulo: o estado guarda "dinheiro", o usuário lê "Dinheiro". O id é minúsculo e estável; o rótulo pode virar "Dinheiro em espécie" sem quebrar nada. Essa separação é a mesma que você viu no select, e vale para toda lista de opções.

No console, a lista e o estado contam a mesma história:

formas.length: 3
pagamento: "dinheiro"
escolhida.rotulo: "Dinheiro"

Sobre o key: ele fica no elemento que o map devolve — aqui, o label que envolve o input. O React usa a chave para saber qual item é qual quando a lista muda; sem ela, o console avisa em desenvolvimento e a ordem pode se confundir em listas que mudam. Como o id é único, ele é a chave natural.

6. O grupo que começa sem escolha

Nem todo grupo pode começar com uma opção marcada. O tamanho da camiseta da padaria é um exemplo: se o site já vem com "P" selecionado, metade dos clientes recebe o tamanho errado por não reparar. O certo é começar sem escolha e pedir que a pessoa decida — e o jeito de fazer isso é o estado inicial vazio, que você já viu na tabela da seção 4.

O grupo já vem com "P" marcado. Faça o estado começar vazio, mostre Escolha o tamanho enquanto ninguém escolheu e Tamanho: G depois de marcar o G.

const tamanhos = ["P", "M", "G"];

function App() {
  const [tamanho, setTamanho] = useState("P");
  return (
    <div>
      <p>Tamanho da camiseta:</p>
      {tamanhos.map((t) => (
        <label key={t}>
          <input type="radio" name="tamanho" value={t} defaultChecked={t === "P"} />
          {t}
        </label>
      ))}
      <p>Tamanho: {tamanho}</p>
    </div>
  );
}

No começo, nenhuma bolinha está marcada e o texto pede a escolha. Ao clicar em G, só ela marca, o texto vira "Tamanho: G" e as outras continuam vazias. O conta:input:checked=0 da missão confere justamente isso: zero caixas marcadas no início. Se o seu grupo marcar sozinho, procure um defaultChecked esquecido ou um checked que não compara com nada.

O passo seguinte, num formulário de verdade, é impedir o envio enquanto o tamanho estiver vazio. Isso é validação, e tem aula própria logo depois desta. Por enquanto, o par estado vazio + comparação já resolve a tela: o cliente vê que precisa escolher e o código sabe que ninguém escolheu.

7. Radio, select ou checkbox?

Os três elementos parecem intercambiáveis quando o assunto é "escolher", mas cada um resolve um caso. O critério tem duas perguntas: quantas opções existem e quantas podem valer ao mesmo tempo?

Se só uma pode valer e são poucas opções, todas importantes para a decisão, use radio — o cliente vê todas sem abrir nada. Se só uma pode valer e são muitas (estados, cidades, sabores), use select: uma lista aberta com trinta bolinhas é ruim de ler e empurra o resto da página para baixo. Se mais de uma pode valer, use checkbox, um por item.

Há também o caso de "nenhuma das opções" ou "outra", que exige uma opção extra. Num grupo de radio, essa opção é só mais um item — com value="outra" —, e o campo de texto que a acompanha aparece condicionalmente, como o cartão do presente na aula do checkbox. Num select, ela é uma option comum. O padrão é o mesmo: o estado guarda a escolha e o resto da tela deriva dela.

Uma última diferença prática: o radio ocupa mais espaço vertical, porque cada opção é uma linha. Em tela de celular, isso é bom para o toque — alvos grandes e separados — e ruim para formulários longos. O select economiza espaço e cobra um toque a mais. Não existe resposta certa universal; existe o caso da sua tela.

8. Acessibilidade do grupo

Um grupo de radio precisa de um rótulo para o grupo inteiro, não só para cada opção. A pergunta "Como você quer receber?" não pertence a nenhuma bolinha específica; ela pertence ao conjunto. A forma de amarrar isso é o fieldset com um legend — elementos que você já pode usar hoje, sem hook nenhum:

function Recebimento() {
  const [forma, setForma] = useState("retirada");

  return (
    <fieldset>
      <legend>Como você quer receber?</legend>
      <label>
        <input
          type="radio"
          name="recebimento"
          value="retirada"
          checked={forma === "retirada"}
          onChange={(e) => setForma(e.target.value)}
        />
        Retirar no balcão
      </label>
      <label>
        <input
          type="radio"
          name="recebimento"
          value="entrega"
          checked={forma === "entrega"}
          onChange={(e) => setForma(e.target.value)}
        />
        Entrega em casa
      </label>
    </fieldset>
  );
}

Com o fieldset, o leitor de tela anuncia a pergunta junto com cada opção, e o teclado entende que as bolinhas formam um conjunto. Clicar no texto do label também marca a opção, como no checkbox. E as setas do teclado pulam de uma opção para outra dentro do grupo, o que é o comportamento nativo de rádio e não precisa de código.

Se o layout não permite o fieldset, dá para usar role="radiogroup" e aria-labelledby apontando para um título. É mais verboso e mais fácil de errar; o fieldset resolve de graça. A aula de formulário acessível entra nos detalhes, mas o hábito de envolver o grupo com um rótulo vale desde o primeiro formulário.

9. Cenários do dia a dia

Cenário 1: dá para marcar as duas opções

A Ana esqueceu o name em uma das opções e o cliente conseguiu marcar retirada e entrega ao mesmo tempo. Sem o mesmo name, o navegador trata cada bolinha como um grupo separado. O conserto é igualar o nome — letra por letra, incluindo maiúsculas — em todas as opções que disputam a mesma escolha. O estado controlado até disfarça o problema, mas o teclado e o envio ficam errados.

Cenário 2: a bolinha não fica marcada

Ela trocou checked por value na comparação e a bolinha voltou ao estado anterior a cada clique. No grupo controlado, checked recebe uma expressão booleana: checked={forma === "entrega"}. Se a comparação estiver sempre falsa — valor com maiúscula diferente, por exemplo —, nenhuma opção marca. Conferir o valor do estado no console resolve em segundos.

Cenário 3: o grupo começa marcado sem o cliente escolher

Ela usou defaultChecked na primeira opção para "dar um exemplo" e metade dos pedidos saiu com a forma errada. O valor inicial de um grupo deve vir do useState, e a decisão de começar vazio é de produto, não de código. Se o campo é obrigatório, comece vazio e valide no envio; se tem um padrão aceitável, comece com ele e deixe claro na tela.

10. Fixando o que ficou

1. O que mantém várias opções no mesmo grupo?

2. O que vai para o estado quando o cliente escolhe uma opção?

3. O que escrever em checked de cada opção?

Exercício: o nome do grupo

As duas opções abaixo precisam formar um grupo: marcar uma deve desmarcar a outra. Complete o atributo que falta na segunda opção, escrevendo só o nome do atributo:

<input type="radio" ="recebimento" value="entrega" checked={forma === "entrega"} onChange={(e) => setForma(e.target.value)} />

Dica: é o atributo que agrupa os radios, com o mesmo valor nas duas opções. Se você escrever id, cada opção fica num grupo próprio e o cliente marca as duas.

11. Resumo

O radio é a escolha única entre opções visíveis. O grupo é definido pelo name igual em todas as opções, e o estado guarda o value da escolhida. No JSX controlado, checked recebe uma comparação — checked={forma === "entrega"} — e onChange lê e.target.value com a mesma função em todas as opções.

Para gerar o grupo a partir de uma lista, use map com uma key estável e guarde o id do item, não o rótulo. Para começar sem escolha, use estado vazio e mostre uma mensagem pedindo a decisão; nenhuma opção marcada é um estado legítimo. E envolver o grupo num fieldset com legend dá o rótulo do conjunto que o leitor de tela precisa.

Com isso, os quatro campos do formulário estão cobertos: texto curto, texto longo, escolha em lista, sim ou não e escolha única. O que falta é a parte que decide se o pedido pode seguir — nome vazio, telefone curto, e-mail sem arroba. A próxima aula é a validação, e ela junta tudo o que você viu até aqui num lugar só: o estado guarda o valor, a tela mostra o erro e o botão só deixa passar quando está tudo certo.

Para lembrar

  • Grupo de radio: mesmo name em todas as opções.
  • Um estado só para o grupo; checked={valor === opcao} em cada uma.
  • onChange igual em todas: setForma(e.target.value).
  • O estado guarda o value da escolhida, sempre texto.
  • defaultChecked é do mundo não controlado; não misture com checked.
  • Estado vazio = nenhuma opção marcada; use para pedir a escolha.
  • map + key geram o grupo a partir de uma lista.
  • Guarde o id, não o rótulo: o texto pode mudar sem quebrar o código.
  • fieldset com legend dá nome ao grupo inteiro.
  • Uma escolha entre muitas opções pede select, não trinta radios.
