Componente Reutilizável

A padaria da Ana tem três cartões de pão no site, e os três foram copiados à mão. Quando ela mudou o preço do francês, esqueceu os outros dois; quando mudou a espessura da borda, fez a mesma coisa em três lugares e errou em um. Nesta aula ela extrai os três cartões para um componente único, dá a ele uma lista pequena de props, cria variantes para o botão e aprende onde parar de generalizar.

Você vai aprender
  • A reconhecer repetição no JSX e transformá-la em um componente.
  • O que é a API de um componente: as props que ele aceita e o que promete devolver.
  • Como escolher nomes e quantas props bastam.
  • Variantes com uma prop de texto, em vez de cinco booleanos.
  • Quando usar children em vez de inventar props para o conteúdo.
  • O limite: por que não vale generalizar antes do terceiro uso.
  • Os erros que aparecem na hora de extrair: key, nomes vagos, estado no lugar errado.

1. A cena: três cartões iguais e três lugares para errar

A página de pães da Ana tem um bloco para cada produto: o nome, o preço, uma frase curta e a classe cartao que dá a borda e o espaçamento. Ela escreveu o primeiro, copiou duas vezes e trocou o texto. Funcionou por um mês. Neste mês, o cartão ganhou o preço em negrito, e ela esqueceu de aplicar no croissant. O site ficou com dois cartões em negrito e um sem.

Esse é o problema que o React existe para resolver, e a solução é sempre a mesma: escrever o desenho uma vez, como um componente, e passar os dados que mudam como props. O cartão deixa de ser um pedaço de HTML repetido e passa a ser uma função que recebe nome e preço e devolve o cartão pronto. Mudou o desenho? Uma função. Preço novo? Uma prop.

A ideia parece óbvia quando está escrita assim, e mesmo assim quase todo mundo começa copiando. O motivo é que copiar é mais rápido no minuto seguinte e mais caro no mês seguinte. A conta fica clara quando você soma: três cartões, cinco mudanças de layout por mês, três lugares para cada uma. São quinze edições onde deveriam ser cinco — e três oportunidades de esquecer uma.

Vale um aviso antes de começar: reutilizável não quer dizer genérico. Um componente bom é pequeno, tem poucas props e faz uma coisa. Um componente que tenta servir para tudo vira um monstro com doze props e um emaranhado de condições, e aí você trocou três cópias por um problema pior. A aula trata dos dois lados: como extrair bem e onde parar.

2. O que torna um componente reutilizável

Um componente é reutilizável quando o que muda entre um uso e outro entra por prop, e o que fica igual está no corpo da função. No cartão, o nome e o preço mudam; a estrutura, a classe e a ordem dos elementos ficam. Essa separação é a API do componente — o mesmo conceito de biblioteca, aplicado a uma função do seu próprio site.

API do componente
O conjunto de props que ele aceita e o que ele devolve na tela. É o contrato com quem usa.
prop obrigatória
Aquela sem a qual o componente mostra algo quebrado: o preço de um cartão de preço.
valor padrão
O que a prop assume quando ninguém passa nada: variante = "primario".
variante
Uma prop de texto que escolhe entre desenhos prontos: variante="destaque".
children
O conteúdo que fica entre a abertura e o fechamento da tag: <Cartao>…</Cartao>.

Há uma diferença prática entre as props de dado e as props de aparência. Dado é o que o cartão mostra: nome, preço, descrição. Aparência é como ele se mostra: destaque, tamanho, cor. Misturar as duas em uma lista única de props é o começo da confusão — e é a razão pela qual componentes grandes acabam com nomes como tipo, variante, tamanho e cor separados dos dados de verdade.

3. Extraindo o primeiro componente

O primeiro passo é o mais mecânico e o mais útil. Copie o bloco repetido para uma função com nome maiúsculo, troque os valores que mudam por props e, no lugar dos três blocos, chame o componente três vezes. A Ana fez isso e, de quebra, colocou o preço em negrito — que era a mudança pendente.

Os três cartões estão copiados à mão. Crie um componente Cartao que recebe nome e preco, use três vezes e mostre o preço em negrito, dentro de um strong, no formato R$ 12,00.

function App() {
  return (
    <div>
      <div className="cartao">
        <h2>Pão francês</h2>
        <p>R$ 12,00</p>
      </div>
      <div className="cartao">
        <h2>Pão de queijo</h2>
        <p>R$ 8,00</p>
      </div>
      <div className="cartao">
        <h2>Croissant</h2>
        <p>R$ 14,00</p>
      </div>
    </div>
  );
}

function Cartao({ nome, preco }) {
  return (
    <div className="cartao">
      <h2>{nome}</h2>
      <p><strong>{"R$ " + preco + ",00"}</strong></p>
    </div>

function App() {
  return (
    <div>
      <Cartao nome="Pão francês" preco={12} />
      <Cartao nome="Pão de queijo" preco={8} />
      <Cartao nome="Croissant" preco={14} />
    </div>
  );
}

O painel depois da solução mostra os três cartões iguais, com o preço em strong — o mesmo HTML que a Ana escreveria à mão, três vezes. A diferença não está no resultado, está no que acontece na próxima mudança: ela mexe no Cartao e os três acompanham. Isso é o reaproveitamento de verdade: uma definição, vários usos.

Repare no {"R$ " + preco + ",00"}. As chaves precisam envolver a conta inteira, senão o JSX não consegue montar o texto. E o preço é número (preco={12}), não texto: assim o componente pode somar, comparar e formatar mais tarde. Passar preco="12" também funciona na tela, mas limita quem recebe. Regra prática: número é número, texto é texto, e a formatação para português acontece na hora de mostrar.

Se você escrevesse <Cartao /> sem props, o React chamaria a função com um objeto vazio, nome e preco viriam undefined, e o cartão mostraria "undefined" no lugar do nome. Props que o componente não sobrevive sem são obrigatórias de fato, e a maneira de deixar isso claro é o nome — ou um valor padrão que faça sentido.

4. A API do componente

Com o cartão extraído, a pergunta seguinte é sempre a mesma: quantas props ele deve ter? A resposta curta é "as que mudam entre um uso e outro, e nada além". A resposta longa é uma decisão de projeto, e ela fica mais fácil quando você olha os usos antes de olhar o componente.

// três usos, três combinações de dado
<Cartao nome="Pão francês" preco={12} />
<Cartao nome="Pão de queijo" preco={8} />
<Cartao nome="Croissant" preco={14} />

Esses usos mostram que nome e preco são dados, sempre presentes. Se um cartão precisasse de uma frase de apoio só às vezes, essa seria uma prop opcional, com valor padrão vazio. Se todos os cartões têm a mesma borda, a borda não é prop: é classe, no CSS. Passar borda="1px solid #ccc" como prop seria transformar CSS em configuração de componente, e isso envelhece mal.

Dentro do componente, as props chegam como um único objeto. Ver esse objeto é o jeito mais rápido de entender o que o componente recebeu, e o painel das caixas mostra o resultado de um console.log(props):

console: renderizou: Pão de queijo
console: {"nome":"Pão de queijo","preco":8}

Duas linhas, duas lições. A primeira mostra que o componente roda uma vez por uso: três cartões são três chamadas da função, com objetos diferentes. A segunda mostra que as props são dados comuns — texto, número, objeto, função — e que o componente pode fazer o que quiser com eles. O que ele não pode é alterá-los: props são somente leitura.

Há um estilo de escrita que vale conhecer agora, porque aparece em todo código React: function Cartao({ nome, preco }). As chaves no parâmetro desestruturam o objeto de props, e você usa nome e preco direto, sem props. na frente. O efeito é o mesmo; a leitura fica mais curta e a lista de props fica visível na primeira linha da função, o que é uma vantagem enorme quando o componente cresce.

5. Variantes: uma prop que escolhe o desenho

Nem toda diferença é de dado. O botão "Comprar pão" e o botão "Ver a lista" mostram textos diferentes e têm a mesma função, mas o primeiro é escuro e o segundo é claro com borda. Isso não é dado, é aparência — e o jeito ingênuo de resolver é uma prop booleana para cada estado: escuro, grande, comBorda, arredondado. Quatro booleanos dão dezesseis combinações, das quais três fazem sentido.

O jeito que envelhece bem é uma prop de texto com um conjunto pequeno de valores permitidos, cada um mapeado para uma classe. A Ana chamou a prop de variante, e a CSS que já existe tem .botao--primario e .botao--secundario:

.botao { padding: 8px 16px; border-radius: 6px; border: 1px solid transparent; }
.botao--primario { background: #7a3e1d; color: #fff; }
.botao--secundario { background: #fff; color: #7a3e1d; border-color: #7a3e1d; }

Com as classes prontas, o componente só precisa montar o nome. A variante entra como texto na classe e o valor padrão cobre o caso mais comum — quem chama não é obrigado a repetir variante="primario" em todos os botões.

Os dois botões têm só a classe botao. Crie um componente Botao com as props rotulo e variante (padrão "primario"), e faça a classe virar botao botao--primario ou botao botao--secundario.

function App() {
  return (
    <div>
      <button className="botao">Comprar pão</button>
      <button className="botao">Ver a lista</button>
    </div>
  );
}
<div>
  <button class="botao">Comprar pão</button>
  <button class="botao">Ver a lista</button>
</div>

function Botao({ rotulo, variante = "primario" }) {
  return <button className={"botao botao--" + variante}>{rotulo}</button>;
}

function App() {
  return (
    <div>
      <Botao rotulo="Comprar pão" />
      <Botao rotulo="Ver a lista" variante="secundario" />
    </div>
  );
}

Depois da solução, o painel mostra um botão com class="botao botao--primario" e outro com class="botao botao--secundario". O primeiro nem precisou da prop: o valor padrão entrou sozinho. E se alguém escrever variante="gigante", a classe vira botao botao--gigante, que não existe no CSS — o botão fica com o estilo base e ninguém vê erro. É o preço de usar texto livre em vez de uma lista fechada.

Para evitar o erro silencioso, o componente pode escolher a classe em um mapa e cair no padrão quando o valor não existe:

function Botao({ rotulo, variante = "primario" }) {
  const estilos = {
    primario: "botao botao--primario",
    secundario: "botao botao--secundario"
  };
  const classes = estilos[variante] || estilos.primario;

  return <button className={classes}>{rotulo}</button>;
}

Esse mapa é a forma mais simples de "lista fechada de variantes" sem nenhuma biblioteca. Ele tem uma vantagem extra: a lista fica visível em um lugar só, e quem for adicionar uma variante nova sabe exatamente onde mexer. Quando o projeto crescer, ferramentas de tipagem fazem esse trabalho — mas a ideia é a mesma.

6. O slot: children para o conteúdo que muda

Há um caso em que a diferença não é dado nem aparência: é estrutura. O cartão dos pães tem título e contagem; o dos bolos também, mas com outro texto; o de encomendas tem um parágrafo e um botão. Se você tentar cobrir isso com props, acaba com temBotao, textoDoBotao, mostraContagem — e o componente vira uma máquina de adivinhar o que desenhar.

A solução do React é a prop especial children: o que fica entre a abertura e o fechamento do componente vai parar ali. O Cartao deixa de saber o que tem dentro e passa a só embrulhar com a classe e o espaçamento. Quem chama decide o conteúdo, e o componente continua reutilizável sem precisar de uma prop nova.

Os dois blocos repetem a div com a classe cartao. Crie um componente Cartao que devolve um section com essa classe e o children dentro. Use-o nas duas seções.

function App() {
  return (
    <div>
      <div className="cartao">
        <h2>Pães</h2>
        <p>12 tipos</p>
      </div>
      <div className="cartao">
        <h2>Bolos</h2>
        <p>8 tipos</p>
      </div>
    </div>
  );
}
<div>
  <div class="cartao">
    <h2>Pães</h2>
    <p>12 tipos</p>
  </div>
  <div class="cartao">
    <h2>Bolos</h2>
    <p>8 tipos</p>
  </div>
</div>

function Cartao({ children }) {
  return <section className="cartao">{children}</section>;
}

function App() {
  return (
    <div>
      <Cartao>
        <h2>Pães</h2>
        <p>12 tipos</p>
      </Cartao>
      <Cartao>
        <h2>Bolos</h2>
        <p>8 tipos</p>
      </Cartao>
    </div>
  );
}

O painel mostra dois section com a classe cartao, cada um com o seu conteúdo dentro. O componente não sabe quantos elementos recebeu: pode ser um título, cinco parágrafos ou nada. É a mesma ideia da prop, com o conteúdo no lugar do dado.

Duas observações práticas. A primeira: children pode ser qualquer coisa que o React desenhe — texto, elementos, outros componentes, uma lista. A segunda: quando o componente precisa de algum pedaço do conteúdo em um lugar específico (um título no topo, um botão no rodapé), o children sozinho não resolve; aí entram props de elemento ou componentes compostos, que é assunto de outra aula. Para o caso comum, o slot basta.

7. Onde parar de generalizar

Depois do primeiro componente extraído, vem a tentação: extrair tudo. A Ana passou uma tarde criando um CartaoGenerico com props para título, subtítulo, imagem, rodapé, cor, borda, botão e contagem. No fim, o componente tinha doze props, sete delas opcionais, e cada uso passava nove. O código ficou maior do que as três cópias originais.

A regra que evita esse destino é simples: espere o terceiro uso. Duas ocorrências parecidas podem ser coincidência; três indicam um padrão. Antes disso, copiar duas vezes custa menos do que manter uma abstração errada — e abstração errada é mais difícil de desfazer do que duplicação.

Sinais de que o componente passou do ponto: props booleanas que só fazem sentido juntas; nomes como tipo, modo ou opcoes que escondem três componentes diferentes; condições dentro do JSX que devolvem estruturas completamente distintas; e a sensação de que qualquer mudança no visual exige uma prop nova. Quando isso acontece, o caminho é dividir: dois ou três componentes pequenos, cada um com uma responsabilidade, em vez de um grande com doze interruptores.

Também vale desconfiar de props que são "só para o CSS": corDaBorda, tamanhoDaFonte, espacamento. Elas obrigam o componente a repassar estilo e amarram o desenho ao JavaScript. Se o cartão pode ter três tamanhos, uma prop tamanho com três valores e três classes resolve; se ele pode ter qualquer tamanho, o lugar é a classe, escolhida por quem usa.

8. Os tropeços na hora de extrair

Extrair um componente parece mecânico e tem suas armadilhas. Quatro delas aparecem sempre, e todas têm sintoma visível no painel ou no console.

O primeiro é o mais comum e o mais fácil de consertar. Quando o cartão era uma div escrita dentro do map, a key ia nela. Depois da extração, a key precisa ir no componente: o React usa a chave para identificar cada item da lista, e ela não é passada como prop — é consumida pelo próprio React.

O terceiro merece atenção porque é conceitual. Estado dentro de um componente é privado: dois Cartao têm dois estados, e um não sabe do outro. Se o botão "+" de um cartão precisa mudar o total que aparece no rodapé da página, o estado sai do cartão e sobe para o pai, que passa o valor e a função de mudar por prop. É o mesmo raciocínio de elevar estado, aplicado ao componente que você acabou de criar.

E o segundo, o "undefined" na tela, é o erro de digitação que mais aparece: titulo em um lugar, name no outro. Com desestruturação na assinatura, a lista de props fica na primeira linha da função, e a comparação com o uso é de dois segundos. Sem ela, você procura no corpo inteiro.

9. Cenários do dia a dia

Cenário 1: o preço novo em dois cartões de três

A Ana mudou o preço do pão francês no cartão escrito à mão e esqueceu os outros. Com um componente único, o preço vem por prop e não existe "outro cartão" para esquecer — mas o dado ainda pode estar em três lugares no App. Quando os dados passam de props simples para uma lista, vale guardar a lista em um estado e renderizar com map: um lugar de verdade, três usos.

Cenário 2: o botão que ficou gigante em uma tela

Ela passou tamanho="grande" em um botão e o componente não conhecia esse valor: a classe virou botao--grande, que não existe no CSS. Nada quebrou e nada mudou. Com o mapa de variantes da seção 5, o valor desconhecido cai no padrão e o botão continua utilizável — e a lista de variantes válidas fica escrita em um lugar só.

Cenário 3: o cartão que só servia para pão

Ao extrair, ela deixou dentro do componente a frase "assado hoje às 5h", que só valia para o pão francês. Os outros dois cartões passaram a mentir. A correção foi mover a frase para uma prop opcional com valor padrão vazio, e não criar uma prop mostrarFrase: quem tem a informação decide se passa. Componente reutilizável não deve saber de qual produto se trata.

Complete o componente. Na primeira lacuna, o conteúdo que chega entre as tags; na segunda, o valor padrão da prop variante, que deve ser "primario" quando ninguém passar nada:

function Cartao({ , variante = }) { return <section className={"cartao cartao--" + variante}>{children}</section>; }

Dica: a primeira é o nome especial que o React usa para o conteúdo entre as tags. A segunda é um texto — o valor padrão entra no lugar do undefined quando a prop não é passada, e precisa de aspas, porque é uma string.

11. Resumo

Componente reutilizável nasce de repetição: o mesmo bloco escrito duas ou três vezes, com valores diferentes. A extração é mecânica — copiar para uma função com nome maiúsculo, trocar o que muda por props, chamar em todos os lugares. O que exige decisão é a API: quais props existem, com que nomes, e o que fica fixo no corpo. Regra prática: dado entra por prop, aparência entra por variante, conteúdo entra por children, e CSS fica no CSS.

Variantes com uma prop de texto e um mapa de classes custam pouco e evitam a explosão de booleanos. Um valor padrão cobre o caso mais comum e deixa os usos curtos. E o limite é o terceiro uso: generalizar antes disso produz abstração errada, que é mais cara de manter do que a duplicação. Se o componente precisa de doze props para servir a três telas, ele provavelmente são três componentes.

Vale reparar no que a Ana ganhou além das linhas economizadas. O cartão virou um lugar de conversa: quando ela quer mudar a borda, sabe onde; quando o preço muda, sabe de onde vem; quando um cartão aparece diferente, sabe que é prop. Um componente bem desenhado é documentação do site — e é por isso que o esforço de extrair compensa mesmo quando o HTML final é idêntico ao copiado.

O próximo passo natural é juntar vários componentes sem criar div inútil no caminho. O React tem uma ferramenta só para isso, e é o assunto da próxima aula.

Para lembrar

  • Repetição com dados diferentes é o sinal de que falta um componente.
  • A API do componente é a lista de props: pequena, com nomes claros.
  • Dado por prop; aparência por variante; conteúdo por children.
  • variante = "primario" no parâmetro é o valor padrão.
  • children é o que fica entre as tags do componente.
  • Espere o terceiro uso antes de generalizar.
  • key vai no componente, dentro do map, não na div de fora.
  • Estado dentro do componente é privado; se os usos precisam concordar, o estado sobe.
  • Componente não deve saber de qual produto se trata: isso é prop.
