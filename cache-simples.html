Cache simples

A vitrine da Ana passou a mostrar o preço do dia buscado no servidor. Ficou bonito e ficou lento: cada visita à página refazia o pedido, e no 3G da feira o preço demorava três segundos para aparecer. Pior, a Ana percebeu que clicava em “ver preço”, voltava, clicava de novo — e o servidor recebia três pedidos idênticos em quinze segundos. A resposta era a mesma nas três vezes; só o trabalho de perguntar de novo era desperdício. Nesta aula ela aprende a guardar a resposta na primeira vez e a servir do bolso nas próximas.

Você vai aprender
  • O que é cache, em três palavras: chave, valor e validade.
  • Como consultar antes de pedir, com um Map.
  • Onde o cache vive: useRef, variável de módulo ou estado — e a diferença prática.
  • Como dar validade à entrada para o preço não ficar velho a tarde inteira.
  • Por que a chave do cache tem de ser a consulta inteira, e não “a última”.
  • Quando não vale a pena guardar — e por que isso é metade do assunto.
  • Como mostrar na tela que o dado veio do cache.

1. A cena: os três cliques e as três esperas

O componente da vitrine, na versão sem cache, faz o que parece certo: um efeito busca o preço quando a página monta, guarda no estado e mostra. Funciona uma vez. O problema aparece quando a Ana navega: cada volta para a vitrine desmonta e monta o componente de novo, o efeito roda de novo, o pedido vai de novo.

function buscarPreco(nome) {
  chamadas += 1;
  return new Promise((ok) => setTimeout(() => ok(1.2), 0));
}

function App() {
  const [preco, setPreco] = useState(null);

  useEffect(() => {
    buscarPreco("pão francês").then((valor) => setPreco(valor));
  }, []);

  return <p>Pão francês: R$ {preco}</p>;
}

Cada montagem custa uma ida ao servidor e um tempinho de tela vazia. Numa página só, nada demais. Num site em que a pessoa entra e sai da vitrine cinco vezes, são cinco esperas para receber cinco vezes o mesmo número. O cache resolve isso com uma ideia antiga e modesta: depois de receber a resposta, guarde uma cópia; antes de pedir, olhe se a cópia está ali.

2. O que é cache, na prática

Cache é uma reserva de respostas já recebidas, guardadas para serem reusadas. Toda entrada de cache tem três partes, e quem esquece a terceira é que se dá mal. A chave diz respeito a qual pergunta — aqui, o nome do pão. O valor é a resposta que veio. A validade é por quanto tempo essa resposta ainda pode ser considerada verdade.

A validade é o que separa cache de mentira. Guardar o preço de hoje e servir amanhã é mostrar preço errado com cara de certo. Guardar por dez segundos, numa vitrine que muda de hora em hora, é seguro. A pergunta “por quanto tempo?” não tem resposta universal: ela depende de quanto tempo o dado leva para envelhecer de verdade. Preço de pão muda no começo do dia; cotação muda a cada segundo; CEP de um endereço não muda nunca.

cache
Reserva de respostas prontas, guardadas para não perguntar de novo a mesma coisa.
chave
O que identifica a pergunta: o nome do pão, a página, o filtro. Duas perguntas diferentes precisam de chaves diferentes, senão uma resposta atende a outra.
validade
Por quanto tempo a cópia ainda vale. Passou do prazo, a entrada é stale (velha) e a resposta tem de ser buscada de novo.
stale
A entrada velha. Ainda pode ser mostrada por um instante enquanto a nova chega, mas não pode ser tratada como verdade.
invalidar
Apagar ou marcar a entrada como velha de propósito — depois de um preço novo ser salvo, por exemplo.

3. Guardar e consultar: o Map

A estrutura de dados certa para um cache é o Map: um dicionário em que você procura pela chave e recebe o valor. Tem set para guardar, get para ler e has para saber se a chave existe. Diferente de um objeto comum, o Map aceita qualquer coisa como chave e sabe quantos itens tem.

O botão busca o preço duas vezes seguidas e o servidor é chamado nas duas. Use o Map chamado cache: guarde na primeira busca e sirva do cache na segunda, sem chamar a API — a tela tem de mostrar veio do: cache e chamadas à API: 1.

function buscarPreco(nome) {
  return new Promise((ok) => setTimeout(() => ok(1.2), 0));
}

const cache = new Map();

function App() {
  const [preco, setPreco] = useState(null);
  const [origem, setOrigem] = useState("");
  const [n, setN] = useState(0);

  async function buscar(nome) {
    const valor = await buscarPreco(nome);
    setPreco(valor);
    setOrigem("servidor");
    setN((v) => v + 1);
  }

  async function verDuasVezes() {
    await buscar("pão francês");
    await buscar("pão francês");
  }

  return (
    <div>
      <button id="buscar" onClick={verDuasVezes}>buscar duas vezes</button>
      <p>preço: {preco === null ? "—" : "R$ " + preco.toFixed(2).replace(".", ",")}</p>
      <p>veio do: {origem}</p>
      <p>chamadas à API: {n}</p>
    </div>
  );
}

4. Onde o cache vive

Essa é a decisão que mais muda o comportamento, e ela quase nunca é explicada. O cache pode ficar em três lugares, e cada um sobrevive a coisas diferentes:

OndeSobrevive a re-render?Sobrevive a desmontar?Quando usar
useStatesimnãoquando o cache aparece na tela e mudar deve redesenhar
useRefsimnãomemória do componente: guarda o Map sem redesenhar
variável de módulosimsimcache que vale para o site inteiro, entre páginas, até recarregar

A variável de módulo — const cache = new Map() no topo do arquivo, fora do componente — é a mais generosa: ela nasce uma vez, quando o arquivo é carregado, e morre quando a página é recarregada. Como o componente é desmontado e montado a cada visita, o cache de módulo é o único que faz a segunda visita valer. É o que a caixa da seção anterior usou, e é a escolha certa para preço de vitrine.

O useRef resolve o caso em que o cache pertence à vida daquele componente: um Map criado com useRef(new Map()) fica guardado entre desenhos e some quando o componente sai da tela. Use ref quando a reserva é da instância; use módulo quando a reserva é do site; use estado quando a tela precisa reagir ao cache — por exemplo, para desenhar uma lista de “já vistos”.

5. Validade: a etiqueta com hora

Sem validade, o cache vira armadilha: a Ana mudaria o preço no servidor e a vitrine mostraria o valor da manhã até alguém recarregar a página. A solução é guardar, junto do valor, o instante em que ele foi buscado, e comparar com o instante de agora.

Nas caixas deste guia não há relógio de verdade — e usar a hora real deixaria o exemplo impossível de conferir, porque cada execução daria um resultado. Por isso o “agora” aqui é um contador que você avança com um botão. No seu projeto, o mesmo lugar é ocupado por Date.now(), que devolve milissegundos desde 1970 — o tipo de número que só serve para subtrair.

O cache está sendo usado para sempre, mesmo depois dos 10 segundos de validade. Faça a consulta verificar a idade da entrada: se agora - salvoEm >= 10, busque de novo no servidor (o contador de chamadas tem de chegar a 2 depois de buscar, avançar e buscar).

function buscarPreco(versao) {
  return new Promise((ok) => setTimeout(() => ok(1.2 + versao * 0.1), 0));
}

const cache = new Map();

function App() {
  const [agora, setAgora] = useState(0);
  const [preco, setPreco] = useState(null);
  const [n, setN] = useState(0);

  async function ver() {
    if (cache.has("pão francês")) {
      setPreco(cache.get("pão francês").valor);
    } else {
      const valor = await buscarPreco(n);
      cache.set("pão francês", { valor: valor, salvoEm: agora });
      setPreco(valor);
      setN(n + 1);
    }
  }

  return (
    <div>
      <button id="buscar" onClick={ver}>ver preço</button>
      <button id="avancar" onClick={() => setAgora(agora + 10)}>avançar 10 s</button>
      <p>preço: {preco === null ? "—" : "R$ " + preco.toFixed(2).replace(".", ",")}</p>
      <p>agora: {agora} s</p>
      <p>chamadas à API: {n}</p>
    </div>
  );
}

A variável velha é a regra escrita por extenso, e vale criar esse nome mesmo quando o projeto é pequeno: ela documenta a decisão. Note os dois casos que caem em “velha”: entrada inexistente (!entrada) e entrada com idade acima do limite. Entrada inexistente é o primeiro acesso, e é justo que ele vá ao servidor.

Existe um meio-termo entre mostrar o valor velho e mostrar tela vazia, e ele tem nome: stale-while-revalidate — “mostre o velho enquanto busca o novo”. A tela desenha o preço que está no cache na hora e a busca acontece por trás; quando a resposta chega, o preço é atualizado. Ninguém espera, e o valor velho aparece no máximo por instantes. Na prática: leia o cache, pinte, dispare a busca, substitua ao chegar.

6. Uma chave por consulta

O erro mais caro de cache é usar um espaço só para todas as perguntas. A Ana tinha isso na primeira versão da vitrine: guardava “o último preço buscado” numa variável. Enquanto ela olhava só o pão francês, funcionava. No dia em que clicou no brioche, a tela mostrou o preço do francês — com a confiança de quem acertou.

O botão consulta o pão francês e depois o brioche. O cache guarda um valor só, então o brioche aparece com o preço do francês. Guarde uma entrada por pão no Map e mostre R$ 4,50 — brioche.

function buscarPreco(nome) {
  return new Promise((ok) => setTimeout(() => ok(nome === "brioche" ? 4.5 : 1.2), 0));
}

const ultimo = { valor: 0 };

function App() {
  const [nome, setNome] = useState("—");
  const [preco, setPreco] = useState(0);

  async function ver(pao) {
    setNome(pao);
    if (ultimo.valor) {
      setPreco(ultimo.valor);
      return;
    }
    const valor = await buscarPreco(pao);
    ultimo.valor = valor;
    setPreco(valor);
  }

  async function verOsDois() {
    await ver("pão francês");
    await ver("brioche");
  }

  return (
    <div>
      <button id="dois" onClick={verOsDois}>ver os dois</button>
      <p>R$ {preco.toFixed(2).replace(".", ",")} — {nome}</p>
    </div>
  );
}

Um cuidado que só aparece em projeto que roda o dia inteiro: o Map cresce. Cada pão diferente vira uma entrada que fica ali até a página ser recarregada. Para uma vitrine com trinta pães não é problema. Para uma busca que aceita qualquer texto digitado, um cache sem limite guarda todas as consultas da tarde. A saída é simples: apague a entrada mais antiga quando o cache.size passar de um número que você escolheu — vinte, cinquenta —, ou use o cache só para as consultas mais repetidas.

A chave tem de conter tudo que muda a resposta. Se a API recebe filtro e página, a chave é o filtro mais a página; se depende de quem está logado, o identificador da pessoa entra na chave — nunca o contrário. Cache que ignora parte da pergunta devolve a resposta de outra pessoa, e esse é o tipo de bug que passa em teste e aparece em produção.

7. Cache que mentiu: invalidar de propósito

Existe uma hora em que a cópia deixa de ser útil mesmo dentro da validade: quando você mesmo muda o dado. A Ana ajustou o preço do brioche pela tela de administração e voltou para a vitrine, que mostrou o valor antigo por dez segundos. Ela sabia que estava certo no servidor e não acreditou na tela — desconfiança justa.

A saída é cache.delete(chave) logo depois de uma gravação bem-sucedida. Chama-se invalidar: o dado mudou, a cópia não presta mais. Não é preciso apagar o cache inteiro; apague a chave afetada. Se a gravação mexe em várias telas, apague as chaves relacionadas — preço do pão afeta a vitrine e o carrinho.

Duas linhas de log como estas, colocadas dentro da função de busca, mostram de onde veio cada resposta e economizam muito tempo de investigação:

console: entregue do cache: pão francês
console: buscando no servidor: brioche

A segunda linha útil é a contagem de entradas, que mostra se o cache está crescendo como você espera — uma entrada por pão, não uma por visita:

console: tamanho do cache: 2

Se o log do servidor aparece sempre, o cache não está sendo encontrado: chave diferente da usada no set, Map recriado a cada desenho ou validade curta demais. Os três tropeços da próxima seção são exatamente essas três causas.

8. Os tropeços com cache

O tropeço silencioso é o cache que nunca acerta: const cache = new Map() escrito dentro do componente. A cada desenho nasce um Map novo, vazio, e a consulta nunca encontra nada. O sintoma é o contrário do esperado — todas as buscas vão ao servidor, e o código parece certo na leitura.

O segundo é o oposto: guardar sem validade e nunca invalidar. A tela fica rápida e mentirosa, e o conserto costuma ser procurado no servidor, que está certíssimo. O terceiro é guardar o que não deve: resposta com dado pessoal, token, carrinho de outra pessoa. Cache é memória compartilhada pelo tempo que você escolher — e vazamento de dado também.

9. Cenários do dia a dia

Cenário 1: a vitrine visitada cinco vezes

A Ana entrava na vitrine, voltava para a home, entrava de novo — e cada volta custava uma ida ao servidor. Com o cache de módulo, a segunda visita em diante aparece instantânea. O número de chamadas caiu de cinco para uma por sessão, e a sensação de velocidade melhorou mais do que qualquer ajuste de CSS.

Cenário 2: o preço que a Ana mudou e a tela não

Ela salvou o preço novo do brioche e voltou para a vitrine: R$ 4,50 no servidor, R$ 4,00 na tela. O cache.delete("brioche") depois do salvamento resolveu o caso e ensinou a regra que fica: quem escreve tem a obrigação de avisar quem lê. Cache sem invalidação é uma segunda fonte de verdade, e duas fontes de verdade sempre discordam.

Cenário 3: o cache que não devia existir

No painel de encomendas, a Ana guardou a lista por cinco minutos para “ficar mais rápido”. O cliente ligou dizendo que a encomenda tinha sumido do painel; ela estava lá, salva, mas fora do cache. Depois disso ela adotou uma regra: dado que a pessoa acabou de gravar, ou dado que ela precisa conferir, entra sem cache — ou com validade de segundos.

Exercício: a memória do componente

O cache precisa sobreviver aos desenhos do componente sem provocar um novo desenho quando muda. Complete com o hook que guarda um valor entre renders sem redesenhar:

function Vitrine() { const cache = (new Map()); ... }

Dica: é o mesmo hook que guarda a referência de um elemento do DOM. Ele devolve um objeto com uma propriedade current, e mudar essa propriedade não chama o componente de novo.

11. Resumo

Cache é guardar a resposta com uma chave e uma validade, e consultar antes de pedir. A ordem importa: has primeiro, servidor depois. O lugar onde o Map vive decide o alcance — dentro do componente ele morre a cada desmontagem; fora, em variável de módulo, ele vale para o site até recarregar a página; em useRef, vale enquanto o componente existir, sem redesenhar.

Validade é o que impede o cache de mentir, e invalidação é o que impede o cache de contradizer você mesmo. A chave precisa conter tudo o que muda a resposta. E nem todo dado merece cache: o que a pessoa acabou de gravar, o que é pessoal e o que precisa estar certo agora ficam de fora.

Para lembrar

  • Cache = chave + valor + validade. Sem validade, é mentira guardada.
  • Map com has, get, set e delete.
  • Consulte o cache antes de chamar a API, nunca depois.
  • Map fora do componente sobrevive a desmontar; dentro, não.
  • Guarde salvoEm junto do valor e compare com o agora.
  • Uma chave por pergunta: nome, filtro, página, pessoa.
  • Depois de gravar, cache.delete(chave).
  • Log de “veio do cache” / “foi ao servidor” economiza uma tarde de depuração.
