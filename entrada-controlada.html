Entrada Controlada

A Ana recebe encomendas por telefone e anota o nome do cliente num campo do site. O texto aparece na tela, ela vê a letra surgir, e mesmo assim o site não sabe quem é o cliente: o parágrafo logo abaixo continua vazio e o botão de fechar o pedido reclama que falta o nome. O problema não é o teclado nem o navegador — é que ninguém contou ao estado do React o que foi digitado. Nesta aula ela liga o campo ao estado e escreve a sua primeira entrada controlada.

Você vai aprender

  • O par value e onChange, e por que um sem o outro não funciona.
  • De onde vem o texto digitado: e.target.value.
  • O ciclo completo de uma tecla: evento, estado, nova tela.
  • Por que value sozinho congela o campo (e o aviso que o React deixa no console).
  • Como limpar um campo com um botão sem tocar no DOM na mão.
  • Os três tropeços mais comuns de quem está começando com formulários.

1. A cena: o nome que a tela esquece

Na aula de eventos, a Ana aprendeu a reagir a um clique. Agora ela quer o contrário: reagir ao que o cliente digita. A página tem um campo de texto e um parágrafo que deveria mostrar o resumo do pedido. Ela escreveu o campo do jeito que aprendeu no HTML puro:

function App() {
  return (
    <div>
      <input placeholder="Nome do cliente" />
      <p>Cliente: ...</p>
    </div>
  );
}

Ela clica no campo, digita Maria e vê a letra aparecer. Só que o parágrafo continua "Cliente: ...". Nada aconteceu do lado do React, porque nada foi avisado: o texto está guardado dentro do próprio elemento input, que é uma peça do navegador, e não dentro do componente. São dois mundos que não se falam.

Isso vira problema de verdade quando a Ana tenta usar o nome: o botão "Fechar pedido" monta a mensagem com uma variável que está vazia; o resumo mostra um traço; a validação acha que o cliente não digitou nada e libera o pedido em branco. O campo parece funcionar — e é justamente essa a armadilha. Funcionar na tela não é o mesmo que funcionar no programa.

Repare que a Ana não errou a sintaxe. O código roda, a página aparece, o campo aceita letras. O erro é de arquitetura: existem duas cópias do mesmo dado, uma na tela e outra no código, e ninguém as mantém iguais. Toda a aula de hoje é sobre juntar essas duas cópias em uma só.

2. Dois donos para o mesmo dado

Um campo de texto pode ser escrito de duas maneiras em React, e a diferença é quem guarda o valor. No primeiro jeito, o campo não controlado, o navegador é o dono: ele guarda o texto, cuida do cursor, apaga quando você apaga. O componente só descobre o que tem ali se for lá ler — e, enquanto ninguém lê, o React não tem motivo nenhum para redesenhar a tela. Foi o que a Ana escreveu sem querer.

No segundo jeito, o campo controlado, o dono é o estado do componente. O elemento input deixa de ter memória: ele mostra o que o estado manda e avisa cada tecla para que o estado se atualize. A tela passa a ser um reflexo do estado — a mesma ideia que sustenta o contador das aulas anteriores, agora aplicada a uma caixa de texto.

3. O par que faz o campo obedecer

Controlar um campo é dar duas instruções a ele. A primeira diz o que mostrar: value={nome}. A segunda diz o que fazer quando o cliente digita: onChange={(e) => setNome(e.target.value)}. As duas juntas fecham um ciclo, e o ciclo é a aula inteira.

O campo aceita o nome, mas o parágrafo não muda. Ligue o campo ao estado: dê a ele value={nome} e um onChange que guarde o que foi digitado. A missão digita Maria no campo e confere se aparece "Cliente: Maria".

function App() {
  const [nome, setNome] = useState("");

  return (
    <div>
      <label>Cliente</label>
      <input placeholder="Nome do cliente" />
      <p>Cliente: ...</p>
    </div>
  );
}
<div>
  <label>Cliente</label>
  <input placeholder="Nome do cliente">
  <p>Cliente: ...</p>
</div>

function App() {
  const [nome, setNome] = useState("");

  return (
    <div>
      <label>Cliente</label>
      <input
        placeholder="Nome do cliente"
        value={nome}
        onChange={(e) => setNome(e.target.value)}
      />
      <p>Cliente: {nome}</p>
    </div>
  );
}

Leia o código da solução de baixo para cima, porque é assim que ele funciona. O estado nome começa vazio. O input recebe value={nome}, então o campo começa vazio — e continuaria vazio para sempre se ninguém mudasse o estado. Quem muda é o onChange: cada vez que o cliente aperta uma tecla, o React chama a função, ela pega o texto atual do campo e entrega ao setNome. O estado muda, o componente roda de novo, e agora value={nome} vale a letra nova. O parágrafo, que lê o mesmo estado, aparece junto.

O detalhe que engana: o campo nunca guarda o texto. Ele recebe o texto, a cada render, do estado. Se você pensar no input como um espelho e no estado como a pessoa na frente dele, tudo fica mais fácil. É por isso que se chama entrada controlada: quem controla é o estado, não o navegador.

4. De onde vem o texto digitado: e.target.value

Falta entender aquele e. Quando o cliente digita, o navegador dispara um evento, e o React chama a função que você entregou ao onChange passando um objeto que descreve o que aconteceu. Esse objeto é o e — de event, evento. Na aula de eventos ele serviu para descobrir qual botão foi clicado; num campo de texto, serve para descobrir o que foi digitado, e o caminho disso é e.target.value.

e
O objeto do evento: tudo o que se sabe sobre aquele acontecimento (que tipo de evento foi, quando, em qual elemento). É o primeiro parâmetro da função do onChange.
e.target
O elemento que disparou o evento. Num campo de texto, é o próprio input — o elemento do DOM, com todos os atributos dele.
e.target.value
O texto que está dentro do campo naquele instante, já com a letra recém-digitada. Sempre uma string, mesmo em campos numéricos.
setNome
A função que vem do useState. Ela não muda a variável nome na hora: pede ao React para renderizar o componente de novo com o valor novo.
entrada controlada
Um campo cujo valor vem do estado (value) e cujas mudanças voltam para o estado (onChange). O dado mora num lugar só.

O tropeço aqui é escrever e em vez de e.target.value. O estado passa a guardar o objeto do evento inteiro; na tela, o campo mostra a conversão para texto desse objeto. Nada quebra de imediato, e é isso que torna o erro chato: o programa continua rodando com um dado errado dentro dele.

Agora um caso mais sutil, e muito comum: o onChange existe, mas ignora o que foi digitado.

Digite qualquer nome no campo e veja: ele volta a ser "Ana". O onChange está escrevendo um valor fixo em vez de guardar o que foi digitado. Conserte a função para que o cumprimento acompanhe o nome. A missão digita Bruno e confere "Bom dia, Bruno".

function App() {
  const [nome, setNome] = useState("");

  return (
    <div>
      <input value={nome} onChange={() => setNome("Ana")} />
      <p>Bom dia, {nome || "..."}</p>
    </div>
  );
}
<div>
  <input value="">
  <p>Bom dia, ...</p>
</div>

    </div>

Aqui está a prova de quem manda no campo. A Ana digitou "Bruno", mas o onChange disse ao estado que o nome era "Ana". O React redesenhou o componente com o estado errado, e o input obedeceu: mostrou "Ana". O texto digitado não foi perdido por acaso — ele foi substituído, porque o campo exibe o estado e não a própria memória.

Guardar isso resolve metade dos bugs de formulário: se o campo mostra algo que você não esperava, não brigue com o campo. Olhe o estado. O campo é só o espelho.

5. O ciclo completo, uma tecla por vez

Vale acompanhar uma tecla do começo ao fim, porque todos os conceitos da aula aparecem nessa sequência. A Ana digitou M no campo vazio:

1) O navegador registra a tecla e dispara um evento de entrada. 2) O React chama a função do onChange com o objeto do evento. 3) A função lê e.target.value e encontra "M". 4) setNome("M") avisa o React que o estado mudou. 5) O React roda o componente App de novo, agora com nome valendo "M". 6) O JSX produz um input com value="M" e um parágrafo com "Cliente: M". 7) O React compara com a tela anterior e atualiza só o que mudou. A letra aparece — mas ela apareceu porque o estado mudou, não porque o teclado escreveu na tela.

Para ver esse ciclo acontecendo, coloque um console.log dentro do componente, antes do return. Ele roda uma vez por render, então cada linha corresponde a uma tecla:

digitou: M
digitou: Ma
digitou: Mar
digitou: Mari
digitou: Maria

Cinco teclas, cinco linhas, cinco renders. Esse número vai importar mais adiante, na aula de atualizações em lote: o React não redesenha a tela a cada tecla por gula, ele redesenha porque o estado mudou. Se o estado não mudasse, nada seria redesenhado.

Duas consequências práticas caem daqui. A primeira: como o valor passa obrigatoriamente pelo estado, você pode transformá-lo no caminho — gravar sempre em maiúsculas, cortar o excesso de espaços, impedir letras num campo de telefone. A segunda: e.target.value é sempre texto. Se o cliente digita 3 num campo de quantidade, o estado recebe a string "3", e não o número 3. Para somar, você precisa converter com Number(...). Essa conversão é o primeiro assunto da próxima aula.

6. O mesmo dado em três lugares da tela

Com o campo controlado, mostrar o nome em outros pontos da página fica trivial: todos leem o mesmo estado. É o que a Ana precisa na etiqueta do pedido, que sai em maiúsculas, e no botão que só deve liberar quando houver um nome.

function App() {
  const [nome, setNome] = useState("");

  return (
    <div>
      <label htmlFor="cliente">Cliente</label>
      <input
        id="cliente"
        value={nome}
        onChange={(e) => setNome(e.target.value)}
      />
      <p>Cliente: {nome || "ninguém ainda"}</p>
      <p>Etiqueta: {nome.toUpperCase()}</p>
      <button disabled={nome.length === 0}>Fechar pedido</button>
    </div>
  );
}

Três leituras, um estado. O parágrafo mostra o nome como ele foi digitado; a etiqueta mostra o mesmo nome em maiúsculas; o botão fica desabilitado enquanto o texto estiver vazio. Nenhuma dessas três coisas é um estado novo — são cálculos feitos na hora de desenhar, a partir do estado que já existe.

Esse ponto merece atenção porque é onde muita gente se perde: é tentador criar const [etiqueta, setEtiqueta] = useState("") e atualizar as duas variáveis a cada tecla. Não faça. Duas variáveis para o mesmo dado voltam ao problema da seção 2, só que agora dentro do componente. O maiúsculo da etiqueta é uma consequência do nome, e consequência se calcula, não se guarda. A aula de estado derivado é dedicada a esse critério.

O htmlFor ali também tem história: no HTML ele se chama for, mas for é palavra reservada do JavaScript, então o React usa htmlFor no JSX e converte para for no HTML gerado. É o mesmo caso do className. Clicar na palavra "Cliente" leva o cursor para o campo, o que ajuda bastante no celular.

7. O campo que trava: value sem onChange

Agora o erro mais instrutivo da aula. Se você der value e esquecer o onChange, o campo vira uma vitrine: mostra o texto, mas não aceita nenhuma letra. A tecla é pressionada, o navegador até tenta escrever, o React redesenha com o valor antigo — e a letra desaparece. O React ainda avisa no console:

Warning: You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field. If the field should be mutable use `defaultValue`. Otherwise, set either `onChange` or `readOnly`.

A mensagem diz exatamente o que está acontecendo e oferece as duas saídas. A primeira: defaultValue em vez de value, quando você quer um valor inicial mas não quer controlar o campo — o navegador assume a partir dali. A segunda: readOnly, quando o campo deve mesmo ser só de leitura e você quer deixar isso explícito no código.

Vale reparar que esse é um caso raro em React: o aviso aparece antes de você perceber o sintoma. Um campo que não aceita digitação tem duas causas possíveis, e a mensagem distingue as duas. Se o console estiver limpo e o campo não aceitar texto, o problema é outro: pode ser CSS (pointer-events: none), pode ser o campo estar coberto por outro elemento, pode ser um disabled esquecido.

Um detalhe que confunde: o valor inicial de um campo controlado não se escreve no input, e sim no useState. Quer que o campo comece com "Balcão"? Escreva useState("Balcão"). Escrever value="Balcão" direto no JSX cria justamente o campo travado desta seção — o estado continua vazio e o campo nunca muda.

8. Quem manda é o estado: limpar com um botão

A prova final de que o estado é o dono do campo: um botão que limpa. A Ana quer um "Limpar" ao lado do nome, para quando o cliente desistir no meio da frase. Nada de procurar o elemento na página e apagar o texto dele — basta mandar o estado ficar vazio.

O botão Limpar não faz nada. Faça ele esvaziar o nome, para o resumo voltar a dizer "Nenhum nome ainda". A missão digita Pão, confere o resumo e depois clica em Limpar.

function App() {
  const [nome, setNome] = useState("Pão de queijo");

  return (
    <div>
      <input value={nome} onChange={(e) => setNome(e.target.value)} />
      <button onClick={() => {}}>Limpar</button>
      <p>{nome ? "Pedido de " + nome : "Nenhum nome ainda"}</p>
    </div>
  );
}
<div>
  <input value="Pão de queijo">
  <button>Limpar</button>
  <p>Pedido de Pão de queijo</p>
</div>

function App() {
  const [nome, setNome] = useState("Pão de queijo");

  return (
    <div>
      <input value={nome} onChange={(e) => setNome(e.target.value)} />
      <button onClick={() => setNome("")}>Limpar</button>
      <p>{nome ? "Pedido de " + nome : "Nenhum nome ainda"}</p>
    </div>
  );
}

O botão não toca no campo. Ele chama setNome(""); o estado fica vazio; o componente roda de novo; o input recebe value="" e se esvazia. Se você fizer o mesmo por fora do estado, escrevendo document.querySelector("input").value = "", a tela esvazia por um instante e o nome volta no próximo render, porque o estado continua com o texto antigo. Esse é o tipo de código que parece funcionar até a página redesenhar por qualquer outro motivo.

O {nome ? "Pedido de " + nome : "Nenhum nome ainda"} mostra outra vantagem do campo controlado: como o estado é sempre uma string, dá para testar se está vazio e trocar a mensagem. Com um campo não controlado, essa decisão só poderia ser tomada no instante do envio, quando o código vai lá ler o elemento.

E se a Ana quisesse que o nome ficasse sempre em maiúsculas enquanto digita? Bastaria setNome(e.target.value.toUpperCase()). O campo mostraria a letra maiúscula no mesmo instante, porque ele reflete o estado transformado. É assim que se fazem máscaras de telefone, de CPF e de moeda: transformando o texto no caminho entre o evento e o estado.

9. Cenários do dia a dia

Cenário 1: as letras saem dobradas

A Ana copiou um exemplo e escreveu setNome(nome + e.target.value). Ao digitar "Maria", o campo passou a mostrar "MMaarriiaa". A razão é que e.target.value já contém o texto inteiro do campo, incluindo a letra nova — somar nome duplica tudo. Em um campo controlado, o onChange recebe o valor completo, nunca só a tecla. A regra é simples: setNome(e.target.value), sem concatenação.

Cenário 2: o botão que limpa só a tela

Para esvaziar o campo, ela escreveu uma função que vai ao DOM e zera o value. O campo esvaziou na hora e, três segundos depois, o nome voltou sozinho — bastou o estado mudar por outro motivo para o React redesenhar e reimpor o valor que ele conhece. Quando a tela discorda do estado, o estado ganha. A correção é uma linha: setNome("").

Cenário 3: o telefone aparece com o nome do cliente

Ao acrescentar o campo de telefone, ela copiou o de nome e esqueceu de trocar o estado: os dois ficaram com value={nome}. Digitando o telefone, o nome mudava junto, e os dois campos mostravam o mesmo texto. Um estado só pode alimentar um campo só; dois campos pedem dois estados. É exatamente o assunto da aula de vários estados.

Complete o campo abaixo para que ele fique controlado pelo estado nome: falta o valor que ele exibe e a função que guarda o que foi digitado. Escreva como se estivesse dentro do JSX.

11. Resumo

Um campo de texto em React tem dois jeitos de existir. Sem value, ele é do navegador: o texto mora dentro do elemento e o componente não fica sabendo de nada. Com value e onChange ligados ao estado, ele é do componente: o campo exibe o estado e avisa cada tecla, e o estado — o único dono do dado — decide o que aparece.

O ciclo é curto e vale decorar: o cliente digita, o React chama a função do onChange com o objeto do evento, você lê e.target.value e entrega ao setNome, o estado muda, o componente roda de novo, o campo recebe o valor novo. O input não guarda nada; ele reflete. Por isso um onChange que grava um valor fixo faz o campo "voltar sozinho", e por isso um botão de limpar se escreve com setNome("") e não com manipulação do DOM.

Duas armadilhas merecem espaço na memória. A primeira: value sem onChange congela o campo e o React avisa no console, sugerindo defaultValue ou readOnly. A segunda: e.target.value é sempre texto; se o dado é número, a conversão é sua responsabilidade. E lembre que o valor inicial de um campo controlado se escreve no useState, não no atributo value.

Com o campo controlado no lugar, o próximo problema da Ana é de quantidade: ela já tem o nome, agora quer o número de pães e o horário de retirada, cada um com o seu próprio estado, sem que um apague o outro. É o assunto da aula seguinte.

Para lembrar

  • Campo controlado = value vindo do estado + onChange devolvendo para o estado.
  • Um dado, um dono: se a tela e o estado guardam o mesmo valor, um dia eles discordam.
  • e é o objeto do evento; e.target é o elemento; e.target.value é o texto.
  • setNome(e.target.value) — nunca setNome(e) nem concatenação.
  • Um onChange que ignora o texto faz o campo voltar sozinho: quem manda é o estado.
  • value sem onChange trava o campo e gera aviso no console.
  • defaultValue é para valor inicial sem controle; readOnly para campo só de leitura.
  • O valor inicial de um campo controlado se escreve no useState.
  • e.target.value é sempre string: converta com Number(...) quando for número.
  • Para limpar: setNome(""). Nada de mexer no DOM na mão.
