O Provider

A Ana copiou o mesmo <ClienteContexto.Provider> em três telas do site, cada uma com a sua cópia do useState do cliente e a sua lista de funções. Quando ela mudou o formato do valor — de texto para objeto —, precisou editar três arquivos e ainda esqueceu um. Nesta aula ela transforma o provider numa peça só dela: um componente chamado ClienteProvider que guarda o estado, publica o canal e recebe o resto da página como children.

Você vai aprender
  • O que um provider faz na árvore e o que ele não faz.
  • Por que o provider mais próximo é o que vale, e como usar isso a favor.
  • Como escrever um provider próprio, com estado e children.
  • Por que o value é comparado por identidade e o que isso custa.
  • Como useMemo segura o objeto do valor entre desenhos.
  • Como empilhar dois providers e por que a ordem entre eles não importa.
  • Onde montar o provider num projeto de verdade.
  • Os tropeços: createContext no lugar errado, valor novo a cada render, provider sem children.

1. A cena: o mesmo provider em três arquivos

O site da Ana tem três telas que precisam saber quem é o cliente: a loja, o carrinho e o acompanhamento do pedido. Em cada uma, o mesmo bloco: um useState para o nome, uma função para entrar, outra para sair, e o <ClienteContexto.Provider value={...}> em volta do conteúdo. Três cópias do mesmo desenho, três lugares para esquecer de atualizar.

O problema não é o contexto — é que o fornecimento não foi extraído. A criação do canal está num arquivo, a leitura está nos componentes, mas o pedaço do meio, que guarda o estado e abastece o canal, ficou solto em cada tela. Extrair esse pedaço num componente é o assunto desta aula, e o resultado é o que a maioria dos projetos chama de ClienteProvider.

Antes de escrever, vale fixar o que um provider é e o que ele não é. Ele é um componente que coloca um valor à disposição de tudo que está abaixo dele, e só disso. Não guarda o valor — quem guarda é o estado de alguém, normalmente o do próprio provider. Não aparece no HTML gerado. Não altera o que os filhos recebem por prop. E não é global: vale só no ramo da árvore em que está montado.

2. O canal, o valor e o escopo

Três nomes se confundem no começo, e separá-los resolve metade das dúvidas. O contexto é o canal, criado uma vez com createContext. O provider é o componente que abastece esse canal com um valor para um pedaço da árvore. O consumidor é quem lê, com useContext. Nesta aula o foco é o do meio.

provider
O componente que publica um valor: <ClienteContexto.Provider value={...}>. Em React 19, o próprio canal também serve: <ClienteContexto value={...}>.
value
O que é publicado. Pode ser texto, número, objeto com dados, objeto com funções. É comparado por identidade, não por conteúdo.
children
O que fica entre as tags do provider. Tudo que está aí dentro pode ler o canal; o que está fora, não.
escopo
A região da árvore coberta por aquele provider. Dois providers do mesmo canal criam dois escopos.
provider próprio
Um componente seu que junta estado, canal e children: ClienteProvider, TemaProvider.
identidade
O que o React compara para decidir se o valor mudou. Objeto novo é valor novo, mesmo com os mesmos campos.

A última linha é a que causa os bugs mais difíceis de achar. O React não olha dentro do objeto para ver se os campos são iguais; ele compara a referência. Um objeto criado no JSX é sempre uma referência nova, e referência nova significa "o valor mudou" para todos os consumidores. Guarde essa frase, porque a quinta seção é sobre ela.

3. O provider mais próximo vence

Dois cartões, dois clientes. O primeiro é da Ana e está dentro de um provider com Ana. O segundo é uma encomenda para a Bruna, e ficou fora do provider: ele recebe o valor padrão do canal, "visitante". A missão é envolver o segundo cartão num provider próprio com Bruna — e aprender que o mais próximo é o que vale.

O cartão do pão de queijo está fora do provider e mostra "visitante". Envolva-o num <ClienteContexto.Provider value={{ cliente: "Bruna" }}> e confira os dois selos.

const ClienteContexto = createContext({ cliente: "visitante" });

function Selo() {
  const { cliente } = useContext(ClienteContexto);
  return <p>Cliente: {cliente}</p>;
}

function Cartao({ titulo }) {
  return (
    <div className="cartao">
      <h2>{titulo}</h2>
      <Selo />
    </div>
  );
}

function App() {
  return (
    <div>
      <ClienteContexto.Provider value={{ cliente: "Ana" }}>
        <Cartao titulo="Baguete" />
      </ClienteContexto.Provider>
      <Cartao titulo="Pão de queijo" />
    </div>
  );
}

Nada mudou no Selo: ele continua lendo o mesmo canal. O que mudou foi qual provider está acima dele. O React não guarda "o valor do contexto" num lugar global — cada provider é uma camada, e o consumidor pega a camada mais próxima. Essa é a mecânica que permite ter duas seções da mesma página com clientes diferentes, ou uma parte da tela em modo escuro sem escurecer o resto.

E se o provider mais próximo não tiver a chave que você procura? Ele não completa com o de cima: o valor publicado é o objeto inteiro, e ponto. Se o provider de cima publica { cliente, entrar } e o de baixo publica só { cliente }, quem lê por baixo recebe só cliente — e entrar fica undefined. Por isso a recomendação é publicar sempre a mesma forma de objeto em todos os providers do mesmo canal.

4. Um provider do seu próprio punho

Agora o ganho de verdade. Em vez de repetir o useState e o .Provider em cada tela, escreva um componente que faz isso uma vez. Ele recebe children, guarda o estado e publica o valor. Quem usa escreve <ClienteProvider> e não sabe que existe um contexto por baixo.

import { createContext, useContext, useState } from "react";

const ClienteContexto = createContext(null);

export function useCliente() {
  const valor = useContext(ClienteContexto);
  if (!valor) throw new Error("useCliente precisa estar dentro de ClienteProvider");
  return valor;
}

export function ClienteProvider({ children }) {
  const [cliente, setCliente] = useState("visitante");

  const valor = {
    cliente,
    entrar: (nome) => setCliente(nome),
    sair: () => setCliente("visitante"),
  };

  return <ClienteContexto.Provider value={valor}>{children}</ClienteContexto.Provider>;
}

Quatro decisões estão embutidas nesse arquivo, e cada uma tem motivo. Primeira: o createContext fica no topo do módulo, fora de qualquer componente, para o canal existir uma vez só. Segunda: o estado mora dentro do provider, e não em quem usa — assim não existe provider sem estado nem estado sem provider. Terceira: as funções entrar e sair vão no mesmo objeto do valor, para quem consome ter tudo num lugar. Quarta: o contexto não é exportado; o que se exporta é o provider e o hook useCliente.

O hook é o detalhe que faz diferença no dia a dia. Sem ele, cada consumidor precisa importar o canal e escrever useContext(ClienteContexto); com ele, escreve useCliente() e pronto. O ganho não é só de digitação: o hook é o lugar onde você documenta o formato do valor e onde decide o que acontece quando alguém usa fora do provider. No exemplo, ele lança um erro com uma mensagem que diz o que fazer — melhor do que um undefined que estoura três componentes adiante.

Em quem usa, a diferença é visível:

import { useCliente } from "./ClienteProvider";

export default function Carrinho() {
  const { cliente, sair } = useCliente();

  return (
    <div>
      <p>Carrinho de {cliente}</p>
      <button onClick={sair}>Sair</button>
    </div>
  );
}

Nenhuma menção a contexto, nenhum useContext, nenhum canal importado. O componente depende de um serviço chamado useCliente. Se um dia o valor deixar de vir de contexto e passar a vir de uma consulta ao servidor, o consumidor não muda — só o provider muda. É a mesma vantagem de esconder o fetch atrás de uma função: quem chama não precisa saber como o dado é obtido.

5. O value é comparado por identidade

O provider publica e o React compara. A comparação é Object.is, ou seja, quase igual a ===: dois objetos com os mesmos campos são diferentes se não forem o mesmo objeto. Isso significa que um value={{ cliente }} escrito no JSX é um valor novo a cada desenho do provider — e todo consumidor é redesenhado junto, mesmo que o cliente seja o mesmo.

Na caixa, o provider tem um segundo estado, o aviso, que não tem nada a ver com o cliente. Um consumidor conta quantas vezes o canal entregou um valor diferente. Clique em "Mostrar aviso": o aviso aparece, e a contagem sobe de um para dois, porque o objeto do valor foi recriado por causa de um estado que nem está nele. A missão é segurar o objeto com useMemo.

O objeto do value é recriado em todo desenho e o consumidor recebe um valor novo à toa. Envolva-o em useMemo(() => ({ cliente, entrar }), [cliente]) e clique em "Mostrar aviso": a contagem tem de ficar em 1.

const ClienteContexto = createContext(null);

function ClienteProvider({ children }) {
  const [cliente, setCliente] = useState("Ana");
  const [aviso, setAviso] = useState(false);

  const valor = { cliente, entrar: (nome) => setCliente(nome) };

  return (
    <ClienteContexto.Provider value={valor}>
      <button id="aviso" onClick={() => setAviso(!aviso)}>Mostrar aviso</button>
      {aviso && <p>Hoje o pão sai quentinho!</p>}
      {children}
    </ClienteContexto.Provider>
  );
}

function ContadorDeLeituras() {
  const valor = useContext(ClienteContexto);
  const [leituras, setLeituras] = useState(0);

  useEffect(() => {
    setLeituras((n) => n + 1);
  }, [valor]);

  return <p>Leituras do canal: {leituras}</p>;
}

function App() {
  return (
    <ClienteProvider>
      <ContadorDeLeituras />
    </ClienteProvider>
  );
}

    <ClienteProvider>
      <ContadorDeLeituras />
    </ClienteProvider>
  );
}

O useMemo aqui faz uma coisa só: guardar o resultado da função enquanto as dependências não mudarem. O objeto é criado no primeiro desenho e reaproveitado nos seguintes; quando cliente muda, o objeto é recriado com o valor novo, e aí sim todos os consumidores são redesenhados — que é exatamente o que deve acontecer. Sem o useMemo, o aviso abrindo e fechando já seria motivo de redesenho geral.

Atenção às dependências: elas listam o que o objeto usa. cliente está lá; entrar é uma função criada dentro do useMemo, então não precisa; setCliente é estável por definição do React. Se o seu valor incluir uma função declarada no corpo do componente, essa função muda em todo desenho e precisa entrar nas dependências — ou ser envolvida em useCallback. Quando o objeto do valor muda com muita frequência, vale considerar dividir o canal em dois: um para os dados, que mudam pouco, e outro para as ações, que não mudam nunca.

6. Providers compõem

Uma tela grande costuma precisar de mais de um canal: cliente, tema, notificações. Nada impede empilhar providers — cada um publica o seu valor, e os consumidores leem de quantos precisarem. A caixa tem o ClienteProvider pronto e um TemaProvider escrito mas não usado; quem lê o tema cai no valor padrão e mostra "sem tema".

Envolva o BotaoTema e o Cartao com <TemaProvider>, por dentro do ClienteProvider. Clique em "Ficar escuro": o cartão tem de mostrar o tema escuro.

const ClienteContexto = createContext({ cliente: "visitante" });
const TemaContexto = createContext({ tema: "sem tema", escurecer: () => {} });

function ClienteProvider({ children }) {
  return (
    <ClienteContexto.Provider value={{ cliente: "Ana" }}>
      {children}
    </ClienteContexto.Provider>
  );
}

function TemaProvider({ children }) {
  const [tema, setTema] = useState("claro");
  return (
    <TemaContexto.Provider value={{ tema, escurecer: () => setTema("escuro") }}>
      {children}
    </TemaContexto.Provider>
  );
}

function BotaoTema() {
  const { escurecer } = useContext(TemaContexto);
  return <button id="escuro" onClick={escurecer}>Ficar escuro</button>;
}

function Cartao() {
  const { cliente } = useContext(ClienteContexto);
  const { tema } = useContext(TemaContexto);
  return <p>{cliente} — tema {tema}</p>;
}

function App() {
  return (
    <ClienteProvider>
      <BotaoTema />
      <Cartao />
    </ClienteProvider>
  );
}

Repare que a ordem entre os dois não importa para o resultado: TemaProvider dentro de ClienteProvider ou o contrário dá o mesmo desenho, porque cada canal é independente. O que importa é que todos os consumidores de um canal estejam dentro do provider daquele canal. O botão precisa do tema para chamar escurecer; o cartão precisa dos dois. Se o botão ficasse fora do TemaProvider, ele leria o padrão e não escureceria nada.

Quando os providers se acumulam, vale extrair um Provedores que junta todos:

export default function Provedores({ children }) {
  return (
    <ClienteProvider>
      <TemaProvider>
        <NotificacoesProvider>{children}</NotificacoesProvider>
      </TemaProvider>
    </ClienteProvider>
  );
}

Quem monta a aplicação envolve tudo uma vez com <Provedores> e as telas não sabem da ordem. É uma conveniência de organização: quando aparecer um quarto canal, ele entra no arquivo e nenhuma tela muda. Só tome cuidado com o que fica dentro do provider: cada nível cria um escopo, e mover um componente para fora sem querer é o tropeço da próxima seção.

7. Onde montar o provider

Num projeto de verdade, o provider fica no ponto mais alto que ainda está sob o seu controle — em geral no arquivo que monta a aplicação, envolvendo o App:

import { createRoot } from "react-dom/client";
import { ClienteProvider } from "./ClienteProvider";
import App from "./App";

createRoot(document.getElementById("raiz")).render(
  <ClienteProvider>
    <App />
  </ClienteProvider>
);

Montar acima do App tem uma consequência boa: o estado do cliente sobrevive à troca de telas, porque o provider não é desmontado quando uma rota muda. Se o provider ficasse dentro de cada página, o valor seria recriado a cada navegação — e o carrinho esvaziaria ao trocar de aba. Nas caixas deste guia o motor monta o App sozinho, então o provider aparece dentro dele; o efeito é o mesmo, o que muda é só quem envolve quem.

Há um limite para subir: nada de colocar no provider o que é de uma tela só. Filtro de busca, aba ativa, página da listagem — esses valores pertencem ao componente que os usa, e promover tudo a canal transforma a aplicação num balcão único onde todo mundo pega tudo. A pergunta é sempre a mesma: esse valor é lido em pontos distantes, por componentes que não compartilham um pai próximo? Se a resposta é não, é prop.

Uma observação sobre o formato: publique sempre um objeto, mesmo quando há um valor só. Objeto permite acrescentar campos sem quebrar as leituras, e combina com o useMemo. Publicar um texto solto (value={cliente}) funciona e é o que a introdução ao contexto mostra; a partir do momento em que existe um provider próprio, o objeto é o formato que envelhece melhor.

8. Os tropeços

O primeiro é criar o canal dentro do componente. const C = createContext(null) dentro da função do provider cria um canal novo a cada desenho; os consumidores passam a olhar para outro canal e caem no valor padrão. O canal é do módulo, não do componente. O segundo é esquecer o {children}: o provider publica o valor e não desenha nada dentro, então a tela some sem erro.

O terceiro é o valor recriado a cada desenho, que a quinta seção mostrou. O sintoma é uma tela que "repinta sem motivo": você mexe num canto e o outro pisca. O quarto é publicar um objeto incompleto num provider aninhado, como já foi dito: o de baixo não herda as chaves do de cima. O quinto é usar o contexto como depósito: nome do cliente, filtro, aba, formulário inteiro. Quanto mais campos no valor, mais consumidores redesenhados e mais difícil saber quem mudou o quê.

Sobre o hook, uma mensagem que vale reconhecer no console do navegador:

Uncaught Error: useCliente precisa estar dentro de ClienteProvider

Ela sai do if (!valor) throw do useCliente e é muito melhor do que a alternativa: sem a checagem, o erro seria Cannot destructure property 'cliente' of 'Object(...)(...)' as it is null — uma mensagem que fala do objeto e não do problema. Se você vir essa mensagem, o componente que chamou o hook está fora do provider: mova o provider para cima ou mova o componente para dentro.

Um último conselho de leitura: quando dois consumidores mostram valores diferentes do mesmo canal, a causa é sempre a mesma — existem dois providers no caminho, ou um deles está fora. Um console.log no provider, antes do return, mostra qual valor cada instância publicou:

ClienteProvider publicou: {"cliente":"Ana"}
ClienteProvider publicou: {"cliente":"Bruna"}

Duas linhas, dois providers. Se o seu caso tem uma linha só e dois comportamentos, o problema não é o provider: é o consumidor estar lendo outro canal.

9. Cenários do dia a dia

Cenário 1: o tema que vale só na vitrine

A vitrine de Natal tem fundo escuro e o resto do site continua claro. A solução não é um estado global de tema: é um <TemaProvider tema="escuro"> em volta apenas da vitrine. Como o provider mais próximo vence, os botões e cartões de dentro ficam escuros e o cabeçalho da loja, que está fora, não muda. No dia seguinte, é só remover o wrapper.

Cenário 2: o provider que também busca dados

O PedidoProvider da Ana guarda o pedido atual, expõe atualizar e cancelar, e usa um useEffect para buscar o pedido quando o número muda. Quem consome continua vendo um objeto com dados e funções, sem saber que existe uma chamada de rede no meio. É a mesma ideia do buscando dados, empacotada num provider: a tela não fica sabendo de detalhes.

Cenário 3: dois canais em vez de um

Quando o valor do canal passou a ter sete campos, a Ana separou: um ClienteProvider para o dado e um AcoesProvider para as funções. As funções não mudam nunca, então os consumidores que só querem adicionar não redesenham quando o nome do cliente muda. Dividir por assunto é a otimização mais barata que existe em contexto, e a mais fácil de explicar para quem chega depois.

Exercício: o provider recebe o resto da página

Complete o provider para que tudo que estiver entre as tags dele seja desenhado dentro do canal:

function ClienteProvider({ }) {
  return <ClienteContexto.Provider value={valor}>{children}</ClienteContexto.Provider>;
}

Dica: é a prop que o React preenche sozinho com o conteúdo entre as tags. Sem ela, o provider publica o valor e não desenha nada.

11. Resumo

Um provider é uma camada: ele publica um valor para tudo que está abaixo dele e nada mais. O mais próximo vence, o objeto publicado não é completado pelo de cima, e o escopo termina onde o provider termina. Extrair o fornecimento num componente seu — ClienteProvider, com estado e children — resolve a duplicação e cria um lugar óbvio para o estado morar.

O detalhe que separa um provider que funciona de um que repinta a página inteira é a identidade do valor. Objeto novo a cada desenho é valor novo para todos os consumidores; useMemo com as dependências certas mantém o objeto estável até que algo relevante mude. E quando o valor fica grande demais, divida o canal por assunto em vez de otimizar o objeto único.

Por fim, o par provider + hook é o que dá acabamento ao padrão: quem consome chama useCliente() e não sabe que existe contexto; o hook documenta o formato, dá a mensagem de erro quando falta o provider e permite trocar a implementação sem tocar nos consumidores. Providers empilham, compõem e se aninham — e a pergunta para decidir se algo merece um deles continua sendo a mesma da introdução ao contexto: esse valor é lido longe, por gente que não tem um pai próximo em comum?

Para lembrar

  • Provider publica; quem lê é o consumidor; o canal é criado uma vez, no módulo.
  • O provider mais próximo vence, e o de baixo não herda chaves do de cima.
  • Provider próprio = estado + .Provider + {children}.
  • Exporte o provider e o hook; mantenha o canal privado.
  • O value é comparado por identidade, não por conteúdo.
  • useMemo segura o objeto; dependências são os campos usados.
  • Empilhe providers por assunto; a ordem entre eles não altera o resultado.
  • Monte o provider acima das telas, para o estado sobreviver à navegação.
