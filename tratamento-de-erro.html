Tratamento de Erro

A mensagem que a Ana colocou na tela era honesta e inútil: "TypeError: Failed to fetch". O cliente não sabia o que era fetch, nem o que fazer com aquilo. Nas aulas anteriores o erro apareceu e ganhou um lugar na tela; agora o assunto é o conteúdo dele. Um erro bem tratado responde três perguntas: o que aconteceu, o que a pessoa pode fazer e onde está o detalhe técnico para quem for consertar. Nesta aula a Ana aprende a separar essas três coisas — e a não cometer o pecado silencioso de engolir o erro.

Você vai aprender
  • As famílias de falha e como reconhecer cada uma.
  • Por que alguns erros nunca chegam no catch.
  • O perigo do catch vazio, que transforma falha em "nada encontrado".
  • A mensagem humana e o detalhe técnico no mesmo lugar.
  • Retentativa com limite, em vez de tentar para sempre.
  • O que registrar no console e o que nunca mostrar.

1. A cena: o erro que fala grego

O cliente digitou "brioche", o servidor não respondeu e a tela mostrou a mensagem crua do navegador. Tecnicamente correta, praticamente inútil: ninguém sabe o que fazer com um nome de tipo em inglês. A Ana percebeu que o erro tinha três públicos ao mesmo tempo — quem usa o site, quem dá suporte e quem programa — e que cada um precisava de uma informação diferente.

Quem usa quer saber se foi culpa dele e se vale tentar de novo. Quem dá suporte quer um jeito de identificar o problema sem abrir o código. Quem programa quer a mensagem original, com o máximo de detalhe, no console e nos registros. Uma tela que mostra só o primeiro caso é confusa; uma que mostra só o terceiro é hostil.

Tratar erro, então, é traduzir sem perder o original. É isso que separa "deu erro" de "não consegui falar com a padaria; verifique sua conexão e tente de novo" — com a mensagem técnica guardada num canto, disponível para quem precisa.

2. O que chega no catch

O catch recebe uma coisa só, e essa coisa pode ser de vários tipos. Na maioria dos casos é um objeto Error, com duas propriedades que interessam: name, que diz a família, e message, que diz o detalhe. Alguns erros carregam mais: o status de uma resposta HTTP, por exemplo, se você anexar.

> const e = new Error("Falha de rede")
undefined
> e.message
'Falha de rede'
> e.name
'Error'
> e instanceof Error
true

Duas armadilhas moram aqui. A primeira: nem tudo que é lançado é um Error — dá para lançar texto (throw "deu ruim"), e aí e.message é undefined. A segunda: a mensagem pode vir vazia, e uma tarja vermelha em branco é pior que nenhuma. Por isso o código de tratamento costuma normalizar antes de usar:

function textoDoErro(e) {
  if (e instanceof Error) return e.message || e.name;
  return String(e);
}
Error
O tipo base dos erros do JavaScript. Tem name, message e stack.
name
A família: "Error", "TypeError", "SyntaxError", "AbortError", "TimeoutError".
message
O detalhe, em texto. Boa para o console e para o suporte; ruim para a tela do cliente.
cause
O erro original, quando você embrulha um erro em outro para dar contexto.
throw
Lançar um erro. Interrompe o fluxo e leva o controle para o catch mais próximo.
error boundary
Componente especial que captura erros de render. Sem ele, um erro de render derruba a árvore.

3. As famílias de falha

Nem todo erro quer dizer a mesma coisa, e a mensagem certa depende da família. Uma tabela resolve a maioria dos casos que aparecem em tela que busca dados.

Repare que a coluna do meio é técnica e a da direita é humana. O trabalho do tratamento é exatamente essa tradução — e ela nunca deve apagar o original. O console continua sendo o lugar do detalhe, e o console.error é o instrumento: ele aparece em vermelho, com a pilha de chamadas, e é o que alguém vai procurar quando o suporte abrir o caso.

4. Os erros que não passam pelo catch

Existe uma família que nunca chega no catch e engana muita gente: a resposta HTTP de erro. Um 404 ou um 500 não rejeita a promessa do fetch; a resposta chega normalmente, e quem decide que aquilo é falha é o seu código, olhando resposta.ok. Se você esquecer essa conferência, nenhum try/catch vai ajudar.

Como o fetch não faz isso por você, o costume é transformar a resposta ruim em erro lançado, logo depois do primeiro await: um if (!resposta.ok) throw new Error("Status " + resposta.status). A partir dali, 404 passa a cair no mesmo catch dos outros problemas, e o tratamento fica em um lugar só. É a ponte entre as duas famílias.

O outro caso é o erro de render. Se o componente quebra durante o desenho — um undefined.map, por exemplo —, o catch do efeito não vê nada: o erro acontece depois, na hora de desenhar. Quem captura isso é um error boundary, um componente especial que existe justamente para mostrar uma tela de reserva quando a árvore quebra. É assunto para outra aula, mas vale saber que a fronteira existe, porque o sintoma — tela vazia sem mensagem — costuma ser confundido com erro de dados.

E há o erro silencioso por excelência, que é o assunto da próxima seção: o catch que existe, roda, e não faz nada com a informação.

5. O catch que engole

Engolir um erro é fácil de escrever e difícil de descobrir. O código abaixo faz o pedido, o pedido falha, o catch limpa a lista — e a tela mostra "Nenhum pão por hoje". Para o cliente, a padaria não tem pão; para o programador, está tudo certo, porque não há erro no console. É o pior dos dois mundos.

O pedido falhou, o catch limpou a lista e a tela diz que não há pão. Use o estado erro: no catch, mostre "Não consegui carregar o cardápio" e esconda a mensagem de lista vazia.

function buscarCardapio() {
  return new Promise((ok, falha) => {
    setTimeout(() => falha(new Error("Falha de rede")), 10);
  });
}

function App() {
  const [lista, setLista] = useState([]);
  const [erro, setErro] = useState("");

  useEffect(() => {
    buscarCardapio()
      .then((dados) => setLista(dados))
      .catch((e) => {
        setLista([]);
      });
  }, []);

  return (
    <div>
      <h1>Cardápio</h1>
      {erro && <p className="falha">{erro}</p>}
      {!erro && lista.length === 0 && <p>Nenhum pão por hoje</p>}
      <ul>
        {lista.map((p) => (
          <li key={p}>{p}</li>
        ))}
      </ul>
    </div>
  );
}

A correção tem duas partes, e as duas importam. A primeira é dizer que falhou: o estado erro deixa de ser decorativo e passa a ser preenchido. A segunda é não mostrar "Nenhum pão por hoje" quando houve falha — a condição !erro faz isso. Sem a segunda, a tela mostraria as duas mensagens ao mesmo tempo, dizendo "não consegui carregar" e "não há pão" na mesma respiração.

Um detalhe que parece firula e não é: a variável e do catch não é usada na solução. Isso é aceitável quando o erro é sempre o mesmo e o registro fica no console. Mas o hábito saudável é nunca descartar sem olhar — um console.error(e) antes da mensagem amigável guarda o detalhe para quem for investigar, sem poluir a tela de quem está comprando pão.

6. Mensagem humana e detalhe técnico

A solução completa mostra as duas camadas. Em cima, uma frase que qualquer pessoa entende e que sugere o que fazer. Embaixo, um bloco recolhido com a mensagem original, para quem precisa copiar e mandar no suporte. O elemento details do HTML faz isso sem uma linha de JavaScript: fechado por padrão, abre no clique.

A tela mostra a mensagem crua do erro. Troque por "Não deu para falar com a padaria" e coloque a mensagem original dentro de um <details>, com um <summary>.

function buscarHorario() {
  return new Promise((ok, falha) => {
    setTimeout(() => falha(new Error("Falha de rede")), 10);
  });
}

function App() {
  const [erro, setErro] = useState("");

  useEffect(() => {
    buscarHorario()
      .then((h) => setErro(""))
      .catch((e) => setErro(e.message));
  }, []);

  return (
    <div>
      <h1>Horário</h1>
      {erro && <p className="falha">{erro}</p>}
    </div>
  );
}

E o texto técnico não desaparece, o que também serve para você: quando o erro chega por foto no WhatsApp, a foto tem a informação que importa.

O que nunca serve: mostrar a pilha de chamadas inteira na cara do cliente, culpar o usuário ("você digitou errado") ou prometer algo que você não sabe ("já estamos consertando"). A mensagem certa descreve o que falhou, sem julgar ninguém, e oferece um próximo passo concreto.

7. Tentar de novo, com limite

Rede instável melhora sozinha em segundos, então tentar de novo é uma boa ideia. Tentar para sempre, não. Sem limite, um servidor fora do ar recebe pedidos sem parar, o navegador fica ocupado e a tela nunca sai do "tentando". O limite é o que separa insistência de teimosia.

O componente tenta de novo sem parar. Limite a três tentativas e, na terceira falha, mostre "Desisti depois de 3 tentativas".

function buscar() {
  return new Promise((ok, falha) => {
    setTimeout(() => falha(new Error("Falha de rede")), 1);
  });
}

function App() {
  const [tentativa, setTentativa] = useState(1);
  const [recado, setRecado] = useState("Tentando de novo...");

  useEffect(() => {
    buscar()
      .then(() => setRecado("Pronto"))
      .catch(() => {
        setTentativa(tentativa + 1);
        setRecado("Tentando de novo...");
      });
  }, [tentativa]);

  return (
    <div>
      <h1>Horário</h1>
      <p>{recado}</p>
    </div>
  );
}

    </div>
  );
}

Quando ninguém trata, o navegador conta a história sozinho — e é essa a mensagem que o cliente acaba vendo se você deixar o erro escapar:

Uncaught (in promise) TypeError: Failed to fetch
    at buscarHorario (App.jsx:9:9)

Três detalhes fazem a diferença nesse padrão. Primeiro, o contador é estado, porque precisa sobreviver entre tentativas. Segundo, a condição vem antes do incremento, senão o componente tenta uma vez a mais do que você queria. Terceiro, a mensagem final diz o que aconteceu e sugere o caminho — "desisti depois de 3 tentativas" é honesto, e fica melhor ainda acompanhada de um botão "tentar de novo" que zera o contador.

Em código de produção, vale espaçar as tentativas: 200 milissegundos, depois 400, depois 800. O nome disso é backoff, e a razão é simples: se o servidor está sobrecarregado, insistir na mesma velocidade só piora. O espaçamento dá tempo para o outro lado respirar.

Vale uma distinção que evita código confuso: retentar é diferente de reenviar. Retentar é perguntar de novo, o que é seguro em leitura. Reenviar é repetir uma ação que talvez tenha acontecido — criar o pedido duas vezes, cobrar duas vezes. Para escrita, tentar de novo exige uma proteção do lado do servidor, um identificador único por envio, que a aula de POST discute. Na dúvida, em escrita, prefira mostrar o erro e deixar a pessoa decidir.

8. Registrar sem vazar

O console.error é o lugar do detalhe, mas ele não é privado: em produção, ferramentas de monitoramento recolhem esses registros, e qualquer pessoa com o console aberto vê o que está lá. Nunca registre o que não pode circular — senha, token de cartão, endereço completo com telefone, dado de saúde. Registre o identificador do pedido, o status e a mensagem; o resto não.

Quando o erro original não diz o suficiente, você pode embrulhar em outro com contexto e guardar o primeiro em cause. O novo erro aparece com a sua mensagem, e o original continua acessível para quem for investigar — o melhor dos dois mundos.

try {
  await enviarPedido(pedido);
} catch (e) {
  const erro = new Error("Não consegui enviar o pedido " + pedido.id);
  erro.cause = e;
  console.error(erro);
  setFalha("Não conseguimos enviar seu pedido. Tente de novo.");
}

Uma última armadilha, e é de sintaxe: catch (e) { } com as chaves vazias não gera aviso nenhum. O código compila, roda, e o erro desaparece em silêncio. Se a intenção é ignorar de propósito, vale escrever o motivo em um comentário — o próximo a ler o código, muitas vezes você mesmo em três meses, vai agradecer.

9. Cenários do dia a dia

Cenário 1: "não há pão" quando havia

O servidor caiu por dez minutos e a tela dizia "Nenhum pão por hoje". Nenhum cliente reclamou, porque todos acreditaram. O catch limpava a lista e seguia como se a resposta tivesse sido vazia. O conserto foi separar os dois casos — lista vazia é resposta legítima, falha é falha — e mostrar mensagens diferentes. Erro engolido é mentira contada com boa intenção.

Cenário 2: a retentativa que virou ataque

Ela colocou uma retentativa automática e testou com a rede boa: funcionou. No dia em que o servidor ficou fora, o site passou a martelar o endereço a cada 100 milissegundos, de cada cliente aberto, e o servidor só piorou. A correção foi limite de três tentativas com espaçamento crescente. Insistir é útil quando o problema é passageiro; com o servidor no chão, é combustível.

Cenário 3: o token no console

Um erro de envio registrava o objeto do pedido inteiro, com o cartão dentro. Durante uma semana, cada falha deixou o número do cartão em um log que outras pessoas acessavam. Depois do susto, o registro passou a levar só o identificador e o status. A regra é fácil de lembrar se você pensar no log como um lugar público: se não pode ser lido por qualquer um, não vai para lá.

11. Resumo

O catch recebe o erro, e quase sempre é um Error com name e message. Nem toda falha passa por ali: resposta 404 ou 500 chega como sucesso e depende de resposta.ok; erro de render é assunto de error boundary. E o pior tratamento é o catch que engole — ele transforma falha em "nada encontrado" e ninguém fica sabendo.

Uma tela boa mostra duas camadas: a frase humana, que diz o que aconteceu e o que fazer, e o detalhe técnico recolhido num <details>. O registro completo vai para o console.error, sem senha, sem token, sem dado pessoal. Retentativa é bem-vinda com limite e com espaçamento crescente; sem limite, ela vira parte do problema.

Na próxima aula o outro lado da rede: enviar dados com POST, com corpo em JSON, cabeçalho certo e o cuidado de não mandar o mesmo pedido duas vezes.

Para lembrar

  • name diz a família; message diz o detalhe.
  • 404 e 500 não vão para o catch: confira resposta.ok.
  • catch vazio esconde a falha e mente para o usuário.
  • Frase humana em cima, detalhe técnico no <details>.
  • console.error para o detalhe; nunca dado sensível.
  • Retentativa com limite e com backoff.
  • Lista vazia e falha são casos diferentes.
  • Embrulhe com cause para não perder o erro original.
