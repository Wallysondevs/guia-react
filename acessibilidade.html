Acessibilidade

Uma cliente da padaria não usa mouse. Ela navega com Tab e Enter, e o leitor de tela anuncia cada coisa que aparece. No site da Ana, o botão de encomendar é uma div com onClick: para o leitor de tela, aquilo não é botão nenhum, e o Tab passa direto. Nesta aula ela aprende o que faz uma tela ser navegável por teclado e por leitor de tela — quase sempre com HTML comum, e não com atributos exóticos.

Você vai aprender
  • O que é nome acessível e por que ele decide se um elemento existe para o leitor de tela.
  • Como o papel de cada elemento vem do HTML, não do CSS.
  • Como descrever imagens e quando deixar a descrição vazia.
  • Por que uma div com onClick não é um botão.
  • Como ligar rótulo, dica e mensagem de erro a um campo.
  • Como anunciar mudanças sem roubar o foco com role="status".
  • Um checklist que roda no console para conferir o básico.

1. A cena: a cliente que chega pelo teclado

A Ana ficou sabendo do problema pelo balcão. A cliente entrou no site, apertou Tab e o foco pulou do menu para um link do rodapé, sem parar em nenhum dos cartões. Apertou Enter no cartão e nada aconteceu. Pediu ajuda à sobrinha, que abriu o site no notebook e mostrou: o “botão” de encomendar era uma div com um onClick — invisível para o teclado e sem nome para o leitor de tela.

O susto da Ana foi descobrir quanto custa um elemento errado. Aquela div não recebe foco, não responde a Enter nem a espaço, não é anunciada como botão e não tem estado de “apertado”. Para consertar, ela não precisou de biblioteca nem de atributo novo: precisou trocar div por button. O navegador entregou foco, teclado, papel e anúncio de graça.

O curioso é que o site dela já tinha passado por um teste de acessibilidade de formulário: os campos tinham rótulo, as mensagens de erro apareciam no lugar certo. O que faltava era o que não é formulário — a navegação, as imagens, os cartões. A aula de Formulário Acessível cobre o campo por campo; esta aqui olha a tela inteira.

Essa é a ideia que atravessa a aula inteira: acessibilidade em React é, na maior parte, escrever HTML direito. O React não inventa regras — ele desenha os elementos que você pediu. Quando você pede div, recebe uma div, com todas as limitações dela.

2. Nome, papel e foco

Três conceitos explicam quase todos os problemas que aparecem. O papel diz o que o elemento é: botão, link, campo, título. O nome acessível diz como ele se chama: é o texto que o leitor de tela fala. O foco diz por onde o teclado passa: sem foco, não há interação.

nome acessível
O texto que o leitor de tela anuncia para um elemento. Vem do conteúdo, de um label, de um alt ou de um aria-label.
papel
O que o elemento é para a tecnologia assistiva. button tem papel de botão; uma div tem papel nenhum.
foco
O elemento que recebe o teclado naquele momento. Só elementos interativos entram na fila do Tab.
leitor de tela
O programa que fala a página em voz alta. Ele lê o nome e o papel, e ignora o que não tem nenhum dos dois.
aria-live
Uma região que o leitor de tela observa. Quando o texto muda, ele anuncia sem tirar o foco de onde a pessoa está.
HTML semântico
Usar o elemento que já significa aquilo: button para ação, a para navegação, nav, main, header.

O React ajuda em uma coisa e atrapalha em outra. Ajuda porque o JSX é praticamente HTML: o que você escreve é o que vai para a página. Atrapalha porque é fácil montar um componente com div e onClick e achar que aquilo é um botão — funciona no mouse, então parece certo. O teclado é o teste que revela a diferença.

A primeira conferência é sempre a mesma: clique na página, aperte Tab e veja se o foco chega onde deveria. Se não chega, o elemento não é interativo para o teclado, por mais que o mouse funcione. Se chega mas o leitor de tela não fala nada, falta nome. São dois testes diferentes, e os dois precisam passar.

3. A caixa: a imagem precisa de descrição

Imagem é o caso mais simples e o mais esquecido. Na caixa abaixo, a foto do pão não tem descrição. A prévia não carrega a imagem — a caixa não tem arquivos —, então você vê exatamente o que aparece quando a foto falha: nada. Com o alt, aparece o texto; e é esse mesmo texto que o leitor de tela fala sempre.

Descreva a foto para quem não vê: acrescente alt="Pão de queijo saindo do forno" à imagem e clique em Rodar.

function App() {
  return (
    <figure>
      <img src="pao.jpg" width="120" />
      <figcaption>Pão de queijo</figcaption>
    </figure>
  );
}
<figure>
  <img width="120" src="pao.jpg">
  <figcaption>Pão de queijo</figcaption>
</figure>

function App() {
  return (
    <figure>
      <img src="pao.jpg" width="120" alt="Pão de queijo saindo do forno" />
      <figcaption>Pão de queijo</figcaption>
    </figure>
  );
}

Repare que a imagem já tinha uma legenda embaixo. Legenda e descrição não são a mesma coisa: a legenda é conteúdo visível para todo mundo; o alt é o substituto da imagem para quem não a vê. Em uma figura com legenda, o alt pode ser curto — “Pão de queijo” — porque o resto da informação está ali do lado. Em uma foto que carrega informação (um gráfico, um mapa), o alt precisa dizer o que a imagem mostra.

E existe o caso opcional: imagem que é só enfeite. Aí o certo é alt="", vazio. Isso diz ao leitor de tela “pule isto, não é conteúdo”. Esquecer o atributo é diferente de deixá-lo vazio: esquecer faz o leitor tentar anunciar o nome do arquivo, o que é pior do que não falar nada.

4. A caixa: uma div não é um botão

Agora o caso que a cliente encontrou. A caixa tem um “botão” feito de div com onClick. No mouse, funciona. No teclado, não existe: a div não entra na fila do Tab, e o clique do verificador nem encontra um button para apertar.

Troque a div com className="botao" por um <button> de verdade, mantendo o onClick e o texto. Depois clique em Encomendar.

function App() {
  const [encomendado, setEncomendado] = useState(false);
  return (
    <div>
      <div className="botao" onClick={function () { setEncomendado(true); }}>Encomendar</div>
      <p>{encomendado ? "Encomendado" : "Nada ainda"}</p>
    </div>
  );
}
<div>
  <div class="botao">Encomendar</div>
  <p>Nada ainda</p>
</div>

function App() {
  const [encomendado, setEncomendado] = useState(false);
  return (
    <div>
      <button onClick={function () { setEncomendado(true); }}>Encomendar</button>
      <p>{encomendado ? "Encomendado" : "Nada ainda"}</p>
    </div>
  );
}

O painel mostra a diferença em uma linha: antes havia um div com classe, agora há um button com o texto dentro. Esse texto é o nome acessível — o leitor de tela anuncia “Encomendar, botão”. O button também responde a Enter e a espaço, recebe foco no Tab, mostra o contorno de foco e entra na lista de controles do formulário, se estiver dentro de um.

Um cuidado com o estado desabilitado. Um button com disabled não recebe foco, então quem navega por teclado pode passar por ele sem saber que existe. Quando a ação está indisponível por um motivo que a pessoa precisa entender, prefira aria-disabled="true" com um clique que não faz nada, ou explique o motivo num texto ao lado. Desabilitar sem explicação é o equivalente visual de uma porta sem maçaneta.

Se o desenho precisa ser outro — um cartão inteiro clicável, por exemplo —, a solução não é div com onClick: é button com CSS que o deixe com a cara do cartão. Nunca o contrário. Um div com role="button" e tabIndex={0} até funciona, mas você passa a ter de reimplementar Enter, espaço, foco e estados — e é quase certo que algum deles vai faltar. Use o elemento pronto.

5. A caixa: rótulo ligado e aviso anunciado

Campo de formulário tem dois nomes em jogo: o que está escrito ao lado e o que o leitor de tela associa ao campo. Um label solto, sem for, não associa nada: quem vê lê “Busca” e o campo; quem usa leitor de tela ouve só “campo de edição”, sem saber de quê.

Ligue o rótulo ao campo com htmlFor="busca" e id="busca", e faça o aviso ser anunciado quando mudar, com role="status".

function App() {
  return (
    <div>
      <label>Busca</label>
      <input name="busca" />
      <p className="aviso">3 pães encontrados</p>
    </div>
  );
}
<div>
  <label>Busca</label>
  <input name="busca">
  <p class="aviso">3 pães encontrados</p>
</div>

function App() {
  return (
    <div>
      <label htmlFor="busca">Busca</label>
      <input id="busca" name="busca" />
      <p className="aviso" role="status">3 pães encontrados</p>
    </div>
  );
}

O par for e id é a ligação: o rótulo aponta para o campo pelo identificador. Em JSX, porém, o atributo se escreve htmlFor, porque for é palavra reservada do JavaScript. O React traduz htmlFor para for no HTML — e é por isso que o painel mostra for="busca" depois de você escrever htmlFor. A aula de O useId mostra como gerar esse id sem repetir em cópias do mesmo campo.

O role="status" é a segunda metade. Ele transforma o parágrafo numa região viva: quando o texto muda, o leitor de tela anuncia o novo conteúdo sem tirar o foco do campo onde a pessoa está digitando. É o que faz a busca avisar “3 pães encontrados” sem interromper a digitação. O aria-live="polite" faz o mesmo e é ainda mais explícito; o role="status" já implica polite.

6. O elemento certo para cada coisa

Metade da acessibilidade de uma tela é escolher o elemento certo. O navegador já sabe se comportar como botão, link, título e lista — desde que você peça. Esta tabela é a cola mais útil da aula.

O que éElementoO que vem de graça
ação que muda a telabuttonfoco, Enter, espaço, papel de botão
navegação para outra páginaa hreffoco, Enter, “link” anunciado, menu de contexto
título de seçãoh2, h3navegação por títulos no leitor de tela
área principalmainatalho para pular direto ao conteúdo
grupo de linksnav“navegação” anunciada, com nome pelo aria-label
imagem com conteúdoimg altdescrição falada no lugar da imagem

Repare na primeira linha contra a segunda. Botão faz algo nesta página; link leva para outro endereço. Trocar os dois é um dos erros mais comuns: um a com onClick e href="#" parece botão, mas o leitor de tela anuncia “link” e a pessoa pode tentar abrir em outra aba. Se a ação não navega, é button.

Já os títulos merecem um cuidado silencioso: use h2 para as seções e h3 para as subseções, sem pular de h1 para h4 só porque o h4 é menor. O tamanho é CSS; a hierarquia é informação. Muita gente navega por títulos — no leitor de tela, é o equivalente a olhar o sumário de um livro.

Outro comando útil lista os elementos que o Tab alcança, na ordem em que ele vai passar. É a melhor forma de descobrir um “botão” que não é botão — ele simplesmente não aparece na lista:

document.querySelectorAll("a[href], button, input, select, textarea")
  .forEach(function (el) { console.log(el.tagName + ": " + (el.textContent || el.name)); });

Na página da padaria, com o menu, o campo de busca e o botão de encomendar, o resultado é curto e revelador:

A: Início
A: Pães
A: Contato
INPUT: busca
BUTTON: Encomendar

Cinco elementos, na ordem do documento. Se o cartão clicável não está nessa lista, ele não é alcançável pelo teclado — e não há CSS que resolva isso. A lista também mostra a ordem: se o Tab pula do rodapé para o topo, o problema está no HTML, não no CSS.

7. O que atrapalha

Existe um conjunto de boas intenções que piora a vida de quem usa tecnologia assistiva. Vale conhecer para não repetir.

O que se vê no códigoPor que atrapalhaO que fazer
div com onClicknão recebe foco nem responde ao tecladobutton
aria-label numa div sem papelo leitor ignora o nomeusar o elemento certo, ou role="img"
placeholder como único rótulosome ao digitar e não é lido como nomelabel de verdade
tabIndex="5"quebra a ordem natural do Tabdeixar a ordem do HTML; usar 0 só quando precisar
ícone “×” sem textoo leitor fala “multiplicação” ou nadaaria-label="Fechar" no botão
erro só com cor vermelhaquem não distingue cor não vê o errotexto e ícone além da cor

O tabIndex positivo é o mais tentador e o mais perigoso. Ele tira o elemento da ordem do documento e o coloca numa fila paralela, que ninguém consegue prever depois de algumas telas. A ordem natural do HTML — de cima para baixo, da esquerda para a direita — quase sempre é a ordem certa. Quando não é, o problema costuma estar no layout, não no tabIndex.

Outro clássico é apagar o contorno de foco no CSS. Aquele anel azul em volta do botão é a única pista de onde o teclado está; removê-lo porque “fica feio” deixa a pessoa sem saber o que vai acontecer quando apertar Enter. Se o anel não combina com o desenho, troque por outro visível — nunca por outline: none sem substituto.

Já o ícone sem nome é o caso mais frequente em componente. Um botão com “×” dentro tem nome acessível “×”, que o leitor fala como “multiplicação” ou “vezes”. O conserto é dar nome ao botão, não ao ícone: <button aria-label="Fechar">×</button>. O aria-label substitui o conteúdo como nome — e é por isso que ele não serve para decorar uma div qualquer.

8. Um checklist no console

Não é preciso esperar o teste com leitor de tela para achar o básico. Um trecho de JavaScript no console do navegador responde três perguntas rápidas: toda imagem tem descrição, todo campo tem rótulo, todo aviso é uma região viva.

var semAlt = document.querySelectorAll("img:not([alt])").length;
var semRotulo = document.querySelectorAll("input:not([id])").length;
var avisos = document.querySelectorAll("[role=status]").length;
console.log("imagens sem alt: " + semAlt);
console.log("campos sem id: " + semRotulo);
console.log("regiões de aviso: " + avisos);

Rodando na página já consertada, o resultado é este:

imagens sem alt: 0
campos sem id: 0
regiões de aviso: 1

Não é um teste completo — uma imagem com alt="imagem" passa e continua inútil. Mas é um filtro barato que pega o que costuma escapar, e roda em qualquer página, inclusive nas que você não escreveu. O complemento é o teste manual: Tab do começo ao fim, Enter em cada botão, e um leitor de tela de verdade se você tiver acesso. Cinco minutos de Tab encontram mais problemas do que uma hora de leitura de código.

9. Cenários do dia a dia

Cenário 1: o cartão que só abria no mouse

O cartão de pão inteiro era clicável, feito de div com onClick. A cliente que navega por teclado não conseguia abrir nenhum. A correção foi colocar um button dentro do cartão, com o nome do pão no texto, e deixar o cartão como moldura. Quem usa mouse continua clicando no botão; quem usa teclado encontra o foco.

Cenário 2: o aviso que ninguém ouvia

A busca mostrava “nenhum pão encontrado” num parágrafo comum. Quem enxerga via a mensagem; quem usa leitor de tela continuava ouvindo o campo vazio, sem saber que a busca tinha terminado. O role="status" resolveu na hora, e a mensagem passou a ser anunciada sem tirar o foco do campo.

Cenário 3: o ícone que virava “multiplicação”

O botão de fechar o carrinho tinha só um “×” dentro. O leitor de tela anunciava “multiplicação, botão”. O conserto foi aria-label="Fechar o carrinho", e o texto do rótulo passou a dizer o que acontece — não só o desenho. Nome acessível bom é nome que explica a ação.

Exercício: dê nome ao botão de fechar

O botão mostra só um “×” e o leitor de tela não sabe o que ele faz. Complete o atributo que dá nome à ação.

<button >×</button>

Dica: é o atributo que substitui o conteúdo como nome acessível. O valor deve dizer a ação — “Fechar” — e não o desenho.

11. Resumo

Acessibilidade começa no elemento certo. button para ação, a para navegação, label ligado ao campo por htmlFor e id, img com alt descrevendo o que importa, títulos em hierarquia. O navegador entrega foco, teclado e papel de graça; a div não entrega nada.

O nome acessível é o que o leitor de tela fala. Ele vem do texto do elemento, do label, do alt ou de um aria-label — que só funciona quando o elemento tem papel. E regiões vivas, como role="status", avisam mudanças sem roubar o foco de quem está digitando.

Para conferir, dois testes: Tab até o fim, apertando Enter em tudo; e o checklist de três linhas no console. O primeiro encontra o que não recebe foco, o segundo encontra o que não tem nome. Na próxima aula o assunto é o outro lado da qualidade: os erros que se repetem em todo projeto React e como reconhecê-los rápido, em Erros Comuns.

Para lembrar

  • Papel vem do HTML; div com onClick não é botão.
  • Nome acessível: texto do elemento, label, alt ou aria-label.
  • Imagem com conteúdo: alt descritivo. Enfeite: alt="".
  • label + htmlFor + id ligam rótulo e campo.
  • Em JSX, o atributo é htmlFor; o HTML final mostra for.
  • role="status" anuncia mudanças sem tirar o foco.
  • Botão de ícone precisa de aria-label com a ação.
  • Não use tabIndex positivo: quebra a ordem natural.
  • Placeholder não substitui rótulo.
  • Teste com Tab e com o checklist no console antes de dizer que está pronto.
