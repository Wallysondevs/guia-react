Elevando o Estado

O carrinho do site da Ana mostra "0 itens" no topo enquanto os dois botões de adicionar contam pão e salgado cada um por si. É o retrato de um problema clássico: o dado que a tela inteira precisa está guardado dentro de um pedaço da tela, e os outros pedaços não têm como vê-lo. Nesta aula a Ana aprende a elevar o estado — mudar o useState de lugar, para o pai comum dos componentes que precisam do mesmo dado — e a manter o fluxo nos dois sentidos: dados descem por props, avisos sobem por funções.

Você vai aprender
  • Como descobrir onde um estado deve morar, a partir de quem o usa.
  • O que muda no filho quando o estado sobe: ele passa a receber valor e a avisar o pai.
  • Como escrever uma prop de callback e por que ela se chama onAlgo.
  • Dois controles diferentes editando o mesmo dado, sem cópias.
  • Quando não elevar: o custo de subir o estado cedo demais.
  • O que se perde quando um componente muda de lugar na árvore.
  • Os tropeços: cópia esquecida no filho, callback recriada, estado derivado guardado à toa.

1. A cena: o carrinho que mostra zero

O carrinho da padaria tem três pedaços: o cabeçalho que conta os itens, a lista de pães e a lista de salgados. Cada lista guarda a própria lista de itens, porque cada uma foi escrita no seu dia e resolveu o problema sozinha. O cabeçalho, coitado, não tem estado nenhum: exibe zero e vai continuar exibindo zero.

O erro não é de digitação, é de lugar. O cabeçalho precisa saber quantos itens existem nas duas listas, e a informação está trancada dentro de cada uma. Não há prop que resolva isso de baixo para cima: em React, os dados descem a árvore, nunca sobem sozinhos. Quem precisa ver os dois lados tem de ser um ancestral dos dois — e é aí que o estado muda de endereço.

Elevar o estado é exatamente isso: pegar o useState que estava no componente que usa e colocá-lo no menor componente que é pai de todos os que precisam do dado. O resto é consequência. O filho que antes mandava em si mesmo passa a receber o valor por prop e a pedir mudanças por uma função que o pai entrega. A tela continua igual; o comando mudou de mãos.

2. Onde o estado deve morar

A pergunta que resolve quase todos os casos é: quem precisa ver esse valor? Se é só o próprio componente, o estado fica nele. Se são dois irmãos, sobe para o pai dos dois. Se são primos distantes, sobe para o avô comum — e aí vale considerar contexto, que é outra aula. O que não funciona é deixar o valor num lugar e pedir que outro lugar o veja por mágica.

elevar
Mover o useState do componente que usa o valor para o menor ancestral comum de todos os que precisam dele.
pai comum
O componente mais próximo que está acima de todos os interessados. É o novo dono do estado.
prop de dado
O valor descendo: <Aviso escuro={escuro} />. Somente leitura, como toda prop.
prop de callback
A função que sobe o aviso: onAlternar={...}. O filho chama, o pai decide o que fazer.
dono
O componente que tem o useState. Só ele chama o set; os outros pedem.
fonte única
Um dado, um lugar. Se duas cópias do mesmo valor existem na tela, uma delas vai ficar velha.

Repare que elevar não é "deixar tudo no topo". O pai comum de dois irmãos é o pai deles, não o App; e se só um componente usa o valor, o pai dele é um lugar desnecessário. O critério é o alcance da informação, não o tamanho do arquivo. Estado no lugar certo é o que faz um componente ser reutilizável: um CampoDeBusca que guarda o próprio texto pode ser usado em dez telas; um que depende do estado da página só funciona naquela página.

3. Subir o estado: um interruptor e um aviso

O primeiro caso é pequeno e mostra o desenho inteiro. Um botão alterna o tema, e um parágrafo mostra qual é o tema atual. Hoje o estado mora no botão: ele sabe se está escuro, mas o parágrafo não. O código inicial mostra "Tema: claro" para sempre, mesmo que você clique e veja o botão mudando por dentro.

Leve o estado escuro para o App, passe escuro para o Aviso e uma função onAlternar para o BotaoTema chamar. Clique em "Alternar tema".

function BotaoTema() {
  const [escuro, setEscuro] = useState(false);
  return <button onClick={() => setEscuro(!escuro)}>Alternar tema</button>;
}

function Aviso() {
  return <p>Tema: claro</p>;
}

function App() {
  return (
    <div>
      <BotaoTema />
      <Aviso />
    </div>
  );
}
<div>
  <button>Alternar tema</button>
  <p>Tema: claro</p>
</div>

function BotaoTema({ onAlternar }) {
  return <button onClick={onAlternar}>Alternar tema</button>;
}

function Aviso({ escuro }) {
  return <p>Tema: {escuro ? "escuro" : "claro"}</p>;
}

function App() {
  const [escuro, setEscuro] = useState(false);

  return (
    <div>
      <BotaoTema onAlternar={() => setEscuro(!escuro)} />
      <Aviso escuro={escuro} />
    </div>
  );
}

Leia a solução como uma mudança de endereço. O useState saiu do BotaoTema e foi para o App; o BotaoTema ficou sem estado nenhum e recebeu uma função para chamar no clique; o Aviso recebeu o valor e só desenha. O App é o único que chama setEscuro, e é isso que faz dele o dono. O botão não decide mais nada: ele avisa.

Guarde o nome onAlternar, porque ele é uma convenção e não um capricho. O prefixo on diz "isto é um aviso que eu emito", e o resto diz qual é o acontecimento. Quem lê <BotaoTema onAlternar={...} /> sabe duas coisas sem abrir o arquivo: o botão vai chamar a função quando algo acontecer, e quem chama decide o que fazer. A convenção funciona igual para onChange, onClick e onEnviar dos seus próprios componentes.

4. Dados descem, avisos sobem

O segundo caso é o carrinho de verdade. Duas listas, cada uma com o próprio estado; um cabeçalho que não tem como somar o que não vê. O caminho da solução tem três passos, sempre nesta ordem: subir os dados, passar os dados para baixo, passar a função que os altera para baixo. Quem faz os três ganha a tela coerente.

Mova a lista de itens para o App, passe quantos para cada lista e uma função onAdicionar para os botões. Clique em "Adicionar pão" e em "Adicionar salgado": o cabeçalho tem de contar dois itens.

function Cabecalho() {
  return <h2>Carrinho: 0 itens</h2>;
}

function Paes() {
  const [paes, setPaes] = useState([]);
  return (
    <div>
      <button id="pao" onClick={() => setPaes([...paes, "Pão"])}>Adicionar pão</button>
      <p>Pães: {paes.length}</p>
    </div>
  );
}

function Salgados() {
  const [salgados, setSalgados] = useState([]);
  return (
    <div>
      <button id="salgado" onClick={() => setSalgados([...salgados, "Queijo"])}>Adicionar salgado</button>
      <p>Salgados: {salgados.length}</p>
    </div>
  );
}

function App() {
  return (
    <div>
      <Cabecalho />
      <Paes />
      <Salgados />
    </div>
  );
}
<div>
  <h2>Carrinho: 0 itens</h2>
  <div>
    <button id="pao">Adicionar pão</button>
    <p>Pães: 0</p>

function Cabecalho({ total }) {
  return <h2>Carrinho: {total} {total === 1 ? "item" : "itens"}</h2>;
}

function Paes({ quantos, onAdicionar }) {
  return (
    <div>
      <button id="pao" onClick={() => onAdicionar("Pão")}>Adicionar pão</button>
      <p>Pães: {quantos}</p>
    </div>
  );
}

function Salgados({ quantos, onAdicionar }) {
  return (
    <div>
      <button id="salgado" onClick={() => onAdicionar("Queijo")}>Adicionar salgado</button>
      <p>Salgados: {quantos}</p>
    </div>
  );
}

function App() {
  const [itens, setItens] = useState([]);

  return (
    <div>
      <Cabecalho total={itens.length} />
      <Paes
        quantos={itens.filter((i) => i === "Pão").length}
        onAdicionar={(item) => setItens([...itens, item])}
      />
      <Salgados
        quantos={itens.filter((i) => i === "Queijo").length}
        onAdicionar={(item) => setItens([...itens, item])}
      />
    </div>
  );
}

O que mudou de fato: existe uma lista de itens, no App, e as duas listas de baixo são apenas janelas para ela. O quantos que cada filho recebe não é um estado novo; é uma conta feita na hora, com filter. O cabeçalho recebe o tamanho da mesma lista. Não há como os três discordarem, porque não há três valores — há um valor e três leituras.

O que também mudou: o filho não tem mais como adicionar nada sozinho. Ele chama onAdicionar("Pão") e quem decide é o pai. Essa dependência parece uma perda de autonomia e é o ponto central do padrão: o filho continua sendo reaproveitável, porque não sabe de onde vem a lista nem para onde vai. Numa outra tela, o mesmo Paes pode receber outra lista e outra função, e vai funcionar igual.

Num arquivo de verdade, o desenho fica assim — e repare que o estado do carrinho não aparece em nenhum filho:

function App() {
  const [itens, setItens] = useState([]);

  function adicionar(item) {
    setItens([...itens, item]);
  }

  return (
    <div>
      <Cabecalho total={itens.length} />
      <Paes quantos={itens.filter((i) => i === "Pão").length} onAdicionar={adicionar} />
      <Salgados quantos={itens.filter((i) => i === "Queijo").length} onAdicionar={adicionar} />
    </div>
  );
}

A função adicionar é declarada uma vez, com nome, e entregue aos dois filhos. É melhor do que duas funções anônimas iguais no JSX, por dois motivos: o nome documenta a intenção e a identidade da função é a mesma nos dois lugares. A identidade da função importa para o desempenho e tem aula própria (useCallback, adiante); aqui basta saber que uma função com nome, fora do JSX, é mais fácil de ler e de reaproveitar.

5. Um estado, dois controles

O terceiro caso mostra que elevar estado não é só para irmãos. A Ana tem dois jeitos de escolher a quantidade de pães: digitando no campo numérico ou arrastando a barra. Hoje cada um tem o próprio useState, então você digita 4 no campo, a barra continua em 1 e o texto embaixo não muda. São três valores para o mesmo fato.

Leve o estado qtd para o App e entregue qtd e onMudar aos dois controles. Digite 4 no campo: a barra e o texto têm de acompanhar.

function Numero() {
  const [qtd, setQtd] = useState(1);
  return (
    <input id="numero" type="number" value={qtd} onChange={(e) => setQtd(Number(e.target.value))} />
  );
}

function Barra() {
  const [qtd, setQtd] = useState(1);
  return (
    <input id="barra" type="range" min="1" max="9" value={qtd} onChange={(e) => setQtd(Number(e.target.value))} />
  );
}

function App() {
  return (
    <div>
      <Numero />
      <Barra />
      <p>Quantidade: 1</p>
    </div>
  );
}
<div>
  <input id="numero" type="number" value="1">
  <input id="barra" min="1" max="9" type="range" value="1">
  <p>Quantidade: 1</p>
</div>

function Numero({ qtd, onMudar }) {
  return (
    <input id="numero" type="number" value={qtd} onChange={(e) => onMudar(Number(e.target.value))} />
  );
}

function Barra({ qtd, onMudar }) {
  return (
    <input id="barra" type="range" min="1" max="9" value={qtd} onChange={(e) => onMudar(Number(e.target.value))} />
  );
}

function App() {
  const [qtd, setQtd] = useState(1);

  return (
    <div>
      <Numero qtd={qtd} onMudar={setQtd} />
      <Barra qtd={qtd} onMudar={setQtd} />
      <p>Quantidade: {qtd}</p>
    </div>
  );
}

Aqui os dois filhos são idênticos na forma: recebem qtd, desenham o campo e chamam onMudar com o número novo. Nenhum dos dois guarda nada. Quem guarda é o App, e é por isso que digitar no campo move a barra: os dois estão desenhando o mesmo qtd. O padrão tem nome — componente controlado — e é o mesmo que o input faz com o seu estado desde a aula de entrada controlada.

Com um console.log em cada componente da caixa, uma tecla no campo imprime três linhas — o pai primeiro, depois os dois filhos, todos com o mesmo número:

render do App: qtd = 4
render do Numero: qtd = 4
render do Barra: qtd = 4

Essa repetição do mesmo número em três lugares é o que se chama de fonte única: não há três valores, há três leituras de um valor só. E é também o custo do padrão — cada mudança no pai desenha todos os filhos que recebem o valor, mesmo os que não mudaram visualmente. Em telas pequenas isso é irrelevante; em listas grandes, é o motivo de existirem as técnicas de otimização das próximas aulas.

O Number(e.target.value) está ali porque todo campo devolve texto. Sem a conversão, a barra receberia "4" e continuaria funcionando por coincidência do navegador, enquanto uma soma posterior viraria "4" + 1 = "41". Converter na borda — no onChange — é o hábito que evita esse tipo de bug silencioso.

6. Onde parar de subir

Elevar tem custo, e o custo é acoplamento. Quanto mais alto o estado mora, mais componentes precisam recebê-lo por prop, e mais a página inteira redesenha quando ele muda. Uma busca que filtra uma lista não precisa do estado no App se a busca e a lista estão no mesmo componente; precisa, no máximo, no pai delas duas. O nome disso é colocar o estado perto de onde ele é usado.

A última linha é a que dói em produção. Um campo controlado no topo da árvore faz o formulário inteiro redesenhar a cada tecla; se houver uma tabela de duzentas linhas na mesma árvore, você vai sentir. A solução não é tornar o campo não controlado por reflexo: é perceber que aquele estado não precisava estar tão alto. Estado no lugar certo é uma decisão de desempenho e de clareza ao mesmo tempo.

7. Quando o estado muda de endereço

Subir o estado muda quem manda, e essa mudança tem um efeito colateral que quase ninguém antecipa: o componente filho pode perder o estado próprio. Isso acontece quando o componente troca de posição na árvore — por exemplo, sai de dentro de um if e vai para outro ramo, ou deixa de ser o primeiro filho e passa a ser o segundo. O React identifica componentes por posição, e mudar de lugar é, para ele, criar outro componente.

O sintoma é um campo que "esquece" o que estava digitado depois de uma mudança que não tinha nada a ver. Quando isso acontece, a pergunta é onde o componente estava antes e onde ele está agora. Se você precisa que ele seja sempre o mesmo, dê uma key estável — e se precisa justamente que ele esqueça, mude a key, como a aula de controlado e não controlado mostra.

Há um caso em que perder o estado é o objetivo. A Ana tinha um seletor de produto e, ao lado, um formulário de avaliação que guardava a nota digitada. Ao trocar de produto, a nota antiga continuava na tela — porque o formulário estava na mesma posição. A solução foi key={produto.id}: novo produto, formulário novo, nota zerada. Não foi preciso nenhum efeito de limpeza; a identidade fez o trabalho.

8. Os tropeços de quem está subindo

O primeiro tropeço é subir e deixar uma cópia. O estado vai para o pai, mas o filho continua com o seu useState e passa a desenhar a cópia local, que ninguém atualiza. O sintoma é uma tela em que metade muda e metade não. Ao elevar, apague o estado do filho; não deixe os dois convivendo "para não quebrar nada".

O segundo é chamar o set do pai de dentro do filho por outro caminho. Passar setItens como prop funciona, e é tentador — mas o filho passa a saber como o pai guarda o dado. No dia em que o pai precisar validar, registrar ou somar frete, vai ter de mudar o filho também. Passe uma função com nome de intenção (adicionar) e deixe a decisão no dono.

O terceiro é guardar em estado o que podia ser conta. "total", "quantosPães", "estaVazio" são derivados da lista; guardá-los significa atualizar dois lugares em cada mudança, e um dia esquecer um. Calcule no desenho, como a solução da caixa faz com filter. Se a conta for pesada, existe useMemo, com aula própria adiante; se for barata, ela é só uma linha.

9. Cenários do dia a dia

Cenário 1: o filtro e a lista

Na tela de produtos, a caixa de busca fica na barra do topo e a lista fica no corpo. São irmãos, e o filtro tem de chegar à lista. Sobe o texto da busca para o componente que contém os dois, e desce como prop. A lista continua dona do que é dela — a ordem, a página atual — e recebe só o termo. Se a barra de busca fosse reutilizável em outra tela, ela receberia o termo e o onBuscar e não saberia de nada.

Cenário 2: o modal de confirmação

O botão "Cancelar encomenda" abre um modal de confirmação, e o modal precisa saber qual encomenda está em jogo. O estado encomendaSelecionada sobe para o pai que desenha a lista e o modal. O modal recebe o dado e duas funções: onConfirmar e onFechar. O modal não decide nada; ele mostra e avisa, e por isso o mesmo modal serve para cancelar, excluir ou arquivar.

Cenário 3: o carrinho que virou contexto

Quando o carrinho passou a ser lido pelo cabeçalho, pela lista, pelo rodapé e pela página de pagamento, o estado subiu até o topo e começou a descer por sete níveis. Aí o problema deixou de ser elevar e virou passagem de prop demais — o assunto de props drilling e o motivo de existir o contexto. Elevar continua sendo o primeiro passo; o segundo é decidir como o valor viaja.

10. Fixando o que ficou

1. Para onde vai o estado quando dois irmãos precisam do mesmo valor?

2. O filho que recebe o dado e precisa mudá-lo recebe o quê?

3. Qual é o sinal de que o estado subiu demais?

Exercício: o aviso que sobe

O filho Paes quer avisar o pai que um pão foi escolhido. Complete a chamada que entrega o item para a função que o pai mandou por prop:

<button onClick={() => ("Pão")}>Adicionar pão</button>

Dica: é o nome da prop de callback, a mesma que o pai passa no JSX. Sem os parênteses, você estaria entregando a função em vez de chamá-la.

11. Resumo

Elevar o estado é mudar o useState de lugar: do componente que usa o valor para o menor ancestral comum de todos os que precisam dele. O dono novo passa a chamar o set, e os outros passam a receber o valor por prop e a pedir mudanças por uma função. Esse é o fluxo inteiro do React em uma frase — dados descem, avisos sobem — e ele aparece em toda tela que tem dois pedaços conversando.

A escolha do lugar é uma decisão de alcance, não de tamanho. Estado baixo demais esconde a informação de quem precisa dela; estado alto demais obriga meia página a redesenhar por causa de uma tecla. O caminho é começar no componente que usa e subir somente quando um segundo componente precisa ver o mesmo valor. Se o valor precisar atravessar muitos níveis, o problema muda de nome e as aulas de props drilling e contexto continuam a conversa.

E o detalhe que separa quem entendeu de quem decorou: um dado, um dono. Se duas cópias do mesmo valor existem na tela, uma delas vai envelhecer. Total, contagem e "está vazio" são contas feitas na hora, não estados paralelos. Guardar o que é derivado é a forma mais comum de criar uma tela que discorda de si mesma.

Para lembrar

  • Estado vai para o menor pai comum de quem precisa do valor.
  • O dono é quem tem o useState; os filhos só pedem.
  • Prop de dado desce; prop de callback sobe o aviso.
  • Nomeie callbacks com on: onAdicionar, onAlternar.
  • Prefira uma função com nome a duas funções anônimas iguais no JSX.
  • Dois controles do mesmo dado: um estado no pai, value e onMudar nos dois.
  • Depois de subir, apague o estado do filho: duas cópias é bug marcado.
  • Total e contagem se calculam no render, não se guardam.
  • Componente que muda de lugar na árvore perde o estado próprio; key resolve.
  • Subir demais custa redesenho e props demais: é hora de falar de contexto.
