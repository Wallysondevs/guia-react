O useReducer

O painel de pedidos da Ana tinha três useState para descrever o mesmo pedido: o status, se estava pago e quem ia entregar. Funcionava até o dia em que um pedido apareceu como "entregue" com pago: false — três estados que deviam mudar juntos, mas mudavam em momentos diferentes. Nesta aula ela junta os três num estado só e aprende a mudá-lo por ações: "pagar", "preparar", "entregar". Quem decide o que cada ação faz é uma função separada, o reducer — e é ela que garante que o pedido nunca fique pela metade.

Você vai aprender
  • O que é um reducer: uma função que recebe o estado e uma ação e devolve o estado novo.
  • Como usar useReducer e o que o dispatch faz.
  • Como montar ações com type e dados.
  • Por que o reducer precisa ser puro — e o que acontece quando ele muta o estado.
  • Como trocar vários useState por uma transição só.
  • Quando o useReducer é melhor que o useState, e quando não é.
  • Os erros clássicos: mutação, ação sem type e dispatch no meio do render.

1. A cena: o pedido com três verdades

O painel da padaria tinha três estados: status (novo, em preparo, pronto, entregue), pago (verdadeiro ou falso) e entregador (o nome de quem levou). Cada botão mexia em um deles. O botão "Pagar" chamava setPago(true). O botão "Entregar" chamava setStatus("entregue") e setEntregador("João").

Um dia, um pedido apareceu como entregue e não pago. Ninguém tinha feito nada de errado: alguém clicou em "Entregar" sem clicar em "Pagar", e o código não impedia. As três informações eram verdades separadas, e ninguém garantia que elas continuassem coerentes. A Ana passou a manhã procurando o bug nos botões, quando o problema era o desenho: o pedido é uma coisa, não três.

A ideia do reducer é essa: juntar os campos que mudam juntos num objeto só, e mudar todos eles numa única transição. Em vez de três setters espalhados, uma função que recebe o pedido de agora e a ação que aconteceu, e devolve o pedido novo — inteiro, coerente, do jeito que você escreveu.

2. O que é um reducer

Um reducer é uma função com dois parâmetros e um retorno: recebe o estado atual, recebe a ação que aconteceu, e devolve o estado novo. Nada mais. Ele não desenha, não busca dados, não chama setter. É uma calculadora de estados.

function reducer(estado, acao) {
  if (acao.type === "pagar") {
    return { ...estado, pago: true, status: "pago" };
  }
  if (acao.type === "entregar") {
    return { ...estado, status: "entregue", entregador: acao.entregador };
  }
  return estado;
}

Repare em três coisas. A primeira: o retorno é um objeto novo, montado com ... para copiar o que não mudou. A segunda: o estado antigo nunca é alterado — ele é lido e descartado. A terceira: toda ação tem um type, um texto que diz o que aconteceu, e pode trazer dados junto, como o nome do entregador.

reducer
A função (estado, acao) => novoEstado. Pura: mesmo estado e mesma ação, mesmo resultado.
ação
Um objeto que descreve o que aconteceu: { type: "pagar" }, { type: "entregar", entregador: "João" }.
dispatch
A função que entrega a ação ao React. É estável entre renders e pode ir como prop sem medo.
transição
A passagem de um estado para outro. No reducer, cada if é uma transição possível.
estado inicial
O objeto com que o componente começa: { status: "novo", pago: false, entregador: "" }.

Quem chama o reducer é o React, não você. O componente pede uma mudança com dispatch(acao), o React chama o reducer com o estado atual e a ação, e usa o retorno como estado novo. Você nunca chama o reducer diretamente — e não precisa: ele é uma função comum, fácil de testar fora do React, porque não depende de nada além dos dois parâmetros.

3. O primeiro useReducer

A assinatura é const [estado, dispatch] = useReducer(reducer, estadoInicial). O React guarda o estado, como no useState; a diferença é que você não recebe um setter com o valor novo, e sim o dispatch, que entrega uma ação para o reducer decidir o que fazer.

const inicial = { paes: 0, total: 0 };

function reducer(estado, acao) {
  if (acao.type === "somar") {
    return { paes: estado.paes + 1, total: estado.total + 2.5 };
  }
  if (acao.type === "zerar") {
    return { paes: 0, total: 0 };
  }
  return estado;
}

function Pedido() {
  const [pedido, dispatch] = useReducer(reducer, inicial);

  return (
    <div>
      <p>pães: {pedido.paes}</p>
      <p>total: {pedido.total}</p>
      <button onClick={() => dispatch({ type: "somar" })}>Somar um</button>
      <button onClick={() => dispatch({ type: "zerar" })}>Zerar</button>
    </div>
  );
}

O reducer fica fora do componente, e isso não é estilo: ele não usa nada de dentro do componente, então não precisa ser recriado a cada render. Fora, ele é uma função estável, fácil de ler e de testar. Dentro, seria mais uma função nova a cada desenho, com os problemas de identidade da aula de useCallback.

Agora a missão. O reducer tem a ação somar pronta, mas a ação zerar devolve o estado como está — o botão Zerar não faz nada.

No código inicial, os dois cliques em Somar levam o total a 5; o clique em Zerar não muda nada, porque a ação chega ao reducer e ele devolve o mesmo objeto. Essa é a diferença prática em relação a dois useState. Com dois setters, cada clique provoca uma atualização separada; se um deles falhar, o estado fica pela metade. Com o reducer, cada ação produz um estado completo — e o React desenha uma vez, com o objeto inteiro coerente.

4. A ação: o que aconteceu, não o que fazer

Uma ação bem escrita descreve o fato, não a instrução. { type: "pagar" } diz que o pagamento aconteceu; o reducer decide que isso significa pago: true e status: "pago". Se amanhã a regra mudar — pagamento aprovado só depois de conferir o comprovante —, você mexe no reducer e todos os botões continuam funcionando, porque nenhum deles sabe como o pagamento funciona.

O type é o nome do fato, sempre no mesmo formato combinado. Escolha um padrão e siga: verbos no infinitivo ("adicionar", "remover") ou no particípio ("pago", "adicionado"). O importante é não misturar. Dados extras vão como campos do mesmo objeto, ao lado do type.

AçãoO que o reducer fazQuem dispara
{ type: "pagar" }marca pago: true e status: "pago"o botão Pagar
{ type: "preparar" }muda o status para "em preparo"a cozinha, ao começar
{ type: "entregar", entregador: "João" }marca status: "entregue" e guarda o nomeo botão Entregar
{ type: "cancelar" }volta ao estado inicial e limpa o entregadoro botão Cancelar

Essa lista de ações é a documentação do componente. Quem chega depois lê os quatro nomes e entende o que o pedido pode fazer; no reducer, vê o que cada um muda. Comparado a três setters espalhados por seis botões, é outra categoria de legibilidade.

Agora a missão com dados na ação. O carrinho abaixo adiciona o pão certo, mas o dispatch esqueceu de mandar o nome: o reducer recebe acao.nome como undefined e a lista ganha a palavra "undefined".

5. O reducer precisa ser puro

Puro, aqui, quer dizer: o reducer não altera o que recebeu e não faz nada além de devolver o estado novo. Nada de push, nada de atribuir em estado.algo, nada de console.log com efeito, nada de chamar setAlgo. Ele lê, calcula e devolve.

Quando o reducer muta o objeto e devolve o mesmo objeto, o React compara e conclui que nada mudou — e não desenha. O estado até está diferente por dentro; a tela, não. É o mesmo problema da aula de estado com objeto, agora dentro de uma função que parece mais "oficial" e por isso engana mais.

O reducer faz push no array e devolve o mesmo objeto, então a tela não muda. Devolva um objeto novo com [...estado.itens, acao.nome] e clique em Adicionar rosca.

const inicial = { itens: ["pão francês"], total: 1 };

function reducer(estado, acao) {
  if (acao.type === "adicionar") {
    estado.itens.push(acao.nome);
    estado.total = estado.total + 1;
    return estado;
  }
  return estado;
}

function App() {
  const [carrinho, dispatch] = useReducer(reducer, inicial);

  return (
    <div>
      <p>itens: {carrinho.itens.join(", ")}</p>
      <p>total: {carrinho.total}</p>
      <button
        id="add"
        onClick={() => dispatch({ type: "adicionar", nome: "rosca" })}
      >
        Adicionar rosca
      </button>
    </div>
  );
}

No inicial, o clique não muda o painel: o array foi alterado por dentro, mas o objeto é o mesmo e o React não vê motivo para desenhar. Pior: o estado guardado agora está diferente do que a tela mostra, e qualquer render posterior (um clique em outro botão, por exemplo) mostra o array já com a rosca — o famoso "só aparece depois de clicar duas vezes". Na solução, cada ação cria um objeto novo e o React desenha na hora.

Uma consequência prática: nunca mute o inicial. Se o reducer dá push dentro de estado.itens e o estado inicial é a constante de fora, a constante muda junto — e a próxima montagem do componente começa com dados que não devia ter. Trate o estado como somente leitura e crie objetos novos.

6. Uma ação, vários campos

Voltando ao pedido da Ana: com o estado junto, cada transição atualiza o que precisa de uma vez. Não existe mais o botão que muda só o status e esquece o pagamento, porque quem decide é o reducer.

const inicial = {
  status: "novo",
  pago: false,
  entregador: ""
};

function reducer(estado, acao) {
  if (acao.type === "pagar") {
    return { ...estado, pago: true, status: "pago" };
  }
  if (acao.type === "preparar") {
    return { ...estado, status: "em preparo" };
  }
  if (acao.type === "entregar") {
    return {
      ...estado,
      status: "entregue",
      entregador: acao.entregador
    };
  }
  if (acao.type === "cancelar") {
    return inicial;
  }
  return estado;
}

O ... espalha o estado atual e as propriedades seguintes sobrescrevem o que mudou. É o mesmo spread da aula de estado com objeto, e a regra é a mesma: copiar e sobrescrever, nunca alterar. Cada if é uma transição possível; tudo que não é ação conhecida devolve o estado como está, nenhum erro.

Com dispatch, o registro do que aconteceu fica fácil. Dá para colocar um console.log na hora de disparar e ver a sequência de estados sem tocar no reducer:

function pagar() {
  dispatch({ type: "pagar" });
  console.log("status: pago, pago: true");
}
status: pago, pago: true, entregador: ""
status: em preparo, pago: true, entregador: ""
status: entregue, pago: true, entregador: "João"

Uma linha por transição, sempre com os três campos coerentes. Se um dia o pedido não puder ser entregue sem estar pago, a regra vai para dentro do reducer — if (!estado.pago) return estado; — e vale para todo botão que dispara entregar, hoje e amanhã. É aí que o reducer ganha o salário: a regra mora num lugar só.

O dispatch é estável entre renders, o que é uma vantagem prática: você pode passá-lo como prop para um filho embrulhado em memo sem precisar de useCallback. Se um botão distante precisa mudar o pedido, mande o dispatch e a ação; o filho não precisa saber como o estado é montado.

7. useState ou useReducer?

O useReducer não substitui o useState. Ele é melhor quando o estado tem regras, quando várias propriedades mudam juntas ou quando a próxima situação depende da anterior. Para um contador simples ou um campo de texto, o useState é mais curto e mais claro.

SituaçãoFerramentaPor quê
um número, um texto, um booleanouseStateo setter resolve em uma linha
um objeto com três campos que mudam juntosuseReducera transição fica num lugar só
próximo estado depende do anterior (passos, fila)useReducera regra cabe na função
vários botões mudam o mesmo dadouseReduceras ações documentam o que pode acontecer
valor que o filho muda com um setter simplesuseStatenão há regra para centralizar
estado que precisa ser registrado para depuraruseReducercada mudança é uma ação nomeada

Um sinal de que chegou a hora: você tem três ou mais useState que mudam no mesmo clique. Outro sinal: você já escreveu uma regra do tipo "se status for entregue, então pago precisa ser verdadeiro" em mais de um lugar. Regra repetida é regra que vai divergir.

Não exagere no outro sentido: começar todo componente com um reducer é complicação. O caminho normal é começar com useState e migrar quando a bagunça aparecer — o que é fácil, porque a tela quase não muda: os nomes dos campos continuam iguais, só a forma de mudar é que passa a ser por ação.

8. Os erros clássicos

Chamar dispatch no meio do render. Um dispatch({ type: "somar" }) solto no corpo do componente dispara uma atualização a cada render, que gera outro render, que dispara de novo. O React interrompe com um erro de profundidade máxima. dispatch é para evento e efeito, como qualquer mudança de estado.

Esquecer o type. Um dispatch() sem ação nenhuma produz a mensagem mais confusa do assunto:

TypeError: Cannot read properties of undefined (reading 'type')

A leitura é literal: alguém tentou ler acao.type e acao é undefined. A causa é quase sempre um dispatch chamado sem argumento, ou uma ação montada com outro nome de campo ({ tipo: "somar" } em vez de { type: "somar" }), que também cai no undefined.

Devolver undefined. Um reducer com if sem return final devolve undefined para as ações que não casam, e o próximo render quebra ao ler estado.algo. O return estado; no fim não é enfeite: é o caminho para toda ação desconhecida.

Ler o estado logo depois do dispatch. dispatch(...) não muda a variável pedido daquele render; ela só agenda a mudança. Se você precisar do valor novo, calcule-o antes ou derive na renderização seguinte. É a mesma lógica do useState, e a aula de batching explica o porquê.

Guardar coisa que não é estado. Reducer é para estado: o que a tela mostra e a pessoa altera. O id de um timer, o elemento do DOM e "já enviei" continuam sendo assunto de useRef.

9. Cenários do dia a dia

Cenário 1: o pedido entregue e não pago

Três setters independentes deixavam qualquer combinação acontecer, inclusive as impossíveis. Com um reducer, entregar sem pagar é uma regra que você escreve uma vez: se não está pago, a ação não muda nada. O estado deixa de ser um conjunto de campos soltos e passa a ser o retrato de uma situação válida.

Cenário 2: a lista que só mudava no segundo clique

O reducer dava push e devolvia o mesmo objeto. O React comparava, via o mesmo objeto, e não desenhava. No clique seguinte, outro render mostrava a lista já alterada — daí a impressão de atraso. O conserto é criar objeto novo: { itens: [...estado.itens, novo] }.

Cenário 3: o botão que não fazia nada

O botão disparava { type: "zera" } e o reducer esperava "zerar". A ação chegava, nenhum if casava, o reducer devolvia o estado como estava e a tela não mudava — sem erro nenhum. Um console.log(acao) temporário no reducer mostra o nome errado em segundos.

11. Resumo

O useReducer troca o par valor/setter por um par estado/dispatch. O estado é um objeto só, com os campos que mudam juntos; o dispatch entrega uma ação, um objeto com type e, quando precisa, dados. O React chama o reducer com o estado atual e a ação, e usa o retorno como estado novo. O reducer é uma função pura, fora do componente, que devolve sempre um objeto novo — nunca altera o que recebeu — e termina com return estado; para as ações que não conhece.

A vantagem aparece quando o estado tem regras: uma ação muda vários campos de uma vez, a regra mora num lugar só e o estado nunca fica pela metade. A desvantagem é cerimônia: para um contador ou um campo de texto, o useState é mais direto. Comece simples e migre quando os estados começarem a precisar uns dos outros.

E os erros que você vai reconhecer de longe: mutação no reducer (a tela não muda), ação sem type (o erro de undefined), reducer sem return final e dispatch no meio do render. Com o estado no lugar certo e as transições nomeadas, o painel da Ana parou de mostrar pedido impossível — e a próxima vez que a regra mudar, ela mexe em um if.

Para lembrar

  • Reducer é (estado, acao) => novoEstado, uma função pura.
  • useReducer(reducer, inicial) devolve [estado, dispatch].
  • A ação descreve o que aconteceu: { type: "pagar" }.
  • Dados extras vão na ação: { type: "entregar", entregador: "João" }.
  • O reducer devolve objeto novo; mutar o estado não redesenha a tela.
  • Escreva o reducer fora do componente: ele não usa nada de dentro.
  • return estado; no fim cobre as ações desconhecidas.
  • dispatch é estável e pode ir como prop sem useCallback.
  • Não chame dispatch no corpo do componente.
  • Vários useState que mudam juntos são o sinal para migrar.
