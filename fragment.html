O Fragment

O topo do site da Ana precisa mostrar o nome da padaria e o horário lado a lado, e o CSS já está pronto para isso — mas o componente devolve uma div no meio, e ela atrapalha o alinhamento. Nesta aula a Ana conhece o Fragment: a casca invisível que deixa um componente devolver vários irmãos sem criar elemento nenhum na página. E descobre os dois lugares em que ele não é só conveniência — é obrigação.

Você vai aprender
  • Por que um componente devolve um elemento só, e como contornar isso sem criar nó.
  • A diferença entre <>…</> e <Fragment>…</Fragment>.
  • Onde a div extra quebra o layout e onde ela é HTML inválido.
  • Como dar key a um fragmento em uma lista.
  • O que o fragmento não aceita — e por que ele não aparece no DevTools.
  • Quando a div é a resposta certa.

1. A cena: dois irmãos e uma div no meio

A Ana quer o topo do site com o nome da padaria e o horário na mesma linha. O CSS dela tem uma regra simples: o container usa display: flex e gap: 12px; os filhos diretos ficam lado a lado, com doze pixels entre eles. Para isso funcionar, o h1 e o p precisam ser irmãos — filhos diretos do mesmo container.

O componente dela devolve uma div embrulhando os dois. O resultado na tela é o esperado, mas o CSS não pega: os filhos diretos do container passaram a ser uma div só, e o gap não tem entre o que espaçar. O h1 e o p ficaram empilhados dentro de uma caixa que ninguém pediu. O React não tem culpa: foi ela quem pediu a caixa.

Esse é o problema que o Fragment resolve. Ele é um componente especial que agrupa elementos para o React sem criar nada para o navegador. O componente devolve um fragmento com dois filhos, o React desenha os dois irmãos direto no HTML, e o CSS encontra exatamente a estrutura que esperava. Nem uma div a mais, nem um span disfarçado.

E há casos em que a div não é só inconveniente: é inválida. Dentro de uma tabela, só entram thead, tbody, tr e seus parentes; uma div no meio é HTML que o navegador não sabe interpretar. O mesmo vale para dl, dt/dd, ul/li e select. Nesses lugares, o fragmento não é estilo: é a única forma de um componente devolver vários itens válidos.

2. Por que um componente devolve um elemento só

Vale entender a raiz da regra, porque ela explica tudo o que vem depois. O JSX não é HTML: cada tag vira uma chamada de função que cria um elemento. <div>oi</div> vira uma chamada com o nome da tag, os atributos e os filhos. Quando você escreve três tags lado a lado, o compilador vê três chamadas soltas e não sabe o que devolver — uma função devolve uma coisa. Daí o erro clássico, que aparece no painel assim que você tenta:

Erro: não compilou: /App.jsx: Adjacent JSX elements must be wrapped in an enclosing tag. Did you want a JSX fragment <>...</>? (4:4)

  2 |   return (
  3 |     <h1>Padaria da Ana</h1>
> 4 |     <p>Aberto das 6h às 18h</p>
    |     ^

A mensagem já sugere a solução: um fragmento. Em vez de inventar uma caixa, você diz "estes elementos andam juntos" — e o React trata o conjunto como um pai invisível, que existe na árvore do React e não existe no DOM.

fragmento
Um agrupador sem elemento. O React usa para devolver vários irmãos e não escreve nada no HTML.
sintaxe curta
<>…</>: o fragmento sem nome. Não aceita atributo nenhum, nem key.
elemento pai
O que o componente devolve como raiz. Pode ser um elemento de verdade ou um fragmento.
nó do DOM
Um elemento que existe na página, com tag e atributos. O fragmento não cria nenhum.
key
A identidade de um item em uma lista. Em fragmento, só funciona na forma <Fragment key={…}>.

Uma comparação ajuda a fixar. Se o componente devolve <div><h1>…</h1></div>, a página tem um div e, dentro, o h1. Se devolve <><h1>…</h1></>, a página tem só o h1, e ele é filho direto de quem chamou o componente. Essa diferença de parentesco é o que decide se o CSS do pai alcança o elemento — e é por isso que ela aparece tanto em layout flexível.

3. A div que sobra

Primeiro exemplo, o mais comum. O componente do topo devolve uma div com o título e o horário. A missão troca a div por um fragmento e prova a diferença contando os elementos: o painel tem de mostrar o h1 e o p como irmãos, sem nenhuma div no HTML gerado.

O Topo devolve uma div em volta dos dois elementos, e ela atrapalha o CSS do pai. Troque a div por um fragmento <>…</>, sem criar nenhum elemento a mais.

function Topo() {
  return (
    <div>
      <h1>Padaria da Ana</h1>
      <p>Aberto das 6h às 18h</p>
    </div>
  );
}

function App() {
  return (
    <main>
      <Topo />
    </main>
  );
}
<main>
  <div>
    <h1>Padaria da Ana</h1>
    <p>Aberto das 6h às 18h</p>
  </div>
</main>

function Topo() {
  return (
    <>
      <h1>Padaria da Ana</h1>
      <p>Aberto das 6h às 18h</p>
    </>
  );
}

function App() {
  return (
    <main>
      <Topo />
    </main>
  );
}

Antes, o painel mostrava main > div > h1. Depois, mostra main > h1 e main > p: o fragmento desapareceu, e os dois elementos subiram um nível. Nenhuma classe, nenhum estilo, nenhuma linha de CSS mudou — mudou o parentesco. É a diferença entre uma caixa e um elástico: o elástico mantém as coisas juntas na hora de entregar e não ocupa espaço na tela.

Repare que o fragmento vazio tem duas metades e nenhum nome: <> abre e </> fecha. Não existe nome no meio, não existe tag de verdade. É por isso que ele não aceita atributos: não há elemento onde pendurá-los. E é por isso que o React precisa do Babel para entendê-lo — o JSX comum não teria como representar essa marca.

4. A sintaxe curta e a longa

O mesmo componente pode ser escrito de duas formas. A curta é a que você viu: <>…</>. A longa usa o nome Fragment, que vem do próprio React, e parece um componente comum. As duas produzem exatamente o mesmo HTML — a diferença está no que você consegue escrever dentro da tag de abertura.

<>…</><Fragment>…</Fragment>

Nas caixas deste guia, Fragment já está no escopo, como useState e useEffect — não é preciso importar. No projeto de verdade, o import aparece no topo do arquivo, e as linhas de import são removidas pelo motor antes de rodar. Se você esquecer o import, o erro é "Fragment is not defined", e o conserto é uma linha.

A escolha do dia a dia é fácil: use <>…</> sempre que não precisar de atributo. Ela é mais curta, não exige import e deixa o JSX mais limpo. A forma longa existe por um motivo específico — o key em listas — e é sobre isso que a seção 6 trata. Também vale lembrar que Fragment é um nome comum em código antigo: você pode encontrar <React.Fragment> em arquivos que não desestruturaram o import. É a mesma coisa.

5. Onde a div é proibida

Agora o caso em que o fragmento deixa de ser conveniência. Um componente que devolve as células de uma linha de tabela não pode devolver uma div: dentro de tr só entram td e th. O React não valida isso — ele cria o que você mandar —, e o navegador aceita a estrutura na árvore, mas o HTML deixa de ser válido e o CSS da tabela se perde.

O componente Celulas devolve uma div dentro do tr, o que é HTML inválido. Troque a div por um fragmento para as duas células ficarem soltas dentro da linha.

function Celulas({ nome, preco }) {
  return (
    <div>
      <td>{nome}</td>
      <td>{"R$ " + preco + ",00"}</td>
    </div>
  );
}

function App() {
  return (
    <table>
      <tbody>
        <tr><Celulas nome="Pão francês" preco={12} /></tr>
        <tr><Celulas nome="Croissant" preco={14} /></tr>
      </tbody>
    </table>
  );
}

O painel do código inicial mostra a prova do crime: um div entre tr e td. Você não veria isso no navegador sem abrir o inspetor, porque o desenho da tabela continua parecido — mas o HTML está errado, os leitores de tela se perdem e qualquer estilo que dependa de tr > td para de funcionar. Com o fragmento, o painel mostra tr com dois td diretos, quatro células no total, nenhuma div dentro da tabela.

O mesmo raciocínio vale para outros agrupadores com filhos obrigatórios: dl aceita dt e dd; ul e ol aceitam li; select aceita option e optgroup; tr aceita td e th. Em todos, se um componente precisa devolver vários filhos desse tipo, o fragmento é a ferramenta — e não há alternativa sem ele, a não ser repetir o componente para cada item.

6. Fragmento em lista precisa de key

Quando o fragmento aparece dentro de um map, ele vira um item de lista e precisa de identidade — a mesma key que você já usa em li e tr. E aqui aparece o único motivo real para usar a forma longa: a sintaxe curta, <>, não aceita atributo nenhum, então não dá para escrever key nela. É <Fragment key={item}> ou nada.

Cada item da lista precisa de um dt e um dd irmãos, e a div no meio do dl é inválida. Use <Fragment key={item}> para agrupar os dois.

const itens = ["Pão", "Bolo", "Café"];

function App() {
  return (
    <dl>
      {itens.map((item) => (
        <div>
          <dt>{item}</dt>
          <dd>Disponível hoje</dd>
        </div>
      ))}
    </dl>
  );
}

Na solução, o painel mostra seis elementos dentro do dl, em pares, sem nenhum div. A key não aparece no HTML — ela é informação para o React, não para o navegador. É por isso que ela precisa estar no elemento mais externo do item, e no fragmento ela só pode entrar na forma longa.

E vale a prova de que o fragmento não cria nó: se você medir os filhos do container no navegador, o número é o de elementos de verdade. Um componente que devolve um fragmento com dois filhos acrescenta dois filhos, não três:

console: filhos de #raiz: 2

Duas linhas de código produzem esse número. A medição é feita dentro de um useEffect, porque é depois da renderização que o DOM existe: antes disso, não há o que contar. E o resultado confirma o que o painel já mostrava — o fragmento é invisível para o navegador e visível para o React.

7. O que o fragmento não aceita

Como o fragmento não é um elemento, ele não tem atributos de elemento. className, style, id, onClick: nada disso existe nele. Se você tentar, o React reclama — e a mensagem é curta porque a lista de props permitidas tem só duas: children e key.

Essa limitação é a própria definição da ferramenta, não um defeito. Querer uma classe no fragmento é querer uma caixa; se você precisa de classe, precisa de div. O fragmento serve exatamente para quando não há nada a aplicar — nem classe, nem estilo, nem evento, só a necessidade de devolver vários irmãos.

Outra consequência prática: o fragmento não aparece no DevTools. Abra o inspetor e você vê main com h1 e p dentro, sem nenhum nó intermediário. Isso confunde na primeira vez, porque o código-fonte mostra o fragmento e a árvore do navegador não. Lembre-se: a árvore do navegador mostra o DOM; o fragmento existe só na árvore do React.

Existe ainda uma pegadinha de leitura. Como <> não tem nome, ferramentas antigas e mensagens de erro às vezes se referem a ele como "fragmento anônimo" ou mostram a posição no arquivo em vez do nome. Quando o erro fala em Fragment e você jura que não escreveu nenhum, procure por <> no arquivo — é o mesmo componente, escrito de forma curta.

8. Quando a div é a resposta certa

Depois de aprender o fragmento, é comum querer usá-lo em tudo. Mas a div não é vilã: ela é o elemento genérico de bloco, e existe justamente para agrupar com estilo. A pergunta certa não é "div ou fragmento?", é "preciso de uma caixa aqui?". Se a resposta for sim, use div — com classe, com estilo, com o que a caixa precisa fazer.

A última linha economiza código e confusão. Se o componente devolve <><p>oi</p></>, o fragmento não está fazendo nada: o p já é um elemento só e podia ser devolvido direto. Fragmento com um filho é sinal de que alguém apagou metade do conteúdo e esqueceu a casca.

Também cuidado com o excesso no sentido oposto: fragmentos dentro de fragmentos, cada um envolvendo dois elementos que poderiam ser irmãos do nível de cima. O JSX fica com uma escada de <> que não agrupa nada e só atrapalha a leitura. Agrupe quando houver motivo — um componente que precisa devolver vários irmãos, um item de lista que precisa de key — e deixe o resto plano.

9. Cenários do dia a dia

Cenário 1: o gap do flex que não aparece

A Ana aplicou display: flex e gap: 12px no container e o espaço não apareceu. O componente filho devolvia uma div com dois elementos dentro, então o container tinha um filho só. Trocado por um fragmento, os dois elementos viraram filhos diretos e o gap funcionou. O sintoma é sempre esse: o CSS parece certo, mas o parentesco no HTML é outro.

Cenário 2: a tabela que ficou torta no celular

O componente de células devolvia div, e a tabela continuou bonita no desktop — até a Ana ver no celular, onde as colunas se desalinharam. O HTML inválido costuma perdoar no computador e cobrar no celular e nos leitores de tela. Com o fragmento, o td volta a ser filho do tr, e a tabela inteira se comporta como tabela.

Cenário 3: o aviso de key que não fazia sentido

Ela usou <>…</> dentro de um map e o console reclamou que faltava key. Tentou escrever key na sintaxe curta e o código nem compilou. A saída é a forma longa: <Fragment key={item}>. Vale sempre lembrar que a key fica no elemento mais externo do item que o map devolve — fragmento, div ou li.

Exercício: o fragmento com nome

Complete as duas lacunas. Na primeira, o nome do componente que permite a key em um fragmento; na segunda, o nome do que o fragmento não cria — o que explica ele ser invisível no inspetor do navegador:

{itens.map((item) => ( < key={item}> <dt>{item}</dt> <dd>Disponível hoje</dd> </Fragment> ))} // o fragmento não cria nenhum na página

Dica: a primeira é o nome que o React exporta e que você importa com import { … } from "react". A segunda é a sigla de três letras do modelo de elementos do navegador — a árvore onde os nós de verdade aparecem.

11. Resumo

Um componente devolve um elemento só, porque o JSX vira uma chamada de função que cria um elemento. Quando você precisa devolver vários irmãos, o Fragment agrupa sem criar nó: o HTML final sai com os irmãos soltos, no nível de cima. A forma curta, <>…</>, serve para quase tudo; a forma <Fragment> existe para quando é preciso passar key, e só isso.

Dois lugares em que o fragmento é obrigação: quando o CSS do pai precisa alcançar os filhos diretos (layout flexível, grid, gap) e quando a estrutura HTML não permite div — tr com td, dl com dt e dd, ul com li, select com option. Nesses casos, a div não é feia, é inválida, e o preço aparece no celular e nos leitores de tela.

E a regra que evita os dois excessos: fragmento quando não há caixa a desenhar, div quando há. Fragmento não aceita className, style nem evento, porque não existe elemento onde pendurar — se você quer estilo no grupo, quer uma div. Se o grupo tem um filho só, não quer nada. Na dúvida, olhe o painel: ele mostra o parentesco real, que é o que o CSS vê.

Para lembrar

  • Componente devolve um elemento só; o fragmento é o pai invisível para vários irmãos.
  • <>…</> não cria nó e não aceita atributo nenhum.
  • <Fragment key={item}> é a forma longa: aceita key e mais nada.
  • Em map, use a forma longa: a curta não aceita key.
  • Dentro de tr, dl, ul e select, a div é HTML inválido.
  • Fragmento não tem classe, estilo nem evento: quer caixa, use div.
  • Um filho só não precisa de fragmento.
  • O fragmento não aparece no DevTools: existe na árvore do React, não no DOM.
