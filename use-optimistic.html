O useOptimistic

A Ana já sabe pintar o resultado antes de ele existir — ela fez isso à mão, com um estado de itens provisórios e um desfazer no catch. Funcionou, mas cada lista nova pedia o mesmo código de novo. O React 19 traz esse padrão como hook: você desenha o item na hora, o servidor confirma depois, e se a resposta for “não” o item sai da tela sozinho. Nesta aula a Ana troca o esquema manual pelo useOptimistic e aprende as duas regras que fazem o hook funcionar.

Você vai aprender
  • O que useOptimistic devolve e por que ele não é um useState.
  • O reducer que transforma o estado real no estado que a pessoa vê.
  • Como o item provisório desaparece sozinho quando o servidor recusa.
  • Por que a função só pode ser chamada dentro de uma ação ou de uma transição.
  • Como atualizar um item que já existe — não só adicionar.
  • O que precisa ser verdade para o otimismo não virar mentira na tela.
  • As armadilhas: item que fica “enviando” para sempre, clique duplo, chave repetida.

1. A cena: o pão que ainda não existe

Na padaria da Ana, adicionar um pão ao catálogo é uma conversa com o servidor: ele confere o nome, verifica se não é duplicado, grava. Enquanto a resposta não chega, nada muda na tela. A cliente digita “broa”, clica em adicionar, olha a lista — e a lista está igual. Ela clica de novo. Agora existem duas requisições iguais a caminho, e uma delas vai voltar dizendo que já existe.

O problema não é a lentidão: é o silêncio. A pessoa fez a ação e não viu retorno nenhum, então conclui que o clique não funcionou. A solução é mostrar o item antes de o servidor responder — o que se chama de atualização otimista, porque você aposta que a resposta vai ser “sim”.

A Ana já fez isso no nível anterior, à mão. Ela guardava duas listas: a real, que vinha do servidor, e a dos provisórios, que ela mesma acrescentava no clique. Na hora de desenhar, juntava as duas. Quando o servidor respondia, promovia o provisório a definitivo; quando recusava, filtrava o provisório fora. Deu certo — e custou uns vinte de linhas por lista, com um catch que ela podia esquecer.

O useOptimistic é esse mesmo esquema dentro do React. Você continua com uma lista só (a real) e diz ao React como ela deve parecer quando tem uma atualização otimista em andamento. Terminada a transição, o React volta a mostrar a lista real — com o item novo, se o servidor confirmou, ou sem ele, se não confirmou.

2. O que o hook faz por você

A chamada tem a forma const [lista, adicionar] = React.useOptimistic(estadoReal, reducer). O primeiro item é o que você desenha na tela — a lista já com as atualizações otimistas aplicadas. O segundo é uma função para pedir uma atualização, chamada dentro da ação que conversa com o servidor.

estado real
A fonte da verdade: a lista que veio do servidor e vive em um useState.
reducer
(estadoAtual, valorPedido) => novoEstado. Diz ao React como aplicar o pedido por cima do estado real.
lista (estado otimista)
O que a pessoa vê. É o estado real, ou o real com o pedido aplicado enquanto a transição não termina.
adicionar
A função que dispara o pedido. Só vale dentro de uma ação de formulário ou de uma startTransition.
transição
O intervalo entre o pedido e a resposta. Quando ela fecha, o estado otimista é descartado e o real assume.

Repare no que o hook não faz: ele não guarda o item, não chama o servidor e não desfaz nada manualmente. Ele deriva um estado de exibição a partir do estado real e de um pedido temporário. É por isso que o desfazer é automático — não existe “item provisório” guardado em lugar nenhum para você remover depois.

Como o useOptimistic não está no escopo das caixas deste guia, o código escreve React.useOptimistic. No seu projeto você importa: import { useOptimistic } from "react". E o startTransition também: import { startTransition } from "react".

3. O item entra na lista na hora

A primeira caixa é a cena da padaria. O formulário envia o nome, a ação espera a resposta do servidor e só então acrescenta o pão à lista real. Enquanto isso, a lista não muda — e o item que a pessoa acabou de digitar não aparece.

A missão é desenhar a broa imediatamente, marcada como “enviando”, e deixar o React trocar pela versão definitiva quando o servidor responder. O botão “servidor responde” faz o papel da rede: enquanto ninguém clica nele, a resposta não chegou.

O pão só aparece depois da resposta. Use React.useOptimistic para desenhar o item novo na hora, com o texto Broa (enviando), mantendo o useState como fonte da verdade.

let responder = null;

function enviar(nome) {
  return new Promise((ok) => {
    responder = () => ok();
  });
}

function App() {
  const [paes, setPaes] = useState([{ nome: "Pão francês" }]);

  return (
    <form action={async (dados) => {
      const nome = String(dados.get("nome") || "").trim();
      if (!nome) return;
      await enviar(nome);
      setPaes((atual) => [...atual, { nome: nome }]);
    }}>
      <input name="nome" />
      <button>Adicionar</button>
      <button type="button" id="responder" onClick={() => responder && responder()}>
        servidor responde
      </button>
      <ul>
        {paes.map((p) => (
          <li key={p.nome}>{p.nome}</li>
        ))}
      </ul>
    </form>
  );
}

Assim que o clique acontece, a lista tem dois itens: o pão francês e a broa marcada como enviando. Depois que o servidor responde, o item otimista é descartado e a lista real — agora com a broa de verdade — assume o lugar. Mesmo texto, mesma posição, sem piscar.

Note a ordem das três linhas dentro da ação: primeiro adicionar(nome), depois a espera, depois o setPaes. Se você chamar adicionar depois do await, a atualização otimista só aparece quando já não serve para nada. E se esquecer o setPaes, o item some quando a transição fecha — o otimista nunca substitui o estado real, ele só o enfeita.

4. Quando o servidor diz não

Otimismo tem hora que dói: o servidor recusa, e o item que estava na tela precisa sair. No esquema manual, isso era um filter no catch. Com o hook, não é nada — o item otimista deixa de existir quando a transição termina, tenha ela dado certo ou não. O que você ainda precisa escrever é a mensagem, para a pessoa entender por que o pão não entrou.

A caixa tem o mesmo formulário, com um servidor que recusa. A missão é mostrar a broa na hora e devolver a lista ao que era quando a recusa chega, com o aviso “Não enviado: sem estoque”.

Use React.useOptimistic para a broa aparecer na hora e sair sozinha quando o servidor recusar. No catch, mostre Não enviado: sem estoque.

let responder = null;

function enviar(nome) {
  return new Promise((ok, falha) => {
    responder = () => falha(new Error("sem estoque"));
  });
}

function App() {
  const [paes, setPaes] = useState([{ nome: "Pão francês" }]);
  const [recado, setRecado] = useState("");

  return (
    <form action={async (dados) => {
      const nome = String(dados.get("nome") || "").trim();
      if (!nome) return;
      try {
        await enviar(nome);
      } catch (e) {
        setRecado("Não enviado: sem estoque");
        return;
      }
      setRecado("");
      setPaes((atual) => [...atual, { nome: nome }]);
    }}>
      <input name="nome" />
      <button>Adicionar</button>
      <button type="button" id="recusar" onClick={() => responder && responder()}>
        servidor recusa
      </button>

      <ul>
        {paes.map((p) => (

}

Na prévia: dois itens enquanto a resposta não chega, um item depois da recusa — e nenhuma linha de código removendo o item. O catch só escreve o recado; quem tira a broa da tela é o fim da transição.

Isso muda o que você precisa testar. No esquema manual, dava para errar o desfazer e deixar um item fantasma na lista. Aqui, o risco é o contrário: esquecer o catch e a pessoa ver o item desaparecer sem explicação nenhuma. O try/catch continua obrigatório — não para desfazer, mas para contar o que aconteceu.

5. Onde a função pode ser chamada

Esta é a regra que faz o hook funcionar e a que mais gera erro de iniciante: a função que pede a atualização otimista só pode ser chamada dentro de uma transição — uma ação de formulário ou um startTransition. Fora disso, o React recusa na hora.

Uncaught Error: An optimistic state update occurred outside a transition or action. To fix, move the update to an action, or wrap with startTransition.

A mensagem é literal e diz o conserto: envolva em startTransition ou mova para uma ação. O motivo é que o hook precisa saber quando a aposta começou e quando terminou; sem uma transição, não existe intervalo para medir, e o estado otimista ficaria para sempre.

Por isso a ação de formulário é o lugar natural. Ela já roda dentro de uma transição, e o adicionar encontra o intervalo aberto. Quando você quer otimismo a partir de um clique — um botão “pagar”, por exemplo —, abre a transição na mão com startTransition.

Duas armadilhas vêm junto. A primeira: a função não pode ser chamada dentro de um efeito para “adiantar” o desenho; efeito não é transição. A segunda: uma chamada fora da transição não é ignorada em silêncio — ela quebra a renderização, e a página fica em branco. Se a sua tela sumiu depois de um clique, procure um adicionar solto no onClick.

6. Atualizar um item que já existe

Otimismo não é só acrescentar. O reducer recebe o estado real e o pedido, e pode devolver qualquer coisa: um item marcado como pago, um item com o texto editado, vários itens de uma vez. A caixa mostra a lista de encomendas da Ana com um botão “pagar” por linha.

O código inicial espera o servidor para marcar, e a linha fica “em aberto” durante a espera. A missão é marcar na hora, com a palavra “enviando” ao lado, e voltar ao normal quando o servidor responder. Aqui a transição abre no clique, com React.startTransition.

O pagamento só aparece depois da resposta. Use React.useOptimistic com um reducer que marque o item pelo id e React.startTransition no clique: a linha deve mostrar Maria: pago (enviando) antes de o servidor responder.

let responder = null;

function enviarPagamento() {
  return new Promise((ok) => {
    responder = () => ok();
  });
}

const encomendas = [
  { id: 1, cliente: "Maria", pago: false },
  { id: 2, cliente: "Joana", pago: true },
];

function App() {
  const [pedidos, setPedidos] = useState(encomendas);

  function pagar(id) {
    React.startTransition(async () => {
      await enviarPagamento();
      setPedidos((atual) =>
        atual.map((p) => (p.id === id ? { ...p, pago: true } : p))
      );
    });
  }

  return (
    <div>
      <ul>
        {pedidos.map((p) => (
          <li key={p.id}>
            {p.cliente + ": " + (p.pago ? "pago" : "em aberto")}
            {p.pago ? null : <button onClick={() => pagar(p.id)}>Pagar</button>}
          </li>
        ))}
      </ul>
      <button type="button" id="responder" onClick={() => responder && responder()}>
        servidor responde
      </button>
    </div>
  );
}

O map do reducer é o mesmo que você usaria no estado real: percorre, acha o item pelo id e devolve uma cópia com o campo trocado. A diferença é o enviando: true, que só existe na versão otimista — ele é a informação de que aquele item ainda não é verdade.

A chave continua sendo o id, e é isso que faz o React reaproveitar a linha em vez de recriá-la: o item otimista e o real são o mesmo item, com um campo diferente. Se você usasse o índice como chave, a lista funcionaria, mas qualquer reordenação no servidor trocaria o conteúdo das linhas.

7. Otimista não é mentira

Pintar antes de confirmar só é honesto se três coisas forem verdade. A primeira: o estado real é a fonte, e a ação sempre o atualiza no fim. Sem isso, o item otimista desaparece quando a transição fecha, e a pessoa vê o que acabou de criar evaporar.

A segunda: o item otimista precisa ser identificável. Use um id que exista nos dois lados — ou um texto único, como nas caixas. Se dois itens tiverem a mesma chave, o React avisa no console e escolhe um; a lista fica com menos linhas do que você escreveu.

A terceira: a tela precisa distinguir o provisório do definitivo. “(enviando)” não é enfeite — é o que permite à pessoa entender por que aquele item está diferente, e é o que evita a sensação de que a página mentiu se a resposta demorar. Sem a marca, o item parece definitivo e some sozinho alguns segundos depois.

O que o hook não resolve é o que depende do servidor: dois cliques rápidos geram duas apostas, e as duas aparecem. Se o envio é lento, desabilite o botão com o pendente da useTransition — o primeiro item do par — ou com o pendente da ação, como você viu na aula do useActionState.

O caso do “enviando para sempre” merece atenção. Se o pedido não tem tempo limite, uma rede ruim deixa a transição aberta indefinidamente — e enquanto ela está aberta, o estado otimista vale. A linha fica marcada como enviando até a pessoa recarregar a página. Um limite de alguns segundos, com rejeição, devolve a lista ao real e mostra o aviso.

9. Cenários do dia a dia

Cenário 1: o botão que aceitava dois cliques

A Ana deixou o botão “adicionar” habilitado durante o envio, e a cliente ansiosa clicou três vezes. A lista mostrou três broas enviando e, quando as respostas chegaram, uma delas voltou com “já existe”. O conserto foi o pendente da transição: disabled={pendente} enquanto a aposta está aberta. Um envio por vez, uma aposta por vez.

Cenário 2: o pedido que ficou pendurado

O servidor da padaria caiu no meio de um envio e a promessa nunca resolveu. A linha ficou “(enviando)” até a página ser recarregada — e a Ana só descobriu porque uma cliente reclamou. Ela passou a usar um tempo limite no pedido: depois de oito segundos, a promessa rejeita e a linha volta ao estado real com um aviso.

Cenário 3: o item que sumia ao confirmar

Ela chamou adicionar(nome), esperou a resposta e esqueceu o setPaes. A broa aparecia na hora e desaparecia três segundos depois — o pior dos dois mundos. O hook não tinha culpa: sem atualizar a fonte da verdade, o estado otimista é a única coisa que existia, e ele é temporário por definição.

11. Resumo

O useOptimistic devolve a lista que você desenha e uma função para pedir uma atualização antes da resposta. O reducer diz como aplicar o pedido por cima do estado real, que continua sendo a fonte da verdade. Quando a transição fecha, o estado otimista é descartado: se o servidor confirmou, o item já está no estado real; se recusou, ele simplesmente deixa de existir. O desfazer é automático.

A função só funciona dentro de uma ação de formulário ou de um startTransition — fora disso, o React lança “An optimistic state update occurred outside a transition or action”. Por isso a ação é o lugar natural, e o clique precisa abrir a transição na mão. Dentro da ação, a ordem é sempre: adicionar primeiro, espera depois, set do estado real no fim.

O reducer serve para mais do que acrescentar: com um map pelo id, você marca um item existente e sinaliza o provisório com um campo como enviando. Três condições mantêm o otimismo honesto: atualizar o estado real no fim, ter chave estável e mostrar na tela que o item ainda não é definitivo.

Com isso o trio do React 19 está completo: action para enviar sem estado paralelo, useActionState para o resultado voltar pela ação e useOptimistic para a tela responder antes do servidor. O próximo passo é o desempenho — medir antes de otimizar, para não trocar clareza por velocidade que ninguém sente.

Para lembrar

  • React.useOptimistic(estadoReal, reducer) devolve [lista, adicionar].
  • O estado real é a fonte; o otimista é uma projeção temporária dele.
  • A função só vale em ação de formulário ou startTransition.
  • Fim da transição: o otimista é descartado e o real assume — sem desfazer manual.
  • Ordem na ação: adicionar, await, set do estado real.
  • Reducer com map pelo id atualiza item existente.
  • Marque o provisório na tela: {p.enviando ? " (enviando)" : ""}.
  • Chave estável e um envio por vez (disabled={pendente}).
  • Sem tempo limite, a transição pode ficar aberta para sempre.
