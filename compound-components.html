Compound Components

As abas do site da Ana funcionam, mas cada pedaço foi escrito como se fosse independente: os botões sabem qual aba está ativa, os painéis não, e quando ela muda um, o outro continua mostrando a mesma coisa. Na aula de hoje ela aprende o padrão que resolve isso sem encher a tela de props: peças que moram dentro do componente pai — <Abas.Botao>, <Abas.Painel> — e conversam entre si por um canal que o pai cria e ninguém mais vê.

Você vai aprender
  • O que é um componente composto e por que a API dele parece uma família.
  • Como prender subcomponentes ao pai com Cartao.Titulo = Titulo.
  • Como as peças compartilham estado por um contexto criado dentro do pai.
  • Por que esse contexto é privado e não deve ser exportado.
  • Por que uma peça usada fora do pai simplesmente não aparece.
  • Quando o padrão ajuda e quando ele só esconde props atrás de pontos.
  • Os tropeços: peça esquecida, peça fora do pai, filhos demais e listas de peças.

1. A cena: um cartão copiado e duas abas desencontradas

A página de produtos da Ana tem cartões. Cada cartão é um quadrado com o nome do pão, o preço e um selinho "Padaria da Ana" no canto. Ela escreveu o primeiro à mão, copiou para o segundo e para o terceiro, e no dia em que quis mudar o selo de lugar precisou mexer em três lugares. Até aí, é a história da aula de componente reutilizável: extraia uma função.

O problema é que o cartão não é uma coisa só. Ele tem partes que variam de forma independente: o título pode ser um h3 ou um h2, o corpo pode ter preço, descrição ou um botão. Se você transformar tudo em props — <Cartao titulo="Baguete" preco="2,00" descricao="..." botao="..." /> — o componente vira um formulário de opções e perde a graça. Componente composto é a terceira via: o pai desenha a moldura, e o leitor do componente escreve as partes por dentro.

As abas têm o mesmo desenho e um desafio a mais. Um botão de aba e o painel correspondente são irmãos na árvore, e precisam concordar sobre qual aba está ativa. Irmãos não conversam por prop. No padrão composto, o pai — o <Abas> — guarda o estado e oferece um canal para os filhos lerem, sem que quem usa o componente veja esse canal.

2. Uma família com sobrenome

Um componente composto é um componente com peças acopladas. Você o usa como um bloco e escreve as partes internas com um ponto no nome: Cartao.Titulo, Abas.Painel. Por baixo, cada peça é um componente comum, preso ao pai como uma propriedade qualquer — porque em JavaScript função também tem propriedade.

componente composto
O pai que desenha a moldura e guarda o estado compartilhado. Cartao, Abas.
peça
Um subcomponente preso ao pai por atribuição: Cartao.Titulo = Titulo. Usa-se <Cartao.Titulo>.
children
O que fica entre a abertura e o fechamento do pai. É por aí que as peças entram no desenho: {children}.
contexto interno
O canal criado pelo pai para as peças lerem o estado comum. Fica no mesmo arquivo e não é exportado.
API
O conjunto de peças e props que o componente oferece. No composto, a API é a lista de nomes depois do ponto.
escopo
A região da árvore em que o canal do pai vale. Fora dela, a peça não encontra nada — e é isso que a terceira caixa mostra.

A primeira vista, o ponto no nome parece decoração. Ele é informação: dizer <Cartao.Titulo> em vez de <TituloDoCartao> avisa que aquela peça não funciona sozinha. O leitor do seu componente não precisa importar quatro coisas; importa uma e encontra as outras dentro dela, como pastas.

3. As peças que moram dentro do pai

Vamos ao cartão. As três funções já existem no arquivo: Titulo, Corpo e Cartao. O que falta é o casamento — prender as duas primeiras ao pai — e trocar o HTML escrito à mão pelos componentes. No código inicial, os dois cartões são div com classes copiadas, e o selo que o Cartao sabe desenhar não aparece em lugar nenhum.

Prenda as peças ao pai com Cartao.Titulo = Titulo; e Cartao.Corpo = Corpo; e reescreva os dois cartões usando <Cartao>, <Cartao.Titulo> e <Cartao.Corpo>. Os dois cartões têm de ganhar o selo.

function Titulo({ children }) {
  return <h3 className="cartao-titulo">{children}</h3>;
}

function Corpo({ children }) {
  return <div className="cartao-corpo">{children}</div>;
}

function Cartao({ children }) {
  return (
    <article className="cartao">
      <span className="selo">Padaria da Ana</span>
      {children}
    </article>
  );
}

function App() {
  return (

        <h3 className="cartao-titulo">Baguete</h3>
        <div className="cartao-corpo">R$ 2,00</div>
      </div>
      <div className="cartao">
        <h3 className="cartao-titulo">Pão de queijo</h3>
        <div className="cartao-corpo">R$ 3,50</div>

Repare no que o painel mostra: cada cartão virou um article com o selo dentro, e o título e o corpo continuam sendo as peças. Quem escreve o App não precisa saber que existe um selo; quem cuida do selo é o Cartao, num lugar só. Se amanhã a Ana quiser o selo embaixo, muda uma linha no pai e os dez cartões do site acompanham.

As duas linhas de atribuição são o coração do padrão, e valem três observações. Primeira: elas ficam fora das funções, no nível do arquivo, e rodam uma vez, quando o módulo carrega. Segunda: a ordem não importa, porque as funções são declaradas com function e existem antes de qualquer linha rodar. Terceira: se você esquecer uma delas, Cartao.Titulo é undefined, e o React não sabe desenhar undefined — o componente inteiro some da tela, sem erro visível no painel. No console do navegador aparece a mensagem da qual a aula fala mais adiante.

Um detalhe de organização: num projeto, cada peça pode ficar num arquivo e o pai importar todas para montar a API. O arquivo do pai vira o índice da família:

import Titulo from "./CartaoTitulo";
import Corpo from "./CartaoCorpo";

function Cartao({ children }) {
  return <article className="cartao">{children}</article>;
}

Cartao.Titulo = Titulo;
Cartao.Corpo = Corpo;

export default Cartao;

Quem usa escreve import Cartao from "./Cartao" e ganha a família inteira. Quem lê o arquivo do pai vê, em quatro linhas, quais peças existem. Essa é a vantagem de descoberta que o ponto no nome oferece: o autocompletar do editor lista Cartao. e mostra as peças disponíveis.

4. O estado que as peças compartilham

O cartão não tem estado: as peças só desenham o que recebem. As abas têm, e é aí que o padrão mostra o segundo mecanismo. O <Abas> guarda qual aba está ativa; os botões precisam saber para se destacar, os painéis precisam saber para aparecer. Nenhum dos dois recebe essa informação por prop de quem usa o componente — ela vem de um contexto que o pai cria.

No código inicial, o Abas tem o estado, mas não o publica: o div das abas é desenhado sem provider. As peças caem no valor padrão do contexto, que é um objeto fixo com setAtiva vazio. Resultado: os botões não trocam nada, o painel de pães fica para sempre, e clicar em "Salgados" não faz nada. A missão é envolver os filhos no provider.

O Abas guarda ativa e não publica. Envolva {children} em <AbaContexto.Provider value={{ ativa, setAtiva }}> e clique em "Salgados".

const AbaContexto = createContext({ ativa: "paes", setAtiva: () => {} });

function Abas({ children }) {
  const [ativa, setAtiva] = useState("paes");

  return <div className="abas">{children}</div>;
}

function BotaoAba({ nome, children }) {
  const { ativa, setAtiva } = useContext(AbaContexto);
  return (
    <button id={"aba-" + nome} aria-selected={ativa === nome} onClick={() => setAtiva(nome)}>
      {children}
    </button>
  );
}

function PainelAba({ nome, children }) {
  const { ativa } = useContext(AbaContexto);
  if (ativa !== nome) return null;
  return <div className="painel">{children}</div>;
}

Abas.Botao = BotaoAba;
Abas.Painel = PainelAba;

function App() {
  return (
    <Abas>
      <Abas.Botao nome="paes">Pães</Abas.Botao>
      <Abas.Botao nome="salgados">Salgados</Abas.Botao>
      <Abas.Painel nome="paes">Baguete e pão de queijo</Abas.Painel>
      <Abas.Painel nome="salgados">Coxinha e empada</Abas.Painel>
    </Abas>
  );
}

O ponto que faz o padrão ser composto e não só "dois componentes": quem usa não passa ativa nem onMudar. O App escreve as peças como se fossem HTML e o canal acontece por baixo. A informação de qual aba está ativa nunca aparece no JSX de fora — ela vive no pai, é publicada para as peças e morre ali dentro.

O preço dessa conveniência é o acoplamento: as peças só funcionam dentro do pai. Isso não é um acidente, é o desenho. Um Abas.Painel solto no meio da página não tem como saber qual aba está ativa, porque o estado está no pai que ele não tem. Na prática, ele lê o valor padrão do contexto e obedece a ele — que é o que a próxima caixa mostra.

5. O contexto interno é privado

O AbaContexto é criado no mesmo arquivo das peças e não é exportado. Essa decisão de projeto tem nome — encapsulamento — e três consequências práticas. A primeira: ninguém de fora pode abastecer o canal por conta própria, então o estado das abas tem um dono só. A segunda: você pode mudar o formato do valor (incluir total, indice, o que for) sem quebrar nenhum consumidor externo, porque não existe consumidor externo.

A terceira consequência é a que resolve o problema do início da aula: as peças não precisam receber ativa por prop de quem usa. Elas leem do canal. Se cada peça recebesse a prop, quem usasse o componente teria de repetir o valor em quatro lugares — e esquecer um deles é a receita do bug que a Ana tinha.

Um hábito que vale criar: peça sempre um objeto no valor do contexto, mesmo quando há um valor só. Objeto permite crescer sem quebrar as peças; valor solto obriga a mudar todas as leituras no dia em que aparecer o segundo dado. E, como toda leitura de contexto, quem lê recebe o valor inteiro e é redesenhado quando ele muda de identidade — assunto da aula de introdução ao contexto.

6. A peça fora do pai não aparece

O erro mais comum de quem usa componente composto é posto assim: o painel simplesmente não aparece. Não há erro vermelho, não há aviso no painel; a área fica vazia. A causa quase sempre é a mesma: a peça foi colocada fora do pai, e sem o pai não existe canal. Abaixo, o painel de salgados ficou depois do fechamento do <Abas>.

O <Abas.Painel nome="salgados"> está fora do <Abas> e nunca encontra o canal. Mova-o para dentro do <Abas> e clique em "Salgados".

O sintoma é curioso porque acontece em duas etapas. Antes do clique, o painel órfão não aparece e ninguém sente falta — o painel de pães está lá, ocupando o espaço. Depois do clique em "Salgados", os dois painéis desaparecem: o de pães porque deixou de ser o ativo, o de salgados porque nunca esteve dentro. A área fica vazia, que é a assinatura do problema de escopo.

Quando o problema é uma peça undefined — por esquecimento da atribuição —, o React reclama no console do navegador, e a mensagem vale conhecer:

Warning: React.jsx: type is invalid -- expected a string (for built-in components) or a class/function (for composite components) but got: undefined.

Em produção, essa mesma falha aparece como "Minified React error #130" com um link para a documentação. É o mesmo erro: uma peça que não existe. A leitura é sempre "confira a atribuição depois das funções".

Ao mesmo tempo, um console.log dentro do pai conta a história do que aconteceu antes:

Abas desenhou: ativa = paes
BotaoAba salgados leu: paes
PainelAba salgados: fora do canal (valor padrão)

A segunda linha mostra o botão lendo "paes" — porque o pai publicava o valor padrão, não o estado. A terceira, o painel órfão. Duas leituras do mesmo canal, dois valores diferentes: é assim que um contexto mal posicionado se denuncia.

7. Composto ou props?

Os dois jeitos resolvem o mesmo problema de reúso, e a escolha depende da forma do componente. Props funcionam bem quando as partes são dados: titulo, preco, cor. Composto funciona bem quando as partes são estrutura: um pedaço de JSX que quem usa decide, com tags, classes e componentes próprios dentro.

SituaçãoPropsComposto
o conteúdo é texto ou númerosim: titulo="Baguete"não vale a cerimônia

Uma heurística que funciona: se você já escreveu <Cartao><h3>… no projeto, você já está usando composição — o composto só dá nomes às partes. E se o componente tem mais de cinco peças, ou peças que só fazem sentido em pares (Titulo obrigatório, Corpo obrigatório), talvez props sejam mais honestas: um composto com muitas regras de uso é um quebra-cabeça disfarçado de API.

Existe um meio-termo muito comum: o pai aceita as duas formas. <Cartao titulo="Baguete"> para o caso simples e <Cartao><Cartao.Titulo> para o caso com JSX dentro. Custa um if no pai e evita obrigar quem só quer um cartão simples a escrever quatro tags.

8. Os tropeços

O primeiro é esquecer a atribuição: você exporta Titulo e usa Cartao.Titulo, que não existe. O sintoma é uma tela em branco no meio de um componente que parecia certo, e o console com a mensagem de tipo inválido. A conferência é rápida: as linhas Pai.Peça = Peça; estão logo depois das funções?

O segundo é usar a peça fora do pai — o caso da caixa anterior. Vale um aviso de projeto: se você perceber que a peça é usada fora com frequência, o padrão está errado para o seu caso; talvez o componente devesse receber o estado por prop e ser controlado de fora, como qualquer outro.

O terceiro é o children com peças demais. O pai precisa saber separar os botões dos painéis para desenhar a barra e a área; se ele só faz {children}, a mistura fica na ordem em que você escreveu. Em geral isso é bom — a ordem é sua —, mas o layout fica sem controle. A saída é pedir peças de agrupamento (<Abas.Lista> e <Abas.Conteudo>) ou deixar o CSS resolver com classes nas peças.

O que você vêCausa provávelConserto

Há um quarto caso que merece um parágrafo: listas de peças. Se você desenha as abas com map, cada peça precisa de key, como qualquer item de lista. O key é da peça e não do pai; esquecê-lo não quebra o desenho, mas cria aquele comportamento de estado trocado entre itens no dia em que a ordem mudar. As duas regras se somam: key para o React identificar a peça, contexto para a peça achar o estado.

9. Cenários do dia a dia

Cenário 1: o menu de ações

A lista de pedidos tem um menu de três pontinhos em cada linha, com "Ver", "Editar" e "Cancelar". O <Menu> composto guarda o estado de aberto, fecha ao clicar fora e posiciona a caixa; as peças <Menu.Item> só recebem o onClick. O menu controla a si mesmo, e cada item é uma ação diferente escrita por quem usa. Sem props para "quais itens existem", o componente não envelhece a cada ação nova.

Cenário 2: a tabela com colunas

O relatório de vendas tem <Tabela>, <Tabela.Cabecalho> e <Tabela.Linha>. As colunas são decididas por quem usa, com os componentes de célula que fizerem sentido. O pai cuida do que é chato e igual em toda tabela: borda, rolagem, alinhamento. É o caso em que o padrão brilha, porque as partes são estrutura e não dado.

Cenário 3: o formulário com erro por campo

<Campo>, <Campo.Rotulo> e <Campo.Erro> compartilham um id gerado pelo pai, para que o rótulo aponte para o campo certo e o erro seja anunciado pelo leitor de tela. O estado do valor, esse sim, mora em quem usa o formulário — o composto cuida da acessibilidade e da montagem, não do dado. Misturar os dois cuidados num componente só costuma dar confusão.

11. Resumo

Componente composto é um pai com peças: o pai desenha a moldura, guarda o estado comum e publica esse estado num contexto interno; as peças leem o canal e desenham a parte que lhes cabe. Quem usa escreve <Abas.Botao> e <Abas.Painel> como se fossem tags, sem passar o estado por prop. O ponto no nome é a assinatura do padrão: aquela peça pertence àquela família.

As duas linhas que fazem tudo funcionar são a atribuição (Pai.Peça = Peça;) e o provider dentro do pai. Esquecer a primeira dá tela em branco com erro de tipo inválido; esquecer o segundo faz as peças caírem no valor padrão do canal — e o sintoma é um botão que não muda nada. Usar a peça fora do pai dá o sintoma mais silencioso de todos: nada aparece, e nada reclama.

O padrão não é para tudo. Ele brilha quando as partes são estrutura e precisam compartilhar estado; atrapalha quando o componente é só um punhado de dados, que props resolvem melhor. E vale lembrar do custo escondido: uma API com muitos nomes depois do ponto é difícil de descobrir sem documentação. Se quem usa precisa abrir o código para saber quais peças existem, o composto virou adivinhação.

Para lembrar

  • Composto = pai + peças: <Abas.Botao>, <Abas.Painel>.
  • As peças se prendem ao pai por atribuição, fora das funções.
  • O pai renderiza {children}; as peças entram por aí.
  • O estado comum mora no pai e é publicado num contexto interno.
  • Esse contexto não se exporta: é detalhe de implementação.
  • Peça usada fora do pai não encontra o canal e cai no valor padrão.
  • Peça undefined dá erro de tipo inválido no console.
  • Peças em lista precisam de key, como qualquer item.
  • Partes que são dados pedem props; partes que são estrutura pedem peças.
  • Muitas peças e muitas regras: o padrão virou um quebra-cabeça.
