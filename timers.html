Timers

O forno da Ana não avisa quando o pão fica pronto, e o relógio da vitrine não anda sozinho. As duas coisas dependem de tempo, e tempo em React não é estado: é o navegador contando. Nesta aula ela liga o setTimeout e o setInterval de dentro de um efeito, descobre por que o contador trava em 1 quando ela usa setRestam(restam - 1) e aprende a pausar e a desligar sem deixar timer fantasma.

Você vai aprender
  • O que setTimeout e setInterval fazem e por que não são do React.
  • Onde criar um timer: dentro do efeito, nunca no corpo do componente.
  • Como mostrar um aviso que só aparece depois de um tempo.
  • Como fazer um contador subir sozinho e parar no fim.
  • Por que setRestam(restam - 1) trava o contador, e por que a forma funcional resolve.
  • Como pausar e continuar com o timer nas dependências do efeito.
  • O que os timers não prometem: precisão de milissegundo e ordem exata.

1. A cena: o pão que assa sozinho

A padaria da Ana tem um forno elétrico com timer mecânico, daqueles que fazem "tic" e desligam no fim. No site, o equivalente seria um componente que mostra "esperando o forno…" e, depois de alguns minutos, troca para "Pão pronto!". Não é um clique do cliente, não é uma resposta do servidor: é o tempo passando. E o tempo passa sem que o React faça nada.

É aí que nasce a confusão. Em React, a tela só muda quando o estado muda. O React não fica olhando o relógio para saber se já passou tempo; ele desenha quando tem motivo. Então, para uma tela mudar com o tempo, alguém precisa avisar: um timer do navegador chama uma função sua, você atualiza o estado, e o React desenha de novo. O tempo não é estado; o resultado do tempo é estado.

A segunda cena é o relógio da vitrine, que mostra a hora e atualiza a cada segundo. Aqui o timer é repetido, um setInterval. E com ele vem o problema mais instrutivo da aula: o timer guarda uma "foto" do estado do momento em que foi criado, e essa foto envelhece. Quem escreve setRestam(restam - 1) dentro do intervalo vê o contador parar de descer depois do primeiro tique — e passa meia hora procurando o culpado.

2. O que são timers e por que não são do React

setTimeout recebe uma função e um número de milissegundos e chama a função uma vez, depois desse tempo. setInterval faz o mesmo, mas repetindo até alguém mandar parar. Os dois devolvem um número (o id do timer), que é o que você usa para cancelar com clearTimeout ou clearInterval.

setTimeout
Chama a função uma vez, depois do tempo: setTimeout(() => avisar(), 3000). Devolve o id.
setInterval
Chama a função repetidamente, a cada intervalo: setInterval(() => tique(), 1000). Devolve o id.
id do timer
O número que identifica o timer para cancelar. Guarde em uma constante do efeito.
clearTimeout/clearInterval
Cancelam o timer pelo id. Sem isso, ele dispara de qualquer jeito.
closure
O "pacote" de variáveis que a função do timer carrega do momento em que foi criada. É de onde vem o valor velho.

Nenhum dos dois é do React: são funções do navegador, como document e fetch. O React não sabe que eles existem, não pausa quando o componente sai da tela e não reinicia quando ele volta. Se você criar um intervalo e não desligar, ele continua chamando a sua função — e a lição da aula de cleanup é exatamente essa: quem cria, desfaz.

Uma consequência prática: os timers contam tempo real, não tempo de render. Um intervalo de 1000 ms dispara aproximadamente a cada segundo, mesmo que a tela esteja travada processando outra coisa. E se a aba estiver escondida, o navegador pode atrasar os timers de propósito, para economizar bateria. Nada disso é problema do React; é o comportamento do navegador, e é bom saber para não caçar bug no lugar errado.

3. O timer no lugar certo

O corpo do componente roda a cada render. Se você criar um timer ali, cada render cria mais um — e eles se acumulam, cada um chamando a sua função. Em dois cliques, dois timers; em dez, dez. Por isso o timer vai dentro de um useEffect, e o efeito decide quantos existem.

function Aviso() {
  useEffect(() => {
    const id = setTimeout(() => console.log("pão pronto"), 3000);

    return () => clearTimeout(id);
  }, []);

  return <p>Esperando o forno…</p>;
}

Três decisões aparecem nesse trecho. A primeira é criar o timer dentro do efeito, não no corpo. A segunda é guardar o id em uma constante, para a limpeza conseguir cancelar. A terceira é o []: o efeito roda uma vez, então existe exatamente um timer, criado na montagem e cancelado na desmontagem.

Se o efeito tivesse uma dependência, o timer seria recriado quando ela mudasse — e a limpeza cancelaria o anterior antes de criar o novo. É esse par que permite coisas como "recomeçar a contagem quando o pão mudar" sem acumular intervalos. O efeito é o dono do timer; a limpeza é o que garante que o dono anterior saiu de cena.

4. O aviso que chega depois

A primeira caixa tem um aviso que deveria trocar sozinho: começa em "esperando o forno…" e vira "Pão pronto!" quando o tempo passa. Falta justamente o timer. A missão é criá-lo dentro do efeito, com a limpeza no lugar.

Use setTimeout dentro do efeito para trocar o aviso por Pão pronto! depois de 20 milissegundos. Guarde o id e devolva o clearTimeout na limpeza.

function App() {
  const [aviso, setAviso] = useState("esperando o forno…");

  return (
    <div>
      <h1>Padaria da Ana</h1>
      <p>{aviso}</p>
    </div>
  );
}

  useEffect(() => {
    const id = setTimeout(() => setAviso("Pão pronto!"), 20);

  }, []);

  return (

O aviso mudou porque o timer chamou setAviso, e o set pediu um novo render. Sem o set, o timer poderia disparar mil vezes e a tela não mudaria — o React não desenha por força do tempo, desenha porque o estado mudou.

Os 20 milissegundos são de propósito: no painel, o resultado aparece na hora. No site da Ana, o mesmo código teria 3000 no lugar do 20. O código é idêntico; só o número muda. E se você deixar o timer sem limpeza, nada quebra visivelmente quando a tela fica aberta — o problema aparece quando o componente sai antes do tempo e a função roda em um componente que já não está lá.

5. O relógio que anda sozinho

Para repetir, é setInterval. O desenho é o mesmo do setTimeout: criar dentro do efeito, guardar o id, cancelar na limpeza. A diferença é o que a função do intervalo faz. No relógio da vitrine, ela atualiza a hora a cada segundo:

useEffect(() => {
  const id = setInterval(() => {
    setHora(new Date().toLocaleTimeString("pt-BR"));
  }, 1000);

  return () => clearInterval(id);
}, []);

Aqui o intervalo não lê nenhum estado: ele cria a hora a partir do relógio do sistema, e o setHora guarda o texto pronto. Como a função não depende de nada que mude, ela não sofre do problema de valor velho que vem a seguir. É quando o intervalo precisa ler o estado para calcular o próximo que a armadilha aparece.

A Ana escreveu um contador de pães no forno: começa em 3 e desce a cada tique. Ela fez setRestam(restam - 1), que é como ela escreve em qualquer outro lugar do componente. Rodou e o número foi para 2 e parou. O intervalo continuou rodando, chamando a função, mas o valor não descia mais.

O motivo é a closure. A função do intervalo foi criada no primeiro render, quando restam valia 3. Ela carrega esse 3 para sempre: a cada tique, calcula 3 - 1 e chama setRestam(2). O estado já é 2, então o React entende "não mudou nada" e nem redesenha. O timer está certo; a conta é que está usando uma foto velha.

O console acima é o que a Ana viu, com um console.log dentro do intervalo: a mesma linha, repetida, sem fim. O conserto é pedir o valor atual ao React em vez de usar o da closure, com a forma funcional do set:

setInterval(() => {
  setRestam((r) => Math.max(0, r - 1));   // r é o valor mais recente
}, 1000);

O contador desce uma vez e para, porque a função do intervalo usa o restam da primeira renderização. Troque por setRestam((r) => Math.max(0, r - 1)) para o pão chegar a zero e o forno apitar.

function App() {
  const [restam, setRestam] = useState(3);

  useEffect(() => {
    const id = setInterval(() => {
      setRestam(restam - 1);
    }, 10);
    return () => clearInterval(id);
  }, []);

  return (
    <div>
      <h1>Padaria da Ana</h1>
      <p>Restam {restam} pães no forno</p>
      {restam === 0 && <p>Forno apitou!</p>}
    </div>
  );
}

6. Por que a forma funcional funciona

setRestam((r) => Math.max(0, r - 1)) é diferente de setRestam(restam - 1) em um ponto essencial: você não passa o valor novo, passa uma função que calcula o valor novo a partir do atual. Quem chama essa função é o React, no momento de aplicar a atualização, com o valor mais recente em mãos. O r nunca é uma foto velha; é o estado de agora.

Isso não é um detalhe só de timers. Em qualquer lugar onde o valor novo depende do antigo — um clique duplo rápido, duas atualizações na mesma função, um intervalo —, a forma funcional é a segura. O Math.max(0, ...) é só para o número não ficar negativo enquanto o intervalo continua rodando depois de chegar a zero; o set com uma função pode ser chamado quantas vezes for, que 0 continua sendo o piso.

FormaDe onde vem o valorQuando travar

Repare que o problema não é o setInterval — é a combinação de "função criada uma vez" com "valor que muda". Um timer criado uma vez sempre carrega a foto do primeiro render. Se a função só usa valores fixos, não há problema. Se ela lê qualquer estado, use a forma funcional ou inclua esse estado nas dependências do efeito (o que recria o timer a cada mudança e tem o seu próprio custo).

7. Pausar, continuar e desmontar

A terceira caixa tem um timer que anda em etapas e um botão de pausar. O botão já muda o estado correndo, e o efeito já tem correndo nas dependências — mas ninguém desliga o intervalo antigo. Ao pausar, o efeito deixa de criar um novo, e o antigo continua contando. É o mesmo vazamento da aula de cleanup, agora com um nome.

Ao pausar, o intervalo antigo continua rodando. Guarde o id e devolva uma função de limpeza que faz clearInterval(id) e anota parei de contar no caderninho. Depois clique em Pausar.

function App() {
  const etapas = ["massando", "modelando", "no forno", "pronto"];
  const [etapa, setEtapa] = useState(0);
  const [correndo, setCorrendo] = useState(true);
  const [registro, setRegistro] = useState([]);

  useEffect(() => {
    if (!correndo) return;
    setRegistro((r) => [...r, "comecei a contar"]);
    setInterval(() => {
      setEtapa((e) => Math.min(e + 1, etapas.length - 1));
    }, 10);
  }, [correndo]);

  return (
    <div>
      <p>Etapa do pão: {etapas[etapa]}</p>
      <button onClick={() => setCorrendo(!correndo)}>
        {correndo ? "Pausar" : "Continuar"}
      </button>
      <ul>
        {registro.map((m, i) => (
          <li key={i}>{m}</li>
        ))}
      </ul>
    </div>
  );
}

function App() {
  const etapas = ["massando", "modelando", "no forno", "pronto"];
  const [etapa, setEtapa] = useState(0);
  const [correndo, setCorrendo] = useState(true);
  const [registro, setRegistro] = useState([]);

  useEffect(() => {
    if (!correndo) return;
    setRegistro((r) => [...r, "comecei a contar"]);
    const id = setInterval(() => {
      setEtapa((e) => Math.min(e + 1, etapas.length - 1));
    }, 10);

    return () => {
      clearInterval(id);
      setRegistro((r) => [...r, "parei de contar"]);
    };
  }, [correndo]);

  return (
    <div>
      <p>Etapa do pão: {etapas[etapa]}</p>
      <button onClick={() => setCorrendo(!correndo)}>
        {correndo ? "Pausar" : "Continuar"}
      </button>
      <ul>
        {registro.map((m, i) => (
          <li key={i}>{m}</li>
        ))}
      </ul>
    </div>
  );
}

O caderninho mostra "comecei a contar" na montagem e ganha "parei de contar" no clique — a prova de que a limpeza rodou. O if (!correndo) return; é a outra metade: quando a contagem está pausada, o efeito não cria timer nenhum. Sem essa linha, pausar criaria um timer e continuar criaria outro, os dois rodando.

Repare também que a limpeza não precisa saber se o timer existe. Quando correndo é false, o efeito devolve undefined e o React não tem nada para chamar. Só que a limpeza da execução anterior — aquela em que o timer foi criado — ainda está guardada e roda normalmente. É o React guardando um par (efeito, limpeza) por execução, como você viu na aula de cleanup.

8. Os tropeços com timers

O primeiro é criar o timer no corpo do componente. Cada render cria mais um, e cliques rápidos multiplicam os intervalos. O sintoma é uma contagem que acelera sozinha com o tempo: um timer, dois, três, cada um somando ao mesmo estado.

O segundo é não guardar o id. Sem ele não há como cancelar, e a única saída é deixar o timer rodando até o fim da aba. Guardar em uma constante dentro do efeito é o que permite a limpeza usar o mesmo valor.

O terceiro é esperar precisão. O número em setTimeout(f, 1000) é um pedido, não uma promessa: o navegador pode atrasar por estar ocupado, por economia de energia ou por a aba estar escondida. Para um cronômetro de verdade, quem conta é o relógio, não a soma dos tiques.

tique 1: 10 ms
tique 2: 21 ms
tique 3: 33 ms

Essas são as medidas de um intervalo pedido a cada 10 ms: os tiques chegam um pouco depois do pedido, e o atraso varia. Se o seu cronômetro soma 1 a cada tique e multiplica por 1000, em cinco minutos ele está errado. A forma certa é guardar o instante de início e calcular a diferença com Date.now().

O quarto é o setTimeout(f, 0). Ele não roda na hora: roda depois que o navegador terminar o que está fazendo, no próximo ciclo. Isso é útil para "esperar um instante" e é a razão pela qual setTimeout com zero às vezes aparece em código de animação e de foco de campo. Zero não é imediato; é "logo depois".

9. Cenários do dia a dia

Cenário 1: o contador que anda mais rápido depois de dois cliques

Cada clique que recria o efeito sem limpeza deixa um intervalo antigo rodando. Com dois intervalos somando no mesmo estado, a contagem dobra de velocidade — e com três, triplica. É o vazamento clássico de timer, e o conserto é sempre o mesmo: guardar o id e cancelar na limpeza.

Cenário 2: a contagem continua depois que o cliente saiu da tela

O componente sumiu da página e o intervalo continuou chamando setEtapa. Em React 19 isso não gera mais aviso no console; o estado é atualizado em um componente que ninguém vê. O sintoma aparece depois, quando o componente volta e começa com um número estranho. A limpeza na desmontagem resolve.

Cenário 3: o botão de continuar cria dois relógios

A Ana escreveu o efeito sem o if (!correndo) return;. Ao pausar, a limpeza cancelou o timer; ao continuar, a limpeza rodou de novo (nada a cancelar) e um timer novo foi criado — correto. Mas se ela tivesse esquecido a limpeza, cada pausa deixaria um relógio rodando, e continuar somaria mais um. Com o par certo, o número de timers é sempre zero ou um.

Exercício: parando o intervalo

Complete a função de limpeza que cancela o intervalo criado no efeito:

return () => (id);

Dica: é o par do setInterval, com o id que o efeito guardou. Sem ele, o intervalo continua depois que o componente sai da tela.

11. Resumo

setTimeout chama uma função uma vez depois do tempo; setInterval chama repetidamente. Os dois são do navegador, devolvem um id e não são cancelados pelo React — quem cancela é você, com clearTimeout ou clearInterval. O lugar de criar é dentro de um useEffect, e o lugar de cancelar é a função que o efeito devolve.

Para mudar a tela com o tempo, o timer chama um set; é o estado que manda o React desenhar de novo. E quando o valor novo depende do anterior, use a forma funcional: setN((n) => n + 1). A função do timer carrega a foto do render em que nasceu, e essa foto não se atualiza sozinha.

Com timers, você tem as quatro peças do assunto: criar no efeito, guardar o id, atualizar o estado com a forma funcional e limpar quando o componente muda ou sai. A partir daqui, o próximo passo natural é guardar coisas no navegador — o assunto da aula O localStorage, que usa o mesmo formato de efeito com limpeza.

Para lembrar

  • setTimeout: uma vez. setInterval: repetido. Os dois devolvem um id.
  • Timer se cria dentro do useEffect, nunca no corpo do componente.
  • Guarde o id para poder cancelar com clearTimeout/clearInterval.
  • Devolva a limpeza: return () => clearInterval(id).
  • Função do timer lê o estado da foto em que nasceu: use setN((n) => n + 1).
  • Pausar é mudar uma dependência e limpar o timer antigo.
  • if (!correndo) return; evita criar timer quando não deve haver nenhum.
  • Timers não são precisos: para cronômetro, calcule com Date.now().
  • setTimeout(f, 0) não é imediato: é "logo depois".
  • Abas escondidas atrasam timers de propósito, para economizar bateria.
