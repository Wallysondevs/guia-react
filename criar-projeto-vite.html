O Projeto com Vite

A Ana já criou um projeto com o Vite uma vez, seguindo a receita. Agora ela vai abrir uma segunda vitrine e quer entender o que responde no assistente: React com JavaScript ou TypeScript? O que é SWC? Por que o servidor abre em 300 milissegundos enquanto o build demora? O que exatamente existe dentro do vite.config.js? Nesta aula ela olha para a ferramenta em vez de só usá-la.

Você vai aprender
  • O que o npm create vite@latest faz antes de fazer qualquer pergunta.
  • Qual variante escolher e o que muda entre React, React + TypeScript e React + SWC.
  • Como o servidor de desenvolvimento serve JSX sem empacotar tudo antes.
  • O que o HMR preserva — e quando ele perde o estado de qualquer jeito.
  • O que escrever no vite.config.js: plugins, porta, host e saída do build.
  • Por que o endereço localhost não abre no celular e o que fazer para abrir.

1. A cena: o segundo projeto e as perguntas do assistente

O primeiro projeto da Ana nasceu com um tutorial ao lado: ela respondeu "React", "JavaScript" e apertou enter sem pensar. Funcionou. Agora ela quer uma vitrine separada, para as encomendas de festa, e o assistente faz perguntas que ela não sabe responder — algumas versões nem perguntam nada, outras oferecem "React + SWC", e ela não quer descobrir no meio do caminho que escolheu errado.

O Vite não é uma caixa-preta: ele é um programa que copia arquivos e outro que serve a página. A primeira parte roda uma vez; a segunda, todo dia. Entender a diferença resolve a maior parte das dúvidas de quem começa — inclusive a mais comum, "por que meu projeto não tem um webpack.config.js?".

2. O que o comando faz antes de perguntar

npm create vite@latest é uma forma abreviada de baixar e rodar o pacote create-vite. O npm baixa esse pacote para o cache, executa o assistente no terminal e, no fim, copia para a pasta escolhida um conjunto de arquivos de partida — o template. Nada de mágica: são arquivos de texto comuns, que você pode abrir e editar. O que o comando não faz é instalar as dependências; isso continua sendo um npm install depois.

Existe uma forma sem perguntas, ótima para quando você já sabe o que quer (e obrigatória em automação): passar o nome do projeto e o template de uma vez, com dois traços antes da opção. O -- separa as opções do npm das opções do programa que ele está rodando.

$ npm create vite@latest vitrine -- --template react

Scaffolding project in /home/ana/estudos/vitrine...

Done. Now run:

  cd vitrine
  npm install
  npm run dev

A mensagem final é literalmente a receita dos próximos três passos. Se você esquecer, ela está lá — e também no README.md que o template escreve. O que costuma confundir é o nome: o comando cria uma pasta chamada vitrine. Se você rodar dentro de uma pasta que já tem arquivos, o assistente avisa e oferece continuar na pasta atual ou cancelar.

3. Escolhendo o modelo

O template é o ponto de partida: quais arquivos nascem, com qual extensão e com qual configuração. A pergunta do assistente tem duas partes — framework e variante. Para React, as variantes que aparecem hoje são quatro, e a diferença é menor do que parece.

VarianteExtensõesQuando escolher
React.jsxo padrão para quem está começando; JSX com JavaScript
React + TypeScript.tsxquando você já sabe TypeScript ou o time exige tipos
React + SWC.jsxmesmo resultado do padrão, com outro compilador (mais rápido)
React + SWC + TypeScript.tsxa combinação das duas escolhas anteriores

SWC é um compilador escrito em Rust que faz o mesmo trabalho do Babel, só que mais rápido. No desenvolvimento a diferença é pequena; em projetos grandes, ela aparece. Para aprender React, tanto faz — o código que você escreve é idêntico. TypeScript é outra história: ele acrescenta tipos, e tipo errado vira erro antes de a página abrir. É uma boa ferramenta e uma péssima segunda coisa para aprender junto com a primeira.

O projeto foi criado com TypeScript sem querer: os arquivos são .tsx. Troque a escolha para o template react, para a lista mostrar main.jsx e App.jsx.

A troca é de uma palavra e muda tudo o que nasce: extensão dos arquivos, conteúdo do main.jsx (que em TypeScript ganha tipos) e as dependências do package.json. Por isso vale decidir antes de escrever código: converter um projeto de JavaScript para TypeScript depois é possível, mas é trabalho.

Se você já criou errado, não precisa começar de novo. Para um projeto de estudo, o caminho mais barato é criar outra pasta com o template certo e mover os seus componentes para lá — eles são só JavaScript e não sabem em qual projeto estão.

4. O que nasce na pasta

O template é pequeno de propósito: um index.html na raiz, um package.json, um vite.config.js e a pasta src com o main.jsx, o App.jsx e dois arquivos de estilo. Nada disso é obrigatório pela ferramenta — o Vite aceita qualquer organização —, mas o modelo é uma convenção que a comunidade reconhece.

O vite.config.js merece atenção porque é o único arquivo que fala com a ferramenta. Ele começa quase vazio e ganha linhas quando você precisa de algo: um plugin, uma porta fixa, um caminho diferente para os arquivos finais. É configuração, não código de aplicação: você mexe nele raramente e sempre com um motivo.

import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()]
});

São quatro linhas e três ideias. O defineConfig existe só para o editor ajudar com autocompletar — a configuração é o objeto que você passa para ele. O plugins recebe uma lista, e o @vitejs/plugin-react é o que ensina o Vite a transformar JSX e a ligar o HMR do React. Sem esse plugin, um arquivo .jsx não seria entendido como componente.

Uma dúvida que aparece no primeiro dia: por que não preciso de import React from "react" no topo dos arquivos? Porque o plugin usa o runtime automático do JSX, que importa as funções necessárias por conta própria. Em código antigo você vai ver o import explícito; nos projetos novos ele é desnecessário.

5. Como o Vite serve a página sem empacotar

Aqui está a diferença que explica a velocidade. Ferramentas mais antigas, como o webpack, juntavam todos os arquivos num pacote antes de abrir a página: mudar uma linha podia custar segundos. O Vite faz outra coisa no desenvolvimento — ele não empacota nada. O navegador já sabe carregar módulos JavaScript (ESM), então o servidor entrega cada arquivo separado, do jeito que está no disco, e transforma apenas o que o navegador não entende: .jsx, .tsx e imports de CSS.

Quando você abre a página, o index.html aponta para o /src/main.jsx; o navegador pede esse arquivo; o Vite transforma o JSX em JavaScript em milissegundos e responde; o main.jsx importa o App.jsx, e o ciclo continua arquivo por arquivo. Só o que a página usa é transformado. É por isso que o servidor sobe em 300 ms, mesmo num projeto com centenas de componentes: ele não fez nada ainda.

scaffold
O ato de criar a pasta do projeto a partir de um modelo, com os arquivos de partida.
template
O conjunto de arquivos copiado: react, react-ts, react-swc.
ESM
Os módulos nativos do JavaScript: cada arquivo importa o que precisa, e o navegador carrega.
servidor de desenvolvimento
O programa que responde em localhost e transforma os arquivos sob demanda.
HMR
Hot Module Replacement: trocar um módulo na página aberta sem recarregar tudo.
build
A versão final, empacotada e minificada, gerada pelo npm run build.

Essa escolha tem uma consequência que confunde: no desenvolvimento, o que roda no navegador são dezenas de arquivos separados; na versão final, são poucos arquivos grandes. O comportamento do React é o mesmo, mas o número de requisições não. É por isso que "funciona no dev, quebra no build" é um sintoma possível — e por isso existe o npm run preview, que serve a versão final localmente antes de publicar.

6. O HMR na prática

Salvar um arquivo e ver a mudança sem apertar F5 é o recurso que mais muda o ritmo de trabalho. O nome técnico é Hot Module Replacement: o Vite avisa o navegador de que um módulo mudou, o navegador pede a versão nova e o React troca aquele componente na árvore, sem recarregar a página. O estado dos outros componentes fica onde está.

Mas HMR não é mágica de preservar tudo. O que ele preserva é o estado dos componentes que não foram substituídos. Se você editar o componente que guarda o contador, ele é trocado, e o estado dele recomeça — porque a função nova é outra função, com outros valores iniciais. É por isso que, às vezes, um número "volta a zero sozinho" enquanto você trabalha: você editou justamente aquele componente.

Os dois botões simulam o que acontece no navegador. "Editar" troca o título e o contador deve continuar em 2 — é o HMR. "Recarregar" precisa zerar o contador, como um F5 de verdade. Dê ao <Contador /> uma key={reloads} para o recarregar recriar o componente.

function Contador() {
  const [cliques, setCliques] = useState(0);

  return (
    <div>
      <p>Cliques: {cliques}</p>
      <button className="somar" onClick={() => setCliques(cliques + 1)}>+1</button>
    </div>
  );
}

function App() {
  const [titulo, setTitulo] = useState("Pão do dia");
  const [reloads, setReloads] = useState(0);

  return (
    <div>
      <h2>{titulo}</h2>
      <Contador />
      <button className="editar" onClick={() => setTitulo("Pão do dia — edição")}>Editar</button>
      <button className="recarregar" onClick={() => setReloads(reloads + 1)}>Recarregar</button>
    </div>
  );
}

A key aqui não é sobre lista: é sobre identidade. Mudar a key diz ao React "este é outro componente, não o mesmo" — e ele descarta o antigo e cria um novo, com estado inicial. É exatamente o que um recarregamento de página faria com o componente inteiro. Trocar a key é uma forma controlada de forçar um recomeço, usada até em produção quando um formulário precisa limpar depois do envio.

O HMR real tem um detalhe a mais: quando o arquivo editado tem erro de sintaxe, o Vite mostra a mensagem numa sobreposição e mantém a última versão boa na tela. Corrigiu, salvou, a página atualiza sozinha. Vale reparar nesse ciclo enquanto trabalha — ele é o motivo de o desenvolvimento em React ser tão rápido hoje.

7. O arquivo vite.config.js

A configuração é um objeto. Você acrescenta chaves conforme a necessidade, e cada uma tem um efeito claro. As que aparecem mais cedo na vida de um projeto são poucas:

ChaveO que fazExemplo
pluginsliga transformações e recursos extras[react()]
server.portfixa a porta do servidor de desenvolvimento3000
server.hostexpõe o servidor na rede localtrue
server.openabre o navegador sozinho ao subirtrue
baseprefixo dos caminhos, para publicar em subpasta"/padaria/"
build.outDirpasta da versão final"dist"
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
  server: {
    port: 3000,
    open: true
  }
});

Configuração é lida quando o servidor sobe. Mudou o arquivo? O Vite reinicia sozinho — mas, se algo parecer ignorado, feche com Ctrl + C e suba de novo. Esse é o primeiro suspeito quando uma opção "não pega".

Repare que o server é um objeto dentro do objeto. Essa forma aparece em toda a configuração do Vite: agrupar por assunto (server, build, preview, resolve). Quando você vir uma configuração grande na internet, leia por blocos, não linha a linha.

8. Porta, host e a rede local

Por padrão o servidor escuta em localhost:5173, e localhost quer dizer "este computador". Se a porta estiver ocupada por outro projeto, o Vite escolhe a próxima livre e avisa no terminal. Quando você precisa abrir a página no celular — para testar o layout de verdade —, localhost não serve: o celular não é o seu computador. É aí que entra o --host.

$ npm run dev -- --host

VITE v7.1.0  ready in 297 ms

➜  Local:   http://localhost:5173/
➜  Network: http://192.0.2.10:5173/
➜  press h + enter to show help

A linha Network mostra o endereço na rede local. Digitando esse endereço no navegador do celular — no mesmo wi-fi —, a página abre. Se não abrir, o suspeito é o firewall do computador, que pode estar bloqueando a porta; liberar a rede privada resolve. Isso vale para desenvolvimento: em produção quem serve a página é a hospedagem.

A função portaLivre devolve sempre a porta pedida, mesmo quando ela está ocupada. Faça ela pular para a primeira porta livre a partir de 5173 — com 5173 e 5174 ocupadas, o endereço precisa ser http://localhost:5175/.

const ocupadas = [5173, 5174];

function portaLivre(inicial, ocupadas) {
  return inicial;
}

function App() {
  const porta = portaLivre(5173, ocupadas);

  return (
    <div>
      <h2>VITE v7.1.0 ready</h2>
      <p>{"➜ Local: http://localhost:" + porta + "/"}</p>
      <p>➜ Network: use --host to expose</p>
    </div>
  );
}
<div>
  <h2>VITE v7.1.0 ready</h2>
  <p>➜ Local: http://localhost:5173/</p>
  <p>➜ Network: use --host to expose</p>
</div>

const ocupadas = [5173, 5174];

function portaLivre(inicial, ocupadas) {
  let porta = inicial;

  while (ocupadas.includes(porta)) {
    porta = porta + 1;
  }

  return porta;
}

function App() {
  const porta = portaLivre(5173, ocupadas);

  return (
    <div>
      <h2>VITE v7.1.0 ready</h2>
      <p>{"➜ Local: http://localhost:" + porta + "/"}</p>
      <p>➜ Network: use --host to expose</p>
    </div>
  );
}

O laço continua enquanto a porta estiver na lista, e para na primeira livre. É uma versão de brinquedo do que o Vite faz de verdade — a diferença é que ele descobre se a porta está ocupada tentando abrir um servidor nela, e não consultando uma lista. O conceito é o mesmo: procurar até achar, e mostrar no terminal a porta que valeu.

Por isso a regra de ouro ao pedir ajuda: copie a linha que o terminal mostrou. Se o Vite disse 5174, o endereço é 5174 — abrir o 5173 antigo vai dar erro de conexão e você vai procurar o problema no lugar errado.

9. Cenários do dia a dia

Cenário 1: a versão do Node é antiga

O Vite 7 exige uma versão recente do Node. Com uma versão antiga, o comando falha antes de qualquer coisa com uma mensagem de versão mínima. A Ana atualizou o Node pelo site oficial, fechou e abriu o terminal — e o comando passou. "Feche e abra o terminal" não é superstição: o caminho do programa novo só entra na sessão seguinte.

Cenário 2: o projeto nasceu dentro de outra pasta

Ela rodou o assistente dentro de Documentos e o Vite criou Documentos/vitrine. Depois rodou de novo, sem sair da pasta, e ficou com Documentos/vitrine/vitrine. O sintoma é um npm install que instala o dobro e um servidor que abre o projeto errado. O conserto é mover a pasta interna para cima e conferir se o package.json está na raiz.

Cenário 3: o CSS do modelo brigando com o seu

O template traz App.css e index.css com estilos de exemplo, e eles valem para a página inteira. A Ana escreveu a vitrine e o layout saiu torto: o body tinha display: flex e place-items: center vindos do modelo. Apagar o conteúdo desses dois arquivos — mantendo os imports — é o primeiro passo de todo projeto novo.

11. Resumo

O npm create vite@latest baixa o create-vite, pergunta framework e variante e copia um template para uma pasta nova. Ele não instala dependências: o npm install vem depois. A variante decide a extensão dos arquivos — .jsx para JavaScript, .tsx para TypeScript — e o SWC troca o compilador por um mais rápido, sem mudar o código que você escreve.

No desenvolvimento, o Vite não empacota: entrega os módulos separados, transformando JSX sob demanda, e é por isso que sobe em centenas de milissegundos. O HMR troca o módulo alterado e preserva o estado do resto; editar o próprio componente do contador reinicia o contador. O vite.config.js é o lugar de plugins, porta, host e pasta de saída, e ele é lido quando o servidor sobe.

Com o projeto criado e entendido, a pergunta seguinte é onde cada arquivo deve morar quando o site cresce: uma pasta para componentes, uma para telas, uma para hooks, imagens em dois lugares diferentes. É o assunto da próxima aula — a estrutura de um projeto que passa de dez arquivos.

Para lembrar

  • npm create vite@latest nome -- --template react cria sem perguntas.
  • Template react gera .jsx; react-ts gera .tsx.
  • O create-vite não instala dependências: rode npm install depois.
  • No dev o Vite não empacota: transforma cada arquivo quando o navegador pede.
  • O plugin @vitejs/plugin-react é quem ensina o Vite a entender JSX.
  • HMR troca o módulo e preserva o resto; editar o próprio componente reinicia o estado dele.
  • key diferente = componente novo, com estado inicial.
  • vite.config.js: plugins, server, base, build.
  • Porta ocupada? O Vite escolhe a próxima e mostra no terminal — use a mostrada.
  • --host expõe na rede local para testar no celular.
