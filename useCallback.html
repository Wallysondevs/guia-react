O useCallback

A Ana montou um painel de pedidos com uma lista longa e um botão "Salvar" em cada linha. Cada botão é um componente separado, embrulhado em memo para não redesenhar à toa. Só que redesenha: basta a Ana digitar uma letra no campo de busca para todos os botões da lista piscarem de novo. O motivo não é o memo — é a função que ela passa como prop, que nasce nova a cada render. Nesta aula ela conhece o useCallback, que guarda a função entre renders, e descobre o preço disso: a função guardada enxerga o passado.

Você vai aprender
  • Por que toda função criada no componente é nova a cada render.
  • Como o useCallback devolve a mesma função enquanto as dependências não mudam.
  • O que é o valor capturado e por que ele causa o bug mais confuso do React.
  • Como a forma funcional do setter resolve sem depender do valor antigo.
  • A corrente completa: memo no filho, useCallback no pai, props estáveis.
  • Quando o useCallback não serve para nada.
  • Como escolher entre memo, useMemo e useCallback.

1. A cena: os botões que piscam

O painel da padaria tem uma lista de pedidos e, em cada linha, um botão "Salvar". O botão é um componente à parte, porque ele muda de cor quando o pedido já foi salvo. Para evitar trabalho, a Ana embrulhou esse componente em memo: se as props não mudaram, ele não desenha de novo.

Na prática, todos desenham. A Ana digitou uma letra no campo de busca e viu a lista inteira piscar. O memo estava lá, funcionando como devia — mas recebia uma prop diferente a cada render. Essa prop era a função salvar, escrita no componente pai. Toda função declarada no corpo de um componente é criada de novo a cada render, e uma função nova não é igual à anterior.

Para o React, comparar funções é comparar identidade, não comportamento: duas funções com o mesmo código são objetos diferentes. O memo vê "prop nova" e desenha. O useCallback existe para resolver esse problema específico — guardar a função entre renders, como o useMemo guarda um valor.

2. Toda função nasce de novo

Um componente é uma função, e o que está dentro dela é recriado a cada chamada. Um const salvar = () => { ... } não é uma exceção: é uma função nova, com um endereço novo na memória, a cada render. Se ela entra nas props de um filho, o filho vê "mudou". Se ela entra no array de dependências de um efeito, o efeito vê "mudou" e roda de novo.

function Painel() {
  const [busca, setBusca] = useState("");

  function salvar(id) {                 // nova a cada render
    console.log("salvando " + id);
  }

  return (
    <div>
      <input value={busca} onChange={(e) => setBusca(e.target.value)} />
      {PEDIDOS.map((p) => (
        <BotaoSalvar key={p.id} id={p.id} aoSalvar={salvar} />
      ))}
    </div>
  );
}

Nesse código, cada tecla no campo de busca muda o estado, o painel renderiza, e a função salvar é criada outra vez. Todos os BotaoSalvar recebem uma prop aoSalvar diferente da anterior. O memo compara e conclui que precisa desenhar — para todos eles. O trabalho de digitar uma letra vira o trabalho de redesenhar a lista inteira.

O problema aparece quando a identidade nova atravessa a fronteira do componente — props de um filho com memo ou array de dependências de um efeito.

3. useCallback: a função que fica

A assinatura é parecida com a do useMemo: uma função e um array de dependências. A diferença é que o useCallback devolve a própria função, não o resultado dela. Ele é, por dentro, um useMemo que guarda a função.

const salvar = useCallback((id) => {
  console.log("salvando " + id);
}, []);

Com o array vazio, a função é criada uma vez e reaproveitada em todos os renders seguintes. O memo do filho compara: mesma função, props iguais, não desenha. A lista para de piscar.

valor capturado
Os valores do render em que a função foi criada. A função guardada continua enxergando aqueles valores.

O embrulho do componente filho que evita render quando as props não mudam. É a outra metade da solução.

Agora a missão. O filho já está em memo; falta o pai entregar sempre a mesma função.

A função salvar nasce nova a cada render e derruba o memo do botão. Envolva-a num useCallback com []: depois de trocar o aviso, o botão tem de continuar em desenho 1.

let desenhos = 0;
const BotaoSalvar = memo(function BotaoSalvar({ aoSalvar }) {
  desenhos = desenhos + 1;
  return (
    <button onClick={aoSalvar}>
      Salvar pedido - desenho {desenhos}
    </button>
  );
});

Sem o useCallback, o clique em Trocar aviso cria uma função nova, o memo vê a prop mudada e o contador vai para 2. Com ele, a função é a mesma, o memo pula o desenho e o contador fica em 1. Note que o setAviso continua funcionando: a função guardada ainda pode chamar o setter, porque o setter é estável.

O array vazio só é correto porque a função não lê nada do componente. É aí que o assunto fica interessante — e perigoso.

4. A função guarda os valores do render

Uma função em JavaScript carrega consigo o ambiente em que nasceu. Isso se chama closure, ou fechamento. Se a função lê nome, ela guarda o valor de nome daquele render — não o valor de agora. Enquanto a função é recriada a cada render, isso não incomoda: cada versão enxerga o valor do seu tempo.

Quando você guarda a função com useCallback, a versão guardada continua enxergando o passado. Se as dependências não incluem nome, a função nunca é recriada e nunca vê o nome novo. O resultado é aquele bug clássico: a tela mostra "Maria", o botão salva "Ana".

const salvar = useCallback(() => {
  setSalvo("pedido de " + nome + " salvo");
}, []);        // falta nome: a função nunca é recriada

O console do navegador não reclama. O ESLint, sim:

React Hook useCallback has a missing dependency: 'nome'.
Either include it or remove the dependency array.
  react-hooks/exhaustive-deps

A tradução: "a sua função usa nome e o array não lista nome". A correção é incluir — [nome] —, e aí a função é recriada só quando o nome muda. Parece que isso anula o ganho, mas não: entre um nome e outro, a identidade é estável, e o memo do filho só redesenha quando o nome muda de verdade, o que é exatamente o que se quer.

A função guardada com [] lê nome e nunca é recriada, então salva o nome antigo. Inclua nome nas dependências, digite "Maria" e clique em Salvar.

function App() {
  const [nome, setNome] = useState("Ana");
  const [salvo, setSalvo] = useState("");

  const salvar = useCallback(() => {
    setSalvo("pedido de " + nome + " salvo");
  }, []);

  return (
    <div>
      <label htmlFor="nome">Nome</label>
      <input
        id="nome"
        value={nome}
        onChange={(e) => setNome(e.target.value)}
      />
      <button id="salvar" onClick={salvar}>Salvar</button>
      <p>{salvo}</p>
    </div>
  );
}

Dependência não é burocracia: é a lista do que a função enxerga. A regra é a mesma do useEffect e do useMemo, e a aula de dependências já mostrou como o React compara esse array.

5. O valor que a função capturou

O caso mais traiçoeiro não é ler um valor e esquecer de listar: é atualizar um valor. Veja o contador abaixo. A função está guardada com [], e dentro dela o código lê total.

const somar = useCallback(() => {
  setTotal(total + 1);
}, []);        // total fica congelado no valor do primeiro render

No primeiro render, total é 0. A função guardada enxerga esse 0 para sempre. Cada clique faz setTotal(0 + 1), ou seja, define 1. A tela mostra 1, 1, 1 — e a pessoa jura que o botão está quebrado. No console, o valor que a função leu aparece sempre igual:

somar com total = 0
somar com total = 0
somar com total = 0

Existem duas saídas, e as duas são legítimas. A primeira é listar total nas dependências: [total], e a função passa a ser recriada a cada mudança do total. A segunda é melhor: usar a forma funcional do setter, que recebe o valor atual em vez de capturá-lo.

const somar = useCallback(() => {
  setTotal((atual) => atual + 1);
}, []);        // não lê total: recebe o valor atual na hora

Com a forma funcional, a função não precisa enxergar total e o array vazio passa a ser verdade. Isso vale para qualquer setter: setLista((l) => [...l, novo]), setPedido((p) => ({ ...p, pago: true })). A aula de batching explica por que a forma funcional também protege contra atualizações em sequência.

Agora a missão: o contador tem os dois problemas juntos — função guardada e valor capturado.

A função guardada enxerga sempre o total 0, então três cliques mostram 1. Use a forma funcional setTotal((atual) => atual + 1) e mantenha o []: o painel tem de mostrar total: 3.

function App() {
  const [total, setTotal] = useState(0);

  const somar = useCallback(() => {
    setTotal(total + 1);
  }, []);

  return (
    <div>
      <p>total: {total}</p>
      <button id="somar" onClick={somar}>Somar um</button>
    </div>
  );
}

Clique três vezes no código inicial: o painel fica em 1. Na solução, cada clique recebe o valor atual e soma, então o total chega a 3. Repare que a função continuou sendo a mesma o tempo todo — o que mudou foi de onde vem o número: antes, de uma foto do primeiro render; agora, do React, na hora do clique.

6. A corrente inteira

useCallback sozinho não faz nada. Ele é um elo de uma corrente de três: o filho precisa estar em memo, o pai precisa entregar props estáveis e a função precisa ter as dependências certas. Se qualquer elo faltar, o trabalho é perdido.

const Linha = memo(function Linha({ pedido, aoSalvar }) {
  return (
    <div>
      <span>{pedido.nome}</span>
      <button onClick={() => aoSalvar(pedido.id)}>Salvar</button>
    </div>
  );
});

function Painel() {
  const [pedidos, setPedidos] = useState([]);

  const salvar = useCallback((id) => {
    setPedidos((lista) =>
      lista.map((p) => (p.id === id ? { ...p, salvo: true } : p))
    );
  }, []);

  return (
    <div>
      {pedidos.map((p) => (
        <Linha key={p.id} pedido={p} aoSalvar={salvar} />
      ))}
    </div>
  );
}

Aqui as três peças aparecem. O filho em memo compara pedido e aoSalvar. A função é estável, porque não lê nada e usa a forma funcional do setter. E cada pedido é um objeto que só muda quando aquele pedido muda — porque o map devolve o mesmo objeto quando nada mudou. O resultado é que salvar um pedido redesenha uma linha, não a lista.

Repare que o onClick dentro do filho é uma função nova a cada render do filho — e isso não importa. Ela não atravessa a fronteira do memo; é usada ali dentro, no elemento button. O React não compara a função do onClick para decidir se desenha um button: ele atualiza o listener. Preocupação com identidade só vale para props de componentes com memo e para dependências de hooks.

Essa tabela resolve a dúvida mais comum. useMemo guarda valor; useCallback guarda função; memo guarda o desenho. Os três são otimização, e nenhum deles muda o que o componente faz — só quanto trabalho ele dá.

7. Quando não usar

A regra prática: useCallback só se paga quando a função atravessa uma fronteira que compara identidade. Se ela é usada só dentro do próprio componente, o embrulho é custo sem retorno.

Filho sem memo. Se o filho não está em memo, ele desenha em todo render do pai, com função nova ou velha. O useCallback não muda nada.

Função usada só aqui. <button onClick={salvar}> no próprio componente não precisa de estabilidade: o React atualiza o listener e segue. A única exceção é quando a função é dependência de um useEffect — aí a identidade importa.

Dependências que mudam sempre. Se a função depende de um objeto recriado a cada render, o useCallback devolve uma função nova a cada render e o trabalho é zero. O conserto está no objeto, com useMemo, ou em listar os campos simples que a função realmente usa.

Muitos embrulhos em série. Um componente com cinco useCallback e dez useMemo é mais difícil de ler e muitas vezes não é mais rápido. O React 19 traz o compilador, que faz boa parte disso sozinho; escrever à mão continua válido, mas com propósito.

E vale lembrar o efeito colateral pedagógico: o useCallback esconde o valor capturado. Quanto mais funções guardadas, mais fácil é criar uma que enxerga o passado. Se você não consegue explicar por que a função precisa ser a mesma entre renders, provavelmente ela não precisa.

8. As regras do useCallback

A função guardada é a do primeiro render, com as dependências daquele momento. Ela não é "atualizada" — é substituída quando uma dependência muda. Se você não listar o que ela lê, ela fica no passado.

Liste tudo o que a função lê. Props, estado e valores do componente. O ESLint avisa, e o aviso não é implicância: é a diferença entre salvar o nome certo e salvar o nome antigo.

Prefira a forma funcional do setter. setTotal((t) => t + 1), setLista((l) => [...l, item]). Assim a função não precisa capturar o valor e o array pode ficar vazio de verdade.

Não chame hooks dentro da função guardada. A função pode rodar em qualquer momento, inclusive depois de um clique, e hooks precisam seguir a ordem das chamadas do componente. O React reclama na hora — e a regra vale para qualquer callback.

Não guarde efeito colateral na criação. useCallback não executa a função; ele só guarda. Se você quer que algo aconteça na montagem, o lugar é o useEffect — a aula de useEffect cobre isso.

Não use para "melhorar a performance" sem medir. Como o useMemo, o useCallback tem custo: uma entrada de cache, uma comparação de array e uma camada a mais para quem lê. Em componente pequeno, o ganho é invisível e o custo de manutenção é real.

9. Cenários do dia a dia

Cenário 1: o memo que não segurava nada

A Ana colocou memo no filho e continuou vendo ele redesenhar. A prop era uma função criada no pai, nova a cada render. O memo comparava e via diferença. Com useCallback no pai, a comparação passou a dar igual e o filho parou de desenhar. Duas peças, um resultado.

Cenário 2: o pedido salvo com o nome antigo

Ela guardou a função com [] e ela lia nome. O campo mostrava "Maria", o pedido saía como "Ana". Nada de errado com o input: a função guardada enxergava o valor do primeiro render. Incluir nome nas dependências resolve — e, se der para usar a forma funcional, melhor ainda.

Cenário 3: o contador que só chegava a 1

Três cliques, total 1. A função guardada lia total do primeiro render e escrevia setTotal(0 + 1) em toda chamada. Com setTotal((atual) => atual + 1), cada clique recebe o valor do momento e o total sobe. O sintoma é sempre o mesmo: o valor na tela não acompanha a conta.

11. Resumo

Toda função declarada dentro de um componente nasce de novo a cada render, e o React compara funções por identidade. Quando essa função vai como prop para um filho em memo ou entra nas dependências de um efeito, a identidade nova derruba a otimização: o filho redesenha, o efeito roda de novo. O useCallback guarda a função e devolve a mesma enquanto as dependências não mudam.

O preço é o valor capturado. A função guardada enxerga os valores do render em que nasceu, então esquecer uma dependência produz aquele bug em que a tela mostra uma coisa e o código salva outra. A saída tem duas portas: listar a dependência ou — melhor — usar a forma funcional do setter, que recebe o valor atual e não precisa capturar nada.

E o mais importante: useCallback sozinho não otimiza nada. Ele é um elo entre o memo do filho, props estáveis e dependências corretas. Se a função não atravessa fronteira nenhuma, o embrulho é só ruído. O próximo hook, o useReducer, muda de assunto: em vez de guardar funções, ele organiza as transições de estado de um componente que já tem estados demais.

Para lembrar

  • Função no componente é nova a cada render; o React compara identidade.
  • useCallback(fn, deps) devolve a mesma função enquanto as deps não mudam.
  • A função guardada enxerga os valores do render em que foi criada.
  • Dependência faltando: valor antigo, sem erro no console — o ESLint avisa.
  • setTotal((t) => t + 1) dispensa a dependência do valor.
  • memo no filho + useCallback no pai + props estáveis = o desenho evitado.
  • Sem memo no filho, o useCallback não muda nada.
  • Função usada só no próprio componente não precisa de useCallback.
  • useMemo guarda valor; useCallback guarda função.
  • Se não dá para explicar por que a função precisa ser a mesma, ela não precisa.
