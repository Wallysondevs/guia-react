Chat

A Ana atende os clientes pelo celular e já perdeu três encomendas deste mês: o recado chegou enquanto ela tirava pão do forno, ficou embaixo de uma conversa antiga e ninguém viu. A solução não é digitar mais rápido — é um chat no site da padaria, onde cada pedido fica registrado na ordem em que chegou. Neste projeto ela monta esse chat do zero, em seis passos, e cada caixa roda um pedaço funcional do app.

Você vai aprender
  • Como planejar um app antes de escrever a primeira linha: dados, estado e telas.
  • Uma lista de mensagens com map, key e classe por remetente.
  • Um campo controlado dentro de um formulário que não recarrega a página.
  • Como acrescentar a mensagem na lista e limpar o campo.
  • Como simular a resposta do cliente com Promise e await.
  • Rolar até a última mensagem com useRef e useEffect.
  • Guardar o histórico no localStorage sem quebrar quando o dado está velho.
  • Os erros que aparecem na ordem errada e como depurar cada um.

1. A cena: o recado que ninguém viu

O chat da padaria não existe ainda. O que existe é o celular da Ana com quatro conversas abertas, uma lista de recados no guardanapo e a memória — que falha às seis da manhã. O cliente pergunta “tem pão de queijo?”, ela responde “tem sim”, ele pede “separa dois”, e no meio disso o forno apita. Quando ela volta, a conversa já desceu na tela.

O app que resolve isso tem uma tela só: a conversa. Em cima, as mensagens na ordem em que chegaram; em baixo, o campo para responder. Quem escreveu aparece de um jeito, quem atende aparece de outro. Quando a Ana envia, a mensagem entra na hora; quando o cliente responde, ela entra quando chega.

Parece pouco, e é por isso que serve como projeto: o chat tem tudo o que um app de verdade tem — uma lista, um formulário, um estado de espera, uma resposta que demora e um histórico que precisa sobreviver ao recarregamento. Montar essa tela pequena ensina o esqueleto de todas as outras.

Uma decisão de escopo antes de começar: não haverá login, nem servidor de verdade, nem notificação. O cliente é simulado por um botão, o servidor é uma Promise que você controla e o histórico fica no navegador. Menos peças, mais aprendizado por peça.

2. O desenho antes do código

Todo projeto começa com três listas. A primeira é o dado: o que o app mostra. A segunda é o estado: o que muda enquanto a pessoa usa. A terceira é o derivado: o que pode ser calculado a partir das outras duas. Confundir as três é a origem de quase todo bug de arquitetura.

No chat, o dado é uma lista de mensagens. Cada mensagem tem um identificador, o remetente ("eu" ou "cliente"), o texto e o horário. O estado é essa lista — que muda quando alguém envia — mais o texto que está sendo digitado e um aviso de “digitando…”. O derivado é a última mensagem, a contagem e a ordem: tudo isso sai da lista.

Com esse desenho, o componente tem três estados e algumas contas. A ordem de montagem segue a tela: primeiro a lista, depois o campo, depois o envio, depois a resposta, depois a rolagem e, por fim, o histórico. Cada passo é uma caixa que roda de verdade — e o app cresce sem você reescrever o que já funciona.

3. Passo 1 — a lista de mensagens

O primeiro passo é o mais parecido com o que você já fez em Listas com map: pegar o array e transformar em elementos. A diferença é que cada item é um objeto e que a classe muda conforme o remetente.

<ul className="chat">
  {mensagens.map((m) => (
    <li className={"mensagem " + m.de} key={m.id}>
      {m.texto}
    </li>
  ))}
</ul>

A key é o id da mensagem, não o índice. Mensagem é o exemplo clássico de lista que só cresce e onde a identidade importa: com índice, quando o histórico é recarregado ou uma mensagem é apagada, o React associa o texto à linha errada e a conversa parece embaralhada. A aula A key explica o mecanismo; aqui basta aplicar.

A conversa tem três mensagens no array, mas a tela mostra só a primeira, escrita à mão. Desenhe as três com map, usando className={"mensagem " + m.de} e key={m.id}.

const mensagens = [

  { id: "m2", de: "eu", texto: "Tem sim, saiu agora do forno." },
  { id: "m3", de: "cliente", texto: "Separa dois, por favor." }
];

function App() {
  return (
    <ul className="chat">
      <li className="mensagem cliente">Bom dia! Tem pão de queijo?</li>

O painel mostra três li com classes diferentes: mensagem cliente e mensagem eu. É essa classe que o CSS usa para alinhar de um lado ou do outro. Se as três saírem com a mesma classe, você escreveu className="mensagem" sem a parte variável; se saírem sem classe, o className ficou de fora.

Três mensagens, três ids distintos. É o mínimo para a lista funcionar: se dois ids coincidirem, o React reclama de key duplicada em desenvolvimento e o resultado visual fica imprevisível. Aqui os ids vêm prontos do array — no app de verdade, quem cria é o servidor.

4. Passo 2 — o campo controlado e o envio

Agora a parte de baixo da tela: o campo onde a Ana escreve. Ele é uma entrada controlada, como em Entrada Controlada: value={texto} manda o estado para o campo e onChange guarda cada tecla.

O envio merece um <form>, e não um botão solto, por dois motivos. Primeiro, porque o Enter no campo dispara o envio — é o que qualquer pessoa espera de um chat. Segundo, porque o navegador recarrega a página ao enviar um formulário, e o onSubmit com preventDefault() é o lugar certo para impedir isso. A aula Envio de Formulário destrincha o assunto; aqui ele aparece em cinco linhas.

function enviar(e) {
  e.preventDefault();
  if (texto.trim() === "") return;
  setMensagens([...mensagens, { id: "m" + (mensagens.length + 1), de: "eu", texto: texto }]);
  setTexto("");
}

<form onSubmit={enviar}>
  <input value={texto} onChange={(e) => setTexto(e.target.value)} placeholder="Escreva sua mensagem" />
  <button className="enviar">Enviar</button>
</form>

Três cuidados escondidos nessas linhas. O primeiro é o trim(): sem ele, um espaço em branco vira mensagem e o chat ganha bolhas vazias. O segundo é criar a lista nova com [...mensagens, nova] em vez de push — push altera o array no lugar e o React pode não redesenhar. O terceiro é limpar o campo depois de enviar, senão a mensagem fica no input e a pessoa envia duas vezes.

O formulário já segura a página e limpa o campo, mas não acrescenta nada à conversa. Complete o envio: crie a mensagem com de: "eu" e um id novo, acrescente ao array e limpe o campo. Depois digite “Cheguei” e clique em Enviar.

A conferência digita “Cheguei”, clica em Enviar e espera três mensagens na lista, com o texto novo visível. Se a contagem continuar em duas, falta o setMensagens; se aparecerem quatro, você enviou duas vezes — provavelmente limpou o campo depois de já ter enviado, ou não limpou e o teste digitou de novo.

Uma armadilha que este projeto evita de propósito: guardar o array com push. Escrever mensagens.push(nova) até parece mais curto, mas o array continua o mesmo objeto e o React compara referências. A tela não muda, e você fica olhando para o console sem entender. Lista nova, tela nova.

5. Passo 3 — quem falou

Um chat sem distinção de remetente é um diário. A classe que você montou no passo 1 resolve isso com CSS, sem nenhuma lógica nova no componente:

.chat { display: flex; flex-direction: column; gap: 8px; }

.mensagem {
  max-width: 80%;
  padding: 8px 12px;
  border-radius: 12px;
  background: #f1f1f1;
}

.mensagem.eu {
  align-self: flex-end;
  background: #d8f0c8;
}

A regra .mensagem.eu só se aplica às bolhas que têm as duas classes. O cliente fica à esquerda, com o cinza padrão; a Ana fica à direita, com o verde. Repare que não há if no JSX para decidir o lado: a decisão está no dado (de) e o CSS cuida da apresentação. Separar as duas coisas é o que permite mudar o visual sem tocar na lógica.

Se você quiser um visual diferente sem CSS, o caminho é o style inline, que também é um objeto: style={{ alignSelf: m.de === "eu" ? "flex-end" : "flex-start" }}. Funciona e é mais difícil de manter. O guia usa classe sempre que a variação é previsível, e guarda o inline para o valor que vem do estado — como a cor escolhida pelo usuário em style Inline.

Há um detalhe de acessibilidade fácil de esquecer: a cor não deve ser a única marca de quem falou. Aqui o alinhamento ajuda, mas quem usa leitor de tela não vê lado nenhum. Duas opções: incluir o nome antes do texto (Ana: / Cliente:) ou um aria-label no item. A primeira é mais simples e serve para todo mundo.

6. Passo 4 — a resposta que demora

Até aqui, tudo acontece na hora. O cliente, não: ele lê, pensa e responde — e esse intervalo é o que dá a sensação de conversa. No app, ele é o estado digitando, que mostra “digitando…” enquanto a resposta não chega.

Para simular sem rede, o truque é o mesmo da aula Atualização Otimista: uma Promise que fica pendurada até alguém chamar o ok. Guardamos essa função numa variável de fora do componente e um segundo botão a chama — é o “servidor” respondendo quando você manda.

let responder = null;

function pedirResposta() {
  return new Promise((ok) => {
    responder = ok;
  });
}

async function enviar() {
  setMensagens([...mensagens, { id: "m3", de: "eu", texto: texto }]);
  setDigitando(true);
  await pedirResposta();
  setMensagens((lista) => [...lista, { id: "m4", de: "cliente", texto: "Obrigada pelo pedido!" }]);
  setDigitando(false);
}

Quatro linhas contam a história toda. Primeiro a mensagem da Ana entra na lista, para a tela responder na hora. Depois o aviso liga. O await pausa a função — e só ela — até a resposta chegar. Quando chega, a mensagem do cliente entra e o aviso desliga. A tela nunca fica travada, porque o JavaScript continua atendendo cliques enquanto espera.

O setMensagens((lista) => ...) com função é importante aqui: como a resposta chega depois, o mensagens capturado no começo pode estar velho. A forma funcional recebe a lista atual do React, e não a cópia do momento do clique. É a mesma recomendação da aula de Atualizar o Estado, e no código assíncrono ela deixa de ser estilo para ser necessidade.

O envio já põe a mensagem da Ana na lista, mas não avisa que o cliente está digitando nem espera a resposta. Ligue o aviso, aguarde pedirResposta() com await e acrescente a resposta do cliente antes de desligar o aviso.

Clique em Enviar pedido e repare que a mensagem da Ana entra imediatamente, enquanto o aviso “digitando…” aparece embaixo. Só quando você clica em Cliente responde é que a mensagem final entra e o aviso some. Essa separação entre “o que eu fiz” e “o que o outro fez” é o coração de qualquer chat.

7. Passo 5 — rolar até a última mensagem

Mensagem nova entra no fim da lista, e o fim da lista costuma estar fora da tela. Sem rolagem automática, a Ana envia uma resposta e não vê o que enviou. A correção é um efeito que roda quando a lista muda e leva o navegador até o fim.

const fim = useRef(null);

useEffect(() => {
  if (fim.current) fim.current.scrollIntoView({ block: "end" });
}, [mensagens]);

<ul className="chat">
  {mensagens.map((m) => (
    <li className={"mensagem " + m.de} key={m.id}>{m.texto}</li>
  ))}
  <li ref={fim} aria-hidden="true"></li>
</ul>

O useRef guarda uma referência a um elemento — no caso, um li vazio no fim da lista. O useEffect roda depois que a tela foi desenhada, e é aí que o elemento já existe para receber o scrollIntoView. Se você tentasse rolar durante o render, o elemento novo ainda não estaria na página.

A lista de dependências [mensagens] diz quando o efeito deve rodar: sempre que a lista mudar de identidade. Como cada envio cria um array novo, o efeito roda no momento certo. É a mesma lógica de As Dependências: o efeito é uma reação, e a lista é o gatilho.

Duas armadilhas comuns. A primeira é usar [mensagens.length]: se uma mensagem for editada sem mudar o tamanho, a rolagem não acontece. A segunda é esquecer o if (fim.current): na primeira renderização o ref pode estar vazio, e você recebe “Cannot read properties of null”. Um if de uma linha evita o erro.

8. Passo 6 — guardar a conversa

Recarregar a página apaga o estado. Num chat, isso significa perder a conversa inteira — e a Ana não vai aceitar. O localStorage resolve para um app pequeno: é um armário de textos no navegador, que sobrevive ao recarregamento e some se a pessoa limpar os dados do site.

const [mensagens, setMensagens] = useState(() => {
  try {
    const salvo = localStorage.getItem("chat-ana");
    return salvo ? JSON.parse(salvo) : inicio;
  } catch (e) {
    return inicio;
  }
});

useEffect(() => {
  localStorage.setItem("chat-ana", JSON.stringify(mensagens));
}, [mensagens]);

A leitura acontece dentro de uma função passada ao useState. Essa forma é intencional: o código ali roda uma vez, na montagem, e não a cada render. Se você chamasse JSON.parse(localStorage.getItem(...)) direto no corpo do componente, leria o armário em cada desenho — lento e sujeito a surpresas.

O try/catch não é enfeite. O armário pode conter lixo: um texto cortado, um JSON de uma versão antiga do app, algo que outra pessoa gravou. JSON.parse lança erro nesses casos, e sem o catch o componente quebra na primeira renderização — a pior hora possível. Com ele, o app volta para o exemplo inicial e segue funcionando.

> localStorage.getItem("chat-ana")

> JSON.parse(localStorage.getItem("chat-ana")).length
1

A gravação fica num efeito que observa mensagens. Toda vez que a lista muda, o armário é atualizado. É o padrão da aula O localStorage, e ele tem um custo que vale conhecer: gravar a cada tecla digitada seria desperdício, por isso o efeito observa apenas a lista, e não o texto do campo.

Cenário 1: a conversa volta vazia depois de recarregar

A Ana gravou no localStorage, mas leu com a chave errada: gravou em "chat-ana" e leu "chat". O armário é indexado por nome, e um caractere de diferença cria outra gaveta. O sintoma é uma conversa vazia sem erro no console. Antes de suspeitar do efeito, confira as duas strings.

Cenário 2: o app quebra ao abrir, e só em um computador

O localStorage daquele navegador tem um JSON inválido — de uma versão anterior, ou de um teste antigo. Sem try/catch, JSON.parse lança e a tela fica em branco. Com o tratamento, o app ignora o lixo e começa do exemplo. Dado guardado é dado não confiável: trate sempre.

9. O que quebra e o que conferir

Um projeto se prova pelo que acontece quando dá errado. Esta é a lista de conferência da Ana, na ordem em que ela testaria o chat antes de mostrar para um cliente.

chave do histórico
O nome usado no localStorage ("chat-ana"). Precisa ser idêntico na leitura e na gravação.
lista nova
Cada envio cria um array novo com spread. push altera no lugar e a tela pode não atualizar.
atualização funcional
setMensagens((lista) => ...) usa a lista atual, não a do momento do clique — essencial depois de um await.
efeito de rolagem
useEffect com [mensagens] que chama scrollIntoView no ref do fim.
formulário contido
onSubmit com preventDefault(); sem isso, o navegador recarrega e apaga o estado.

A ordem de teste também importa. Comece pelo envio: escreva, envie, veja a mensagem entrar e o campo limpar. Depois recarregue e confira o histórico. Só então simule a resposta do cliente e observe o aviso. Se você começar pela resposta, um erro no envio fica escondido atrás de outro.

Três perguntas para fechar o assunto:

Dica: o nome da variável que guarda a mensagem recém-criada no passo 2.

10. Resumo

O chat é uma lista de mensagens, um campo controlado e um envio que cria um array novo. Cada mensagem tem id, remetente e texto; a key é o id, e a classe combina mensagem com o remetente para o CSS decidir o lado. Nada disso é específico de chat: é o mesmo desenho de qualquer lista com formulário.

A resposta que demora é uma Promise aguardada com await, e o aviso “digitando” é um booleano que liga antes e desliga depois. Quando a atualização depende da lista atual — e depois de um await sempre depende —, use a forma funcional do setter. A tela continua respondendo enquanto espera.

A rolagem automática é um efeito com useRef: um elemento vazio no fim da lista recebe a referência e o efeito chama scrollIntoView quando as mensagens mudam. E o histórico vive no localStorage, com leitura preguiçosa no useState, gravação num efeito e try/catch para o dado podre.

Com o chat pronto, a Ana nunca mais perde um pedido embaixo de outra conversa. O próximo projeto usa as mesmas peças — lista, filtro, detalhe e formulário — numa vitrine em vez de uma conversa.

Para lembrar

  • Planeje com três listas: dado, estado e derivado.
  • Lista de mensagens: map com key={m.id} e classe por remetente.
  • Envio em <form onSubmit> com preventDefault() e trim().
  • Acrescente com [...mensagens, nova]; nunca push.
  • Resposta simulada: Promise + await + estado de espera.
  • Depois de await, use setMensagens((lista) => ...).
  • Rolagem: useRef no fim da lista e useEffect com [mensagens].
  • Histórico: ler no useState, gravar no useEffect, tratar erro no JSON.parse.
  • Guarde só o que faz sentido reencontrar ao abrir o app.
  • Teste na ordem: envio, recarregamento, resposta, rolagem.
