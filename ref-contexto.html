Contexto

Contexto é o cano que leva um dado do alto da árvore até um componente distante sem passar por todos os níveis do meio. A Ana usa três: o tema da tela, o cliente logado e o carrinho. Esta página é a consulta — quando vale abrir um canal, como abastecer, o que faz um consumidor redesenhar, e em que ponto o contexto começa a atrapalhar mais do que ajuda.

Como usar esta página
  • A seção 1 decide se o seu caso é contexto; as seções 2 e 3 mostram como montar.
  • Se a tela “redesenha demais”, o assunto é a seção 4; se o valor aparece errado, a seção 6.
  • As duas caixas rodam com React 19: edite, clique em Rodar e leia o painel.
  • Os trechos de arquivo mostram o código como ele fica no projeto, com import.

1. O dado que atravessa a árvore

Props descem um nível por vez. Enquanto o dado interessa ao filho direto, isso é uma qualidade: a dependência aparece na assinatura do componente e qualquer pessoa lê de onde o valor veio. O problema começa quando o dado precisa chegar a um componente cinco níveis abaixo e os quatro intermediários não usam nada dele — é o prop drilling, o encanamento que a aula Props Drilling mostra acontecendo.

Contexto resolve um caso específico: um valor que pertence a uma região da tela e é lido em pontos distantes dela. Tema, cliente logado, idioma, carrinho, permissões. Não resolve dado que muda de tela para tela, nem substitui estado elevado quando dois irmãos precisam combinar um valor.

contexto
Um canal nomeado que carrega um valor para todos os componentes abaixo do provider. Criado com createContext, uma vez, fora dos componentes.
Provider
O componente que abastece o canal para uma região da árvore: <ClienteContexto.Provider value={cliente}>. Não aparece no HTML.
value
O que o provider publica. Pode ser texto, número, objeto ou função — e normalmente vem de um estado ou de um useMemo.
consumidor
Todo componente que chama useContext(Canal). Vira assinante: redesenha quando o valor publicado muda de identidade.
valor padrão
O que o createContext recebeu. Só aparece quando não há provider acima — não é “carregando” nem “dado ainda não chegou”.
identidade
O React compara o valor por referência. Objeto recriado a cada desenho é sempre “outro” valor, mesmo com o mesmo conteúdo.

O sinal de que o encanamento passou do ponto é concreto: você escreveu a mesma prop em três assinaturas que não a usam. Na padaria, cliente aparecia em App, Loja, Setor, Cartao e Selo — quatro intermediários para um dado que só o último lia. Contexto corta esse caminho, mas cobra um preço: a dependência sai da assinatura e passa a morar dentro do corpo do componente. Quem lê o código do selo não vê, pela chamada, que ele depende do cliente.

Vale conhecer a alternativa antes de abrir um canal: passar o dado pronto pela children. Se o componente do meio só embrulha, ele pode receber o bloco montado de cima e repassar sem saber o que tem dentro — a aula Composição faz isso com o cartão de preço. É a saída mais barata quando o dado serve a um bloco só.

2. As três peças, na ordem

Criar o canal, abastecer uma região, ler de dentro. As três linhas têm nome próprio e vale decorar, porque aparecem em todo arquivo que usa contexto.

PeçaOnde ficaO que fazErro clássico
createContexttopo do arquivo, fora de componentecria o canal e define o valor padrãochamar dentro do componente: canal novo a cada desenho — Introdução ao Contexto
.Providerno JSX, envolvendo um ramopublica o valor para os descendentesenvolver só uma parte e esperar que valha para a tela inteira — O Provider

import { createContext, useContext } from "react";

export const ClienteContexto = createContext("visitante");

export function useCliente() {
  return useContext(ClienteContexto);
}

O createContext fica no topo do arquivo, fora de qualquer componente. Se ele ficar dentro de um componente, cada desenho cria um canal novo: o provider abastece um e o consumidor lê outro, e o valor padrão aparece no lugar do dado. É o erro mais silencioso do assunto.

O provider cobre só o primeiro cartão; o segundo cai no valor padrão. Mova o provider para fora, envolvendo os dois cartões, mantendo value="escuro".

const TemaContexto = createContext("claro");

function Cartao() {
  const tema = useContext(TemaContexto);
  return (
    <article className={"cartao tema-" + tema}>
      <h2>Pão do dia</h2>
      <p>Modo: {tema}</p>
    </article>
  );
}

function App() {
  return (
    <div>
      <TemaContexto.Provider value="escuro">
        <Cartao />
      </TemaContexto.Provider>
      <Cartao />
    </div>
  );
}

O painel deixa a região à vista: um cartão com tema-escuro e outro com tema-claro. Provider é delimitação, não configuração global — o que está fora continua lendo o valor padrão. E note que o provider não aparece no HTML gerado: ele é um componente que só repassa os filhos.

O provider não guarda estado por si: ele publica o que recebe. Na maioria dos projetos, quem guarda é um componente LojaProvider, que tem o useState e desenha o <ClienteContexto.Provider value={cliente}> em volta dos filhos. Assim o estado e o canal moram no mesmo lugar, e o resto da tela só lê. Se o provider aparecer em cinco lugares diferentes com valores distintos, você tem cinco regiões independentes — o que pode ser exatamente o que quer numa prévia, e é quase sempre um engano na tela principal.

No React 19, o próprio objeto do canal serve de provider, sem o .Provider: <TemaContexto value="escuro">. As duas formas convivem e fazem a mesma coisa; o guia usa .Provider porque é o que você encontra na maioria dos projetos. A aula Introdução ao Contexto monta esse primeiro canal do zero, e a O Provider detalha o componente que abastece — inclusive o caso de um provider que guarda o estado e expõe as ações.

3. Um canal por assunto

A tentação depois do primeiro canal é juntar tudo em um objeto só: { usuario, tema, carrinho }. Funciona, e cobra caro. Todo consumidor passa a assinar o objeto inteiro: mudar o tema redesenha o carrinho, e mudar o carrinho redesenha o cabeçalho. Além disso, quem lê precisa saber a forma do objeto inteiro para usar um campo.

CanalO que guardaMuda com que frequênciaQuem lê
tema"claro" ou "escuro"quase nuncatodos os blocos com estilo
clientenome e permissões de quem entrouao entrar e saircabeçalho, rodapé, nota fiscal
carrinhoitens e totala cada itemcarrinho, botão de finalizar, selo — Estado com Array
açõesfunções: entrar, sair, adicionarnunca (funções estáveis)botões espalhados — O Provider

A última linha é a que mais rende. Separar os dados das ações deixa o botão de “entrar” fora do caminho quando o nome do cliente muda — ele assina o canal de ações, que não muda. A seção 5 mostra o padrão completo; a seção 4 explica por que ele importa tanto.

Um canal por assunto também facilita testar e reaproveitar: um componente que lê só o tema pode ser usado em qualquer tela com um provider de tema, sem arrastar cliente e carrinho junto. E dá para aninhar providers do mesmo canal quando existe uma prévia dentro de um painel — a prévia mostra o “visitante” enquanto o painel mostra a Ana.

4. O valor tem identidade

O React não compara o conteúdo do valor: compara a referência. Um objeto escrito no JSX nasce de novo a cada desenho do provider, então todo consumidor abaixo é chamado de volta mesmo que nada tenha mudado no conteúdo. Em tela pequena ninguém percebe; em tela com lista e tabela, vira lentidão.

function LojaProvider({ children }) {
  const [cliente, setCliente] = useState("visitante");

  const valor = useMemo(() => ({ nome: cliente }), [cliente]);

  return (
    <ClienteContexto.Provider value={valor}>
      {children}
    </ClienteContexto.Provider>
  );
}

Três saídas, da mais simples à mais elaborada: publicar um valor primitivo (value={cliente}) quando der; criar o objeto fora do componente quando ele é constante; e guardar com useMemo quando ele depende de estado. O que não ajuda é embrulhar o consumidor em memo e esperar que ele segure: contexto que muda de identidade atravessa o memo e redesenha do mesmo jeito.

O useMemo só compensa se a lista de dependências for honesta. Se você escreve useMemo(() => ({ nome: cliente }), []) com lista vazia, o objeto nunca é recriado — e o nome congela no primeiro valor. O sintoma é o pior possível: a tela funciona até alguém entrar, e depois o cabeçalho insiste em dizer “visitante”. Dependência é o que o valor usa, não o que você gostaria que ele usasse.

O caso do objeto com função dentro é o mais comum de todos: value={ cliente, entrar } recria os dois a cada desenho. Como a função também muda de identidade, separar em dois canais (dados e ações) já elimina metade do problema — a outra metade é o useMemo. A aula O useContext mede isso com um contador de desenhos.

5. Dados e ações, em dois canais

O padrão que escala é este: um canal para o dado, outro para as funções. O provider guarda o useState (ou o useReducer) e publica nos dois canais. Quem só chama uma ação não redesenha quando o dado muda; quem só lê o dado não carrega função nenhuma.

O botão lê o canal de ações, mas o App não abastece esse canal — a função que chega é a vazia do valor padrão. Envolva os dois componentes com <AcoesContexto.Provider value={ entrar }>, alimentando o canal com setCliente.

const ClienteContexto = createContext("visitante");
const AcoesContexto = createContext({ entrar: () => {} });

function Cabecalho() {
  const cliente = useContext(ClienteContexto);
  return <h1>Olá, {cliente}</h1>;
}

function BotaoEntrar() {
  const { entrar } = useContext(AcoesContexto);
  return <button onClick={() => entrar("Ana")}>Entrar como Ana</button>;
}

function App() {
  const [cliente, setCliente] = useState("visitante");

  return (
    <ClienteContexto.Provider value={cliente}>
      <Cabecalho />
      <BotaoEntrar />
    </ClienteContexto.Provider>
  );
}
<h1>Olá, visitante</h1>

        <Cabecalho />
        <BotaoEntrar />
      </ClienteContexto.Provider>
    </AcoesContexto.Provider>
  );
}

Clique antes de consertar: o cabeçalho não muda. O botão está lendo o canal de ações e recebendo a função vazia do valor padrão — prova de que o valor padrão não é um aviso, é um valor de verdade que o código executa. Depois do conserto, “Olá, Ana” aparece e o botão continua no lugar.

Repare no objeto acoes da solução: ele é criado a cada desenho do App. Para um botão que só chama função isso é inofensivo, mas é o mesmo padrão que causa redesenhos quando o canal de ações tem muitos consumidores — a correção definitiva é useMemo em volta, ou publicar a função direto (value={setCliente}) quando ela é a única ação. Publicar uma função só é o caminho mais simples e o mais estável: funções de useState e dispatch de useReducer não mudam de identidade entre desenhos.

Quando o estado do provider cresce, troque o useState por useReducer e publique o dispatch: a função é estável por definição e o componente que só dispara ação nunca redesenha. A aula O useReducer mostra o mesmo carrinho nos dois formatos, e a O Provider junta as peças em um arquivo só.

6. Valor padrão e erro claro

O valor padrão só aparece quando não há provider acima. Ele não é “carregando”, não é “sem dado” e não é substituído por undefined: se o provider existe e publica undefined, o consumidor recebe undefined. Essa distinção explica dois comportamentos que parecem bugs.

O primeiro: o selo mostra “visitante” mesmo depois de você passar o cliente. Quase sempre o provider está fora do ramo onde o selo mora, ou o canal foi criado dentro de um componente. O segundo: o erro de leitura em cima de null, quando o canal foi criado com createContext(null) e alguém esqueceu o provider:

Uncaught TypeError: Cannot read properties of null (reading 'nome')

A tradução é “o consumidor está fora da área abastecida”. Para que o erro apareça com o nome do problema, crie o canal com null e leia por um hook próprio que checa o valor:

export function useCliente() {
  const cliente = useContext(ClienteContexto);
  if (cliente === null) {
    throw new Error("useCliente precisa estar dentro de LojaProvider");
  }
  return cliente;
}

Um caso que engana: o provider condicional. Escrever {logado && <Provider>…</Provider>} faz o ramo inteiro sumir quando a condição é falsa — e os consumidores caem no valor padrão de uma vez. Se a intenção é só esconder parte da tela, a condição vai dentro dos filhos, não em volta do provider. Regra curta: provider no lugar mais alto que precisa dele, sempre montado; o que é condicional é o conteúdo.

O ganho é de depuração, não de estilo: em vez de descobrir três telas depois, o erro aponta o componente e o provider que faltou. O custo é uma linha por canal. A aula O useContext discute quando vale criar com null e quando um padrão razoável (“visitante”, “claro”) comunica melhor.

7. Quando não usar contexto

Contexto é confortável e invisível: quem lê não revela a dependência para quem usa o componente. Isso facilita a vida hoje e cobra na hora de testar, reaproveitar e entender. A tabela ajuda a escolher antes de abrir o canal.

SituaçãoSaídaPor quê

Dois sinais de que o contexto passou do ponto: o provider tem dez campos com ritmos de mudança diferentes, e o consumidor lê o canal inteiro para usar um valor. Nos dois casos, dividir em canais menores devolve clareza. E vale desconfiar de contexto que existe para “evitar passar props” em uma tela de dois níveis: props resolvem melhor e com menos mistério.

Um caso em que o contexto é bom e ainda assim não é o primeiro passo: o tema. Se a única coisa que muda é a cor, uma classe no <html> e variáveis de CSS resolvem sem provider nenhum — o componente não precisa saber o tema, o navegador cuida. Contexto de tema compensa quando o valor é lido em JavaScript: o gráfico que escolhe a cor da linha, o selo que troca o texto, o botão que alterna. Antes de abrir o canal, pergunte se o consumidor realmente precisa do valor ou só precisa que o estilo mude.

Se o estado é grande e cheio de ações, o par useReducer mais contexto de dispatch é o padrão mais previsível — o reducer concentra a regra, o dispatch é estável e o componente que só dispara não redesenha. A aula Compound Components mostra a mesma ideia aplicada a um componente que distribui estado entre os seus filhos.

8. Erros comuns

Nenhum destes dá aviso no console; todos aparecem como valor errado ou tela que atualiza demais.

Para conferir a identidade sem instrumentar nada, um console.log no consumidor mostra cada redesenho. Com dois providers aninhados, o mesmo log mostra de onde veio cada valor:

cliente no balcão: Bento
cliente na loja: Ana

Para testar um consumidor, você monta o provider em volta dele — não existe consumidor sem canal. É um teste de três linhas: renderize <ClienteContexto.Provider value="Ana"><Selo /></ClienteContexto.Provider> e confira o texto. Se o componente lê dois canais, os dois providers entram. Isso é mais verboso que uma prop, e é a conta honesta do contexto: quem lê precisa de alguém abastecendo.

Se o número de linhas cresce sem parar, o valor publicado está mudando de identidade a cada desenho. Se o valor é sempre o padrão, procure o provider: ele pode estar no ramo errado, dentro de um componente que desenha depois, ou o canal pode ter sido criado duas vezes. A aula O useContext percorre os cinco casos com a caixa mostrando cada um.

Resumo

Contexto leva um valor de uma região da árvore para consumidores distantes: createContext cria o canal, o Provider abastece um ramo e useContext lê o provider mais próximo ou, sem provider, o valor padrão. Um canal por assunto; dados e ações separados; valor com identidade estável — primitivo quando der, useMemo quando depender de estado.

O valor padrão é valor de verdade, não aviso: se ele aparece quando você esperava o dado, o provider está fora do ramo ou o canal foi criado duas vezes. Para falhar cedo, crie com null e leia por um hook que lança erro com o nome do provider que faltou. E lembre que o contexto esconde a dependência: use para telas distantes, não para pai e filho nem para dado constante.

Para lembrar

  • createContext fora dos componentes, uma vez por canal.
  • .Provider value={...} delimita o ramo; fora dele vale o padrão.
  • React 19 aceita o canal como provider, sem .Provider.
  • Um canal por assunto: tema, cliente, carrinho, ações.
  • O React compara o valor por referência: objeto novo redesenha todos.
  • memo não segura consumidor de contexto que muda.
  • Separar dados e ações evita redesenho de quem só chama função.
  • Valor padrão não é “carregando”; value={undefined} publica undefined.
  • createContext(null) mais hook com erro é a rede de segurança.
  • Para pai e filho, prop; para bloco montado, children.
