O useImperativeHandle

A Ana tem um botão "Focar o nome" no formulário de encomenda: o cliente abre a tela, o botão põe o cursor no primeiro campo. O botão está fora do componente do campo, e focar é uma coisa que só o próprio campo sabe fazer. Até hoje a Ana resolvia isso passando o elemento do input para o pai — e o pai acabava com o campo inteiro nas mãos, podendo apagar o texto por baixo do React. Nesta aula ela aprende o useImperativeHandle: o jeito de um componente dizer "eu sei focar e eu sei limpar; o resto não é da sua conta".

Você vai aprender
  • Por que existem ações que o pai não consegue fazer sozinho.
  • O que é um handle e como uma ref deixa de ser "o elemento" e passa a ser "a API".
  • Como escrever useImperativeHandle(ref, () => ({ … })) e chamar os métodos de fora.
  • Como o React 19 entrega a ref por prop, sem forwardRef.
  • O que dá errado quando o pai recebe o elemento cru e escreve direto no DOM.
  • Por que o handle também tem array de dependências.
  • O que vale a pena expor, e o que é sinal de que o desenho está errado.

1. A cena: o botão que mora fora do campo

O formulário de encomenda tem uma caixa de texto para o nome do cliente e, acima dela, um botão "Focar o nome". Quando o cliente clica no botão, o cursor tem de pular para o campo. Parece pouco, e é exatamente o tipo de coisa que o React não faz por você: o foco é um estado do navegador, mora no elemento, e nenhuma prop o controla. Não existe focado={true} no vocabulário do JSX.

A primeira tentativa da Ana foi passar uma ref do App para o Campo, e o Campo a pendurou no input. Funcionou: o pai chamou entrada.current.focus() e o cursor apareceu. O problema veio depois, quando ela quis limpar o campo pelo mesmo caminho e escreveu entrada.current.value = "". O campo esvaziou na tela, o estado do componente continuou com o nome antigo, e a tela passou a mostrar duas verdades diferentes.

O useImperativeHandle existe para esse meio-termo. Em vez de o pai receber o elemento — com value, style, remove() e tudo o mais —, ele recebe um objeto pequeno, escrito pelo próprio componente, com os métodos que o componente decidiu publicar. Um handle é uma API com verbo, não um monte de propriedades. "Focar" e "limpar" são verbos; .value é um detalhe interno que vazou.

2. Um handle, três peças

A palavra imperative assusta e quer dizer apenas "por comando". No estilo declarativo, você diz como a tela deve ser e o React cuida do resto; no estilo imperativo, você manda fazer uma coisa agora — focar, rolar, tocar. Os dois convivem no React, e o hook é a porta oficial entre eles. As peças são sempre as mesmas três: alguém cria a ref, o componente se registra nela com o hook, e alguém chama um método.

ref
O objeto criado com useRef(null) pelo pai e entregue ao filho como prop. O .current é o que o filho preencher.
useImperativeHandle
O hook que registra no .current o objeto que o filho quer publicar. No projeto ele vem de import { useImperativeHandle } from "react"; aqui na caixa, escreva React.useImperativeHandle.
handle
O objeto publicado: { focar() { … } }. Um contrato pequeno, com os verbos que o pai pode usar.
método
Cada verbo do handle. É uma função comum, e por isso pode ler o estado do componente e chamar setAlgumaCoisa.
dependências
O terceiro argumento, um array: quando um valor usado dentro dos métodos muda, o handle é recriado com o valor novo.
forwardRef
O jeito antigo de receber a ref. No React 19 a ref chega como uma prop comum, e você não precisa dele.

Duas observações sobre versões, porque você vai encontrar as duas formas em código por aí. Antes do React 19, uma função componente não recebia ref como prop: era preciso embrulhar o componente em forwardRef e declarar (props, ref). Hoje basta declarar a prop, como qualquer outra: function Campo({ ref }). O forwardRef continua funcionando, e você vai vê-lo em tutoriais; não precisa dele em código novo.

A segunda observação é do nosso motor: os hooks mais comuns já estão no escopo das caixas, mas useImperativeHandle não está entre eles. Por isso o código da aula escreve React.useImperativeHandle. Num projeto de verdade, a primeira linha do arquivo importa o hook e o resto do código fica igual.

3. A primeira exposição: focar

O Campo guarda a ref do input numa variável interna e publica um único método, focar. O App recebe a ref do Campo e chama campo.current?.focar(). Repare no ponto de interrogação: antes de o filho montar, o .current é null, e o ?. evita o erro. No código inicial o hook não existe, então o clique não faz nada — a missão é escrevê-lo.

O Campo recebe a ref e não faz nada com ela. Registre um handle com o método focar(), que chama entrada.current.focus(). Depois clique em "Focar o nome": o cursor vai para o campo e o aviso muda para "Campo em foco".

function Campo({ ref }) {
  const [focado, setFocado] = useState(false);
  const entrada = useRef(null);

  return (
    <div>
      <input
        ref={entrada}
        placeholder="Nome do cliente"
        onFocus={() => setFocado(true)}
        onBlur={() => setFocado(false)}
      />
      <p>{focado ? "Campo em foco" : "Campo sem foco"}</p>
    </div>
  );
}

function App() {
  const campo = useRef(null);

  return (
    <div>
      <button onClick={() => campo.current?.focar()}>Focar o nome</button>
      <Campo ref={campo} />
    </div>
  );
}

function Campo({ ref }) {
  const [focado, setFocado] = useState(false);
  const entrada = useRef(null);

  React.useImperativeHandle(ref, () => ({
    focar() {
      entrada.current.focus();
    }
  }));

  return (
    <div>
      <input
        ref={entrada}
        placeholder="Nome do cliente"
        onFocus={() => setFocado(true)}
        onBlur={() => setFocado(false)}
      />
      <p>{focado ? "Campo em foco" : "Campo sem foco"}</p>
    </div>
  );
}

  return (
    <div>
      <button onClick={() => campo.current?.focar()}>Focar o nome</button>
      <Campo ref={campo} />
    </div>
  );
}

Vale ler o caminho do clique inteiro, porque ele mostra a diferença entre os dois mundos. O botão chama campo.current.focar() — um comando, do lado de fora. O método roda dentro do Campo, onde a entrada existe, e chama focus(), que é do navegador. O navegador dispara o evento focus, o onFocus do input roda, o estado focado vira true e o parágrafo muda. Nada disso passou pelo App: ele só sabia o verbo.

Se o botão estivesse dentro do próprio Campo, o handle não seria necessário — bastaria chamar entrada.current.focus() no onClick. A regra prática é essa: handle é para quando quem manda está fora e não tem acesso ao elemento. Quando o botão e o campo moram no mesmo componente, você está resolvendo um problema que não existe.

4. Por que não entregar o elemento cru

A tentação de economizar o hook é grande: basta passar ref={entrada} do App para o input e usar tudo. É o que o código inicial da segunda caixa faz. A Ana queria limpar o nome do cliente depois de enviar a encomenda; escreveu uma linha e o campo esvaziou. Mas o Caracteres continuava três, e o Cliente continuava "Ana".

O botão esvazia o campo escrevendo no DOM e o estado não fica sabendo. Troque a ref crua por um handle com o método limpar(), que chama setTexto(""), e clique em "Limpar o nome".

function Campo({ entrada }) {
  const [texto, setTexto] = useState("Ana");

  return (
    <div>
      <input ref={entrada} value={texto} onChange={(e) => setTexto(e.target.value)} />
      <p>Cliente: {texto || "(vazio)"}</p>
      <p>Caracteres: {texto.length}</p>
    </div>
  );
}

function App() {
  const entrada = useRef(null);

  return (
    <div>
      <button onClick={() => { entrada.current.value = ""; }}>Limpar o nome</button>
      <Campo entrada={entrada} />
    </div>
  );
}

Na prévia, logo depois do clique, o campo aparece vazio e o parágrafo continua "Cliente: Ana". O painel mostra o desencontro pelo outro lado: o input com value="Ana" e Caracteres: 3, porque ele lê o HTML que o React desenhou — e para o React o valor do campo nunca mudou. É o retrato de um componente com dois donos: o navegador achando uma coisa, o estado achando outra, e ninguém avisando.

Não é que escrever no DOM seja proibido. Rolar uma lista, como na aula do useLayoutEffect, é exatamente isso, e não tem nada de errado porque rolagem não é dado. O problema é a escrita que deveria ter passado pelo estado: o valor de um campo é dado do componente, e mexer nele por fora quebra a regra de um dado, um dono. Com o handle, o pai pede "limpe" e o filho decide como — no caso, mudando o estado, que é o caminho certo.

5. O que o painel mostra quando o DOM e o estado discordam

Essa discordância merece um parágrafo, porque ela é a causa de metade dos bugs estranhos de formulário. O React desenha o campo a partir do estado: se o estado diz "Ana", o campo mostra "Ana". Quando alguém escreve no elemento por fora, o navegador mostra outra coisa até o próximo desenho; nesse instante, os dois lados estão errados de um jeito diferente. Qualquer evento que dispare um desenho — um clique em outro botão, uma tecla, um temporizador — pode trazer o texto antigo de volta, e o leitor vê o campo "se consertar sozinho".

valor do campo (DOM): ""
cliente no estado: Ana

Um painel assim, com os dois valores lado a lado, é a melhor forma de diagnosticar. Se eles discordam, o culpado é sempre uma escrita fora do fluxo: atribuição em .value, innerHTML, manipulação com document.querySelector. A cura também é sempre a mesma: trazer a intenção para dentro do componente e publicá-la como método no handle.

Há um custo escondido em entregar o elemento cru, além do bug: o contrato vira "o campo todo". No dia em que a Ana trocar o <input> por um componente de máscara de telefone, o pai que escrevia entrada.current.value quebra, porque o que está lá dentro mudou. Com o handle, o pai chama limpar(), o contrato continua valendo, e a troca por dentro não vaza. É a mesma ideia de encapsulamento que você já usa ao escolher props em vez de passar o objeto inteiro.

6. O handle também tem dependências

Falta a parte que quase ninguém explica: o terceiro argumento do useImperativeHandle. Ele funciona como o array do useEffect e responde a uma pergunta simples: quando o handle deve ser recriado? Os métodos que você publica são funções criadas naquele desenho, e funções lembram das variáveis do desenho em que nasceram. Se o handle é criado uma vez e nunca mais, ele guarda os valores do primeiro desenho.

Na caixa, o Campo publica confirmar(), que monta um recado com o texto atual. O array está vazio, então o handle nasceu com o texto "Baguete" e ficou com ele. Digite "Croissant" no campo e clique em "Confirmar": aparece "Confirmado: Baguete". O estado está certo, o campo está certo, o handle está velho.

O handle foi criado uma vez e guardou o texto do primeiro desenho. Acrescente texto ao array de dependências, digite Croissant no campo e clique em "Confirmar".

function Campo({ ref }) {
  const [texto, setTexto] = useState("Baguete");
  const [recado, setRecado] = useState("Nada confirmado");

  React.useImperativeHandle(ref, () => ({
    confirmar() {
      setRecado("Confirmado: " + texto);
    }
  }), []);

  return (
    <div>
      <input value={texto} onChange={(e) => setTexto(e.target.value)} />
      <p>{recado}</p>
    </div>
  );
}

function App() {
  const campo = useRef(null);

  return (
    <div>
      <button id="confirmar" onClick={() => campo.current?.confirmar()}>Confirmar</button>
      <Campo ref={campo} />
    </div>
  );
}
<div>
  <button id="confirmar">Confirmar</button>

    <p>Nada confirmado</p>

</div>

Com [texto] no array, cada mudança no campo recria o handle, o método novo enxerga o valor novo, e o recado sai certo. Quando não há array nenhum, o handle é recriado em todo desenho — funciona, mas entrega um objeto novo a cada render, e qualquer coisa que compare identidade vai ver diferença. Na dúvida, liste as dependências: é a mesma disciplina do useEffect, e o motivo é o mesmo, o de não guardar uma foto velha do mundo.

Note que o conjunto de verbos não muda quando o handle é recriado: continua sendo { confirmar }. O pai não percebe nada, porque ele nunca guardou uma cópia do objeto — ele lê campo.current na hora do clique. Essa indireção é o que faz o mecanismo funcionar sem o pai precisar saber que houve recriação.

7. O que entra e o que não entra no handle

A pergunta de projeto é: o que publicar? A resposta curta é "o que só o filho sabe fazer". O foco, a rolagem interna, o play de um vídeo, o início de uma animação, a validação de um campo com máscara — coisas que dependem do elemento ou de um estado que o pai não tem. O que é dado deve ir por prop, porque prop é declarativa e o React consegue comparar.

O pai quer…HandleProp
que o cursor vá para o camposim: focar()não existe prop para foco
limpar o texto do camposim: limpar()ou controlar o valor por prop, se o pai já é dono
saber quantos itens há no carrinhonãosim: o dado desce e sobe por callback

Se a sua lista de verbos passa de dois ou três, pare e releia: provavelmente o pai está tentando controlar o filho por comando em vez de conversar por dados. Um handle com dez métodos é um componente que nunca aprendeu a receber props. O sintoma clássico é o método getValor(): se o pai precisa perguntar o valor, o valor deve estar no pai desde o começo — é o assunto da aula de elevar o estado.

Outro detalhe prático: o handle pode perfeitamente chamar setState, como o limpar() da segunda caixa faz. Ele roda dentro do componente, no mesmo lugar de qualquer outra função de evento, e as regras são as mesmas. O que ele não pode é ser chamado durante o desenho de outro componente: chamadas imperativas acontecem em eventos, efeitos ou temporizadores, nunca no corpo do render.

8. Os tropeços

O primeiro tropeço é esquecer que .current pode ser null. No primeiro desenho, o handle ainda não existe; se o seu evento disparar antes disso — um efeito que roda na montagem, por exemplo — a chamada quebra. O ?. resolve a chamada, e a mensagem abaixo é o que aparece sem ele:

TypeError: campo.current.focar is not a function

Essa mensagem tem duas leituras. Se campo.current é null, o filho não montou ou não recebeu a ref. Se é um objeto mas não tem focar, o nome do método no handle é outro — ou o hook não foi chamado. Vale conferir a assinatura do componente: com forwardRef o segundo parâmetro é a ref; sem ele, no React 19, a ref chega dentro das props e precisa ser desestruturada com o nome exato.

O segundo tropeço é usar useImperativeHandle para devolver o próprio elemento: useImperativeHandle(ref, () => entrada.current). Funciona e não resolve nada — é o elemento cru com uma camada extra de cerimônia. O terceiro é publicar o handle inteiro sem necessidade, coisa de quem veio de programação orientada a objetos e quer um this. Aqui, menos verbos é melhor.

Um último detalhe de leitura do painel: quando um componente quebra dentro de um evento, o React de produção não desenha uma tela de erro com a mensagem — ele para de atualizar aquele pedaço. Se um clique "não faz nada" e o console não mostra nada no painel, o caminho é abrir o console do navegador com F12, porque o erro foi para lá. Aqui na caixa, os erros de desenho aparecem como Erro: no painel; os de evento, não.

9. Cenários do dia a dia

Cenário 1: o botão "escrever avaliação"

Na página do produto, o botão "Escrever avaliação" abre o formulário e põe o cursor no campo de texto. O formulário é um componente à parte, com o próprio estado. O handle publica abrirEFocar(), que faz as duas coisas na ordem certa: muda o estado que mostra o campo e, num useEffect, chama focus() depois que o campo existe. O pai nem sabe que houve uma etapa no meio.

Cenário 2: o carrossel da vitrine

O carrossel de pães é um componente que guarda o índice atual. As setas ficam fora, na barra da seção, e chamam proximo() e anterior() pelo handle. O estado continua dentro do carrossel, onde pertence; o pai só empurra. Se amanhã o carrossel ganhar autoplay, o handle pode ganhar pausar() sem quebrar ninguém, porque o contrato só cresce.

Cenário 3: a busca que limpa tudo

O campo de busca da padaria tem um "x" que aparece quando há texto. O botão está fora do componente do campo, na barra de filtros. O campo publica limpar(), que zera o texto e avisa o pai pelo onBuscar("") — os dois caminhos convivem: prop para o dado que sobe, handle para a ação que só o filho sabe executar. Quando os dois são usados no mesmo componente, é sinal de que o desenho está são.

11. Resumo

O useImperativeHandle é a porta oficial entre o React declarativo e os comandos do navegador. O pai cria uma ref, o filho a recebe como prop e registra nela um objeto com os métodos que quer publicar; o pai chama esses métodos quando precisa. O elemento do DOM continua lá dentro, escondido, e o pai nunca recebe value, style ou remove(). É a diferença entre entregar a chave da casa e entregar o controle remoto do portão.

No React 19 a ref chega como prop comum, então não há forwardRef no caminho. Aqui nas caixas, o hook aparece como React.useImperativeHandle porque não está no escopo automático; num projeto, ele vem de import e o código é idêntico. Os métodos publicados podem ler estado e chamar setState — é isso que faz o handle ser a solução certa para limpar um campo sem criar dois donos para o mesmo dado.

E o array de dependências não é enfeite: ele decide quando o handle é recriado, e um handle velho age com valores velhos. Liste o que os métodos leem. Se você se pegar querendo publicar getValor() ou uma dúzia de métodos, é sinal de que o dado deveria subir por prop ou por callback. Guarde o handle para o que é comando: foco, rolagem, reprodução, validação pontual. O resto é conversa por dados, que é onde o React brilha.

Para lembrar

  • Handle é a API que o filho publica numa ref, não o elemento do DOM.
  • React.useImperativeHandle(ref, () => ({ focar() { … } }), [deps]).
  • No React 19 a ref é prop: function Campo({ ref }); forwardRef é código antigo.
  • O pai chama campo.current?.focar(); antes da montagem, o .current é null.
  • Métodos do handle podem chamar setState: é assim que o estado continua sendo um só.
  • Escrever em .value por fora esvazia a tela e deixa o estado para trás.
  • Array de dependências vazio congela os valores do primeiro desenho.
  • Publique o que só o filho sabe fazer; dado vai por prop.
  • Handle com muitos verbos é sintoma de componente que não aprendeu a receber props.
  • Chamada imperativa acontece em evento ou efeito, nunca no corpo do render.
