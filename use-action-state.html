O useActionState

O formulário de encomenda da Ana já usa uma ação, mas o resultado ficou espalhado: um estado para a mensagem, outro para o erro, outro para o “enviando”. No React 19 existe um hook que devolve os três de uma vez, com uma diferença importante — é a ação que decide o novo estado, devolvendo o valor. Nesta aula a Ana troca três estados por um e aprende a ler o pendente sem contar clique.

Você vai aprender
  • O que o useActionState devolve: estado, ação e pendente.
  • A nova assinatura da ação: (estadoAnterior, dados) => novoEstado.
  • Como validar e devolver o erro sem criar estados paralelos.
  • Como usar o pendente para desabilitar o botão e trocar o rótulo.
  • Por que o resultado anterior continua na tela durante o envio.
  • Quando um useState comum já resolve e o hook é exagero.
  • As armadilhas: formulário que se limpa no erro, valor inicial instável, ação que lança.

1. A cena: três estados para um formulário

A encomenda da Ana já usa action, então o envio está resolvido. O que sobrou foi o depois: mostrar “encomenda registrada” quando dá certo, “informe o nome” quando falta o nome, e “enviando…” enquanto a resposta não chega. Para isso ela tem três useState — mensagem, erro e pendente — e três lugares onde eles podem ficar desalinhados.

O desalinhamento aparece na prática. O envio falha, ela esquece de limpar a mensagem de sucesso e a tela mostra as duas coisas ao mesmo tempo. Ela desabilita o botão no lugar errado e a pessoa fica sem poder reenviar. Ela atualiza o erro dentro de uma função assíncrona e o erro aparece depois que o formulário já foi limpo.

O useActionState existe para juntar esse trio. Ele recebe a ação e um valor inicial, e devolve três coisas em uma linha: o estado que a ação produziu, a ação já embrulhada para usar no formulário e o pendente do envio. É o mesmo padrão de useState, com uma diferença de dono: quem escreve o estado é a ação, não você.

Essa inversão é o coração do hook. Em vez de a ação chamar setMensagem e setErro, ela devolve o novo estado. O React guarda esse retorno e o entrega na próxima renderização. A ação fica uma função pura de dados — recebe o estado anterior e os campos, devolve o próximo estado —, o que a torna fácil de testar e de mover para o servidor depois.

2. O que o hook devolve

A chamada tem a forma const [estado, acao, pendente] = React.useActionState(funcao, inicial). O primeiro elemento é o estado atual; o segundo, uma ação pronta para o action do formulário ou um formAction de botão; o terceiro, um booleano que fica verdadeiro do envio até a resposta.

estado
O que a última execução da ação devolveu. Começa com o valor inicial e só muda quando a ação termina.
ação
A função embrulhada pelo hook. Vai no action do formulário ou no formAction de um botão.
pendente
true enquanto a ação roda. É o que desabilita o botão e troca o rótulo.
estado anterior
O primeiro argumento da sua função: o estado da última execução. Serve para somar, manter mensagem antiga ou contar tentativas.
valor inicial
O estado antes do primeiro envio. Precisa ter a mesma forma do que a ação devolve.

Um detalhe do motor deste guia: o useActionState não está no escopo das caixas, então o código escreve React.useActionState. No seu projeto, a primeira linha do arquivo importa o hook — import { useActionState } from "react" — e você chama pelo nome. É o mesmo hook, com o endereço completo.

E vale saber o que ele era antes: no React 18 o mesmo hook se chamava useFormState e vinha do react-dom. Se você encontrar esse nome em código ou tutorial, é o mesmo comportamento com outro endereço. O React 19 renomeou para deixar claro que ele serve a qualquer ação, não só a formulário.

3. Validar e devolver o erro

O primeiro uso é a validação. A ação olha os campos, decide se dá para seguir e devolve um objeto com o que a tela precisa: uma mensagem de erro, ou uma de sucesso. A tela não pergunta “deu certo?”; ela desenha o que o estado diz.

A caixa começa com a ação que não valida nada. Enviar o formulário vazio registra uma encomenda sem nome — e o pior é que ninguém percebe até o pão chegar sem dono. A missão é trocar o estado paralelo pelo retorno da ação.

A ação registra encomenda até com o nome vazio. Use React.useActionState para o estado voltar da ação: sem nome, ela devolve Informe o nome do cliente; com nome, Encomenda de Maria registrada.

function App() {
  const [recado, setRecado] = useState("nada ainda");

  async function enviar(dados) {
    const nome = String(dados.get("nome") || "").trim();
    setRecado("Encomenda de " + nome + " registrada");
  }

  return (
    <form action={enviar}>
      <input name="nome" />
      <button type="submit">Encomendar</button>
      <p>{recado}</p>
    </form>
  );
}

    const nome = String(dados.get("nome") || "").trim();
    if (!nome) {
      return { erro: "Informe o nome do cliente", mensagem: anterior.mensagem };
    }
    return { erro: "", mensagem: "Encomenda de " + nome + " registrada" };
  }, inicial);

  return (
    <form>
      <input name="nome" />
      <button formAction={acao}>Encomendar</button>
      <p>{estado.erro || estado.mensagem || "nada ainda"}</p>
    </form>
  );
}

Na solução, o botão vazio mostra o erro e o botão com “Maria” mostra a confirmação — e o useState do recado desapareceu. O estado agora é um objeto com dois campos, e a tela escolhe o que mostrar com um ||: erro primeiro, mensagem depois, texto padrão se não houver nenhum.

Repare na assinatura (anterior, dados). O primeiro argumento é o estado da execução anterior — foi dele que a solução copiou anterior.mensagem para não apagar a confirmação antiga ao mostrar um erro novo. O segundo é o FormData, o mesmo da aula de ações. A ordem importa: dados primeiro, estado depois, e o erro é silencioso (o hook devolve undefined no lugar do estado).

Há um detalhe que confunde na primeira leitura: o estado é um objeto novo a cada execução, e o React compara por identidade. Se a ação devolver o mesmo objeto de antes, o React entende que nada mudou e não redesenha. Isso é bom para desempenho e péssimo quando você tenta “forçar” uma atualização devolvendo o estado anterior sem mudar nada — a tela fica como está, e você acha que a ação não rodou.

4. O pendente, de graça

O segundo item que o hook entrega é o pendente. Ele fica verdadeiro do envio até a ação terminar — não até o próximo desenho, não até a promessa resolver sozinha. É exatamente o intervalo em que o botão precisa estar desligado e o rótulo precisa dizer “enviando…”.

A caixa usa um servidor controlado por você: a encomenda fica pendurada até o botão “servidor responde”. Assim dá para ver o estado pendente sem correr contra o relógio — e, quando o servidor responde, o estado volta e o botão reabre.

O botão pode ser clicado várias vezes durante o envio. Pegue o terceiro item do React.useActionState e use para desabilitar o botão e trocar o texto para Enviando… enquanto a ação roda.

let responder = null;

function gravar(nome) {
  return new Promise((ok) => {
    responder = () => ok({ erro: "", mensagem: "Encomenda de " + nome + " registrada" });
  });
}

const inicial = { erro: "", mensagem: "" };

    if (!nome) return { erro: "Informe o nome do cliente", mensagem: "" };

Duas consequências práticas. A primeira: a ação precisa ser async e precisa esperar o que é lento. Se ela dispara o pedido e retorna antes, o pendente cai cedo demais. A segunda: o pendente é do formulário, não da tela — se você tem dois formulários com dois hooks, cada um tem o seu. Se você quer um só status para o formulário inteiro, o useFormStatus da aula anterior é a alternativa.

5. O estado anterior: a lista que cresce

O primeiro argumento da ação não é enfeite. Ele é o único jeito de acumular: cada execução recebe o estado que a anterior devolveu, então a ação pode somar em vez de substituir. Sem ele, a única coisa que a tela pode mostrar é o resultado do último envio.

A Ana quer o histórico das encomendas da sessão — não para guardar em banco, mas para conferir o que já foi registrado sem sair da página. O código da caixa faz o contrário: a cada envio ele troca a lista inteira pela encomenda nova, então a lista cresce até um item. A missão é acumular.

Cada envio substitui o histórico pela encomenda nova. Com React.useActionState, use o estado anterior para construir um array novo: [...anterior.lista, texto]. Depois de duas encomendas, a lista precisa ter dois itens.

let responder = null;

function gravar(nome) {
  return new Promise((ok) => {
    responder = () => ok("Encomenda de " + nome + " registrada");
  });
}

function App() {
  const [lista, setLista] = useState([]);

  async function enviar(dados) {
    const nome = String(dados.get("nome") || "").trim();
    if (!nome) return;
    const texto = await gravar(nome);
    setLista([texto]);
  }

  return (
    <form action={enviar}>
      <input name="nome" />
      <button type="submit">Encomendar</button>
      <button type="button" id="responder" onClick={() => responder && responder()}>
        servidor responde
      </button>
      <ul>
        {lista.map((texto, i) => (
          <li key={i}>{texto}</li>
        ))}
      </ul>
    </form>
  );
}

Duas encomendas, dois itens na lista. O segredo está em três palavras: ...anterior.lista. O espalhamento copia os itens que já estavam lá e o texto novo entra no fim, formando um array novo. O array antigo continua intacto — e é isso que o React precisa para perceber a mudança.

Comparar por identidade é o que faz o React redesenhar. Um array novo, mesmo com o mesmo conteúdo, é um valor diferente aos olhos dele. Um array mutado — com push — é o mesmo objeto, e o React conclui que nada mudou. Se a lista não atualizar na tela depois de um envio, procure um push; troque por espalhamento e o problema desaparece.

O mesmo raciocínio vale para qualquer acumulação: um total de fiado, um contador de tentativas, uma mensagem que junta avisos. O estado anterior é a memória da ação — e o hook entrega essa memória de graça, sem que você precise guardá-la em um useRef ou em uma variável de módulo.

6. Durante o envio, o resultado anterior fica na tela

Tem um comportamento do hook que parece mágica e é só consequência do lugar onde a ação roda: o estado só muda quando a ação termina. Enquanto a promessa está aberta, a tela continua mostrando o resultado anterior — a confirmação do pedido passado, o erro da tentativa passada. Nada de tela em branco no meio do envio.

O motivo é que a ação de formulário roda dentro de uma transição, como você viu na aula de useTransition. O React segura o desenho novo até a transição terminar, e só então pinta o resultado. As atualizações de estado feitas no meio do caminho são aplicadas juntas, no fim — não uma a uma, conforme cada await resolve.

Isso explica também um comportamento que surpreende quem vem de código imperativo: limpar o estado no começo da ação não produz tela vazia. O setRecado("") fica guardado junto com o resto e é aplicado quando a transição fecha. Ele não “pisca” — ele simplesmente deixa o estado novo errado, porque apagou o que devia estar sendo mostrado.

A consequência prática: você não precisa se proteger contra a tela vazia. Precisa decidir o que a pessoa deve ver durante a espera. Se o resultado anterior ainda faz sentido, deixe-o ali e use o pendente no botão para sinalizar “enviando de novo…”. Se não faz, é sinal de que o estado guarda informação demais e a tela deveria mostrar menos.

E, quando a ação termina com erro, o erro substitui o resultado anterior — porque agora existe um estado novo de verdade. É por isso que um formulário bem feito alterna entre “registrada com sucesso” e “informe o nome” sem acumular as duas mensagens: existe um campo só, e a ação decide o valor dele a cada envio.

7. Quando o hook é exagero

Nem todo formulário precisa dele. Se a ação só precisa avisar que deu certo e a tela mostra um texto fixo, um useState com o recado resolve — e é mais fácil de ler. O useActionState ganha quando o resultado é dado: erro de validação por campo, mensagem que vem do servidor, número de protocolo, lista de horários disponíveis.

Outra comparação útil: o useFormStatus responde “está enviando?” e nada mais; o useActionState responde “está enviando? e o que voltou?”. Se você só precisa desabilitar o botão, o primeiro é menor. Se você precisa mostrar o que o servidor disse, o segundo evita o estado paralelo.

Uma regra de bolso: se você escreveria três useState para o resultado de um envio, use o hook. Se escreveria um, comece com o useState e migre quando o segundo aparecer. Migrar é mecânico — mover os campos para um objeto e devolver esse objeto da ação.

8. As armadilhas

Quatro problemas aparecem sempre, e todos têm a ver com o ciclo do formulário, não com o hook em si. A tabela resume; os parágrafos explicam os dois mais caros.

O primeiro é o mais surpreendente. O React limpa os campos não controlados depois que a ação termina — qualquer ação, inclusive a que devolveu erro. Se a validação falha e você quer que a pessoa corrija o que digitou, o campo não pode ter sido limpo. A saída é devolver o valor dentro do estado e usar defaultValue no campo, ou validar no cliente antes de enviar e só chamar a ação quando os dados estiverem completos.

    at enviar (app/encomenda/acao.jsx:14:11)

O quarto é o que derruba a página. Ação que lança exceção não devolve estado: o React considera o envio falho, mostra o erro no console e não atualiza a tela. Em produção, isso vira a tela de erro do framework. Trate dentro da ação — try/catch e devolver { erro: ... } — e a mensagem chega na tela como qualquer outro estado.

Vale ainda um cuidado com o valor inicial: ele precisa ser estável. Um objeto literal criado no useActionState é recriado a cada renderização e, embora o React só use o primeiro, ler o código fica confuso. Declare o inicial fora do componente, como nas caixas desta aula.

9. Cenários do dia a dia

Cenário 1: a validação que apagava o nome

A Ana validou o nome dentro da ação e devolveu o erro. O campo se limpou no mesmo instante, e a cliente, que tinha digitado “Maria Aparecida”, viu o formulário vazio com a mensagem “informe o nome”. O conserto foi devolver também o nome no estado e usá-lo em defaultValue — assim o campo reabre preenchido, com o erro embaixo.

Cenário 2: o pendente que nunca aparecia

Ela tirou o await da ação “para ficar mais rápido”, e o pendente passou a cair no mesmo instante. Sem espera, não há intervalo — e o botão nunca fica desabilitado de verdade. A ação precisa esperar o que é lento; a velocidade vem de a resposta ser rápida, não de o código fingir que ela já chegou.

Cenário 3: o estado que sobreviveu à troca de formulário

Ela usou o mesmo hook para a encomenda e para o cadastro de pão, e a mensagem de um apareceu no outro. Cada formulário precisa do seu useActionState: o estado é local ao componente que chamou o hook. Se dois formulários precisam do mesmo resultado, o estado sobe para o pai e desce por prop.

const [estado, acao, pendente] = React.( async (, dados) => { return { erro: "", mensagem: "ok" }; }, { erro: "", mensagem: "" } );

Dica: a primeira é o nome do hook — o mesmo que aparece no título da aula. A segunda é o estado da execução passada, que serve para preservar uma mensagem antiga ou somar tentativas; o segundo argumento é o FormData com os campos.

11. Resumo

O useActionState devolve três coisas em uma linha: o estado que a ação produziu, a ação pronta para o formulário e o pendente do envio. A ação muda de assinatura — recebe o estado anterior e o FormData, devolve o novo estado — e deixa de chamar set para qualquer coisa. Um estado só, com os campos que a tela precisa: erro, mensagem, tentativas.

O pendente vem junto e dispensa o setEnviando(true/false): ele é verdadeiro do envio até a promessa resolver, e é a base do botão desabilitado com “enviando…”. E o estado só troca quando a ação termina, o que mantém o resultado anterior na tela durante a espera — em vez de piscar em branco.

As armadilhas vêm do ciclo do formulário: o React limpa os campos não controlados ao fim de qualquer ação, inclusive a que devolveu erro; ação que lança exceção não devolve estado; ação sem await não tem pendente. Trate dentro da ação, devolva objeto com a mesma forma do inicial e declare o inicial fora do componente.

Falta a última peça do trio do React 19: mostrar o resultado antes de ele existir. É o useOptimistic, que pinta o item novo na lista enquanto o servidor decide — e desfaz sozinho quando a resposta é “não”.

  • O estado só muda quando a ação termina: o resultado anterior fica na tela.
