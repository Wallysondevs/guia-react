useCallback na Prática

A Ana já sabe que o useCallback guarda uma função entre desenhos. O que ela ainda não sabia é quanto isso custa quando falta: a cada tecla no campo de busca, dois componentes memoizados desenham de novo porque recebem uma função nova. Nesta aula ela usa o useCallback onde ele realmente importa — na dupla com o useMemo, nas ações que saem de hooks próprios e nas dependências curtas com a forma funcional do set.

Você vai aprender
  • Por que uma função criada no corpo do componente derruba o memo do filho.
  • A ajustar a dupla: useMemo para os dados, useCallback para as ações.
  • A devolver ações estáveis de um hook próprio.
  • Como manter o array de dependências curto usando a forma funcional do set.
  • Onde o useCallback importa de verdade: prop, efeito, listener e contexto.
  • Quando ele é exagero e o que o React Compiler muda nessa conversa.
  • Como ler a corrente de dependências sem se perder.

1. A cena: cada tecla redesenha a lista

A página de busca da padaria tem um campo, um filtro e uma lista. O campo guarda o texto; a lista filtra os pães; o filtro é um botão que alterna entre doces e salgados. A Ana digitou "queijo" e sentiu o campo engasgar. No console, com um contador de desenhos, viu a lista desenhar uma vez por tecla.

No console, o contador dentro da lista mostrava a cascata:

desenhou a lista (2)
desenhou a lista (3)
desenhou a lista (4)

O que a incomodou foi o motivo. A lista recebe os pães filtrados, e os pães não mudaram por causa da letra digitada. O botão de filtro recebe a função que troca o filtro, e essa função também não mudou de comportamento. Os dois componentes estavam embrulhados com memo. Mesmo assim, desenhavam.

A causa é a mesma das duas aulas anteriores, vista do outro lado: o memo compara as props por referência, e o pai recria o array e a função a cada desenho. O array precisa de useMemo; a função, de useCallback. Sem os dois, o memo dos filhos é decoração.

Esta aula é sobre o segundo. E sobre uma coisa que ninguém conta: o useCallback também pode ser exagero. Função inline não é problema por si só; ela é problema quando cruza uma fronteira que compara referências.

2. Toda função nasce nova

Dentro do corpo de um componente, uma função declarada é criada a cada desenho. Não é um detalhe de implementação: é o que permite a função enxergar o estado daquele desenho. () => setFiltro("doce") criada no desenho 7 carrega o setFiltro do desenho 7; no desenho 8, outra função é criada.

Para o JavaScript, tudo certo. Para o memo de um filho, é uma prop nova a cada vez. E a comparação que o filho faz não olha o corpo da função: olha a referência. Duas funções com o mesmo corpo e referências diferentes são props diferentes.

função inline
A função escrita direto na prop: onClick={() => setX(1)}. Nova a cada desenho.
useCallback
Guarda a função entre desenhos e devolve a mesma referência enquanto as dependências não mudam.
dependências
O array que decide quando a função é recriada. Liste o que a função lê de fora.
ação estável
Uma função que não muda de referência entre desenhos: o que hooks próprios costumam devolver.
corrente
A sequência de dependências que liga um valor ao outro: um array memoizado que depende de uma função memoizada, que depende de um estado.

Vale repetir o que o useCallback não faz: ele não impede a função de ser chamada, não congela o valor que ela lê e não deixa o componente mais rápido por si só. Ele só devolve a mesma referência entre desenhos. Quem aproveita isso é outra coisa — o memo do filho, a lista de dependências de um efeito, o comparador de um contexto.

3. A dupla: dados com useMemo, ações com useCallback

Na caixa, a lista e o filtro são componentes memoizados. O pai cria o array filtrado e a função de filtrar no corpo, então as duas props mudam a cada desenho — inclusive quando o que muda é só o aviso. Clique em Trocar aviso e veja os dois contadores subirem.

A lista e o filtro desenham a cada troca de aviso. Envolva o filter em useMemo com [filtro] e a função aoFiltrar em useCallback com []. Depois clique em Trocar aviso.

const PAES = [
  { nome: "sonho", tipo: "doce" },
  { nome: "pão francês", tipo: "salgado" },
  { nome: "pão de queijo", tipo: "salgado" },
];

let desenhosLista = 0;
let desenhosFiltro = 0;

const Lista = memo(function Lista({ itens }) {
  desenhosLista = desenhosLista + 1;
  return <p>lista desenhada: {desenhosLista} ({itens.length} pão(es))</p>;
});

const Filtro = memo(function Filtro({ aoFiltrar }) {
  desenhosFiltro = desenhosFiltro + 1;
  return (
    <div>
      <p>filtro desenhado: {desenhosFiltro}</p>
      <button id="doce" onClick={() => aoFiltrar("doce")}>Só doces</button>
    </div>
  );
});

function App() {
  const [filtro, setFiltro] = useState("todos");
  const [aviso, setAviso] = useState("Padaria aberta");

  const itens = PAES.filter((p) => filtro === "todos" || p.tipo === filtro);
  const aoFiltrar = (valor) => setFiltro(valor);

  return (
    <div>
      <button id="trocar" onClick={() => setAviso(aviso === "Padaria aberta" ? "Forno quente" : "Padaria aberta")}>
        Trocar aviso
      </button>
      <p>{aviso}</p>
      <Filtro aoFiltrar={aoFiltrar} />
      <Lista itens={itens} />
      <p>filtro atual: {filtro}</p>
    </div>
  );
}

O painel do código inicial mostra os dois contadores em 1, porque só houve a montagem. Depois do clique, o código antigo mostra 2 nos dois; a solução continua em 1. Duas props estáveis, dois filhos parados.

Repare nas dependências diferentes: o useMemo depende de [filtro], porque o array muda quando o filtro muda; o useCallback tem [], porque a função só usa setFiltro, que o React garante ser sempre o mesmo. Essa assimetria é normal e é o assunto da seção 5.

E repare no que acontece quando você clica em Só doces: o filtro muda, o array é recalculado, a lista desenha de novo — agora sim por um motivo. O Filtro continua parado, porque a função dele não mudou. É o comportamento que se quer: trabalho só onde houve mudança real.

4. Ações que vêm de hooks próprios

Quando o estado e as ações saem para um hook próprio, o useCallback vira quase obrigatório. Um hook que devolve { itens, adicionar } cria adicionar a cada desenho do componente que o usa — e todos os filhos que recebem essa função desenham junto. O hook é o lugar certo para estabilizar: quem devolve a ação garante a referência.

O botão está com memo, mas adicionar é recriada a cada desenho do hook. Envolva a função em useCallback com [] e use a forma funcional no setItens. Depois clique duas vezes em Adicionar sonho.

function useCarrinho() {
  const [itens, setItens] = useState([]);
  const adicionar = (nome) => {
    setItens((lista) => [...lista, nome]);
  };
  return { itens, adicionar };
}

let desenhos = 0;
const Botao = memo(function Botao({ adicionar }) {
  desenhos = desenhos + 1;
  return (
    <div>
      <button id="add" onClick={() => adicionar("sonho")}>Adicionar sonho</button>
      <p>botão desenhado: {desenhos}</p>
    </div>
  );
});

function App() {
  const { itens, adicionar } = useCarrinho();

  return (
    <div>
      <Botao adicionar={adicionar} />
      <p>itens na sacola: {itens.length}</p>
    </div>
  );
}

O painel depois dos dois cliques mostra o contraste: no código antigo, botão desenhado: 3 (uma montagem e dois cliques); na solução, botão desenhado: 1 e itens na sacola: 2. A sacola cresceu, o botão não redesenhou — ele só chama uma função que não mudou.

Note que a função usa a forma funcional do set ((lista) => [...lista, nome]). Não é detalhe de estilo: sem ela, a função precisaria ler itens, e aí itens teria de estar nas dependências — o que recriaria a função a cada item adicionado, e o memo do botão cairia. A forma funcional é o que permite o [] honesto.

5. Dependências curtas com a forma funcional

A terceira caixa mostra o padrão que mais aparece em código revisado: um useCallback com a dependência total, que muda a cada clique e recria a função. O filho memoizado desenha sempre. A missão é trocar para a forma funcional e esvaziar o array.

A função somar depende de total, então muda a cada clique. Use setTotal((t) => t + 1) e deixe as dependências []. Depois clique duas vezes em Somar um pão.

let desenhos = 0;
const BotaoSomar = memo(function BotaoSomar({ somar }) {
  desenhos = desenhos + 1;
  return (
    <div>
      <button id="somar" onClick={somar}>Somar um pão</button>
      <p>botão somar desenhado: {desenhos}</p>
    </div>
  );
});

function App() {
  const [total, setTotal] = useState(0);
  const somar = useCallback(() => setTotal(total + 1), [total]);

  return (
    <div>
      <BotaoSomar somar={somar} />
      <p>total: {total}</p>
    </div>
  );
}

Depois dos dois cliques, o código antigo mostra botão somar desenhado: 3 e a solução 1, com total: 2 nos dois. O resultado é o mesmo; o trabalho é que muda.

A regra que fecha a seção: se a função só precisa do valor anterior, use a forma funcional. Ela deixa o array vazio e a referência estável. Se a função precisa de outro valor — um nome digitado, um filtro escolhido —, esse valor entra nas dependências, e aí a função muda quando ele muda, o que costuma ser o correto: o filho deve desenhar porque a ação agora é outra.

6. Onde o useCallback importa de verdade

Quatro lugares, e vale reconhecer cada um. O primeiro é a prop de um componente com memo, que você acabou de ver. O segundo é a lista de dependências de um useEffect: uma função nova a cada desenho faz o efeito rodar em todo desenho, e efeitos costumam fazer coisas caras — buscar, inscrever, medir.

O terceiro é o listener. Um efeito que faz document.addEventListener("keydown", aoTeclar) depende da função para remover o listener antigo; sem estabilidade, cada desenho remove e inscreve de novo, e o console mostra o vaivém:

inscrevi o listener (1)
removi o listener (1)
inscrevi o listener (2)

O quarto é o contexto. Um provider que publica { cliente, sair } cria um objeto novo a cada desenho, e todos os consumidores desenham junto. A receita é useMemo no objeto e useCallback nas funções que ele carrega — os dois juntos, sempre na mesma ordem.

Fora desses quatro, o useCallback raramente paga. Um onClick em um <button> comum não tem comparação de props a fazer: a função nova é descartada no desenho seguinte e o custo é irrelevante. Embrulhar cada handler "por garantia" só deixa o componente mais difícil de ler.

7. O custo e o exagero

O useCallback guarda a função e compara as dependências a cada desenho. O custo é pequeno, mas não é zero — e, principalmente, cada um deles é uma chance de errar a lista de dependências. Uma dependência a menos produz a clássica função que lê o valor antigo; uma a mais recria a função sem necessidade e anula o memo que ela deveria proteger.

Há também um efeito colateral na leitura do código: quando tudo é useCallback, o componente deixa de parecer uma função que desenha e passa a parecer um quebra-cabeça de referências. Quem chega depois precisa reconstruir o raciocínio. O comentário curto ("estável para o BotaoSomar") resolve boa parte disso.

E o mesmo recado das outras aulas: com o React Compiler ligado no projeto, a memoização de funções passa a ser automática. Ele não vem ligado por padrão no React 19, e a recomendação oficial é usar useCallback como exceção, quando a medição ou o contrato de uma prop memoizada exigirem. Sem o compilador, a regra prática é: estabilize funções que cruzam uma fronteira de comparação; deixe as outras em paz.

8. Lendo a corrente de dependências

Quando um valor memoizado alimenta outro, as dependências formam uma corrente. Um array memoizado que usa uma função memoizada depende daquela função; se a função muda, o array refaz. Ler a corrente de baixo para cima evita a maior parte dos bugs de identidade.

const aoFiltrar = useCallback((valor) => setFiltro(valor), []);
const itens = useMemo(() => filtrar(filtro), [filtro]);
const resumo = useMemo(() => resumir(itens), [itens]);
const ctx = useMemo(() => ({ itens, aoFiltrar }), [itens, aoFiltrar]);

Nesse trecho, aoFiltrar não depende de nada e nunca muda; itens depende do filtro; resumo depende de itens; e o objeto do contexto depende dos dois. Se alguém trocar o useCallback por uma função inline, a corrente inteira se rompe: a função muda, o contexto muda, todos os consumidores desenham — e o sintoma aparece longe da causa.

Duas dicas de leitura. A primeira: se um useMemo depende de um objeto que veio de outro useMemo, confira se o de baixo está estável; um objeto novo em baixo derruba tudo em cima. A segunda: prefira dependências primitivas. Um useMemo que depende de filtro (texto) é mais fácil de acertar do que um que depende de um objeto de configuração inteiro.

9. Cenários do dia a dia

Cenário 1: o useCallback resolveu a lista e quebrou o filtro

A Ana estabilizou a função de filtrar e a lista parou de redesenhar. Só que o filtro mostrava sempre o primeiro valor: a função tinha dependências [] e lia um estado. O clássico valor velho. O conserto é incluir o valor lido no array — e aceitar que a função mude quando ele muda, que é o correto naquele caso.

Cenário 2: o efeito que busca a cada tecla

A busca estava em um efeito com dependência [aoBuscar], e aoBuscar era criada no corpo do componente. Resultado: uma requisição por tecla, inclusive quando a tecla era do campo de CEP. Estabilizar a função com useCallback, com o termo nas dependências, deixou uma busca por mudança real de termo.

Cenário 3: o botão que nunca atualiza o rótulo

Um botão memoizado recebia aoEnviar estável e texto; o texto vinha de uma prop que o pai montava com uma função memoizada de dependências vazias, e o rótulo ficou congelado. O problema não era o useCallback do botão: era o useMemo do pai com dependências incompletas. Corrente quebrada em cima, sintoma embaixo.

11. Resumo

Toda função criada no corpo do componente é nova a cada desenho. O useCallback guarda essa função e devolve a mesma referência enquanto as dependências não mudam. Ele serve para quem compara referências: o memo de um filho, a lista de dependências de um efeito, o listener que precisa ser removido com a mesma função, o objeto publicado em um contexto.

A dupla produtiva é useMemo para os dados e useCallback para as ações; um sem o outro deixa a otimização pela metade. Dentro de hooks próprios, a responsabilidade é de quem devolve a ação: o hook entrega funções estáveis. E a forma funcional do set é o que permite manter o array vazio sem ler valor velho.

Como sempre: medir, estabilizar o que cruza fronteira e deixar o resto em paz. Função inline não é pecado; ela só custa caro quando encontra uma comparação de props do outro lado. E, com o React Compiler no futuro, boa parte disso vira automático — o que não dispensa entender a corrente de dependências, porque é ela que explica os bugs de hoje.

Para lembrar

  • Função no corpo do componente nasce de novo a cada desenho.
  • useCallback(fn, [deps]) devolve a mesma referência enquanto as deps não mudam.
  • Ele não guarda resultado nem impede a chamada: só estabiliza a referência.
  • Dupla certa: useMemo para dados, useCallback para ações.
  • Hook próprio que devolve ação deve devolver ação estável.
  • Forma funcional no set permite [] sem valor velho.
  • Importa em: prop de memo, dep de efeito, listener, contexto.
  • Não importa em: onClick de botão comum, função que ninguém compara.
  • Corrente de dependências: objeto novo embaixo derruba tudo em cima.
  • React Compiler memoiza sozinho — e não vem ligado por padrão.
