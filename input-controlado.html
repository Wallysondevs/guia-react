Input Controlado

A Ana está montando o cadastro do site da padaria: nome, e-mail, senha, telefone e um campo de busca. Ela escreveu todos com a mesma tag, do mesmo jeito, e o resultado ficou estranho — a senha aparece para quem está do lado, o e-mail abre o teclado de letras no celular, o telefone aceita letra. Nesta aula ela aprende o que diferencia um input do outro: o atributo type, os atributos de configuração e o fato de que o valor que chega ao estado é sempre texto.

Você vai aprender
  • O que todo input controlado tem em comum, em uma revisão rápida.
  • O que o atributo type muda — e o que ele não muda.
  • Os tipos que resolvem o dia a dia: texto, e-mail, senha, busca, telefone, data e número.
  • A diferença entre atributo de configuração e estado que muda.
  • Por que o valor do campo chega como string, mesmo em campo numérico.
  • Como converter e formatar o texto sem que o cursor pule.
  • Por que um input é uma linha só, e quando o campo precisa de outra tag.

1. A cena: cinco campos e uma tag só

A padaria da Ana precisa de um cadastro simples: o cliente digita o nome, o e-mail, uma senha, o telefone e, se quiser, procura um pão no campo de busca. Ela abriu o editor e escreveu cinco campos iguais, mudando só o rótulo de cada um. Funcionou do jeito que funciona uma folha em branco: todos aceitam qualquer coisa. A senha aparece em letras legíveis na tela, o telefone aceita "abc", o e-mail aceita "maria" sem arroba, e no celular o teclado que sobe é o de letras, mesmo no campo de telefone.

Nada disso é culpa do React. É o comportamento padrão do elemento input: sem instruções, ele é um campo de texto de uma linha. O que diz a ele como se comportar é um atributo chamado type. Trocar type="text" por type="email" não muda a ligação com o estado — muda o teclado, a validação nativa e, no caso da senha, o que aparece na tela. É um atributo pequeno com efeito grande, e é por onde esta aula começa.

Antes de seguir, vale um aviso de roteiro: nesta aula o foco é o elemento. O par value + onChange, o ciclo de uma tecla por vez e o campo que trava sem onChange já foram contados com calma na aula Entrada Controlada. Se algum desses pontos ainda estiver nebuloso, vale voltar lá primeiro; daqui para a frente eu assumo que você reconhece o par.

2. O que todo input controlado tem em comum

Independente do tipo, um campo controlado é sempre a mesma dupla: value recebendo o estado e onChange devolvendo o texto novo para o estado. O tipo muda a aparência e o comportamento do campo; o estado continua sendo o dono do valor. Este é o esqueleto que você vai repetir em todos os campos do cadastro:

function App() {
  const [nome, setNome] = useState("");

  return (
    <div>
      <label htmlFor="nome">Seu nome</label>
      <input
        id="nome"
        type="text"
        value={nome}
        onChange={(e) => setNome(e.target.value)}
      />
      <p>Olá, {nome || "cliente"}!</p>
    </div>
  );
}

Três detalhes desse esqueleto merecem atenção porque voltam sempre. O primeiro é o id: ele existe para o label apontar para o campo com htmlFor e para o navegador saber qual rótulo pertence a qual campo. O segundo é o value curto e previsível: o estado é uma string, e o campo mostra essa string. O terceiro é o {nome || "cliente"} no parágrafo: quando o estado está vazio, a expressão cai no texto da direita, o que evita um "Olá, !" sem graça.

Se você trocar o parágrafo por um resumo do pedido, ou puser o nome dentro de um h2, nada muda no campo: o mecanismo é o mesmo. O que muda de uma tela para outra é o que você faz com o valor depois de receber. Guarde o esqueleto e vamos variar o type.

3. O atributo type é o que muda tudo

O type é uma instrução para o navegador, não para o React. Ele decide que tipo de controle desenhar, que teclado sugerir no celular, que validação nativa aplicar e como mostrar o texto. Para o React, o campo continua sendo um campo controlado: value e onChange funcionam igual em todos os tipos. Vale conhecer as peças do elemento antes de escolher o tipo:

type
O tipo do campo: text, email, password, number, search, tel, date. Sem ele, o navegador assume text.
value e onChange
O par que liga o campo ao estado. O value mostra; o onChange devolve o texto novo para o estado.
atributo de configuração
O que fica fixo no JSX e não muda com a digitação: type, id, placeholder, maxLength, autoComplete, readOnly.
propriedade × atributo
O que você vê digitado é a propriedade value do elemento; o painel das caixas mostra os atributos do HTML, então o texto digitado não aparece lá.
e.target.value
O texto atual do campo no momento do evento, sempre como string. É o que o onChange entrega para o seu estado.

Com essas peças claras, o tipo deixa de ser um detalhe estético. Um type="email" diz ao celular para mostrar o arroba no teclado e ao navegador para conferir o formato no envio do formulário. Um type="password" esconde os caracteres na tela. Um type="number" mostra setinhas e aceita rolagem do mouse. Nenhum deles impede o usuário de digitar bobagem — a validação de verdade é sua e tem aula própria —, mas todos melhoram a experiência sem custar uma linha de JavaScript.

Agora o primeiro trabalho da Ana: os campos do cadastro estão todos como texto comum. O e-mail precisa do tipo certo para o celular colaborar, e a senha precisa esconder o que está sendo digitado. Repare que o estado e o onChange já estão prontos — o que falta é o atributo:

Troque o type do campo de e-mail para email e o do campo de senha para password. O resto do componente já está pronto.

Essa é a prova de que o tipo é uma camada de apresentação por cima do mesmo mecanismo — e não uma peça diferente do React.

5. O valor que chega é sempre texto

Aqui está a consequência do type que mais confunde: ele não muda o tipo do valor. Todo campo de texto do HTML entrega uma string em e.target.value. type="number" inclui setinhas, teclado numérico e até recusa de letras no navegador, mas o estado recebe "3", com aspas, e não 3. Se você somar, o JavaScript cola os textos; se multiplicar, ele converte por conta própria. Essa diferença é a origem de metade dos totais errados por aí.

A Ana quer vender pão a R$ 2 e deixar o cliente escolher a quantidade. O campo parece numérico, o código parece uma conta e o resultado aparece como "R$ 32" para três pães. O problema está na linha do total, não no campo:

Digite 3 no campo: o total aparece como "R$ 32", porque o valor do campo é texto e está sendo colado no 2. Use Number() para transformar a quantidade em número e multiplicar por 2.

function App() {
  const [quantidade, setQuantidade] = useState("1");
  const total = quantidade + 2;
  return (
    <div>
      <label htmlFor="qtd">Quantos pães?</label>
      <input
        id="qtd"
        type="number"
        value={quantidade}
        onChange={(e) => setQuantidade(e.target.value)}
      />
      <p>Total: R$ {total}</p>
    </div>
  );
}
<div>

function App() {

  return (

      <label htmlFor="qtd">Quantos pães?</label>

        id="qtd"

      />

    </div>

}

Number() converte texto em número: Number("3") vira 3, Number("") vira 0 e Number("3,5") vira NaN, porque a vírgula não é o separador decimal do JavaScript. Se o seu campo aceita vírgula, troque por ponto antes de converter: Number(texto.replace(",", ".")). O NaN é o "não é número": aparece quando a conversão não deu certo, e é melhor tratar antes de mostrar no total.

No console do navegador, a diferença entre o texto do campo e o número da conta fica evidente:

typeof e.target.value: string
Number("3"): 3
Number(""): 0
Number("3,5"): NaN

Existe um atalho do React para campos numéricos: e.target.valueAsNumber entrega o número já convertido, ou NaN quando o campo está vazio. Funciona, mas espalha tratamento de NaN por todo lado. Para quem está começando, guardar a string e converter no lugar da conta é mais fácil de ler. O importante é não esquecer a conversão: o tipo do campo é uma promessa do navegador, não do valor.

6. Atributos que não são estado

Nem tudo no input é value. Existe uma família de atributos que configura o campo e fica igual durante toda a digitação. Eles não precisam de estado, não mudam com o evento e podem ser escritos direto no JSX. A tabela abaixo separa o que é configuração do que é valor:

AtributoO que fazCuidado
placeholdermostra uma dica cinza dentro do campo vazionão é valor: some ao digitar e não deve substituir o rótulo
maxLengthlimita quantos caracteres o usuário consegue digitarnão vale para texto colado por código; valide também
autoCompleteajuda o navegador a preencher (ou a não preencher)off é útil em campo de busca; on ajuda no cadastro
readOnlymostra o valor e não deixa editaro valor ainda é enviado; use quando o dado é só leitura
disableddesliga o campo e o cinzacampo desabilitado não é enviado e não recebe foco
requiredpede preenchimento na validação nativa do navegadorsó age no envio de um formulário; não substitui a sua validação

Um exemplo com os três mais usados, num campo de busca da padaria. O placeholder dá a dica, o maxLength impede um texto gigante, o autoComplete="off" evita que o navegador sugira o endereço da casa da Ana no meio da busca, e o value continua vindo do estado:

function Busca() {
  const [termo, setTermo] = useState("");

  return (
    <div>
      <label htmlFor="busca">Buscar pão</label>
      <input
        id="busca"
        type="search"
        placeholder="Pão de queijo"
        maxLength={40}
        autoComplete="off"
        value={termo}
        onChange={(e) => setTermo(e.target.value)}
      />
      <p>Procurando por: {termo || "nada ainda"}</p>
    </div>
  );
}

Repare que só o value muda durante o uso. Se você colocar o placeholder dentro de um estado, ele passa a mudar sem motivo e o campo perde a dica quando o texto é apagado de outro jeito. A regra é simples: o que varia com o usuário é estado; o que configura o campo é atributo.

7. Formatar sem brigar com o cursor

Formatar é transformar o texto antes de guardar: deixar só dígitos no telefone, maiúsculas no nome, sem espaços no começo. O lugar certo é o onChange, porque ali você recebe o texto cru e devolve o texto tratado para o estado. O campo mostra o resultado no próximo desenho, já limpo.

A Ana quer o telefone só com números — é o formato que ela usa para mandar mensagem no WhatsApp. Se guardar os parênteses e o traço, o número não serve para nada na hora de discar. A missão é limpar o texto na entrada:

O telefone está sendo guardado com parênteses e traço. Use replace(/\D/g, "") dentro do onChange para guardar só dígitos e acrescente maxLength={11} no campo.

function App() {
  const [telefone, setTelefone] = useState("");
  return (
    <div>
      <label htmlFor="tel">Telefone</label>
      <input
        id="tel"
        type="tel"
        value={telefone}
        onChange={(e) => setTelefone(e.target.value)}
      />
      <p>Telefone: {telefone}</p>
    </div>
  );
}
<div>
  <label for="tel">Telefone</label>
  <input id="tel" type="tel" value="">

</div>

function App() {
  const [telefone, setTelefone] = useState("");
  return (
    <div>
      <label htmlFor="tel">Telefone</label>
      <input
        id="tel"
        type="tel"
        maxLength={11}
        value={telefone}
        onChange={(e) => setTelefone(e.target.value.replace(/\D/g, ""))}
      />
      <p>Telefone: {telefone}</p>
    </div>
  );
}

\D significa "qualquer coisa que não seja dígito", e o g manda trocar todas as ocorrências, não só a primeira. Por isso "(11) 99999-8888" vira "11999998888". O maxLength limita o que a pessoa consegue digitar; a limpeza no onChange garante que nada além de dígito entre no estado, mesmo colado.

Dá para testar a expressão sozinha no console, antes de colocar no componente:

"(11) 99999-8888".replace(/\D/g, "")
"11999998888"

Agora o cuidado que separa formatar de brigar com o usuário. Toda vez que você muda o texto no onChange, o campo é redesenhado com o texto novo e o navegador recoloca o cursor no fim. Para um telefone isso quase não incomoda, porque a pessoa digita da esquerda para a direita. Para maiúsculas no meio de uma frase, incomoda muito: a pessoa corrige uma letra no meio e o cursor salta. A saída é formatar só quando o campo perde o foco (onBlur) ou aceitar as transformações que não movem o cursor, como remover caracteres indesejados.

8. O input é uma linha só

Um input é, por definição, uma linha. Apertar Enter dentro dele não cria uma linha nova: em um formulário, o Enter envia; fora dele, não faz nada. Se o campo precisa de várias linhas — o recado no bolo, a observação do pedido, o endereço completo —, a tag certa é textarea, com regras próprias de altura e quebras de linha. Se a escolha é entre poucas opções fixas, a tag certa é select. E se a resposta é sim ou não, é checkbox.

Essa separação não é preciosismo: cada tag tem um comportamento e uma acessibilidade diferentes. Um input com type="text" usado como campo de recado esconde o texto quando passa da largura, não aceita Enter e não dá para arrastar a altura. Trocar a tag é mais simples do que tentar consertar o input depois. As próximas aulas do nível são exatamente essas: textarea, select, checkbox, radio e validação — na ordem em que os formulários costumam crescer.

Vale também saber o que o input não faz sozinho. Ele não guarda o valor em lugar nenhum depois que a página fecha, não envia nada para o servidor e não impede o usuário de digitar errado. Quem guarda é o estado, quem envia é o formulário, quem impede é a validação. O campo é só a porta de entrada.

9. Cenários do dia a dia

Cenário 1: o e-mail sem arroba passou no cadastro

A Ana trocou o campo para type="email" e achou que estava validado. Só que a conferência nativa do navegador acontece no envio de um form e pode ser desligada com noValidate. Fora de um formulário, o campo aceita "maria" numa boa. O tipo melhora o teclado e dá uma dica ao navegador; a validação de verdade é uma função sua, que olha o valor antes de seguir. Isso tem aula própria, mas já vale a expectativa certa: type não é validação.

Cenário 2: o placeholder virou valor na cabeça do código

Ela escreveu placeholder="Seu nome" e, no resumo do pedido, testou if (nome) esperando que o campo tivesse algo. O placeholder é só uma dica visual: não entra no estado e some na primeira tecla. Quem diz se o campo está preenchido é o value do estado, e é ele que você confere com nome.trim() !== "" antes de enviar. Placeholder não é dado.

Cenário 3: a senha apareceu no resumo do pedido

O campo de senha esconde os caracteres na tela, mas o estado tem o texto puro. Quando a Ana colocou {senha} num parágrafo de conferência, a senha apareceu em letras legíveis para qualquer um que olhasse a tela. type="password" é uma cortina, não um cofre: o valor continua disponível para o seu código. A regra prática é nunca imprimir senha em tela, em log ou em resumo — mostre só a quantidade de caracteres.

Exercício: esconder a senha

Complete o atributo type do campo abaixo para que os caracteres apareçam como bolinhas na tela. Escreva só o valor do atributo:

<input id="senha" type="" value={senha} onChange={(e) => setSenha(e.target.value)} />

11. Resumo

Todo input controlado é a mesma dupla: value mostrando o estado e onChange devolvendo o texto novo. O que diferencia um campo do outro é o atributo type, que fala com o navegador — teclado, máscara, validação nativa — e não com o React. O valor que chega em e.target.value é sempre string, inclusive em type="number"; para fazer conta, converta com Number() e trate o NaN.

Os outros atributos são configuração e ficam fora do estado: placeholder dá a dica, maxLength limita a digitação, autoComplete ajuda ou atrapalha o preenchimento, readOnly e disabled tiram a edição de formas diferentes. Formatar é transformar o texto dentro do onChange antes de guardar; cuidado com o cursor, que volta para o fim quando o valor é reescrito a cada tecla.

Por fim, o elemento tem limites: uma linha só, sem Enter, sem altura arrastável. Quando o campo precisa de mais, a tag muda — e o mecanismo de estado que você aprendeu aqui continua o mesmo. É por isso que vale entender o input com calma: os próximos quatro formulários do nível são variações deste mesmo par value e onChange, cada um com suas manias.

Para lembrar

  • type muda teclado, máscara e validação nativa; não muda a ligação com o estado.
  • Todo valor de campo chega como string, mesmo em type="number".
  • Number("") é 0; Number("3,5") é NaN.
  • valueAsNumber existe, mas espalha NaN pelo código.
  • placeholder é dica, não valor; não substitui o label.
  • maxLength limita a digitação, mas não o texto colado por código.
  • readOnly mantém o valor e o envio; disabled desliga tudo.
  • Formatar no onChange com replace(/\D/g, "") deixa só dígitos.
  • Reescrever o valor a cada tecla move o cursor para o fim.
  • input é uma linha; recado é textarea, escolha é select.
