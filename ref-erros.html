Mensagens de Erro

Erro em React quase nunca é “o React quebrou”: é uma mensagem que aponta um lugar e um motivo, e a maior parte delas tem três ou quatro causas conhecidas. A Ana aprendeu a ler as dela na ordem certa — primeiro onde a mensagem aparece, depois o que ela quer dizer, depois o conserto. Esta página é o catálogo: as mensagens que você mais vai ver, traduzidas, com o primeiro passo de cada uma.

Como usar esta página
  • Comece pela seção 1 para saber onde procurar a mensagem; depois vá direto à seção do seu caso.
  • As mensagens de aviso (chave de lista, modo estrito) só aparecem em desenvolvimento — a seção 1 explica.
  • As duas caixas quebram de propósito: leia o painel e conserte. Ele mostra o erro de compilação completo.
  • O roteiro da seção 8 serve para qualquer mensagem, inclusive as que não estão aqui.

1. Como ler uma mensagem

Antes do texto, o lugar. Um erro de compilação impede o componente de rodar e aparece no próprio painel da caixa, com a linha e um trecho de código. Um erro de execução acontece durante o desenho: a tela fica vazia ou congela e a mensagem vai para o console do navegador. E um aviso não impede nada: a página roda e o React só reclama de algo que vai dar problema depois.

erro de compilação
O JSX não vira JavaScript: falta fechar uma tag, há dois elementos sem pai, falta uma chave. O painel mostra “não compilou” com a linha.
erro de execução
O componente rodou e lançou uma exceção: leitura de undefined, objeto desenhado, hook fora de lugar. A mensagem aparece no console.
aviso
O React reclama de algo que não quebra a tela agora: key faltando, atributo errado, dependência de efeito. A página continua.
pilha
A lista de chamadas que levou ao erro, com arquivo, linha e coluna. É o que diz onde, não por quê.
componente
O nome que aparece na pilha do React. É por ele que você acha o arquivo, mesmo quando a linha é de uma biblioteca.
modo de desenvolvimento
O React compilado sem minificação, que faz verificações extras e escreve mensagens longas e explicativas. As caixas deste guia rodam o build de produção.
TipoOnde apareceExemplo de começoPrimeiro passo
compilaçãono painel da caixa, com linhanão compilou: …ler a linha apontada e a de cima
execuçãoconsole do navegadorUncaught TypeError: …abrir a pilha e achar o seu componente — Depurando no Navegador

Uma dica de leitura que economiza tempo: copie a mensagem sem os pedaços que mudam — o nome da variável, o número da linha, o texto do dado. O que sobra é a assinatura do problema, e ela é padronizada. “Cannot read properties of undefined” é sempre a mesma causa; o que muda é qual propriedade. Procurar pela frase inteira, com o nome do seu dado no meio, devolve resultados piores do que procurar pela parte fixa.

Uma particularidade deste guia vale desde já: as caixas rodam a versão de produção do React, que não escreve os avisos de desenvolvimento. Por isso, nas caixas, você vê os erros de compilação e os erros de execução que acontecem antes do primeiro desenho — e não vê os avisos de key ou de modo estrito. No seu projeto, rodando npm run dev, todos aparecem. A seção 8 mostra como aproveitar os dois mundos.

2. JSX adjacente: o erro que o painel mostra

É o erro número um de quem começa. O componente devolve dois elementos lado a lado, sem um pai em volta. O JSX é traduzido para uma chamada que cria um elemento, e dois não cabem em um. A mensagem fala de “elementos JSX adjacentes” e sugere a saída: embrulhar em uma tag ou em um fragmento.

O App devolve um título e um parágrafo soltos e não compila. Envolva os dois em uma <div> (ou em <>...</>) e rode.

function App() {
  return (
    <h1>Padaria da Ana</h1>
    <p>Aberto das 6h às 18h</p>
  );
}
Erro: não compilou: /App.jsx: Adjacent JSX elements must be wrapped in an enclosing tag. Did you want a JSX fragment <>...</>? (4:4)

  2 |   return (
  3 |     <h1>Padaria da Ana</h1>
> 4 |     <p>Aberto das 6h às 18h</p>
    |     ^
  5 |   );
  6 | }

function App() {
  return (
    <div>
      <h1>Padaria da Ana</h1>
      <p>Aberto das 6h às 18h</p>
    </div>
  );
}

O painel mostra a mensagem inteira, com o arquivo, a linha, a coluna e um trecho com um acento circunflexo embaixo do ponto exato. Duas leituras úteis: a linha apontada é a do segundo elemento (o primeiro não tem culpa), e a sugestão entre parênteses já traz a correção. Quando a mensagem sugerir um fragmento, lembre que ele não cria nó no HTML — a aula O Fragment compara as duas saídas.

O erro também aparece quando alguém tenta devolver um comentário ou um texto solto ao lado de um elemento. Em JSX, comentário é {/* … */} e só existe dentro de um elemento; fora dele, o compilador vê dois filhos. O mesmo vale para texto: return "Pão" funciona, return "Pão" <p>…</p> não.

Se o componente devolve dois elementos de propósito e você não quer um div extra, o fragmento resolve. E se o erro acontecer dentro de um map, a causa é outra: ali cada item já é um elemento, e o problema costuma ser chave faltando ou return esquecido — a página Listas cobre os dois.

3. Tag não fechada e o ponto e vírgula invisível

O segundo erro de sintaxe mais comum é a tag que ninguém fechou. A mensagem é Unterminated JSX contents, “conteúdo JSX não terminado”, e o detalhe importante: ela aponta a linha depois do problema, porque é ali que o compilador percebe que ainda estava dentro de uma tag.

O <h1> não foi fechado e a caixa não compila. Feche a tag e rode.

function App() {
  return (
    <div>
      <h1>Padaria da Ana
      <p>Aberto das 6h</p>
    </div>
  );
}
Erro: não compilou: /App.jsx: Unterminated JSX contents. (6:10)

  4 |       <h1>Padaria da Ana
  5 |       <p>Aberto das 6h</p>
> 6 |     </div>
    |           ^
  7 |   );
  8 | }

function App() {
  return (
    <div>
      <h1>Padaria da Ana</h1>
      <p>Aberto das 6h</p>
    </div>
  );
}

O método que resolve rápido: comece pela linha apontada e suba contando as tags abertas e fechadas. Em JSX, toda tag precisa fechar, inclusive as que no HTML não fecham — <br> se escreve <br />, <img> se escreve <img />, e <input> também.

O terceiro erro de sintaxe é o mais traiçoeiro porque não parece sintaxe: o return com o JSX na linha de baixo. O JavaScript insere um ponto e vírgula invisível depois do return, a função devolve undefined e o React reclama que nada foi devolvido. O conserto é colocar o JSX na mesma linha do return ou abrir parênteses antes de quebrar. O sintoma não é uma mensagem de sintaxe: é uma tela vazia com “nothing was returned from render”.

4. Erros de JavaScript no meio do React

Boa parte das mensagens vermelhas não é do React: é JavaScript reclamando de um valor que não existia. O React só estava desenhando quando a conta estourou. As três mais comuns estão na tabela.

A primeira merece um exemplo, porque acontece todo dia com dado vindo da rede. O componente desenha antes de a resposta chegar, e o valor é undefined. A leitura de uma propriedade de undefined derruba o desenho com a mensagem do console:

Uncaught TypeError: Cannot read properties of undefined (reading 'nome')

O conserto não é try/catch: é desenhar só quando o dado existe — um if antes do acesso, um valor inicial ([] para lista, "" para texto) ou o operador ?. para leitura opcional. A aula Carregando e Erro mostra o caminho completo, e a Erros Comuns reúne mais mensagens dessa família.

Há um erro de JavaScript que não gera exceção e por isso não tem mensagem: a conta que devolve NaN. Ela aparece na tela como “NaN” no meio do preço, e a causa é sempre a mesma — uma conversão que falhou, como Number("12,50") ou undefined + 1. Se você vir NaN em vez de uma mensagem, o caminho é o mesmo da seção 8: console.log nas parcelas da conta antes de olhar o código que desenha.

Vale lembrar de uma armadilha de leitura: a linha que aparece na pilha costuma ser a do return do componente, não a do dado que faltou. O culpado está uma chamada acima — o pai que não passou a prop, o estado que começou vazio, a resposta que ainda não chegou.

5. Erros de hooks

Hooks têm mensagens próprias e todas falam de lugar ou de ordem. A primeira é a chamada fora do corpo de um componente — estado no topo do arquivo, hook dentro de um onClick, hook em função auxiliar comum:

Uncaught Error: Invalid hook call. Hooks can only be called inside of the body of a function component.

“Chamada de hook inválida: hooks só podem ser chamados no corpo de um componente de função.” O conserto é mover a chamada para dentro do componente. Nas caixas deste guia, a mesma situação aparece com outra mensagem, porque a versão de produção é mais seca: Cannot read properties of null (reading 'useState').

A segunda família é a ordem: Rendered more hooks than during the previous render (desenhou mais hooks que no desenho anterior) e Rendered fewer hooks than expected (menos hooks que o esperado). As duas querem dizer que um hook apareceu ou sumiu entre desenhos — if, laço ou return antecipado. A página As Regras dos Hooks mostra cada caso quebrando na caixa.

Uma terceira família de mensagens de hook não é sobre ordem, e sim sobre dependência: React Hook useEffect has a missing dependency. Ela aparece no ESLint e no console de desenvolvimento, e quer dizer que o efeito lê um valor que não está na lista — o valor pode estar desatualizado quando o efeito rodar. Não derruba a página; produz o bug mais chato do React, aquele que só aparece depois de três cliques. Aula: As Dependências.

Antes de rodar, o ESLint avisa com uma mensagem diferente e mais fácil de entender: React Hook “useState” is called conditionally. Se você vir essa, não precisa nem abrir o navegador — o conserto é subir a chamada para o topo. Aula: Hooks Próprios mostra o mesmo aviso dentro de um hook seu.

6. Lista e objeto

Duas mensagens dominam as listas. A primeira é aviso, não erro: falta key em um item. Ela não impede a tela e é fácil de ignorar — e cobra depois, como estado no item errado.

Warning: Each child in a list should have a unique "key" prop.

A segunda é erro de verdade e confunde porque fala de “objeto” quando o assunto é lista: você desenhou o item inteiro em vez de um campo dele.

Uncaught Error: Objects are not valid as a React child (found: object with keys {nome, preco}).

“Objetos não são filhos válidos do React.” O conserto é escolher o campo: {pao.nome} em vez de {pao}. Para inspecionar, {JSON.stringify(pao)} mostra o conteúdo como texto. A página Listas junta as duas mensagens na tabela de erros comuns.

Existe uma segunda mensagem de chave, menos conhecida e mais grave: Encountered two children with the same key. Ela aparece quando dois itens da mesma lista usam a mesma chave — um id repetido no dado, ou um índice somado a alguma coisa. O sintoma é o React reaproveitar o estado do primeiro no segundo, e o conserto é garantir unicidade no dado ou combinar campos (id + "-" + tamanho).

Um terceiro caso, que não dá mensagem nenhuma e engana: desenhar uma função. O React não reclama de função como filho — ele simplesmente não mostra nada. Se a tela está vazia e o JSX está certo, confira se você não chamou a função duas vezes ou esqueceu de chamar: {formatar} desenha a função, e {formatar()} desenha o resultado.

7. Formulário e laço de atualização

No formulário, o erro clássico é o campo que não aceita digitação porque tem value e não tem onChange. Em desenvolvimento, o React avisa com todas as letras:

Warning: You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field.

“Campo somente leitura.” O conserto é ligar o onChange ao estado — ou usar defaultValue, se a intenção era um campo não controlado. A página Formulários traz a tabela completa de campo por campo.

O outro erro de formulário é o laço: setEstado chamado durante o desenho, sem evento no meio. O React corta depois de alguns ciclos e diz:

Uncaught Error: Too many re-renders. React limits the number of renders to prevent an infinite loop.

“Desenhos demais.” A causa quase sempre é uma chamada de função no lugar de uma referência: onClick={somar()} roda somar no desenho e muda o estado, que desenha de novo. O conserto é passar a função sem chamar: onClick={somar} ou onClick={() => somar()}. O mesmo laço aparece com useEffect sem dependências corretas, com a mensagem Maximum update depth exceeded — vista na página Performance.

8. Um roteiro para qualquer mensagem

Quando a mensagem não está neste catálogo, o caminho continua o mesmo. Quatro passos, na ordem, resolvem a maior parte dos casos sem chute.

Primeiro: separe compilação de execução. Se o painel (ou o terminal) diz “não compilou”, não há o que depurar em estado: é sintaxe, e a linha apontada e a anterior são o mapa. Se compilou e a tela está errada, o problema é de dado ou de fluxo.

Segundo: reduza até o osso. Apague o componente e devolva um parágrafo fixo. Apareceu? O problema está no que você apagou. Não apareceu? O problema está no nome do componente, no return ou em quem o chama. Reduzir acha o culpado mais rápido que reler quarenta linhas.

Terceiro: olhe o valor, não o código. Um console.log antes da linha que quebra mostra o que você achava que era uma coisa e é outra — lista vazia, prop com outro nome, número em texto. Nas caixas do guia, as linhas de console.log aparecem no painel prefixadas com console:; no projeto, é a aba Console.

Um recurso que muda o jogo em produção: o error boundary, um componente que captura o erro dos filhos e desenha uma tela de desculpa em vez de deixar a página em branco. Ele não conserta nada, mas evita que um erro em um cartão derrube a loja inteira. A aula Tratamento de Erro mostra o componente e o que ele não captura — erro dentro de evento e de promessa passa por fora.

Quarto: procure a mensagem exata. Copie a frase sem os valores que mudam (nomes de variável, números) e procure. Mensagem de erro de React é padronizada: a mesma frase tem sempre a mesma causa. A aula Depurando no Navegador mostra onde ficam a pilha, o breakpoint e o valor de cada variável.

Resumo

Primeiro o lugar: compilação aparece no painel e impede rodar; execução aparece no console e derruba o desenho; aviso aparece só em desenvolvimento e não impede nada. Depois o texto: JSX adjacente pede um pai, tag não fechada aponta a linha seguinte, objeto desenhado pede um campo, hook fora de ordem pede chamada fixa no topo.

Os consertos são poucos e se repetem: embrulhar irmãos, fechar a tag, escolher o campo do objeto, ler o dado só quando ele existe, ligar onChange ao value e passar função em vez de chamá-la. E o roteiro vale para o resto: separar sintaxe de dado, reduzir, olhar o valor e procurar a mensagem exata.

Para lembrar

  • “Não compilou” é sintaxe: leia a linha apontada e a anterior.
  • JSX adjacente: embrulhe em div ou em <>...</>.
  • “Unterminated JSX contents”: falta fechar uma tag logo acima.
  • Objeto na tela: escolha o campo, ou JSON.stringify para inspecionar.
  • “Invalid hook call”: hook fora do corpo do componente.
  • “More/fewer hooks”: ordem mudou por if, laço ou return antecipado.
  • value sem onChange deixa o campo somente leitura.
  • “Too many re-renders”: onClick={somar()} em vez de onClick={somar}.
  • Avisos de key e de modo estrito são de desenvolvimento.
  • Reduzir o componente a um parágrafo acha o culpado mais rápido que reler.
