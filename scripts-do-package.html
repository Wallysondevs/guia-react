Os Scripts do package.json

A Ana decora vite --port 3000 --host e erra na terceira letra. O time dela digita npm run dev e funciona. A diferença está numa seção pequena do package.json que quase ninguém lê: os scripts. Nesta aula ela entende como o npm run acha o programa, como passar argumentos, como encadear comandos e como deixar o projeto rodando com um comando só — na máquina dela e no servidor.

Você vai aprender
  • O que é um script e como o npm run nome o executa.
  • Por que vite funciona sem npx e sem instalação global.
  • O que cada um dos quatro scripts do Vite faz e quando rodar.
  • Como passar argumentos com o -- separador.
  • Encadear comandos com &&, usar pre/post e rodar dois de uma vez.
  • Scripts para o time e para o CI, com código de saída.

1. A cena: o comando comprido que ninguém decora

Para abrir o site no celular, a Ana precisa subir o servidor na porta 3000 e expor na rede. Ela digita npx vite --port 3000 --host, erra uma letra, tenta de novo, e no dia seguinte esqueceu o comando. O colega dela digita npm run dev e o servidor abre na porta certa, com as opções certas, sem pensar.

A diferença é que o comando do colega está escrito no package.json, na seção scripts. Um script é um apelido: um nome curto que aponta para uma linha de comando. Em vez de lembrar de flags, você lembra de dev, build, test. E, melhor: o script fica versionado junto com o projeto, então todo mundo que clona roda a mesma coisa.

Este é o assunto da aula: a seção mais subestimada do projeto e a que mais economiza tempo no dia a dia. No fim, você vai saber ler qualquer package.json e entender o que cada npm run faz por baixo.

2. O que é um script

No package.json, a chave scripts é um objeto de pares nome e comando. O nome é livre; o comando é uma linha de terminal. Quando você digita npm run dev, o npm procura a chave dev e executa o comando dela — com uma diferença importante em relação a rodar o mesmo comando à mão: o npm coloca a pasta node_modules/.bin na frente do caminho de busca.

{
  "name": "padaria",
  "private": true,
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview",
    "lint": "eslint ."
  }
}

É essa injeção de caminho que explica a pergunta mais comum: por que vite funciona dentro do script se não está instalado globalmente? Porque o npm procura primeiro em node_modules/.bin, onde o Vite foi instalado como dependência de desenvolvimento. Fora do script, o mesmo vite não é encontrado — a não ser que você use npx vite. É a mesma ideia do PATH do sistema, aplicada ao projeto.

script
Um par nome e comando dentro do package.json: "dev": "vite".
runner
O npm run: ele lê o nome, acha o comando e executa.
.bin
A pasta node_modules/.bin, onde ficam os atalhos dos programas instalados.
argumento
Uma opção passada ao comando: --port 3000. No npm, vai depois do --.
gancho
Um script pre ou post que roda em volta do principal.
código de saída
O número que o comando devolve: zero é sucesso, qualquer outro reprova o CI.

Rodar npm run sem nome nenhum lista os scripts disponíveis. É o comando que responde "o que esse projeto sabe fazer?" sem abrir arquivo nenhum:

$ npm run

Scripts available in padaria@0.0.0 via `npm run`:
  dev
    vite
  build
    vite build
  preview
    vite preview
  lint
    eslint .

Repare que a saída mostra o nome e, embaixo, o comando real. Isso é ouro quando você entra num projeto que não conhece: dá para ver se o time usa test ou test:unit, se existe um format, se o build tem etapas a mais. Antes de perguntar para alguém, rode npm run.

A função executar deveria imitar o npm run: devolver o comando quando o script existe e uma mensagem de erro quando não existe. Hoje ela devolve undefined para tudo. Corrija para a lista mostrar os comandos e o aviso de script ausente.

const scripts = {
  dev: "vite",
  build: "vite build",
  lint: "eslint ."
};

function executar(nome) {
  return undefined;
}

function App() {
  const pedidos = ["dev", "build", "lint", "test"];

  return (
    <ul>
      {pedidos.map((nome) => (
        <li key={nome}>
          npm run {nome} → {executar(nome)}
        </li>
      ))}
    </ul>
  );
}
<ul>
  <li>npm run dev →</li>
  <li>npm run build →</li>
  <li>npm run lint →</li>
  <li>npm run test →</li>
</ul>

const scripts = {
  dev: "vite",
  build: "vite build",
  lint: "eslint ."
};

function executar(nome) {
  if (scripts[nome]) {
    return scripts[nome];
  }

  return 'Missing script: "' + nome + '"';
}

function App() {
  const pedidos = ["dev", "build", "lint", "test"];

  return (
    <ul>
      {pedidos.map((nome) => (
        <li key={nome}>
          npm run {nome} → {executar(nome)}
        </li>
      ))}
    </ul>
  );
}

Dá para ler a saída como o próprio terminal leria: cada linha é um pedido e a resposta. Quando o script existe, o comando aparece; quando não existe, a mensagem é a que o npm imprime de verdade — Missing script: "test", com o nome entre aspas. É um erro claro, e a saída dele é justamente "você digitou um nome que não está aqui".

Um detalhe de sintaxe que vale guardar: ao acrescentar um script, não esqueça a vírgula entre as entradas e as aspas no comando. O package.json é JSON, e JSON é rígido. O editor costuma mostrar o erro na hora, mas se o npm run começar a reclamar de arquivo inválido, a causa é essa.

3. Os quatro scripts que o Vite escreve

O template do Vite cria quatro scripts, e cada um resolve um momento diferente do trabalho. Conhecê-los evita rodar o comando errado na hora errada — o que, no caso do build, faz diferença.

ScriptComandoQuando rodar
devviteenquanto trabalha: servidor com HMR
buildvite buildao publicar: gera a versão final em dist/
previewvite previewantes de publicar: serve o dist/ localmente
linteslint .antes de entregar: aponta código suspeito

O dev é o do dia a dia e não gera arquivo nenhum: ele serve o código na hora, como você viu na aula do Vite. O build é o único que produz a pasta dist — e é o que roda no servidor de publicação. O preview existe para conferir esse resultado sem publicar: ele sobe um servidor comum em cima do dist, para você ver se os caminhos e as imagens continuam funcionando.

O lint é o mais ignorado e o mais barato de rodar. Ele lê os arquivos e aponta variável não usada, import quebrado, efeito com dependência faltando. Não conserta sozinho, mas lista o que consertar. Muitos projetos têm também lint:fix, que aplica as correções automáticas.

Uma confusão comum: rodar npm run build para "ver o site" e depois abrir o dist/index.html com dois cliques. Não funciona — os caminhos gerados são absolutos e precisam de um servidor. Para ver o resultado, npm run preview. O build não é para olhar; é para publicar.

4. Passando argumentos com o --

Chega o dia em que você precisa de uma opção que não está no script: mudar a porta, abrir o navegador, expor na rede. O caminho intuitivo é npm run dev --port 3000 — e ele não faz o que você espera. O npm entende --port como uma opção dele, e o Vite continua na porta padrão. Para separar as opções do npm das opções do programa, existe o -- sozinho no meio.

$ npm run dev -- --port 3000

  VITE v7.1.0  ready in 288 ms

  ➜  Local:   http://localhost:3000/
  ➜  press h + enter to show help

Tudo o que vem depois do -- é repassado ao comando do script, como se você o tivesse digitado lá. É por isso que a linha aparece com a porta 3000. A regra é fácil de lembrar: as opções antes do -- são do npm (raras), as depois são do programa (as que você quer).

Se uma opção é usada sempre — a porta 3000, por exemplo —, o lugar dela é dentro do script, não na linha de comando: "dev": "vite --port 3000". Aí todo mundo que roda npm run dev tem o mesmo comportamento, e ninguém precisa lembrar da flag. Script é justamente para o que se repete.

A função montar deveria juntar o comando do script com os argumentos recebidos, mas está ignorando os argumentos. Faça as três linhas mostrarem o comando completo: vite, vite --port 3000 e vite --host.

const script = "vite";

const chamadas = [
  { texto: "npm run dev", args: [] },
  { texto: "npm run dev -- --port 3000", args: ["--port", "3000"] },
  { texto: "npm run dev -- --host", args: ["--host"] }
];

function montar(comando, args) {
  return comando;
}

function App() {
  return (
    <ul>
      {chamadas.map((c) => (
        <li key={c.texto}>
          {c.texto} → {montar(script, c.args)}
        </li>
      ))}
    </ul>
  );
}
<ul>
  <li>npm run dev → vite</li>
  <li>npm run dev -- --port 3000 → vite</li>
  <li>npm run dev -- --host → vite</li>
</ul>

const script = "vite";

const chamadas = [
  { texto: "npm run dev", args: [] },
  { texto: "npm run dev -- --port 3000", args: ["--port", "3000"] },
  { texto: "npm run dev -- --host", args: ["--host"] }
];

function montar(comando, args) {
  if (!args.length) {
    return comando;
  }

  return comando + " " + args.join(" ");
}

function App() {
  return (
    <ul>
      {chamadas.map((c) => (
        <li key={c.texto}>
          {c.texto} → {montar(script, c.args)}
        </li>
      ))}
    </ul>
  );
}

A lista vazia precisa de um caso à parte, senão o comando ganharia um espaço no fim — detalhe pequeno que, num script de verdade, pode virar argumento vazio e erro de leitura. O join(" ") monta a linha final. É literalmente isso que o npm faz: pega o comando do script e concatena os argumentos que vieram depois do --.

5. Encadeando comandos

Scripts podem chamar outros scripts e outros comandos. Duas formas resolvem quase tudo. A primeira é o &&, que executa em sequência e para no primeiro erro:

{
  "scripts": {
    "check": "npm run lint && npm run build",
    "dev": "vite"
  }
}

Com check, o lint roda primeiro; se ele falhar, o build nem começa. Essa é a diferença entre && e ;: o ponto e vírgula continua mesmo com erro, o && para. Para verificação, você quer parar — não adianta gerar o build de um código que acabou de ser reprovado.

A segunda forma são os scripts pre e post: o npm procura automaticamente por pre<nome> e post<nome> e os executa antes e depois do script principal. É um gancho antigo e ainda útil, especialmente no build:

{
  "scripts": {
    "prebuild": "npm run lint",
    "build": "vite build",
    "postbuild": "node scripts/copiar-robots.js"
  }
}

Ao rodar npm run build, o npm executa prebuild, depois build, depois postbuild — nessa ordem, e parando se algum falhar. Use com moderação: quando há muitos ganchos, fica difícil saber o que um comando faz só de olhar. Se a ordem importa e é longa, prefira um script único e explícito com &&.

A função ordem devolve só o script principal. Monte a sequência que o npm executa: o prebuild antes, o build no meio e o postbuild depois — três itens na lista, nesta ordem.

const scripts = {
  prebuild: "npm run lint",
  build: "vite build",
  postbuild: "node scripts/copiar-robots.js"
};

function ordem(nome) {
  return [nome];
}

function App() {
  const sequencia = ordem("build");

  return (
    <ol>
      {sequencia.map((passo) => (
        <li key={passo}>npm run {passo}</li>
      ))}
    </ol>
  );
}
<ol>
  <li>npm run build</li>
</ol>

const scripts = {
  prebuild: "npm run lint",
  build: "vite build",
  postbuild: "node scripts/copiar-robots.js"
};

function ordem(nome) {
  const passos = [];

  if (scripts["pre" + nome]) {
    passos.push("pre" + nome);
  }

  passos.push(nome);

  if (scripts["post" + nome]) {
    passos.push("post" + nome);
  }

  return passos;
}

function App() {
  const sequencia = ordem("build");

  return (
    <ol>
      {sequencia.map((passo) => (
        <li key={passo}>npm run {passo}</li>
      ))}
    </ol>
  );
}

O <ol> em vez de <ul> é proposital: a ordem faz parte do resultado. E o teste com scripts["pre" + nome] mostra a ideia por trás dos ganchos — o npm não tem uma lista fixa, ele simplesmente procura o nome com o prefixo e roda se existir.

6. Rodando dois servidores de uma vez

Quando o projeto cresce, aparece a necessidade de rodar duas coisas ao mesmo tempo: o Vite e uma API local, por exemplo. O && não serve, porque o primeiro comando não termina nunca — e o segundo nunca começa. Para paralelismo, a ferramenta mais usada é o concurrently:

{
  "scripts": {
    "dev": "vite",
    "api": "node servidor/api.js",
    "dev:full": "concurrently \"npm run dev\" \"npm run api\""
  }
}

O concurrently é uma dependência de desenvolvimento (npm install -D concurrently) e recebe os comandos entre aspas. A saída dos dois aparece no mesmo terminal, com prefixos coloridos, e Ctrl + C derruba os dois de uma vez. Existe também o npm-run-all, com outra sintaxe; qualquer um resolve.

Para variáveis de ambiente dentro de scripts, cuidado com a diferença entre sistemas. No Linux e no macOS, "dev": "VITE_API=local vite" funciona; no Windows, o mesmo script falha. O cross-env resolve: "dev": "cross-env VITE_API=local vite". Hoje o Vite também lê arquivos .env, que são a solução mais limpa — e o assunto da última aula deste bloco.

7. Scripts para o time

Um projeto maduro tem scripts que padronizam o que todo mundo faz. Não é burocracia: é a diferença entre "rode o eslint aí, acho que é npx eslint src" e npm run lint. Alguns nomes se tornaram convenção:

ScriptComando típicoPara quê
linteslint .apontar problemas sem alterar arquivos
lint:fixeslint . --fixaplicar as correções automáticas
formatprettier --write .padronizar espaçamento e aspas
testvitest runrodar os testes uma vez
test:watchvitestrodar os testes enquanto trabalha
typechecktsc --noEmitconferir tipos sem gerar arquivo

O sufixo com dois-pontos é uma convenção para variações do mesmo assunto: test e test:watch, lint e lint:fix. Não muda o funcionamento — o nome é livre —, mas ajuda a agrupar na lista do npm run e na cabeça de quem lê.

Dois nomes têm significado especial e vale conhecer: npm start roda o script start sem precisar do run, e npm test roda o test. O template do Vite não cria start, porque o nome dele é dev; se você criar start apontando para o mesmo comando, os dois funcionam.

8. Scripts no CI

Servidor de integração contínua não tem memória: ele baixa o código, instala e roda comandos. Os scripts são a interface entre o seu projeto e essa máquina. Um pipeline mínimo de um projeto Vite é assim:

name: ci
on: [push]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - run: npm run lint
      - run: npm run build

Três comandos, e todos existem porque estão no package.json. Se o lint falhar, ele para ali — e o motivo é o código de saída: todo comando devolve zero quando dá certo e outro número quando dá errado. O npm repassa esse número, e o CI usa isso para decidir se o trabalho passou. Um script que engole o erro com || true faz o CI ficar verde com código quebrado.

O npm ci na primeira linha, em vez de npm install, é a mesma escolha da aula de npm: instalar exatamente o lock, sem mexer em versões. A partir daí, npm run lint e npm run build fazem o resto — e se um deles não existir, o CI falha com Missing script, o que também é informação.

9. Cenários do dia a dia

Cenário 1: o script que não existe

Ela digitou npm run tests, no plural. O npm respondeu Missing script: "tests" e listou os que existiam. A causa era só o plural; o conserto, um npm run test. Vale reparar que a mensagem mostra a lista completa — é a forma mais rápida de descobrir o nome certo sem abrir o arquivo.

Cenário 2: a opção foi para o lugar errado

Ela rodou npm run dev --port 3000 e o servidor abriu na 5173. O npm tratou a opção como dele e não repassou nada. Faltou o -- separador: npm run dev -- --port 3000. Se a opção é usada todo dia, o melhor é colocá-la dentro do script e nunca mais digitar.

Cenário 3: o build passou, mas o CI falhou

O build local funcionava e o CI reclamava de módulo não encontrado. O script chamava uma ferramenta que estava em devDependencies, e o CI rodava npm ci --omit=dev antes. A ferramenta não existia naquele ambiente. O conserto foi mover o pacote para dependencies — ou parar de usá-lo no build, que era o caso, porque ele só servia para gerar um arquivo estático.

11. Resumo

Script é apelido: um nome no package.json que aponta para uma linha de comando. O npm run nome procura a chave, coloca node_modules/.bin no caminho e executa — é por isso que o Vite funciona sem instalação global. Sem nome, npm run lista tudo o que o projeto sabe fazer.

Os quatro scripts do Vite cobrem o ciclo: dev para trabalhar, build para gerar, preview para conferir o resultado, lint para revisar. Argumentos extras vão depois do --. Para sequência, && para no primeiro erro; para paralelismo, concurrently; para ganchos automáticos, os prefixos pre e post.

E o valor maior aparece no time e no CI: um comando só, igual para todo mundo, com código de saída que diz se passou. Com o projeto organizado e os comandos padronizados, falta entender o que o build faz com os arquivos — por que o site fica em dist, o que é o hash no nome e por que o pacote final é menor que a soma das partes. É a próxima aula.

Para lembrar

  • scripts no package.json: nome → comando.
  • npm run sem nome lista os scripts do projeto.
  • O npm põe node_modules/.bin no caminho: nada de instalação global.
  • dev, build, preview e lint são os quatro do Vite.
  • Argumento extra vai depois do --: npm run dev -- --port 3000.
  • && para no primeiro erro; ; continua mesmo assim.
  • prebuild e postbuild rodam em volta do build.
  • Dois servidores: concurrently; variável no Windows: cross-env.
  • Sufixos como lint:fix e test:watch agrupam variações.
  • No CI: npm ci + npm run build; código de saída diferente de zero reprova.
