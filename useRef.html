O useRef

A Ana quer que, quando o cliente clicar em Encomendar com o nome vazio, o cursor pule para o campo do nome em vez de ficar parado no botão. Ela também quer guardar o id do aviso que aparece depois de seis segundos, para poder cancelá-lo. As duas coisas têm o mesmo problema: precisam de um valor que dure enquanto o componente estiver na tela, mas que não obrigue o React a redesenhar tudo quando muda. Para isso existe uma caixa chamada ref, criada pelo useRef — e nesta aula a Ana aprende onde ela é a ferramenta certa e onde ela é uma armadilha.

Você vai aprender
  • O que o useRef devolve e por que ele é uma caixa, não um valor.
  • Como a ref sobrevive aos renders sem provocar nenhum.
  • Como usar ref={campo} para falar com um elemento do DOM de verdade.
  • A diferença entre estado, ref e variável local.
  • Os casos em que a ref é a escolha certa: foco, id de timer, flags e valores anteriores.
  • Por que a ref não serve para o que aparece na tela.
  • As regras: valor inicial sempre, nada de ler ou escrever no meio do render.

1. A cena: o cursor que não vai para o campo

O formulário da padaria já estava acessível: rótulo ligado, erro anunciado, campo marcado como inválido. Faltava um detalhe que a Ana só percebeu usando o teclado. Ao clicar em Encomendar com o nome vazio, a mensagem aparecia embaixo do campo e o leitor de tela a anunciava — mas o cursor continuava no botão. Quem enxerga via o erro de longe; quem não enxerga tinha que apertar Shift+Tab várias vezes para voltar ao campo e corrigir.

Mover o cursor para um campo é uma operação do navegador, não do React. O React desenha elementos a partir do estado; ele não tem uma função focarCampo(). Para chamar .focus() num elemento, você precisa do elemento de verdade — o objeto do DOM, aquele que o navegador criou —, e o JSX não entrega isso. O que o JSX entrega é uma descrição do que deve existir.

É aí que entra a ref. Ela é uma caixa que o React mantém para você, ligada a uma posição fixa no componente. Você enche a caixa com o elemento quando ele aparece na tela e, depois, pode tirar de lá o elemento e chamar os métodos dele. A mesma caixa serve para guardar qualquer outra coisa que precise durar — um número, um id, um objeto — sem que o React precise saber.

2. O que é uma ref

useRef(0) devolve um objeto com uma única propriedade: current. Esse objeto nasce na primeira renderização e continua sendo o mesmo até o componente sair da tela. Não é o valor 0 que fica guardado no estado do React; é a caixa que fica guardada, e dentro dela o valor inicial.

function Contador() {
  const caixa = useRef(0);

  console.log(caixa);          // { current: 0 }
  caixa.current = caixa.current + 1;
  console.log(caixa.current);  // 1

  return <p>guardado: {caixa.current}</p>;
}

No console, o que aparece é o objeto, não o número:

{ current: 0 }
1

Essa diferença de formato é a diferença de ideia. O estado é um valor que o React guarda e compara para decidir se redesenha. A ref é um objeto que você mesmo mexe, e o React não fica sabendo. Ninguém redesenha a tela quando você escreve em caixa.current; a tela só muda quando outra coisa provoca um novo render e aquele valor é lido de novo.

ref
A caixa em si: o objeto devolvido por useRef, com a propriedade current.
.current
O que está dentro da caixa. Pode ser número, texto, objeto, função ou um elemento do DOM.
render
O ato de o React chamar o seu componente e montar o JSX de novo. Só acontece quando o estado ou as props mudam.
DOM
A árvore de elementos que o navegador criou. É onde vivem .focus(), .scrollIntoView() e .play().
estado
O valor que o React guarda e observa. Mudar estado redesenha; mudar ref, não.

Três frases resumem a ref e valem a aula. Primeira: ela sobrevive aos renders — cada chamada do componente enxerga a mesma caixa, com o que você deixou lá. Segunda: mexer nela não redesenha nada — o React nem fica sabendo. Terceira: ela não é comparada com nada — não existe "valor antigo" para o React detectar.

3. Falar com o DOM: ref={campo}

O uso mais comum é apontar a ref para um elemento. Você cria a caixa com useRef(null) e entrega essa caixa na prop ref do elemento. Quando o React monta aquele elemento, ele coloca o objeto do DOM dentro de .current; quando desmonta, devolve null.

function Busca() {
  const [termo, setTermo] = useState("");
  const campo = useRef(null);

  function buscar() {
    campo.current.focus();       // o input de verdade
    console.log("buscando " + termo);
  }

  return (
    <div>
      <label htmlFor="busca">Buscar pão</label>
      <input
        id="busca"
        ref={campo}
        value={termo}
        onChange={(e) => setTermo(e.target.value)}
      />
      <button type="button" onClick={buscar}>Buscar</button>
    </div>
  );
}

Depois de montado, campo.current é exatamente o que você pegaria com document.querySelector("#busca") — com a diferença de que a ref aponta para o elemento certo daquele componente, e não para o primeiro que aparecer na página. Dois componentes iguais, cada um com a sua ref, não se atrapalham.

O que dá para fazer com o elemento é o que o navegador oferece: focus(), blur(), select(), scrollIntoView(), play(), pause(), medir offsetHeight, ler value. O que não dá é mudar o desenho por fora: se você escrever no elemento, o React não fica sabendo e a próxima renderização sobrescreve. Para o desenho, quem manda é o estado.

Agora a missão. O botão Buscar só mostra o termo; o cursor continua nele.

Crie uma ref para o campo de busca e, dentro do clique, leve o foco até ele com campo.current.focus(). Clique em Buscar: o contorno tem de aparecer no campo.

function App() {

Se você esquecer o ref={campo} no input, campo.current continua null e o clique quebra com uma mensagem no console:

TypeError: Cannot read properties of null (reading 'focus')

A leitura é direta: alguém tentou chamar .focus() em null. As duas causas possíveis são a prop esquecida e o momento errado — durante o primeiro render, o elemento ainda não existe, então .current ainda é null. Por isso o acesso a elementos acontece em eventos e efeitos, depois que a tela foi montada, e não no corpo do componente.

4. O que a ref não faz: redesenhar

A pergunta que separa quem entendeu de quem decorou: se eu mudar caixa.current, a tela muda? Não. E isso não é defeito — é a definição. O React redesenha quando o estado ou as props mudam, porque é isso que ele observa. A ref é justamente a caixa para o que não precisa de redesenho.

O exemplo clássico é contar quantas vezes o componente foi chamado. Uma variável comum zera a cada render; uma ref não. Veja a diferença: no código abaixo, renders é uma variável let criada de novo a cada chamada da função, então ela sempre vale 1.

O contador de renders zera a cada desenho porque é uma variável local. Guarde-o numa ref (useRef(0)) e some 1 no .current: depois de um clique, o painel tem de mostrar renders: 2.

function App() {
  const [cliques, setCliques] = useState(0);
  let renders = 0;
  renders = renders + 1;

  return (
    <div>
      <button id="somar" onClick={() => setCliques(cliques + 1)}>Somar um</button>
      <p>cliques: {cliques}</p>
      <p>renders: {renders}</p>
    </div>
  );
}
<div>
  <button id="somar">Somar um</button>
  <p>cliques: 0</p>
  <p>renders: 1</p>
</div>

function App() {
  const [cliques, setCliques] = useState(0);
  const renders = useRef(0);
  renders.current = renders.current + 1;

  return (
    <div>
      <button id="somar" onClick={() => setCliques(cliques + 1)}>Somar um</button>
      <p>cliques: {cliques}</p>
      <p>renders: {renders.current}</p>
    </div>
  );
}

Clique em Somar um: cliques vira 1, o React redesenha, a função roda de novo e renders.current chega a 2. A ref não provocou o desenho — ela só sobreviveu a ele. Esse é o comportamento que você quer numa ref e o que você não quer num valor que a tela mostra.

Uma ressalva honesta: contar renders assim é truque de aula. Em desenvolvimento, o React monta o componente duas vezes de propósito (para denunciar efeitos colaterais), então o número aparece maior do que na build de produção — a caixa deste guia roda produção, e por isso o 2 é previsível. Em código de verdade, ninguém conta renders: o número não serve para nada além de estudar.

5. Estado, ref ou variável?

Com três lugares para guardar coisa, a dúvida é legítima. A pergunta que decide é sempre a mesma: esse valor precisa aparecer na tela? Se sim, estado. Se não, ref. Se ele pode ser recalculado a cada render, nem um nem outro — variável local.

Um exemplo de cada, no mesmo componente. O total é calculado a partir do estado, então é variável local: nasce de novo a cada render, sempre com o valor certo. O enviando aparece no botão, então é estado. O idDoAviso é um número que o navegador usa para cancelar um timer e que ninguém precisa ler na tela, então é ref.

function Encomenda() {
  const [preco, setPreco] = useState(2.5);
  const [quantidade, setQuantidade] = useState(1);
  const [enviando, setEnviando] = useState(false);
  const idDoAviso = useRef(null);

  const total = preco * quantidade;      // variável local

  return (
    <div>
      <p>total: {total}</p>
      <button disabled={enviando} onClick={() => setEnviando(true)}>
        Encomendar
      </button>
    </div>
  );
}

Repare que a ref não aparece no JSX. Isso é uma pista e tanto: se você se pegar escrevendo {caixa.current} dentro do return, pare e pergunte se aquilo não devia ser estado. A resposta quase sempre é sim.

6. Onde a ref é a ferramenta certa

Existe um punhado de situações que se repetem. Todas têm a mesma cara: o valor precisa durar entre renders, ninguém precisa vê-lo e mudá-lo não deve desenhar nada.

O timer é o exemplo mais útil no dia a dia. O setTimeout devolve um número que identifica o agendamento; para cancelar, você precisa desse número. Se ele ficar numa variável local, o próximo render o perde e o clearTimeout não tem o que cancelar. Numa ref, ele dura:

function Aviso() {
  const [texto, setTexto] = useState("");
  const id = useRef(null);

  function mostrar() {
    clearTimeout(id.current);                     // cancela o anterior
    setTexto("pão quentinho saindo do forno");
    id.current = setTimeout(() => setTexto(""), 6000);
  }

  return (
    <div>
      <button type="button" onClick={mostrar}>Avisar</button>
      <p>{texto}</p>
    </div>
  );
}

O texto do aviso é estado, porque aparece na tela. O id é ref, porque é um detalhe do navegador. Essa separação é o que mantém o componente legível: quem lê o código sabe, de cara, o que desenha e o que só controla.

7. Onde a ref é a ferramenta errada

O erro mais comum de quem acabou de conhecer a ref é usá-la para tudo — inclusive para o que a tela mostra. Aí a conta não fecha: o valor muda, mas a tela não. O React não tem como saber que você mexeu na caixa, e o desenho continua com o valor antigo até outra coisa provocar um render.

A Ana fez exatamente isso com o total da compra: guardou o total numa ref e mostrou {total.current}. Cada clique somava 2,50 na caixa, mas a tela continuava em 0. O código parecia certo, o botão funcionava, o console mostrava o valor crescendo — e o cliente via zero.

O total está numa ref, então a tela não acompanha a soma. Troque por useState e faça o clique somar 2,50 de um jeito que o painel mostre total: 2.5 depois do clique.

function App() {
  const total = useRef(0);

  return (
    <div>
      <p>total: {total.current}</p>
      <button
        id="somar"
        onClick={() => {
          total.current = total.current + 2.5;
        }}
      >
        Somar um pão
      </button>
    </div>
  );
}
<div>
  <p>total: 0</p>
  <button id="somar">Somar um pão</button>
</div>

function App() {
  const [total, setTotal] = useState(0);

  return (
    <div>
      <p>total: {total}</p>
      <button id="somar" onClick={() => setTotal(total + 2.5)}>
        Somar um pão
      </button>
    </div>
  );
}

Clique em Somar um pão no código inicial e veja o que acontece: nada. O valor dentro da ref foi para 2,5, mas nenhum render foi pedido, então o parágrafo continua mostrando 0. Nem o React reclama — ele não sabe que o valor mudou. Na solução, o setTotal avisa o React e o parágrafo acompanha.

A regra de bolso: se você escreveria {caixa.current} no JSX, o valor é estado. Ref é para o que fica nos bastidores — e o sintoma de ter errado é sempre o mesmo: o dado está certo no console e errado na tela.

8. As regras da ref

São poucas e todas têm a ver com o momento em que você mexe na caixa.

Sempre passe um valor inicial. useRef(0), useRef(""), useRef(null). O valor inicial define o que existe antes de qualquer clique e deixa claro o tipo de coisa que vai morar ali. No React 19 ele é obrigatório na assinatura, e começar com null é o padrão quando a caixa vai receber um elemento.

Não leia nem escreva durante o render. O corpo do componente pode rodar várias vezes, e o React espera que ele seja previsível. Mexer na ref no meio do render é um efeito colateral escondido — o mesmo tipo de problema que a aula de quando não usar efeito descreve. As exceções são a inicialização e o caso de medição que você viu no contador de renders, que é didático e não vai para produção. Para reagir a uma mudança, use evento ou efeito.

Não use ref para disparar desenho. Se a mudança precisa aparecer, é estado. Ref não avisa ninguém: nem o React, nem o componente filho, nem o CSS. Quem depende do valor só vê a mudança no próximo render, por acidente.

Não use ref como atalho para o DOM inteiro. A ref serve para falar com o elemento do seu componente. Se você se pegar procurando elementos com document.querySelector de dentro de um componente, provavelmente está brigando com o React: a maior parte do que se faz assim se faz com estado e props.

Não guarde o que dá para calcular. Se o valor sai de uma conta com estado e props, faça a conta no render, como na aula de estado derivado. Uma ref com um total calculado à mão é uma segunda fonte de verdade esperando para divergir.

9. Cenários do dia a dia

Cenário 1: o foco que não funcionava

A Ana chamou campo.current.focus() no corpo do componente e levou um erro de null. No primeiro render o elemento ainda não existe: a ref só é preenchida depois que o React monta o DOM. O conserto é chamar dentro do evento ou de um useEffect, que rodam depois da montagem. É sempre uma questão de quando, não de como.

Cenário 2: o total que não aparecia

Ela trocou useState por useRef para "evitar renders desnecessários" e o total parou de aparecer. O React não redesenha por causa de uma ref — é o que ela é. Se o valor aparece na tela, o lugar dele é o estado; otimizar render é assunto de useMemo e useCallback, não de ref.

Cenário 3: o timer que nunca era cancelado

O id do setTimeout ficou numa variável local dentro do componente. Cada render criava uma variável nova, o clearTimeout recebia undefined e o aviso antigo continuava aparecendo. Numa ref, o id sobrevive e o cancelamento funciona. Detalhe: o id é do navegador, não do React — quem devolve é o setTimeout.

11. Resumo

useRef cria uma caixa que dura enquanto o componente estiver na tela. O que está dentro dela fica em .current, e mexer ali não redesenha nada: o React não observa refs, só estado e props. Essa é a diferença que decide onde cada valor mora — se aparece na tela, estado; se é bastidor, ref; se dá para recalcular, variável local.

O uso mais comum é falar com o DOM: ref={campo} coloca o elemento em campo.current, e daí você chama focus(), select(), scrollIntoView() ou mede o que precisar. O segundo uso é guardar o que precisa durar sem desenhar: id de timer, trava de envio, valor anterior, contador de tentativas. O erro clássico é usar a ref para o que a tela mostra — o valor muda, o console confirma e a tela não acompanha.

As regras são curtas: valor inicial sempre, nada de ler ou escrever no meio do render, e nada de {caixa.current} no JSX. Guarde o sintoma para reconhecer o problema em dez segundos: dado certo no console, errado na tela, é sinal de que alguém guardou em ref o que devia estar no estado.

Para lembrar

  • useRef(0) devolve { current: 0 }, e esse objeto dura entre renders.
  • Mudar .current não redesenha a tela — e isso é intencional.
  • ref={campo} coloca o elemento do DOM em campo.current.
  • campo.current é null antes da montagem: acesse em evento ou efeito.
  • Estado aparece na tela; ref fica nos bastidores; variável local é recalculada.
  • Ref é boa para foco, id de timer, trava de envio e valor anterior.
  • Ref é ruim para o que a tela mostra: o valor muda e o desenho não.
  • Passe sempre um valor inicial: useRef(null), useRef(0).
  • Não leia nem escreva .current no meio do render.
  • Dois componentes iguais têm refs separadas: cada um fala com o seu elemento.
