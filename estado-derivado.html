Estado Derivado

A tela de encomendas da Ana mostra o total do dia. Ela guardou esse total num useState e atualizou em dois lugares — mas esqueceu o terceiro, o botão de remover, e desde então o caixa fecha com o valor errado. O problema não é o esquecimento: é que o total nunca precisou de um estado, porque ele pode ser calculado a partir da lista. Nesta aula a Ana aprende a diferença entre guardar e derivar.

Você vai aprender
  • O que é um valor derivado e por que ele não vira estado.
  • Calcular no render: reduce para somar, length para contar.
  • Filtrar uma lista enquanto a pessoa digita, sem estado intermediário.
  • Por que sincronizar dois estados com useEffect costuma piorar as coisas.
  • O caso mais traiçoeiro: copiar props para dentro de um estado.
  • As raras situações em que guardar o valor calculado faz sentido.

1. A cena: o total que fecha errado

A padaria precisa fechar o caixa no fim do dia. A tela mostra os pedidos e o total. A Ana criou um estado para a lista e outro para o total, e atualizou o total em cada função que mexe na lista: ao acrescentar, somou o preço; ao esvaziar, zerou. Faltou o botão de remover — e uma semana depois a diferença entre o total da tela e a soma dos pedidos era de vinte e três reais.

Esse bug tem uma característica que o torna caro: ele não aparece na hora. A tela continua bonita, o total continua sendo um número plausível, e só uma conferência na calculadora revela o erro. Pior: cada nova função que mexe na lista é uma chance nova de esquecer o total. Quanto mais o sistema cresce, mais lugares precisam lembrar de atualizar a mesma informação.

A saída é parar de guardar o que pode ser calculado. Se você tem a lista de pedidos, o total é a soma dos preços — não é um dado novo, é uma conta sobre os dados que já existem. Guardar a conta junto com os dados é manter duas cópias de uma verdade só, e cópias se desencontram. Essa é a definição de estado derivado: o valor que sai de outro valor.

A regra, escrita de forma direta: se dá para calcular a partir do estado e das props que você já tem, calcule durante o render. Nada de useState para o total, para a quantidade de itens, para a lista filtrada ou para saber se o botão deve ficar habilitado.

2. Estado é memória, não conta

O estado tem um papel específico: guardar o que não pode ser reconstruído a partir do resto. O texto que o cliente digitou não está em lugar nenhum além do estado. A lista de pedidos veio do servidor ou das ações do usuário — também não se recalcula. Mas o total, a contagem, a média, o filtro e o "está válido?" saem todos de combinações dessas fontes.

estado derivado
Um valor calculado a partir de outros valores, a cada render. Não tem useState, não tem setter, não desencontra.
cálculo no render
Fazer a conta no corpo do componente, antes do return. Roda toda vez que o componente desenha, e isso é barato.
fonte única
A ideia de que cada informação tem um dono só. Se o total é derivado da lista, a lista é a fonte; o total é consequência.
sincronização
Manter dois valores iguais na mão, chamando setters em todo lugar que mexe num deles. É a origem do bug desta aula.
snapshot
Uma cópia tirada num momento, que deve ficar congelada mesmo que o original mude. É um dos poucos casos em que guardar faz sentido.

Repare que derivar não é "fazer a conta toda hora por preguiça de otimizar". É a escolha que elimina uma classe inteira de bugs. Se a conta é pesada — somar dez mil itens a cada tecla, por exemplo —, existe uma ferramenta para isso, o useMemo, que guarda o resultado do cálculo enquanto as entradas não mudam. O useMemo é do Nível 2; a decisão de calcular vem antes da otimização.

3. Calculando o total no render

O reduce transforma uma lista num valor só: ele percorre os itens somando ao acumulador. A leitura é "comece em 0 e, para cada pedido, some o preço dele". Como é uma expressão, o resultado pode ser uma constante do componente — recalculada a cada render.

O total está guardado num estado e não acompanha a remoção. Tire o estado e calcule a soma a partir da lista. A missão clica em Remover e confere que o total passou a "R$ 20".

function App() {
  const [pedidos, setPedidos] = useState([
    { id: 1, nome: "Pão francês", preco: 1 },
    { id: 2, nome: "Bolo de cenoura", preco: 20 }
  ]);
  const [total, setTotal] = useState(21);

  function remover(id) {
    setPedidos(pedidos.filter((p) => p.id !== id));
  }

  return (
    <div>
      <ul>
        {pedidos.map((p) => (
          <li key={p.id}>
            {p.nome + " — R$ " + p.preco}{" "}
            <button onClick={() => remover(p.id)}>Remover</button>
          </li>
        ))}
      </ul>
      <p>Total: R$ {total}</p>
    </div>
  );
}

A diferença é brutal: a versão com estado tinha setTotal em três funções e esquecia uma. A versão derivada tem setTotal em nenhuma, porque o total não é atualizado — ele é recalculado. Remover, acrescentar, ordenar, limpar: qualquer mudança na lista chega ao total de graça, no render seguinte.

Para acompanhar, um console.log mostrando os dois valores a cada render deixa claro de onde o número vem:

render 1 — pedidos: 2, total: 21
render 2 — pedidos: 1, total: 20

O total nunca "ficou velho", porque ele nem existe entre um render e outro. É uma variável local, recriada a cada chamada da função. O que persiste é a lista; o resto é conta.

4. Filtrar enquanto a pessoa digita

O mesmo raciocínio vale para a lista filtrada pela busca. Muita gente cria um estado para "a lista que aparece" e outro para o texto da busca, e tenta manter os dois em sincronia. O resultado é uma tela que só filtra quando alguém lembra de chamar o setter — e um segundo estado que envelhece.

Digite "queijo" na busca: a lista continua com os dois pedidos, porque os itens visíveis foram copiados para um estado na primeira renderização. Mostre a lista filtrada na hora. A missão confere que sobrou um item.

function App() {
  const [pedidos] = useState([
    { id: 1, nome: "Pão francês" },
    { id: 2, nome: "Pão de queijo" }
  ]);
  const [busca, setBusca] = useState("");
  const [visiveis, setVisiveis] = useState(pedidos);

  return (
    <div>
      <input value={busca} onChange={(e) => setBusca(e.target.value)} />
      <ul>
        {visiveis.map((p) => (
          <li key={p.id}>{p.nome}</li>
        ))}
      </ul>
    </div>
  );
}

function App() {
  const [pedidos] = useState([
    { id: 1, nome: "Pão francês" },
    { id: 2, nome: "Pão de queijo" }
  ]);
  const [busca, setBusca] = useState("");

  const visiveis = pedidos.filter((p) =>
    p.nome.toLowerCase().includes(busca.toLowerCase())
  );

  return (
    <div>
      <input value={busca} onChange={(e) => setBusca(e.target.value)} />
      <ul>
        {visiveis.map((p) => (
          <li key={p.id}>{p.nome}</li>
        ))}
      </ul>
    </div>
  );
}

O estado que ficou é só o texto da busca — o que o usuário digitou, que não existe em nenhum outro lugar. A lista filtrada virou uma constante calculada: muda quando pedidos muda e quando busca muda, sem nenhum setter no caminho.

Note que a lista completa não se perde: visiveis é uma lista nova, e pedidos continua inteira no estado. Se a busca ficar vazia, includes("") é verdadeiro para todo texto e todos os itens voltam. Nada de guardar a lista original "para restaurar depois" — ela já está lá.

5. O efeito que sincroniza (e atrapalha)

Quando o valor guardado começa a desencontrar, a primeira ideia é sincronizar com useEffect: "sempre que a lista mudar, atualizo o total". O código parece cuidadoso e cria dois problemas novos.

const [total, setTotal] = useState(0);

useEffect(() => {
  setTotal(pedidos.reduce((soma, p) => soma + p.preco, 0));
}, [pedidos]);

O primeiro problema é o render duplo: o componente desenha com o total antigo, o efeito roda depois, chama setTotal, e o React desenha tudo de novo — com a tela piscando um valor velho no caminho. O painel da caixa mostra as duas passadas:

render — pedidos: 1, total: 21
render — pedidos: 1, total: 20   (o efeito chamou setTotal e desenhou de novo)

O segundo problema é pior: o efeito é uma segunda fonte da verdade. Se o total for atualizado em outro lugar, o efeito o sobrescreve no render seguinte. E se a lista de dependências estiver incompleta, o total para de acompanhar em silêncio. Você trocou um bug de esquecimento por um bug de ordem de execução, que é bem mais difícil de enxergar.

A regra prática: nunca use efeito para calcular algo a partir do estado ou das props. Se o valor sai de um cálculo, escreva o cálculo. O useEffect serve para falar com o mundo fora do React — buscar dados, ouvir um evento do navegador, mexer no título da aba — e as aulas de efeitos tratam disso em detalhe. Há uma aula inteira, quando não usar efeito, sobre exatamente este atalho.

Se você já tem um efeito desses no código, o conserto costuma ser apagar: delete o estado, delete o efeito e deixe a conta no corpo do componente. Menos linhas, menos renders, menos lugares para esquecer.

6. O caso mais traiçoeiro: props copiadas para o estado

Um componente recebe uma lista por props. Para "poder mexer nela", alguém copia a prop para um estado na primeira renderização:

function Lista({ itens }) {
  const [visiveis, setVisiveis] = useState(itens);
  return <ul>{visiveis.map((i) => <li key={i.id}>{i.nome}</li>)}</ul>;
}

O useState(itens) usa a prop apenas como valor inicial. O React guarda aquele array e não olha mais para a prop: nas renderizações seguintes, itens pode ter mudado, que visiveis continua com o primeiro array. A lista congela no dia em que o componente nasceu.

O botão acrescenta um pedido, mas a lista continua com um item, porque o componente copiou a prop para um estado. Mostre o que ele recebe, sem estado intermediário. A missão clica em Acrescentar e confere dois itens.

function Lista({ itens }) {
  const [visiveis, setVisiveis] = useState(itens);

  return (
    <ul>
      {visiveis.map((p) => (
        <li key={p.id}>{p.nome}</li>
      ))}
    </ul>
  );
}

function App() {
  const [pedidos, setPedidos] = useState([{ id: 1, nome: "Pão francês" }]);

  return (
    <div>
      <button
        onClick={() =>
          setPedidos([...pedidos, { id: pedidos.length + 1, nome: "Pão de mel" }])
        }
      >
        Acrescentar
      </button>
      <Lista itens={pedidos} />
    </div>
  );
}

A prop é o canal por onde o dado desce; o estado é a memória local. Copiar um para o outro cria uma memória que nasce desatualizada. Se o componente só mostra o que recebe, desenhe a prop. Se ele precisa mudar o dado, a mudança é do pai — o filho chama uma função recebida por prop, e o pai atualiza a lista de verdade.

Existe uma exceção legítima: quando o formulário precisa divergir do dado recebido até o usuário salvar. Aí a cópia é intencional — é um rascunho, um snapshot. Mesmo nesse caso, o valor inicial não deve ser lido uma vez só: costuma-se usar o key para remontar o formulário, ou comparar com a prop para oferecer "descartar alterações". É assunto de formulário, não de lista.

7. Quando guardar faz sentido

Derivar é o padrão, não uma lei absoluta. Existem três casos em que vale ter um estado para um valor que, em teoria, poderia ser calculado.

SituaçãoPor que guardarFerramenta
Cálculo caro a cada renderevitar refazer a conta sem necessidadeuseMemo (Nível 2)
Rascunho de formulárioo usuário edita antes de salvar; o dado original não pode ser alterado no meiouseState com valor inicial da prop
Dado que vem da redenão há de onde calcular: o servidor é a fonteuseState + useEffect

Fora desses casos, o valor guardado é uma cópia esperando para desencontrar. E note que o primeiro caso — cálculo caro — não é sobre corretude e sim sobre velocidade: o resultado do useMemo é o mesmo cálculo, feito menos vezes. Se a conta é barata, nem isso.

Um jeito de decidir em dois segundos: pergunte "se eu apagar este estado e calcular no render, a tela continua igual?". Se a resposta for sim, apague. O único motivo para manter é a tela precisar de um valor diferente do que o cálculo daria agora — e isso quase sempre significa que existe um estado de verdade escondido ali, como o texto que o usuário digitou.

8. Contas de verdade: números, arredondamento e formatação

Voltando ao total da Ana, dois cuidados práticos. O primeiro: preços em reais com centavos não são números redondos, e somar 0.1 + 0.2 em JavaScript dá 0.30000000000000004. Trabalhar em centavos inteiros evita o problema: guarde preco: 350 e mostre dividindo por 100 na hora de desenhar.

O segundo: formatar é derivar também. O texto "R$ 12,50" não precisa de estado; sai de total.toFixed(2) ou, melhor, de total.toLocaleString("pt-BR", { style: "currency", currency: "BRL" }), que já põe o símbolo, a vírgula e o ponto de milhar no lugar certo. Como é conta, muda sozinho quando o total muda.

const total = pedidos.reduce((soma, p) => soma + p.preco, 0);
const emReais = total.toLocaleString("pt-BR", { style: "currency", currency: "BRL" });
const vazio = pedidos.length === 0;

Três derivados, zero estados. E o componente fica fácil de ler: cada linha diz o que o valor é. Quando o cálculo cresce demais, ele pode virar uma função auxiliar fora do componente — o importante é que receba os dados e devolva o valor, sem guardar nada no caminho.

9. Cenários do dia a dia

Cenário 1: o contador que a tela mostra e o estado esquece

A Ana quis mostrar "3 pedidos na fila" e criou const [quantidade, setQuantidade] = useState(0), incrementando ao acrescentar. Quando removeu um pedido, a quantidade continuou em 3. O número que ela queria é pedidos.length — a lista já sabe quantos itens tem. Contagem é sempre derivada; estado para contagem é bug marcado para depois.

Cenário 2: o botão que fica habilitado com o carrinho vazio

Ela guardou podeFechar num estado e chamou setPodeFechar(true) quando o cliente digitou o nome. Ao apagar o nome, o botão continuou liberado. A condição é nome.trim() !== "" && pedidos.length > 0, calculada no render: assim o botão segue cada mudança sozinho, inclusive as que ela não previu. Botão habilitado é consequência, não memória.

Cenário 3: o total que "funcionava" porque a lista era pequena

Em uma tela com dois campos, ninguém notou que o total guardado ficava velho: as duas funções atualizavam o valor e o terceiro caminho ainda não existia. O bug apareceu cinco meses depois, com o botão de remover. Estado derivado não é preciosismo — é a diferença entre um número que sempre fecha e um número que fecha até alguém acrescentar uma tela.

11. Resumo

Estado é memória; derivado é conta. O texto digitado, a lista de pedidos e o dado que veio do servidor precisam de useState. O total, a contagem, a lista filtrada, o texto formatado e a condição que habilita um botão saem do que já está lá, calculados no corpo do componente, a cada render. Se dá para calcular, não guarde.

As ferramentas são as que você já conhece: reduce para somar, length para contar, filter para a lista que aparece, toLocaleString para o dinheiro. Sincronizar dois estados com useEffect não é solução: cria render duplo e uma segunda fonte da verdade. E copiar props para dentro de um estado é o caso extremo — a cópia nasce congelada e a lista para de crescer.

Com isso, a Ana tem a fila funcionando e o caixa fechando certo. O próximo assunto parece pequeno e mexe com tudo o que veio antes: quando um clique chama três setters de uma vez, quantas vezes o componente desenha? A resposta explica por que um contador às vezes soma só um, e é o tema da aula de atualizações em lote.

Para lembrar

  • Se dá para calcular a partir do estado e das props, calcule no render.
  • Total: pedidos.reduce((soma, p) => soma + p.preco, 0).
  • Contagem: pedidos.length; nunca um estado que você incrementa na mão.
  • Lista filtrada: pedidos.filter(...) na hora de desenhar.
  • Estado só para o que o usuário digitou, o que veio da rede ou o que não se recalcula.
  • Efeito que chama setter para sincronizar derivado = render duplo e segunda fonte da verdade.
  • useState(props.itens) congela a prop: a cópia não acompanha o pai.
  • Guardar faz sentido em cálculo caro (useMemo), rascunho de formulário e dado da rede.
  • Formatação é derivada: toLocaleString em vez de estado com texto pronto.
  • Preço em centavos evita 0.30000000000000004.
