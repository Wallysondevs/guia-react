Eventos

Evento é o que acontece com a página: o clique, a tecla, o envio do formulário. No React, você não chama addEventListener para cada elemento — escreve uma prop com o nome do evento e entrega uma função. Esta página é a consulta rápida: quais eventos existem, o que chega no objeto do evento, como ligar campo e estado com onChange, como segurar o formulário com onSubmit e quais erros aparecem no caminho. A Ana liga botões desde a primeira aula; aqui está o resumo que ela consulta quando um clique não faz o que devia.

Como usar esta página
  • A tabela da seção 4 é a lista de eventos para consultar; as outras explicam o mecanismo.
  • As caixas rodam React 19: edite, clique em Rodar e leia o painel.
  • Se o clique não faz nada, comece pela seção 2; se o campo não atualiza, pela seção 5.

1. O que é um evento no React

Evento é um acontecimento do navegador: o ponteiro clicou, a tecla desceu, o formulário foi enviado, o campo ganhou foco. O React escuta esses acontecimentos na raiz da aplicação e os entrega ao componente certo, na forma de uma prop. Escrever onClick={salvar} é dizer "quando o clique acontecer neste elemento, chame esta função".

O nome da prop é o nome do evento em camelCase: onClick, onChange, onSubmit, onKeyDown. O valor é sempre uma função. Não há string com código, como no HTML antigo (onclick="salvar()") — e essa é a primeira coisa que muda para quem vem do HTML.

function Botao() {
  function avisar() {
    console.log("clicou");
  }

  return <button onClick={avisar}>Avisar</button>;
}

Por baixo, o React usa um único listener na raiz e descobre qual componente deve receber cada evento. Isso economiza memória em listas grandes e faz os eventos funcionarem igual em qualquer navegador. O objeto que chega na sua função não é o evento nativo: é um SyntheticEvent, uma casca com a mesma interface — target, preventDefault, stopPropagation — e com os campos do evento original quando você precisa deles.

Na prática, você trata o evento como o do navegador. As diferenças aparecem em detalhes: os nomes são camelCase, o handler é uma função de verdade e o objeto que chega é a casca do React, não o evento nativo. Nada disso muda o dia a dia; muda a leitura das mensagens de erro.

evento
O acontecimento que o navegador avisa: clique, tecla, envio, foco. No React, vira o nome de uma prop.
handler
A função que você entrega ao evento: onClick={salvar}. Também chamada de manipulador.
SyntheticEvent
A casca que o React entrega no lugar do evento nativo, com a mesma interface e comportamento igual em qualquer navegador.
propagação
A subida do evento pela árvore: do elemento clicado até os pais. stopPropagation interrompe.
alvo
O elemento que disparou o evento (e.target), que pode não ser o dono do handler (e.currentTarget).

2. O handler é uma função, não uma chamada

A confusão número um é a diferença entre passar a função e chamar a função. onClick={salvar} passa a referência: o React guarda e chama no clique. onClick={salvar()} chama na hora do render e passa o retorno — que quase sempre é undefined.

// certo: a função é chamada no clique
<button onClick={salvar}>Salvar</button>

// errado: a função roda no render e o clique fica sem handler
<button onClick={salvar()}>Salvar</button>

// certo: uma função nova que chama com argumento
<button onClick={() => salvar("pão de queijo")}>Salvar</button>

O sintoma do erro depende do que a função faz. Se ela só registra no console, a mensagem aparece antes de qualquer clique — uma vez por render. Se ela muda estado, o React entra em laço: render chama a função, a função muda o estado, o estado pede outro render. Se ela devolve algo, o React reclama que esperava uma função.

Uma convenção de nome ajuda a não cair nisso: handler é verbo no infinitivo (salvar, remover, abrir) ou handle mais o evento (handleClique). Quando a função vira prop, o prefixo ao deixa claro o momento: aoSalvar. Quem lê onClick={aoSalvar} entende que a chamada acontece no clique, não ali.

Uma mesma função pode servir a vários botões. Se o comportamento é o mesmo, não há problema em repetir onClick={fechar} em três lugares; se muda por item, a função intermediária com argumento é o caminho. O que não vale é criar uma função nova em cada render dentro de um componente que compara props sem necessidade — e mesmo isso só importa quando há memo no meio.

Quando precisa de argumento, use a função intermediária. Ela é criada a cada render, o que é normal e não custa nada na maioria dos casos; só vira problema quando atravessa um componente embrulhado em memo, e aí a resposta é useCallback. O importante é que a chamada esteja dentro do corpo da função, não no valor da prop.

3. O objeto do evento

O primeiro parâmetro do handler é o evento. Dele saem as informações do que aconteceu: quem foi o alvo, qual o valor do campo, qual tecla foi pressionada, se o padrão do navegador deve continuar. Os campos mais usados estão na tabela.

function Campo() {
  function mudou(e) {
    console.log(e.type);          // "change"
    console.log(e.target.value);  // o texto digitado
  }

  return <input onChange={mudou} />;
}

Duas confusões comuns. e.target é quem disparou; e.currentTarget é quem tem o handler — num botão com um ícone dentro, clicar no ícone dá target diferente de currentTarget. E value é sempre texto: mesmo em type="number", o que chega é string, e converter é trabalho seu (Number(e.target.value)), com cuidado para o caso vazio.

O React antigo reaproveitava o objeto do evento e o limpava depois do handler; desde o React 17 isso acabou. Hoje dá para guardar e.target e ler depois, sem o clássico e.persist(). Se você encontrar esse método em código antigo, é herança daquela época.

Um hábito do HTML que não funciona no React: return false para cancelar o padrão. Aqui, quem cancela é e.preventDefault(), e o retorno do handler é ignorado. O mesmo vale para onclick="return false" em atributo — no React, o valor precisa ser função, e função não recebe string de código.

Para campo de texto, onChange no React dispara a cada tecla — é o evento input do navegador, não o change que só dispara ao sair do campo. Isso é proposital: o estado acompanha a digitação, e o valor na tela nunca fica atrasado. Para caixa de seleção, o mesmo onChange serve, lendo e.target.checked.

Eventos de ponteiro que mudam só a aparência — onMouseEnter, onMouseLeave — costumam ser melhor resolvidos com CSS (:hover), porque não precisam passar pelo estado. Use JavaScript quando a mudança precisa de dado, não de estilo.

Select e textarea usam o mesmo onChange do input: no select, e.target.value é o valor da opção escolhida; no textarea, é o texto inteiro, com as quebras de linha. Não existe onInput separado no uso normal — o onChange do React já cobre a digitação e a escolha, e é por isso que um único hábito serve para todos os campos do formulário.

5. Formulários: onChange e onSubmit

Campo controlado é o par value e onChange: o valor vem do estado, a mudança vai para o estado. Sem os dois, o campo fica travado e o React avisa. A leitura do texto está sempre em e.target.value; a leitura da marcação, em e.target.checked.

function Campo() {
  const [nome, setNome] = useState("");

  return (
    <div>
      <label htmlFor="nome">Nome</label>
      <input
        id="nome"
        value={nome}
        onChange={(e) => setNome(e.target.value)}
      />
      <p>Olá, {nome}</p>
    </div>
  );
}

O formulário inteiro tem um evento só: onSubmit. Ele dispara no clique de um botão type="submit" ou no Enter dentro de um campo. A primeira linha do handler precisa ser e.preventDefault(), senão o navegador envia e recarrega a página, levando o estado junto. O botão que não envia leva type="button", porque dentro de um form o padrão é submit.

No inicial, digitar não muda nada: o handler grava o mesmo nome do render e o estado não sai do lugar. Na solução, cada tecla atualiza o estado e a saudação acompanha. O value é o que fecha o ciclo: sem ele, o campo mudaria sozinho e o estado ficaria desatualizado — o problema inverso.

Enter dentro de um campo de texto também envia o formulário: é o comportamento nativo, chamado de submissão implícita. Por isso o handler de envio precisa estar no form, e não no onClick do botão — assim os dois caminhos passam pelo mesmo lugar. Se você quer Enter para outra coisa (buscar enquanto digita, por exemplo), o evento é onKeyDown no campo, e o preventDefault impede o envio.

6. Propagação, teclado e acessibilidade

Eventos sobem na árvore. Um clique num botão dentro de um cartão dispara o handler do botão e depois o do cartão. Quando você não quer o segundo, chame e.stopPropagation() no primeiro. Quando quer cancelar o comportamento do navegador — o envio do form, o link que navega —, chame e.preventDefault(). São coisas diferentes: uma para a subida, outra para o padrão.

function Cartao({ children }) {
  function clicou() {
    console.log("cartão");
  }

  return <div onClick={clicou}>{children}</div>;
}

// dentro do cartão, um botão que não deve abrir o cartão
<button
  onClick={(e) => {
    e.stopPropagation();
    remover(id);
  }}
>
  Remover
</button>

Teclado é o outro lado. onKeyDown recebe e.key, com nomes como "Enter", "Escape" e "ArrowUp". Use quando o atalho faz sentido: Enter para confirmar uma busca, Escape para fechar um painel. Não use para recriar o que o elemento já faz — um button responde a Enter e a Espaço sozinho.

Isso vale como regra maior: clique em div funciona com mouse e falha com teclado, porque a div não recebe foco nem responde a Enter. Botão é button. O mesmo vale para o label, que já transfere o clique para o campo, e para o form, que já trata o Enter. Usar o elemento certo economiza evento e código.

onFocus e onBlur servem para validar no momento certo. O primeiro dispara quando o campo ganha o cursor; o segundo, quando perde. A dupla é útil para mostrar a dica ao entrar e a mensagem de erro ao sair, sem incomodar quem ainda está digitando a primeira letra. O blur também acontece quando a pessoa clica em outro lugar — inclusive no botão de enviar —, então a validação ao sair precisa ser rápida e não pode bloquear o clique.

Foco é um estado do navegador, não do React: quem guarda "este campo está em foco" é o DOM, e o :focus-visible do CSS resolve a maioria dos casos de estilo. Use o evento quando precisar de dado — contar tentativas, buscar sugestões ao entrar — e deixe a aparência com o CSS.

7. Passar argumentos e manter a identidade

Para mandar um dado junto com o clique, a função intermediária resolve: onClick={() => remover(id)}. Outra opção é ler o dado do próprio elemento com data-* — data-id={id} e e.currentTarget.dataset.id —, mas isso devolve string e esconde a intenção; prefira o argumento.

O botão chama pedir() sem argumento e a tela mostra undefined. Passe o nome do pão com uma função intermediária: onClick={() => pedir("pão de queijo")}.

function App() {
  const [pedido, setPedido] = useState("");

  function pedir(nome) {
    setPedido(nome);
  }

  return (
    <div>
      <button id="queijo" onClick={() => pedir()}>
        Pedir pão de queijo
      </button>
      <p>pedido: {pedido}</p>
    </div>
  );
}
<div>

Repare que pedir() sem argumento grava undefined, e o painel mostra o campo vazio depois dos dois-pontos. A função intermediária é nova a cada render — irrelevante aqui, porque ela não é prop de um filho em memo. Quando for, o assunto é useCallback, e o cuidado é o mesmo: a função precisa ver os valores do render em que foi criada.

Em lista, cada item cria a sua função: {itens.map((i) => <li key={i.id}><button onClick={() => remover(i.id)}>X</button></li>)}. A key identifica a linha; o argumento identifica o dado. Um não substitui o outro.

Em handler assíncrono, leia o que precisa do evento antes do primeiro await. O objeto do evento continua válido — o React não o limpa mais —, mas e.target aponta para o elemento do momento, e o valor pode ter mudado enquanto a resposta não chegava. Guarde const nome = e.target.value e use a variável depois; é mais previsível e mais fácil de testar.

8. Erros comuns

Quando um clique não faz nada, a ordem de investigação é sempre a mesma: o handler é uma função? O elemento certo recebeu o evento? Algum pai está interceptando? Um console.log("clicou") dentro do handler responde à primeira pergunta em segundos; se ele aparece no console, o problema está no que a função faz, não no evento.

O erro da string tem mensagem específica no console de desenvolvimento:

Warning: Expected `onClick` listener to be a function, instead got a value of `string` type.

A leitura: o valor entre aspas é texto, e o React não executa texto. Em produção o aviso não aparece — o handler simplesmente não roda e o botão fica morto. É o tipo de erro que passa no teste de quem só olha a tela e falha no primeiro clique de verdade.

Os outros erros desta tabela não geram mensagem nenhuma: campo travado, formulário que recarrega, div que não responde ao teclado. Por isso vale a conferência rápida antes de entregar: todo handler é uma função? Todo campo controlado tem value e onChange? Todo form tem onSubmit com preventDefault? Todo clique que precisa de teclado usa button?

Resumo

Evento no React é prop em camelCase com uma função como valor: onClick, onChange, onSubmit. Passe a referência (onClick={salvar}) ou uma função intermediária quando precisar de argumento (onClick={() => salvar(id)}); nunca chame a função no valor da prop.

O handler recebe um SyntheticEvent com target, value, checked, key, preventDefault e stopPropagation. Campo controlado é value mais onChange lendo e.target.value; formulário é onSubmit com preventDefault na primeira linha e botão de envio com type="submit".

Eventos sobem na árvore; stopPropagation para a subida e preventDefault cancela o padrão. Teclado e clique funcionam de graça nos elementos certos — button, label, form —, e é aí que a maior parte dos problemas de acessibilidade se resolve antes de virar código.

Para lembrar

  • Eventos são props em camelCase com uma função como valor.
  • onClick={salvar} passa a função; salvar() chama na hora.
  • Para argumento, use onClick={() => salvar(id)}.
  • e.target.value é texto, mesmo em type="number".
  • Checkbox e rádio leem e.target.checked.
  • preventDefault cancela o padrão; stopPropagation para a subida.
  • onChange no React dispara a cada tecla.
  • onSubmit precisa de preventDefault na primeira linha.
  • Dentro de um form, botão sem type envia.
  • Clique em div não funciona no teclado: use button.
