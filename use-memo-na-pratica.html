useMemo na Prática

O catálogo da Ana tem quatrocentos pães, e a tela de resumo conta quantos são doces e quantos são salgados. A conta é barata uma vez; o problema é que ela roda em todo desenho — até quando a Ana só troca a cor do aviso. Nesta aula ela usa o useMemo nos três casos que aparecem de verdade em um projeto: a conta derivada, a identidade que um filho memoizado precisa e o elemento JSX que não pode ser recriado.

Você vai aprender
  • Como decidir se vale memoizar — e como medir antes de decidir.
  • Guardar o resultado de uma conta derivada que roda em todo desenho.
  • Dar identidade estável para um array que alimenta um componente memoizado.
  • Memoizar um elemento JSX para manter a referência entre desenhos.
  • Onde a identidade importa: dependência de efeito, prop de memo, value de contexto.
  • O custo do useMemo: comparação, memória e código mais difícil de ler.
  • Quem guarda o quê: useMemo, useCallback e memo.

1. A cena: a conta que roda em todo desenho

A página de resumo da padaria mostra dois números: quantos pães doces e quantos salgados existem no catálogo. O catálogo vem de uma planilha e tem quatrocentas linhas. A conta é simples — um filter para cada tipo — e leva alguns milissegundos. Uma vez só, ninguém nota.

O problema é que a função roda a cada desenho do componente. A Ana troca o texto do aviso, a conta roda. Ela abre o menu, a conta roda. Ela digita no campo de busca, a conta roda em cada tecla. Como o resultado é sempre o mesmo enquanto o catálogo não muda, esse trabalho é desperdício — e, em uma tela com mais de uma conta dessas, é a diferença entre uma digitação fluida e uma travada.

O useMemo resolve exatamente isso: ele guarda o resultado de um cálculo entre desenhos e só refaz o cálculo quando uma das dependências muda. A forma é useMemo(() => conta(), [dependencias]). Se as dependências forem as mesmas do desenho anterior, o React devolve o valor guardado sem chamar a função.

A pergunta certa, antes de qualquer código, é se vale a pena. Memoizar tem custo e complica a leitura; um cálculo de dois números não precisa. O critério prático: o cálculo é caro, ou o resultado é usado em um lugar que depende de identidade — um filho memoizado, uma dependência de efeito, um valor de contexto.

2. Medir antes de memoizar

A Ana mediu antes. Colocou um performance.now() antes e depois da conta e imprimiu a diferença. É o jeito mais simples de responder "isso é caro?" sem chutar. O número que ela viu no notebook, com o catálogo de quatrocentas linhas, foi este:

agrupar: 9.4 ms
agrupar: 9.1 ms
agrupar: 9.6 ms

Nove milissegundos por desenho é bastante quando o desenho acontece a cada tecla. Se a conta levasse 0,2 ms, a resposta seria outra: provavelmente não valeria memoizar, porque comparar dependências e guardar o resultado também custa. O React DevTools tem uma aba Profiler que mostra o tempo de cada componente em cada desenho; é a ferramenta mais direta para achar o culpado antes de mexer no código.

conta derivada
Um valor que pode ser calculado a partir de outros: o resumo a partir do catálogo, o total a partir dos itens.
useMemo
O gancho que guarda o resultado de uma função entre desenhos e a refaz só quando as dependências mudam.
dependências
O array que decide quando refazer a conta. Vale a mesma regra do efeito: lista tudo o que a função lê.
identidade
A referência do valor. Dois arrays com o mesmo conteúdo são identidades diferentes.
perfil
A medição. Sem ela, memoizar é chute; com ela, é decisão.

E há um detalhe de honestidade que vale desde já: o useMemo é uma dica, não uma garantia. A documentação diz que o React pode descartar o valor guardado em situações de pressão de memória. Nenhuma regra do seu site pode depender de "essa conta rodou uma vez só"; o que você pode esperar é que ela rode menos.

3. Guardando a conta derivada

Na caixa, o resumo é calculado no corpo do componente e conta quantas vezes a conta rodou, em uma variável de módulo. Clique em Trocar aviso: o aviso é só um texto e, mesmo assim, o contador sobe. A missão é envolver a conta em useMemo com o array vazio, porque o catálogo é uma constante de módulo e não muda.

O resumo do catálogo é recalculado a cada desenho. Envolva a chamada de agrupar(CATALOGO) em um useMemo com dependências [] e faça o contador continuar em 1 depois do clique.

const CATALOGO = Array.from({ length: 400 }, (_, i) => ({
  nome: "pão " + (i + 1),
  tipo: i % 3 === 0 ? "doce" : "salgado",
}));

let agrupamentos = 0;
function agrupar(itens) {
  agrupamentos = agrupamentos + 1;
  return {
    doces: itens.filter((p) => p.tipo === "doce").length,
    salgados: itens.filter((p) => p.tipo === "salgado").length,
  };
}

function App() {
  const [aviso, setAviso] = useState("Padaria aberta");
  const resumo = agrupar(CATALOGO);

  return (
    <div>
      <button id="trocar" onClick={() => setAviso("Forno quente até as 10h")}>
        Trocar aviso
      </button>
      <p>{aviso}</p>
      <p>doces: {resumo.doces}</p>
      <p>salgados: {resumo.salgados}</p>
      <p>agrupamentos: {agrupamentos}</p>
    </div>
  );
}

O painel do código inicial termina com agrupamentos: 1, que é a montagem. Depois do clique, o código antigo mostra 2 e a solução continua em 1. Os números de doces e salgados são os mesmos nos dois casos — a diferença está só em quando a conta acontece.

Repare no []. Ele diz "não dependo de nada que mude". Se o catálogo viesse de uma prop ou de um estado de busca, ele entraria no array, e é aí que mora o erro clássico: esquecer uma dependência e mostrar o resumo de ontem. A regra é a mesma do useEffect: liste tudo o que a função lê — nada a mais (que faria refazer à toa) e nada a menos (que faria guardar valor velho).

4. Identidade para um filho memoizado

O segundo uso é o que mais aparece em código de verdade, e ele não tem a ver com tempo de cálculo: tem a ver com referência. O memo compara props por identidade, então um array filtrado no corpo do pai é sempre "novo" — e o filho desenha mesmo recebendo o mesmo conteúdo.

Na caixa, o componente Doces está embrulhado com memo e recebe os doces filtrados. Como o filter acontece no corpo do App, cada desenho do pai entrega um array novo e o memo libera o desenho do filho. A conta é barata; o problema é a identidade.

O filho está com memo, mas recebe um array novo a cada desenho. Envolva o filter em um useMemo com dependências [] e faça o número continuar em 1 depois do clique.

const PAES = [
  { nome: "sonho", tipo: "doce" },
  { nome: "pão francês", tipo: "salgado" },
  { nome: "pão de queijo", tipo: "salgado" },
];

let desenhos = 0;
const Doces = memo(function Doces({ itens }) {
  desenhos = desenhos + 1;
  return <p>doces desenhados: {desenhos} ({itens.length} pão(es))</p>;
});

function App() {
  const [aviso, setAviso] = useState("Padaria aberta");
  const doces = PAES.filter((p) => p.tipo === "doce");

  return (
    <div>
      <button id="trocar" onClick={() => setAviso("Forno quente até as 10h")}>
        Trocar aviso
      </button>
      <p>{aviso}</p>
      <Doces itens={doces} />
    </div>
  );
}

O useMemo aqui não economiza o filter de três itens — isso seria irrelevante. Ele existe para que a referência do array seja a mesma entre desenhos, e o memo do filho possa concluir "nada mudou". É a dupla que funciona: um estabiliza a referência, o outro compara.

Quando o array depende de um filtro escolhido pela pessoa, o padrão é o mesmo, com o filtro no array de dependências: useMemo(() => filtrar(filtro), [filtro]). Aí a referência muda só quando o filtro muda — que é exatamente quando o filho precisa desenhar.

5. O elemento JSX memoizado

O terceiro caso é o mais surpreendente e o mais útil para quem tem um layout com children. Quando você escreve <Moldura><p>oi</p></Moldura>, aquele <p>oi</p> é um objeto criado no desenho do pai. Para o memo da moldura, é uma prop nova toda vez — e o desenho dela não é pulado.

A saída é tratar o elemento como qualquer outro valor: guardá-lo em um useMemo. Se as dependências não mudarem, a referência é a mesma, e o memo da moldura funciona. É a mesma ideia da seção anterior, com JSX no lugar do array.

A Moldura tem memo, mas o <p> passado como filho é recriado a cada desenho. Guarde o conteúdo em um useMemo com [] e faça o número continuar em 1 depois do clique.

let desenhos = 0;
const Moldura = memo(function Moldura({ children }) {
  desenhos = desenhos + 1;
  return (
    <div>

    </div>

});

Esse padrão tem nome na comunidade: "elemento como prop" ou "slot". Ele é útil quando o conteúdo é caro ou quando a moldura tem animações e não pode redesenhar. Também é a explicação de metade dos casos em que "o memo não funciona": quase sempre há um elemento sendo recriado no meio.

6. Onde a identidade importa

Os três casos acima têm a mesma raiz: alguém compara referências. Vale conhecer os quatro lugares em que isso aparece, porque o conserto é sempre o mesmo — useMemo para valores, useCallback para funções — e o sintoma muda de lugar.

O caso do efeito merece um exemplo, porque é o que mais surpreende. Um efeito que busca dados com [filtro], onde filtro é um array montado no corpo do componente, roda a cada desenho — e a aba Network mostra uma busca por tecla digitada em qualquer outro campo da tela:

buscando doces...
buscando doces...
buscando doces...

Com o array estabilizado por useMemo, o efeito roda quando o filtro muda de verdade. E, se a dependência fosse um objeto com duas propriedades, valeria memoizar o objeto inteiro ou listar as propriedades soltas — o segundo jeito costuma ser mais simples de ler e de acertar.

Nos contextos, o padrão tem nome próprio: value memoizado. Um provider que recebe value={{ cliente, entrar }} cria um objeto novo a cada desenho do provider, e todos os consumidores desenham junto. Com useMemo, o valor só muda quando o cliente ou a função mudam — e aí a função também precisa de useCallback, ou a corrente se rompe no elo seguinte.

7. O custo de memoizar

O primeiro custo é a comparação. O useMemo guarda o valor e o array de dependências do desenho anterior e compara item por item. Para duas dependências primitivas, é barato. Para um array de dez itens, é uma comparação de dez — sempre menor que refazer a conta, se a conta for caras, e sempre maior se não for.

O segundo é a memória: o valor guardado fica vivo enquanto o componente estiver montado. Guardar uma lista de quatrocentas linhas para economizar um filter pode ser um mau negócio; guardar a contagem de doces, um número, é barato. O que você guarda importa tanto quanto guardar.

O terceiro custo é o mais subestimado: a leitura. Cada useMemo é uma pergunta nova para quem lê — "por que isso está memoizado?" — e um lugar novo onde a dependência pode estar errada. Em código de time, um useMemo sem motivo aparente vira discussão em revisão. O comentário curto ("identidade estável para o Doces") paga o preço.

8. Quem guarda o quê

Os três nomes parecidos confundem, e a diferença é simples quando se olha para o que cada um guarda. O memo guarda o resultado do desenho de um componente. O useMemo guarda um valor calculado no corpo. O useCallback guarda uma função — é o useMemo de uma função, sem a camada de chamada.

const total = useMemo(() => precos.reduce(somar, 0), [precos]);
const aoSomar = useCallback((item) => setItens((l) => [...l, item]), []);
const Item = memo(function Item({ item, aoSomar }) { /* ... */ });

Nesse trecho os três trabalham juntos: memo evita desenhar o item, useCallback mantém a função estável para o memo funcionar e useMemo guarda o total. Se um dos três faltar, o elo se rompe — e o sintoma é sempre "continua desenhando".

Uma nota sobre o futuro, porque ela muda o conselho: com o React Compiler ligado no projeto, boa parte desses useMemo vira automático. Ele não vem ligado por padrão no React 19, e a documentação recomenda tratar a memoização manual como exceção. Enquanto o projeto não usa o compilador, medir e memoizar o que dói continua sendo o caminho.

9. Cenários do dia a dia

Cenário 1: o resumo ficou com o valor de ontem

A Ana memoizou a conta com [], mas o catálogo vinha de uma busca que mudava. O resumo congelou no primeiro resultado. O conserto é listar a dependência que a conta lê. O aviso do ESLint (react-hooks/exhaustive-deps) aponta exatamente isso, e ele aparece no editor antes de o bug chegar na tela.

Cenário 2: a lista de cards pesada e o useMemo que não resolveu

Memoizar o array filtrado resolveu a identidade, e a digitação continuou pesada: o problema era o número de cards desenhados, não a referência. A solução foi memoizar cada card, e depois limitar quantos aparecem. É o lembrete de que useMemo é uma ferramenta entre várias — e que a medição diz qual usar.

Cenário 3: useMemo em tudo desde o primeiro dia

Um projeto com useMemo em cada variável fica mais difícil de ler e não fica mais rápido: as contas que importam continuam lá. O hábito saudável é escrever direto, medir no Profiler e memoizar só o que aparece na medição — ou o que precisa de identidade estável por contrato, como a prop de um filho memoizado.

11. Resumo

O useMemo guarda o resultado de um cálculo entre desenhos e refaz o cálculo só quando uma dependência muda. Ele serve para três coisas na prática: economizar uma conta derivada caras, dar identidade estável a um valor que outro lugar compara (o memo de um filho, a dependência de um efeito, o value de um contexto) e guardar um elemento JSX para uma moldura memoizada.

O array de dependências segue a mesma regra do efeito: tudo o que a função lê, nada a mais e nada a menos. O custo existe — comparação, memória e legibilidade —, então a ordem é sempre escrever claro, medir e memoizar o que dói. Números que vêm do performance.now() ou do Profiler decidem melhor do que a intuição.

E, se o objeto guardado for uma função, a ferramenta é o useCallback: a mesma ideia, com o foco em manter a referência estável para quem compara. É o assunto da próxima aula, onde a corrente de dependências aparece inteira.

Para lembrar

  • useMemo(() => conta(), [deps]) guarda o resultado, não a função.
  • As dependências listam o que a conta lê; [] só quando não lê nada que mude.
  • Serve para conta caras, para identidade estável e para elemento JSX.
  • Identidade importa em: prop de memo, dependência de efeito, value de contexto.
  • Array filtrado no corpo do pai é sempre novo — e derruba o memo do filho.
  • Elemento JSX também é valor: dá para guardar em useMemo.
  • Medir antes: Profiler ou performance.now().
  • Memoizar não é garantia: o React pode descartar o valor guardado.
  • Para funções, o nome é useCallback.
  • O React Compiler memoiza sozinho — e não vem ligado por padrão.
