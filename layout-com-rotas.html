Layout com Rotas

A Ana percebeu um detalhe no site: o cliente digita "sonho" na busca do topo, clica em "Cardápio" e o campo esvazia. O topo não sumiu — ele foi recriado, porque estava dentro de cada página. Nesta aula ela separa a moldura do site do conteúdo das rotas: o topo, o menu e o rodapé ficam montados uma vez só, e só a área do meio troca quando o caminho muda.

Você vai aprender
  • O que é um layout em uma aplicação com rotas e por que ele existe.
  • Por que o topo dentro de cada página perde o estado a cada navegação.
  • Como receber a página por children e deixar o layout sem conhecer as rotas.
  • Como aninhar layouts para uma seção com sub-navegação própria.
  • O que um layout não deve fazer: buscar os dados da página, guardar o estado dela ou levar key por caminho.
  • O que muda no desempenho quando a moldura fica montada.
  • Onde ficam as rotas quando o layout é só a moldura.

1. A cena: o campo de busca que esvazia

O site da Ana tem uma barra no topo com o nome da padaria e um campo de busca. Ele aparece na vitrine, no cardápio e no contato. Acontece que o campo está escrito dentro de cada uma das três páginas — a Ana copiou e colou, como fazia no tempo do HTML puro. Funciona, até o cliente digitar alguma coisa e navegar: o texto desaparece.

Não é um bug do campo, e sim do lugar onde ele mora. Cada página tem o seu próprio campo, com o seu próprio estado. Quando o cliente troca de página, o React tira a página antiga da tela (desmonta) e monta a nova. O campo novo nasce vazio, porque nada do antigo sobreviveu. Na cabeça do cliente, é "o site esqueceu o que eu digitei".

A solução é a mesma ideia que abriu o guia, aplicada um nível acima: em vez de repetir o topo em cada página, escreva um topo e coloque as páginas dentro dele. O topo passa a ser o que fica; o que muda é só a área do conteúdo. Esse arranjo tem nome: o layout (ou moldura, ou shell) da aplicação.

E o ganho não é só o campo de busca. Um layout montado uma vez significa menos trabalho para o navegador a cada navegação, menos requisições se ele carrega algo, e um lugar óbvio para o que é comum a todas as páginas: cabeçalho, menu, rodapé, aviso de cookies.

2. O que é um layout, na prática

Um layout é um componente que desenha a moldura e reserva um espaço para o conteúdo. Ele não sabe qual página está ali: recebe o conteúdo pronto pela prop children e o coloca no lugar certo. Quem decide qual é o conteúdo é o componente de cima, o mesmo que guarda a rota atual. A ideia de compor telas com pedaços assim é a mesma de componentes de layout.

layout
O componente que desenha o que é comum a várias rotas: topo, menu, rodapé, largura da página.
children
A prop que carrega o conteúdo passado entre as tags do componente. É o encaixe do layout.
moldura
Outro nome para o layout. Ajuda a lembrar: moldura fica, quadro troca.
layout aninhado
Um layout dentro do outro: a moldura do site e, dentro dela, a moldura de uma seção com a sua sub-navegação.
remontar
Tirar o componente da tela e criar de novo. O estado volta ao inicial e os efeitos rodam outra vez.

A distinção que resolve a aula inteira: renderizar de novo é barato e normal — o componente é chamado, compara o que mudou e segue; remontar é caro — o componente é destruído e recriado, com estado zerado e efeitos disparando de novo. Um layout bem colocado pode renderizar a cada navegação; o que não pode é remontar.

Nos roteadores de verdade, esse arranjo costuma aparecer de duas formas: uma rota "pai" que desenha o layout e um <Outlet /> no lugar do conteúdo, ou o layout envolvendo as rotas filhas como children. As duas ideias são a mesma: a moldura fica acima da troca de páginas.

3. O topo dentro de cada página remonta

Na caixa, o topo mora dentro de Vitrine e dentro de Cardapio. Digite algo no campo e clique em Cardápio: o caminho muda, o conteúdo muda e o campo volta vazio. O painel mostra o valor do campo, então a perda fica visível.

O Topo está repetido nas duas páginas e remonta a cada navegação. Suba o <Topo /> para o App, acima da troca de páginas, e apague das páginas. Depois digite pão no campo e clique em Cardápio.

O painel depois do clique mostra o que interessa: o campo vale pão e o cardápio está no lugar do conteúdo. O Topo não foi recriado, porque nada mudou na posição dele na árvore — o React só trocou o filho que veio depois do botão.

A regra que se extrai daqui é curta: um componente perde o estado quando sai da tela. Se um estado precisa sobreviver à navegação, ele tem de morar acima da troca de páginas. Isso vale para o campo de busca do topo, para a aba aberta do menu, para o carrinho aberto — tudo o que deveria continuar igual enquanto o cliente navega.

4. A página como children

Subir o topo resolve o campo de busca, mas não resolve o próximo problema: agora o App conhece o topo, a troca de páginas e os botões. Se a padaria crescer para dez páginas, esse componente vira um emaranhado. A solução é separar a moldura em um componente próprio, que recebe o conteúdo por children.

O desenho fica assim: o App guarda o caminho, escolhe a página e monta a árvore <Layout><Pagina /></Layout>. O Layout só sabe que precisa desenhar um cabeçalho, um <main> e um rodapé, e que o conteúdo vai dentro do main. Ele não importa nenhuma página e não conhece nenhum caminho.

O Layout conhece as rotas com uma lista de if, e a página de contato ficou de fora: ela não aparece. Troque a prop caminho por children e deixe o App escolher a página. Depois clique em Contato.

function Vitrine() {
  return <p>pães quentinhos na vitrine</p>;
}

function Cardapio() {
  return <p>pão de queijo no cardápio</p>;
}

function Contato() {
  return <p>fale com a Ana pelo balcão</p>;
}

function Layout({ caminho }) {
  return (
    <div>
      <header>
        <p>Padaria da Ana</p>
      </header>
      <main>
        {caminho === "/" && <Vitrine />}
        {caminho === "/paes" && <Cardapio />}
      </main>
    </div>
  );
}

function App() {

  return (
    <div>
      <button id="ir-contato" onClick={() => setCaminho("/contato")}>Contato</button>
      <Layout caminho={caminho} />
    </div>
  );
}

O painel do código inicial mostra o <main> vazio depois do clique: o caminho é /contato, nenhuma das duas condições casou e o layout não tinha o que desenhar. Depois da missão, o mesmo clique mostra a frase do contato dentro do main — e, se amanhã a Ana criar a página de promoções, basta acrescentar uma linha no mapa de páginas. O Layout não muda.

Essa é a vantagem prática do children: o layout não precisa crescer quando o site cresce. Quem conhece as rotas é um lugar só — o mapa PAGINAS —, e o layout é uma peça de apresentação, do mesmo tipo que você viu na aula de composição. Moldura e conteúdo evoluem separados.

5. Layouts aninhados

Quando uma seção tem páginas próprias, ela merece um layout próprio. As encomendas da Ana têm duas abas — novas e prontas — e um cabeçalho de seção com o total do dia. Esse cabeçalho pertence à seção, não ao site; e, como o topo, ele não pode remontar quando o cliente troca de aba.

Na caixa, o SubTopo está dentro de cada aba e conta as montagens. O contador usa useState com uma função de inicialização, que roda só na primeira vez — é o jeito de contar montagens sem criar um laço. Clique em Prontas e veja o número subir para 2: o submold antigo saiu e outro nasceu.

O SubTopo mora dentro de cada aba e remonta na troca. Crie SecaoEncomendas, que desenha o SubTopo e recebe a aba por children; no App, envolva a aba escolhida com ela. Depois clique em Prontas.

let montagensSub = 0;

function SubTopo() {
  const [id] = useState(() => {
    montagensSub = montagensSub + 1;
    return montagensSub;
  });
  return <p>sub-topo montado {id} vez(es)</p>;
}

function Novas() {
  return (
    <div>

}

function Prontas() {
  return (

function App() {

O painel do código inicial já mostra o problema sem clique: o SubTopo aparece com o número 1, porque é a primeira montagem. Depois do clique, o mesmo painel do código antigo mostraria 2. Na solução, o número fica em 1 e a frase "encomendas prontas" aparece — a seção inteira continuou no lugar, só a aba trocou.

Repare na forma da solução: a seção recebe children e desenha o SubTopo antes deles. Se a padaria tiver uma terceira aba, nada muda; se a seção precisar de um botão "atualizar", ele mora ali e não é recriado a cada troca de aba. É o mesmo padrão do layout do site, um nível abaixo — e é por isso que esse arranjo é chamado de aninhado: um layout dentro do outro, cada um dono do seu pedaço.

6. O que o layout não deve fazer

O primeiro erro é guardar no layout um estado que pertence à página. A posição do scroll da lista, a aba selecionada dentro de um painel, o texto do formulário de contato: se estiver no layout, sobrevive à navegação e aparece na página errada depois. A pergunta é sempre "esse estado deve sobreviver a uma troca de página?" — se a resposta é não, ele mora na página.

O segundo é buscar no layout os dados da página. Acontece quando o layout começa a crescer: ele busca os pães para mostrar a contagem no menu, busca os pedidos para o aviso, busca o perfil para o avatar. Cada navegação passa a disparar uma rodada de pedidos que nada tem a ver com o conteúdo que o cliente quer ver. Dados da moldura ficam na moldura; dados da página, na página.

O terceiro é o key. Escrever <Layout key={caminho}> parece inofensivo e é a forma mais rápida de remontar a moldura inteira a cada navegação: mudar a key diz ao React "isto é outro componente". O campo de busca esvazia, o menu fecha, os efeitos rodam de novo. Se você precisa remontar de propósito — para zerar um formulário ao trocar de registro, por exemplo — use a key no componente certo, não na moldura.

O quarto é deixar o layout decidir qual é a página. Enquanto ele tiver a lista de caminhos, cada página nova exige mexer em dois lugares. O layout desenha a moldura; quem escolhe o conteúdo é quem sabe qual é a rota — o componente que guarda o caminho.

7. O que muda no desempenho

Manter a moldura montada economiza trabalho em três frentes. A primeira é a criação de elementos: a cada navegação, o React deixa de criar e comparar a árvore do topo, do menu e do rodapé. A segunda são os efeitos: um layout com um efeito de "carregar o aviso do dia" não repete o pedido a cada clique. A terceira é a memória: cada remontagem cria objetos novos que o coletor de lixo vai ter de varrer.

O ganho não é gigante em um site de quatro páginas — e vale dizer isso com honestidade. Em uma aplicação pequena, o motivo para separar o layout é o estado que precisa sobreviver e a organização do código, não os milissegundos. O desempenho passa a importar quando a moldura é pesada (um menu grande, um avatar com pedidos, um carrinho com contagem) ou quando a navegação é frequente.

Há um custo do outro lado: um layout montado para sempre também guarda estado para sempre. Se ele mostra a hora do último pedido, essa hora envelhece enquanto o cliente navega. É por isso que a regra do "o que sobrevive" precisa ser pensada de propósito, e não por acidente.

8. Onde ficam as rotas

Com o layout separado, cada peça tem um lugar claro. As rotas ficam em um mapa ou uma lista, em um arquivo só; o componente que guarda o caminho escolhe a página; o layout desenha a moldura; a página desenha o conteúdo. Essa divisão é o que permite trocar o roteador de brinquedo por uma biblioteca sem reescrever a moldura.

Peça do siteOnde moraPor quê
topo, menu, rodapélayout do siteiguais em todas as rotas; não podem remontar

mapa de caminhosum arquivo de rotasquem escolhe a página não é o layout
estado do formulárioa páginanão deve sobreviver à navegação

Em uma biblioteca de rotas, essa tabela continua valendo, com outros nomes: o layout vira uma rota pai com <Outlet />, o mapa vira a lista de <Route>, e o layout aninhado vira uma rota filha com o seu próprio <Outlet />. A pergunta "quem é o pai de quem" é a mesma que você respondeu nas caixas. E quando o caminho não casa com nenhuma rota, quem responde é a página de 404, que fica fora da moldura ou dentro dela, conforme o desenho do site.

9. Cenários do dia a dia

Cenário 1: o menu lateral fecha a cada navegação

O menu mobile guarda aberto/fechado em um estado dentro de cada página. Ao navegar, o menu remonta fechado — e o cliente que estava navegando pelo menu tem de abrir de novo. Movendo o estado (ou o próprio menu) para o layout, ele continua aberto enquanto o cliente navega; fechar passa a ser uma ação dele, não um efeito colateral da navegação.

Cenário 2: a página nova abre no meio do texto

Sem recarregar, o navegador não zera a rolagem: você clica no rodapé, muda de rota e a página nova aparece rolada para baixo. Com o layout fixo o problema fica mais visível, porque só o conteúdo troca. A saída é um efeito que rola para o topo quando o caminho muda — o layout é justamente o lugar onde esse efeito mora bem.

Cenário 3: duas buscas iguais a cada clique

O layout busca o perfil do cliente e a página busca os pedidos; ao navegar, o layout remonta e busca o perfil de novo, mesmo que nada tenha mudado. Se o perfil é da moldura, ele fica no layout e é buscado uma vez; se é da página, sai do layout. Duas buscas iguais na aba Network é o sintoma clássico de dado no lugar errado.

11. Resumo

Layout é o componente que desenha o que é comum a várias rotas: topo, menu, rodapé. Ele fica acima da troca de páginas e recebe o conteúdo por children, então não precisa conhecer nenhum caminho. Assim o que é moldura não remonta quando o cliente navega — e o estado que precisa sobreviver (a busca do topo, o menu aberto) sobrevive de verdade.

Dentro de uma seção com páginas próprias, o mesmo padrão se repete: um layout da seção, com a sub-navegação, envolvendo a sub-página. Cada nível cuida do seu pedaço, e o mapa de rotas fica em um lugar só — quem escolhe a página é quem guarda o caminho, nunca o layout.

Evite guardar no layout o estado da página, buscar no layout os dados da página e, principalmente, colocar key={caminho} na moldura. O ganho de desempenho existe, mas o motivo principal é outro: com a moldura separada, cada peça do site tem um dono claro, e o cliente não perde o que estava fazendo só porque clicou em outro link.

Para lembrar

  • Layout desenha a moldura; a página chega por children.
  • Componente que sai da tela perde o estado: suba o estado que deve sobreviver.
  • Remontar é caro; renderizar de novo é normal.
  • O layout não conhece rotas: quem escolhe a página é quem guarda o caminho.
  • Layout aninhado: a seção tem o seu próprio children e a sua sub-navegação.
  • Estado da página não mora no layout.
  • key={caminho} no layout remonta a moldura a cada navegação.
  • Dados da moldura na moldura; dados da página na página.
  • Com a moldura fixa, a rolagem não zera sozinha: um efeito resolve.
  • Em bibliotecas de rotas, o layout vira rota pai com <Outlet />.
