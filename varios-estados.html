Vários Estados

O pedido da Ana cresceu. Era só o nome do cliente; agora ela precisa do telefone, da quantidade de pães e do horário de retirada — quatro informações que mudam em momentos diferentes. Com um useState só, o segundo campo apaga o primeiro: ela digita o telefone e o nome do cliente vira número. Nesta aula a Ana aprende a ter vários estados no mesmo componente, cada um cuidando da sua pergunta.

Você vai aprender
  • Quantos useState um componente pode ter — e como decidir.
  • Como declarar, ler e atualizar vários estados no mesmo componente.
  • Por que alguns estados deveriam ser um só.
  • Como guardar números, textos e booleanos, cada um no seu estado.
  • Por que um campo numérico entrega texto, e como converter.
  • O critério para separar estados ou juntar tudo num objeto.

1. A cena: o pedido que cresceu

Na aula de entrada controlada, a Ana resolveu o nome do cliente com um estado e um campo amarrado a ele. Funcionou tão bem que ela quis o resto do pedido na mesma tela: o telefone para avisar quando o pão sair, a quantidade de pães e o horário de retirada.

O jeito mais rápido de acrescentar um campo é copiar o que já funciona. Ela copiou o input e mudou só o rótulo. O resultado foi o desastre silencioso: ao digitar o telefone, o nome do cliente desapareceu. Os dois campos estavam ligados ao mesmo estado — a cópia levou junto o value={nome} e o onChange que escreve em nome. Um estado, dois campos, um valor só.

A tentação seguinte é criar um estado para o texto e outro para "tudo o mais", ou guardar os quatro dados numa frase separada por barras. As duas ideias dão trabalho depois: mostrar cada dado exige desmontar a frase, e atualizar um campo mexe no texto inteiro. O React tem uma resposta mais simples: um estado para cada dado que muda por conta própria. Quatro informações independentes, quatro estados.

Isso não é gambiarra nem desperdício. Um componente com cinco ou seis useState é comum e saudável — cada linha responde a uma pergunta clara, e qualquer pessoa que abrir o arquivo entende o que aquele componente guarda. O que não pode é um estado fazer o papel de dois.

2. Um estado por pergunta

Cada chamada de useState cria um par: um valor e uma função para trocá-lo. Várias chamadas criam vários pares, e eles são independentes: mudar um não mexe no outro. A leitura no JSX é direta, pelo nome de cada variável.

function App() {
  const [nome, setNome] = useState("");
  const [telefone, setTelefone] = useState("");
  const [quantidade, setQuantidade] = useState(1);
  const [retirada, setRetirada] = useState("18:00");

  return (
    <div>
      <p>Cliente: {nome || "ninguém"}</p>
      <p>Telefone: {telefone || "sem contato"}</p>
      <p>{quantidade} pão(ões) às {retirada}</p>
      <button onClick={() => setQuantidade(quantidade + 1)}>Mais um</button>
    </div>
  );
}

Repare que o componente guarda quatro valores, mas continua sendo uma função só. O React chama essa função a cada mudança de estado e, entre uma chamada e outra, guarda os quatro valores em algum lugar dele. Para você, é como se fossem quatro caixinhas com etiqueta — e a chave de cada caixinha é o setter que veio junto com ela.

3. Acrescentar um estado é barato

Quando a tela ganha um dado novo, o trabalho é sempre o mesmo, em três passos: criar o estado, dar o value ao campo e escrever o onChange que guarda o que foi digitado. O tropeço da Ana foi fazer o passo 1 e esquecer de trocar o par no passo 2 e 3.

Os dois campos mostram o mesmo texto, porque dividem o mesmo estado. Dê ao telefone um estado próprio. A missão digita Ana no nome e 11 99999-0000 no telefone, e confere que cada campo ficou com o seu valor.

Vale ler a solução procurando os três pares: nome/setNome, telefone/setTelefone. O primeiro campo usa o primeiro par, o segundo campo usa o segundo. Se você trocar o par de um campo, os dois passam a compartilhar o mesmo valor — exatamente o que a Ana fez sem perceber.

Depois desse passo, o resumo "Contato" continua lendo só o nome. Tudo bem: cada estado é lido onde for útil, e não precisa ser lido em todos os lugares. O que não pode é dois campos escreverem no mesmo estado.

4. Nomes que não mentem

Com um estado só, o nome da variável era quase decorativo. Com quatro, ele vira documentação. A convenção do React é [coisa, setCoisa]: o valor no singular e a função com o prefixo set. Nada obriga, mas seguir isso faz o código ser lido em voz alta sem tropeço.

nome / setNome
Texto digitado pelo cliente. O par mais comum de todos.
quantidade / setQuantidade
Um número. O nome diz o tipo e o significado ao mesmo tempo.
pago / setPago
Um booleano (true ou false). O nome parece uma pergunta de sim ou não, e isso é bom: if (pago) lê como uma frase.
pedidos / setPedidos
Uma lista. No plural o valor, porque tem vários; no singular o setter, porque ele troca a lista inteira de uma vez.
carregando / setCarregando
Outro booleano, o mais comum das telas que buscam dados. A aula de carregando e erro usa este par.

Os nomes a evitar são os genéricos: valor, dados, info, aux. Eles funcionam hoje e atrapalham amanhã, quando o componente tiver três "valores" diferentes e você precisar lembrar qual é qual. Um nome bom responde "que pergunta este estado responde?".

Outro hábito que economiza tempo: mantenha as declarações de estado juntas, no topo do componente, antes de qualquer cálculo. Assim dá para ver de longe o que o componente guarda, e a regra do useState — hooks no topo, sempre na mesma ordem — é obedecida sem esforço.

5. Um estado de cada tipo

Texto, número e booleano convivem no mesmo componente. A diferença aparece na hora de atualizar: o valor que sai de um campo de formulário é sempre texto, mesmo quando o campo é declarado como numérico. Se o estado deve guardar um número, a conversão é sua.

Digite 3 no campo: o total deveria ser 4, mas aparece 31. O estado está guardando o texto "3" e somando texto com número. Converta o valor antes de guardar.

function App() {
  const [quantidade, setQuantidade] = useState(1);

  return (
    <div>
      <label htmlFor="qtd">Pães</label>
      <input
        id="qtd"
        type="number"
        value={quantidade}
        onChange={(e) => setQuantidade(e.target.value)}
      />
      <p>Com mais um: {quantidade + 1}</p>
    </div>
  );
}
<div>

O sinal do problema é o total "31": o JavaScript viu uma string, então colou o número 1 no fim do texto, em vez de somar. Number("3") vira 3 de verdade, e a soma passa a dar 4. Esse tipo de bug é traiçoeiro porque funciona com alguns valores e falha com outros — com 1 e 2 a concatenação parece soma até alguém digitar 10.

O campo vazio merece aviso: Number("") é 0, não é "nada". Se o cliente apagar o conteúdo, a quantidade salta para zero silenciosamente. Quando zero não for uma resposta aceitável, guarde o texto e converta só na hora de mostrar, ou trate o caso vazio explicitamente.

6. Dois booleanos que se contradizem

Com vários estados, aparece um problema que nenhum deles tem sozinho: dois estados que podem dizer coisas incompatíveis. A tela de encomendas da Ana precisa mostrar quatro situações — buscando, lista vazia, erro e lista pronta — e ela começou com dois booleanos: carregando e erro.

Enquanto o código é novo, tudo funciona. Depois de duas semanas, uma função esqueceu de desligar carregando quando deu erro, e a tela passou a mostrar o "Buscando…" e a mensagem de falha ao mesmo tempo. Dois estados independentes sempre podem formar combinações que você não planejou — e o JSX tem de decidir o que fazer com cada uma.

carregandoerroQue tela é essa?
truefalsebuscando — a única combinação boa com carregando
falsetruedeu erro
falsefalselista pronta (vazia ou com itens)
truetrueimpossível — e é justamente a que apareceu na tela

A saída é trocar os dois booleanos por um estado só, que guarda a situação atual como texto: useState("inicial") e os valores "inicial", "buscando", "pronto" e "erro". Um estado não consegue valer duas coisas ao mesmo tempo, e o JSX escolhe o que desenhar com um if ou um objeto de mensagens.

O console da caixa mostra o problema sem disfarce quando os dois são independentes:

console: carregando=true erro=true
console: a tela mostra "Buscando..." e "Não foi possível carregar" juntos

O critério geral: dois estados só valem a pena quando as combinações fazem sentido. Nome e telefone podem ser preenchidos em qualquer ordem, então são dois. Já "buscando" e "com erro" são etapas de um mesmo caminho — só uma pode estar valendo —, então são um. Quando você se pegar escrevendo uma condição do tipo if (carregando && !erro), é sinal de que dois estados deveriam ser um.

7. Estados independentes de verdade

Um estado só muda quando o setter dele é chamado. Nenhum outro setter mexe nele, nenhum outro render o apaga. Isso parece óbvio e é a razão pela qual vários estados funcionam tão bem — e também a razão pela qual um set a mais, copiado por engano, estraga a tela.

O botão "Mais um pão" deveria só aumentar a quantidade, mas ele apaga o horário de retirada. Tire a linha que limpa o horário. A missão digita 18:00, clica no botão e confere que o horário continua lá.

function App() {
  const [nome, setNome] = useState("Ana");
  const [quantidade, setQuantidade] = useState(2);
  const [retirada, setRetirada] = useState("18:00");

  return (
    <div>
      <input id="nome" value={nome} onChange={(e) => setNome(e.target.value)} />
      <input id="hora" value={retirada} onChange={(e) => setRetirada(e.target.value)} />
      <button onClick={() => { setQuantidade(quantidade + 1); setRetirada(""); }}>
        Mais um pão
      </button>
      <p>{quantidade} pães</p>
      <p>Retirada às {retirada}</p>
    </div>
  );
}

Três estados, um botão que mexe em um deles. O nome e o horário continuam onde estavam porque ninguém chamou os setters deles. Esse é o comportamento normal: cada caixinha só se abre com a sua chave.

Note também que a função do onClick pode chamar mais de um setter — o código inicial chama dois de propósito. Isso é permitido e às vezes necessário. Só cuidado com a ordem e com o fato de que o valor novo não aparece na variável antiga dentro do mesmo handler; esse é o assunto da aula de atualizações em lote.

Para conferir o retrato completo do componente, um console.log com os três valores logo antes do return mostra o que a tela vai desenhar:

nome: Ana
quantidade: 3
retirada: 18:00

Três linhas por render. Se você clicar no botão e aparecer um bloco de três linhas com quantidade: 3, o estado mudou e o componente foi redesenhado. É o jeito mais simples de acompanhar vários estados ao mesmo tempo.

8. Quando os dados andam juntos

Vários estados é o padrão. Mas existe um caso em que eles atrapalham: quando dois ou três valores sempre mudam na mesma hora, são salvos juntos e lidos juntos. Aí eles não são perguntas separadas — são um dado só, com partes.

O exemplo clássico é o endereço. Rua, número, bairro e CEP nunca mudam separadamente: quando o cliente muda de endereço, muda tudo. Guardar quatro estados e quatro setters obriga você a lembrar de atualizar os quatro em cada lugar que mexe no endereço; esquecer um produz um endereço meio novo, meio velho. Um objeto só mantém as partes juntas por construção.

O critério, então, é uma pergunta: estes valores podem mudar separadamente? Se sim — nome do cliente e quantidade de pães —, um estado para cada. Se não — rua, número, bairro e CEP de um endereço —, um estado só, com um objeto dentro. E o formato mais comum de um pedido é misto: dados do cliente num objeto, lista de itens num array, e um booleano solto dizendo se a compra foi paga.

O objeto traz uma complicação na hora de atualizar: não basta trocar um campo, é preciso entregar ao setter um objeto novo, com o campo alterado e os outros copiados. Essa mecânica é a aula seguinte, e ela tem uma pegadinha famosa — a mutação que não redesenha a tela. Guarde o critério, que é o que importa aqui.

9. Cenários do dia a dia

Cenário 1: o valor que aparece e nunca muda

A Ana trocou o useState por uma variável comum, let nome = "", e usou value={nome}. A tela apareceu com o campo vazio e assim ficou: digitar não mudava nada, porque ninguém avisava o React de que algo mudou. Variável comum é recriada a cada render; estado sobrevive entre um render e outro. Se a tela precisa mudar, o dado precisa estar num estado.

Cenário 2: a tela que mostrava "buscando" e erro juntos

A Ana tinha carregando e erro como dois estados e atualizava os dois em lugares diferentes. Numa resposta lenta, a tela exibiu o indicador e a mensagem de falha ao mesmo tempo. Trocar os dois por um situacao de texto resolveu de vez: cada valor desenha uma tela, e nenhuma combinação impossível existe.

Cenário 3: o campo vazio que virou zero

Com Number(e.target.value), apagar o campo de quantidade faz o estado virar 0 e o resumo anunciar "0 pães". A conversão está certa; o problema é que zero não é uma resposta aceitável para "quantos pães". A saída é guardar o texto no estado e converter só na hora de calcular, tratando o vazio: const n = quantidade === "" ? 1 : Number(quantidade).

11. Resumo

Um componente pode ter quantos estados precisar, e o critério é simples: um estado para cada dado que muda por conta própria. Nome do cliente, telefone, quantidade e horário são quatro perguntas independentes, logo quatro pares [valor, setValor]. Cada setter mexe apenas no seu estado, e um componente com cinco ou seis declarações no topo é normal.

Um estado não deve fazer o papel de dois, mas dois estados também não devem contar a mesma história. Quando as combinações possíveis se contradizem — "buscando" e "com erro" ao mesmo tempo —, o certo é um estado só, com a situação atual em texto. O critério é sempre o mesmo: cada estado tem a sua pergunta, e as respostas de todas precisam poder conviver.

Tipos diferentes pedem cuidados diferentes: texto vem pronto do e.target.value, número precisa de Number(...) porque o campo entrega string, booleano se alterna com setPago(!pago). E quando dois ou três valores sempre mudam juntos, o caminho deixa de ser "mais um estado" e passa a ser um estado só com um objeto dentro — que é exatamente o que a próxima aula mostra em detalhe.

Para lembrar

  • Um estado por dado independente; não há limite de quantidade.
  • Cada par é [coisa, setCoisa] e vive no topo do componente.
  • Um setter só mexe no seu próprio estado.
  • Copiar um campo sem trocar o par faz dois campos dividirem um valor.
  • Dois estados só valem quando as combinações entre eles fazem sentido.
  • Flags que se excluem (buscando, com erro) viram um estado de situação.
  • Campo de formulário entrega string; para número, Number(e.target.value).
  • Number("") é 0: trate o campo vazio se zero não fizer sentido.
  • Booleano se alterna com setPago(!pago).
  • Se os valores sempre mudam juntos, use um objeto — a próxima aula.
