O useState

Até agora a página da Ana só muda quando alguém muda o código. Ela quer clicar em "Fechar a loja" e ver a placa virar, sem recarregar nada. O que falta é memória: um lugar onde o componente guarde um valor entre um desenho e o outro e avise o React quando esse valor muda. Esse lugar tem nome — estado — e a porta de entrada é uma função chamada useState.

Você vai aprender

  • O que useState devolve: o par [valor, setValor].
  • Para que serve o valor inicial e quando ele é usado.
  • O que acontece entre chamar o setter e a tela mudar.
  • Por que o estado sobrevive de um desenho para o outro.
  • As regras de onde o hook pode ser chamado — e o que acontece quando você erra.

1. A cena: a placa que não vira

A placa da porta da padaria tem dois estados: aberto e fechado. No site, ela é um parágrafo com o texto "Aberto agora". A Ana quer um botão que vire a placa quando ela clicar. O botão existe, a função existe, o texto está lá — e nada acontece.

Ela já sabe por quê. Na aula de renderização condicional, o texto na tela era consequência do valor de uma variável: mudou a variável, mudou o JSX. Só que o JSX é montado uma vez, quando o React chama a função. Se nada mandar o React chamar a função de novo, a tela continua com o desenho antigo, mesmo que a variável tenha mudado no meio do caminho.

O estado resolve exatamente esse buraco. Ele é uma caixinha que o React guarda para o componente, fora da função, e que sobrevive a cada chamada. Quando você pede para mudar o que está na caixinha, o React anota: "esse componente precisa ser desenhado de novo". Desenhar de novo é chamar a função outra vez, com o valor novo já dentro. É esse ciclo — mudar, avisar, desenhar — que faz a tela reagir.

2. Por que uma variável comum não resolve

Vamos ver o tropeço com o código na frente. A função virar muda a variável e escreve no console, então dá para provar que o valor mudou. Mesmo assim, a placa continua dizendo "Aberto":

O botão muda a variável aberto, mas a placa não muda. Troque a variável por um estado com useState e faça o clique virar a placa para "Fechado".

function App() {
  let aberto = true;

  function virar() {
    aberto = !aberto;
    console.log("aberto agora é " + aberto);
  }

  return (
    <div>
      <h1>Padaria da Ana</h1>
      <p>Placa: {aberto ? "Aberto" : "Fechado"}</p>
      <button onClick={virar}>Virar a placa</button>
    </div>
  );
}
<div>
  <h1>Padaria da Ana</h1>
  <p>Placa: Aberto</p>
  <button>Virar a placa</button>
</div>

function App() {
  const [aberto, setAberto] = useState(true);

  function virar() {
    setAberto(!aberto);
    console.log("aberto agora é " + !aberto);
  }

  return (
    <div>
      <h1>Padaria da Ana</h1>
      <p>Placa: {aberto ? "Aberto" : "Fechado"}</p>
      <button onClick={virar}>Virar a placa</button>
    </div>
  );
}

Rode o código inicial, clique no botão e abra o console do navegador com F12 antes de olhar o HTML. É isto que aparece:

aberto agora é false

O valor mudou. O console provou. E a tela continuou igual, porque ninguém avisou o React de que havia algo novo para desenhar.

Uma explicação sobre onde essa linha aparece: o painel das caixas mostra o que o código escreveu durante o desenho do componente. O que é escrito dentro de um manipulador de clique sai depois do desenho, no console do navegador — por isso a linha acima é uma transcrição do DevTools, e não do painel.

E o valor mudou mesmo? Mudou, mas só dentro daquela execução. aberto é uma variável local: ela nasce do zero cada vez que a função roda, morre no fim e não tem contrato nenhum com a tela. Quem tem esse contrato é o estado.

Vale entender a diferença com precisão, porque ela é a base de tudo o que vem depois. Uma variável local guarda um valor durante uma execução da função. O estado guarda um valor durante todas as execuções, e a mudança dele agenda uma execução nova. Não é que a variável seja proibida — ela é ótima para o que não precisa aparecer na tela nem sobreviver ao desenho. Ela só não serve para o que muda e precisa ser visto.

Um caminho que parece resolver e não resolve é declarar a variável fora do componente. Aí ela sobrevive, é verdade, mas continua sem avisar o React — e ganha dois problemas novos: passa a ser compartilhada por todas as instâncias do componente e por todas as pessoas que usarem a página, e volta ao valor original quando a página recarrega. Estado não é só "um lugar para guardar": é um lugar que o React conhece, acompanha e redesenha. Guardar do lado de fora é esconder o valor do único interessado em vê-lo mudar.

3. O que o useState devolve

useState é um hook: uma função especial do React que você chama no topo do componente. Ela recebe o valor inicial e devolve um array de duas posições. A primeira é o valor de agora; a segunda é uma função que troca esse valor e pede um novo desenho. A escrita normal usa desestruturação de array:

const [aberto, setAberto] = useState(true);
estado
Um valor que o React guarda para o componente entre um desenho e outro, e que dispara um novo desenho quando muda.
hook
Uma função do React que só pode ser chamada no topo do componente: useState, useEffect e as outras que você vai ver.
setter
A segunda posição do par: a função que troca o valor e agenda o desenho. setAberto, setPedidos.
valor inicial
O argumento do useState, usado só no primeiro desenho: useState(true), useState("Pão francês"), useState(0).
desenho
Cada execução da função do componente. Mudou o estado, o React desenha de novo.

O nome das duas variáveis é escolha sua, mas a convenção do React é forte e ajuda muito: aberto e setAberto, pedidos e setPedidos, nome e setNome. Quem lê o código sabe na hora o que é valor e o que é setter, sem procurar a declaração. Fuja de nomes como valor e mudaValor repetidos em três componentes diferentes.

4. O valor inicial

O argumento do useState é o valor do primeiro desenho. Ele é usado uma vez, quando o componente aparece pela primeira vez, e depois é ignorado — o estado passa a valer por si. Isso explica um comportamento que confunde: mudar o argumento no código e salvar não muda um componente que já está na tela; ele já tem o valor dele.

O tipo do valor inicial define o tipo do estado. useState(0) guarda número; useState("Pão francês") guarda texto; useState(true) guarda booleano; useState([]) guarda lista; useState({ nome: "Ana" }) guarda objeto. E o estado não converte tipo sozinho: se você começar com 0 e chamar setPedidos("2"), passa a valer a string "2", e aí pedidos + 1 vira "21". É o tipo de bug que aparece longe, no cálculo.

O estado pao já nasce com "Pão francês", mas o botão não troca nada. Chame setPao com o texto "Broa" dentro do manipulador do clique.

function App() {
  const [pao, setPao] = useState("Pão francês");

  function trocar() {
    console.log("trocando o pão do dia");
  }

  return (
    <div>
      <h1>Padaria da Ana</h1>
      <p>Pão do dia: {pao}</p>
      <button onClick={trocar}>Trocar para broa</button>
    </div>
  );
}
<div>

function App() {

No painel, o primeiro desenho mostra "Pão do dia: Pão francês". Depois do clique, mostra "Broa". O setter recebeu o valor novo direto — não é uma soma, é uma substituição. Essa é a forma mais simples de atualizar estado e a que você vai usar na maior parte do tempo: setPao("Broa"), setAberto(false), setNome("Ana").

Quando o valor novo depende do anterior — somar um, alternar um booleano, acrescentar num array —, a conversa muda um pouco. Dá para fazer com o valor atual (setAberto(!aberto), como no exemplo acima), e funciona para um clique por vez. Na aula de atualizar o estado você vai ver o caso em que isso falha e a forma de função que resolve. Por enquanto, guarde a regra: o setter recebe o valor novo, não um pedaço dele.

5. O que acontece entre o clique e a tela

Vale acompanhar o caminho inteiro, porque ele explica quase todos os comportamentos estranhos do React. O leitor clica. O navegador dispara o evento. A função virar roda e chama setAberto(false). O React guarda o valor novo e marca aquele componente como "precisa desenhar". Terminado o evento, ele chama a função do componente outra vez, agora com aberto valendo false, e compara o JSX novo com o anterior. Só a parte que mudou é tocada no navegador.

Duas consequências práticas. A primeira: a função do componente roda inteira a cada mudança de estado, não só o pedacinho que mudou. Qualquer console.log no corpo dela aparece a cada clique — e é por isso que logar dentro do componente é um jeito tão bom de descobrir quantos desenhos aconteceram. A segunda: o valor novo não chega para a linha seguinte do mesmo evento. Dentro de virar, aberto continua sendo o valor antigo até o próximo desenho. Guarde isso; é a origem de metade dos bugs de estado.

function virar() {
  setAberto(!aberto);       // pede o novo desenho
  console.log(aberto);      // ainda imprime o valor antigo
}

Esse detalhe explica uma pergunta que todo mundo faz na primeira semana: "por que meu console.log mostra o valor antigo se eu acabei de atualizar?". Porque o valor que a função enxerga é o do desenho em que ela foi criada — e o desenho em que ela foi criada é o de antes do clique. Na aula de atualizar o estado, essa mesma característica vai aparecer como aliada, quando o assunto for somar várias vezes de uma vez só.

Se você precisa do valor novo na mesma função, calcule numa variável e use a variável: const novo = !aberto;, depois setAberto(novo) e console.log(novo). Simples e sem surpresa.

6. O estado é memória — e ela é do componente

O teste definitivo de que o estado guarda memória é clicar duas vezes. Uma variável local voltaria a zero em cada desenho; o estado continua de onde parou. O exemplo abaixo é o contador de pedidos da Ana, e ele começa com uma variável comum:

O botão soma na variável, mas o painel continua em "Pedidos: 0". Troque a variável por useState(0) e clique duas vezes: o painel precisa chegar a Pedidos: 2.

function App() {
  let pedidos = 0;

  function pedir() {
    pedidos = pedidos + 1;
    console.log("pedidos agora: " + pedidos);
  }

  return (
    <div>
      <h1>Padaria da Ana</h1>
      <p>Pedidos: {pedidos}</p>
      <button onClick={pedir}>Pedir pão</button>
    </div>
  );
}
<div>
  <h1>Padaria da Ana</h1>
  <p>Pedidos: 0</p>
  <button>Pedir pão</button>
</div>

function App() {
  const [pedidos, setPedidos] = useState(0);

  function pedir() {
    setPedidos(pedidos + 1);
  }

  return (
    <div>
      <h1>Padaria da Ana</h1>
      <p>Pedidos: {pedidos}</p>
      <button onClick={pedir}>Pedir pão</button>
    </div>
  );
}

No código inicial, dois cliques escrevem duas linhas no console do navegador — e é interessante ver que o número cresce lá enquanto a tela fica parada em zero:

pedidos agora: 1
pedidos agora: 2

A variável viveu durante o evento e morreu. No código com estado, o valor 2 está guardado fora da função, e por isso o terceiro desenho nasce com ele. Essa memória é o que permite construir carrinho, formulário, contador, aba aberta, filtro — tudo o que precisa lembrar de uma interação para a próxima.

Uma sutileza que cedo ou tarde aparece: a memória é de cada componente, não do programa. Dois <Contador /> na mesma tela têm estados separados, cada um com o seu zero. E quando o componente sai da tela e volta — porque uma condição deixou de desenhá-lo —, o estado dele é descartado e recomeça do valor inicial. Estado não é banco de dados; é memória de curto prazo enquanto o componente está montado.

7. As regras do hook

useState tem duas regras duras, e as duas existem pelo mesmo motivo: o React identifica cada estado pela ordem das chamadas, não pelo nome da variável. No primeiro desenho ele anota "primeira chamada é o estado A, segunda é o B". Nos desenhos seguintes, ele entrega os valores nessa mesma ordem. Se a ordem mudar, os valores trocam de lugar.

Por isso: chame o hook sempre no topo do componente, antes de qualquer return, e nunca dentro de um if, de um laço ou de uma função aninhada. Dentro de um manipulador de evento, então, nem pensar: o manipulador roda no clique, muito depois do desenho, e o hook precisa rodar sempre, na mesma ordem, em todo desenho.

function App({ logado }) {
  if (logado) {
    const [nome, setNome] = useState("Ana");   // ERRADO: hook dentro de if
  }

  function alternar() {
    const [aberto, setAberto] = useState(false);   // ERRADO: hook dentro de função
  }
}

O certo é declarar tudo no topo e usar as condições no JSX, como você já faz:

function App({ logado }) {
  const [nome, setNome] = useState("Ana");
  const [aberto, setAberto] = useState(false);

  return (
    <div>
      {logado && <p>Olá, {nome}</p>}
      <p>Placa: {aberto ? "Aberto" : "Fechado"}</p>
    </div>
  );
}

Você não precisa decorar a mensagem de erro, mas vale reconhecer o sintoma: quando a ordem dos hooks muda entre desenhos, o React reclama de "ordem dos hooks" e a tela pode quebrar. Se um componente seu começar a se comportar de forma absurda depois de uma condição nova, procure um hook que entrou para dentro de um if.

8. Quando usar estado (e quando não)

Estado é para o que muda com o tempo e precisa aparecer na tela: a placa aberta ou fechada, a lista de pedidos, o texto digitado, a aba selecionada. Se o valor não muda, é constante — e constante não precisa de estado. Se o valor pode ser calculado a partir de outro estado ou das props, também não precisa: calcule na hora.

function Venda({ precoUnitario }) {
  const [quantidade, setQuantidade] = useState(1);

  const total = quantidade * precoUnitario;   // calculado, não é estado

  return (
    <div>
      <p>Quantidade: {quantidade}</p>
      <p>Total: {total.toFixed(2)}</p>
      <button onClick={() => setQuantidade(quantidade + 1)}>+</button>
    </div>
  );
}

Guardar o total num estado seria pior: você teria dois valores para manter sincronizados, e no dia em que um mudasse sem o outro, a tela mostraria uma conta errada. Essa ideia — estado só para a fonte da verdade, o resto é cálculo — tem uma aula só dela mais adiante. Por ora, a pergunta "isso pode ser calculado a partir do que eu já tenho?" resolve a maioria dos casos.

9. Cenários do dia a dia

Cenário 1: o botão que parece não fazer nada

A Ana escreveu setAberto(aberto) em vez de setAberto(!aberto). O React recebeu o mesmo valor e, como o estado não mudou, não redesenhou: a tela ficou igual e o clique pareceu morto. Não é bug do React — é economia. Ele só redesenha quando o valor muda de verdade, e comparar booleano, número e texto é fácil.

Cenário 2: dois contadores que se mexem juntos

Ela colocou um único estado no App e passou o mesmo valor para dois contadores na tela. Clicar em um mexia nos dois, porque havia um estado só. Estado pertence ao componente onde foi declarado; para ter dois independentes, cada componente declara o seu. Essa diferença vai ficar clara na aula do contador, quando o mesmo componente aparecer duas vezes.

Cenário 3: o estado que volta a zero

Ela clicou três vezes, foi para outra aba do site e voltou: o contador estava em zero. O componente tinha sido desmontado ao sair da tela, e o estado foi junto. Isso é o esperado. Quando o valor precisa sobreviver à navegação ou ao recarregamento, o lugar é outro — o localStorage, mais adiante no guia, ou o servidor.

11. Resumo

Estado é a memória do componente: um valor que sobrevive entre um desenho e outro e que, quando muda, pede um desenho novo. useState cria essa memória e devolve um par — o valor de agora e o setter. O argumento é o valor do primeiro desenho e só é usado nele. O setter recebe o valor novo, e a partir daí a função do componente roda outra vez com o valor atualizado.

Variável comum não substitui estado por dois motivos: ela não avisa o React e ela não sobrevive ao fim da função. O console mostrando o valor novo enquanto a tela permanece velha é a assinatura desse problema — e uma boa forma de lembrar que "mudar o dado" e "mudar a tela" são dois passos, não um.

As regras são curtas: hook no topo, sempre na mesma ordem, nunca dentro de condição, laço ou manipulador. E estado só para o que muda e aparece; o que pode ser calculado, calcule. Com isso, o próximo passo é natural: usar o estado para construir um contador de verdade — com mais, menos, zerar e um componente que pode aparecer várias vezes na tela, cada um com a sua própria memória.

Para lembrar

  • const [valor, setValor] = useState(inicial); — par de valor e setter.
  • O valor inicial vale só no primeiro desenho; depois o estado manda.
  • Variável local não redesenha a tela e não sobrevive ao fim da função.
  • Chamar o setter agenda um novo desenho; a tela muda depois, não na linha seguinte.
  • Dentro do mesmo evento, o valor lido ainda é o antigo.
  • O setter substitui o valor; para somar, passe o resultado da conta.
  • useState só no topo do componente, nunca dentro de if ou laço.
  • Estado é por componente: duas instâncias, duas memórias.
  • Componente desmontado perde o estado; ele não é banco de dados.
  • O que dá para calcular não vira estado.
