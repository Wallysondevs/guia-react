Abortar um Pedido

A cliente pediu dois pães, o atendente foi ao forno e ela desistiu: virou as costas e saiu. Na padaria isso é natural — ninguém continua assando o pão para quem já foi embora. Na web também: quando o leitor troca de tela, cancela a busca ou fica impaciente, o pedido que ele fez não interessa mais. Nesta aula a Ana aprende a avisar o navegador que o pedido foi abandonado, com o AbortController — e a lidar com o erro que aparece quando isso acontece, sem mostrar "deu errado" para quem simplesmente mudou de ideia.

Você vai aprender
  • O que são o AbortController, o signal e o abort().
  • Como um botão Cancelar interrompe um pedido em andamento.
  • O erro de cancelamento: AbortError e signal.reason.
  • Como definir o motivo do cancelamento em vez de mostrar a mensagem técnica.
  • Tempo limite: AbortSignal.timeout e o TimeoutError.
  • Quando cancelar e quando não vale a pena.

1. A cena: o pedido que ninguém vai buscar

O cardápio da Ana tem uma busca: a pessoa digita "queijo" e o site pede ao servidor a lista de pães que combinam. Se ela digitar mais uma letra antes da resposta chegar, o pedido anterior está perdido — a resposta que vier não interessa mais. Mas ele continua viajando: o servidor procura, monta a lista, manda de volta. O navegador recebe, o código do site processa e, se ninguém tomou cuidado, sobrescreve a tela com resultado velho.

Existe uma forma de parar isso no meio do caminho, e ela é do navegador, não do React: o AbortController. Ele é um controle remoto com um botão só. Você entrega ao fetch um cartão que esse controle assinou; quando aperta o botão, todo pedido que estiver segurando aquele cartão é interrompido na hora, com a conexão fechada.

São três objetos que aparecem sempre juntos. O controle, que é quem manda cancelar. O sinal, que é o cartão entregue ao pedido. E o pedido, que avisa o controle quando é interrompido. Guarde os nomes: controle, signal, abort.

2. As três linhas do cancelamento

Não há mistério na montagem. Cria-se o controle, passa-se o sinal nas opções do fetch e, quando for preciso, chama-se o abort. É a mesma ordem em qualquer lugar do código.

const controle = new AbortController();

fetch("https://loja.test/api/paes", { signal: controle.signal })
  .then((resposta) => resposta.json())
  .then((lista) => setPaes(lista));

// quando quiser cancelar:
controle.abort();

Repare que o signal vai dentro do objeto de opções, junto com method ou headers quando existirem. Não é um argumento separado. E repare também que o abort() não devolve nada: ele apenas avisa a todos os pedidos que estão usando aquele sinal. Se não houver nenhum, nada acontece — e não é erro.

AbortController
O controle remoto. Cada pedido que você quer poder cancelar precisa de um controle só dele.
signal
O cartão do controle, entregue ao fetch nas opções. É por ele que o pedido sabe que foi cancelado.
abort()
O botão. Fecha a conexão e rejeita a promessa do pedido com um erro de cancelamento.
AbortError
O nome do erro que aparece no catch quando o pedido é interrompido.
signal.aborted
Verdadeiro depois do abort(). Serve para perguntar "já cancelou?" sem esperar o erro.
signal.reason
O motivo do cancelamento. Por padrão, um objeto técnico em inglês; você pode definir o seu.

3. O botão que cancela de verdade

A primeira tentativa da Ana foi mudar o estado do componente quando o botão fosse clicado. A tela dizia "Cancelar" e, ao clicar, ela via o texto voltar para carregando — mas o pedido continuava vivo, e quando a resposta chegava o componente desenhava a lista como se nada tivesse acontecido. Mudar estado não cancela nada: quem cancela é o abort().

O controle está guardado em controle.current e o pedido está esperando. Faça o botão cancelar de verdade: chame controle.current.abort() na função cancelar.

function buscar(sinal) {
  return new Promise((ok, falha) => {
    const id = setTimeout(() => ok(["Pão francês", "Croissant"]), 400);
    sinal.addEventListener("abort", () => {
      clearTimeout(id);
      falha(sinal.reason);
    });
  });
}

function App() {
  const [lista, setLista] = useState([]);
  const [estado, setEstado] = useState("carregando");
  const controle = useRef(null);

  useEffect(() => {
    controle.current = new AbortController();
    buscar(controle.current.signal)
      .then((dados) => {
        setLista(dados);
        setEstado("pronto");
      })
      .catch((e) => {
        if (e.name === "AbortError") setEstado("cancelado");
      });
    return () => controle.current.abort();
  }, []);

  function cancelar() {
    setEstado("carregando");
  }

  return (
    <div>
      <h1>Padaria da Ana</h1>
      {estado === "carregando" && <p>Carregando...</p>}
      {estado === "cancelado" && <p>Pedido cancelado</p>}
      {estado === "pronto" && (
        <ul>
          {lista.map((p) => (
            <li key={p}>{p}</li>
          ))}
        </ul>
      )}
      <button onClick={cancelar}>Cancelar pedido</button>
    </div>
  );
}

Depois do clique, o pedido é interrompido, a promessa é rejeitada e o catch roda — com um erro cujo nome é AbortError. É por isso que o catch testa o nome antes de decidir o que fazer: cancelamento não é falha do sistema, é decisão do usuário. Se você tratar os dois igual, quem muda de ideia vê "erro de conexão".

E note o detalhe do useRef: o controle precisa sobreviver entre renders, porque a função do botão é recriada a cada render e precisa do mesmo controle que o efeito criou. Guardar em variável comum não funciona; guardar em estado também não, porque guardar o controle é guardar uma instância, não um dado para desenhar.

4. O que acontece de verdade quando o pedido é cancelado

O abort() não é um setState disfarçado. Ele fecha a conexão de rede. Se a resposta ainda não começou a chegar, o servidor pode até parar de preparar; se já começou, o navegador descarta o que vier. O ganho é de banda, de bateria e de trabalho no servidor — e, principalmente, de clareza: nenhum código seu vai receber dado que não pediu mais.

Do lado do JavaScript, o efeito é imediato: a promessa do fetch é rejeitada com uma DOMException cujo name é "AbortError". Ela cai no .catch (ou no catch do try) como qualquer outro erro. E o sinal passa a responder verdadeiro para aborted:

> const controle = new AbortController();
undefined
> controle.signal.aborted
false
> controle.abort()
undefined
> controle.signal.aborted
true
> controle.signal.reason
DOMException: The user aborted a request.

Essas cinco linhas explicam tudo o que dá errado com cancelamento. Antes do abort, o sinal está limpo. Depois, ele fica marcado para sempre: um controle abortado não volta atrás. Se você precisa disparar outro pedido cancelável, cria outro new AbortController() — não tenta reaproveitar o antigo.

Uma ressalva honesta, que vale antes de você confiar demais no cancelamento: ele interrompe a conversa, não o trabalho do servidor. Se o pedido já chegou ao outro lado e a rotina começou a rodar — gravar um pedido, debitar um cartão —, desistir do lado do navegador não desfaz nada disso. Por isso cancelar é seguro para leitura (buscar lista, buscar preço) e delicado para escrita: um POST cancelado no meio do caminho pode ter sido executado. A aula de POST volta a esse ponto.

Repare também na última linha: existe um motivo no sinal, e o motivo padrão é um objeto técnico com mensagem em inglês. É desse motivo que vem a mensagem que o seu catch recebe. Mostrar isso ao cliente é o mesmo que mostrar um erro de compilador.

5. O motivo do cancelamento

O abort() aceita um argumento: o motivo. O que você passar ali vira signal.reason e é o que o pedido recebe como erro. Isso permite separar dois cancelamentos que pareciam iguais — o usuário desistiu, o termo de busca mudou, a tela foi fechada — e mostrar a mensagem certa em cada caso.

Ao cancelar, a tela mostra o motivo padrão do navegador, em inglês. Passe um motivo seu: controle.current.abort(new DOMException("O cliente desistiu do pedido", "AbortError")).

O DOMException é o mesmo tipo de erro que o navegador usa, e por isso ele mantém o name igual a "AbortError" — importante, porque é esse nome que o código costuma testar. Você pode passar qualquer valor, inclusive uma string simples; nesse caso, o signal.reason é a string, e o seu catch precisa saber com o que está lidando.

Uma consequência prática que vale anotar: se você personaliza o motivo, não teste apenas e.name === "AbortError". A string que você passou não tem name. O teste mais confiável é controle.signal.aborted ou e.name === "AbortError" || typeof e === "string". Simples é passar sempre um DOMException com nome de AbortError, como na caixa.

6. Tempo limite: o servidor que não responde

Tem um caso em que ninguém aperta botão nenhum: o servidor simplesmente não responde. O fetch não tem tempo limite embutido — ele espera para sempre, e a tela fica em "Carregando" até o fim dos tempos. Para resolver isso sem criar um controle na mão, existe o AbortSignal.timeout: ele devolve um sinal que se cancela sozinho depois do tempo dado, em milissegundos.

O servidor nunca responde e a tela fica em "Carregando". Passe um sinal de tempo limite: buscarLento(AbortSignal.timeout(20)). O erro que chega tem name igual a "TimeoutError".

function buscarLento(sinal) {
  return new Promise((ok, falha) => {
    const id = setTimeout(() => ok(["Pão francês"]), 5000);
    if (sinal) {
      sinal.addEventListener("abort", () => {
        clearTimeout(id);
        falha(sinal.reason);
      });
    }
  });
}

function App() {
  const [estado, setEstado] = useState("Carregando...");

  useEffect(() => {
    buscarLento()
      .then(() => setEstado("Pão a caminho"))
      .catch((e) => setEstado(e.name === "TimeoutError" ? "Demorou demais" : "Deu erro"));
  }, []);

  return (
    <div>
      <h1>Pedido da Ana</h1>
      <p>{estado}</p>
    </div>
  );
}

Vinte milissegundos é um tempo absurdo de curto, escolhido só para a caixa responder rápido. No projeto de verdade, o valor fica entre três e dez segundos — o tempo que o seu usuário aceita esperar antes de preferir uma mensagem de erro. E o erro que chega não é AbortError: é TimeoutError, com nome próprio, justamente para você poder dizer "demorou demais" em vez de "cancelado".

Uncaught (in promise) DOMException: signal timed out

Essa mensagem aparece no console quando o sinal de tempo limite cancela e ninguém trata. Tratar é o que a caixa faz com o catch e a comparação de name. Se você quiser dois motivos de cancelamento no mesmo pedido — o botão do usuário e o tempo limite —, existe o AbortSignal.any([sinal1, sinal2]), que dispara quando qualquer um dos dois dispara.

7. Quando cancelar (e quando não vale a pena)

Cancelar tem custo de código, e não é sempre que compensa. A tabela abaixo é o resumo das situações em que o ganho é claro.

SituaçãoCancelar o quêComo
busca enquanto digitao pedido anterior, a cada letraabort() na limpeza do efeito
tela trocada ou fechadatodos os pedidos daquela telaabort() na limpeza
botão "desistir"o pedido em andamentoabort() no onClick
servidor lentoo pedido que passou do tempoAbortSignal.timeout(ms)
um pedido que já terminounadao abort() não tem efeito

A última linha é tranquilizadora: chamar abort() depois de a resposta ter chegado não quebra nada. O pedido já foi, o sinal só fica marcado. Do mesmo jeito, chamar abort() duas vezes seguidas é inofensivo — o segundo não faz nada. Isso permite escrever a limpeza sem medo: ela roda em toda troca, mesmo quando não há nada pendente.

O que chegou no catche.nameO que fazer

Uma armadilha que fecha a seção: cancelar não é o mesmo que ignorar. Se o código só ignora a resposta que chega (com uma variável de controle, como a aula de limpeza mostrou), o pedido continua viajando e o servidor continua trabalhando. O abort() é a única forma de parar o trabalho no meio. Os dois podem conviver — um economiza a rede, o outro protege o estado —, mas o abort() sozinho já resolve a maior parte dos casos.

8. Detalhes que economizam depuração

Primeiro: um controle, um pedido. Se você usar o mesmo AbortController para três pedidos e abortar, os três param juntos — o que às vezes é exatamente o que se quer (cancelar a tela inteira). Mas se cada pedido precisa da sua própria vida, cada um tem o seu controle.

Segundo: um controle abortado não é reutilizável. Depois do abort(), o sinal fica permanentemente marcado; um fetch novo com esse sinal falha imediatamente. Por isso o efeito cria um new AbortController() a cada execução, e não guarda um global.

Terceiro: o momento do abort() importa. Se ele acontece antes de o fetch começar, a promessa já nasce rejeitada, e o catch roda do mesmo jeito. Isso é útil em formulário que valida primeiro: se o campo está vazio, cancele antes de pedir.

Quarto: não confunda cancelar com desmontar. O React desmonta o componente quando a tela sai; a limpeza do efeito roda nessa hora e é o lugar natural do abort(). Mas o cancelamento também pode acontecer com a tela viva — no clique do botão, na troca do termo de busca. As duas coisas usam o mesmo mecanismo, e é isso que torna o AbortController tão útil.

Quinto, e o mais fácil de esquecer: depois de cancelar, alguém precisa arrumar a tela. O catch do AbortError é o único lugar que sabe que o pedido foi cancelado, então é ele que deve devolver o componente ao estado inicial — "nada buscado", lista vazia, botão habilitado. Se o catch só faz return, o "Carregando..." fica na tela para sempre e o leitor conclui que o site travou.

9. Cenários do dia a dia

Cenário 1: o botão que só mudava de cor

A Ana fez o botão Cancelar trocar o estado para "cancelado" e considerou o assunto resolvido. Três segundos depois, a lista aparecia na tela — o pedido nunca foi interrompido e o .then rodou depois, sobrescrevendo tudo. O conserto foi chamar controle.current.abort() e tratar o AbortError no catch. Estado não fecha conexão; só o abort() fecha.

Cenário 2: "erro de conexão" para quem só desistiu

O cancelamento funcionava, mas a tela mostrava uma tarja vermelha dizendo que a internet tinha caído sempre que alguém clicava em Desistir. O catch tratava todo erro igual. A correção foi olhar e.name antes de decidir: AbortError volta para o estado inicial em silêncio; o resto vira mensagem. Quem cancelou sabe o que fez — não precisa ser informado de um erro que não existe.

Cenário 3: o controle reaproveitado

Ela guardou o AbortController fora do efeito, para não criar um novo a cada busca. A primeira busca funcionou, o primeiro cancelamento também; da segunda em diante, todo pedido falhava na hora. O sinal estava marcado desde o primeiro abort(). A regra é simples: um controle por pedido, criado no mesmo lugar onde o pedido nasce.

const controle = new AbortController(); fetch("/api/paes", { : controle.signal });

Dica: é a propriedade do controle que carrega o aviso de cancelamento — a mesma que responde .aborted. Depois, o cancelamento é controle.abort().

11. Resumo

Cancelar um pedido é criar um AbortController, passar controle.signal nas opções do fetch e chamar controle.abort() quando não interessar mais. O pedido é interrompido na rede, a promessa é rejeitada e o erro chega ao catch com name igual a "AbortError" — que não deve virar mensagem de erro para o usuário.

O abort() aceita um motivo, que vira signal.reason e chega no erro. O motivo padrão é técnico e em inglês; definir o seu é o que permite mostrar "O cliente desistiu do pedido" em vez de "The user aborted a request". Para servidor lento, AbortSignal.timeout(ms) cria um sinal que se cancela sozinho, e o erro tem name "TimeoutError".

Três regras fecham a aula: um controle por pedido, criado onde o pedido nasce; um controle abortado não se reaproveita; e cancelar não é o mesmo que ignorar — só o abort() fecha a conexão. Na próxima aula, o que a tela mostra enquanto o pedido está no ar: estados de carregamento que não piscam nem mentem.

Para lembrar

  • new AbortController() cria o controle; .signal é o que vai no fetch.
  • abort() fecha a conexão e rejeita a promessa.
  • O erro tem name "AbortError": não é falha, é desistência.
  • abort(motivo) define signal.reason.
  • AbortSignal.timeout(ms) cancela sozinho, com "TimeoutError".
  • Um controle por pedido; depois de abortado, não serve mais.
  • Abortar duas vezes, ou depois do fim, não causa erro.
  • Cancelar economiza rede; ignorar só economiza estado.
